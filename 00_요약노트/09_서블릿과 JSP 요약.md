# 서블릿과 JSP 요약

자바로 **웹 서버 프로그램**을 만드는 방법이다. 서블릿으로 요청을 받고, JSP로 화면을 만들고, MVC로 둘을 분리하는 흐름을 따라가며 스프링이 왜 필요한지의 배경까지 이해한다.

## 1. 한눈에 보기

| 주제 | 핵심 |
|---|---|
| 톰캣과 서블릿 | 톰캣은 서블릿을 실행하는 서버(컨테이너), 서블릿은 요청을 받아 응답하는 자바 클래스 |
| 서블릿 생명주기 | 생성(init) → 요청마다 service(doGet, doPost) → 소멸(destroy) |
| 스프링과의 관계 | 스프링도 서블릿 위에 있다(디스패처 서블릿) |
| 빌드 도구 | Maven이 `pom.xml`로 의존성과 빌드를 관리한다. 표준 디렉토리 구조가 정해져 있다 |
| 어노테이션 매핑 | 수동 매핑(web.xml)의 한계 → `@WebServlet`. 톰캣이 리플렉션으로 읽어서 실행한다 |
| JSP | 서블릿으로 화면을 만들면 `out.println`이 고통스러워서 등장. 재스퍼가 JSP를 서블릿으로 바꿔 준다 |
| JSP 태그 | 스크립틀릿 `<% %>`, 표현식 `<%= %>`, 선언 `<%! %>` |
| MVC / 모델2 | 서블릿(제어)과 JSP(화면)를 분리한다. 모델1은 JSP가 다 한다 |
| 포워딩 | 컨트롤러에서 JSP로 요청을 넘긴다. View를 사용자가 직접 요청하지 못하게 한다 |
| 4가지 저장소 | page, request, session, application. 범위만 다르다 |
| EL | 저장소 값을 코드 블록 없이 꺼내는 표현식 `${...}` |

## 2. 개념 정리

### 2-1. 요청이 처리되는 과정

```
브라우저 → 톰캣 → 서블릿(service → doGet/doPost) → 응답
```

- 매핑 정보가 없으면 톰캣은 어느 서블릿을 호출할지 알 수 없다(404).
- HTTP 메서드(GET, POST)와 에러 코드를 구분해서 다룬다.

### 2-2. 모델2 구조

```
요청 → 서블릿(Controller: 처리, 모델 생성) → request에 담기 → forward → JSP(View: 출력)
```

- 서블릿은 데이터를 준비하고, JSP는 **출력만** 한다.
- 값을 넘기는 저장소를 `request`로 두면 요청 한 번 동안만 공유된다.
- 배열과 `size`를 따로 들고 다니는 불편함은 컬렉션(`ArrayList`)과 제네릭으로 해결한다.

### 2-3. 4가지 저장소

| 저장소 | 범위 |
|---|---|
| page | 해당 페이지 안 |
| request | 한 번의 요청 |
| session | 사용자 한 명 (세션 기간) |
| application | 서버 전체 |

- 이름이 같은 값이 여러 저장소에 있으면 좁은 범위(page → request → session → application) 순으로 찾는다.
- EL은 **지역변수를 쓸 수 없다.** 저장소에 담긴 값만 꺼낸다.
- `param`(사용자가 전달한 값), `header`(브라우저가 보내는 정보)도 EL로 읽는다.

## 3. 자주 헷갈리는 것

- **정적 문서 vs 동적 문서:** 서버가 요청이 올 때마다 만들어 내는 쪽이 동적 문서다.
- **JSP는 결국 서블릿이다.** 재스퍼가 서블릿으로 변환해 컴파일한다.
- **한글 깨짐:** 인코딩과 `Content-Type` 설정이 맞지 않을 때 생긴다.
- **라이브러리 하나가 아니라 의존성 트리가 따라온다.** Maven이 대신 받아 준다.

## 4. 이 카테고리의 실습과 참고자료

- 실습: Nginx 리버스 프록시, 서블릿 프로그램 만들기, Maven 기반 프로젝트, 인코딩과 Content-Type, JSP와 CSV 조회, 서블릿·JSP·리포지토리·JDBC 연동, 메뉴 등록(Create) 기능, systemd 서비스와 HTTPS 배포
- 참고자료: 포워딩과 request 속성, 클라우드와 가상 컴퓨터, 서블릿·HTTP API 메서드 체이닝
