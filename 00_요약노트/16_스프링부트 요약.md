# 스프링부트 요약

스프링은 **객체를 만들어 조립해 주는 DI 컨테이너**에서 출발했다. 이 카테고리는 스프링이 왜 필요했는지, 3계층 구조와 DI, 그리고 API와 DTO를 어떻게 설계하는지를 다룬다.

## 1. 한눈에 보기

| 주제 | 핵심 |
|---|---|
| 패러다임의 진화 | 절차적 → 구조적 → 객체지향 → 단일 책임 → DI → IoC 컨테이너 |
| 스프링의 정체성 | 객체를 생성·조립해 주는 DI 컨테이너. 이후 웹, JDBC, 보안 등으로 확장됐다 |
| 자바 EE와의 차이 | EJB는 무겁고 유료였다. 스프링은 무료 라이브러리로 같은 문제를 해결했다 |
| OCP와 DI | 수정 대신 확장한다. 확장해도 남는 "누가 연결하나"를 스프링이 대신한다 |
| IoC / 빈 | 객체 생성의 주도권이 개발자에서 프레임워크로 역전됐다. 컨테이너가 빈을 보관한다 |
| 3계층 | Controller(입출력) → Service(업무) → Repository(데이터 접근) |
| 스프링 부트 | 스타터로 라이브러리와 설정을 함께 제공해 설정 부담을 없앤다 |
| 빈 등록 | `@Component`와 특화된 `@Service`, `@Repository`, `@Controller` |
| DI 방식 | 필드 주입 대신 **생성자 주입** |
| 디스패처 서블릿 | 톰캣은 서블릿만 호출한다. POJO인 컨트롤러는 디스패처 서블릿(프론트 컨트롤러)을 거쳐 호출된다 |
| Entity와 DTO | Entity는 DB 원본, DTO는 화면이 원하는 형태 |
| 설정 파일 | `application.yml`, Gradle Kotlin DSL(`build.gradle.kts`) |

## 2. 개념 정리

### 2-1. 요청이 흐르는 길

```
요청 → Security/Filter → 디스패처 서블릿 → Controller → Service → Repository → DB
                                                  ↓
                                         View 또는 JSON 응답
```

### 2-2. 3계층의 역할과 이름 짓기

| 계층 | 역할 | 이름 규칙 |
|---|---|---|
| Controller | 사용자(원격 클라이언트)와의 입출력. 서빙 | 도메인명만 쓰고, 역할자는 폴더(패키지)로 구분 |
| Service | 여러 엔티티를 조합해 업무를 처리하고 모델을 만든다. 주방 | public 함수는 사용하는 쪽이 내리는 "명령어" |
| Repository | 저장소 접근을 대리한다. 재료상 | CRUD 함수만 제공. 조회 메서드는 `find…` 계열 |

- 계층은 **트리 구조**여야 한다. 같은 계층끼리 서로 호출하지 않는다.
- 인터페이스로 계층 사이를 약속하면 **병렬 개발**이 가능하다.

### 2-3. API 설계

| 판단 | 규칙 |
|---|---|
| API 개수 | 화면 컴포넌트(섹션) 수를 기준으로 하되, DB 관리가 필요 없는 정적 값은 제외 |
| URL 체계 | 페이지 URL과 API URL은 다르다. 버전은 `/api/v1/...`처럼 명시 |
| 주인공 / 곁다리 | 화면의 주인공 리소스를 최상위에, 곁다리는 그 뒤 하위 경로에 둔다 |
| 곁다리 공유 | 곁다리 API는 화면마다 따로 두고 공유하지 않는다 |
| 코로케이션 | **수정 시점이 같은 것끼리** 모은다 |
| 식별자 | SEO가 필요 없으면 ID, 필요하면 슬러그 |

### 2-4. DTO와 컨벤션

- DTO는 **유스케이스(화면) 단위**로 잘게 쪼갠다. `Request` / `Response`는 겹치지 않게 짓는다.
- 클래스 이름이 아니라 **폴더명**으로 구분한다.
- 쿼리 스트링(`@RequestParam`)은 "페이지의 상태 변수", JSON 본문(`@RequestBody`)은 등록·수정 데이터.
- CRUD와 HTTP 메서드: 개념적으로는 PATCH가 맞지만 실무에서는 PUT도 쓴다.
- 응답이 필요한지는 **화면 반영 여부**로 판단한다.

### 2-5. 컨트롤러 어노테이션

| | 반환 | 용도 |
|---|---|---|
| `@Controller` | 페이지 이름 | MVC 화면 |
| `@RestController` | 데이터(JSON) | REST API |

## 3. 자주 헷갈리는 것

- **IoC의 의미:** "내 할 일을 외부에 맡기는 것". 스프링 DI도 자바스크립트 콜백도 IoC다.
- **구현체 이름:** 공통분모(인터페이스명)는 뒤에 두고, 특화된 수식어는 앞에 붙인다.
- **Entity는 테이블 구조가 아니다.** 업무에서 다루는 데이터의 원본이다.
- 설정을 외우지 못하는 것은 실력과 무관하다. 어디를 보면 되는지가 중요하다.
- 규모가 커지면 헥사고날 같은 구조로 넘어간다. 이 카테고리는 기본 골격까지다.

## 4. 이 카테고리의 실습, 오답노트, 참고자료

- 실습: ncafe 프로젝트의 첫 API, PostgreSQL 연결과 JDBC Repository, 메뉴·카테고리 API와 DTO·DI, DI·IoC를 JAR로 직접 설치해 배우기, JdbcTemplate로 Menu API, 관리자 메뉴 CRUD 컨트롤러
- 오답노트: Controller와 RestController, 스프링 빈 등록 어노테이션, 전역 예외 처리
- 참고자료: 객체지향 관계와 의존성 주입(DI)의 본질
