# 객체지향 프로그래밍 요약

구조화로 코드를 잘라도 함수가 계속 늘어나면 다시 찾기 어렵다. 객체지향은 **데이터를 기준으로 함수를 묶어 캡슐을 만들고, 캡슐끼리 협력하게** 하는 방식이다.

## 1. 한눈에 보기

| 주제 | 핵심 |
|---|---|
| 전역변수의 문제 | 어디서든 바뀔 수 있어 책임이 흩어진다. 데이터와 서비스를 한 캡슐로 묶는다 |
| 캡슐화 | 데이터는 숨기고(은닉화) 서비스(메서드)만 공개한다. 사용하는 쪽은 데이터가 아니라 서비스에 관심을 둔다 |
| 오버로드 / 생성자 | 같은 이름, 다른 매개변수의 메서드 / 객체를 만들 때 초기화하는 특수한 메서드 |
| UI와 데이터 분리 | 변경 이유가 다른 책임은 캡슐을 나눈다(단일 책임) |
| HAS-A | 한 객체가 다른 객체를 가진다. Composition(직접 생성)과 Association(외부에서 주입) |
| DI | 필요한 부품을 외부에서 주입받아 결합력을 낮춘다 |
| IS-A (상속) | 부모의 기능을 물려받는다. HAS-A로 부족할 때 등장한다 |
| 오버라이드와 `super` | 부모의 메서드를 다시 구현한다. 생성자 체이닝으로 부모를 먼저 초기화한다 |
| 다형성 | 부모 타입으로 여러 자식을 일괄 관리한다. 업캐스팅은 항상 안전하다 |
| 추상 클래스 | 공통점만 추려 만든 틀. 객체로 만들 수 없고, 자식이 채워야 할 부분을 남긴다 |
| `protected` | 자식에게만 공개하는 보호 모드. 공통 로직 + 부분 위임 패턴에 쓴다 |
| 인터페이스 | 구현이 없는 순수한 약속. 구현체가 바뀌어도 사용하는 쪽이 깨지지 않는다 |
| 람다와 스트림 | 익명 클래스 → 람다식 → 메서드 레퍼런스. 함수형 인터페이스와 Stream API로 이어진다 |

## 2. 개념 정리

### 2-1. 구조화에서 객체지향으로 (성적 프로그램의 3단계)

| 단계 | 형태 | 한계 |
|---|---|---|
| 구조화 | 함수로 분리 | 함수가 많아지면 다시 찾기 어렵다 |
| 캡슐 | 데이터 + 함수를 클래스로 묶음 | UI와 업무가 한 캡슐에 섞인다 |
| 관계 | 책임별로 캡슐을 나누고 DI로 결합 | 상속, 인터페이스로 확장한다 |

### 2-2. 부품과 제품, HAS-A

- **부품**은 제품에 쓰이는 쪽, **제품**은 부품을 이용하는 쪽이다.
- 계산은 데이터를 가진 쪽의 책임이다. 필요한 값은 게터로 꺼내 가는 것이 아니라, 가진 쪽에 계산을 시킨다.
- 객체가 필요한 부품을 직접 만들면(Composition) 결합이 강해져 교체와 테스트가 어렵다. 외부에서 받으면(DI) 유연해진다.

### 2-3. 상속과 다형성

```java
Exam exam = new NewlecExam();   // 부모 타입 변수로 자식 객체를 가리킨다 (업캐스팅)
exam.total();                    // 실제로는 자식이 오버라이드한 total()이 실행된다
```

- 업캐스팅이 항상 안전한 이유: 자식은 부모의 구조를 모두 갖고 있기 때문이다.
- 부모-자식 관계가 아닌 것들을 묶고 싶으면 **추상 클래스**나 **인터페이스**로 공통 타입을 만든다.
- 자바의 가장 큰 추상화는 `Object`다. 다만 `Object`로 관리하면 꺼낼 때마다 형변환이 필요해 불편하다.

### 2-4. 추상 클래스와 인터페이스

| | 추상 클래스 | 인터페이스 |
|---|---|---|
| 성격 | 공통 구현과 틀을 가진 부모 | 구현이 없는 약속 |
| 객체 생성 | 불가 | 불가 |
| 예 | `Shape`(공통 타입) | `Comparator`, `MouseListener` |

- 추상 클래스로 공통 타입을 만들면 형변환 없이 쓸 수 있다.
- 인터페이스를 구현하기 번거로우면 어댑터 클래스, 익명 클래스, 람다식, 메서드 레퍼런스 순으로 간단해진다.

### 2-5. 람다식과 스트림

- **함수형 인터페이스:** 추상 메서드가 하나뿐인 인터페이스(`@FunctionalInterface`). 람다로 표현할 수 있다.
- **스트림 API:** 소스 → 중간 연산 → 최종 연산 구조로 컬렉션을 가공한다.

## 3. 자주 헷갈리는 것

- **오버로드 vs 오버라이드:** 오버로드는 같은 이름, 다른 매개변수. 오버라이드는 부모의 메서드를 자식이 다시 구현.
- `Shape s = new Shape();`는 추상 클래스를 생성하려는 시도라서 틀리고, `s.draw()`도 구현이 없어 틀리다.
- `onSave`는 `private`이면 자식이 못 쓰고, `public`이면 아무나 호출한다. 그래서 `protected`다.
- 라이브러리로 배포해도 소스는 숨겨지지 않는다(디컴파일 가능).
