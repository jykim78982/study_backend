# 개발 방법론 요약

개발을 **어떤 순서와 방식으로 진행할 것인가**를 다룬다. 고객의 두서없는 요구사항을 정리하는 방법과, 폭포수에서 애자일에 이르는 흐름이 중심이다.

## 1. 한눈에 보기

| 주제 | 핵심 |
|---|---|
| 요구사항 | 고객의 요구사항은 두서없이 온다. 정리하는 일이 분석이다 |
| 폭포수 모델 | 분석 → 설계 → 구현 → 테스트를 순서대로. 변경에 약하다 |
| 폭포수의 정체 | 원래는 문제점을 보여 주는 반면교사 사례로 소개됐다 |
| 나선형 모델 | 폭포수를 작게 반복한다 |
| 방법론의 계보 | RUP, XP, 스크럼 등이 나선형에서 갈라져 나왔다 |
| 애자일 선언 | 따로 놀던 방법론이 하나로 모인 철학. 가볍게, 자주 전달하고, 변화에 대응한다 |
| 유즈케이스 / 스토리 | 시스템이 사용자에게 주는 가치를 사용자 입장의 문장으로 쓴다 |
| 백로그 | 해야 할 일의 목록. 우선순위를 정한다 |

## 2. 개념 정리

### 2-1. 방법론이 남긴 것

| 개념 | 유래 | 실무에 남은 흔적 |
|---|---|---|
| 유즈케이스, UML | RUP | 요구사항을 스토리로 표현하는 방식의 뿌리 |
| TDD, 유저 스토리 | XP | 테스트 기반 개발, 스토리 단위 작업 |
| 스프린트, 백로그 | 스크럼 | 기간 단위 계획, 할 일 목록 관리 |
| 네 가지 가치, 열두 원칙 | 애자일 선언 | 가볍게, 자주 전달하고, 변화에 대응 |

애자일은 특정 방법론 하나의 이름이 아니라, 필요한 만큼만 가져다 쓰자는 **철학**이다.

### 2-2. 요구사항 분석의 흐름

```
고객의 말 → 시스템과 유즈케이스로 정리 → 스토리(백로그)로 쪼개기 → 우선순위 → 개발
```

- 예시로 카페 온라인 주문 시스템의 요구사항을 분석했다.

### 2-3. 개발 순서의 원칙

**페이지(URL)부터** 만들고, 콘텐츠는 직접 채우고, 스타일은 나중에 입힌다.

## 3. 자주 헷갈리는 것

- 폭포수는 "나쁜 방법론"이라기보다 **한계를 보여 주려고 소개된 모델**이다.
- 스프린트와 백로그라는 용어는 스크럼에서 왔지만, 지금은 방법론과 상관없이 실무 용어로 쓰인다.
