# 스프링 시큐리티와 인증 요약

**인증**(누구인가)과 **인가**(이 페이지를 받아도 되는가)를 다룬다. 서블릿 필터에서 시작해 쿠키와 세션, 스프링 시큐리티 설정, 그리고 JWT 토큰 인증까지 이어진다.

## 1. 한눈에 보기

| 주제 | 핵심 |
|---|---|
| 필터와 필터 체인 | 모든 요청이 서블릿에 가기 전에 거치는 입구. `chain.doFilter()`를 부르지 않으면 멈춘다 |
| 스프링 시큐리티 | 보안 필터를 만들어 둔 라이브러리. 스타터를 추가하면 모든 요청을 막는다 |
| `@Bean` | 소스가 없어 어노테이션을 못 붙이는 클래스의 객체를 IoC에 담는다 |
| UserDetails / Service | 사용자 정보와 그것을 제공하는 서비스. 인메모리, DB, 커스텀 세 가지 |
| POST와 리다이렉트 | POST는 페이지를 주지 않는다. `redirect:`로 다음 갈 곳을 안내한다 |
| 쿠키 | 서버가 브라우저에 맡기는 작은 데이터. 훔치면 사칭이 가능하다 |
| 세션 | 사용자 정보는 서버에, 세션 ID만 쿠키로. "기간"의 개념 |
| 인가 설정 | `SecurityFilterChain`으로 URL별 허용 규칙. 위에서부터 처음 걸린 것 하나만 적용 |
| 403 | 로그인은 했지만 권한이 없다 |
| 인증 방식의 변화 | 세션 → SAML(SSO) → OAuth 2.0 → JWT(토큰) |
| JWT | 헤더 . 페이로드 . 서명. 인코딩일 뿐 암호화가 아니다 |
| BFF | 모든 요청을 Next.js로 모아 백엔드를 숨기고, 토큰은 Next.js 서버가 보관한다 |
| JWT 인증 필터 | 추출 → 검증 → `SecurityContextHolder`에 등록 |
| 로그인 API | `AuthController` → `AuthService` → `AuthenticationManager` → `JwtProvider` |

## 2. 개념 정리

### 2-1. 로그인이 풀어 가는 단계

```
직접 구현 (인증 판별만)
   → 쿠키로 기억시키기 (위험)
   → 세션으로 기억시키기 (서버가 저장)
   → 필터로 모든 요청 검사 (곁다리 업무)
   → 스프링 시큐리티가 대신 해 주기
   → 토큰(JWT)으로 서버가 기억하지 않게 하기 (Stateless)
```

### 2-2. 인가 설정 예

```java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/login", "/css/**").permitAll()
    .requestMatchers("/admin/**").hasRole("ADMIN")
    .anyRequest().authenticated());
```

- 좁은 규칙(권한 필요)을 위로, 넓게 여는 규칙을 아래로 둔다.
- 정적 리소스도 열어야 화면이 깨지지 않는다.
- 역할자를 URL 앞에 두면(`/admin`, `/my`) 규칙이 깔끔해진다.

### 2-3. 세션과 JWT

| | 세션 | JWT |
|---|---|---|
| 인증 정보 위치 | 서버 | 토큰 안(클레임) |
| 요청마다 | 세션 ID로 저장소 조회 | 토큰 검증·해석 |
| 서버 상태 | Stateful | Stateless |
| 서버가 여럿일 때 | 세션 공유가 어렵다 | 그대로 쓸 수 있다 |
| 컨텍스트를 채우는 쪽 | 시큐리티가 자동으로 | 직접 만든 JWT 필터 |

서버 한 대가 인증·페이지·리소스를 다 맡으면 세션도 괜찮고, 역할이 나뉘면(Next.js + 스프링) 토큰이 맞다.

### 2-4. JWT 로그인 흐름

```
POST /api/auth/login
  → AuthController
  → AuthService: AuthenticationManager.authenticate()
        → DaoAuthenticationProvider (UserDetailsService + PasswordEncoder)
  → JwtProvider.createAccessToken()
  → LoginResponse(accessToken, "Bearer")

이후 요청: Authorization: Bearer <토큰>
  → JwtAuthenticationFilter (추출 → 검증 → 등록) → 인가 필터 → 컨트롤러
```

- `AuthenticationManager`는 인터페이스이고 JWT를 모른다. 검증이 끝나면 토큰은 우리가 만든다.
- `authenticate()`는 `SecurityContextHolder`에 담지 않는다. 담는 것은 요청마다 JWT 필터다.
- `AuthenticationManager` 빈은 `AuthenticationConfiguration`에서 꺼내 등록해야 한다.
- 토큰이 없거나 잘못돼도 필터는 막지 않고 컨텍스트를 비워 둔다. 막는 것은 뒤쪽 인가 단계다.

### 2-5. 인증 방식의 변화

| 단계 | 문제 | 해결 |
|---|---|---|
| 아이디/비밀번호 + 세션 | — | 서버가 세션에 상태 저장 |
| SAML 2.0 | 서버마다 로그인을 따로 해야 함 | 회사 안 IdP에 위임 (폐쇄형 SSO) |
| OAuth 2.0 / OIDC | 회사를 넘는 SSO 필요 | 구글·네이버 등이 인증 서버 공개 (개방형 SSO) |
| 프론트/백 분리 | 서버가 둘이라 세션 공유 어려움 | 토큰(JWT) |
| 백엔드 노출 | CSR이 API를 직접 부르려면 포트를 열어야 함 | BFF |

## 3. 자주 헷갈리는 것

- **JWT는 암호화가 아니라 서명**이다. 페이로드는 누구나 풀어 볼 수 있어서 비밀번호 같은 값은 넣지 않는다. 내용을 숨기려면 JWE.
- **세션은 저장소가 아니라 "기간"** 이다. 타임아웃 안에 다시 오지 않으면 지운다.
- **토큰은 누가 받나:** 브라우저가 직접 받는 구조와, Next.js 서버가 받아 세션이나 HttpOnly 쿠키로 보관하는 BFF 구조가 있다.
- **세션 고정 공격:** 로그인 성공 시 세션 ID를 바꿔 막는다. 기본 전략은 `changeSessionId`.
- **PRG 패턴:** POST 후 리다이렉트해서 새로고침 시 재전송을 막는다.
- 인증 정보가 없는 요청에 `AuthenticationEntryPoint`가 없으면 기본 응답은 403이다.

## 4. 이 카테고리의 실습, 오답노트, 참고자료

- 실습: 스프링 부트 JWT 인증 구현(JJWT, JwtProvider, 인증 필터, SecurityConfig, 로그인 API)
- 오답노트: 리다이렉트와 PRG 패턴, 스프링 시큐리티 세션 고정 방지, JWT 인증 필터
- 참고자료: 스프링 보안의 개념과 기술적 기반, 서블릿 필터와 보안 필터 체인, 컨트롤러로 로그인 직접 구현, 쿠키, 세션 로그인과 로그아웃, JDBC 기반 인증, 커스텀 UserDetails
- 남은 학습: 리프레시 토큰, 로그아웃, `AuthenticationEntryPoint` / `AccessDeniedHandler`, DB 기반 `UserDetailsService`
