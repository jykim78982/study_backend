# 자바스크립트 플랫폼의 진화 — DOM API에서 jQuery, MVC, React(Flux)까지

## 1. 페이지 요청 기반 웹의 한계와 AJAX의 등장

웹의 기본 요청 단위는 원래 "페이지"다 — 링크를 클릭하면 새 페이지를 통째로 요청하고, 서버가 이를 내려주면 화면이 전부 다시 로드된다. 문제는 이렇게 페이지가 리로드되면 그 순간까지 유지되고 있던 상태(예: 재생 중이던 음악)가 전부 끊긴다는 점이다. 과거 싸이월드는 이 문제를 피하기 위해 `<iframe>`으로 페이지를 여러 조각으로 쪼개, 특정 영역만 다시 로드되고 나머지(배경음악 등)는 유지되도록 하는 편법을 썼다.

이후 브라우저에 자바스크립트가 직접 서버에 GET/POST 요청을 보낼 수 있는 기능(AJAX)이 탑재되면서 상황이 바뀐다. 이제는 페이지 전체가 아니라 필요한 데이터만 비동기로 받아와서, 자바스크립트가 DOM의 일부만 바꾸는 방식이 가능해졌다 — 화면은 그대로 유지된 채 데이터만 갱신되는 것이다.

## 2. 팻 클라이언트(Fat Client)와 SPA

원래 문서(화면)를 만드는 역할은 서버의 몫이었다. 그런데 AJAX 이후 "화면 일부를 바꾸는 정도라면 서버에 다시 만들어 달라고 요청할 필요 없이 자바스크립트가 직접 만들면 되겠다"는 흐름이 생기면서, 화면을 만드는 역할이 점점 서버에서 클라이언트(자바스크립트) 쪽으로 옮겨간다. 이렇게 클라이언트 쪽 코드가 점점 무거워지는 현상을 **팻 클라이언트(Fat Client)**라 부른다.

이 흐름이 극단까지 가면, 서버는 거의 빈 HTML 한 장(사실상 자바스크립트 파일을 실어 나르기 위한 용도)만 내려주고, 화면을 만드는 모든 로직은 전부 클라이언트의 자바스크립트가 담당하게 된다. 여러 페이지를 서버에 요청하던 방식(다중 페이지 애플리케이션) 대신, 페이지 요청은 처음 한 번만 하고 이후 모든 화면 전환은 자바스크립트가 처리하는 방식 — 이것이 **SPA(Single Page Application)**의 개념이다.

## 3. DOM 반복 작업의 고통과 MVC의 등장

Google의 한 개발자가 웹 기반 GUI(예: 피드백 입력창)를 순수 자바스크립트와 DOM API만으로 구현하면서 심각한 문제를 겪는다. `getElementById` 같은 DOM 접근·조작 코드가 전체 코드의 대부분을 차지하고, 정작 "실제로 하고 싶은 업무 로직"은 코드 전체에서 극히 일부였다는 것이다. 실제로 그가 만든 피드백 창 하나에 17,000줄의 코드가 필요했다고 한다.

이 문제를 해결하기 위해 그는 직접 라이브러리를 만들어 같은 기능을 1,500줄로 줄였고, 이를 사내에 공개해 큰 반향을 일으킨 뒤 외부에도 공개했다. 핵심 아이디어는 DOM 접근·조작 코드를 라이브러리 뒤로 완전히 숨기고, 개발자는 오직 **데이터(모델)**만 준비하면 되도록 만드는 것이었다.

이 방법론의 뿌리는 1960년대 Smalltalk 언어 시절 만들어진 **MVC(Model-View-Controller)** 패턴이다. 핵심은 모델을 중심에 두고, 모델이 바뀌면 화면(뷰)이 자동으로 갱신되도록 하며, 화면 쪽에서는 처리 로직(컨트롤러)을 걷어내 여러 화면이 같은 모델을 공유하도록 만드는 것 — 이렇게 하면 여러 화면 간 데이터 공유 문제가 자연스럽게 해결된다. MVC 계열은 구현 세부 방식에 따라 MVP, MVVM 등 다양한 이름으로 불리기도 하지만, "모델을 화면에 바인딩해서 로직과 뷰를 분리한다"는 핵심 개념은 모두 동일하다.

이 개발자가 만든 라이브러리는 이후 **AngularJS**라는 이름을 갖게 된다.

## 4. Angular의 흥망과 Vue, React의 등장

AngularJS(1.x)는 순수 자바스크립트·DOM 지식만으로 코드량을 획기적으로 줄여줬고, 등장과 동시에 폭발적인 인기를 얻었다. 그러나 이후 "Angular"(이름에서 JS가 빠진 2.0)로 넘어가면서 큰 변화가 일어난다. 성능이 크게 개선되고 웹뿐 아니라 앱·데스크톱까지 아우르는 멀티플랫폼을 지향했지만, 그 대가로 이전 버전과 호환되지 않는 사실상 완전히 새로운 언어·플랫폼이 되어버렸다.

| | AngularJS | Angular2+ |
|---|---|---|
| 공통 학습 내용 | JavaScript + DOM | JavaScript + DOM |
| 추가로 배워야 할 것 | (없음) | Node.js, ES2015 이상, TypeScript |

AngularJS는 자바스크립트·DOM 지식 위에 AngularJS 자체만 얹으면 됐지만, Angular2부터는 그 위에 Node.js·최신 자바스크립트 문법(ES2015+)·TypeScript까지 먼저 알아야 Angular를 배울 수 있는 구조가 되어, 학습량이 훨씬 늘어났다. 이 진입 장벽 때문에 많은 개발자들이 대체재를 찾기 시작한다.

이때 선택지로 떠오른 것이 Vue와 React다. Vue는 개인 개발자가 만든 라이브러리로 기술적으로 우수하다는 평가를 받았지만, 거대 빅테크가 아닌 개인이 만든 프로젝트라는 점 때문에 상대적으로 채택이 저조했다. 반면 React는 페이스북(현 메타)이라는 거대 빅테크가 만들었고, 실제로 자사 서비스(페이스북)에 쓰고 있다는 신뢰가 크게 작용해 압도적인 채택을 이끌어냈다. 즉 React가 널리 쓰이게 된 데에는 기술적 우수성 외에 "누가 만들고 실제로 쓰고 있는가"라는 신뢰 요인도 크게 작용했다.

실제 사용률 추이를 보면 2016년 이후 Angular의 점유율은 계속 하락한 반면, 2017년 무렵부터 React(페이스북이 만듦)가 빠르게 치고 올라왔고, 2018~2019년 무렵에는 Vue도 함께 성장했다 — 이후 프론트엔드 프레임워크 시장은 사실상 React·Vue·Angular 세 진영으로 재편된다.

## 5. MVC 체감하기 — 양방향 데이터 바인딩

MVC 라이브러리를 쓰면 DOM을 몰라도 되는지 직접 확인하기 위해, 온전히 MVC 원형을 유지하고 있는 Vue.js로 간단한 덧셈 계산기를 만들어본다.

```html
<section id="calc">
    <input :value="x">
    <input v-model="y">
    <input type="button" value="계산하기" v-on:click.prevent="calcHandler">
    <span>{{ z }}</span>
</section>
<!-- v-on:click은 @click으로 줄여 쓸 수도 있다 -->

<script src="https://unpkg.com/vue@3/dist/vue.global.js"></script>
<script>
const app = Vue.createApp({
    data() {
        return { x: 3, y: 4, z: 0 };
    },
    methods: {
        calcHandler() {
            this.z = Number(this.x) + Number(this.y);
        }
    }
});
app.mount("#calc");
</script>
```

- `Vue.createApp({...}).mount("#calc")`: `#calc` 영역을 대상으로 애플리케이션을 시작한다. 이제부터 이 영역 안에서는 `document.querySelector` 같은 DOM 접근 코드를 전혀 쓰지 않는다.
- `data()`가 반환하는 객체가 곧 **모델**이다. 여기서 정의한 `x`, `y`, `z` 값을 화면에 연결(바인딩)하기만 하면, 값이 바뀔 때 화면이 자동으로 갱신된다.
- `:value="x"`(= `v-bind:value`)처럼 콜론(`:`)이 붙은 속성은 모델 값을 화면에 그대로 반영하는 **읽기 전용(단방향) 바인딩**이다. `value` 속성 자체는 원래 사용자 입력을 받을 수 있는 속성이지만, `:value`로 바인딩하면 그 입력을 다시 모델로 되돌려 반영해주지는 않는다.
- 사용자 입력을 다시 모델에 반영해야 하는 경우(**양방향 바인딩**)에는 `v-model`을 쓴다. `v-model="y"`로 바인딩하면 사용자가 입력창에 값을 바꿀 때 모델 `y`도 함께 바뀌고, 반대로 `y`를 코드로 바꾸면 입력창도 함께 바뀐다.
- 태그의 속성이 아닌 일반 텍스트 위치에 모델 값을 꽂아 넣을 때는 중괄호를 두 번 겹쳐 쓴 `{{ }}`를 쓴다. `{{ z }}`라고 쓰면 `z`의 현재 값이 그 자리에 그대로 렌더링된다.
- `v-on:click`(= `@click`)으로 클릭 시 실행할 메서드를 지정한다. 이때 `<input type="button">`이나 `<form>` 등 브라우저가 기본으로 갖고 있는 **기본 행위**(폼 전송, 페이지 새로고침 등)를 막으려면, `event.preventDefault()`를 직접 호출하는게 아니라 `.prevent`라는 수식어(modifier)만 붙이면 된다(`v-on:click.prevent="..."`) — 이벤트 객체를 몰라도 되는 것이 MVC 라이브러리의 핵심 목적이기 때문이다.
- `methods`에 정의한 함수 안에서는 `this.모델명`으로 현재 모델 값에 접근·수정할 수 있다.
- `v-model`로 받은 입력값도 순수 DOM의 `input.value`와 마찬가지로 기본적으로 모두 문자열이라서, `x + y`를 그대로 쓰면 문자열 결합이 된다. `Number(x)`로 변환해도 되지만, `v-model.number="y"`처럼 `.number` 수식어를 붙이면 라이브러리가 자동으로 숫자로 변환해준다.

이처럼 MVC 라이브러리를 쓰면 `document` 객체를 얻어오는 코드도, 이벤트 객체를 직접 다루는 코드도 필요 없어지고, 오직 모델을 준비하고 그 모델을 화면 어디에 연결할지만 신경 쓰면 된다.

정리하면 Vue의 코드 구조는 **모델(Model)**, **화면(View)**, 그리고 `methods` 안의 함수들이 맡는 **컨트롤러(Controller)** 역할로 나뉜다. 컨트롤러는 사용자 조작(클릭 등)에 반응해 모델을 갱신하고, 모델→화면 방향은 `:value`처럼 **1-Way Binding**(모델이 바뀌면 화면에 반영되지만 화면에서 되돌아오지는 않음)으로, 화면↔모델 양방향은 `v-model`처럼 **2-Way Binding**(양쪽 중 어디를 바꿔도 서로 반영됨)으로 연결된다는 것이 이 실습의 핵심이다.

## 6. Flux — 왜 React는 양방향 바인딩을 버렸나

페이스북 개발자들은 MVC의 양방향 바인딩이 애플리케이션 규모가 커질수록 오히려 문제가 된다고 진단했다. 화면(뷰)과 모델이 여러 개로 늘어나고 서로 관계를 맺기 시작하면, 어떤 모델의 변경이 다른 모델을 연쇄적으로 바꾸고, 그 변경이 다시 앞의 모델에 영향을 주는 식으로 **변경의 흐름이 순환하거나 뒤엉켜서 추적하기 어려워진다**. 특히 모델을 바꾸는 주체가 사용자 입력만이 아니라 외부(실시간 채팅, 외부 API 응답 등)에서도 들어올 수 있다는 점이 이 복잡도를 더 키운다 — 여러 화면이 하나의 모델을 동시에 바라보고 있을 때, 어떤 변경이 어떤 순서로 도착했는지 알기 어려워지는 것이다.

이 문제에 대한 해결책이 데이터 흐름을 양방향이 아니라 **단방향(one-way)**으로 강제하는 것이다. Flux의 데이터 흐름은 다음 네 단계를 한 방향으로만 거친다.

```
Action → Dispatcher → Store → View
              ↑                 │
              └──── Action ─────┘
```

- **Action**: 사용자 입력이나 외부 이벤트를 계기로 "무엇이 일어났는지"를 표현하는 객체. 예전 순수 DOM 방식의 이벤트 핸들러가 하던 역할과 비슷하다.
- **Dispatcher**: 모든 Action이 반드시 거쳐가는 중앙 관문. Action을 받아 그것이 필요한 Store로 전달하는 역할만 하고, 그 자체에 로직을 담지 않는다.
- **Store**(Flux에서 "모델"을 부르는 이름): Dispatcher로부터 전달받은 Action에 따라 실제 데이터(상태)를 갱신한다.
- **View**: Store의 변경 사항을 반영해 화면을 그린다. 사용자가 View를 조작하면 그 결과는 모델을 직접 바꾸는 게 아니라, 다시 새로운 **Action**을 만들어 Dispatcher로 보내는 것으로 시작된다 — 즉 View에서 Store로 곧장 되돌아가는 경로 자체가 없고, 항상 Action → Dispatcher → Store를 다시 거쳐야 한다.

굳이 "모델" 대신 "Store"라는 이름을 쓰는 이유는, 짧은 시간 안에 값이 연속으로 여러 번 바뀌어도 그때마다 매번 화면을 다시 그리지 않고, 변경 내역을 버퍼처럼 모아뒀다가 한 번에 반영해 성능을 높이는 개념까지 포함하기 때문이다. 이렇게 데이터를 한 방향으로만 흘려보내는 방법론을 **Flux**라 하고, 리액트는 이 Flux 방법론을 채택했다.

이 단방향 원칙은 `<input>` 같은 입력 요소에서 가장 분명하게 드러난다. React에서 `value`만 지정하고 아무 이벤트 핸들러도 달지 않으면, 사용자가 그 입력창에 값을 바꾸려고 해도 전혀 바뀌지 않는다 — `value`가 항상 상태(모델) 값으로 고정되어버리기 때문이다(이런 입력 요소를 **제어 컴포넌트**라 부른다). 값을 바꾸려면 `onChange` 핸들러 안에서 상태를 직접 갱신해야 한다.

```jsx
<input
    value={x}
    onChange={(event) => setX(event.target.value)}
/>
```

Vue의 `v-model`이 "사용자 입력 → 모델 반영"을 자동으로 해주는 것과 달리, React는 이 연결 자체를 개발자가 `onChange`로 직접 작성해야 한다 — 이것이 "React는 단방향 바인딩만 지원한다"는 말의 실제 의미다. `setX`(상태 갱신 함수, `useState`로 만든다)를 호출하면 그 갱신된 상태를 기준으로 화면이 다시 렌더링된다.

## 7. React의 핵심 — 가상 DOM과 렌더링

리액트가 제공하는 가장 기본적인 기능은 "무엇을, 어디에 렌더링할 것인가"이다.

```js
const app = document.querySelector("#calc-app");

ReactDOM.render("Hello React JS", app);
```

여기서 중요한 점은, 리액트가 다루는 대상은 브라우저의 진짜(Real) DOM이 아니라 **리액트 자신의 가상 DOM(Virtual DOM)**이라는 것이다. Vue 같은 다른 라이브러리는 가상 DOM 개념을 실제 DOM과 거의 완벽히 호환되게 감춰서, 사용자가 그 차이를 의식하지 않고도 쓸 수 있게 만든다. 반면 리액트는 이 가상 DOM이라는 개념 자체를 사용자에게 그대로 드러낸다는 차이가 있다.

단순한 문자열을 렌더링하면 지정한 영역의 내용을 그 문자열로 통째로 덮어쓴다. 하지만 태그를 포함한 내용을 넣고 싶을 때, 문자열 안에 태그를 그대로 적으면 오류가 난다 — 리액트가 기대하는 두 번째 인자는 문자열이 아니라 **가상 DOM 엘리먼트 객체**이기 때문이다. 이를 위해 `React.createElement(태그명, 속성, 내용)` 형태로 가상 DOM 엘리먼트를 직접 만들어 넘겨야 한다.

```js
const h1 = React.createElement("h1", null, "Hello world");
ReactDOM.render(h1, app);
```

매번 `createElement`를 이렇게 직접 호출하는 방식은 태그가 복잡해질수록 코드가 읽기 어려워진다. 이 문제를 해결하기 위해 등장하는 것이 HTML 태그처럼 보이는 문법을 그대로 쓸 수 있게 해주는 **JSX** 문법이다 — JSX는 결국 `createElement` 호출을 사람이 읽기 쉬운 태그 형태로 대신 써주는 문법일 뿐이며, 브라우저가 직접 이해할 수 있는 문법이 아니라서 별도의 변환(트랜스파일) 과정이 필요하다.

## 8. 참고 — CDN과 npm

라이브러리를 실제 프로젝트에 가져오는 방법은 크게 두 가지다.

- **npm(npmjs.com)**: 자바스크립트 라이브러리들을 모아놓은 저장소(자바의 Maven 저장소에 대응). Node.js 환경에서 다음처럼 설치해서 쓴다.

```
npm install react react-dom
```
- **CDN(Content Delivery Network)**: 전 세계 여러 지역에 라이브러리 파일의 복사본(미러)을 분산 배치해두는 네트워크. `<script src="https://...">`로 URL만 지정하면 별도 설치 없이 바로 가져다 쓸 수 있다. 서버가 하나뿐이면 물리적으로 먼 지역에서는 응답이 느리거나 서버 장애 시 아예 받아올 수 없는 문제가 있는데, CDN은 같은 파일을 여러 지역 서버에 복제해두어 사용자와 가장 가까운(혹은 살아있는) 서버가 응답하도록 해 이 문제를 해결한다.

React를 CDN(예: unpkg.com)으로 가져올 때는 `React`와 `ReactDOM` 두 라이브러리를 함께 실어야 한다.

```html
<!-- 개발용(오류 메시지·경고 포함) -->
<script crossorigin src="https://unpkg.com/react@17/umd/react.development.js"></script>
<script crossorigin src="https://unpkg.com/react-dom@17/umd/react-dom.development.js"></script>

<!-- 배포용(경량화) -->
<script crossorigin src="https://unpkg.com/react@17/umd/react.production.min.js"></script>
<script crossorigin src="https://unpkg.com/react-dom@17/umd/react-dom.production.min.js"></script>
```

URL의 `@17`처럼 버전을 명시해서 가져오는 것이 안전하다 — 새 버전은 API나 문법이 크게 바뀌었을 수 있으므로, 학습·실습 시에는 17 이하의 안정적인 버전을 지정하는 것이 권장된다. `development.js`는 오류 메시지와 경고를 자세히 보여줘 개발 중에 쓰고, `production.min.js`는 코드가 압축(minify)되어 실제 배포 시 사용한다. `crossorigin` 속성은 다른 출처(origin)의 CDN에서 스크립트를 가져올 때 오류 메시지를 온전히 받아보기 위해 붙인다.

## 9. 중첩된 가상 DOM 만들기 — `createElement`의 한계

`h1` 안에 `span`을 넣는 것처럼 태그를 중첩시키고 싶을 때는, 문자열 안에 태그를 직접 적으면 안 된다 — `React.createElement`가 세 번째 인자(자식 내용)로 기대하는 것은 문자열이 아니라 또 다른 가상 DOM 엘리먼트이기 때문이다. 그래서 자식 태그도 각각 `createElement`로 따로 만들어서 넘겨야 한다.

```js
const span = React.createElement(
    "span",
    { style: { color: "red" } },
    "Hello React"
);
const h1 = React.createElement("h1", null, span);
ReactDOM.render(h1, app);
```

여기서 두 가지를 눈여겨봐야 한다.

- 태그가 중첩될 때마다 `createElement` 호출도 함께 중첩된다 — 태그 구조가 복잡해질수록 이 방식은 코드가 급격히 읽기 어려워진다.
- 두 번째 인자(속성)에 `style`을 줄 때, `style="color: red"`처럼 문자열로 쓰는 HTML 방식이 아니라 `{ style: { color: "red" } }`처럼 **자바스크립트 객체**로 써야 한다. 이는 가상 DOM이 실제로는 HTML 문자열이 아니라 자바스크립트 객체 트리이기 때문이다.

## 10. Babel — 원래 리액트와 무관했던 트랜스파일러

이 `createElement` 중첩 문제를 해결해준 것이 **Babel**이다. 다만 Babel은 원래 리액트와 아무 관계가 없었다.

자바스크립트 문법이 크게 개편된 ES6(ES2015) 시점, 최신 문법으로 코드를 작성하고 싶어도 구형 브라우저(예: 인터넷 익스플로러)가 이를 지원하지 않는 문제가 있었다. Babel은 이 문제를 해결하기 위해 등장한 **트랜스파일러**다 — 최신 문법으로 작성된 코드를, 구형 브라우저도 이해할 수 있는 하위 버전 문법으로 자동 변환(다운그레이드)해준다. 개발자는 최신 문법을 그대로 쓰고, 실행 전에 Babel이 알아서 호환되는 코드로 바꿔주는 것이다.

이후 Babel 팀은 리액트 진영과 협업하면서, 이 변환 능력에 한 가지 기능을 추가한다 — HTML 태그처럼 보이는 문법을 그대로 쓰면, 이를 `React.createElement(...)` 호출로 자동 변환해주는 기능이다. 이렇게 태그 형태로 가상 DOM을 작성할 수 있게 해주는 문법이 **JSX**다.

```html
<script src="https://unpkg.com/react@17/umd/react.development.js"></script>
<script src="https://unpkg.com/react-dom@17/umd/react-dom.development.js"></script>
<script src="https://unpkg.com/@babel/standalone/babel.min.js"></script>

<script type="text/babel">
    const h1 = <h1><span style={{ color: "red" }}>Hello Babel</span></h1>;
    ReactDOM.render(h1, document.getElementById("root"));
</script>
```

`<script>`에 `type="text/babel"`을 지정해야 Babel이 "이 블록은 내가 번역해야 할 코드"라고 인식한다. 이 표시가 없으면 브라우저가 이 코드를 직접 자바스크립트로 실행하려다 태그 문법에서 그대로 오류를 낸다.

## 11. JSX는 HTML이 아니다 — 문법적으로 지켜야 할 것들

JSX(JavaScript + XML)로 작성한 코드는 겉보기엔 HTML 같지만 실제로는 전혀 다른 규칙을 따른다.

- **완결성(Well-formed) 규칙**: JSX는 XML 문법을 기반으로 하므로, 열었으면 반드시 닫혀야 한다. HTML에서는 `<br>`, `<input>`처럼 닫지 않아도 되는 태그가 있지만, JSX에서는 이런 태그도 `<br />`, `<input />`처럼 자기 자신을 닫는 표기를 반드시 붙여야 한다.
- **속성 값은 자바스크립트 문법을 따른다**: `style` 속성처럼 HTML에서는 문자열(`style="color:red"`)로 쓰던 것을, JSX에서는 중괄호로 감싼 자바스크립트 표현식(`style={{ color: "red" }}`)으로 써야 한다. 안쪽의 `{ color: "red" }`는 실제 자바스크립트 객체이고, 바깥의 중괄호는 "여기부터는 자바스크립트 표현식을 쓰겠다"는 JSX 고유의 표시다.
- **예약어와 겹치는 속성은 이름이 바뀐다**: HTML의 `class` 속성은 자바스크립트의 예약어(`class` 선언 키워드)와 이름이 겹치기 때문에, JSX에서는 대신 `className`을 쓴다(`<h1 className="title">`). HTML 표기법을 자바스크립트 쪽 문법 제약에 맞춰 순화해서 쓰는 사례라는 점에서, 앞서 다룬 `id`·`style` 속성 표기 문제와 같은 종류의 제약이다.
- **HTML 지식을 그대로 옮기면 오류가 난다**: JSX는 HTML을 흉내 낸 새로운 문법이지, HTML 자체가 아니다. 웹 퍼블리셔가 만든 순수 HTML 코드를 그대로 복사해 붙여넣으면, 속성 표기 방식 차이 때문에 대부분 수정이 필요하다.

지금 작성하고 있는 코드는 엄밀히 말해 **순수 자바스크립트가 아니라, Babel이 이해하는 확장 문법(속칭 "바벨 스크립트")**이다. 이 문법은 표준 자바스크립트 문법을 대부분(약 90%) 포함하지만, JSX처럼 표준 자바스크립트에는 없는 문법도 섞여 있어서 브라우저가 직접 실행할 수 없고 반드시 Babel의 변환을 거쳐야 한다.

## 12. 리액트의 기본 구조 — 마운트와 컴포넌트 분리

리액트 애플리케이션의 HTML은 대개 다음처럼 텅 빈 상태로 시작한다.

```html
<body>
    <div id="root"></div>
    <script type="text/babel">
        const h1 = <h1>Hello React</h1>;
        ReactDOM.render(h1, document.getElementById("root"));
    </script>
</body>
```

`#root`는 처음엔 비어 있는 컨테이너일 뿐이고, JSX로 만든 내용을 여기에 렌더링해 넣는 것이 전부다. 이렇게 문서 트리(DOM)의 한 지점에 새로운 노드 뭉치가 연결되는 것을 **마운트(Mount)**라 부른다 — 리눅스에서 저장 장치를 디렉터리 트리의 한 지점에 연결하는 것을 마운트라 부르는 것과 같은 비유다. 마운트가 되기 전까지는 화면에 아무것도 나타나지 않고, 마운트된 순간 비로소 화면에 그려지는(렌더링되는) 것이다.

JSX 내용이 복잡해지면, 이를 변수에 담아 분리해서 쓸 수 있다.

```js
const calc = (
    <div>
        <input value={x} />
        <input value={y} />
        <input type="button" value="계산하기" />
    </div>
);
ReactDOM.render(calc, document.getElementById("root"));
```

더 나아가 Babel은 **함수를 태그처럼 쓸 수 있는 기능**도 제공한다 — 대문자로 시작하는 태그 이름을 만나면, Babel은 이를 같은 이름의 함수 호출로 해석한다.

```js
function Calc() {
    return (
        <div>
            <input value={x} />
            <input value={y} />
        </div>
    );
}

const app = <Calc />;
ReactDOM.render(app, document.getElementById("root"));
```

리액트의 핵심 철학은 단순함이다 — "무엇을, 어디에 렌더링할 것인가"라는 한 가지 개념만 있을 뿐이며, 코드가 복잡하게 느껴진다면 뭔가 잘못 만들고 있다는 신호로 봐야 한다. 화면이 복잡해지면, 함수를 잘게 나누듯이 컴포넌트를 계속 더 작은 함수로 쪼개서 계층적으로 조립해나가는 것이 리액트의 기본적인 해결 방식이다.

## 13. 참고 — 기술적 우수성과 인기는 별개다

리액트의 확산 과정을 냉정하게 짚어볼 필요가 있다. 리액트는 실제 벤치마크상 다른 라이브러리보다 빠르다고 단정하기 어렵다 — 가상 DOM을 만드는 오버헤드, 그리고 (Babel을 쓰는 구성이라면) 브라우저에서 JSX를 자바스크립트로 번역하는 추가 비용까지 있기 때문이다. 실제로 리액트를 선택한 이유를 물었을 때 "속도가 빠르다", "생산성이 높다" 정도로만 답하고 다른 프레임워크와 실제로 비교해본 적은 없는 경우가 많다는 지적도 있다.

이런 정황을 보면, 리액트의 압도적인 채택에는 순수한 기술적 우수성 못지않게 **생태계 효과**가 크게 작용했다고 볼 수 있다 — 페이스북(현 메타)이 만들고 자사 서비스에 실제로 쓰고 있다는 신뢰, 애플 개발자 생태계와 맞물린 문화적 친화력, 그리고 한번 다수가 채택하면 관련 자료·라이브러리·채용 공고가 더 많이 쌓이는 선순환(네트워크 효과)이 맞물린 결과라는 것이다. AI 코드 생성 도구들이 리액트 코드를 유독 잘 작성하는 것도, 학습 데이터에 리액트 코드 사례 자체가 압도적으로 많이 쌓여 있기 때문이라는 해석이 가능하다.

## 14. 번들링 — 브라우저에서 매번 번역하는 비용을 없애기

지금까지의 방식은 브라우저가 리액트·리액트 DOM·Babel 라이브러리를 각각 내려받고, 그 안에서 JSX가 섞인 코드를 매번 실시간으로 번역한 뒤에야 실행할 수 있었다. 애플리케이션이 여러 파일·여러 라이브러리로 커질수록 이 방식은 심각한 성능 문제를 만든다 — 파일마다 별도로 다운로드해야 하고, 다운로드가 끝난 뒤에도 브라우저 안에서 번역까지 거쳐야 실행이 시작되기 때문이다.

이 문제의 해결책이 **번들링(Bundling)**이다.

- 여러 개의 파일을 하나로 합쳐서, 다운로드 요청 횟수를 줄인다.
- Babel 변환(JSX → `createElement`)을 브라우저가 아니라 **미리(빌드 시점에)** 끝내둔다 — 브라우저는 이미 순수 자바스크립트로 번역된 코드만 받으면 된다.
- 공백·줄바꿈 제거, 긴 식별자 축약 등으로 파일 용량을 최소화하는 **압축(Minify)**까지 함께 적용한다.
- 처음 화면에 당장 필요 없는 코드는 나중에 실제로 필요해지는 시점에 따로 내려받게 나누는 **코드 분할(Code Splitting)**까지 적용하면, 첫 로딩에 포함되는 번들 크기를 더 줄일 수 있다.

이런 번들링 작업을 처리해줄 전용 도구가 필요한데, 이 도구는 특정 OS나 다른 언어 런타임(JDK 등)에 의존하지 않고 순수하게 자바스크립트 개발자의 도구여야 자연스럽다. 이 필요에 정확히 들어맞는 실행 환경이 바로 **Node.js**다 — 번들링 도구, 컴파일 과정, 심지어 개발용 웹 서버까지 모두 Node.js 위에서 자바스크립트로 돌아가게 된다.

## 15. Node.js의 탄생 — 브라우저 밖에서 실행되는 자바스크립트

자바스크립트는 원래 HTML 없이는 존재 이유가 없는 언어였다 — 자바스크립트 코드는 HTML 문서 안에 실려서만 브라우저에 전달되고, 그 코드를 실제로 실행하는 것은 언제나 브라우저였다. 즉 자바스크립트를 실행하려면 반드시 "HTML이라는 배"에 태워 "브라우저"라는 목적지로 보내야 했다.

이 전제를 깬 것이 Node.js다. 여기에는 구글이 크롬 브라우저를 위해 만든 자바스크립트 실행 엔진 **V8**이 결정적인 역할을 한다. V8은 성능을 위해 완전히 새로 만들어진 엔진이었는데, 특이하게도 브라우저와 일체형이 아니라 **브라우저에서 분리해서 쓸 수 있는 구조**로 설계되었다. 라이언 달(Ryan Dahl)은 이 분리 가능한 V8 엔진에 콘솔(터미널) 껍데기를 씌워, 브라우저 없이도 자바스크립트를 실행할 수 있는 새로운 실행 환경을 만들었다 — 이것이 Node.js다.

Node.js는 자바(JVM)나 닷넷(.NET) 같은 기존 언어 실행 환경과 같은 위치에 서게 된다 — 다만 실행되는 언어가 자바스크립트라는 점이 다르다. 이제 자바스크립트는 브라우저의 DOM만 다루던 언어에서 벗어나, 콘솔·파일 시스템·네트워크 소켓 등 운영체제가 제공하는 다양한 자원을 직접 다룰 수 있는 범용 언어로 확장된다.

| 구분 | 브라우저 자바스크립트 | Node.js 자바스크립트 |
|---|---|---|
| 실행 위치 | 브라우저 내부 | 운영체제 위의 런타임 |
| 주요 API | DOM, 브라우저 API | 파일, 네트워크, 프로세스 API |
| 대표 활용 | UI, 사용자 상호작용 | 서버, 빌드, 번들링, 자동화 도구 |
| DOM 접근 | 가능 | 기본적으로 DOM이 존재하지 않음 |

## 16. 프로세스와 스레드 — Node.js의 동시성 논쟁을 이해하기 위한 배경

Node.js가 내세우는 차별점을 이해하려면 먼저 프로세스와 스레드의 관계를 짚어야 한다.

| 개념 | 설명 |
|---|---|
| 프로그램 | 저장장치에 존재하는 실행 가능한 파일 |
| 프로세스 | 메모리에 로드되어 실행 중인 프로그램 인스턴스 |
| 스레드 | 프로세스 내부에서 실행 흐름을 나눈 단위 |
| 컨텍스트 스위칭 | 실행 상태를 저장하고 다른 실행 단위로 전환하는 과정 |

- 디스크에 저장된 실행 파일을 셸(터미널, 파일 탐색기 등)을 통해 실행하면, 운영체제가 이를 메모리에 적재한다 — 이렇게 적재되어 실행 중인 상태를 **프로세스**라 부른다. 같은 프로그램이라도 여러 번 실행하면 그만큼 여러 개의 프로세스가 만들어진다.
- CPU 하나로 여러 프로세스를 "동시에" 실행하는 것처럼 보이게 하려면, 실제로는 아주 짧은 시간 단위로 프로세스를 번갈아 실행하는 **시분할(time-slicing)**이 필요하다. 이렇게 다른 프로세스로 전환되는 순간, 지금까지 실행한 지점·스택·힙 상태 등을 저장해두는 과정을 **컨텍스트 스위칭**이라 부른다.
- 문제는 어떤 프로세스가 여러 자식 프로세스를 계속 만들어내면, 그 프로세스 가족이 전체 CPU 시간에서 차지하는 비중이 계속 커진다는 점이다 — 다른 프로세스 입장에서는 형평성이 깨지는 셈이다.
- 이를 해결하기 위해 등장한 것이 **스레드**다. 스레드는 하나의 프로세스에게 할당된 실행 시간을 그 프로세스 내부에서 더 잘게 나눠 쓰는 단위다. 프로세스 전체가 갖는 코드·데이터·힙 영역은 스레드끼리 공유하고, 실행 흐름을 나타내는 스택만 스레드마다 따로 갖는다. 이렇게 하면 한 프로세스 안에서 여러 흐름을 동시에 처리하면서도, 다른 프로세스들과의 형평성 문제를 일으키지 않는다.

이후 서버 프로그램(예: 톰캣)들은 동시 접속자를 처리할 때 접속자 수만큼 스레드를 만들어 처리하는 방식을 표준처럼 써왔다.

## 17. Node.js가 스레드 대신 콜백을 선택한 이유

Node.js는 여기서 다른 길을 택한다 — 동시 접속 처리를 위해 스레드를 여러 개 만드는 대신, 하나의 실행 흐름 위에서 **콜백 함수** 기반으로 비동기 작업을 처리한다. 어차피 스레드도 결국 OS가 시간을 잘게 나눠 번갈아 실행시키는 것이므로 "진짜 동시 실행"은 아니며, 스레드를 만들고 스케줄링하는 데 드는 오버헤드(메모리, 컨텍스트 스위칭 비용)를 아예 없애고, 대신 I/O 작업이 끝났을 때 "신호(콜백)"만 받아서 처리하는 방식이 더 가볍다는 것이 Node.js 진영의 주장이다.

이 주장의 근거로 흔히 드는 비교가 **스레드 기반 웹 서버(Apache)**와 **이벤트/콜백 기반 웹 서버(Nginx)**의 성능 비교다.

- Apache는 요청이 들어올 때마다 스레드를 새로 배정해 처리한다 — 동시 접속자가 늘어날수록 스레드 수와 메모리 사용량이 함께 가파르게 증가하고, 일정 수준을 넘으면 초당 처리량이 급격히 떨어진다.
- Nginx(그리고 Node.js)는 스레드를 늘리지 않고 하나의 이벤트 루프 위에서 콜백으로 요청을 처리한다 — 동시 접속자가 수천 명으로 늘어나도 메모리 사용량 증가폭이 완만하게 유지된다.

Node.js는 이 이벤트 기반 모델을 자바스크립트의 콜백 함수 문법과 결합해 "스레드 없는 고성능 서버 자바스크립트 런타임"으로 포지셔닝했다. 다만 이 비교가 모든 상황에서 스레드 방식보다 우월하다는 뜻은 아니며, CPU 연산이 무거운 작업에는 여전히 한계가 있다는 점은 실무에서 함께 고려해야 한다.
