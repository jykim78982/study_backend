# 자바스크립트와 브라우저 플랫폼 — 탄생 배경, DOM, 이벤트, 함수

## 1. 브라우저와 자바스크립트의 탄생 배경

최초의 상용 브라우저(넷스케이프 내비게이터) 시절에는, 사용자가 입력한 내용을 검사하지 않고 그대로 서버로 전송했다. 당시 서버로 보내는 요청 하나하나가 지금과 비교할 수 없을 만큼 큰 부담이었기 때문에(그 시절 세계에서 가장 빠른 컴퓨터보다 지금의 평범한 스마트폰이 더 빠를 정도), 유효성 검사 없이 무조건 전송하는 방식은 곧 한계에 부딪혔다.

그래서 브라우저에 "사용자 입력을 감지할 수 있는 최소한의 플랫폼" 기능이 추가된다. 입력 상자를 감싸는 `<form>`을 객체화하고, 그 값을 조건 검사할 수 있는 언어가 필요해졌다. 이때 만들어진 언어가 처음엔 **라이브스크립트(LiveScript)**라는 이름이었다가, 자바를 만든 썬 마이크로시스템즈와의 제휴 이후 **자바스크립트**로 이름이 바뀐다(90년대 후반).

최초의 자바스크립트가 다룰 수 있는 객체는 **오직 `form`과 그 안의 입력 요소뿐**이었다 — 지금처럼 이미지나 텍스트를 자유롭게 바꾸는 건 불가능했고, 입력값을 확인해서 유효하면 서버로 전송(POST)하고, 유효하지 않으면 오류 메시지를 보여주는 정도가 전부였다.

90년대 중후반, `form` 객체가 **모든 HTML 요소를 객체화하는 수준으로 확장**되면서 "다이나믹 HTML(DHTML)"이라는 화두가 등장한다. 문서가 로드되면 그 안의 폰트·문단·주석 같은 요소들을 자바스크립트로 다룰 수 있게 되어, 정적이던 HTML이 실행 중에 바뀌는 동적인 문서가 된 것이다. (요즘 "빅데이터"나 "AI"라는 말이 그랬듯, 당시엔 책 제목마다 DHTML을 붙여 팔던 시절이 있었지만, 지금은 너무 당연해져서 이 용어 자체를 아는 사람이 드물다.)

## 2. 프로그램 = 언어 + 플랫폼

모든 프로그래밍 환경은 결국 "언어"와 "플랫폼" 두 가지로 이루어지고, 언어와 플랫폼은 직접 맞닿을 수 없어서 그 사이에 **인터페이스**를 두고 플랫폼을 이용한다는 점은 어디서나 같다.

자바스크립트에서 그 플랫폼이 바로 **브라우저**다. 다만 브라우저 자체를 직접 조작할 수는 없고, 브라우저가 메모리에 로드해 둔 **객체**(인터페이스)를 통해서만 다룰 수 있다. 대표적으로 다음 세 가지가 있다.

- **`window`(프레임)**: 브라우저 창 자체를 캡슐화한 객체. 창의 위치·크기 등에 영향을 준다. 다만 모바일 환경에서는 창이 항상 전체화면이라 위치·크기 조정의 의미가 크게 줄었다.
- **`location`**: 주소창에 해당하는 객체. 사용자가 주소를 입력해서 페이지가 바뀌는 것처럼, 코드로도 페이지 이동을 다룰 수 있다.
- **`document`**: 문서 자체를 표현하는 객체.

우리가 다루는 내용의 대부분(체감상 90% 이상)은 `window.document` 안에 계층적으로 얽혀 있는 객체들이다. 문서 안의 버튼, 그 안의 이미지, 그 안의 텍스트까지 가계도처럼 계층 구조를 이루며 존재한다.

## 3. DOM — 메모리에 로드된 동적 HTML

우리는 사실 HTML을 두 가지 형태로 다루게 된다.

- **정적인 HTML**: 디스크에 저장된 파일 자체. 화면에 영향을 주긴 하지만, 이걸 바꾸려면 파일을 다시 수정하고 브라우저를 다시 열어야 한다.
- **동적인 HTML(DOM)**: 브라우저가 정적 HTML을 읽어 들여 메모리에 객체 트리로 만든 것. 실행 중에 이 객체를 바꾸면 파일을 건드리지 않고도 화면이 즉시 바뀐다.

우리가 자바스크립트로 실제로 다루는 건 왼쪽의 정적인 HTML 파일이 아니라, 가운데 있는 **동적인 HTML, 즉 DOM(Document Object Model)**이다.

브라우저가 문서를 읽어 들이는(Load) 과정에서 각 태그가 객체 트리로 바뀐다. 예를 들어 다음과 같은 HTML이 있다고 하면,

```html
<body>
    <div>
        <font></font>
        <input />
    </div>
    <p>
        <form>
            전송할까요?
            <input />
            <input />
        </form>
        hello~
    </p>
    <!-- 주석 -->
</body>
```

이 문서는 로드 과정을 거쳐 다음과 같은 객체 트리(DOM)로 메모리에 올라간다.

```
#document
  └ body
      ├ div
      │   ├ font
      │   └ input
      ├ p
      │   ├ form
      │   │   ├ #text
      │   │   ├ input
      │   │   └ input
      │   └ #text
      └ #comment
```

태그뿐 아니라 **텍스트(`#text`)와 주석(`#comment`)도 각각 하나의 노드로 취급**되어 트리에 포함된다는 점이 특징이다. 이 트리 구조를 만드는 과정(Load)이 끝나야 화면에 그려지고(Show) 사용자에게 보이는 인터페이스가 완성된다.

## 4. `<script>` 태그의 위치와 `defer`

자바스크립트 코드는 원칙적으로 문서 어디에 놓아도 동작한다 — `<head>`든 `<body>`든 상관없다. 다만 위치에 따라 결과가 달라질 수 있다.

- 문서 파서는 HTML을 **위에서 아래로 순서대로** 읽으며 DOM 객체를 만든다.
- 만약 스크립트가 **자신이 다루려는 요소보다 먼저** 등장하면, 그 요소는 아직 메모리에 올라오지 않은(`undefined`) 상태이므로 오류가 난다.
- 과거에는 이 문제를 피하려고 스크립트를 **문서 맨 끝**에 두는 관행이 있었다(화면이 다 그려진 뒤에 스크립트를 실행해서, 스크립트 오류나 지연이 화면 렌더링 자체를 막지 않도록 하기 위함).
- 요즘은 `<script>` 태그에 **`defer`** 옵션을 주는 방식을 쓴다. `defer`가 있으면 브라우저는 문서를 끝까지 다 읽어서 DOM 트리를 완성한 뒤에야 그 스크립트를 실행한다 — 스크립트 위치를 `<head>`에 두면서도, 실행 시점만 뒤로 미룰 수 있다.
- 같은 목적을 위해 `window`의 **`onload`** 이벤트를 쓸 수도 있다. `window.onload`에 등록한 코드는 모든 DOM이 완전히 로드된 뒤에만 실행되므로, 스크립트를 문서 어디에 두든 안전하게 요소에 접근할 수 있다.

## 5. 이벤트 — 새로운 진입점

지금까지 다룬 언어들은 `main` 함수라는 하나의 진입점에서 코드가 시작됐지만, 브라우저(GUI) 환경에는 `main` 함수가 없다. 대신 코드는 **"화면에 윈도우를 띄우는 것"부터 시작**하고, 그 이후의 흐름은 사용자의 동작에 반응하는 방식으로 진행된다.

사용자가 클릭하거나, 마우스를 누르거나 떼거나 움직이거나, 키를 누르는 것 — 이런 것들을 **이벤트**라고 부른다. "사건"보다는 "내가 기대하고 있는 상황"에 가깝다: 나는 코드를 미리 만들어 두고, "사용자가 클릭하면 이걸 하겠다"는 식으로 반응을 준비해 두는 것이다. 대표적인 이벤트 종류는 다음과 같다.

- 마우스: `click`, `mousedown`, `mouseup`, `mousemove`
- 키보드: `keydown`, `keyup`, `keypress`
- 기타: `scroll`

이런 이벤트에 반응해서 실행되는 코드를 등록하는 속성이 `on이벤트명`(`onclick`, `onmouseover` 등) 형태로 모든 엘리먼트에 존재한다. HTML 속성으로 직접 쓰면 다음처럼 된다.

```html
<input type="button" value="출력"
       onclick="alert('안내 메시지');" />
```

이때 `onclick` 안의 문자열은 **큰따옴표로 감싼 HTML 속성 값 안에 있는 문자열**이므로, 그 안에서 문자열을 표현할 때는 작은따옴표(`'...'`)를 쓴다. 자바스크립트 자체는 원래 큰따옴표가 기본이지만, 이렇게 중첩되는 상황(HTML 속성 안)에서는 관례적으로 작은따옴표를 쓰는 것이다.

## 6. 산술 연산자와 자동 형변환

기본 산술 연산자는 다른 언어와 크게 다르지 않다.

| 연산자 | 설명 | 예시 |
|---|---|---|
| `+` | 더하기 | `10 + 5 // 15` |
| `-` | 빼기 | `10 - 5 // 5` |
| `*` | 곱하기 | `10 * 5 // 50` |
| `/` | 나누기 | `10 / 5 // 2` |
| `%` | 나머지 | `10 % 3 // 1` |
| `**` | 거듭제곱(ES6+) | `2 ** 3 // 8` |
| `++` | 증가(1씩 증가) | `x++` 또는 `++x` |
| `--` | 감소(1씩 감소) | `x--` 또는 `--x` |

주의할 점은 **브라우저에서 입력받는 모든 값은 형태가 숫자처럼 보여도 항상 문자열**이라는 것이다(`prompt()`의 반환값 포함). 그래서 입력받은 두 값을 그냥 `+`로 이으면 산술 덧셈이 아니라 **문자열 결합**이 일어난다 — 예를 들어 `"3" + "5.4"`는 `8.4`가 아니라 `"35.4"`가 된다. 반대로 `-`, `*`, `/`처럼 문자열 결합과 겹치지 않는 연산자를 쓰면 자바스크립트가 알아서 숫자로 묵시적 변환을 해준다. 그래서 입력값을 계산에 쓰려면 명시적으로 숫자로 변환해야 한다.

## 7. 함수 — 사실은 "정의"가 아니라 "객체 생성"

자바스크립트 함수는 다른 C 계열 언어(C, C++, Java 등)와 겉모습부터 다르다.

```java
// C 계열 언어의 함수 — 매개변수 타입과 반환 타입을 반드시 명시
int add(int x, int y) {
    return x + y;
}
```

```js
// 자바스크립트 — 매개변수·반환값의 타입을 아예 쓰지 않는다
function add(x, y) {
    return x + y;
}
```

자바스크립트에 타입 표기가 없는 이유는, 애초에 자바스크립트에는 "정의(definition)"라는 개념 자체가 없기 때문이다 — **정의는 곧 객체를 생성하는 것**이다. 브라우저 콘솔에 뜨는 `"OOO is not defined"`(정의되지 않음) 오류도, 다른 언어라면 "선언되지 않았다"로 이해할 내용이지만 자바스크립트에서는 **그 객체가 아직 생성(존재)되지 않았다**는 뜻에 더 가깝다.

`function add(x, y) { ... }`처럼 쓰는 함수 선언문은 사실 다음의 눈속임(축약형)이고, 원래는 이렇게 **`Function`이라는 생성자로 객체를 만드는 것**이 본모습이다.

```js
// 진짜 모습: Function 생성자로 함수 객체를 생성
var add = new Function("x, y", "return x+y;");
alert(add(3, 4));

// 위와 같은 의미의 함수 표현식(더 널리 쓰는 형태)
var add = function (x, y) {
    return x + y;
};

// 우리에게 익숙한 함수 선언문
function add(x, y) {
    return x + y;
}
```

즉 함수는 정의되는 게 아니라 **변수에 담기는 하나의 객체**다. 이렇게 이해하고 나면, 함수를 다른 변수·속성에 대입하는 것도 전혀 이상한 일이 아니게 된다.

```js
printButton.onclick = function () { printResult(); }; // 익명 함수 안에서 호출
printButton.onclick = printResult;                     // 함수 자체(참조)를 대입
```

두 번째 줄처럼 **소괄호 없이 함수 이름만 대입**하면, `printResult`라는 변수(함수 객체에 대한 참조)를 그대로 넘기는 것이다. 이벤트 핸들러 안에 특별한 추가 코드가 없다면(그 함수 하나만 호출하면 끝이라면), 이렇게 참조를 바로 대입하는 방식을 더 선호한다.

반면 이벤트가 발생했을 때 **여러 문장을 실행**해야 하거나 매개변수를 전달해야 한다면, 이름이 필요 없는 **익명 함수(이벤트 핸들러)**로 감싸서 등록한다.

```js
printButton.onclick = function () {
    var x, y;
    x = prompt("x 값을 입력하세요", 0);
    y = prompt("y 값을 입력하세요", 0);
    alert(x + y);
};
```

이벤트 핸들러는 사용자가 이름으로 호출할 일이 없기 때문에, 굳이 이름을 붙여 변수를 늘릴 필요가 없다 — 그래서 이벤트 속성에는 대부분 익명 함수를 바로 대입하는 형태가 일반적이다.

## 8. 코드 조직화 — HTML과 자바스크립트 완전히 분리하기

`onclick="alert('안내 메시지');"`처럼 HTML 속성 안에 직접 코드를 쓰는 방식은 코드가 조금만 복잡해져도(변수 선언, 여러 문장 등) HTML 문자열 안에 그대로 넣을 수 없어 한계가 뚜렷하다. 그래서 실제로는 다음 순서로 발전시킨다.

1. **HTML 속성에 직접 코드 작성** — `onclick="..."` (가장 원초적, 복잡한 코드에는 부적합)
2. **이름 있는 함수로 분리 후 HTML에서 호출** — `function printAdd() {...}` 정의 + `onclick="printAdd();"`
3. **HTML 속성 자체를 없애고, 자바스크립트 쪽에서 DOM으로 이벤트를 등록** — `printButton.onclick = printResult;`를 `<script>` 안에 두어, HTML에는 순수 마크업만 남기고 동작(behavior)은 전부 스크립트 쪽으로 옮긴다.
4. **자바스크립트를 아예 별도 파일로 분리** — `<script src="step1.js"></script>`처럼 외부 파일로 빼서, HTML과 로직을 완전히 나눈다.

이렇게 단계를 거치면 HTML에는 구조만 남고, 동작(어떤 이벤트에 어떤 함수가 실행되는지)은 전부 자바스크립트 파일 한 곳에 모이게 되어 유지보수가 쉬워진다.

## 9. `id` 네이밍 규칙과 함정

HTML의 `id`/`class` 이름은 관례상 케밥 표기법(`kebab-case`, 예: `btn-calc`)을 쓴다. 그런데 이 이름을 자바스크립트 쪽에서 **변수명처럼 직접 사용하려고 하면 문제**가 생긴다 — 자바스크립트 식별자에는 하이픈(`-`)을 쓸 수 없기 때문에, `btn-calc`라는 이름을 코드에서 `btn-calc`로 그대로 쓰면 "`btn` 빼기 `calc`"로 해석되어 오류가 난다.

이 문제 때문에 예전에는 `id`를 카멜케이스(`btnCalc`)로 짓는 편법을 쓰기도 했지만, 이는 애초에 접근 방법 자체가 잘못된 것이다. **`id`는 HTML의 명명 규칙(케밥케이스)을 그대로 따르고, 자바스크립트에서는 그 값을 문자열로 전달해서 `getElementById("btn-calc")`처럼 DOM API를 통해 가져와야 한다.** 가져온 엘리먼트를 어떤 변수명에 담을지는 자바스크립트 쪽의 자유이므로, `id`의 표기법과 자바스크립트 변수 표기법이 서로 부딪힐 이유가 없다.

## 10. 노드 선택 — `getElement*` 계열과 Selectors API(`querySelector`)

DOM 트리에서 원하는 노드를 찾을 때 쓰는 전통적인 방법은 `document`의 다음 메서드들이다.

```js
document.getElementById();          // id로 단 하나의 엘리먼트를 찾음
document.getElementsByClassName();  // 클래스명으로 찾음 (배열 형태로 반환)
document.getElementsByName();       // name 속성으로 찾음 (배열 형태로 반환)
document.getElementsByTagName();    // 태그명으로 찾음 (배열 형태로 반환)
```

`getElementById`만 단일 결과(하나의 엘리먼트)를 반환하고, 나머지(`ByClassName`/`ByName`/`ByTagName`)는 조건에 맞는 노드가 여러 개일 수 있어 **배열 형태**로 반환한다. 그래서 실제로 하나만 쓰고 싶어도 인덱스(`[0]`)를 붙여야 하는 번거로움이 있다.

```js
var section = document.getElementById("s1");
var input = section.getElementsByClassName("input")[0];
var button = section.getElementsByClassName("button")[0];
```

**문서 전체가 아니라 찾아낸 요소(`section`) 안에서 다시 검색**한다는 점도 중요하다 — 문서 전체를 뒤지는 것보다 이미 좁혀 놓은 범위(섹션) 안에서 찾는 게 더 빠르고, 다른 섹션에 같은 이름이 있어도 충돌하지 않는다. 그래서 이름을 부여할 때도 문서 전체에서 유일해야 하는 `id`보다, 섹션 범위 안에서만 겹치지 않으면 되는 `class`를 실무에서 훨씬 많이 쓴다.

요즘은 이 대신 CSS 선택자 문법을 그대로 쓸 수 있는 **Selectors API**(`querySelector`/`querySelectorAll`)를 더 많이 쓴다.

```js
// 1. DOM 기능을 이용해 노드 객체를 선택하는 방법
var section = document.getElementById("s1");
var input = section.getElementsByClassName("input")[0];
var button = section.getElementsByClassName("button")[0];

// 2. Selectors API를 이용해 노드 객체를 선택하는 방법
var section = document.querySelector("#s1");
var input = section.querySelector(".input");
var button = section.querySelector(".button");
```

`querySelector`는 CSS에서 쓰는 선택자 문법(`#id`, `.class` 등)을 그대로 문자열로 넘기면 되고, **항상 조건에 맞는 첫 번째 요소 하나만** 반환하므로 배열 인덱싱(`[0]`)이 필요 없다. 여러 개를 모두 찾아야 할 때는 `querySelectorAll`을 쓴다.

## 11. 실전 예제 — `publishing/js/step1.html` / `step1.js`

앞서 다룬 개념들(외부 파일 분리, `window.onload`, `querySelector`로 범위를 좁혀 찾기, 익명 함수 이벤트 핸들러, 문자열 결합 함정)이 실제로 합쳐진 예제다.

```html
<!DOCTYPE html>
<html lang="ko">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>Document</title>
    <script src="step1.js"></script>
</head>
<body>
    <section id="notice-create">
    <input class="btn-calc" type="button" value="click">
    </section>
</body>
</html>
```

```js
window.onload = function() {
    var section = document.querySelector("#notice-create");
    var btnCalc = section.querySelector(".btn-calc");
    // "btn-calc"는 querySelector에 넘기는 문자열일 뿐 식별자가 아니라서
    // 케밥케이스 그대로 써도 되고, 가져온 엘리먼트는 btnCalc라는
    // 자유로운 변수명에 담는다

    btnCalc.onclick = function() {
        var x, y;
        x = prompt("x 값을 입력하세요", 0);
        y = prompt("y 값을 입력하세요", 0);
        btnCalc.value = x + y;
    }
    // 이름 없는 함수를 onclick에 바로 대입한 이벤트 핸들러다.
    // 이 함수는 지금 실행되는 게 아니라 클릭이라는 사건이
    // 발생할 때마다 나중에 호출되도록 등록만 해두는 것이며,
    // 다시 부를 일이 없으니 이름을 붙일 필요도 없다.
}
```

- `<script src="step1.js">`로 HTML과 로직을 완전히 분리했다.
- 전체 코드를 `window.onload`로 감싸서, DOM이 다 로드된 뒤에 실행되도록 했다.
- `document.querySelector("#notice-create")`로 먼저 섹션을 좁힌 뒤, 그 섹션 안에서 다시 `.querySelector(".btn-calc")`로 버튼을 찾았다 — `id`를 변수명으로 직접 쓰지 않고 DOM API로 가져오는 방식이 그대로 적용된 예다.
- 버튼 클릭 시 실행되는 코드는 익명 함수로 `onclick`에 직접 대입했다.
- `x + y`는 `prompt`로 받은 문자열을 그대로 더한 것이라, 실제로는 산술 덧셈이 아니라 **문자열 결합**이 된다.

## 12. 엘리먼트와 엘리먼트 객체 — 속성 이름이 거의 같다

디스크에 있는 태그 자체를 **엘리먼트**라 부르고, 그 태그가 메모리에 그대로 옮겨져 올라간 것을 **엘리먼트 객체**라 부른다. 엘리먼트 객체는 결국 엘리먼트를 보고 메모리에 만들어진 것이므로, 둘의 속성 이름은 원칙적으로 같다 — 자바스크립트에서 이미 쓰고 있는 예약어와 충돌하는 한두 개(`class` → `className` 등)만 이름이 살짝 다를 뿐, 나머지는 HTML 속성 이름을 그대로 객체 속성으로 쓸 수 있다. 즉 DOM 객체가 가진 속성을 따로 암기할 필요 없이, HTML 속성을 아는 만큼 그대로 이 객체를 다룰 수 있다.

## 13. 태그로 감싼 콘텐츠 수정하기 — `textContent` / `innerText` / `innerHTML`

```html
<span id="span1">제목 : <a href="">안녕하세요</a></span>
```

`id`, `href`처럼 태그 자체에 적힌 속성은 **객체 속성**으로 그대로 바꿀 수 있다(`span1.href = "..."`). 하지만 `<span>`과 `<a>` 사이에 있는 "제목 : 안녕하세요"라는 부분은 속성이 아니라 **태그가 감싸고 있는 콘텐츠(자식)**다. 감싸는 태그와 그 안의 콘텐츠 사이에는 부모-자식 관계가 있고, 이 관계는 계속 중첩되다가 말단에서는 결국 텍스트로 끝난다.

여기서 흔한 착각이 하나 있다 — `<span>`에는 `<input>`과 달리 `value` 속성이 없다. `span1.value`로 안의 글자를 바꾸려는 시도는 애초에 존재하지 않는 속성을 있다고 착각하는 것이다. 콘텐츠(자식)를 바꾸려면 속성 대입이 아니라 자식을 바꾸는 전용 방법을 써야 하고, 여기엔 세 가지가 있다.

- `textContent`: 텍스트만 대입한다. 태그 문자열을 넣어도 태그로 해석되지 않고 문자 그대로(인코딩되어) 보이거나 무시된다.
- `innerText`
- `innerHTML`: 문자열을 HTML로 해석해서 통째로 꽂아 넣는다.

`innerText`/`innerHTML`은 원래 인터넷 익스플로러가 자체적으로 만든 비표준 속성이었는데, 당시 인터넷 익스플로러의 점유율이 워낙 높다 보니 표준이 아니면서도 사실상 표준처럼 굳어져 지금까지 남아있는 것이다. 단순 텍스트를 바꿀 때는 `innerText` 대신 `textContent`를 표준으로 쓰고, HTML 구조 자체를 통째로 넣어야 할 때도 `innerHTML`보다 더 안전하고 바람직한 함수를 쓰는 쪽을 권장한다.

## 14. 이벤트 위임이 필요한 이유 — 반복 바인딩의 문제

`ul` 안에 여러 개의 `li`가 있고 그 안에 각각 `img`가 있는 것처럼, 같은 구조가 여러 번 반복되는 요소들에 **똑같은 이벤트 처리**를 걸어야 하는 경우가 자주 생긴다. 이때 각 `img`마다 개별로 이벤트 핸들러를 하나씩 등록하는 방식에는 세 가지 문제가 있다.

- **동적으로 추가된 요소는 반응하지 않는다**: 이벤트 핸들러는 페이지가 로드되는 시점에 존재하던 요소에만 걸리므로, 나중에 자바스크립트로 새로 만들어 붙인 요소에는 핸들러가 없다.
- **똑같은 함수를 반복해서 여러 개 만든다**: 반복되는 요소마다 값만 다를 뿐 하는 일(알고리즘)은 완전히 같은 함수 객체가 개수만큼 생성되어 메모리를 낭비한다.
- **반복문으로 등록해도 근본적으로 해결되지 않는다**: 개별 등록을 반복문(`for`)으로 줄여서 코드 줄 수만 겉으로 짧아 보이게 만들어도, 여전히 요소 수만큼 함수가 만들어지는 문제와 나중에 다룰 클로저 문제까지 새로 끌어들이게 된다.

이 문제를 근본적으로 해결하려면 반복해서 등록하는 대신, 부모 요소 하나에만 이벤트를 걸고 그 안에서 실제로 클릭된 자식을 구분해내는 방식이 필요하다.

## 15. 캡처링과 버블링 — 이벤트가 실행되는 순서

윈도우 프로그램은 큰 창 안에 작은 창, 그 안에 더 작은 창이 겹겹이 들어있는 구조를 이룬다. `ul`(부모) 안에 `li`들, 그 안에 `img`들이 있는 구조도 마찬가지다. 사용자가 이 중 가장 안쪽의 `img`를 클릭했다고 해도, 그 클릭 신호는 한 곳에서 끝나지 않고 두 단계를 거친다.

- **캡처링(Event Notification)**: 최상위 조상에서부터 실제 클릭된 요소를 향해 아래로 내려가며 알림이 전달되는 단계.
- **버블링(Event Bubbling)**: 실제로 클릭된 요소에서부터 부모, 조상을 거쳐 다시 위로 신호가 올라가는 단계. 물속 거품이 표면으로 떠오르는 모습에 빗대어 버블링이라 부른다.

`div` 세 겹을 중첩시켜 각각에 `onclick`을 걸고 가장 안쪽 자식을 클릭해보면, 자기 자신뿐 아니라 부모, 조상의 핸들러까지 순서대로(안쪽 → 바깥쪽) 총 세 번 실행되는 것을 콘솔에서 직접 확인할 수 있다.

버블링 덕분에 [13. 이벤트 위임이 필요한 이유]에서 다룬 문제를 해결할 수 있다 — 자식 요소들이 서로 빽빽하게 붙어 있어서 그 사이의 빈 여백(부모 자신의 영역)을 직접 클릭하기 어려운 경우에도, 자식을 클릭하면 그 이벤트가 버블링되어 부모까지 올라오므로 **부모 하나에만 핸들러를 걸어두면 그 부모를 클릭한 것과 똑같은 효과**를 자식 클릭으로 얻을 수 있다. 이때 부모의 핸들러 입장에서 "내가 직접 클릭된 것"인지 "자식이 클릭되어 버블링으로 전달된 것"인지 구분해야 하는데, 이를 위해 모든 이벤트 핸들러는 현재 이벤트에 대한 추가 정보를 담은 **이벤트 객체**를 매개변수로 넘겨받는다 — 실제로 클릭된 가장 안쪽 원본 요소가 무엇인지도 이 객체 안에 담겨 있다.

## 16. 이벤트 기반 프로그래밍과 콜백 — 동기화를 벗어나는 방법

지금까지의 프로그램은 `main` 함수 하나에서 시작해 정해진 순서대로 실행되는 **동기(synchronous)** 흐름이었다 — 한 번에 하나의 작업을 순서대로 처리하며, 앞의 작업이 끝나야 다음 작업으로 넘어간다. 문제는 브라우저(GUI) 환경에서는 "사용자가 언제 클릭할지"를 미리 알 수 없다는 점이다. 만약 이 흐름을 동기적으로 짠다면, 클릭을 기다리는 동안 화면을 그리거나 다른 작업을 하는 코드는 전혀 실행되지 못하고 멈춰 있어야 한다 — 마치 택배를 직접 받으려고 집 앞에서 하염없이 기다리느라 다른 일을 아무것도 못 하는 것과 같다.

이 문제는 **콜백(callback)**이라는 개념으로 해결한다. "택배가 오면 대신 받아두고 나에게 전화해줘"라고 동생에게 맡겨두면, 나는 그동안 다른 일을 할 수 있고, 동생이 실제로 택배(이벤트)를 받았을 때만 전화(호출)를 걸어준다. 브라우저에서도 마찬가지로, 사용자의 클릭을 실제로 감지하고 기다리는 역할은 코드의 메인 흐름과는 별개로 백그라운드에서 동작하며, 클릭이라는 사건이 실제로 발생했을 때에만 미리 등록해둔 함수(콜백 함수, 곧 이벤트 핸들러)를 대신 호출해준다. 그동안 메인 흐름은 멈추지 않고 화면 렌더링 등 다른 작업을 계속 진행할 수 있다.

여기서 중요한 특징은, 콜백으로 등록한 함수는 내가 직접 이름을 불러 호출하는 것이 아니라 **호출 시점과 호출 여부 자체를 외부(브라우저)가 결정**한다는 점이다 — 원래는 내가 필요할 때 함수를 호출했어야 하는데, 그 주도권이 외부로 넘어가 버린 셈이다. 이렇게 실행의 흐름을 내가 아니라 외부가 쥐게 되는 구조를 **제어의 역전**이라 부른다.
