# 프론트엔드의 변화와 Next.js의 필요성

## 1. 프론트엔드 변화의 용어 정리

프론트엔드가 걸어온 변화 과정을 한눈에 정리하면 아래 순서다.

| 용어 | 핵심 |
|---|---|
| Static Web Page | 순수 HTML(초기에는 CSS도 없음)만으로 만든 페이지 |
| Dynamic Server Web Page(= Server Page, On-demand Page) | 사용자 요청이 올 때 서버가 그때그때 페이지를 만들어 응답 |
| Fat Client | 화면에서 할 수 있는 조작은 서버에 요청하지 않고 클라이언트(자바스크립트)가 직접 처리 |
| SPA(Single Page Application) | 서버는 데이터(API)만 제공하고, 문서 조작은 전부 클라이언트가 담당 |
| Full-Stack | 하나의 언어(자바스크립트)로 프론트엔드와 백엔드를 함께 만드는 흐름 |
| Frontend: SSR | 프론트엔드 기술(React 등)로 서버 사이드 렌더링까지 함께 제공하는 방식 — Next.js가 여기 해당 |

이 흐름은 과거에서 현재로 갈수록 "누가 문서를 만드느냐"의 무게중심이 서버 → 클라이언트 → 다시 서버로 이동해 온 역사이기도 하다.

## 2. Static Web Page — 순수 HTML의 시대

1990년대에는 CSS 자체가 없었다. HTML만으로 문서를 만들었고, 이렇게 만든 페이지를 스태틱 웹페이지라 불렀다. 90년대 말 "문서와 스타일은 분리되어야 한다"는 웹 표준 논의와 함께 CSS가 등장했지만, 실제로 널리 쓰이기 시작한 것은 2000년대에 들어서면서부터다. CSS가 추가된 뒤에도 내용이 미리 정해진 채 서버에 그대로 올려두는 방식이라는 점에서는 여전히 스태틱 페이지였다.

## 3. Dynamic Server Web Page — 요청이 오면 그때 만드는 페이지

오늘 날씨, 지금 이 순간의 스포츠 중계 결과, 방금 등록된 채팅 내용처럼 실시간으로 달라지는 정보는 미리 만들어 둘 수 없다. 그래서 이런 데이터를 데이터베이스에 저장해 두고, 사용자 요청이 들어오는 순간 그 데이터를 바탕으로 페이지를 그때 만들어 응답하는 방식이 등장했다.

이런 페이지를 만드는 초기 기술이 CGI(C언어 기반)였고, 이를 더 쉽게 다룰 수 있게 해주는 플랫폼으로 ASP·PHP·JSP 등이 뒤이어 등장했다. 이후 Node.js 위에서 자바스크립트로 Express를 얹어 페이지를 만드는 방식까지 이어진다.

이렇게 만들어진 페이지는 관점에 따라 여러 이름으로 불린다.

- **동적으로 만들어진다**는 관점 → 다이나믹 페이지
- **서버에서 만들어진다**는 관점 → 서버 페이지
- **요청이 온 시점에 만들어진다**는 관점 → 온디맨드 페이지

셋 다 같은 대상을 가리키는 서로 다른 이름일 뿐이다.

### 3-1. 서버 스택 조합

이 시절 자주 쓰이던 무료 조합이 **LAMP 스택**이다 — Linux + Apache(웹 서버) + MySQL(데이터베이스) + PHP. 전부 무료라는 공통점 때문에 스타트업들이 즐겨 썼고, 페이스북·위키피디아·구글도 초기에는 이 조합으로 시작했다. 자바 진영에서는 PHP 대신 JSP·Servlet을 얹은 자바 웹스택을 쓴다는 차이만 있을 뿐, "서버가 페이지를 만든다"는 본질은 같다.

## 4. Fat Client — 클라이언트가 역할을 나눠 갖기 시작하다

서버가 페이지를 전부 만드는 방식에는 한계가 있었다. 예를 들어 계산기 앱에서 `3 + 3`의 결과를 요청할 때마다 서버가 결과 페이지를 새로 만들어 보내야 한다면, 사용자가 뭔가를 조작할 때마다 매번 서버 왕복이 필요해진다. 사용자가 1,000명만 되어도 그 1,000명 모두가 사소한 조작 하나하나를 서버에 요청하게 되므로 서버 부담이 커진다.

그런데 자바스크립트는 단순히 입력값을 검사하는 수준을 넘어, DOM을 직접 조작해 문서 자체를 바꿀 수 있다. 화면에서 무언가를 지우는 게 목적이라면, 서버에 다시 만들어 달라고 요청하는 것보다 클라이언트가 DOM을 직접 조작하는 편이 훨씬 빠르다. "클라이언트가 처리할 수 있는 일은 클라이언트가 가져가고, 서버와의 통신은 최소화하자"는 흐름이 이렇게 시작됐다. 서버가 담당하던 역할을 코드 조각 단위로 조금씩 클라이언트에 넘겨주며 클라이언트를 점점 무겁게(Fat) 만들어가는 이 과정을 Fat Client라 부른다.

## 5. SPA(Single Page Application) — 문서는 전부 클라이언트가 담당

Fat Client가 극단으로 가면 결국 서버는 문서를 전혀 만들지 않고 데이터만 제공하는 형태에 도달한다. 서버는 "너는 문서를 다 만들어라, 나한테는 필요한 데이터만 요청해"라는 역할로 재편된다.

브라우저에 XHR(XMLHttpRequest, 자바스크립트로 서버에 데이터를 요청하는 도구)이 추가되면서, 클라이언트는 페이지 전체를 새로 요청하는 대신 필요한 데이터만 비동기로 요청해 화면 일부만 갱신할 수 있게 됐다. 이렇게 "자바스크립트로 데이터를 요청해 화면을 갱신하는 기술"을 통틀어 **Ajax**라 부른다. XHR이라는 이름에 XML이 들어 있지만, 지금은 XML 대신 JSON이 데이터 포맷의 대세다.

이 흐름이 자리 잡으면서 서버의 역할이 명확히 나뉜다.

- **웹 서버**: 문서(페이지)를 제공하는 서버
- **API 서버**: `csv`·`xml`·`json` 같은 데이터를 제공하는, 데이터를 위한 중계자(인터페이스)

SPA 환경에서 웹 서버가 실제로 하는 일은 거의 없다 — 빈 페이지 하나에 클라이언트로 내려보낼 스크립트를 실어 나르는 `<script src="...">` 한 줄을 담아 보내는 것뿐이다. 실제 화면을 만드는 일은 그 스크립트가 브라우저에서 전담한다. 이렇게 하나의 페이지로 전달받아 그 안에서 애플리케이션 전체가 동작하는 방식을 **싱글 페이지 애플리케이션(SPA)**이라 부른다.

이 방식이 인기를 끈 배경에는 네트워크 환경의 발전도 있다. 과거 모뎀 시절에는 문서 하나를 내려받는 데도 시간이 오래 걸려 스크립트 덩어리를 통째로 내려받는 방식이 부담스러웠지만, 네트워크 대역폭이 커진 지금은 스크립트를 매번 새로 내려받아도 큰 문제가 되지 않는다.

## 6. Full-Stack — 하나의 언어로 프론트와 백을 함께

SPA가 자리 잡으면서, "자바스크립트 하나만 할 줄 알면 프론트와 백엔드를 모두 만들 수 있다"는 흐름이 등장했다. 대표적인 조합이 **MEAN 스택**(MongoDB + Express + Angular + Node)이다.

이 구조에서 프론트엔드는 클라이언트 사이드에서 화면을 만드는 **CSR(Client-Side Rendering)**을 담당하고, 백엔드는 API를 제공하는 역할로 재편된다. Node가 이 흐름 속에서 "페이지를 만드는 도구"에서 "API를 만드는 도구"로 자리를 옮겨 갔다. 처음에는 "자바스크립트만 할 줄 알면 다 할 수 있다"는 의미로 시작한 Full-Stack이라는 말이, 지금은 "프론트와 백엔드를 모두 다룰 줄 안다"는 더 넓은 의미로 쓰이게 됐다.

## 7. Full-Stack(SPA)의 치명적 문제 — 검색엔진 노출

Full-Stack/SPA 구조에는 한 가지 심각한 문제가 있다. 검색엔진 봇은 스크립트를 실행하지 않는다 — 악성코드일 가능성을 배제할 수 없기 때문이다. 봇이 실제로 확인하는 것은 **서버가 응답하는 HTML 문서**뿐이다.

그런데 SPA 구조에서 웹 서버가 응답하는 문서는 빈 페이지(`<div id="root"></div>` 정도)뿐이고, 실제 내용은 브라우저에서 스크립트가 실행된 뒤에야 채워진다. 즉 봇이 보는 문서는 항상 비어 있는 셈이다. 그 결과 구글 검색 결과에 이 페이지가 전혀 노출되지 않는다.

검색엔진 노출은 단순한 부가 기능이 아니다. 사용자는 광고를 보고도 사이트 주소를 기억하지 못해 다시 검색하는 경우가 많으므로, 검색 노출이 안 되면 아무리 광고비를 써도 효과를 보기 어렵다. Full-Stack(SPA) 구조가 이 문제를 안고 있다는 사실이 뒤늦게 드러나면서, 한동안은 SPA용 화면과 검색엔진용 서버 페이지를 별도로 두 벌 만드는 비효율적인 대응이 이어지기도 했다.

## 8. Frontend: SSR — 프론트엔드 기술로 서버 사이드까지

이 문제를 근본적으로 해결하기 위해, 프론트엔드 프레임워크 자체가 서버 사이드 렌더링까지 지원하는 흐름이 등장했다.

| 프론트엔드 기술 | 서버 사이드 렌더링 프레임워크 |
|---|---|
| Angular | Angular Universal |
| Vue | Nuxt |
| React | **Next.js** |

이 프레임워크들은 클라이언트로 보낼 스크립트를 서버에서도 실행해, 요청이 들어오면 그 순간 서버에서 완성된 HTML을 만들어 클라이언트에 내려준다. 검색엔진 봇은 이 서버 렌더링 결과(완성된 HTML)를 그대로 읽을 수 있으므로 검색 노출 문제가 해결된다. 이후 클라이언트에서는 이 페이지에 자바스크립트가 추가로 로드되어, 이어지는 사용자 상호작용(CRUD 등)을 담당하게 된다.

이 흐름 속에서 React 자체의 성격도 바뀌었다. React는 원래 "웹 문서를 조작하기 위한 라이브러리"로 나왔지만, SPA 방식으로 쓰다 보니 정작 웹의 핵심 요건인 검색엔진 노출이 안 되는 역설적인 상황에 놓였다. 이를 보완해 "웹을 위한 React"로 만들어진 것이 바로 **Next.js**다. 지금은 React 공식 사이트의 프로젝트 생성 안내도 Next.js(`create-next-app`) 기준으로 되어 있다.

## 9. Next.js 프로젝트 구조 — 파일 기반 라우팅

Next.js는 과거 `src/` 디렉터리에 코드를 모으던 방식 대신, 프로젝트 루트의 `app/` 폴더 안에 폴더 구조 자체로 URL 경로를 표현하는 **앱 라우터** 방식을 쓴다.

- `app/page.js` → 루트 경로(`/`)의 페이지
- `app/hello/page.js` → `/hello` 경로의 페이지
- `app/admin/menu/page.js` → `/admin/menu` 경로의 페이지

폴더 경로가 곧 URL이 되고, 그 폴더 안의 `page.js`(또는 `page.jsx`)가 해당 경로의 화면을 담당한다. 이 규칙만 지키면 라우팅 설정을 따로 코드로 작성할 필요가 없다.

```jsx
// app/hello/page.js
function HelloPage() {
    return <h1>Hello</h1>;
}

export default HelloPage;
```

`export default`로 내보내면, 이 컴포넌트를 가져다 쓰는 Next.js 내부 입장에서는 이름과 상관없이 이 파일의 대표 컴포넌트로 인식해 렌더링한다. `/hello`로 접속하면 이 컴포넌트가 서버에서 렌더링되어 응답으로 내려간다.

과거 SPA 방식이 전체 자바스크립트 번들 하나를 통으로 클라이언트에 내려보냈던 것과 달리, Next.js는 페이지(또는 컴포넌트) 단위로 요청이 들어올 때마다 그 페이지에 필요한 HTML과 자바스크립트를 함께 내려준다. 그래서 초기 화면은 완성된 HTML로 즉시 보이고, 이후의 상호작용은 함께 전달된 자바스크립트가 이어받는 구조가 된다.

## 10. 빌드 도구 비교 — npm, pnpm, yarn, bun

Node 진영에는 라이브러리를 설치·관리하는 빌드 도구가 여럿 있다.

| 도구 | 특징 |
|---|---|
| npm | 가장 널리 쓰이는 기본 도구. 프로젝트마다 `node_modules`를 독립적으로 생성 |
| pnpm | 라이브러리를 전역 공용 공간에 한 번만 저장하고 각 프로젝트는 이를 참조 — 디스크 절약, 속도도 빠름 |
| yarn | npm의 대안으로 나온 도구 |
| bun | Rust 기반으로 매우 빠르지만, 상대적으로 신생이라 아직 불안정한 부분이 있음 |

pnpm은 여러 프로젝트가 라이브러리를 공유해 효율적이지만, 그만큼 한 프로젝트에서 문제가 생기면 그 라이브러리를 공유하는 다른 프로젝트에도 영향을 줄 수 있다는 단점이 있다. 학습 목적으로는 이런 상호 영향 없이 프로젝트별로 완전히 독립된 환경을 유지하는 것이 낫기 때문에, 전통적인 **npm**을 기준으로 사용한다.

참고로 Rust는 C/C++이 개발자가 직접 메모리를 해제(`delete`)해야 해서 메모리 누수에 취약했던 문제를, 실행 환경 없이도 컴파일 시점에 안전성을 보장하는 방식으로 해결한 언어다. 최근 Next.js의 번들링 엔진 일부(Turbopack)에도 이 Rust가 쓰이고 있다.

## 11. 서버 기반 vs 서버리스

실제 서비스를 운영하려면 데이터베이스와 웹 서버(또는 API 서버)를 어딘가에서 24시간 돌려야 한다. 이를 마련하는 방식은 크게 두 갈래로 나뉜다.

### 11-1. 서버 기반(직접 운영)

내가 직접 컴퓨터(또는 클라우드 가상 머신)를 마련해 원하는 데이터베이스·웹 서버를 설치하고 운영하는 방식이다. 대표적으로 AWS의 **EC2**가 이런 서비스다 — CPU·메모리·디스크 용량을 원하는 사양으로 구매하고, 그 위에 원하는 운영체제와 소프트웨어를 직접 설치해 원격으로 접속해 쓴다.

장점은 내가 원하는 대로 자유롭게 구성할 수 있다는 점이지만, 서버가 다운되지 않도록 안정적으로 운영하는 책임도 전부 내 몫이 된다. 초기 비용 대비 실제 운영 비용이 예상보다 커질 수 있다는 점도 고려해야 한다.

### 11-2. 서버리스(클라우드 서비스 이용)

서버를 직접 사거나 운영할 여건이 안 될 때는, 이미 설치·운영되어 있는 서비스를 빌려 쓰는 방식을 택한다. 데이터베이스를 서비스 형태로 제공하는 Firebase·Supabase, 프론트엔드 배포를 전문으로 하는 Vercel 등이 여기 해당한다. 서버를 직접 소유하지 않는다는 의미에서 이를 **서버리스**라 부른다.

장점은 하드웨어 관리·다운타임 걱정 없이 내 소프트웨어(코드)에만 집중할 수 있다는 점이다. 단점은 사용량에 비례해 매달 이용료를 계속 내야 하고, 데이터가 많아질수록 다른 서비스로 이전하기도 점점 어려워진다는 점이다.

### 11-3. 선택 기준

| 상황 | 적합한 방식 |
|---|---|
| 초기 스타트업, 소규모 프로젝트 | 서버리스(관리 인력 없이 빠르게 시작) |
| 서버 운영을 전담할 인력이 있는 조직 | 서버 기반(직접 구매·운영) |
| 데이터 보안이 특히 중요한 경우 | 민감한 데이터만 별도로 직접 운영하는 서버로 분리 |

## 12. 정리

프론트엔드는 "서버가 전부 만든다(Static/Dynamic Server Page)" → "클라이언트가 일부를 나눠 가진다(Fat Client)" → "클라이언트가 전부 담당한다(SPA/Full-Stack)" → "검색엔진 노출 문제로 다시 서버 렌더링이 필요해진다(Frontend: SSR)"는 흐름을 거쳐 왔다. Next.js는 이 마지막 단계, 즉 React의 생산성과 서버 사이드 렌더링을 동시에 확보하기 위해 등장한 프레임워크이며, 파일 기반 라우팅(`app/` 폴더 구조)으로 URL과 페이지 컴포넌트를 자동으로 연결해 준다.
