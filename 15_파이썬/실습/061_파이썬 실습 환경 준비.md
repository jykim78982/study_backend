## 이 노트의 목표

코드를 한 줄도 작성하기 전에, 앞으로의 학습을 진행하면서 환경 문제로 막히지 않을 작업 환경을 구축한다. 이 노트를 끝까지 따라 하면 다음과 같은 상태가 된다.

1. 터미널에서 `uv run python check_env.py` 명령을 실행했을 때 **"환경 준비 완료"**라는 메시지가 정상적으로 출력된다.
2. 프로젝트 폴더 내의 각 파일과 폴더가 어떤 역할을 하는지 구체적으로 이해하게 된다.
3. 단계별 실습 코드를 git 브랜치를 활용해 자유롭게 조회하고 이동하는 법을 터득한다. *(브랜치 조회는 이어지는 단계에서 본격적으로 다룬다. 이 노트에서는 예제 zip을 받아 환경을 맞추는 것까지다.)*

소요 시간은 약 1시간에서 1시간 반 정도다. Windows 사용자는 Linux 환경(WSL2) 설치 과정이 포함되어 있어 시간이 조금 더 걸릴 수 있다.

이 설명은 프로그래밍을 처음 시작하는 입문자의 눈높이에 맞춰 작성되었다. 터미널 조작, 가상환경 개념이 낯설더라도 안내된 절차를 차례대로 따라 진행하면 차근차근 완수할 수 있을 것이다.

## 1-1. 운영체제별 준비

이 과정의 모든 명령은 Linux 셸(bash) 기준이다. macOS와 Linux 사용자는 터미널을 열어 그대로 따라 하면 되고, Windows 사용자는 WSL2를 설치해서 사용한다.

> [!tip] 🎓 newlec 쌤의 코멘트
> 이 노트는 파이썬 학습에 집중하는 문서이다 보니 지면상 WSL을 깊이 있게 다루지는 못했다. 다음 절에서 WSL 설치법을 간단히 소개하고 있지만, 작동 원리나 활용법을 더 자세히 알고 싶다면 리눅스·WSL을 다루는 노트([[006_컴퓨터와 리눅스의 역사]], [[036_WSL2 기반 VSCode 개발 환경 구축 및 자바 프로젝트 실습]] 등)를 참고하기 바란다.

### Windows: WSL2 설치

WSL2는 Windows 안에서 가상으로 진짜 Linux 환경을 돌려주는 기능이다.

이 과정 뒤에 이어지는 데이터 분석이나 AI 과정에서는 Windows에 직접 설치하기 까다로운 패키지를 자주 다루게 된다. 따라서 처음부터 WSL2를 사용해 Linux 환경을 갖춰 두는 편이 시행착오를 줄이고 시간을 아끼는 길이다.

시스템 요구사항 및 사전 조건을 확인한다. Windows 10 버전 2004 이상(빌드 19041 이상) 또는 Windows 11 환경이어야 하며, 메인보드 BIOS/UEFI 설정에서 가상화(Virtualization, Intel VT-x 또는 AMD-V) 기능이 활성화되어 있어야 한다. (최근 판매되는 대부분의 PC와 메인보드는 이 기능이 기본으로 켜져 있어 별도로 설정할 필요가 없다.)

- **Windows 버전 확인:** `Win + R` → `winver` 입력 후 확인
- **가상화 활성화 여부:** `Ctrl + Shift + Esc` → 작업 관리자 → 성능 탭 → CPU. 하단 **가상화**가 '사용'인지 확인. '사용 안 함'이면 재부팅 후 BIOS/UEFI에서 켠다.

PowerShell을 **관리자 권한**으로 연다. (시작 메뉴에서 'PowerShell' 검색 후 마우스 우클릭 → '관리자 권한으로 실행') 이후 아래 명령을 입력하고 Enter를 누른다.

```bash
wsl --install
```

이 명령은 WSL 필수 구성 요소와 기본 Linux 배포판(Ubuntu)을 자동으로 다운로드하고 설치한다. 기본 설정이 Ubuntu이므로 별도로 우분투를 찾아 설치하지 않아도 된다. 이미 WSL만 있거나 배포판을 지정하려면 `wsl --install -d Ubuntu` 를 써도 된다.

설치가 완료되면 컴퓨터를 **재부팅**한다.

재부팅 후 우분투(Ubuntu) 설치 및 초기 설정 창이 자동으로 뜬다. (안 뜨면 시작 메뉴에서 "Ubuntu" 검색)

- `UNIX username:` 영문 소문자 계정 이름
- `New password:` 비밀번호 (입력 중 화면에 아무 표시가 없어도 정상이다)

확인:

```bash
wsl --list --verbose     # 또는 wsl -l -v
```

출력에서 Ubuntu의 **VERSION** 열이 `2`여야 한다. `1`이면 `wsl --set-version Ubuntu 2` 로 전환한다.

이후 모든 작업은 **Ubuntu 터미널** 안에서 진행한다. 시작 메뉴의 "Ubuntu" 또는 Windows Terminal에서 Ubuntu 탭을 연다.

> [!tip] 🎓 newlec 쌤의 코멘트
> 프로젝트 폴더를 만들 때는 설치 위치를 꼭 확인해야 한다. Windows 파일이 들어 있는 `/mnt/c/...` 경로에 프로젝트를 두면 파일 처리 속도가 수십 배 느려진다. 따라서 WSL 환경에서는 반드시 Linux 홈 디렉터리(`~`) 안에 프로젝트 폴더를 만들어야 한다.

### macOS

기본 터미널(Terminal) 앱을 연다. Xcode Command Line Tools가 없으면 `git` 첫 실행 때 설치 안내가 뜬다. 미리 설치하려면:

```bash
xcode-select --install
```

### Linux

별도 준비 없음. 기본 터미널을 연다.

## 1-2. 터미널 명령 네 개

이 과정에서 터미널로 하는 일은 거의 이 네 개다. 지금 한 번씩 쳐 본다.

| 명령 | 뜻 | 예 |
|---|---|---|
| `pwd` | 지금 어느 폴더에 있는가 | `pwd` → `/home/me` |
| `ls` | 이 폴더에 뭐가 있는가 (`-a` 면 숨김 파일도) | `ls -a` |
| `cd 폴더` | 그 폴더로 이동 (`cd ..` 한 단계 위, `cd ~` 홈) | `cd python-101` |
| `cat 파일` | 파일 내용 출력 | `cat README.md` |

파일 이름 앞에 `.` 이 붙은 것(`.gitignore`, `.venv`)은 숨김 파일이다. `ls` 로는 안 보이고 `ls -a` 로 보인다. 이 과정의 설정 파일 대부분이 숨김 파일이라 자주 쓰게 된다.

## 1-4. 예제 코드 받기

이 과정은 노트마다 예제 파일을 별도의 zip으로 제공한다. VS Code에서 디렉터리를 준비해 두면 편하다.

우선 터미널에서 WSL(Ubuntu)로 접속한 뒤 홈으로 이동한다.

```bash
cd ~
```

이 노트의 첨부 `python-101-step-01.zip` 링크를 복사해 받는다. (또는 볼트에 둔 zip을 사용한다.)

![[python-101-zip-copy-link.png]]

첨부 zip 경로(WSL Workspace3):

`~/Workspace3/python-101-step-01/python-101-step-01.zip`

### zip 푸는 도구 확인

```bash
unzip -v
```

버전이 나오면 된다. 안 나오면:

```bash
# Ubuntu / WSL
sudo apt update && sudo apt install -y unzip
# macOS 는 기본으로 들어 있다
```

### 풀기

브라우저로 받은 파일은 보통 다운로드 폴더에 있다. WSL에서는 Windows 다운로드가 `/mnt/c/Users/<윈도우 계정>/Downloads/` 로 보인다.

`cd ~` 로 홈에 두는 이유: `unzip`이 **현재 작업 디렉터리**에 폴더를 풀기 때문이다. zip 파일 경로는 절대 경로로 지정한다.

```bash
cd ~                                                               # 홈 디렉터리로
# Workspace3 에 둔 zip
unzip ~/Workspace3/python-101-step-01/python-101-step-01.zip
# 또는 Downloads 에서
unzip /mnt/c/Users/<윈도우 계정>/Downloads/python-101-step-01.zip    # WSL
unzip ~/Downloads/python-101-step-01.zip                           # macOS / Linux
cd python-101
ls -a
```

`python-101` 폴더가 생기고 그 안에 파일 몇 개가 들어 있다. 각각이 무엇인지는 1-8에서 본다.

### 앞으로 오는 zip은 비교용이다

노트마다 오는 zip은 그 노트가 끝난 시점의 완성 코드다. 작업은 계속 `~/python-101` 에서 이어서 하고, 다음 노트의 zip을 그 위에 덮어쓰지 않는다. 막히거나 비교하고 싶을 때 다른 폴더에 푼다.

```bash
unzip ~/Downloads/python-101-step-NN.zip -d ~/answers    # ~/answers/python-101 에 풀린다
```

직접 고쳐 보다가 엉켜도 걱정 없다. `~/python-101` 을 지우고 zip을 다시 풀면 된다.

## 1-5. uv 설치

`uv` 는 Python 버전, 프로젝트별 환경, 패키지 설치를 한 번에 맡는 도구다. 왜 이것을 쓰는지는 바로 다음 절에서 실험으로 체감하고, 그 다음 절에서 다른 도구와 비교한다. 먼저 설치부터 한다.

```bash
# macOS / Linux / WSL
curl -LsSf https://astral.sh/uv/install.sh | sh
```

설치가 끝나면 터미널을 닫고 새로 연다. (PATH에 `uv`가 추가되는데, 열려 있던 터미널에는 반영되지 않는다.)

```bash
uv --version
```

`uv 0.13.x` 처럼 나오면 된다.

## 1-6. 실험: 같은 코드, 다른 환경

### 패키지란

파이썬에 처음부터 들어 있지 않은 기능은 남이 만들어 올려 둔 **패키지**를 설치해서 쓴다. 공개 저장소(PyPI)에 수십만 개가 있다. 웹 서버, 데이터 분석, AI 전부 패키지다. 그래서 "패키지를 어디에 설치하느냐"가 파이썬 환경의 핵심 문제다.

선택지는 둘이다.

1. **전역 설치:** 컴퓨터에 깔린 Python 하나에 모든 패키지를 넣는다. 모든 프로젝트가 같은 패키지를 본다.
2. **격리 설치:** 프로젝트 폴더마다 전용 환경(`.venv`)을 두고 그 안에만 넣는다. 프로젝트끼리 서로 모른다.

말로는 차이가 안 느껴진다. 직접 해 본다. 10분이면 된다.

### 프로젝트 두 개 만들기

홈 디렉터리에 실험용 폴더를 만들고, 그 안에 프로젝트 두 개를 만든다. `cowsay` 라는 작은 패키지를 쓰는데, A에는 6.0, B에는 6.1을 넣는다.

```bash
cd ~
mkdir uv-lab && cd uv-lab

uv init --bare lab-a            # 프로젝트 A. pyproject.toml 하나만 생긴다
cd lab-a
uv add "cowsay==6.0"            # A 에 cowsay 6.0 설치
cd ..

uv init --bare lab-b            # 프로젝트 B
cd lab-b
uv add "cowsay==6.1"            # B 에 cowsay 6.1 설치
cd ..
```

`uv add` 한 줄이 끝나면 폴더 안에 `.venv` 와 `uv.lock` 이 생겨 있다. `ls -a lab-a` 로 확인한다.

### 같은 코드를 두 곳에서 실행

아래 코드를 `lab-a/show.py` 와 `lab-b/show.py` 에 똑같이 만든다.

```python
from importlib.metadata import version
import cowsay

print("cowsay 버전:", version("cowsay"))
cowsay.cow("안녕")
```

```bash
cd lab-a && uv run python show.py && cd ..
```

```
cowsay 버전: 6.0
  ____
| 안녕 |
  ====
     \
      \
        ^__^
        (oo)\_______
        (__)\       )\/\
            ||----w |
            ||     ||
```

```bash
cd lab-b && uv run python show.py && cd ..
```

```
cowsay 버전: 6.1
  ...
```

코드는 한 글자도 다르지 않은데 버전이 다르게 나온다. A는 A의 `.venv` 안 6.0을, B는 B의 `.venv` 안 6.1을 쓴다. 두 폴더는 서로의 존재를 모른다.

### 시스템 Python에서 같은 코드

이번엔 `uv run` 없이, 컴퓨터에 원래 깔린 Python으로 실행한다.

```bash
python3 lab-a/show.py
```

```
ModuleNotFoundError: No module named 'cowsay'
```

시스템 Python에는 `cowsay`가 없다. 방금 두 번이나 설치했는데도 없다. 설치가 프로젝트 폴더의 `.venv` 안에만 됐기 때문이다. 밖으로 새어 나간 것이 하나도 없다. **이것이 격리**다.

### 전역 설치였다면

만약 격리 없이 시스템 Python 하나에 설치했다면:

1. A를 위해 cowsay 6.0을 설치한다.
2. B를 위해 cowsay 6.1을 설치한다. 같은 자리라서 6.0이 지워지고 6.1로 바뀐다.
3. A를 실행하면 6.1이 돌아간다. A가 6.0에만 있는 기능을 썼다면 A가 깨진다. A 코드는 건드린 적도 없는데.

프로젝트가 둘일 때도 이런데, 실무에서는 프로젝트가 열 개고 패키지가 수십 개씩 얽힌다. 그래서 요즘 운영체제는 시스템 Python에 패키지를 설치하는 것 자체를 막는다. 실제로 `python3 -m pip install cowsay` 를 치면 `No module named pip` 이거나 `externally-managed-environment` 오류가 난다.

> [!tip] 🎓 newlec 쌤의 코멘트
> 가상환경을 처음 배우는 분들은 "왜 이렇게 번거롭게 하나" 싶어 건너뛰고 전역에 설치하곤 합니다. 그러다 몇 달 뒤 프로젝트 하나가 이유 없이 깨지고, 그때서야 가상환경을 배웁니다. 그 몇 달을 아끼시라고 이 실험을 1단계에 넣었습니다. **원칙은 하나입니다. 패키지는 항상 프로젝트 안에 설치합니다. 시스템 Python은 건드리지 않습니다.**

실험이 끝났으면 `uv-lab` 폴더는 지워도 된다. `rm -rf ~/uv-lab`.

## 1-7. 같은 일을 하는 세 가지 도구, 그리고 왜 uv 인가

방금 한 일을 정리하면 네 가지다. 환경을 만들고, 패키지를 설치하고, 무엇을 설치했는지 기록하고, 그 환경에서 실행한다. 이 네 가지를 하는 도구가 시대별로 세 가지 있다.

| 할 일 | pip + venv (2012~) | Poetry (2018~) | uv (2024~) |
|---|---|---|---|
| Python 설치 | 따로 (공식 설치 파일, pyenv) | 따로 | `uv python install 3.12` |
| 환경 만들기 | `python -m venv .venv` | `poetry init` | `uv init` |
| 환경 켜기 | `source .venv/bin/activate` (매번) | `poetry shell` | 필요 없음 |
| 패키지 설치 | `pip install cowsay` | `poetry add cowsay` | `uv add cowsay` |
| 기록 | `pip freeze > requirements.txt` (손으로) | `pyproject.toml` + `poetry.lock` (자동) | `pyproject.toml` + `uv.lock` (자동) |
| 실행 | `python show.py` (환경 켠 뒤) | `poetry run python show.py` | `uv run python show.py` |
| 다른 컴퓨터에서 복원 | `pip install -r requirements.txt` | `poetry install` | `uv sync` |

### pip + venv: 오랫동안 표준이었다

`pip`은 2008년부터, `venv`는 2012년 Python 3.3부터 내장됐다. 추가 설치가 없어 10년 넘게 표준이었고, 인터넷 자료의 대부분이 이 방식이다. 단점은 손이 많이 간다는 것이다.

### Poetry: 기록을 자동화했다

2018년 Poetry는 설치와 기록을 한 명령으로 묶었다. 지금도 많은 프로젝트가 쓴다. 다만 Python 자체는 따로 설치해야 하고, 속도가 느리다.

### uv: 셋을 하나로, 그리고 빠르다

2024년 `uv`는 Python 설치, 환경, 패키지, 기록, 실행을 전부 한 도구로 합쳤다. Rust로 만들어져 설치 속도가 pip의 수십 배다. 환경을 "켜는" 단계가 아예 없어서, 1-6의 전역 설치 사고가 일어날 자리 자체가 없다.

이 과정은 처음부터 끝까지 **uv만** 쓴다. `pip`과 `venv` 명령은 한 번도 직접 치지 않는다.

### 다른 자료를 읽을 때 번역표

| 자료에 이렇게 적혀 있으면 | 이 과정에서는 |
|---|---|
| `pip install X` | `uv add X` |
| `python -m venv .venv` + `source .venv/bin/activate` | 필요 없음. `uv run` 이 대신한다 |
| `python app.py` | `uv run python app.py` |
| `requirements.txt` | `pyproject.toml` 과 `uv.lock` |
| `pip install -r requirements.txt` | `uv sync` |

## 1-8. 이 과정의 프로젝트 환경 만들기: uv sync

이제 실험이 아니라 진짜 프로젝트다. 1-4에서 받은 `python-101` 폴더로 가서 한 번 실행한다.

```bash
cd ~/python-101
uv sync
```

이 한 줄이 하는 일:

1. `.python-version` 파일을 읽어 Python 3.12를 내려받는다. 시스템에 다른 Python이 있어도 건드리지 않는다.
2. `.venv/` 폴더에 이 프로젝트 전용 가상환경을 만든다. 1-6의 lab-a, lab-b에 생겼던 그것이다.
3. `uv.lock`에 적힌 패키지를 설치한다. 지금은 외부 패키지가 없어서 순식간에 끝난다.

1-6에서는 `uv add`가 환경을 만들었고, 여기서는 `uv sync`가 만든다. 차이는 하나다. **새로 추가할 때는 `uv add`, 남이 만들어 둔 프로젝트를 받아서 똑같이 맞출 때는 `uv sync`.** 이 프로젝트는 받은 것이니 `uv sync`다.

> [!tip] 🎓 newlec 쌤의 코멘트
> 왜 3.12로 고정하는지 궁금하실 겁니다. 지금 최신은 3.14입니다. 이 과정만 보면 3.14를 써도 되지만, 이어지는 데이터·AI 과정에서 쓰는 패키지 일부가 최신 Python 지원이 몇 달씩 늦습니다. 과정 전체를 같은 버전으로 가기 위해 3.12로 고정했습니다. 어떤 버전을 쓸지는 `.python-version` 한 줄이 결정합니다.

### 프로젝트 파일이 각각 하는 일

| 파일 | 역할 | 직접 고치나? |
|---|---|---|
| `pyproject.toml` | 프로젝트 이름, 필요한 패키지 목록 | `uv add`가 자동으로 고침 |
| `uv.lock` | 모든 패키지의 정확한 버전 고정 | 절대 손으로 안 고침 |
| `.python-version` | 사용할 Python 버전 | 고칠 일 없음 |
| `.venv/` | 설치된 패키지가 들어 있는 폴더 | 건드리지 않음. zip에도 없고, 지워도 다시 생김 |
| `.gitignore` | git에서 제외할 목록. `.venv/`가 여기 있음 | 지금은 신경 안 써도 됨 |

실행은 항상 `uv run`:

```bash
uv run python check_env.py
```

`uv run`은 "이 프로젝트의 가상환경 안에서 실행해라"는 뜻이다. 1-6에서 `uv run`을 빼자 cowsay를 못 찾은 것을 기억한다. 이 과정의 모든 명령은 `uv run`으로 통일한다.

나중에 패키지를 추가할 때:

```bash
uv add httpx          # pyproject.toml 과 uv.lock 이 함께 갱신된다
```

공통 과정에서는 30단계(`python-dotenv`)부터 외부 패키지가 들어온다. 그 전까지는 Python에 내장된 것만 쓴다.

### 일부러 망가뜨려 보기

1. `uv run`을 빼고 `python3 check_env.py`로 실행해 본다. 시스템 Python으로 실행되어 "3.12가 아닙니다", "시스템 Python으로 실행됐습니다"가 나올 수 있다. 이것이 `uv run`을 붙이는 이유다.
2. `.venv` 폴더를 통째로 지우고 `uv run python check_env.py`를 쳐 본다. uv가 가상환경을 다시 만들고 실행한다. `.venv`는 언제든 지워도 되는 폴더라는 뜻이다.
3. `uv run python --version` 과 그냥 `python3 --version` 을 비교해 본다. 다르게 나올 수 있고, 그게 정상이다.

### 자주 겪는 오류

| 증상 | 원인 | 해결 |
|---|---|---|
| `uv: command not found` | 설치 후 터미널을 새로 안 열었음 | 터미널 새로 열기, 또는 `source ~/.bashrc` |
| `wsl --install` 이 안 됨 | 가상화가 BIOS에서 꺼져 있음 | BIOS에서 Virtualization 켜기 |
| WSL에서 `uv sync`가 너무 느림 | 프로젝트가 `/mnt/c` 아래에 있음 | `~` 아래로 옮기기 |
| `No such file or directory: check_env.py` | 프로젝트 폴더 밖에서 실행함 | `pwd`로 위치 확인, `cd python-101` |
| `3.12 가 아닙니다` | `uv run` 없이 실행함 | 명령 앞에 `uv run` |
| `unzip: command not found` | unzip 미설치 | `sudo apt install -y unzip` (1-4) |
| `unzip: cannot find or open ...zip` | 경로가 틀림. Windows 계정 이름 확인 | `ls /mnt/c/Users/` 로 계정 폴더부터 확인 |
