# 객체지향 관계와 의존성 주입(DI)의 본질

캡슐화·책임 분리·Composition·Association·인터페이스 의존이라는 다섯 가지 개념이 어떻게 하나의 흐름(강한 결합 → 약한 결합)으로 이어지는지, 그리고 DI가 왜 스프링만의 기술이 아니라 순수 자바 설계 원칙인지를 정리한다.

## 1. 캡슐화 바로잡기 — "묶는 것"이 아니라 "경계를 긋는 것"

캡슐화를 "필드와 메서드를 클래스 하나에 묶는 것"으로 외우면, 왜 클래스를 여러 개로 쪼개야 하는지를 설명할 수 없게 된다. 필드·메서드를 묶는 것은 캡슐화의 **형식(문법)**일 뿐이고, 본질은 **책임(Responsibility)을 하나의 단위로 묶고 내부 구현을 숨기는 것**이다.

왜 굳이 여러 캡슐로 나누는가는 결국 **변경의 파급 범위** 문제로 귀결된다. 하나의 클래스가 여러 책임을 동시에 지고 있으면, 그중 한 책임과 무관한 변경 요청이 들어와도 같은 클래스를 건드려야 하므로 다른 책임의 코드까지 재검토·재테스트해야 한다. 책임별로 캡슐을 나누면 "이 변경은 이 객체 안에서만 끝난다"는 예측이 가능해진다. 즉 캡슐화가 잘 되어 있다는 것은 클래스 개수가 아니라, **하나의 변경 사유(reason to change)가 하나의 클래스에만 대응하는가**로 판단해야 한다.

## 2. 역할(책임) 나누기 — 단일 책임 원칙

주문 처리 도메인을 예로 들면, 처음에는 데이터 조회 로직과 업무 로직이 `OrderManager` 하나에 뒤섞여 있기 쉽다.

```java
public class OrderManager {
    // 데이터 저장소 접근 로직 (조회 책임)
    public Order findOrderById(Long id) {
        return new Order(id, "Item A");
    }

    // 비즈니스 로직 (주문 처리 책임)
    public void createOrder(String item) {
        System.out.println("Order created for " + item);
    }
}
```

이 상태에서 데이터 저장 위치가 DB에서 파일로 바뀌거나 조회 API가 바뀌면, `findOrderById`만 고치면 될 일인데도 같은 클래스 안에 있는 `createOrder`까지 수정 범위(재컴파일, 재테스트)에 딸려 들어간다. 테스트 관점에서도 문제가 생긴다 — `createOrder`의 로직만 검증하고 싶어도, 같은 클래스 안에 있는 `findOrderById`가 실제 DB나 파일을 필요로 하면 단위 테스트가 통합 테스트처럼 무거워진다.

해결은 책임을 분리하는 것이다.

```java
// 데이터 접근 책임
public class OrderRepository {
    public Order findOrderById(Long id) {
        return new Order(id, "Item A");
    }
}

// 비즈니스 로직 책임
public class OrderService {
    public void createOrder(String item) {
        System.out.println("Order created for " + item);
    }
}
```

이것이 SOLID 원칙 중 **단일 책임 원칙(Single Responsibility Principle)**이 말하는 것과 같다 — "클래스를 변경할 이유는 오직 하나여야 한다."

## 3. Composition(has-a)과 강한 결합

책임이 나뉘면 두 캡슐은 협력해야 한다. `OrderService`가 업무를 처리하려면 `OrderRepository`의 기능이 필요한데, 가장 쉬운 방법은 한 객체가 다른 객체를 멤버로 가지는 것 — **"가진다(has-a)" 관계**다. 그중에서도 멤버 객체를 자기 내부에서 직접 생성해 갖는 관계를 **Composition**이라 부른다.

```java
public class OrderService {
    private OrderRepository repository;

    public OrderService() {
        this.repository = new OrderRepository(); // 직접 생성
    }

    public void createOrder(String item) {
        Order existing = repository.findOrderById(1L);
        System.out.println("Order created for " + item);
    }
}
```

`new OrderRepository()`가 `OrderService` 내부에 박혀 있으면 결합력이 매우 강하다. 구체적으로는 다음 세 가지 문제가 생긴다.

- `OrderRepository`의 생성자 시그니처가 바뀌면 `OrderService`도 함께 고쳐야 한다.
- 파일 기반 저장소로 바꾸고 싶어도 `OrderService`의 소스 코드를 직접 열어 `new FileOrderRepository()`로 바꿔야 한다 — **컴파일 타임에 이미 어떤 구현체를 쓸지 결정되어 버린 것**이다.
- 테스트할 때 `OrderService`만 검증하고 싶어도 진짜 `OrderRepository`가 함께 생성되므로, DB 연결이 없으면 테스트 자체가 실패한다. Mock으로 바꿔치기할 방법이 없다.

Composition은 생명주기까지 함께 묶인다는 특징도 있다 — `OrderService` 객체가 없어지면 그 안에서 만든 `OrderRepository`도 같이 사라진다. 이 "생명주기 공유"가 강한 결합의 근본 원인이다.

## 4. Association(has-a)과 DI — 생성 책임을 밖으로 넘긴다

결합력을 낮추려면 `OrderService`가 `OrderRepository`를 스스로 만들지 않고, 이미 만들어진 것을 **외부에서 받아서** 쓰면 된다. 멤버 객체를 직접 생성하지 않고 참조만 받아 쓰는 관계를 **Association**이라 하고, 그 참조를 넘겨주는 행위 자체가 **의존성 주입(Dependency Injection, DI)**이다.

> DI는 스프링 같은 프레임워크의 전유물이 아니라, 객체 간 결합도를 낮추기 위한 순수한 설계 패턴이다. 스프링은 이 DI를 사람이 직접 하지 않도록 컨테이너가 대신 해주는 것뿐이다.

**생성자 주입(Constructor DI)** — 의존성을 생성 시점에 통째로 넘겨받는다.

```java
public class OrderService {
    private final OrderRepository repository; // final: 생성 이후 변경 불가

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}

// 사용 예시 — "누구를 쓸지"는 App(외부)이 결정한다
OrderRepository repo = new OrderRepository();
OrderService service = new OrderService(repo);
```

**세터 주입(Setter DI)** — 객체를 만든 뒤 메서드 호출로 나중에 주입받는다.

```java
public class OrderService {
    private OrderRepository repository;

    public void setRepository(OrderRepository repository) {
        this.repository = repository;
    }

    public void createOrder(String item) {
        if (repository == null) {
            throw new IllegalStateException("Repository not set");
        }
        ...
    }
}

// 사용 예시 — 생성 시점과 주입 시점이 분리되어 있다
OrderService service = new OrderService();
service.setRepository(new OrderRepository()); // 주입
service.createOrder("Item C");
```

| 특징 | Constructor DI | Setter DI |
|---|---|---|
| 결합력 | 낮음 (외부에서 결정) | 낮음 (외부에서 결정) |
| 불변성 | `final` 필드 사용 가능, 객체가 완성된 상태로 생성됨 | 필드가 변경 가능, 주입 전에는 상태가 불완전할 수 있음 |
| 필수 의존성 | 필수 의존성 표현에 적합 | 선택적 의존성 표현에 적합 |
| 테스트 용이성 | 항상 의존성이 채워진 상태로 테스트 가능 | 주입 전 호출 시 NPE(NullPointerException) 위험 |
| 추천 | 대부분의 경우 권장 | 선택적 의존성이나 순환 참조 회피가 필요할 때 |

세터 주입에서 `null` 체크를 직접 넣어야 하는 이유는, 세터 주입은 "객체 생성"과 "의존성 채우기"가 두 단계로 분리되기 때문이다. 그 사이 시점에 메서드가 호출되면 필드가 비어 있는 상태로 실행된다 — 이것이 세터 주입이 "선택적 의존성"에는 어울리지만 "필수 의존성"에는 위험한 이유다. 생성자 주입은 아예 생성자 호출 자체가 막혀 있어서(파라미터 없이는 인스턴스를 만들 수 없음) 이런 불완전 상태가 애초에 존재하지 않는다.

핵심은 한 문장으로 요약된다 — **DI의 목적은 `new`를 제거해서 결합도를 낮추는 것**이다. "누가 어떤 객체를 생성할지"의 결정권을 객체 내부가 아니라 외부(조립자, 구성자)에게 넘긴다. `OrderService`의 입장에서 말로 풀면 "나는 내가 쓸 Repository를 직접 만들지 않을 것이다. 나를 생성하는 쪽이 만들어서 건네달라"는 선언과 같다.

## 5. 인터페이스에 의존하는 이유 — DI만으로는 부족하다

DI를 적용해도 주입받는 타입이 **구체 클래스**라면 결합도는 여전히 높다.

```java
public class OrderService {
    private final OrderRepository repository; // 구체 클래스에 의존

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}
```

`OrderRepository`가 파일 기반 구현으로 완전히 대체되어야 한다면, 필드 타입 자체가 `OrderRepository`(구체 클래스)로 못 박혀 있으므로 `OrderService`의 소스 코드를 열어 타입 이름을 바꿔야 한다. DI로 생성 시점의 결합은 끊었지만, **타입 자체의 결합**은 아직 남아 있는 것이다.

해결은 인터페이스로 **계약(Contract)**을 만들고, `OrderService`는 그 계약에만 의존하게 하는 것이다.

```java
// 인터페이스: 계약
public interface OrderRepository {
    Order findOrderById(Long id);
}

// 구현체 1: DB 기반
public class JdbcOrderRepository implements OrderRepository {
    @Override
    public Order findOrderById(Long id) {
        return new Order(id, "From DB");
    }
}

// 구현체 2: 파일 기반
public class FileOrderRepository implements OrderRepository {
    @Override
    public Order findOrderById(Long id) {
        return new Order(id, "From File");
    }
}

// OrderService: 인터페이스 타입에만 의존
public class OrderService {
    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}
```

여기서 인터페이스 이름과 클래스 이름이 겹쳐 보이지만(`OrderRepository`가 인터페이스이고 `JdbcOrderRepository`/`FileOrderRepository`가 구현체) 헷갈리지 않아야 하는 지점이 있다 — `OrderService`가 필드로 들고 있는 타입은 인터페이스 `OrderRepository`이지, 두 구현체 중 어느 것도 아니다. 실행 시점에 그 자리에 어떤 구현체의 인스턴스가 들어올지는 오직 조립하는 쪽(`App`)만 안다.

```java
public class App {
    public static void main(String[] args) {
        OrderRepository repo = new JdbcOrderRepository();
        // OrderRepository repo = new FileOrderRepository(); // 교체는 이 한 줄만 바꾸면 끝
        OrderService service = new OrderService(repo);
        service.createOrder("Item D");
    }
}
```

이 구조가 주는 이득은 세 가지다.

- **유연성**: `OrderService`는 어떤 구현체가 오는지 몰라도 되고, 알 필요도 없다.
- **교체 용이성**: 구현체를 바꾸는 결정은 `App`(조립하는 코드) 한 곳에만 있다.
- **테스트 용이성**: 테스트 코드에서는 `OrderRepository`를 구현한 모의 객체(Mock)를 만들어 주입하면, 실제 DB 없이도 `OrderService`의 로직만 독립적으로 검증할 수 있다.

## 6. 스프링과의 연결 고리

여기까지는 스프링 없이 순수 자바만으로 설명 가능한 원리다. 스프링의 DI 컨테이너가 하는 일은 결국 `App.main()`에서 사람이 직접 하던 "구현체 선택 → 생성 → 주입" 과정을, `@Component`로 등록된 빈들을 스캔해서 자동으로 대신 해주는 것뿐이다. 즉 스프링이 없어도 성립하는 이 장에서의 원리(캡슐화 → 책임 분리 → Composition의 강한 결합 → Association/DI로 결합 완화 → 인터페이스로 타입 결합까지 제거)를 먼저 이해해야, [[065_스프링의 정체성 — DI 컨테이너, IoC, 인터페이스와 병렬 개발]]에서 다루는 "컨테이너가 결합을 어떻게 대신 낮춰주는가"가 자연스럽게 이어진다.

## 7. 정리

| 단계 | 관계/개념 | 결합력 | 핵심 |
|---|---|---|---|
| 1 | 캡슐화 | — | 필드·메서드를 묶는 게 아니라 책임과 변경 이유를 하나로 묶는 것 |
| 2 | 책임 분리(SRP) | — | 하나의 클래스는 하나의 변경 이유만 가져야 한다 |
| 3 | Composition (has-a, 직접 생성) | 매우 강함 | 생성과 사용이 한 곳에 있어 구현체 교체·테스트가 어렵다 |
| 4 | Association (has-a, DI) | 낮음 | 생성 책임을 외부로 넘겨 `new`를 제거한다 |
| 5 | 인터페이스 의존 | 가장 낮음 | 타입 자체를 추상화해 구현체를 자유롭게 교체·모킹할 수 있다 |

DI는 "의존성을 주입한다"는 기술이고, 인터페이스는 "어떤 의존성을 주입할지"를 유연하게 만드는 추상화다. 이 둘이 결합되어야 결합도가 낮고 유지보수하기 쉬운 객체지향 시스템이 완성된다.
