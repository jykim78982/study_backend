# 스프링의 정체성 — DI 컨테이너, IoC, 인터페이스와 병렬 개발

"스프링은 프레임워크고 개발자를 편하게 해준다"는 설명은 답이 되지 않는다 — 그건 모든 라이브러리의 공통된 특징이지, 스프링만의 정체성이 아니다. 스프링을 다른 프레임워크와 구분 짓는 핵심은 **부품(객체)을 생성하고 조립해주는 능력**, 즉 **DI(의존성 주입)**다.

## 1. 스프링이 등장하기 전 — 무겁고 비쌌던 자바 엔터프라이즈

자바 플랫폼에는 용도별로 세 가지 에디션이 있다.

| 에디션 | 용도 |
|---|---|
| 자바 SE(Standard Edition) | 로컬 앱 개발. 지금까지 설치해온 JDK가 이것 |
| 자바 EE(Enterprise Edition) | 분산형 애플리케이션(웹) 개발. 서블릿, 트랜잭션 처리, DI 등을 담당하는 EJB(Enterprise Java Bean)를 포함 |
| 자바 ME(Mobile Edition) | 모바일용 |

기업용 애플리케이션을 만들려면 원래는 자바 EE가 필요했지만, 문제가 두 가지 있었다.

- **유료**: CPU가 아니라 **코어당** 과금되어, 코어 수가 많을수록 비용이 커진다.
- **무겁고 불안정**: EJB 기능을 쓰려면 별도의 EJB 서버를 띄워야 했고, 톰캣 같은 웹 서버와 EJB 서버를 동시에 운영해야 했다. 설정은 복잡한데 서버는 자주 다운됐다.

이 답답함 속에서 등장한 것이 스프링이다. 스프링은 **서버가 필요 없는 단순한 라이브러리**로 DI와 트랜잭션 처리를 해결했다. 성능은 더 좋고 구현은 더 쉬우며, 오픈소스라 유료화될 걱정도 없다. 이후 스프링은 웹 개발(MVC), JDBC, 보안, 빅데이터 분석 등으로 계속 기능을 넓혀갔지만, 가장 기본이 되는 능력은 예나 지금이나 **DI**다.

## 2. 계층 분리와 DI가 필요해지는 순간

기업용 프로그램은 역할을 계층으로 나눈다.

```
컨트롤러(입력 담당) → 서비스(업무 로직) → 리포지토리(데이터 제공)
```

서블릿 앞단에 프론트 컨트롤러를 두어, 컨트롤러가 서블릿에 의해 동작한다는 사실 자체를 몰라도 되게 만든 것이 스프링이 서블릿 위에 만든 구조다. 이렇게 나눈 계층은 각각 캡슐(객체)이고, 서로 데이터를 위임·조합하며 협력한다.

문제는 여기서 발생한다. 컨트롤러가 `JdbcMenuRepository`라는 구체적인 클래스를 직접 사용하고 있는데, 기술이 바뀌어(`JdbcMenuRepository` → `JpaMenuRepository`, `MyBatisMenuRepository` 등) 리포지토리를 교체해야 하는 상황이 온다. 이때 `JdbcMenuRepository`가 버그가 있어서 바꾸는 게 아니다 — 다른 곳에서도 쓰고 있는 예전 버전이므로 그 소스 자체를 고치면 안 된다.

## 3. 왜 "수정"이 아니라 "확장"이어야 하는가

여기서 객체지향 5원칙(SOLID) 중 두 가지가 등장한다.

- **SRP(단일 책임 원칙)**: 클래스는 하나의 역할만 가져야 한다. 우물을 파는 객체는 우물만 파야지, 버퍼 관리·학생 관리까지 다 떠맡는 "통짜" 객체를 만들면 안 된다.
- **OCP(개방-폐쇄 원칙)**: 수정에는 닫혀 있고, 확장에는 열려 있어야 한다.

기존 코드를 직접 열어서 고치면, npm의 "레프트패드 사건"처럼 과거 버전이 사라지면서 그 버전에 의존하던 다른 곳이 전부 깨진다. 그래서 기존 클래스는 그대로 두고, 새 클래스를 만들어 **상속·구현**으로 확장한 뒤 오버라이드해서 새 내용을 반영해야 한다.

그런데 확장만으로는 부족하다. 컨트롤러가 예전 리포지토리를 직접 `new`해서 쓰고 있다면, 새 리포지토리로 바꾸는 순간 그 `new` 코드를 컨트롤러에서 직접 고쳐야 한다. 즉 **누군가는 여전히 수정을 해야 하는 상황**이 남는다. 이 불편함을 해결하기 위해 등장한 것이 스프링의 DI다 — "네가 뭘 쓸지는 내가 대신 만들어서 꽂아줄게, 너는 설정만 알려줘"라는 방식이다.

## 4. IoC 컨테이너와 빈

스프링은 객체(빈, Bean)를 생성해서 보관하는 **공유 객체 저장소**를 갖고 있다. 이 저장소를 "빈 컨테이너"가 아니라 **IoC(Inversion of Control, 제어의 역전) 컨테이너**라고 부르는 이유는, 원래 개발자가 직접 갖고 있던 "객체를 만드는 주도권"이 프레임워크(스프링) 쪽으로 뒤바뀌었기 때문이다.

- 클래스 앞에 `@Component`를 붙이면, 스프링 부트가 실행되면서 클래스를 스캔해 그 객체를 컨테이너(창고)에 담는다.
- `@Autowired` 같은 설정을 만나면, 스프링이 필요한 객체를 창고에서 꺼내 연결(DI)해준다.

이때 개발자는 **"객체를 누가 생성하는지"는 몰라도 되지만, "가져온 객체를 어떻게 쓸지"는 알아야 한다.** 그리고 그 사용법이 구체적인 클래스에 묶여 있으면 안 된다 — 구체적인 클래스가 바뀌어도 코드가 깨지지 않으려면, 참조하는 자료형이 **추상적**이어야 한다.

### 4-1. 예시로 보는 계층 구조와 DI

기업형 웹 서비스의 기본 구조는 흔히 이렇게 그려진다.

```
[Controller] → [Service] → [DAO] --JDBC--> [DBMS]
      ↓
   [Model] → [View(JSP)]
```

여기서 `DAO`(리포지토리)를 하나가 아니라 여러 구현체(`D1`, `D2`)로 두고, 상황에 따라 어떤 구현체를 쓸지 바꿔 끼워야 한다고 하자.

```
[Controller] → [Service] --DI--> [D1] --JDBC--> [DBMS]
                              └-> [D2] --JDBC--> [DBMS]
```

`Service`가 `D1`을 쓸지 `D2`를 쓸지는 코드에 직접 적지 않는다. 대신 **XML 설정 파일**이나 **애노테이션**으로 "이 자리엔 이 구현체를 꽂아라"라고 지정해두면, 스프링 IoC 컨테이너가 그 설정을 읽어서 실제 연결을 대신 해준다.

```
[XML 설정] ─┐
            ├─ read ─→ [Spring IoC Container: C, S, D1/D2 빈 보관]
[애노테이션] ─┘                    ↕
                            [개발자] ←--- Spring DI가 연결해줌
```

개발자는 `D1`을 `D2`로 바꾸고 싶을 때 `Service`의 소스 코드를 열어 고치는 게 아니라, 설정(XML 또는 애노테이션)에서 어떤 구현체를 주입할지만 바꾸면 된다. 이것이 3절에서 말한 "수정이 아니라 확장·설정으로 해결한다"는 원칙이 실제 구조로 구현된 모습이다.

## 5. 추상화의 끝판왕 — 인터페이스

지금까지 써온 상속(`extends`)은 부모 클래스가 이미 구현해놓은 것을 물려받아 필요하면 오버라이드하는 방식이다. 반면 `implements`(구현하다)로 연결되는 대상은 **아무것도 구현되어 있지 않은** 자료형이다.

```java
class JdbcMenuRepository implements MenuRepository { ... }
```

- **상속(`extends`)**: 부모가 이미 구현한 내용이 있고, 그걸 틀로 가져다 쓰거나 오버라이드해서 고쳐 쓴다. 이 부모를 추상 클래스라 부른다.
- **인터페이스(`implements`)**: 구현이 아예 없다. 함수 이름과 시그니처만 있는 "약속"이다.

```java
interface MenuRepository {
    List<Menu> findAll();   // 구현 없음 — 세미콜론으로 끝
    void update(Menu menu); // 구현 없음
}
```

인터페이스의 특징은 그래서 다음과 같다.

- 구현된 함수가 없다(있어서도 안 된다).
- 속성을 가질 수 없다.
- `new`로 객체화할 수 없다 — 오직 자료형(타입)으로만 쓰인다.

추상 클래스와 인터페이스는 둘 다 추상화지만, 추상 클래스가 "일부는 구현되어 있고 일부만 약속인" 존재라면, 인터페이스는 **구현체가 아예 없는, 순수한 약속**이라는 점에서 추상화의 끝판왕이라 할 수 있다.

## 6. 인터페이스가 있어야 병렬 개발이 가능하다

기업용 프로그램은 보통 계층별로 분업한다.

- **화면(껍데기)**: 사용자와 상호작용. 경력이 적은 사람이 맡아도 큰 문제가 없다.
- **업무 로직(서비스)**: 계좌 이체처럼 실제 업무를 처리. 경력이 많은 사람이 맡는다.
- **데이터 계층(리포지토리)**: 데이터 소스를 숨기고 접근 방법을 제공.

이 세 역할이 **순차적으로** 일하면(서비스 담당자가 리포지토리 완성을 기다렸다가 개발을 시작하는 식) 병목이 생긴다. 세 사람이 줄 서서 기다리는 동기적 방식이 아니라, **병렬(비동기적)로** 동시에 일할 수 있어야 한다.

이걸 가능하게 하는 것이 인터페이스다. 리포지토리 담당자가 아직 구현을 끝내지 않았어도, "나는 `findAll()`, `update()`라는 기능을 제공할 거야"라는 **약속(인터페이스)** 만 먼저 정해두면, 서비스 담당자는 그 인터페이스를 자료형으로 삼아 코드를 바로 작성할 수 있다. 실제 구현체는 나중에 DI로 꽂아주면 된다. 이 약속은 **서비스를 제공하는 쪽(서버)** 이 정하는 것이 일반적이다.

## 7. 정리

| 개념 | 핵심 |
|---|---|
| 스프링의 정체성 | 객체를 생성·조립해주는 DI 컨테이너. 이후 웹, JDBC, 보안 등으로 기능이 확장됐다 |
| 자바 EE와의 차이 | 자바 EE(EJB)는 유료·무거움. 스프링은 무료 라이브러리로 같은 문제를 해결 |
| OCP | 기존 코드는 수정하지 않고, 상속·구현으로 확장해서 고쳐 쓴다 |
| DI가 필요한 이유 | 확장만으로는 "누가 새 객체를 연결해줄지"의 수정 지점이 남는다. 스프링이 그 연결을 대신한다 |
| IoC 컨테이너 | 빈을 만들어 보관하는 공유 저장소. 객체 생성의 주도권이 개발자에서 프레임워크로 역전됐다는 뜻에서 "제어의 역전" |
| 인터페이스 | 구현이 전혀 없는 순수한 약속. 자료형으로만 사용되며, 구현체가 바뀌어도 사용하는 쪽 코드는 깨지지 않는다 |
| 인터페이스의 효과 | 구현이 끝나길 기다리지 않고, 약속(인터페이스)만으로 여러 담당자가 병렬로 개발할 수 있게 한다 |
