# 스프링 DI — 생성자 주입, POJO와 디스패처 서블릿, 요청 DTO 설계

인터페이스 뒤에 숨은 구현체 이름을 어떻게 짓는지, 필드 주입 대신 생성자 주입을 써야 하는 이유, 우리가 만든 컨트롤러가 톰캣에게 어떻게 호출되는지, 그리고 요청 DTO에 어떤 속성을 담아야 하는지를 정리한다.

## 1. 지금 배우고 있는 것의 위치 — 아키텍처 로드맵

지금 다루는 내용은 코딩 문법이 아니라 **아키텍처**다. 계층을 배우고, 그 계층별로 서비스를 작성하는 방법을 배우고, 계층 사이의 결합을 DI(IoC 컨테이너)로 처리하는 방법을 배우는 중이다. 이후 순서로는 데이터베이스 이용을 위한 JPA, 트랜잭션, 스프링 보안이 이어진다. 지금 다루는 DI와 계층 구조는 그 뒤에 나오는 모든 내용의 토대가 된다.

## 2. 인터페이스의 구현체 이름 짓기 — 공통분모는 뒤로, 특화는 앞으로

서비스를 인터페이스로 두는 이유는 "이 자리에 콕 집어 특정 구현체 하나만 와야 한다"는 제약을 없애기 위해서다. 짐을 옮길 때 "그 사람이 아니면 안 된다"고 특정인을 지목하는 대신 "누구 한 사람만 도와주면 된다"고 말하면 훨씬 유연해지는 것과 같다. 그래서 컨트롤러가 참조하는 타입은 특정 구현체가 아니라 **"메뉴 서비스 기능을 갖고 있으면 된다"**는 약속(인터페이스)이면 충분하다.

인터페이스는 아직 구현체가 없어도 성립하는 약속이므로, 실제 동작하는 클래스는 별도로 만들어야 한다. 이때 우리가 쓰는 방식은, 인터페이스 이름(`MenuService`)을 그대로 뒤에 두고 그 앞에 수식어를 붙이는 것이다 — 특별히 구분할 필요가 없는 기본 구현체라면 **`Df`(Default)**를 앞에 붙여 `DfMenuService`로 짓는다. `MenuServiceImpl`처럼 "구현했다"는 사실 자체를 이름 뒤에 넣는 방식도 쓰이지만, 나중에 특화된 구현체가 여러 개 생겼을 때(예: `UserMenuService`, `AdminMenuService`) `Df`가 그 이름들과 더 일관된 짝을 이룬다.

왜 수식어를 뒤가 아니라 **앞에** 붙이는가 하면, 우리가 평소 사물의 이름을 짓는 방식과 같은 어순을 따르는 것뿐이다. 자동차를 부를 때 "빨간 자동차", "산업용 자동차"처럼 **공통분모(자동차)는 뒤에, 특화된 수식어(빨간, 산업용)는 앞**에 붙인다. 이 어순은 한국어든 영어든 세계적으로 비슷하다. 그래서 인터페이스라는 공통분모는 그대로 뒤에 두고, 그 인터페이스를 어떻게 특화한 것인지를 나타내는 수식어(`Df`)만 앞에 얹는 것이 자연스럽다.

이름 짓기는 코딩에서 가장 어려운 작업 중 하나다. 연산자나 반복문보다 이름이 훨씬 어렵다 — 이름이 잘못되면 코드를 다른 사람이 납득하기 어려워지기 때문이다. AI에게 물어보며 다듬는 것도 좋은 방법이다.

## 3. 누가 구현체를 만들어서 꽂아주는가 — 그것이 스프링이다

인터페이스에는 실체가 없으므로, 누군가는 구현체 객체를 생성해서 그 인터페이스 타입의 자리에 꽂아주어야 한다. 이 작업(생성 + 결합)을 사람이 직접 코드로 하면, 구현체를 교체할 때마다 그 코드를 찾아 고쳐야 하는 부담이 남는다.

스프링은 이 부담을 없애준다 — "그 조립은 내가 대신 해줄 테니, 너는 표시만 해라"는 방식이다. 클래스에 `@Component`(또는 그 특화된 형태)만 붙이면, 스프링이 그 클래스를 찾아 생성해서 자신의 보따리(컨테이너)에 담아두고, 필요한 자리에 자동으로 결합해준다. 이 보따리를 **IoC 컨테이너**라 부르는 이유는, 단순히 객체(빈)를 담고만 있는 게 아니라 "생성과 조립"이라는 일 자체를 대신 맡아서 하기 때문이다 — 그 "일을 맡기는" 행위가 바로 **제어의 역전(Inversion of Control)**이다.

## 4. `@Component`와 그 특화된 형태들

`@Component`는 "이 클래스를 스프링이 생성해서 관리해달라"는 가장 일반적인 표시다. 여기서 더 구체적인 의미를 담은 특화된 어노테이션들이 파생된다 — 시맨틱 HTML에서 `<div>`(범용 블록)보다 `<nav>`, `<article>`, `<aside>`(의미가 담긴 블록)를 쓰는 것과 같은 원리다.

- `@Service`: "나는 서비스 계층이다"라는 의미가 담긴 `@Component`.
- `@Repository`: "나는 데이터 접근 계층이다"라는 의미가 담긴 `@Component`.
- `@Controller`: 단순히 객체를 생성하는 것을 넘어, **URL 매핑 기능**이라는 특화된 능력이 포함되어 있다. 이 기능은 `@Component`로는 대체할 수 없고, 오직 컨트롤러 계열 어노테이션만 갖는다.

서비스나 리포지토리 자리에 `@Component`를 그대로 써도 동작에는 차이가 없다 — 다만 의미가 더 특화되어 있지 않을 뿐이다. 반면 URL 매핑이 필요한 자리에는 반드시 컨트롤러 계열 어노테이션을 써야 한다.

`@Controller`와 `@RestController`의 차이도 여기서 갈린다.

- `@Controller`: 함수가 **페이지 이름**을 반환한다. 서버가 JSP 등 뷰를 직접 그려주던 MVC 방식(서버 페이지를 개발하던 시절)에서 쓰던 방식이다.
- `@RestController`: 함수가 **데이터**를 반환한다. 지금처럼 JSON 형태로 데이터만 내려주는 REST API를 만들 때는 반드시 이것을 써야 한다.

## 5. POJO와 디스패처 서블릿 — 우리가 만든 컨트롤러는 누가 호출하는가

지금 쓰는 웹 서버는 톰캣이다. 사용자 요청이 오면 결국 톰캣이 그 요청을 처리할 객체를 호출해야 하는데, **톰캣이 직접 호출할 수 있는 객체는 서블릿(`HttpServlet`을 상속한 클래스)뿐이다.** 그런데 우리가 만든 컨트롤러 클래스는 `HttpServlet`을 상속하고 있지 않다 — 아무 부모 클래스도 상속하지 않는 순수한 자바 클래스, 즉 **POJO(Plain Old Java Object)**다.

톰캣이 POJO를 직접 호출할 수 없으므로, 그 사이를 이어주는 존재가 필요하다. 스프링 라이브러리(`spring-webmvc` jar, `org.springframework.web.servlet` 패키지) 안에 이미 이 역할을 하는 서블릿이 준비되어 있는데, 그것이 **디스패처 서블릿(`DispatcherServlet`)**이다. 이 서블릿은 `HttpServlet`을 상속하고 있어서 톰캣이 정상적으로 호출할 수 있고, 모든 요청을 일단 이 서블릿 하나가 전부 받는다.

요청이 처리되는 흐름은 이렇다.

```
[요청 "/index"] → Tomcat → Front Controller(DispatcherServlet, HttpServlet 상속)
                                    ↓ (매핑 정보로 대상 컨트롤러를 찾음)
                              Controller(POJO, MenuController 등)
                                    ↑ (처리 결과 반환)
                Front Controller ← 응답 데이터/페이지
[응답] ← Tomcat ←
```

디스패처 서블릿(프론트 컨트롤러)은 요청받은 URL을 보고, 스프링 컨테이너(보따리) 안에서 그 URL에 매핑된 컨트롤러를 찾아 대신 호출해준다. 즉 우리가 만드는 컨트롤러는 톰캣이 직접 부르는 게 아니라, **디스패처 서블릿을 거쳐서** 호출되는 구조다. 모든 요청의 입구를 이 프론트 컨트롤러 하나가 관장하고 있다.

이 디스패처 서블릿은 우리가 직접 만들거나 등록하는 게 아니다. `spring-boot-starter-web` 의존성만 추가하면, **스프링 부트가 내장 톰캣을 띄우면서 디스패처 서블릿까지 자동으로 준비해서 그 톰캣 위에 등록해준다.** 예전 순수 스프링에서는 `web.xml`에 디스패처 서블릿을 직접 등록하는 설정이 필요했지만, 스프링 부트는 이 과정까지 자동 설정으로 감춰버렸다. 그래서 우리는 `@RestController`, `@GetMapping` 같은 어노테이션만 붙이면 되고, 그 뒤에서 요청을 가로채 알맞은 컨트롤러로 연결해주는 디스패처 서블릿의 존재 자체는 평소에는 신경 쓸 일이 없다.

## 6. DI 방식 — 필드 주입 대신 생성자 주입을 쓴다

필드에 직접 `@Autowired`를 붙이는 **필드 주입**은 코드가 짧고 깔끔해 보여서 한동안 널리 쓰였지만, 다음 이유로 지양해야 한다.

- 의존성이 필드 안에 숨어 있어서 겉으로 드러나지 않고, 어떤 의존성이 필요한지 한눈에 파악하기 어렵다.
- 순수하게 이 클래스만 꺼내서 단위 테스트하기가 어렵다 — 프레임워크 없이는 필드에 값을 채울 방법이 마땅치 않다.
- `private` 필드에 컨테이너가 직접 값을 꽂아 넣는 방식 자체가, 캡슐화 원칙(외부에서 내부 상태를 직접 건드리지 않는다) 관점에서도 개념적으로 바람직하지 않다.
- `final`로 선언할 수 없어서, 생성 이후 다른 구현체로 바뀌지 않게 막는 안전장치를 둘 수 없다.

그래서 **생성자 주입**을 기본으로 쓴다. 의존성이 하나뿐일 때는 `@Autowired` 자체를 생략해도 스프링이 알아서 주입해준다. 의존성이 둘 이상일 때만 `@Autowired`를 명시한다.

```java
@RequestMapping("/api/v1/menus")
@RestController
public class MenuController {
    // 추상형식을 이용해서 참조를 해요.
    // 추상형식의 끝판왕 -> 인터페이스
    // @Autowired // Field Injection - 지양
    private final MenuService service;

    // 밖에서 주입을 해주기 때문에, 내가 객체를 직접 생성하지 않는다.
    // Constructor Injection
    // @Autowired  // 의존성이 하나뿐이면 생략 가능
    public MenuController(MenuService service) {
        // 결합형: Association
        this.service = service;
        // 일체형: Composition — 이렇게 쓰지 않는다
        // service = new MenuService();
    }
}
```

주석에서 보듯, 생성자 안에서 직접 `new`로 생성하면 Composition(강한 결합)이 되고, 밖에서 만들어진 객체를 받아 대입하면 Association(느슨한 결합, DI)이 된다. 우리는 항상 후자를 쓴다.

## 7. 요청 DTO 설계 — 쿼리 스트링은 "페이지의 상태 변수"다

목록을 요청할 때 사용자가 함께 전달하는 값(쿼리 스트링)은, 그 페이지가 **여러 상태를 가질 수 있다는 전제** 위에서만 필요해진다. 페이지가 단 하나의 고정된 상태만 갖는다면 상태 변수(쿼리 스트링) 자체가 필요 없다.

메뉴 목록 페이지가 가질 수 있는 상태 변수는 대표적으로 이런 것들이다.

- **카테고리**: 어떤 카테고리의 메뉴만 볼 것인가
- **검색어**: 어떤 단어로 찾을 것인가
- **정렬 기준**: 최신순 등 어떤 등록 일자 기준으로 정렬할 것인가
- **가격 범위**: 가격대로 필터링할 것인가
- **페이지 번호**: 전체 목록을 한 번에 다 보여줄 수 없으므로 몇 번째 페이지를 볼 것인가

이 상태 변수들을 담는 그릇이 요청 DTO다. 이때 알아두어야 할 내용이 하나 있다.

**요청 DTO(그리고 Entity·응답 DTO 전부)의 필드에는 기본 자료형(primitive, `long`, `int` 등)을 쓰지 않고, 래퍼 클래스(`Long`, `Integer`, `Boolean` 등)를 쓴다.** 이유는 "값이 전달되지 않았다"는 상태를 표현할 방법 때문이다. 기본 자료형은 `null`을 담을 수 없어서, 값이 없을 때 어쩔 수 없이 `0` 같은 기본값이 들어간다. 하지만 `0`은 "값이 없음"이 아니라 숫자로서 엄연히 의미를 갖는 값이다(예: 카테고리 아이디 `0`과 "카테고리를 지정하지 않음"은 서로 다른 의미여야 한다). 반면 래퍼 클래스는 `null`을 담을 수 있어서, "값이 없다"와 "값이 0이다"를 명확히 구분할 수 있다.

가격대처럼 자주 바뀌지 않는 고정된 구간이라면, 굳이 데이터베이스로 관리하지 않고 화면(프론트) 쪽에 값을 박아두는 선택도 가능하다.

## 8. Entity는 데이터베이스 원본, DTO는 화면이 원하는 형태

리포지토리가 다루는 Entity는 데이터베이스 테이블 구조를 SQL 조회 결과 그대로 자바 객체로 옮긴 것이다. 테이블에 있는 컬럼이 그대로 Entity의 속성이 된다 — 요리에 비유하면 **재료(춘장, 면, 양파)**에 해당한다.

서비스는 이 재료(Entity)들을 조합해서 화면에 필요한 요리(DTO)를 만들어낸다. DTO를 설계할 때 가장 먼저 떠올리는 것은 화면에 실제로 보이는 값들이다 — 메뉴 이름, 가격, 이미지처럼 사용자 눈에 직접 나타나는 항목들을 하나씩 채워 넣으면 된다.

그런데 여기서 그치면 안 되고, **눈에 보이지 않지만 식별을 위해 반드시 필요한 값**도 함께 담아야 한다는 것을 따로 생각해야 한다. 대표적인 것이 아이디다. 예를 들어 "좋아요" 버튼을 누를 때, 메뉴 이름만으로는 어떤 메뉴인지 서버에 정확히 전달할 수 없다 — 화면에는 보이지 않더라도 아이디가 함께 담겨 있어야 그 항목을 정확히 식별해서 처리할 수 있다.

## 9. 곁다리 API는 화면마다 별도로 만들고 공유하지 않는다

한 화면에 여러 데이터가 함께 나올 때는 먼저 **"이 화면의 주인공이 누구인가"**를 정해야 한다. 메뉴 목록 화면이라면 주인공은 메뉴이고, 그 화면에 카테고리가 함께 보이더라도 카테고리는 그 화면에서는 곁다리일 뿐이다. 카테고리는 메뉴 목록 화면 말고도 랜딩 페이지, 관리자 페이지 등 여러 화면에 반복해서 곁다리로 등장한다.

이렇게 곁다리로 등장하는 데이터는, 우연히 속성이 똑같아 보이더라도 화면마다 **별도의 DTO와 API로 따로 만든다.** 지금 당장 두 화면의 카테고리 DTO가 우연히 같은 모양이라고 해서 하나로 합쳐 공유하면, 나중에 한쪽 화면의 요구사항 때문에 그 DTO를 고쳤을 때 전혀 상관없는 다른 화면까지 함께 영향을 받는 문제가 생긴다. 페이지(유즈케이스) 단위로 독립적으로 만드는 원칙은 예외를 두지 않는다.

이 주인공/곁다리 구분은 URL에도 그대로 드러난다. **주인공은 URL 최상위에 단독으로 두고, 곁다리는 그 주인공 뒤에 하위 경로로 붙인다.**

```
GET /api/v1/menus              # 주인공 단독 — 메뉴 목록
GET /api/v1/menus/categories   # 메뉴가 주인공인 화면에서 곁다리로 쓰이는 카테고리
```

`/api/v1/categories`처럼 카테고리를 독립된 최상위 API로 만들지 않는 이유가 바로 여기에 있다 — 그렇게 하면 이 API가 "어느 화면의 무엇을 위한 것인지"가 URL만 보고는 드러나지 않는다. 반면 `/api/v1/menus/categories`는 "메뉴가 주인공인 컨텍스트에서 쓰이는 카테고리"임이 URL 구조 자체로 명확해진다. 이 두 API는 같은 컨트롤러(`MenuController`)가 함께 구현한다.

같은 이유로, 여러 컨트롤러 메서드의 URL에 공통된 앞부분이 반복된다면, 그 공통 부분은 클래스 레벨의 `@RequestMapping`으로 한 번만 선언하고 각 메서드에는 나머지 경로만 남긴다.

## 10. 코드로 보는 전체 구조

지금까지의 원칙(인터페이스 참조, 생성자 주입, `Df` 접두어, 래퍼 클래스, DTO/Entity 분리)을 하나의 메뉴 목록 기능으로 엮으면 다음과 같은 파일 구성이 된다.

```
controller/MenuController.java
dto/menu/MenuListRequestDto.java
dto/menu/MenuListResponseDto.java
entity/Menu.java
repository/MenuRepository.java       (인터페이스)
repository/DfMenuRepository.java     (구현체)
service/MenuService.java             (인터페이스)
service/DfMenuService.java           (구현체)
```

**응답 DTO** — 화면에 필요한 값과, 눈에 보이지 않지만 식별에 필요한 아이디를 함께 담는다.

```java
@Data
@NoArgsConstructor
public class MenuListResponseDto {
    private Long id;
    private String categoryName;
    private String korName;
    private String engName;
    private Integer price;
    private String imgSrc;
    private Boolean isLike;
}
```

**서비스 인터페이스** — "메뉴 목록을 줄 수 있다"는 약속만 정의한다.

```java
public interface MenuService {
    List<MenuListResponseDto> getList();
}
```

**서비스 구현체** — `@Component` 대신 의미가 특화된 `@Service`를 붙이고, 리포지토리를 생성자로 주입받는다.

```java
// @Component
@Service
public class DfMenuService implements MenuService {

    private final MenuRepository repository;

    public DfMenuService(MenuRepository repository) {
        this.repository = repository;
    }

    @Override
    public List<MenuListResponseDto> getList() {
        List<Menu> menus = repository.findAll();
        List<MenuListResponseDto> list = new ArrayList<>();
        // menus(Entity)를 list(DTO)로 변환하는 조합 로직이 이 자리에 들어간다
        return list;
    }
}
```

**리포지토리 인터페이스와 구현체** — Entity(`Menu`)를 반환하는 약속과 그 구현.

```java
public interface MenuRepository {
    List<Menu> findAll();
}
```

```java
public class DfMenuRepository implements MenuRepository {
    @Override
    public List<Menu> findAll() {
        return null; // 실제로는 DB 조회 로직이 들어간다
    }
}
```

**컨트롤러** — 인터페이스(`MenuService`)만 참조하고, 생성자로 주입받은 서비스에게 목록 조립을 위임한다. 목록 조회 함수와, 곁다리인 카테고리 조회 함수가 같은 클래스 안에 함께 있다.

```java
@RequestMapping("/api/v1/menus")
@RestController
public class MenuController {

    private final MenuService service;

    public MenuController(MenuService service) {
        this.service = service;
    }

    // 사용자에게 목록을 출력하는 함수 — 메뉴 목록 줘~
    @GetMapping
    public List<MenuListResponseDto> list(MenuListRequestDto request) {
        List<MenuListResponseDto> list = service.getList();
        return list;
    }

    // @RequestMapping("/api/v1/menus/categories")
    @GetMapping("categories")
    public List<MenuCategoryListResponseDto> categories() {
        // 카테고리 목록(곁다리) 조회 — 별도 DTO로 처리
        return new ArrayList<>();
    }
}
```

컨트롤러가 참조하는 것(`MenuService`, `MenuRepository`)은 항상 **인터페이스**이고, 실제로 스프링이 생성해서 꽂아주는 것은 그 뒤의 **구현체**(`DfMenuService`, `DfMenuRepository`)다. 이 참조 형식(추상)과 실사용 대상(구체)의 분리가, 지금까지 다룬 모든 원칙(인터페이스 기반 서비스, 생성자 주입, 결합형 Association)이 실제 코드에서 맞물리는 지점이다.

## 11. 정리

| 주제 | 핵심 |
|---|---|
| 학습 순서 | 계층 → 계층별 서비스 작성 → 계층 결합(DI/IoC) → (이후) JPA·트랜잭션·보안 |
| 구현체 이름 | 공통분모(인터페이스명)는 뒤에 유지, 특화된 수식어(`Df` 등)는 앞에 붙인다 |
| 스프링의 역할 | `@Component` 계열 표시만 하면, 생성과 결합(DI)을 스프링이 대신 해준다(IoC) |
| 어노테이션 특화 | `@Service`·`@Repository`는 의미가 특화된 `@Component`, `@Controller`만 URL 매핑 기능을 갖는다 |
| `@Controller` vs `@RestController` | 전자는 페이지명 반환(MVC), 후자는 데이터 반환(REST API) |
| POJO와 디스패처 서블릿 | 톰캣은 서블릿만 호출 가능 → 우리 컨트롤러(POJO)는 디스패처 서블릿(프론트 컨트롤러)을 거쳐 호출된다 |
| DI 방식 | 필드 주입 지양, 생성자 주입 사용. 의존성이 하나면 `@Autowired` 생략 가능 |
| 요청 DTO | 쿼리 스트링 = 페이지의 상태 변수(카테고리/검색어/정렬/가격대/페이지 등) |
| 자료형 선택 | 기본형 대신 래퍼 클래스를 써서 "값 없음(null)"과 "값 0"을 구분한다 |
| Entity vs DTO | Entity는 DB 원본(재료), DTO는 화면이 원하는 가공된 형태(요리) |
| 곁다리 API | 우연히 모양이 같아도 화면마다 별도로 만들고 절대 공유하지 않는다 |

이 모든 규칙은 결국 "구현체를 갈아 끼우거나 화면 요구사항이 바뀔 때, 그 영향이 다른 곳으로 번지지 않게 만드는 것"이라는 하나의 목표로 수렴한다.
