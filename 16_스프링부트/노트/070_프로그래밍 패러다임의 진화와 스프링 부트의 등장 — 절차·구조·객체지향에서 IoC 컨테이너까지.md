# 프로그래밍 패러다임의 진화와 스프링 부트의 등장 — 절차·구조·객체지향에서 IoC 컨테이너까지

코드가 길어질 때마다 개발자들이 그것을 정리하기 위해 어떤 방식을 차례로 시도해왔는지, 그 흐름의 끝에 왜 객체지향과 DI, 그리고 스프링 부트가 등장할 수밖에 없었는지를 정리한다.

## 1. 우리가 지금 배우는 것은 코딩이 아니라 "정리"다

입력받고 계산하고 출력하고 조건을 처리하고 반복하는 것 — 이것이 코딩(프로그래밍의 기초 문법)이다. 어떤 프로그램이든 본질은 이 정도로 단순하며, 복잡해 보이는 이유는 이 단순한 절차가 반복되는 양이 많아질 뿐이기 때문이다.

지금 배우는 것은 입출력 방법이나 연산자, 제어 구조가 아니다. 코드가 길어질 수밖에 없다는 것을 전제로, **그 길어진 코드를 어떻게 정리해서 알아보기 쉽고 유지보수하기 쉽게 만들 것인가**를 배우는 것이다. 이 질문에 대한 답이 시대 순으로 바뀌어온 과정이 곧 프로그래밍 패러다임의 역사다.

## 2. 구조적 프로그래밍 — 코드를 잘라서 계층을 만들다

한 줄로 쭉 이어지는 코드는 길어질수록 원하는 부분을 찾기가 어려워진다. 그래서 처음 시도한 정리 방법은 **코드를 기능 단위로 잘라서 함수로 이름 붙이는 것**이었다. 코드를 잘라 함수로 정의하면, 그 함수를 호출하는 코드만 보고도 전체 흐름을 거시적으로 파악할 수 있게 된다. 이렇게 코드를 미시적인 부분과 거시적인 부분으로 나누고, 거시적인 코드를 다시 함수로 묶으면 더 상위의 거시적인 코드가 만들어진다 — 이렇게 코드에 **계층**이 생기는 방식이 구조적 프로그래밍이다.

문제는 프로그램이 커질수록 이 계층 자체가 깊어진다는 점이다. 함수의 개수가 수백, 수천 개로 늘어나면 "코드 줄 수가 많아서 찾기 어렵다"는 문제가 "함수 개수가 많아서 어떤 함수를 찾아야 할지조차 알기 어렵다"는 문제로 형태만 바뀐 채 그대로 남는다. 도서관에 책이 너무 많아지면 카테고리를 몇 단계나 거쳐야 원하는 책을 찾을 수 있는지조차 애매해지는 것과 같다.

## 3. 객체지향의 탄생 — 데이터를 기준으로 함수를 묶는다

함수가 너무 많아져서 관리가 안 되는 문제를 풀기 위해, 개발자들은 함수들의 패턴에 주목했다. 성적을 다루는 코드든 회원을 다루는 코드든, 결국 모든 코드는 "입력 → 계산 → 출력"이라는 같은 구조를 반복하고 있었고, 달라지는 것은 **그 함수가 다루는 데이터**뿐이었다.

여기서 착안한 정리 방법이 "기능이 아니라 **데이터를 기준으로** 그 데이터를 사용하는 함수들을 한데 모으자"는 것이다. 성적이라는 데이터가 바뀌면 그 데이터를 쓰는 모든 함수가 영향을 받으므로, 아예 데이터와 그 데이터를 다루는 함수를 하나의 단위로 묶어 "이 데이터를 관리하는 책임자"라는 개념을 만든 것이다. 이 책임자가 바로 **캡슐**이고, 자바 같은 언어에서는 **클래스**로 구현된다.

캡슐화는 단순히 데이터와 함수를 한곳에 모으는 문법적 조치가 아니라, "이 데이터에 대한 서비스는 이 캡슐이 전담한다"는 **책임의 경계**를 만드는 것이다.

## 4. 단일 책임 원칙 — 같은 데이터를 쓴다고 같은 책임은 아니다

초기 객체지향에서는 "같은 데이터를 쓰는 함수는 다 같은 캡슐에 넣으면 된다"고 생각했지만, 실제로 묶어보면 성격이 다른 함수들이 뒤섞여 있다는 것을 알게 된다. 성적을 입력받고 출력하는 함수(입출력, I/O)와 성적을 계산하는 함수(업무 로직)를 예로 들면, 이 둘은 데이터는 같지만 **변경 이유가 다르다.**

- 입출력은 콘솔에서 웹으로, 웹에서 모바일로 실행 플랫폼이 바뀌면 함께 바뀐다 — **플랫폼에 종속된 책임**이다.
- 계산 로직은 콘솔이든 웹이든 모바일이든 성적 계산 공식이 달라지지 않는다 — **플랫폼과 무관한 업무 책임**이다.

이 둘을 한 캡슐에 묶어두면, 플랫폼이 바뀌어 입출력 코드를 수정할 때마다 업무 로직도 함께 재검토·재배포 대상이 되어버린다. 그래서 "하나의 캡슐은 하나의 변경 이유만 가져야 한다"는 **단일 책임 원칙(SRP)**에 따라 입출력을 담당하는 UI 계층과 업무를 담당하는 Service 계층을 분리하게 된다. 이 분리는 이후 항상 "UI ↔ Service ↔ Data"라는 기본 골격으로 반복해서 나타난다.

## 5. Has-a 관계 — Composition과 Association의 결합력 차이

책임을 분리하면 나뉜 캡슐들은 서로 협력해야 한다. UI가 Service의 계산 기능을 쓰려면 Service를 멤버로 가지고 있어야 하는데, 이렇게 한 객체가 다른 객체를 멤버로 갖는 관계를 **has-a 관계**라 부른다. 이 has-a 관계에는 결합력이 전혀 다른 두 가지 방식이 있다.

**Composition(구성)**: 멤버 객체를 자기 내부에서 직접 생성해서 갖는 방식이다.

```java
public class UI {
    private Service service = new Service(); // 내부에서 직접 생성

    public void run() {
        service.calculate();
    }
}

// 사용하는 쪽 — UI만 생성하면 끝, Service는 신경 쓸 필요가 없다
UI ui = new UI();
ui.run();
```

"나는 이 서비스만 쓸 것이다"라고 박아버리는 것과 같아서, 더 나은 구현체가 나와도 사용하는 쪽 코드를 직접 열어 `new` 대상 자체를 고쳐야 한다. 생성과 사용이 한 곳에 있는 만큼 결합력이 매우 강하며, 여기에는 두 가지 특징이 함께 따라온다.

- **생명주기 공유**: `UI` 객체가 사라지면 그 안에서 직접 만든 `Service` 객체도 함께 사라진다. 멤버 객체가 독립적으로 존재할 수 없고 전체(whole)에 완전히 종속된다.
- **교체 불가능**: 생성 시점에 타입이 코드에 고정되어버리므로, 실행 중에 다른 구현체로 바꿔 끼울 방법이 없다. 테스트할 때도 이 내부 생성을 피할 수 없어서, 가짜(Mock) 객체로 갈아끼우는 것이 불가능하다.

**Association(연관)**: 멤버 객체를 직접 생성하지 않고, 외부에서 이미 만들어진 것을 넘겨받는 방식이다.

```java
public class UI {
    private Service service; // 필드만 선언

    public UI(Service service) { // 외부에서 넘겨받음
        this.service = service;
    }

    public void run() {
        service.calculate();
    }
}

// 사용하는 쪽 — 어떤 Service를 쓸지는 여기서 결정한다
Service service = new Service(); // 또는 new BetterService();
UI ui = new UI(service);
ui.run();
```

필요한 객체를 넘겨받는 행위 자체가 **의존성 주입(Dependency Injection, DI)**이다. `UI` 입장에서는 `new Service()`라는 코드 자체가 아예 없으므로, 어떤 구현체가 들어올지는 몰라도 되고 알 필요도 없다. 이 방식은 Composition과 정반대되는 특징을 갖는다.

- **생명주기 독립**: `Service` 객체는 `UI`와 무관하게 이미 존재하고 있던 것을 빌려 쓰는 것뿐이라, `UI`가 사라져도 `Service`는 다른 곳에서 계속 살아있을 수 있다.
- **교체 가능**: Service 구현체가 새 버전으로 교체되어도, 그것을 사용하는 `UI` 쪽 코드는 전혀 바뀔 필요가 없다 — 그저 조립하는 외부 코드에서 다른 것을 넘겨주기만 하면 된다. 테스트할 때도 진짜 `Service` 대신 Mock을 넘겨주면 그만이다.

정리하면 두 관계 모두 "가진다(has-a)"는 점은 같지만, **"누가 생성하는가"** 하나의 차이가 결합력·생명주기·교체 가능성·테스트 용이성까지 전부 갈라놓는다. Composition은 부품을 아예 내 몸에 용접해버리는 것이고, Association은 부품을 소켓에 꽂아두는 것이어서 언제든 다른 부품으로 갈아 끼울 수 있는 것과 같다.

기업용 소프트웨어에서는 결합력을 낮추는 쪽이 압도적으로 유리하므로, 기본적으로 Composition이 아니라 Association(DI)을 선택한다.

## 6. 제어의 역전(IoC)과 컨테이너의 필요성

DI로 결합은 낮췄지만, 새로운 문제가 남는다 — **"결국 누군가는 객체를 생성하고 조립해서 넘겨줘야 한다."** 이 생성·조립 코드를 어딘가에 직접 두면, 구현체가 바뀔 때마다 그 조립 코드를 계속 수정해야 하는 부담이 사라지지 않는다.

이 부담 자체를 프로그램에서 없애기 위해, "객체 생성과 조립을 대신 해주는 존재"가 필요하다는 결론에 이른다. 원래는 내가 만든 함수나 객체는 내가 부르고 내가 사용하는 것이 자연스럽다. 그런데 그 조립의 흐름 자체를 외부의 다른 존재에게 맡기는 것 — 이것을 **제어의 역전(Inversion of Control, IoC)**이라 부른다. 콜백 함수도 실행의 흐름을 다른 대상에게 맡긴다는 점에서 같은 원리다.

이 "객체 생성과 조립을 대신해주는 보따리"가 바로 **IoC 컨테이너**이고, 스프링에서는 이를 **컨텍스트(Context)**라고 부른다. 컨텍스트라는 단어 자체가 "보따리"에 가까운 의미이며, 그 보따리에서 필요한 객체를 꺼내 쓰는 것(`getBean`)이 스프링 컨테이너의 기본 동작이다.

> DI는 스프링만의 기능이 아니라 객체지향이 원래 가지고 있던 결합력을 낮추는 특징이다. 다만 그 결합력을 낮추는 것을 극한까지 밀어붙이면 결국 "누가 조립할 것인가"라는 제어의 역전이 필요해지고, 스프링은 그 역할을 대신 해주는 도구일 뿐이다.

## 7. 스프링의 설정 방식 — XML vs 어노테이션

스프링에게 "무엇을 생성하고 조립해야 하는지"를 알려주는 방법은 두 가지다 — XML 설정 파일에 적어두는 방법과, 코드에 **어노테이션(annotation)**을 붙이는 방법이다.

**XML 방식**: 별도의 설정 파일(예: `spring-context.xml`)에 "이 클래스를 생성해서 이런 이름으로 등록해달라"는 내용을 적는다.

```xml
<bean id="orderRepository" class="com.example.JdbcOrderRepository" /> <!-- 주입되는 대상(의존성) -->
<bean id="orderService" class="com.example.OrderService"> <!-- 주입받는 대상(클라이언트) -->
    <constructor-arg ref="orderRepository" /> <!-- orderRepository 빈을 생성자로 주입 -->
</bean>
```

```java
// App에서 사용하는 쪽 — XML 파일을 읽어 컨테이너를 만들고, 완성된 빈을 꺼내 쓴다
ApplicationContext context = new ClassPathXmlApplicationContext("spring-context.xml");
OrderService orderService = context.getBean("orderService", OrderService.class);
```

설정이 코드와 분리되어 있지만, 그만큼 코드와 설정 파일을 오가며 관리해야 하고, 둘 사이에 불일치가 생기기 쉽다. 구현체를 교체하려면 설정 파일과 자바 코드를 모두 고쳐야 하는 경우가 많다.

주입해야 할 빈(bean)이 많아질수록 이 문제는 더 커진다. 대부분의 클래스를 스프링에게 맡기게 되면 XML 파일 안에 등록해야 할 빈 설정이 계속 늘어나 파일 하나가 감당하기 힘들 만큼 길어지고, 결국 컨텍스트 설정·보안 설정처럼 관심사별로 XML 파일 자체를 여러 개로 쪼개서 관리하게 된다. 즉 설정을 분리한 것이 아니라, 코드 대신 XML이라는 또 다른 형태의 코드가 여러 개로 늘어나는 것과 같아서 관리 부담이 줄어들지 않는다.

**어노테이션 방식**: 클래스 코드 위에 `@Component` 같은 어노테이션을 바로 붙인다.

```java
@Component
public class JdbcOrderRepository implements OrderRepository { ... }

@Service
public class OrderService {
    @Autowired
    private OrderRepository orderRepository;
}
```

```java
// App에서 사용하는 쪽 — 패키지를 스캔하게만 지정하면, @Component/@Service가 붙은 클래스를 찾아 알아서 조립해준다
@ComponentScan("com.example")
public class AppConfig { }

ApplicationContext context = new AnnotationConfigApplicationContext(AppConfig.class);
OrderService orderService = context.getBean(OrderService.class);
```

어노테이션도 결국 주석(comment)의 일종이지만, 우리가 흔히 쓰는 주석과 대상이 다르다.

- 사람이 보는 일반 주석: 설명을 위한 것으로, 컴파일하면 사라진다.
- 어노테이션: 컴파일해도 사라지지 않고 남아 있는 주석이다. 사람이 아니라 **그 코드를 실행하거나 처리하는 소프트웨어(번역기, 실행환경, 테스트 도구 등)**가 읽기 위한 것이기 때문이다.

이 실행환경이 읽는 주석이기 때문에 자연어로 자유롭게 쓸 수 없고, 미리 약속된 키워드로만 작성해야 한다. 예를 들어 어떤 테스트 도구가 "테스트가 필요한 코드에는 특정 키워드를 붙여달라"고 정해두면, 그 코드를 만드는 사람은 그 키워드를 그대로 붙여야 도구가 인식한다 — 이때 그 키워드를 정의하는 주체는 코드를 작성하는 사람이 아니라 **그 코드를 읽어 들이는 도구를 만든 쪽**이다. 스프링의 `@Component`, `@Autowired` 같은 어노테이션도 마찬가지로 스프링이 정의해둔 키워드이며, 스프링이 이 어노테이션을 읽고 "이 클래스는 내가 생성해야 하는 대상이구나", "이 자리에는 인터페이스에 맞는 구현체를 찾아서 주입해야 하는구나"를 판단한다.

별도 설정 파일이 없으므로 XML 방식과 달리 코드와 설정이 어긋나는 불일치가 생길 여지가 적다. 구현체를 교체할 때도 새 구현체 파일을 두고 기존 파일만 빼면, 재부팅 시 스프링이 알아서 새 구현체를 찾아 주입해준다 — 설정을 고칠 필요가 없다.

이런 이유로 실무에서는 어노테이션 방식을 훨씬 선호하지만, 예전 코드나 AI가 생성한 코드에는 XML 방식이 여전히 섞여 나올 수 있으므로 두 방식을 모두 알아둘 필요가 있다.

## 8. 스프링의 압박과 스프링 부트의 등장

스프링은 원래 DI(IoC 컨테이너) 기능만 제공하던 프레임워크였지만, 점점 트랜잭션, MVC, 보안 등 기능을 계속 추가하면서 그에 딸린 라이브러리 수도 함께 늘어났다. DI 기능 하나에만도 여러 개의 라이브러리가 필요했는데, 웹·트랜잭션·보안까지 다 쓰려면 최소 필요한 라이브러리가 수십 개(예: 48개)에 이르렀고, 그 각각의 설정까지 맞춰야 했다. 개발자들이 이 복잡함 때문에 스프링을 떠나 다른 대안을 찾기 시작할 정도였다.

이 문제를 해결하기 위해 등장한 것이 **스프링 부트(Spring Boot)**다. 스프링 부트는 스프링과 다른 결의 프로젝트로, 스프링을 대체하는 것이 아니라 스프링을 "다시 시작(재부팅)"하듯 쓰기 쉽게 감싸는 역할을 한다.

- **스타터(Starter) 의존성**: 수십 개의 개별 라이브러리를 낱개로 받는 대신, 용도별로 묶어놓은 스타터 하나만 추가하면 된다.
- **자동 설정(Auto Configuration)**: 스타터 안에 합리적인 기본 설정이 이미 들어 있어서, 별도로 세세한 설정을 하지 않아도 바로 동작한다.
- **임베디드 톰캣(Embedded Tomcat)**: 예전에는 톰캣 서버를 별도로 설치하고 그 위에 애플리케이션을 서블릿 단위로 배포해야 했다. 스프링 부트는 서버(톰캣)를 애플리케이션 안으로 들여보내서, `main()` 함수 하나만 실행하면 서버까지 함께 뜨는 구조로 바꿨다 — 일반 자바 프로그램을 실행하듯 웹 애플리케이션을 실행할 수 있게 된 것이다.

내부적으로 스프링 부트도 결국 스프링을 사용하지만, 개발자가 다루는 라이브러리 구성과 설정 방식이 완전히 달라진다는 점에서 스프링과는 별개의 버전 체계를 갖는다(예: 스프링 자체는 7.x대, 스프링 부트는 4.x대처럼 독립적으로 버전이 매겨진다).

## 9. 정리

| 단계 | 정리 방식 | 한계 |
|---|---|---|
| 절차적 프로그래밍 | 한 줄로 이어지는 코드 | 길어질수록 원하는 부분을 찾기 어려움 |
| 구조적 프로그래밍 | 코드를 함수로 잘라 계층화 | 함수 개수가 폭증하면 다시 찾기 어려워짐 |
| 객체지향(캡슐화) | 데이터를 기준으로 함수를 묶어 캡슐(클래스)을 만듦 | 서로 다른 책임(플랫폼/업무)이 한 캡슐에 섞이는 문제 |
| 단일 책임 원칙 | 변경 이유가 다른 책임을 별도 캡슐로 분리(UI/Service/Data) | 분리된 캡슐끼리 협력할 방법이 필요 |
| Composition | 필요한 객체를 직접 생성해서 사용 | 결합력이 매우 강해 구현체 교체·테스트가 어려움 |
| Association / DI | 필요한 객체를 외부에서 주입받아 사용 | 결국 누군가는 조립을 대신해야 함 |
| IoC 컨테이너 | 객체 생성과 조립 자체를 컨테이너(스프링 컨텍스트)에 위임 | 설정(XML/어노테이션)과 라이브러리 관리 부담 |
| 스프링 부트 | 스타터·자동 설정·임베디드 톰캣으로 스프링의 설정·라이브러리 부담을 없앰 | — |

결국 절차적 코드를 정리하려는 반복된 시도(구조화 → 캡슐화 → 책임 분리 → 결합력 완화 → 제어의 역전)의 끝에 스프링의 DI 컨테이너가 있고, 스프링이 쓰기 무거워지자 그 무게를 다시 덜어낸 결과가 스프링 부트다.
