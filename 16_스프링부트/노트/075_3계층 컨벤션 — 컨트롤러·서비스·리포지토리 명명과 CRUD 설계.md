# 3계층 컨벤션 — 컨트롤러·서비스·리포지토리 명명과 CRUD 설계

3계층을 "일단 돌아가게" 만드는 것과, 계층별 역할이 명확해서 다른 사람(또는 AI)이 코드를 봐도 오해하지 않는 구조를 만드는 것은 전혀 다른 일이다. 이 노트는 CRUD 기능 하나를 실제로 설계하면서 겪게 되는 세세한 결정들 — 메서드 이름, DTO 이름, HTTP 메서드 선택, 응답 상태 코드, 입력을 받는 방식 — 을 왜 그렇게 정하는지 정리한다.

## 1. 계층을 나눈다는 것의 의미 — 왜 AI 시대에 더 중요해졌는가

계층이라는 것은 식당의 부서나 조직의 부서처럼, 역할을 분리해서 **"이 코드는 어디에 있을 것이다"를 명확하게 예측 가능**하게 만드는 장치다. 계층 구조가 어설프게 걸쳐져 있으면(예: 서빙하는 쪽이 요리까지 손대는 식), 당장은 동작하더라도 기능이 추가될 때마다 서로 영향을 주고받다가 결국 "이거 어디서부터 손대야 하지"라는 상황을 만나게 된다.

이게 왜 AI를 쓸 때 특히 중요하냐면, **AI는 지금 보이는 코드 구조를 그대로 참고자료로 삼는다.** 어설픈 구조가 한 군데 있으면 "아, 이렇게 하는 거구나"라고 학습해서 그 패턴을 계속 복제한다. 게다가 AI 세션이 바뀌면 기존 코드를 전부 다시 확인하지 않고(비용 문제로) 또 자기 나름의 방식으로 코드를 만들기 때문에, 기준이 흔들린 코드베이스는 세션이 거듭될수록 점점 더 엉망이 된다. 그래서 개발자가 할 일은 **기준을 스스로 명확히 세워두고, 어떤 기능을 고쳐도 다른 기능에 영향이 가지 않도록 고립화를 잘 해두는 것**이다.

## 2. 서빙·주방·재료상 — 3계층의 역할을 식당에 비유하면

- **컨트롤러 = 홀 서빙**: 사용자(손님)의 요청을 받아서 주방(서비스)에 전달한다. 서빙하는 사람이 요리에 관여하면 안 되듯, 컨트롤러는 업무 로직(비즈니스 로직)을 처리하지 않는다. 요청을 받아 전달하고, 결과를 그대로 토스(전달)할 뿐이다.
- **서비스 = 주방(요리사)**: 재료(Entity)를 받아 실제 업무 로직을 수행해서 요리(DTO)를 만든다.
- **리포지토리 = 재료상**: 데이터 소스(DB, 파일 등)에서 날것의 재료(Entity)를 가져다주는 역할만 한다.

예를 들어 "짜장면을 주세요"라는 요청이 들어오면, 컨트롤러는 그 요청과 함께 전달된 상태 값(쿼리 스트링 등)을 **DTO**로 포장해서 서비스에 넘긴다. 서비스는 리포지토리로부터 춘장·면·양파 같은 재료(Entity 여러 개)를 받아와 조합해서 짜장면(DTO)을 완성하고, 컨트롤러는 그 결과를 그대로 사용자에게 돌려준다.

**절대로 하면 안 되는 것**: 리포지토리가 "조합까지 끝낸 결과"(예: 카테고리 이름까지 포함한 메뉴)를 서비스에 건네주는 것. 그건 재료상이 요리를 하고 있는 셈이다. 요리(조립)가 여러 군데(리포지토리, 서비스 등)에 흩어지면, 나중에 "이 값은 대체 어디서 채워진 거야?"를 찾아 헤매게 된다. 계층을 나누는 이유는 정확히 이걸 막기 위해서다 — **코드가 어디에 있는지 명확하게 알 수 있어야 한다.**

## 3. 계층은 트리 구조여야 한다 — 같은 계층끼리 서로 참조 금지

서비스 하나가 다른 서비스의 로직을 재사용하고 싶어지는 순간이 온다(예: 짜장 서비스가 짬뽕 서비스의 조리 과정 일부를 가져다 쓰고 싶은 경우). 이렇게 같은 계층끼리 서로 참조하기 시작하면, 처음엔 좋은 의도였더라도 점점 **같은 계층 안에서 참조가 얽히는 구조**가 되어 나중엔 코드가 어디 있는지 알 방법이 없어진다.

계층 구조는 나무(트리) 또는 조직의 부서 구조처럼, **반드시 아래로 수렴**해야 하고 같은 계층끼리 엮이면 안 된다. 공통으로 필요한 로직이 있다면 같은 계층끼리 서로 참조하는 대신, **공통 부모나 별도의 유틸로 분리**해서 그걸 각자 이용하는 방식으로 가야 한다.

**나쁜 예 — 형제 서비스를 직접 참조**

```java
public class JjajangService {
    private JjamppongService jjamppongService; // 짬뽕 서비스를 직접 참조

    public Jjajang makeJjajang() {
        String noodle = jjamppongService.boilNoodle(); // 짬뽕이 가진 면 삶기 로직을 빌려 씀
        ...
    }
}
```

이렇게 하면 `JjajangService`가 `JjamppongService`에 의존하게 된다. 나중에 짬뽕 서비스 내부 구조가 바뀌면 짜장 서비스까지 영향을 받고, 반대로 짬뽕 쪽에서도 짜장 쪽 로직을 끌어다 쓰기 시작하면 서로가 서로를 참조하는 순환 구조가 생긴다.

**좋은 예 1 — 공통 로직을 유틸 클래스로 분리**

```java
public class NoodleUtil {
    public static String boilNoodle() {
        return "삶은 면"; // 면 삶는 공통 로직
    }
}

public class JjajangService {
    public Jjajang makeJjajang() {
        String noodle = NoodleUtil.boilNoodle(); // 형제가 아니라 공통 유틸을 씀
        ...
    }
}

public class JjamppongService {
    public Jjamppong makeJjamppong() {
        String noodle = NoodleUtil.boilNoodle(); // 얘도 같은 유틸을 씀
        ...
    }
}
```

**좋은 예 2 — 공통 부모 클래스로 분리**

```java
public abstract class NoodleService {
    protected String boilNoodle() {
        return "삶은 면";
    }
}

public class JjajangService extends NoodleService {
    public Jjajang makeJjajang() {
        String noodle = boilNoodle(); // 부모가 가진 공통 기능을 물려받아 씀
        ...
    }
}

public class JjamppongService extends NoodleService {
    public Jjamppong makeJjamppong() {
        String noodle = boilNoodle(); // 얘도 같은 부모를 통해 씀
        ...
    }
}
```

나쁜 예는 `JjajangService → JjamppongService`처럼 형제가 형제를 가리키는 가로 방향 화살표가 생기지만, 좋은 예는 `JjajangService, JjamppongService → NoodleUtil`(또는 `NoodleService`)처럼 둘 다 같은 지점을 바라보는 세로 방향 구조가 된다. 이것이 "아래로 수렴한다"는 말의 실체다 — 모든 화살표가 결국 공통 부모나 유틸이라는 한 지점으로 모여야지, 같은 층위에 있는 것들끼리 서로를 가리키면 안 된다.

## 4. 컨트롤러 메서드 이름 — 통일이 먼저, 정답은 그다음

컨트롤러의 CRUD 메서드 이름을 지을 때 "메뉴 목록 줘"를 코드로 어떻게 표현할지는 사실 여러 방식이 다 답이 될 수 있다. 예를 들어 "메뉴 목록을 달라"는 `getList`로도, "메뉴 목록을 출력해달라"는 의미로도 표현할 수 있다. 중요한 것은 **둘 중 뭐가 정답이냐가 아니라, 하나로 통일해서 끝까지 지키는 것**이다. 이 노트의 사례에서는 투표를 통해 `getList`로 통일했다.

또한 메서드 이름에 **도메인 이름을 중복해서 넣지 않는 것**도 중요한 컨벤션이다. `MenuController` 안에서 `getMenuList`라고 쓰는 것은 "메뉴 마을에서 메뉴에게 메뉴를 달라"고 두 번 말하는 것과 같다. 패키지/클래스 이름에 이미 도메인이 드러나 있으므로, 메서드 이름에서는 굳이 반복하지 않고 `getList`로 충분하다.

## 5. CRUD와 HTTP 메서드 — PATCH가 개념적으로 맞지만 PUT을 쓰는 이유

데이터를 다루는 API는 문서를 요청할 때 쓰던 GET/POST만으로는 부족하다. CRUD에 대응하는 HTTP 메서드는 다음과 같다.

| CRUD | HTTP 메서드 |
|---|---|
| Create | `POST` |
| Read | `GET` |
| Update | `PUT` 또는 `PATCH` |
| Delete | `DELETE` |

Update에서 `PUT`과 `PATCH` 중 무엇을 쓸지는 고민이 필요하다. 개념적으로는 `PATCH`(부분 수정)가 더 정확하다 — 이름만 바꾸고 싶을 때 레코드 전체를 다시 보낼 필요가 없어 보이기 때문이다. 하지만 현실적으로는 속성 하나하나를 개별적으로 수정하는 API를 다 만들면, 속성이 6개면 수정 조합의 경우의 수가 팩토리얼로 늘어나는 조합 폭발이 일어난다.

그래서 실무에서는 **무엇을 바꾸든 레코드 전체를 통째로 덮어쓰는 방식의 업데이트 하나만 준비**하고(바뀌지 않는 값은 같은 값으로 그대로 채워서 보냄), 이는 개념적으로 `PUT`에 해당한다. 결론: **개념상으로는 PATCH가 맞지만, 현실적으로는 PUT을 쓰는 것이 일반적이다.**

## 6. 응답이 필요한가 없는가 — 화면 반영 여부로 판단한다

각 CRUD 동작이 응답(response)을 반환해야 하는지는 **"그 결과가 화면에 즉시 반영되어야 하는가"**로 판단한다.

- **Create(생성)**: 응답이 **필요하다.** 사용자가 등록한 메뉴가 화면에 즉시 보여야 하는데, 서버가 자동으로 채우는 값(예: 생성 시간, 자동 증가 ID)까지 포함한 **완전한 데이터**를 클라이언트가 받아야 화면에 제대로 반영할 수 있다. 생성 시간처럼 서버가 채워야 하는 값은 클라이언트가 전달하면 안 된다(위조 가능해지기 때문) — 그래서 더더욱 서버가 응답으로 그 값을 돌려줘야 한다.
- **Update(수정)**: 응답이 **필요하다.** 수정한 내용이 화면에 반영되어야 하기 때문이다.
- **Delete(삭제)**: 데이터 응답은 **필요 없다.** 삭제된 데이터를 다시 받아올 이유가 없다. 다만 "정상적으로 삭제되었다"는 **상태(status)**는 알려줘야 한다.

## 7. HTTP 상태 코드와 ResponseEntity

웹 응답에는 데이터와 별개로 **상태 코드**가 함께 온다.

| 상태 코드 | 의미 | 주로 쓰는 상황 |
|---|---|---|
| 200 OK | 요청 성공, 기본값 | GET, PUT/PATCH (별도 지정 안 해도 자동으로 감) |
| 201 Created | 생성 성공 | POST(Create) |
| 204 No Content | 성공했지만 반환할 내용 없음 | DELETE |

단순히 객체를 `return`하면 상태 코드는 자동으로 200이 간다. 201이나 204처럼 **기본값이 아닌 상태를 명시**하고 싶을 때는 `ResponseEntity`로 감싸서 반환한다.

```java
// 생성 — 201 Created + 바디
return ResponseEntity.created(uri).body(responseDto);

// 삭제 — 204 No Content, 바디 없음
return ResponseEntity.noContent().build();
```

여기서 주의할 점: `ResponseEntity<Void>`처럼 쓸 때는 **참조형 `Void`**(대문자 V)를 써야 한다. 기본형 `void`는 제네릭의 타입 인자로 쓸 수 없기 때문이다.

이미 200(기본값)으로 충분한 GET 요청에 굳이 `ResponseEntity`를 써서 200을 명시할 필요는 없다 — **기본값은 기본값대로 두고, 특별히 다른 상태를 보내야 할 때만 `ResponseEntity`를 쓰는 것**이 불필요한 코드를 줄이는 선택이다. (이 역시 일관성 있게 항상 `ResponseEntity`를 쓸지, 필요할 때만 쓸지는 팀의 합의로 정하면 된다 — 정답이 하나만 있는 문제는 아니다.)

## 8. DTO 이름 짓기 — Request/Response는 겹치면 안 된다

사용 목적별로 DTO 이름을 패턴화해서 기억해야 다른 사람도 바로 이해할 수 있다.

- 목록 요청: `MenuListRequestDto`
- 상세 요청(식별자만 필요한 경우가 많아 생략 가능): `MenuDetailRequestDto` 또는 그냥 `@PathVariable Long id`
- 생성 요청/응답: `MenuCreateRequestDto` / `MenuCreatedResponseDto`
- 수정 요청/응답: `MenuUpdateRequestDto` / `MenuUpdatedResponseDto`
- 상세 조회 응답: `MenuDetailResponseDto`

여기서 중요한 설계 판단 하나 — **Create의 응답 DTO와 Update의 응답 DTO를 같은 이름(예: `MenuResponseDto`)으로 묶어서 재사용하면 안 된다.** 둘 다 "메뉴 하나를 반환한다"는 점에서 비슷해 보이지만, 같은 DTO를 공유하는 순간 생성 기능과 수정 기능이 "한 몸"으로 강하게 결합된다. 나중에 한쪽(예: 수정 응답)에만 필드를 추가해야 할 때, 공유하던 다른 쪽(생성 응답)까지 영향을 받는다. 그래서 `MenuCreatedResponseDto`, `MenuUpdatedResponseDto`처럼 **용도별로 이름을 특화**해서 분리한다. (생성은 `Create`, 응답 이름은 과거형 `Created`; 수정은 `Update`, 응답 이름은 과거형 `Updated`로 시제를 맞추는 것도 관례다.)

삭제처럼 **식별자 하나만 필요한 경우**에는 굳이 별도의 요청 DTO 클래스를 만들지 않고, `@PathVariable`로 ID 하나만 받는 것이 더 간결한 선택이 될 수 있다. 이런 것은 "맞다/틀리다"의 문제가 아니라 팀이 어느 쪽을 선택할지 정하면 되는 문제다.

## 9. URL 설계 — 식별자는 어디에 붙이는가

수정·삭제·상세조회처럼 **특정 레코드 하나**를 대상으로 하는 요청은 목록 URL 뒤에 식별자를 이어 붙인다.

```java
@RequestMapping("/menus")
@RestController
public class MenuController {

    @PostMapping
    public ResponseEntity<MenuCreatedResponseDto> create(MenuCreateRequestDto requestDto) {
        return ResponseEntity.created().body(...);
    }

    @GetMapping
    public List<MenuListResponseDto> getList(MenuListRequestDto requestDto) { ... }

    @GetMapping("{id}")
    public MenuDetailResponseDto getDetail(@PathVariable("id") Long id) { ... }

    @PutMapping("{id}")
    public MenuUpdatedResponseDto update(@PathVariable("id") Long id, MenuUpdateRequestDto requestDto) { ... }

    @DeleteMapping("{id}")
    public ResponseEntity<Void> delete(@PathVariable("id") Long id) {
        return ResponseEntity.noContent().build();
    }
}
```

수정/삭제 URL에 "update"라는 단어를 또 넣을 필요는 없다 — 이미 `PUT`/`DELETE`라는 HTTP 메서드 자체가 "무엇을 할지"를 말해주고 있으므로, URL에는 "어떤 레코드를"에 해당하는 식별자(`id` 또는 slug)만 붙이면 된다.

## 10. 입력을 받는 방식 — 쿼리 스트링(@RequestParam)과 JSON 바디(@RequestBody)는 다르다

같은 "p=1&c=2" 형태의 데이터라도, 그것이 **URL 쿼리 스트링으로 오는지 JSON 바디로 통째로 오는지**에 따라 받는 방법이 완전히 다르다.

전통적인 웹 폼 방식(또는 브라우저가 직접 만드는 요청)에서는 `key=value&key=value` 형태로 쪼개져서 오기 때문에, 스프링이 변수 이름만 맞춰주면 각 키-값을 자동으로 매핑해줄 수 있다.

```java
// 키=값 형태로 쪼개져서 오는 경우 (쿼리 스트링 또는 전통적인 폼 전송)
@GetMapping
public List<MenuListResponseDto> getList(@RequestParam("p") int page, @RequestParam("c") int categoryId) { ... }
```

하지만 이 프로젝트처럼 **Next.js 서버가 중간에서 사용자 요청을 받아 백엔드로 다시 요청하는 구조**에서는, Next.js가 자바스크립트로 데이터를 모아 **JSON으로 통째로** 백엔드에 보낸다. JSON 바디는 키-값이 분리되어 오는 게 아니라 **통짜 문자열 하나**로 오기 때문에, `@RequestParam`처럼 "이름만 맞으면 자동으로 채워주는" 방식이 전혀 동작하지 않는다. 이 통짜 바디를 "쪼개서 그 안의 키와 같은 이름의 setter를 찾아 채워 넣으라"고 지시하는 것이 `@RequestBody`다.

반면 URL 경로(path)에 박혀 있는 값(`/menus/3`의 `3`)은 쿼리 스트링도 JSON 바디도 아니라서 위 두 방법 어느 쪽으로도 자동으로 담기지 않는다. 이 경우에는 `@PathVariable`로 별도 지정해야 하며, 매개변수 이름과 URL 템플릿의 중괄호 안 이름(`{id}`)이 일치해야 한다.

## 11. Entity란 정확히 무엇인가 — "테이블 구조"가 아니라 "레코드 하나"

Entity를 "테이블 구조에 대응하는 자바 객체"라고만 알아두면 반쯤만 맞은 것이다. 더 정확히 말하면, 테이블의 컬럼(속성)들이 모여 하나의 **데이터 구조**를 이루고, **그 데이터 구조로 실제로 채워진 레코드 한 건**이 바로 엔티티다. 즉 엔티티는 "구조"가 아니라 "그 구조를 가진 실존하는 값 하나"를 가리킨다. 레코드가 여러 건 모이면 "엔티티 집합"이라고 부를 수 있다.

흥미로운 지점은, **DB에서 리포지토리로 올 때의 데이터와 리포지토리에서 서비스로 전달될 때의 데이터가 값 자체는 완전히 같다**는 것이다. 둘 다 "엔티티"라고 부르지만, 값이 같다면 왜 굳이 리포지토리라는 계층을 거칠까? 답은 **포장지가 다르기 때문**이다. DB 쪽에서 오는 것은 자바가 아닌 날것의 데이터(드라이버 레벨의 결과, 로우 데이터)이고, 리포지토리를 통과하고 나면 자바 객체 형식으로 포장된다. 이 포장 과정에서 리포지토리는 두 가지를 숨긴다.

1. **기술적 세부사항을 숨긴다**: 서비스는 자바 문법으로 값을 꺼내 쓰면 되고, 그 아래에 있는 JDBC·드라이버 같은 기술적인 내용을 알 필요가 없다.
2. **데이터 출처를 숨긴다**: 그 재료가 DB에서 왔는지, 파일에서 왔는지, 로컬인지 원격인지를 서비스는 몰라도 된다.

그리고 이 변환 과정에서 **데이터 자체(각 속성값)는 추가되거나 변형되면 안 된다** — 엔티티가 서비스로 넘어갈 때 그 속성은 그대로 전달되어야 한다.

## 12. 리포지토리 메서드 이름이 Find 계열로 바뀐 이유

예전에는 리포지토리의 메서드 이름도 서비스와 똑같이 `getList`처럼 지은 적이 있었다. 문제는 "메뉴 목록을 달라"는 똑같은 표현이 컨트롤러·서비스·리포지토리 세 군데에서 전부 반복되면, 이름만 보고는 그게 **재료를 가져오는 요청**인지 **요리를 완성한 결과**인지 구분이 안 된다는 것이다. 재료의 목록과 완성된 요리의 목록은 결코 같은 게 아닌데, 셋 다 "리스트"라고 부르면 혼란스럽다.

그래서 데이터를 "주는" 역할을 하는 쪽의 이름을 더 명확하게 바꾸기 시작했다. 리포지토리(저장소)라는 이름 자체가 "저장소의 역할"을 의미하므로, 저장소가 하는 일은 결국 **자료를 찾아주는 것**이다. 그래서 리포지토리의 메서드는 `getList` 대신 `findById`, `findAll`, `findByCategoryId`처럼 **Find 계열의 이름**으로 짓는 관례가 자리 잡았다.

이 컨벤션을 어긴다고 프로그램이 멈추거나 에러가 나지는 않는다. 하지만 계층별 역할과 각 계층이 다루는 재료가 무엇인지 잘 이해하고 있는 사람이라면, 그 구분을 이름에도 반영해서 **오해를 유발하지 않는 코드**를 짤 수 있다. "돌아가긴 하지만 오해를 유발하는 코드"는 결국 버그의 씨앗이 된다 — 그래서 함수·클래스·계층의 이름을 잘 짓는 능력이, 큰 프로그램을 설계하는 능력의 기반이 된다.
