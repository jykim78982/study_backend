# 전역변수와 캡슐화, 객체지향의 역할 개념

## 1. 전역변수

**전역변수**란 특정 함수 안이 아니라, **프로그램 전체 어디서든 접근할 수 있는 변수**를 말한다.

- 자바에서 전역변수를 만들려면 **`static`을 붙여야 한다**
- 특별한 이유가 없는 이상 **사용하지 않는 것이 좋다**

### 전역변수가 왜 문제인가

- 전역변수를 쓰고 있는 함수는, 그 함수를 **다른 파일로 옮기면 더 이상 동작하지 않는다** — 함수가 자기 파일 밖(전역 공간)에 있는 값에 의존하고 있기 때문
- 함수가 **독립적이지 못하게 된다** — 재사용하려 해도 전역변수까지 통째로 딸려가야 해서, 함수 하나만 뚝 떼어서 다른 곳에 가져다 쓸 수 없다
- 전역변수를 손대는 순간 **전역 공간 전체에 영향력을 행사**하게 된다 — 어디서 그 값을 바꿨는지 추적하기 어려워지고, 결국 **코드 전체가 서로 얽힌 한 덩어리**가 되어버린다

## 2. 변수 선언 vs 정의 — 위치에 따라 의미가 달라진다

**변수를 선언한다**는 것은 **공간을 확보하는 것**이다. 그런데 같은 모양의 코드라도, **어디에 쓰였는지**에 따라 "선언"이 되기도 하고 "정의"에 그치기도 한다.

| 위치 | 의미 | 특징 |
|---|---|---|
| 함수 안 | 선언 | 실행 흐름이 지나가면서 실제로 공간을 마련함 |
| 함수 밖, `static` 없이 | 정의만 됨 | 실행 흐름이 가지 않는 영역이라, 공간을 마련하지 않음. 선언하거나 연산할 수 없음 |

즉 클래스 영역(함수 밖)에 있는 건 **속성을 정의**하는 것일 뿐이고, 그 자리에서는 변수 선언이나 연산 자체가 있을 수 없다.

### 변수 선언의 두 가지 의미

| 시점 | 의미 |
|---|---|
| 컴파일할 때 | 컴파일러한테 "이런 기호(이름)가 있다"고 알려주는 것 |
| 실행할 때 | 실제로 **공간을 마련**하는 것 |

### `static`이 하는 일

- `static int x;`처럼 클래스 영역에 `static`이 붙으면, 이건 더 이상 "클래스의 속성"이 아니라 **함수 밖에서 "선언"한 전역변수**가 된다
- `static`은 **전역**의 의미를 갖는 키워드다
- 전역변수는 **프로세스가 올라가자마자 제일 먼저** 메모리에 잡힌다

## 3. 전역변수 vs 인스턴스변수

| | 전역변수 | 인스턴스변수 |
|---|---|---|
| 구분 키워드 | `static` | 없음 |
| 메모리에 잡히는 시점 | 프로세스가 올라가자마자 | 객체를 생성할 때 |

## 4. 전역함수 vs 서비스(인스턴스 메소드)

| | 전역함수 (static 메소드) | 서비스 (인스턴스 메소드) |
|---|---|---|
| 앞에 `static` | 있음 | 없음 |
| 호출 방식 | 클래스명과 같이 쓰기도 하지만, **직접 호출 가능** | **객체를 통해서만** 사용 가능 |
| 정체 | 그냥 함수 | 특정 객체(역할자)에 속한 동작 |

- 다른 클래스에 있는 `static` 함수도, 클래스 안에 적혀 있을 뿐 사실상 **전역변수와 같은 성격**이다 — 클래스 소속처럼 보이지만 특정 객체 없이도 부를 수 있기 때문
- 일반적으로는 전역함수를 **static 메소드**, 서비스를 **instance 메소드**라고 부른다

### 메소드라는 이름

클래스 안에 있는 모든 함수는 **메소드**라고 부른다.

- `static`이 있으면 → **스태틱 메소드**
- `static`이 없으면 → **인스턴스 메소드**

## 5. 객체지향 프로그래밍 — 캡슐화

### 세상이 흔히 말하는 캡슐화

> 데이터(속성)와 그 데이터를 다루는 동작(함수)을 하나로 묶는 것

그런데 여기서 짚고 넘어가야 할 질문이 있다.

- 데이터와 함수를 그냥 묶기만 하면 캡슐화인가?
- 묶는 데에는 **기준**이 있어야 하지 않을까?
- "객체지향은 실세계를 반영했다"고 하는데, 단순히 묶으면 그게 정말 실세계를 반영하는 것인가?

### 기준 — 역할을 나누는 것

캡슐화를 좀 더 실용적으로 풀면 다음 순서로 이해할 수 있다.

1. 어떤 **기능**이 필요하면 함수를 만든다
2. 그 기능은 필연적으로 **데이터**를 필요로 한다
3. 그 데이터를 관리하면서, 기능을 **서비스**로 제공하는 **역할자**를 만든다 → 이게 캡슐화다

정리하면, 프로그램은 **역할자**들로 이루어진다.

```
역할이 있다
  → 역할은 역할자가 맡는다
  → 역할자한테 데이터 공간을 준다
  → 그 데이터 공간을 이용하는 서비스를 제공받는다
```

즉 **캡슐은 역할자다.**

## 6. 어떤 역할자들이 있는가

우리가 지금 만들고 있는 프로그램을 포함해서, 거의 대부분의 프로그램은 다음과 같은 역할로 계층을 나누어서 만든다. 필요에 따라 계층을 추가하거나 뺄 수도 있다.

```
UI(작은 조각 UI : 컴포넌트) ←→ 업무(여러 업무) ←→ 콜렉션 ←→ 엔티티
```

## 7. 캡슐 간의 관계를 만드는 두 가지 방법

| 방법 | 이름 | 의미 |
|---|---|---|
| 캡슐끼리 조립하기 | HAS-A 관계 | 한 캡슐이 다른 캡슐을 **가지고(속성으로 품고)** 쓰는 방식 |
| 캡슐을 확장하거나 수정해서 쓰기 | IS-A 관계 (상속) | 기존 캡슐을 물려받아 확장 — **다형성**과 연결됨 |
