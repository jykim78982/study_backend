# 구조화에서 객체지향으로

## 1. 문제 — 코드가 길어진다

프로그래밍이란 결국 **실행 절차를 적는 것**이다. 절차가 많아지면 코드는 계속 길어진다.

**해결책**: 코드를 나누자.

- 데이터도 그냥 흩어두지 말고 **그룹으로 나누자** → **구조적인 프로그램(코드의 구조화)**

코드를 구조화하는 이유는 여러 가지다.

- 중복 제거를 위해 나누기
- 재사용을 위해 나누기
- 코드가 커서 나누기
- 협업을 위해 나누기

## 2. 구조화만으로는 부족하다

함수를 계속 나누다 보면 새로운 문제가 생긴다. 함수가 늘어날수록 이름이 계속 충돌하고, 함수가 너무 많아져서 원하는 함수를 찾기도 어려워진다. 결국 함수를 **수납할 공간**이 필요해지는데, 어떤 기준으로 묶어야 할지가 애매하다 — 기능별로 묶어야 할까, 아니면 데이터별로 묶어야 할까?

함수가 구조화된 데이터(예: `Exam` 같은 구조체)의 필드를 **외부에서** 직접 가져다 쓰면, 그 필드 이름이 바뀔 때마다 그 데이터를 쓰는 모든 함수를 같이 고쳐야 한다. 그래서 함수를 "기능별"이 아니라 **데이터 기준으로 모아두는 게 낫겠다**는 결론에 이르는데, 이게 객체지향으로 바뀌어가는 시작점이다.

함수를 데이터 기준으로 묶으면, 이번엔 그 함수들을 **관리할 책임자**가 필요해진다
→ 이 책임자가 바로 **객체(Object)**다.
객체지향 프로그래밍(Object Oriented Programming)은, 한 코드 안에 흩어져 있던 함수들을 **클래스(구조체)** 안에 넣어서 관리하는 것이다 — 클래스를 관리자·책임자(직업명)로 두고, 데이터와 함수를 함께 맡긴다.
코드에서 객체를 두고 그 객체에게 책임을 지워 책임자로 만들면, 그 다음부터는 객체에게 **서비스를 불러오는 방식**으로 코드를 쓰게 된다.

## 3. 실습으로 확인한 3단계 — 성적 프로그램

`step1_struct`, `step2_static`, `step3_capsule` 세 버전으로, 같은 "성적 입력/출력 프로그램"이 구조화 → 객체지향으로 넘어가는 과정을 순서대로 실습했다.

### 3-1. `step1_struct` — 데이터만 구조화, 함수는 아직 밖에 있음

`Exam`은 필드만 있는 순수 데이터 뭉치(구조체)다.

```java
public class Exam {
    int kor;
    int eng;
    int math;
}
```

함수(`inputExam`, `printExam`)는 여전히 `App` 안에 있고, `Exam`을 매개변수로 받아서 **밖에서** 그 필드를 직접 건드린다.

```java
private static void inputExam(Exam exam) {
    ...
    exam.kor = kor;
    exam.eng = eng;
    exam.math = math;
}

private static void printExam(Exam exam) {
    int kor = exam.kor;
    int eng = exam.eng;
    int math = exam.math;
    ...
}
```

여기서 2장에서 말한 문제가 그대로 드러난다 — `exam.kor`, `exam.eng`, `exam.math`처럼 `App`이 `Exam`의 필드 이름을 하나하나 알고 직접 접근한다. `Exam`의 필드 이름이 바뀌면 `App` 안의 이 함수들도 전부 고쳐야 한다. 데이터(`Exam`)와 그 데이터를 다루는 동작(`inputExam`, `printExam`)이 **분리**되어 있는 상태다.

### 3-2. `step2_static` — 함수를 클래스 안으로 옮겼지만, 아직 OOP를 지원하지 않는 경우

이 단계의 `Exam.java`에는 `init`, `inputExam`, `printExam`이 전부 `static` 함수로 들어와 있다.

```java
static void init(Exam exam) {
    exam.kor = 50;
    exam.eng = 50;
    exam.math = 50;
}
```

함수의 **위치**만 보면 `Exam` 클래스 안으로 들어왔으니 얼핏 객체지향처럼 보인다. 하지만 여전히 `Exam exam`을 **매개변수로 받아서**, `exam.kor`처럼 "밖에서 안을 들여다보는" 방식 그대로다. `static`이 붙어 있으니 `Exam.init(exam)`처럼 객체 없이도 부를 수 있고, 결국 3-1단계의 `App.inputExam(exam)`/`App.printExam(exam)`과 **본질적으로 똑같은 패턴**이다 — 함수가 사는 파일만 `App.java`에서 `Exam.java`로 옮겨졌을 뿐, "데이터를 자기 자신이 직접 관리하는" 캡슐화는 아직 일어나지 않았다.

### 3-3. `step3_capsule` — 데이터와 서비스가 하나로 묶임

이름 그대로 **capsule(캡슐)** 단계다. `Exam`이 자기 데이터(`kor`, `eng`, `math`)와, 그 데이터를 다루는 서비스(`init`, `input`, `print`)를 전부 스스로 가지고 있다.

```java
public class Exam {
    int kor;
    int eng;
    int math;

    void init() {
        this.kor = 50;
        this.eng = 50;
        this.math = 50;
    }

    void input() {
        ...
        this.kor = kor;
        this.eng = eng;
        this.math = math;
    }

    void print() {
        int kor = this.kor;
        int eng = this.eng;
        int math = this.math;
        ...
    }
}
```

`App`은 이제 `Exam`의 필드 이름을 전혀 몰라도 된다. `App`이 아는 건 오직 **`Exam`이 어떤 서비스를 제공하는지**뿐이다.

```java
Exam exam = new Exam();
exam.init();
...
exam.input();
exam.print();
```

`App`이 `exam.kor`처럼 필드를 직접 건드리는 코드는 한 줄도 없다. 3-1단계에서 문제였던 "필드 이름이 바뀌면 `App`도 같이 고쳐야 한다"는 문제가 사라진다 — `Exam` 내부에서 필드 이름을 바꿔도, `Exam`이 제공하는 서비스(`init()`, `input()`, `print()`)의 이름과 사용법만 그대로면 `App`은 전혀 영향받지 않는다.

## 4. 세 단계 비교

| | 구조화만 | 과도기 | 캡슐화 |
|---|---|---|---|
| 데이터 | `Exam`에 있음 | `Exam`에 있음 | `Exam`에 있음 |
| 함수 위치 | `App` | `Exam`(static) | `Exam`(instance) |
| 필드 접근 | `App`이 `exam.kor`로 직접 | 둘 다 존재 | `Exam` 내부에서만 `this.kor` |
| `App`이 아는 것 | `Exam`의 필드 이름까지 | 점점 서비스 위주로 이동 | `Exam`의 서비스 이름만 |
| 결합도 | 높음 (필드 이름 바뀌면 `App`도 고쳐야 함) | 낮아지는 중 | 낮음 |

이 흐름은 [[023_전역변수와 캡슐화, 객체지향의 역할 개념]]에서 정리한 "데이터를 관리하면서 서비스로 제공하는 역할자를 만드는 것이 캡슐화다"라는 정의를, 실제 코드 3단계로 직접 확인한 것이다.
