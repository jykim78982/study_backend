# 자바에서 설정이란 무엇인가 — 선택권을 위한 코드 분리

리플렉션 SQL 생성기가 왜 하드코딩에 갇혀 있었는지, 그리고 그 문제를 "설정(Configuration)"이라는 개념으로 어떻게 풀어내는지를 정리한다.

## 1. 리플렉션 SQL 생성기의 한계

앞서 만든 SQL 생성기는 `User` 클래스의 필드 이름(`id`, `username`, `email`)을 그대로 SQL 컬럼명으로 쓰고, 클래스 이름을 그대로 테이블명으로 가정했다.

문제는 데이터베이스 쪽 컬럼명이 `user_name`으로 바뀌거나 테이블명이 `t_user`로 바뀌어야 하는 경우다. 지금 구조로는 **클래스의 소스 코드 자체를 고쳐서 다시 컴파일**해야만 SQL이 바뀐다. 이미 배포된 애플리케이션의 소스를 열어 고치고 재배포하는 것은 비효율적인 것을 넘어, 운영 환경에서는 거의 불가능한 방식이다.

## 2. "설정"이란 — 선택권을 주기 위해 데이터를 코드에서 분리하는 것

**설정(Configuration)**이란, 사용자에게 선택권을 주기 위해 값을 코드에서 떼어내 별도의 데이터로 관리하는 것이다.

- **에어컨 리모컨**: 에어컨 본체(코드)는 냉방·난방 기능을 갖고 있지만, 원하는 온도(데이터)는 사용자가 리모컨으로 정한다. 온도를 바꾸겠다고 본체를 뜯어 회로를 바꾸지는 않는다.
- **프린터**: 용지 크기나 양면 인쇄 여부를 설정으로 열어두면, 프린터 자체(하드웨어·펌웨어)를 바꾸지 않고도 사용자가 다양한 방식으로 쓸 수 있다.

프로그래밍에서 이 둘의 역할은 명확히 나뉜다.

| 구분 | 질문 | 예 |
|---|---|---|
| 코드(Code) | 무엇을 할 수 있는가 (기능, 로직) | 필드를 읽어와 SQL 문장 구조를 조립하는 로직 |
| 설정(Configuration) | 어떻게 할 것인가 (값, 이름, 경로, 옵션) | "필드 `username`은 컬럼 `user_name`으로 바꿔서 SQL을 만들어라" |

코드만 있으면 사용자가 끼어들 자리가 없다. 여기에 설정을 추가하면, **코드를 바꾸지 않고 설정값만 바꿔서** 다른 데이터베이스 스키마·다른 환경에 대응할 수 있게 된다.

## 3. 설정을 `.properties` 파일로 저장하기

자바에서 설정을 외부 파일로 분리하는 대표적인 방법은 XML과 `.properties` 두 가지인데, 가장 간단한 형식은 `.properties`다.

**형식 규칙**

- `key=value` 형식으로 한 줄에 하나씩 작성한다.
- `#` 또는 `!`로 시작하는 줄은 주석이다.
- 값에 공백이 있으면 따옴표로 감싸거나 백슬래시(`\`)로 이스케이프한다.

**`db-config.properties` 예시** (클래스 루트, 즉 `main()`이 있는 파일과 같은 경로에 둔다)

```properties
# 데이터베이스 테이블 이름
tableName=t_user

# 필드명 -> 컬럼명 매핑
columnName.username=user_name
columnName.age=user_age
```

**`Properties` 클래스로 읽기** — `java.util.Properties`가 이 파일을 읽어 key로 value를 조회할 수 있게 해준다.

```java
import java.io.FileInputStream;
import java.io.IOException;
import java.util.Properties;

public class ConfigLoader {
    public static Properties loadConfig(String filePath) throws IOException {
        Properties props = new Properties();
        try (FileInputStream fis = new FileInputStream(filePath)) {
            props.load(fis);
        }
        return props;
    }
}
```

## 4. SQL 생성기에 설정을 적용하기

하드코딩된 이름 대신, `properties`에서 읽어온 설정을 사용하도록 SQL 생성기를 고친다.

```java
import java.lang.reflect.Field;
import java.util.Properties;

public class ConfigurableSqlGenerator {

    public String generateInsertSql(Object obj, Properties config) throws Exception {
        String className = obj.getClass().getSimpleName();

        // 1. 설정에서 테이블 이름을 가져온다 (없으면 클래스 이름 소문자로 기본값 사용)
        String tableName = config.getProperty("tableName", className.toLowerCase());

        StringBuilder sql = new StringBuilder();
        sql.append("INSERT INTO ").append(tableName).append(" (");

        Field[] fields = obj.getClass().getDeclaredFields();
        boolean first = true;

        for (Field field : fields) {
            if (java.lang.reflect.Modifier.isStatic(field.getModifiers())) continue;

            String fieldName = field.getName();

            // 2. 설정에서 컬럼 이름을 가져온다 (없으면 필드 이름 그대로 사용)
            // 키 형식: columnName.필드명
            String columnName = config.getProperty("columnName." + fieldName, fieldName);

            if (!first) {
                sql.append(", ");
            }
            sql.append(columnName);
            first = false;
        }

        sql.append(") VALUES (");
        for (int i = 0; i < fields.length; i++) {
            if (i > 0) sql.append(", ");
            sql.append("?");
        }
        sql.append(")");

        return sql.toString();
    }
}
```

```java
import java.io.FileInputStream;
import java.io.IOException;
import java.util.Properties;

public class App {
    public static void main(String[] args) {

        Properties config = new Properties();
        try (FileInputStream fis = new FileInputStream("db-config.properties")) {
            config.load(fis);
        } catch (IOException e) {
            System.err.println("설정 파일을 읽을 수 없습니다: " + e.getMessage());
            return;
        }

        User user = new User();
        user.setId(1);
        user.setUsername("홍길동");
        user.setEmail("hong@newlecture.com");

        ConfigurableSqlGenerator generator = new ConfigurableSqlGenerator();
        try {
            String sql = generator.generateInsertSql(user, config);
            System.out.println("생성된 SQL: " + sql);
        } catch (Exception e) {
            e.printStackTrace();
        }
    }
}
```

**실행 결과 비교**

| 상황 | 결과 |
|---|---|
| 설정 파일 없음 (기본값 사용) | `INSERT INTO user (name, age) VALUES (?, ?)` |
| `db-config.properties` 적용 (`tableName=t_user`, `columnName.name=user_name`, `columnName.age=user_age`) | `INSERT INTO t_user (user_name, user_age) VALUES (?, ?)` |

핵심은 **같은 자바 코드(`ConfigurableSqlGenerator`)가 그대로 실행되었는데, 설정 파일만 바뀌어서 다른 SQL이 생성되었다**는 점이다. 이것이 "사용자에게 선택권을 준다"는 것의 실체다 — 운영자는 코드를 열어보지 않고 `.properties` 파일만 고치면 된다.

## 5. 실제 프레임워크에서의 설정

이 원리는 실제 자바 프레임워크 전반에 동일하게 적용된다.

- **서블릿(Servlet)**: `web.xml`(XML 형식) 또는 `.properties` 파일로 필터, 리스너, 초기 파라미터를 설정한다.
- **스프링(Spring)**: `application.yml` 또는 `application.properties`로 데이터베이스 URL, 포트, 빈(Bean)의 속성 값을 설정한다.

## 6. 정리

| 개념 | 핵심 |
|---|---|
| 설정(Configuration) | 사용자에게 선택권을 주기 위해 값을 코드에서 분리해 관리하는 것 |
| 코드 vs 설정 | 코드는 "무엇을 할 수 있는가", 설정은 "어떻게 할 것인가" |
| `.properties` | `key=value` 형식의 가장 단순한 외부 설정 파일 형식 |
| 적용 결과 | 코드를 재컴파일하지 않고, 설정 파일만 바꿔서 동작을 바꿀 수 있다 |
| 실무 연결 | `web.xml`, `application.yml`/`application.properties` 모두 같은 원리 — "코드는 고정, 값은 외부에서 읽는다" |

어떤 프레임워크든 결국 이 구조를 따른다 — 리플렉션이 "클래스의 구조를 실행 중에 알아내는 방법"이라면, 설정은 "그 구조를 어떻게 다룰지의 규칙을 코드 밖에 두는 방법"이다. 이 둘이 합쳐지면 코드를 건드리지 않고도 동작을 바꿀 수 있는 유연한 프레임워크가 만들어진다.
