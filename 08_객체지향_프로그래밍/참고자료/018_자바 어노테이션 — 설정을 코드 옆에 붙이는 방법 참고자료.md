# 자바 어노테이션 — 설정을 코드 옆에 붙이는 방법

`.properties` 파일로 두었던 설정(테이블명·컬럼명 매핑)을 어노테이션으로 옮기면 무엇이 달라지는지, 그리고 어노테이션을 직접 정의하는 문법(`@interface`)을 SQL 생성기 예제로 정리한다.

## 1. 어노테이션이란 무엇인가 — "소프트웨어가 읽는 메모"

"Annotation"은 사전적으로 주석·메모·표시를 뜻하지만, 평소 쓰는 `//`나 `/* */` 주석과는 성격이 다르다.

- **일반 주석(`//`)**: 사람이 코드를 이해하도록 돕는 용도다. 컴파일러가 무시하며, 컴파일 후 `.class` 파일에는 남지 않는다 — 실행 시점에는 이미 사라진 상태다.
- **어노테이션(`@`)**: 사람도 읽지만, 본질적으로는 **다른 프로그램(소프트웨어)이 실행 시점에 읽기 위해 남겨둔 메타데이터**다.

"코드를 읽는 프로그램"의 구체적인 예:

- **자바 컴파일러**: `@Override`를 보고 "이 메서드가 정말 부모 클래스의 메서드를 오버라이드한 것이 맞는지" 검증한다.
- **프레임워크(Spring, JPA 등)**: `@Autowired`를 보고 "이 필드에 어떤 객체를 주입해야 하는지" 판단한다.
- **우리가 만드는 SQL 생성기**: `@Column`을 보고 "이 필드가 데이터베이스의 어떤 컬럼에 매핑되는지" 판단한다.

즉 어노테이션은 사람을 위한 메모가 아니라 **소프트웨어를 위한 명령어 또는 정보**다.

## 2. 왜 외부 설정 파일 대신 어노테이션을 쓰는가

[[017_자바에서 설정이란 무엇인가 — 선택권을 위한 코드 분리 참고자료]]에서는 `db-config.properties`라는 외부 파일에 테이블명·컬럼명을 정의했다.

```properties
tableName=t_user
columnName.username=user_name
```

이 방식은 코드와 설정이 분리되어 있어서, 코드만 봐서는 `username` 필드가 실제로 어떤 컬럼에 매핑되는지 알 수 없다 — 코드와 설정 파일을 번갈아 봐야 한다.

어노테이션은 설정(매핑 정보)을 **코드 바로 옆에** 붙여서 이 문제를 해결한다.

```java
@Column("user_name")
private String username;
```

`username` 필드를 보는 순간 이것이 `user_name` 컬럼에 대응한다는 것을 바로 알 수 있다. 파일 대신 코드 옆에 붙이는 것이 유리한 이유는 결국 **가독성**과 **결합도**(관련 정보가 물리적으로 붙어 있는가) 문제다.

## 3. 어노테이션의 세 가지 특징

- **독자적인 주체가 읽는다**: 어노테이션을 읽는 주체는 사람이 아니라 소프트웨어(번역기, 우리가 만든 도구, JVM, 프레임워크, 컴파일러)다.
- **정의가 필수다**: 사람이 임의로 아무 문구나 적을 수 있는 일반 주석과 달리, **정의되지 않은 어노테이션을 사용하면 컴파일 에러**가 난다. `@Column`을 쓰려면 `Column`이라는 어노테이션을 먼저 정의해두어야 한다.
- **구조화된 데이터다**: 단순 텍스트가 아니라, 값(인자)을 가질 수 있는 구조화된 데이터다.

## 4. 어노테이션은 누가 정의하는가

어노테이션은 **그 코드를 읽는 도구나 환경을 만드는 쪽**이 정의한다. 이는 [[070_프로그래밍 패러다임의 진화와 스프링 부트의 등장 — 절차·구조·객체지향에서 IoC 컨테이너까지]]에서 다룬 "누가 정의한 키워드인가"와 같은 원리다.

- **자바 실행환경이 이미 정의해둔 것(Built-in)**: `@Override`(메서드가 오버라이드되었음을 명시), `@Deprecated`(더 이상 사용되지 않는 코드임을 경고), `@SuppressWarnings`(컴파일러 경고를 무시). 이들은 별도로 정의할 필요 없이 바로 쓸 수 있다.
- **우리가 직접 정의하는 것(Custom)**: 이번 글에서 다루는 `@Column`이 여기 해당한다.

"누가 정의하느냐"가 "누가 읽느냐"를 결정한다 — 우리가 `@Column`을 정의하면, 우리가 만든 `SqlGenerator`가 그 값을 읽어온다.

## 5. 어노테이션을 정의하는 문법 — `@interface`

```java
public @interface Column {
    String value();
}
```

- 어노테이션은 내부적으로 인터페이스를 기반으로 동작하기 때문에 `interface`라는 단어가 들어간다.
- `@interface` 뒤에 오는 이름(`Column`)이 그 인터페이스의 이름이 된다.
- `String value();`는 이 어노테이션이 가질 수 있는 속성(멤버)을 정의한다.
- `value`는 특별한 이름이다 — 사용할 때 `@Column("user_name")`처럼 괄호 안에 값만 넣으면 그 값이 `value`에 저장된다. 만약 이름을 `name`으로 정의했다면 `@Column(name="user_name")`처럼 이름을 명시해서 써야 한다.

## 6. properties 설정을 어노테이션으로 바꾸기

**1) `Column` 어노테이션 정의**

```java
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Target(ElementType.FIELD) // 필드에만 사용 가능
@Retention(RetentionPolicy.RUNTIME) // 실행 시점까지 유지 (리플렉션으로 읽기 위해)
public @interface Column {
    String value();
}
```

- `@Target(ElementType.FIELD)`: 이 어노테이션은 클래스나 메서드가 아니라 필드에만 붙일 수 있음을 명시한다.
- `@Retention(RetentionPolicy.RUNTIME)`: 컴파일 후에도 클래스 파일에 정보를 남기고, JVM 실행 시 리플렉션으로 읽을 수 있게 한다. 이 설정이 없으면 실행 시점에 어노테이션 정보 자체가 사라져 읽을 수 없다.

**2) `User` 클래스에 어노테이션 붙이기** — `columnName.username=user_name`이라는 설정을 필드 바로 위로 옮긴다.

```java
public class User {
    private int id;

    @Column("user_name") // username 필드는 user_name 컬럼에 매핑
    private String username;

    @Column("user_email") // email 필드는 user_email 컬럼에 매핑
    private String email;

    public String getUsername() { return username; }
    public void setUsername(String username) { this.username = username; }
    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }
    public int getId() { return id; }
    public void setId(int id) { this.id = id; }
}
```

**3) `AnnotationSqlGenerator`** — 리플렉션으로 필드를 순회하며, `@Column`이 있으면 그 값을, 없으면 필드 이름 그대로를 컬럼명으로 쓴다.

```java
import java.lang.reflect.Field;

public class AnnotationSqlGenerator {

    public String generateInsertSql(Object obj) throws Exception {
        String className = obj.getClass().getSimpleName();
        String tableName = className.toLowerCase(); // 테이블명은 여전히 클래스 이름 소문자로 가정

        StringBuilder sql = new StringBuilder();
        sql.append("INSERT INTO ").append(tableName).append(" (");

        Field[] fields = obj.getClass().getDeclaredFields();
        boolean first = true;

        for (Field field : fields) {
            if (java.lang.reflect.Modifier.isStatic(field.getModifiers()))
                continue;

            // 1. 필드에 @Column 어노테이션이 있는지 확인
            Column columnAnnotation = field.getAnnotation(Column.class);

            String columnName;
            if (columnAnnotation != null) {
                columnName = columnAnnotation.value(); // 2. 있으면 그 value를 컬럼명으로 사용
            } else {
                columnName = field.getName(); // 3. 없으면 필드 이름 그대로 사용
            }

            if (!first) {
                sql.append(", ");
            }
            sql.append(columnName);
            first = false;
        }

        sql.append(") VALUES (");
        for (int i = 0; i < fields.length; i++) {
            if (i > 0) sql.append(", ");
            sql.append("?");
        }
        sql.append(")");

        return sql.toString();
    }
}
```

**실행용 `App`**

```java
public class App {
    public static void main(String[] args) {
        User user = new User();
        user.setId(1);
        user.setUsername("john_doe");
        user.setEmail("john@example.com");

        AnnotationSqlGenerator generator = new AnnotationSqlGenerator();

        try {
            String sql = generator.generateInsertSql(user);
            System.out.println("생성된 SQL:");
            System.out.println(sql);
        } catch (Exception e) {
            e.printStackTrace();
        }
    }
}
```

**결과 비교**

| 방식 | 결과 | 특징 |
|---|---|---|
| properties 파일 기반 (이전 편) | `INSERT INTO user (id, user_name, user_email) VALUES (?, ?, ?)` | 설정 파일이 없으면 기본 필드명(`username`)이 그대로 쓰인다 |
| 어노테이션 기반 (이번 편) | `INSERT INTO user (id, user_name, user_email) VALUES (?, ?, ?)` | 설정 파일 없이도, 코드를 컴파일하는 순간 매핑 정보가 고정된다 |

## 7. 어노테이션 방식의 장점과 한계

**장점**

- **가독성 향상**: 필드 바로 옆에 매핑 정보가 있어서, 코드를 읽는 순간 데이터베이스 스키마와의 관계를 파악할 수 있다.
- **파일 관리 부재**: `db-config.properties`를 별도로 만들고 경로를 설정하고 배포 시 함께 올려야 하는 번거로움이 없다.
- **IDE 지원**: IntelliJ, Eclipse 같은 IDE가 어노테이션을 인식해서 값 누락이나 오류를 컴파일 전에 경고해줄 수 있다.

**한계**

- **변경이 어렵다**: `.properties`는 배포 후에도 운영자가 파일만 고치고 재시작하면 되지만, 어노테이션은 코드의 일부라서 값을 바꾸려면 소스를 수정하고 다시 컴파일·배포해야 한다.
- **환경별 분리가 어렵다**: 개발 DB와 운영 DB의 컬럼명이 다르면, 어노테이션 하나로 두 환경을 모두 대응하기 어렵다. 이런 경우 어노테이션과 `.properties`를 함께 쓰거나, 프로파일 기반 설정을 사용해야 한다.

## 8. 정리

| 개념 | 핵심 |
|---|---|
| 어노테이션 | 컴파일 후에도 남아, 소프트웨어(컴파일러·프레임워크·우리 도구)가 실행 중에 읽는 메타데이터 |
| 일반 주석과의 차이 | 대상이 사람이 아니라 소프트웨어이고, 컴파일해도 사라지지 않는다 |
| 정의 문법 | `@interface 이름 { 타입 value(); }`, 내부적으로 인터페이스 기반 |
| `@Target` | 어노테이션을 붙일 수 있는 위치(필드/클래스/메서드 등)를 제한 |
| `@Retention` | 어노테이션 정보가 언제까지 유지되는지 지정 — 리플렉션으로 읽으려면 `RUNTIME` 필수 |
| properties와의 관계 | 배타적이지 않다 — "코드의 구조·관계"는 어노테이션이, "환경마다 자주 바뀌는 값"은 외부 설정 파일이 더 적합하며 목적에 따라 섞어 쓴다 |

결국 어노테이션은 "설정을 어디에 둘 것인가"라는 질문에 대해 **코드 옆**이라는 답을 준 것이고, `.properties`는 **코드 밖**이라는 답을 준 것이다. Spring이 `@Component`, `@Autowired` 같은 어노테이션과 `application.properties`를 동시에 쓰는 이유도 이 두 방식이 서로 다른 종류의 설정에 적합하기 때문이다.
