# 다형성과 추상 클래스, Object

## 1. `super` 영역 안에는 메소드가 없다 — 메모리 구조로 보기

`SmartDevice`(자식)를 생성하면 부모 영역(`super`)이 먼저 만들어지고, 그 위에 자식이 확장한 나머지 부분이 만들어진다. 여기서 흔히 하는 착각이 있다.

- **잘못된 생각**: `super` 영역 안에 필드(데이터)와 메소드(함수)가 같이 들어가 있다
- **바른 생각**: `super` 영역에는 **데이터만** 들어간다. 메소드는 애초에 객체 공간에 올라가지 않는다

이유는 메모리 구조에 있다. 메모리는 크게 **코드영역(텍스트 영역)**과 **데이터영역(스택+힙)**으로 나뉜다.

- **코드영역**: 메소드(함수)의 실행 코드가 고정되어 있는 곳. 함수는 이 영역에 딱 한 번 자리 잡고, 호출될 때마다 실행 흐름만 그 위치로 왔다 갔다 할 뿐이다
- **데이터영역(스택/힙)**: 실제 필요한 데이터 공간이 올라가는 곳

`new`로 객체를 만들면, **그 객체의 데이터(필드)만 힙에 올라간다.** 메소드는 객체마다 복사되어 올라가는 게 아니라, 코드영역에 이미 고정되어 있는 걸 여러 객체가 공유해서 실행 흐름만 갖다 쓰는 것이다. 그래서 `super` 영역(부모 부분)에도 데이터만 존재하고, 메소드는 존재하지 않는다 — 메소드는 애초에 "객체 공간의 일부"가 아니기 때문이다.

## 2. 업캐스팅이 항상 안전한 이유 — 공간이 아니라 구조의 문제

```java
Device device = new SmartDevice();
```

이게 가능한 이유를 오해하기 쉽다.

- **오답 예상**: "`SmartDevice`가 `Device`보다 크니까(필드가 더 많으니까) 큰 게 작은 그릇에 들어가는 거 아니야?"
- **바른 이유**: 이건 "공간 크기"의 문제가 아니라 **참조(구조)**의 문제다

`SmartDevice` 객체 안에는 `Device`(부모) 부분이 **통째로, 완전한 형태로** 포함되어 있다(`super`로 초기화되는 그 영역). 그래서 `Device` 타입 참조 변수는 `SmartDevice` 객체 안에서 자신이 아는 `Device` 부분을 **항상 안전하게** 찾아낼 수 있다.

반대로는 성립하지 않는다. `SmartDevice`(자식)가 `Device`(부모)만 가리키는 참조를 담을 수 있는 공간은 없다 — 진짜 `Device` 객체(자식이 아닌, 순수 부모 객체)에는 `SmartDevice`가 기대하는 추가 필드를 위한 공간 자체가 존재하지 않기 때문이다. 그래서 부모 타입으로 자식을 참조하는 것(업캐스팅)은 항상 안전하지만, 그 반대(다운캐스팅)는 실제 객체가 진짜 그 자식 타입이 아닌 이상 위험하다.

## 3. 배열로 여러 자식을 일괄 관리하기

`Animal`이라는 부모에게서 태어난 세 자식 `Dog`, `Cat`, `Bird`가 있다고 하자. 이들을 개별적으로 따로 관리할 수도 있지만, **일괄 관리하려는 이유가 충분할 때가 많다.**

```java
Animal[] animals = new Animal[3];
animals[0] = new Dog();
animals[1] = new Cat();
animals[2] = new Bird();
```

배열의 타입은 `Dog`도 `Cat`도 아닌, **셋의 공통 부모인 `Animal`**이어야 한다. `Animal`을 부모로 갖는 자식들은 모두 `Animal` 타입으로 참조 가능하므로, 이런 식으로 형식이 다른 자식들을 하나의 배열에 묶어서 일괄적으로 다룰 수 있다.

## 4. 부모-자식 관계가 아닌 것들을 묶어야 한다면 — 추상 클래스

```java
Duck duck = new Duck();
Airplane airplane = new Airplane();
?[] list = new ?[2];
```

`Duck`과 `Airplane`이 원래 상속 관계가 아니라면, 이 배열의 타입을 뭘로 써야 할지 애매해진다 — 공통 부모가 없어서 일괄 관리가 불가능하다. 이럴 때 **`Duck`과 `Airplane`을 일괄 관리하기 위한 목적으로 새로운 클래스를 만든다.** 이게 **추상 클래스**다("날 수 있는 것"이라는 의미의 `Flyer` 정도로 만들 수 있다). 원래 없던 "공통 부모"를 필요에 의해 새로 만들어내는 것이다.

**왜 일괄 관리가 필요한가 — 그림판 예시**

그림판에서 선, 원, 네모 같은 도형 객체를 만든다고 하자. 이걸 종류별로 따로 배열에 담을 수도 있다(선 배열, 원 배열, 네모 배열). 하지만 이렇게 나눠 놓으면 **"어떤 순서로 그려졌는지"**가 사라진다. 하나의 배열에 순차적으로 담아야 그 순서를 그대로 유지할 수 있고, 이건 **undo/redo** 같은 기능을 구현할 때 반드시 필요하다. 모든 도형이 한 공간에 담겨있어야 관리가 쉬워진다.

## 5. 추상화의 의미 — 구체적인 것들의 공통점만 추리기

**추상적**이라는 말은 "구체적이지 않다"는 뜻이다. 예를 들어:

- SUV, 클래식카, 세단을 구체적이지 않게 묶으면 → **자동차**
- 농부, 어부, 탈곡하는 사람을 구체적이지 않게 묶으면 → **사람**
- 선, 네모, 원을 구체적이지 않게 묶으면 → **도형**

객체를 일괄적으로 관리하려는 목적이 있을 때는, 이렇게 **개별 객체를 좀 더 추상적인 시선으로 바라볼 필요**가 있다. "도형"이라는 형식을 만들어서 선/네모/원의 부모로 두면, 이 형식을 통해 셋을 일괄 관리할 수 있게 된다.

## 6. 자바가 이미 만들어둔 추상화의 끝판왕 — `Object`

자바를 설계할 당시(제임스 고슬링) 이미 C++로 객체지향이 무르익어 있던 시기였다. 앞으로 개발자들이 만들어낼 수많은 클래스들을 **전부 일괄적으로 관리할 수 있는 형식**이 필요하다는 걸 자바는 처음부터 알고 있었다. 그래서 자바 세계에 존재하는 **모든 형식을 끌어안을 수 있는 클래스**를 이미 만들어뒀다 — 바로 **`Object`**다.

- `Object`는 구현한 게 아무것도 없는 빈 깡통이다
- 자바의 **모든 클래스는 예외 없이 `Object`를 부모로 갖는다** (직접 `extends`를 안 써도 자동으로 그렇게 된다)
- `Object` 배열에는 `Device` 객체든 `SmartDevice` 객체든 `int[]` 배열이든, **무엇이든 담을 수 있다**

```java
Object[] list = new Object[2];
list[0] = new Device();
list[1] = new SmartDevice();
```

## 7. `Object`로 일괄 관리할 때의 문제 — 형변환의 불편함

`Object`가 이미 있는데 왜 굳이 우리가 필요할 때마다 새 추상 클래스를 만들어야 할까?

`Object` 배열의 원소에 `.`을 찍어 메소드를 확인해보면, **`Object`가 갖고 있는 기본 기능만** 나온다 — 실제로 그 자리에 들어있는 객체(`Device`, `SmartDevice` 등) 고유의 기능은 보이지 않는다. `Object`로 참조하고 있는 이상, **참조만 가능할 뿐 실제 객체 본인의 기능은 쓸 수 없다.**

그 기능을 쓰려면 반드시 **형변환(캐스팅)**을 거쳐야 한다.

```java
SmartDevice d = (SmartDevice) list[0];
d.run();

// 또는 한 줄로
((SmartDevice) list[0]).run();
```

괄호가 겹겹이 필요한 이유는 **연산 우선순위** 때문이다. `(SmartDevice) list[0].run()`처럼 쓰면 캐스팅이 `.run()` 호출보다 먼저 적용되지 않을 수 있어서, 캐스팅 대상 전체를 괄호로 한 번 더 묶어줘야 한다.

**결론**: `Object`로 일괄 관리하면 매번 이런 형변환을 거쳐야 해서 불편하다. 그래서 **가능하면 필요한 범위로 좁힌 전용 추상 클래스(또는 공통 부모)**를 만들어서 관리하는 게 낫다. `Device`로 범위를 좁혀서 자식들만 관리하면, 형변환 없이 곧바로 `Device`가 아는 기능들(`run()` 등)을 쓸 수 있다.

## 8. 참조형과 객체형 — 다형성의 우선순위 규칙

```java
Device device = new SmartDevice();
device.run();
```

참조 타입은 `Device`(부모)이지만, 실제 객체는 `SmartDevice`(자식)이다. `run()`의 결과는 **자식이 오버라이드한 버전이 실행된다.** 자바는 **참조형식의 호출보다 객체형식의 함수 호출을 우선시**하기 때문이다 — 이전에 다룬 다형성(동적 바인딩)이 바로 이 규칙이다.

**만약 부모 `Device`에 `run()`이 아예 없다면?**

이 경우 `device.run()` 자체가 컴파일 에러다. **참조 형식(`Device`)이 애초에 알지 못하는 기능은 호출할 수 없다** — "참조 가능한 기능 중에서, 객체형식(오버라이드된 것)을 우선적으로 쓴다"는 것이지, 참조형이 모르는 기능까지 객체형이 알아서 열어주는 게 아니다.

**규칙 정리**

- 참조형이 아는 기능 범위 안에서, 오버라이드가 있다면 **객체형(실제 객체)**이 우선한다
- 참조형이 모르는 기능은 애초에 **호출 자체가 불가능**하다

```java
Vehicle v = new ElectricCar();
// ElectricCar extends Vehicle,
// ElectricCar에는 charge()가 추가로 있음
v.drive(); // 가능 (Vehicle이 아는 기능)
v.charge(); // 컴파일 에러! (Vehicle은 charge()를 모름 — 참조형이 아는 범위 밖)
```

참조형이 `Vehicle`이어도 객체가 `ElectricCar`라면 실행 우선권은 무조건 `ElectricCar`가 갖는다. 다만 **참조형이 알고 있는 범위 안에서만** 그 우선권이 적용된다.

## 9. 프레임워크와 오버라이드 — 흐름은 사용자가 좌우한다

`Vehicle` 같은 부모 형태가 바로 **우리가 사용할 프레임워크**의 모습이다. 프레임워크는 기본적으로 전체 세트(여러 함수가 서로 호출하고 호출하는 흐름)가 이미 다 만들어져 있고, 그중 일부 함수는 **비워둔 채로** 제공된다 — "나중에 사용자가 오버라이드해서 원하는 로직을 끼워 넣어라"는 의도다.

**오버라이드는 단순히 부모 것을 가리는 게 아니다.** 프레임워크의 실행 흐름이 결국 사용자가 오버라이드한 코드를 거쳐서 지나가기 때문에, 사용자는 그 흐름 중간에서 자기가 원하는 대로 흐름을 조정하고 빈 공백을 채울 수 있다. 원래 흐름을 계속 이어가고 싶으면 `super`를 호출하면 되고, 그건 전적으로 사용자 마음이다.

## 10. 추상화란 결국 무엇인가

**추상화**란, **추상 클래스가 존재하지 않는 상황에서 그것을 새로 만들어내는 과정**이다. 그 필요성은 지금까지 다룬 것과 같다 — **형식이 다른 여러 객체를 일괄 관리하기 위해서**다.

`Object`가 이미 모든 것을 끌어안을 수 있는데도 새로 추상 클래스를 만드는 이유는, `Object`로 관리하면 **형변환해서 쓰기가 불편하기** 때문이다. 그래서 가능하면 **내 상황에 맞는 기능을 형변환 없이 충분히 쓸 수 있는 범위로 특화시켜서** 추상화하는 것이 좋다.
