# WBS 리뷰 — 페이지 URL과 백엔드 API, 슬러그를 쓸 곳과 안 쓸 곳

기획을 마치고 WBS(작업 분해 구조)를 만든 뒤, 한 조의 WBS를 화면에 띄워 함께 리뷰했다. 조 안에서만 "이게 맞나?"를 따지다 보면 방향을 잃기 쉬운데, 이럴 때 **다른 사람의 리뷰**를 받는 것이 도움이 된다. 리뷰에서 나온 질문과 답을 정리한다.

## 1. 페이지 URL에는 무엇을 쓰나

### 장바구니 — cart인가, cart-items인가

지난 피드백에서 "URL에는 그 화면이 다루는 **데이터**를 쓴다"고 했다. 그러자 이런 의문이 생겼다.

> 장바구니 화면에서 실제로 다루는 건 장바구니가 아니라 **장바구니에 담긴 상품들**이다. 그럼 URL을 `/cart`가 아니라 `/cart-items`로 해야 하나?

답은 두 가지 질문으로 정리된다.

1. **페이지 URL은 실제 페이지를 가리킨다.** 구현된 화면 중에 "cart items"라는 페이지가 있나? 없다. "장바구니" 페이지가 있을 뿐이다. 그러니 페이지 URL은 `cart`다.
2. **그 장바구니는 누구의 것인가?** 모든 사용자의 장바구니가 아니라 **특정 사용자(나)**의 장바구니다. 그래서 한정어를 붙여 `/my/cart`로 쓰는 게 좋다.

| 고민 | 결론 |
|---|---|
| `/cart` vs `/cart-items` | 실제 페이지 이름 → `cart` |
| `/cart` vs `/my/cart` | 내 것으로 한정되는 페이지 → **`/my/cart`** |

### 뮤직박스 — 신청곡이 담기는 페이지

이 조의 서비스에는 손님이 신청곡을 등록하고 목록을 보는 **뮤직박스** 페이지가 있다. 조회와 등록이 모두 이 한 페이지에서 일어난다면, 페이지 URL은 그대로 `/musicbox`다.

## 2. 백엔드 API에는 페이지의 주인공을 쓴다

### request-songs만으로는 부족하다

뮤직박스의 API가 `/api/v1/request-songs`처럼 되어 있었다. 그런데 `request-songs`라는 API는 **다른 화면에도 있을 수 있다.**

지금 만드는 것은 그냥 API가 아니라 **백엔드 API**다. 백엔드 API는 페이지를 기준으로 만들고, 그 페이지의 **주인공**을 붙인다.

- 뮤직박스 페이지의 주인공은? **뮤직박스에 담긴 곡들(songs)**이다.
- 모든 곡이 나오는 페이지라면 그냥 `/songs`가 맞다. 하지만 이건 장바구니에 담긴 상품처럼 **뮤직박스에 담긴 곡**이다.

| 대상 | URL |
|---|---|
| 페이지 | `/musicbox` (페이지 자체가 목록이라 따로 대시보드가 없다면 이걸로 충분) |
| 목록 조회 API | `GET /api/v1/musicbox/songs` |
| 신청곡 등록 API | `POST /api/v1/musicbox/songs` |

`request`라는 단어는 굳이 붙이지 않아도 된다. 같은 페이지에 **곁다리** 데이터가 여러 개 있다면 그것도 같은 방식으로 API를 따로 둔다.

### 검색은 목록 조회와 같은 API다

WBS에 "메뉴 조회"와 "메뉴 검색"이 따로 있었는데, 검색은 결국 목록 조회에 **필터 조건**이 붙은 것이다. 둘 다 같은 GET 요청이므로 검색 API를 지우고 목록 조회 하나로 합친 것은 잘한 결정이다.

```
GET /api/v1/menus                  → 전체 목록
GET /api/v1/menus?keyword=아메      → 같은 API에 조건만 추가
```

## 3. 대시보드는 데이터가 아니다

마이페이지의 기본 화면을 "대시보드"라고 하고, API도 `/api/v1/dashboard`로 만들려고 했다.

- 백엔드 API이므로 자원 이름이 아니어도 괜찮다. 그런데 **대시보드라는 데이터(엔티티)는 없다.** 대시보드는 데이터가 아니라 **UI**다.
- 굳이 쓴다면 `/my/dashboard`처럼 페이지 URL로는 가능하다. 하지만 API는 그 화면에 나오는 **실제 데이터**의 이름으로 지어야 한다.

이 조의 마이페이지 첫 화면에는 회원의 닉네임 정도만 있었다.

- 로그인한 회원의 정보는 DB에서 따로 조회하는 게 아니라 **인증 정보**에서 가져온다. 전역 변수처럼 이미 가지고 있으므로 별도 API가 필요 없다. 페이지 URL의 `my`가 그 회원을 가리킨다.
- 닉네임 **수정**처럼 실제로 데이터를 바꾸는 기능이 있다면 그건 API가 필요하다.
- 일반적인 대시보드에는 작업 내역이나 통계 데이터가 들어가는데, 이 서비스는 **감성** 중심이라 그런 데이터가 없을 수도 있다.

## 4. 슬러그 — 쓸 곳과 안 쓸 곳

메뉴 상세 조회 URL을 `/menus/{id}/{slug}`처럼 아이디와 슬러그를 둘 다 넣었다. 이에 대해 다른 조의 의견을 들었다.

### 슬러그를 쓰는 이유

- **검색 노출(SEO)**: URL에 메뉴 이름 같은 키워드가 들어가 검색 엔진에 더 잘 걸린다.
- **링크를 보고 내용을 알 수 있다**: `/menus/3`보다 `/menus/iced-americano`가 무슨 내용인지 바로 보인다. 링크를 받은 사람도 덜 수상하게 여긴다.
- **보안상 유리할 수 있다**: 일련번호는 `2, 3, 4, 5...`처럼 **다음 값을 쉽게 짐작**해서 넘나들 수 있다. 슬러그는 제목을 쓰므로 그런 허점이 줄어든다.

결론: 아이디와 슬러그를 **둘 다 넣을 필요는 없고, 하나만 남긴다.** 외부에 공개되는 페이지라면 **슬러그만** 남기는 게 좋다.

> **추가 설명 — 슬러그는 보안 장치가 아니다**: 일련번호를 감추면 다른 사람의 데이터를 번호만 바꿔 들여다보는 시도가 **어려워지는** 것은 맞다. 하지만 슬러그를 짐작해서 들어오는 것까지 막지는 못한다. 진짜 보안은 "이 사용자가 이 데이터를 볼 **권한**이 있는가"를 서버에서 검사하는 것이고, 슬러그는 그 위에 더하는 보조 효과 정도로 보면 된다.

### 슬러그의 단점 — 한글

한글 제목을 URL에 넣으면 **인코딩**되어 `%EC%95%84...`처럼 알아볼 수 없는 문자로 바뀐다. 그래서 보통 **영문 슬러그 컬럼을 따로** 추가해야 하는 번거로움이 있다(예: `아이스 아메리카노` → `iced-americano`).

> **추가 설명**: 요즘 브라우저 주소창은 한글 URL을 한글로 보여 주고 검색 엔진도 한글 URL을 처리한다. 다만 링크를 복사해 메신저나 문서에 붙이면 `%EC%95%84...`처럼 인코딩된 형태로 나오는 경우가 많아서, 영문 슬러그를 따로 두는 곳이 많다.

### 공개되지 않는 페이지에도 쓸까?

| 페이지 | 슬러그 | 이유 |
|---|---|---|
| 메뉴 상세처럼 **외부에 공개**되는 페이지 | 쓴다 | 검색 노출, 링크 공유 |
| **관리자** 페이지 | 안 쓴다 | URL이 외부에 노출될 일이 없고, 노출되어서도 안 된다. 슬러그는 **오버헤드**다 |
| **마이페이지** | 애매 | 공개되지는 않지만 고객을 위한 페이지다. 강사도 정답을 모르겠다며 장단점을 함께 고민해 보라고 했다 |

## 5. WBS 다음 단계 — 백로그와 첫 시스템

리뷰를 마치며 강사가 앞으로의 순서를 정리했다.

1. **WBS를 끝까지 채운다.** "거의 다 적었다"고 생각해도 빠진 부분이 있기 마련이다. 발표한 기획의 페이지와 기능이 모두 들어갔는지 확인한다.
2. **확정된 WBS가 곧 구현할 백로그다.**
3. **백로그를 어떤 순서로 만들지** 정한다.
4. **첫 번째 시스템은 조원 모두가 함께** 만든다. 누구 하나 빠짐없이 같은 방식으로 만들 수 있다는 확신이 서야 한다.
5. 그다음 시스템부터 **서로 나눠서** 구현한다.

```
WBS 완성 → 백로그 확정 → 순서 정하기 → 첫 시스템 함께 구현 → 나머지 분배
```

## 6. 덧붙인 이야기 — 이 사람과 같이 만들고 싶다

리뷰 중간에 강사가 요즘 AI와 채용에 대해 덧붙인 이야기다.

- **AI 모델의 발전은 거의 끝나 가고, 지금은 에이전트가 발전하고 있다.** 화면을 캡처해 읽고, 마우스를 움직여 클릭하는 기능도 결국 과거의 오픈소스 도구에 AI를 붙인 것이다.
- 그런 도구를 어떻게 알고 붙이나? **AI에게 물어본다.** 기본 지식이 있으면 "이런 걸 할 수 있는 라이브러리가 있어?"라고 묻고, 검색을 잘하는 신입사원과 이야기하듯 함께 만들어 간다.
- 이제는 백엔드만으로는 매력이 적다. **프론트와 백엔드를 모두**, 거기에 **자동화**까지 할 줄 알아야 하고, 그 위에 **업무 지식**을 얹어 "이걸 만들어 보고 싶다"는 방향성과 동기가 있어야 한다.
- 사람을 뽑는 이유는 하나다. **이 사람과 이 아이디어를 같이 이야기하고 만들어 보고 싶다**는 마음이 드는 사람. "경험은 없지만 열심히 배우겠습니다"보다 "이런 걸 해 봤고, 이런 걸 해 보고 싶다"고 말하는 사람이 중요하다.
- 무엇을 할지 미리 고민만 하지 말고, **지금 당장 쓸 만한 것부터 시작**하면 된다. 세상은 안개길과 같아서, 걸어 봐야 그다음이 보인다.

## 7. 한 줄 정리

- **페이지 URL**은 실제 페이지 이름으로, 특정 사용자의 것이면 `/my/cart`처럼 한정어를 붙인다.
- **백엔드 API**는 페이지의 **주인공**을 붙여 다른 화면의 API와 구분한다(`/api/v1/musicbox/songs`). 검색은 목록 조회에 조건을 붙인 같은 API다.
- **대시보드는 UI이지 데이터가 아니다.** API 이름은 화면에 나오는 실제 데이터로 짓는다.
- **슬러그**는 공개 페이지에서 SEO와 가독성을 위해 쓰고, 아이디와 둘 중 하나만 남긴다. 관리자 페이지에는 쓰지 않는다.
- WBS가 확정되면 그게 **백로그**다. 순서를 정하고, **첫 시스템은 함께** 만든 뒤 나눈다.
