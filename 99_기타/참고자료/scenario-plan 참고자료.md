# scenario-plan

기획·요구사항을 시나리오로 바꾸고, 시나리오를 통과시키는 순서로 작업을 짠다.
plan의 모든 줄은 요구사항(R)이나 시나리오(S) 번호로 거슬러 올라갈 수 있어야 한다.

## 순서

### 1. 요구사항 쪼개기
기획 문서, 이슈, 대화에서 받은 내용과 대상 폴더의 AGENTS.md, 관련 코드를 읽는다.
요구사항을 `R1, R2, …`로 나눈다. 하나의 R은 한 문장이고, 동작으로 확인할 수 있다.

완료: 원문의 모든 문장이 어떤 R에 들어갔거나 "범위 밖"으로 분류됐다.

### 2. 빈 곳 메우기
요구사항이 정하지 않은 동작을 찾는다. 입력이 비었을 때, 외부 API가 실패할 때,
이미 처리한 항목을 다시 만났을 때, 출력 위치와 형식 같은 것.

- 답에 따라 시나리오나 구조가 달라지면 시나리오를 쓰기 전에 사람에게 묻는다.
- 그 외는 합리적인 기본값을 정하고 `가정`으로 표시한다.

완료: 남은 빈 곳은 모두 질문했거나 `가정`으로 적혀 있다.

### 3. 시나리오 쓰기
R마다 정상 시나리오 하나 이상, 해당되면 경계·실패 시나리오를 쓴다.
Given/When/Then에는 구체적인 값을 넣는다 ("기사 3개", "HTTP 500").
Then은 출력, 파일, 종료 코드, 로그처럼 밖에서 관찰할 수 있는 결과로 쓴다.

완료: 모든 R이 시나리오로 덮였고, 모든 Then을 테스트나 명령 한 번으로 확인할 수 있다.

### 4. 작업 순서 짜기
처음부터 끝까지 한 번에 도는 가장 얇은 경로를 먼저 만들고, 시나리오를 하나씩 붙여 나간다.
각 단계에는 통과시킬 시나리오, 바꿀 파일, 확인 명령을 적는다.
테스트가 있는 폴더는 시나리오를 테스트 케이스와 1:1로 맞춘다.

완료: 모든 S가 어떤 단계에 배정됐다.

### 5. 저장하기
plan을 아래 형식으로 작업 대상 프로젝트 폴더의 `docs/`에 저장한다. `docs/`가 없으면 만든다.
레포 전체 작업이면 루트의 `docs/`에 저장한다.
파일 이름은 `YYYY-MM-DD-작업이름.md`로 쓴다 (예: `news-brief/docs/2026-10-19-feed-dedup.md`).

완료: plan 파일이 `docs/`에 있다.

### 6. 승인받기
저장한 경로와 `한눈에`, `질문` 섹션을 보여주고 멈춘다. 전체 내용은 사람이 요청할 때 보여준다.
사람이 승인하면 코드를 고치기 시작한다.
수정 요청이 오면 같은 파일을 고쳐 다시 보여준다.

## 형식

사람이 결정할 것이 맨 위에 오고, 그 아래로 상세 내용, 맨 끝에 근거가 온다.
`한눈에`만 읽어도 무엇이 생기는지, 무엇에 답해야 하는지 알 수 있어야 한다.

```markdown
# <작업 이름>

## 한눈에
- 끝나면: <사람이 확인할 수 있는 결과 한 줄>
- 결정 필요: <질문의 요지, 없으면 "없음">
- 규모: <n>단계, 약 <시간>

## 질문
- Q1: … (답에 따라 S2가 달라짐)

## 1. <요구사항 이름> (R1)
<요구사항 한 문장>

S1 정상
- Given …
- When  …
- Then  …

S2 실패
- Given …
- Then  …

## 2. <요구사항 이름> (R2)
…

## 범위 밖
- …

## 작업 순서
1. <단계> — S1, S3
   - 파일: …
   - 확인: `명령`

## 브랜치·커밋
- 브랜치: 종류/폴더명
- 커밋: 종류(폴더): 요약 — 단계 n~m

## 가정
- …

## 참고
- <조사로 확인한 사실과 확인한 날짜>
```

- 질문이 없으면 `## 질문` 섹션을 뺀다.
- 시나리오는 해당 요구사항 섹션 안에 둔다. 여러 R에 걸치면 주된 R에 두고 제목에 적는다 (`S7 실패 (R1·R2)`).
- Given/When/Then은 각각 한 줄에 쓰고, 한 줄에는 사실 하나만 쓴다. When이 바로 앞 시나리오와 같으면 생략한다.
- 실행 뒤 가정이 바뀌면 원래 줄을 고치고 끝에 `(고침 MM-DD: 이유)`를 붙인다.
