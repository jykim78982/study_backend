# 페이지·시스템·API를 구분해 WBS 작성하기

페이지와 시스템의 역할을 구분하고, **페이지에 필요한 데이터를 기준으로** API와 WBS를 구성하는 방법을 정리한다.

한 페이지의 **핵심 기능**과 **보조 데이터**를 구별하고, 이름과 URL을 역할에 맞게 짓는 것이 중요하다.

## 핵심 개념

| 개념 | 의미 |
|---|---|
| **페이지** | 사용자가 보는 **화면 단위**. 화면에 여러 데이터 영역이 있어도 페이지 자체는 하나일 수 있다 |
| **시스템** | 특정 도메인이나 데이터를 관리하는 **기능의 묶음**. 기능 이름과 시스템 이름을 혼동하지 않는다 |
| **API** | 페이지에 필요한 데이터를 가져오거나 처리하는 **요청 단위**. 페이지에 표시되는 엔티티별로 나눌 수 있다 |
| **주인공 데이터와 보조 데이터** | 페이지의 핵심 대상이 **주인공**이고, 카테고리·필터·추천 정보 등은 목적에 따라 **보조 데이터**가 될 수 있다 |

```
페이지 (화면)  ── 필요한 데이터 ──→  API (요청)
                                       │
                                       ↓ 어떤 데이터를 다루나
                               시스템 (도메인·데이터 관리 기능의 묶음)
```

## 페이지와 시스템 구분

### 데이터가 없으면 API도 없다

- 정적인 데이터만 보여 주는 메인 화면은 데이터를 가져오는 **API가 필요 없을 수 있다.** 이럴 때는 불필요한 API 항목을 WBS에서 지운다.
- 헤더나 레이아웃처럼 화면마다 공통으로 깔리는 부분도, 그 자체가 실제 콘텐츠를 가져오지 않는다면 WBS에 따로 둘 필요가 없다. "전체 공통", "공통 시스템" 같은 줄은 시스템 이름으로도 어색하므로 지운다.

### 메인 페이지·대시보드도 시스템으로 적는다

리뷰 중에 "메인 페이지나 대시보드처럼 **페이지 하나인 것**도 시스템이라고 할 수 있나?"를 두고 투표했는데, 다섯 명 모두 "아니다"에 표를 던졌다. 하지만 강사는 수업에서 **대시보드도 시스템**이라고 설명했다며, `메인 페이지`를 시스템으로 적으라고 했다.

- 메인 페이지가 정적 파일뿐이라 조금 민망하긴 하지만, **구현할 페이지가 존재하므로** 백로그에 들어간다.
- 이름은 `메인 공방`처럼 서비스 안의 별칭이 아니라 **`메인 페이지`**로 적고, 페이지 URL은 루트(`/`)처럼 **실제 경로**를 적는다.

> 원문 바로잡기 — 요약에는 "페이지 하나를 곧바로 별도의 시스템이라고 부르는 것은 적절하지 않을 수 있다"고 되어 있지만, 강의에서 강사의 결론은 반대였다. 투표 결과(전원 "아니다")와 달리 **메인 페이지·대시보드처럼 독립된 페이지도 시스템으로 적는다.** 요약에서 맞는 부분은 아래 "메뉴 목록 조회"처럼 **한 페이지 안의 곁다리 영역들을 각각 시스템으로 쪼개면 안 된다**는 점이다.

### 시스템은 명사, 기능은 행위

**시스템명은 관리 대상이나 도메인**(명사)을 나타내고, 시스템 안의 **기능(중분류)은 행위 중심**으로 적는다. 중분류 자리에 명사가 들어왔다면 둘 중 하나다.

1. 그 명사가 사실 **시스템**인데 위치를 잘못 잡았다. → 시스템으로 빼낸다.
2. 시스템이 아닌데 **이름을 잘못** 지었다. → 행위가 드러나는 이름으로 고친다.

예를 들어 실제로 관리하는 "책장"이 있다면 `책장 관리` 시스템 아래에 `책장 등록`, `책장 수정`, `책장 삭제` 기능이 와야 한다. 그런데 이 조의 `메뉴 책장`은 책장이 아니라 **메뉴 목록을 보여 주는 기능**이었다. 그러니 이름을 잘못 지은 경우이고, `메뉴 목록 조회` 또는 `메뉴 상세 조회`처럼 고친다.

| 구분 | 이름 짓는 법 | 예 |
|---|---|---|
| 시스템 | 관리 대상·도메인 (명사) | 메뉴 조회, 물약 관리, 인증 |
| 기능 | 대상 + 행위 | 메뉴 목록 조회, 메뉴 상세 조회 |
| 애매한 이름 | 명사만 있어서 무엇인지 모호 | ~~메뉴 책장~~ |

### 시스템명에 사용자를 섞지 않는다 — 역할자 열 추가

시스템명이 `손님 메뉴`로 적혀 있었다. "손님"은 시스템이 아니라 **그 기능을 쓰는 사람**이다. 그래서 시스템명에서 `손님`을 지우고 `메뉴 조회`로 고친 뒤, 표에 **역할자(액터)** 열을 따로 추가했다.

| 시스템 | 역할자 | 기능(중분류) | 페이지 URL | API |
|---|---|---|---|---|
| 메인 페이지 | 익명 사용자 | 메인 화면 보기 | `/` | (없음 — 정적) |
| 메뉴 조회 | 익명 사용자 | 메뉴 목록 조회 | `/menus` | `GET /api/v1/menus` 외 |

> **추가 설명 — 역할자를 따로 두면 좋은 점**: 같은 "메뉴" 시스템이라도 손님은 조회만 하고 관리자는 등록·수정·삭제를 한다. 역할자를 시스템 이름에 섞으면 `손님 메뉴`, `관리자 메뉴`처럼 시스템이 사람 수만큼 늘어난다. 열로 분리하면 시스템은 도메인 기준으로 하나로 두고, 기능마다 누가 쓰는지만 표시하면 된다. 나중에 스프링 시큐리티로 **URL별 권한(인가)**을 설정할 때도 이 열이 그대로 기준이 된다.

## 페이지와 API 구성

- 페이지의 중심이 메뉴 목록이라면 페이지 이름과 URL을 **리소스 중심**(clean URL)으로 정하고, **복수형 URL**을 쓴다. 예: `/menus`. 이 조의 WBS에는 단수형 `/menu`로 적혀 있었는데, 수업에서는 항상 복수형을 썼다.
- 메뉴 목록 페이지에 카테고리나 추천 정보가 함께 표시되더라도, 각 항목이 **독립적인 시스템이나 페이지라고 단정하지 않는다.**

### 페이지 하나에는 주인공과 곁다리가 있다

이 조의 WBS에는 `메뉴 조회` 시스템 아래에 `메뉴 책장`, `오늘의 추천`, `카테고리 필터`가 각각 기능처럼 나란히 들어 있었다. 하지만 화면을 보면 이것들은 모두 **메뉴 목록 페이지 하나** 안에 있는 영역이다. 그 밖에 장바구니 개수 같은 것도 보이지만, 페이지는 여전히 하나다.

```
메뉴 목록 페이지 (/menus)
├─ 메뉴 목록        ← 주인공
├─ 카테고리 필터    ← 곁다리
├─ 오늘의 추천      ← 곁다리
└─ 장바구니 개수 등 ← 곁다리
```

- 백로그(기능)는 **`메뉴 목록 조회` 하나**다. 곁다리가 있다고 백로그가 늘어나는 게 아니라, **오른쪽 API 칸만 늘어난다.**
- 오늘의 추천, 카테고리 필터 같은 곁다리 영역에는 따로 기능 이름을 붙이지 않는다. 메뉴 목록 조회를 구현하는 데 필요한 API일 뿐 독자적인 기능이 아니기 때문이다. 페이지 URL 칸에는 위의 페이지 주소를 그대로 복사해 넣으면 된다.

### API는 주인공 → 곁다리 순서로 따진다

1. **주인공 영역의 데이터**를 가져오는 API가 있는지 본다. 메뉴 목록 영역 → `GET /api/v1/menus`.
2. 곁다리 데이터가 **이 페이지 때문에 필요한 것인지** 따진다. 카테고리는 메뉴 목록을 거르기 위해 필요한 것이지 다른 곳에서 독자적으로 쓰이는 것이 아니다. → `GET /api/v1/menus/categories`.
3. 곁다리가 **여러 건인지 한 건인지** 따진다. 추천 메뉴는 여러 개다. → 복수형 `GET /api/v1/menus/recommendations`. 이름이 너무 길면 줄여도 되지만, 사람이 봤을 때 무엇인지 알아볼 수 있어야 한다.

> **추가 설명 — "아무도 안 고친" 단수형 URL**: 강사는 단수형 `/menu`를 짚으며, 조원 중 누군가 봤다면 이미 고쳐졌어야 했다고 지적했다. 다들 "내 일이 아니다" 하고 넘겼거나, 아무도 몰랐다는 뜻이기 때문이다. WBS는 팀이 함께 쓰는 문서이므로, 잘못된 부분을 보면 **본 사람이 말하는 것**이 기본이다.
- 그 페이지에 필요한 데이터를 API로 정리한다. 메뉴 데이터와 카테고리 데이터가 각각 필요하면 API를 각각 두되, 카테고리가 메뉴 페이지를 위한 데이터라면 **메뉴 리소스와의 관계가 드러나도록** 구성한다. 예: `/menus/categories`.
- 추천 데이터처럼 여러 건을 가져오는 경우에는 **복수형 리소스명** 등을 써서 의미를 분명히 한다.
- 페이지를 맡은 사람이 그 페이지에 필요한 데이터를 충분히 파악하고 정리해야 다른 작업과의 혼선을 줄일 수 있다.

메뉴 목록 페이지를 예로 들면 다음과 같다.

| 대상 | URL | 역할 |
|---|---|---|
| 페이지 | `/menus` | 메뉴 목록 화면 하나 |
| 주인공 API | `GET /api/v1/menus` | 메뉴 목록 |
| 보조 API | `GET /api/v1/menus/categories` | 메뉴를 거르기 위한 카테고리 목록 |
| 보조 API | `GET /api/v1/menus/recommendations` | 추천 메뉴 여러 건 (복수형) |

> **추가 설명 — `/categories`와 `/menus/categories`**: 카테고리가 여러 화면에서 두루 쓰이는 독립 데이터라면 `/categories`로 따로 두는 것도 자연스럽다. 이 자료가 `/menus/categories`를 권하는 이유는, 지금 이 카테고리가 **메뉴 페이지를 위한 보조 데이터**라는 관계를 URL에서 바로 읽히게 하려는 것이다. 어느 쪽이든 팀 안에서 기준을 정해 일관되게 쓰는 것이 중요하다.

## 핵심 대상과 보조 데이터

- 화면에 카테고리 선택지가 많더라도, 최종적으로 등록하거나 조회하는 **핵심 대상이 따로 있다면 그 대상이 주인공**이다.
- 예를 들어 게시판에서 글을 쓸 때 스포츠, 고객 문의 등 카테고리가 아무리 많아도 카테고리는 주인공이 아니다. 그것들을 고른 뒤 **마지막에 등록하는 글**이 주인공이다.
- 마찬가지로 이 조의 등록 폼에서 재료·계열·카테고리는 보조 데이터이고, 최종 저장되는 **물약**(레시피)이 핵심 대상이다. 즉 이 페이지는 **물약을 등록하는 폼**이다.
- 등록 페이지 URL은 핵심 리소스를 중심으로 구성할 수 있다. 예: `/potions/new` 또는 `/potions/create`.
- 등록 API는 **핵심 리소스 경로**를 쓰고, 등록 요청은 **`POST`**로 처리한다. 등록 폼에 필요한 재료·분류·카테고리 데이터는 **별도의 조회 API**로 제공할 수 있다.

물약 등록 페이지를 예로 들면 다음과 같다.

| 대상 | URL | 구분 |
|---|---|---|
| 등록 페이지 | `/potions/new` | 페이지 |
| 물약 등록 API | `POST /api/v1/potions` | **주인공** — 최종 저장 대상 |
| 재료 목록 API | `GET /api/v1/potions/ingredients` | 보조 — 폼의 선택지 |
| 분류 목록 API | `GET /api/v1/potions/categories` | 보조 — 폼의 선택지 |

이 기능의 WBS 위치는 `물약 관리` 시스템 아래의 `물약 등록` 기능이다. 등록하기 위해 POST를 하지만, 그 전에 폼을 열 때(GET) 재료·구분자·카테고리를 먼저 가져와야 하므로 곁다리 API가 필요하다.

> **강사의 당부 — 다 똑같다**: "이 페이지만 특별할 것"이라는 생각을 버리고, 모든 페이지를 **같은 방식**으로 정리하면 된다. ① 페이지의 주인공이 무엇인지 찾고, ② 그 주인공이 속한 시스템과 행위(기능)를 정하고, ③ 주인공과 곁다리 데이터를 API로 나열한다.

> **추가 설명 — 페이지 URL과 API URL의 차이**: 페이지 URL에는 `new`, `create`처럼 **어떤 화면인지** 나타내는 말이 들어갈 수 있다. 하지만 API에서는 행위를 **HTTP 메서드**가 표현하므로, 등록 API는 `POST /api/v1/potions/create`가 아니라 `POST /api/v1/potions`로 쓰는 것이 일반적이다. 같은 `/potions` 경로라도 `GET`은 목록 조회, `POST`는 등록이 된다.

## 인증과 구현 순서

- 이 조는 `인증` 시스템 아래에 회원가입·로그인·로그아웃 기능을 두고, 로그인 API를 `/api/v1/...` 형태로 잘 적었다. 다만 순서의 문제가 남는다.
- 회원가입·로그인 같은 인증 기능이 개발 초기에 **항상 먼저 만들어져야 하는 것은 아니다.**
- 인증을 나중에 구현하고, 초기 개발 중에는 **테스트용 데이터**를 활용할 수 있다. 인증을 먼저 만들면 개발 중에 매번 로그인해야 해서 작업이 번거로워질 수 있다.

> **추가 설명 — 테스트용 데이터로 버티는 법**: 예를 들어 "내 장바구니"처럼 로그인한 사용자가 필요한 기능이라면, 처음에는 **회원 ID를 1번으로 고정**해 두고 기능을 만든다. 나중에 인증을 붙이면 그 고정값 자리를 "로그인한 사용자의 ID"로 바꾸기만 하면 된다. 이렇게 하려면 처음부터 회원 ID를 꺼내는 부분을 한곳에 모아 두는 것이 좋다.

## 컴포넌트와 API 분류

- "페이지별로 API를 나눈다"는 설명은 **컴포넌트 수에 맞춰 URL을 만들라는 뜻이 아니다.** 우선 페이지에서 쓰는 **엔티티와 데이터를 기준**으로 API를 분류한다.
- 컴포넌트 구조를 명확히 이해하고 있다면 컴포넌트 단위로 나눌 수도 있다. 이때 API와 컴포넌트가 대응하는 부분이 있을 수 있지만, 잘 모르는 단계에서는 **페이지에 필요한 데이터부터** 정리한다.

리뷰가 끝난 뒤 한 수강생이 이런 질문을 했다.

> **Q.** 메뉴 페이지는 크게 보면 카테고리 컴포넌트와 메뉴 리스트 컴포넌트로 이루어져 있는데, 컴포넌트 위주로 URL을 작성하라는 뜻인가요? 예전에 컴포넌트별로 분류해 보라고 하셨던 게 생각나서요.
>
> **A.** 컴포넌트 이야기를 한 것이 아니다. 페이지에서 쓰는 데이터는 **테이블(엔티티)이 다르다.** 그래서 **엔티티별로 데이터를 요청**하는 API를 두라는 것이다. 메뉴가 주인공이고, 카테고리는 곁다리로 오는 데이터이며, 페이지는 하나다.
>
> 다만 컴포넌트를 이해하고 있다면 컴포넌트로 따로 빼도 괜찮다. 페이지를 컴포넌트로 잘 나눌 줄 알면, 결국 **백엔드 API를 나눈 것과 컴포넌트가 일맥상통**하기 때문이다. 그 경우 API와 컴포넌트를 일단 **1:1로 맞추면** 된다. 잘 모르겠다면 "페이지에서 데이터를 가져다 쓴다"고만 생각하고, 페이지에 쓰이는 데이터로 API를 분류할 수 있으면 된다.

```
❌ 컴포넌트 기준:  MenuHeader, MenuFilter, MenuGrid, MenuCard … → API도 4개?
✅ 데이터 기준:    이 페이지에 나오는 데이터는? → 메뉴, 카테고리, 추천 → API 3개
```

## 정리

- **페이지**는 화면, **시스템**은 도메인을 관리하는 기능의 묶음, **API**는 페이지에 필요한 데이터 요청이다. 셋을 섞어 부르지 않는다.
- 시스템명은 **명사(도메인)**, 기능은 **대상 + 행위**로 적는다. 중분류에 명사가 있으면 시스템으로 빼거나 이름을 고친다.
- 메인 페이지·대시보드도 시스템으로 적는다. 하지만 한 페이지 안의 곁다리 영역은 시스템이나 기능으로 쪼개지 않는다. **곁다리는 API 칸만 늘린다.**
- 사용자(손님, 관리자)는 시스템명에 섞지 말고 **역할자 열**로 분리한다.
- 정적인 페이지나 공통 레이아웃에는 API가 없을 수 있다. 필요 없는 줄은 WBS에서 지운다.
- URL은 **주인공 리소스 중심, 복수형**으로 짓는다. 보조 데이터는 주인공과의 관계가 드러나게 둔다(`/menus/categories`).
- 등록 화면의 주인공은 **최종 저장되는 대상**이다. 등록은 그 리소스 경로에 `POST`, 선택지는 별도 조회 API로 둔다.
- 인증은 나중에 붙여도 된다. 그동안은 테스트용 데이터로 개발한다.
- API는 컴포넌트 수가 아니라 **페이지에 나오는 데이터**를 기준으로 나눈다.
