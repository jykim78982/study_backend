# 프로젝트 마무리와 발표 — 핵심 기능, 코드 소유권, 설득 구조

개발자 소셜 프로젝트의 마무리에서는 **기능 수를 늘리기보다 서비스의 핵심 정체성과 사용자가 얻는 가치를 분명히 구현**하는 것이 중요하다. AI 도구나 외부 코드를 썼더라도 구현 내용을 스스로 이해하고, 변경과 오류에 대응할 수 있는 상태인지 검토해야 한다. 발표에서는 결과물만이 아니라 **문제 정의 → 구현 방식 → 사용자 혜택**을 하나의 흐름으로 설명한다.

> **핵심 메시지**: 완성도는 기능의 개수가 아니라 핵심 기능이 정체성을 드러내는 정도로, 발표는 기술의 나열이 아니라 선택의 이유를 자기 말로 설명하는 능력으로 결정된다.

## 1. 핵심 기능과 서비스 정체성

프로젝트 완성도는 모든 기능을 구현했는지보다, **서비스가 풀려는 문제와 고유한 정체성을 핵심 기능으로 보여 주는지**에서 갈린다.

- 개발자 대상 소셜 서비스라면 일반 소셜 기능(글쓰기, 팔로우, 좋아요)을 조합하는 데서 그치면 안 된다. **개발자라는 집단의 특성, 사용 목적, 상호작용 방식**이 화면과 기능 흐름에 반영되어야 차별화된 정체성이 생긴다.
- 핵심 기능은 제한된 시간 안에 **가장 먼저 완성해야 하는 범위**다. 부가 기능이 일부 미완성이어도, 사용자가 서비스의 목적을 이해하고 주요 가치를 경험할 수 있으면 프로젝트의 중심은 유지된다.

| 원칙 | 내용 |
|---|---|
| 핵심 기능의 정의 | 사용자가 **가장 먼저 경험하는 문제 해결 흐름** |
| 우선순위 기준 | 구현 난이도가 아니라 **서비스 정체성에 기여하는 정도** |
| 미완성 기능 | 핵심 사용자 경험이 동작하면 의도는 전달된다 |
| 기능 추가 | 대상 사용자에게 어떤 **실질적 효용**을 주는지 먼저 검토 |

서비스 가치는 기능 명세가 아니라 **사용자 관점의 변화**로 설명하는 편이 효과적이다. 개발자 소셜이라면 사용자가 ① 자신의 기술적 정체성을 표현하고 ② 관심 있는 개발자와 연결되며 ③ 관련 정보를 탐색하는 과정이 자연스럽게 설계되어야 한다.

## 2. 구현 이해와 코드 소유권

AI가 생성한 코드나 빠르게 조합한 구현물도, 개발자가 **구조와 동작 원리를 이해하지 못하면 유지보수와 장애 대응이 어려워진다.** 코드가 동작한다는 사실이 구현 책임을 없애 주지는 않는다. 담당자는 해당 코드의 **입력, 출력, 의존성, 예외 상황**을 설명할 수 있어야 한다.

이해하지 못한 구현은 요구사항이 바뀌거나 오류가 날 때 큰 비용이 된다. 원인을 추적할 수 없으면 작은 수정도 위험하고, 기능 간 영향 범위를 판단할 수 없으며, 결국 **코드를 고치지 못하는 상태**에 빠진다.

| 검토 항목 | 확인할 내용 | 미확인 시 위험 |
|---|---|---|
| 기능 흐름 | 사용자 입력부터 결과 화면까지의 처리 순서 | 오류 지점을 빠르게 좁힐 수 없다 |
| 데이터 처리 | 데이터의 생성·조회·변경·저장 방식 | 데이터 불일치와 손실 문제를 풀기 어렵다 |
| 외부 의존성 | API, 라이브러리, AI 생성 코드의 역할과 제약 | 환경 변화나 호출 실패에 대응하기 어렵다 |
| 예외 처리 | 실패 시 메시지, 복구 방식, 재시도 조건 | 운영 환경에서 장애가 확대될 수 있다 |

**코드 소유권은 모든 코드를 혼자 썼다는 뜻이 아니다.** 외부 도움을 받았더라도 ① 왜 그 방식을 골랐는지 ② 어떻게 동작하는지 ③ 어떤 조건에서 고쳐야 하는지를 판단할 수 있으면 실질적인 소유권이 있다.

마무리 단계에서는 새 기능을 무리하게 넣기보다 **기존 구현을 되짚는 시간**이 필요하다. 설명할 수 없는 파일, 함수, API 호출, 데이터 모델은 직접 실행해 보고 흐름을 추적하며 이해를 보완한다.

## 3. 프로젝트 발표의 설득 구조

발표는 구현 결과를 나열하는 자리가 아니라 **문제, 해결 방식, 사용자 혜택을 연결해 제품의 가치를 전달**하는 과정이다.

- 자기소개와 프로젝트 소개를 분리하지 않는다. **내가 맡은 역할 → 중요하게 본 문제 → 그것을 푼 기술적 선택**을 이어 말하면 개발 경험의 맥락이 분명해진다.
- 기능 목록을 화면 순서대로 읽지 말고 **사용자 흐름** 중심으로 구성한다. 사용자가 겪는 불편 → 서비스의 해결 → 그 결과의 혜택 순서다.

| 구성 요소 | 설명에 담을 내용 |
|---|---|
| 문제 정의 | 서비스가 해결하려는 **사용자 불편**과 **대상 사용자**를 구체적으로 |
| 구현 설명 | 핵심 기능의 **동작 흐름**과 선택한 기술·구조의 **이유** |
| 사용자 혜택 | 기능 자체가 아니라 시간·정보·연결 측면에서 **사용자가 얻는 변화** |
| 개인 기여도 | 담당 기능과 해결한 기술 문제를 **검증 가능한 수준**으로 |

표현 능력은 발표 기술이 아니라 **프로젝트의 기술적 의도를 전달하는 역량**이다. 같은 결과물이라도 설계 이유, 구현 과정, 한계와 개선 방향을 논리적으로 설명하면 프로젝트의 신뢰도와 개발자의 문제 해결 역량이 함께 드러난다.

### 발표 준비 체크리스트

1. 핵심 기능의 **데모 경로**를 정한다.
2. 예상 질문에 대비해 **데이터 흐름과 예외 상황**을 설명할 수 있게 한다.
3. 내가 구현한 부분은 **코드 수준의 질문**이 들어와도 구조와 선택 이유를 답할 수 있도록 정리한다.

## 4. 한 줄 정리

- 핵심 기능은 **서비스 정체성에 기여하는 정도**로 우선순위를 정하고, 부가 기능이 비어도 핵심 경험은 동작해야 한다.
- AI·외부 코드도 **입력·출력·의존성·예외**를 설명할 수 있어야 내 코드다. 마무리 단계는 추가보다 **되짚기**다.
- 발표는 **문제 → 구현(선택의 이유) → 사용자 혜택**의 흐름으로, 개인 기여도는 검증 가능하게 말한다.
