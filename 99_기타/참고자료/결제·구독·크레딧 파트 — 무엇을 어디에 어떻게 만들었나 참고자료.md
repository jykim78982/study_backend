# 결제·구독·크레딧 파트 — 무엇을 어디에 어떻게 만들었나

test-moa에서 돈과 크레딧이 오가는 부분을 맡아 만든 내용입니다. 무엇을, 어디에, 어떤 방식으로 했는지 영역별로 정리했습니다. 자세한 규칙과 시나리오는 `docs/backend/payment/`와 `docs/frontend/payment/`, `docs/frontend/admin/`에 있습니다.

## 1. 한눈에

| 영역 | 하는 일 | 주요 화면 |
| --- | --- | --- |
| 크레딧 | 잔액·내역 조회, 출금 신청·처리, 가입 크레딧 지급 | `/my/credits`, `/my/credits/withdrawals`, `/admin/withdrawals` |
| 구독 | 플랜·내 구독 상태, 무료 플랜 조건, 운영자 플랜·구독 관리 | `/subscription`, `/my/subscription`, `/admin/plans` |
| 결제 | 크레딧·현금(카카오페이·토스페이) 결제, 결제 내역 | `/my/subscription/checkout` 아래 화면들 |

이슈는 #45(엔티티) → #66·#67·#68(크레딧·출금) → #69·#70·#71(구독·결제) → #203·#204(무료 플랜·운영자 구독) → #249(PG 연동) → #252(결제 팝업) → #255(가입 크레딧) → #257(운영자 플랜 관리) 순으로 진행했습니다.

## 2. 크레딧

**지갑과 장부.** 회원마다 지갑 하나(`credit_wallets`)가 있고, 세 가지 잔액을 따로 둡니다.
- 이벤트 크레딧: 가입 보상 같은 것. 구독 결제에는 쓰지만 출금은 못 합니다.
- 적립 잔액: 테스트로 번 크레딧. 출금할 수 있고, 구독 결제에도 쓸 수 있습니다.
- 잠긴 잔액: 출금 신청 중인 금액. 처리가 끝나기 전까지 쓸 수 없습니다.

장부(`credit_ledgers`)에는 잔액이 실제로 바뀐 일만 한 줄씩 남깁니다(변동량, 원인, 종류 이벤트·적립). 출금 신청과 반려처럼 총잔액이 안 바뀌는 이동은 장부에 남기지 않습니다. 구독을 크레딧으로 결제하면 쓴 종류마다 한 줄씩 남습니다("구독 결제(이벤트 크레딧)", "구독 결제(적립 크레딧)").

**방식.** 엔티티에 setter를 두지 않고 `grantEvent`, `lockForCashout` 같은 메서드로만 바꿉니다. 값 하나로 판단하는 검사는 요청 DTO, 상태 전이는 엔티티, 다른 테이블까지 보는 규칙(이미 처리된 요청인지, 행 잠금, 장부 기록)은 서비스가 맡습니다.

**출금.** 회원이 계좌와 금액으로 신청하면 그만큼 적립에서 잠김으로 옮깁니다. 운영자가 `PAID`로 처리하면 잠긴 금액이 빠지고 장부가 한 줄 남고, `REJECTED`로 반려하면 잠긴 금액이 적립으로 돌아옵니다(사유 필수). 계좌번호와 예금주는 DB에 암호화(AES-GCM, 키는 환경 변수)해서 저장하고, 응답에서는 대기 중이면 전체, 끝난 요청은 마스킹해서 보여 줍니다.

**가입 크레딧(#255).** 회원가입이 끝나면 지갑이 만들어지고 이벤트 크레딧 3,000(설정 `CREDIT_SIGNUP_BONUS_AMOUNT`)이 지급됩니다.
- 가입과 같은 트랜잭션이라, 지급이 실패하면 가입도 되돌아갑니다. 지갑 없는 회원이 새로 생기지 않습니다.
- 이미 받았는지는 새 컬럼 없이 장부에 "가입 크레딧" 이벤트 행이 있는지로 가립니다.
- 기존 회원은 설정(`CREDIT_SIGNUP_BONUS_BACKFILL=true`)을 켜고 서버를 시작하면 한 번 도는 실행기가 지급합니다. 관리자·탈퇴·파기 회원은 빼고, 지급 직전에 회원 행을 잠가 상태를 다시 확인합니다. 두 번 돌아도 중복 지급은 없습니다.

## 3. 구독

**플랜과 구독 상태.** 플랜(`plans`)은 등급, 현금·크레딧 가격, 기간(일), 혜택, 버전을 가집니다. 조건이 바뀌면 행을 고치지 않고 `version`을 올린 새 행을 만듭니다. 그래서 이미 구독한 회원은 산 당시의 조건이 그대로 남습니다. 구독 중인지는 날짜(`start_at`~`end_at`)로 판단하고 만료 배치는 두지 않습니다. 상태 값은 `ACTIVE`와 `CANCELLED`만 있습니다.

**무료 플랜(#203).** 무료 조건은 `plans`가 아니라 별도 테이블 `free_plans`(행 하나, 고정 PK)에 둡니다. `plans`에 넣으면 판매 목록에 섞여 결제 대상이 되기 때문입니다. 행이 없으면 `FREE`와 빈 혜택을 200으로 줘서 화면이 깨지지 않습니다. 이 테이블은 다른 테이블과 연결이 없습니다.

**운영자 구독 부여(#204, 시연용).** 시연과 확인용 계정을 만들려고, 운영자가 회원의 이메일로 구독 상태를 보고 결제 없이 주고 뺄 수 있게 했습니다. 결제와 크레딧에는 아무것도 남지 않습니다.

**운영자 플랜 관리(#257).** `/admin/plans`에 두 탭이 있습니다.
- 혜택: 무료 플랜의 이름·혜택은 `PUT /api/v1/admin/plans/free`로 같은 행을 고칩니다. 구독 플랜은 혜택만 고치는 API가 없어서 `POST /api/v1/admin/plans`로 `version`이 오른 새 행을 만듭니다. 가격과 기간은 저장하는 순간의 서버 값을 그대로 보내고, 화면이 오래돼도 다른 값으로 덮어쓰지 않습니다.
- 회원 구독: 위 #204 화면을 이 탭으로 옮겼습니다. 예전 `/admin/subscriptions` 주소는 이 탭으로 넘어갑니다.

## 4. 결제

**크레딧 결제(#71).** 지갑 행을 잠근 뒤 이벤트 크레딧부터 쓰고 모자란 만큼 적립에서 빼며, 장부와 구독 기간을 함께 저장합니다. 지갑이 없으면 "없을 때만 넣는" SQL로 만들고 잠급니다. 직전 결제 후 5초 안이면 더블클릭으로 보고 409로 거절합니다.

**현금 결제(#249).** 카카오페이와 토스페이(테스트 환경)를 씁니다. 서버가 금액을 정하고 브라우저가 보낸 값은 믿지 않습니다.
1. 준비: 서버가 결제 시도를 저장하고 결제창 정보를 줍니다.
2. 결제창에서 결제하면 돌아오는 화면이 값을 받아 승인 API를 부릅니다.
3. 승인: 서버가 PG에 승인을 요청하고, 성공하면 결제(`provider`, `pg_transaction_id` 포함)와 이용 기간을 저장합니다.

**결제 팝업(#252).** PC에서는 결제창이 새 페이지가 아니라 원래 창 가운데에 뜨는 팝업으로 열립니다. 모바일은 현재 창에서 이동합니다.
- 팝업은 제출 즉시(서버 응답 전에) 열어야 차단되지 않아서, 폼 제출 시점에 빈 창을 먼저 열고 서버 응답 뒤 주소를 넣습니다.
- 결제가 끝나면 결과 화면은 원래 창에 나타나고, 원래 창이 확인 응답을 보내면 팝업이 닫힙니다(응답이 없으면 팝업에 결과가 남습니다). 창 사이 통신은 자기 팝업에서 온 메시지만 받고, 토스 결제 값은 주소에 노출하지 않고 메시지로 주고받습니다.
- 팝업이 막혔으면 차단을 풀고 "결제하기"를 다시 누르도록 안내하고, 결제를 취소하면 경고색 안내가 보입니다.

## 5. 프론트엔드 구조

**전체 흐름(BFF).** 브라우저는 백엔드를 직접 부르지 않습니다. Next 서버(서버 컴포넌트와 서버 액션)가 `lib/backend.ts`의 `backendFetch`로 백엔드를 부르고, httpOnly 쿠키의 액세스 토큰을 Bearer로 붙입니다. 환경 변수 `AUTH_MODE=backend`일 때만 로그인·데이터가 서버를 쓰고, 값이 없으면 목업(`demo/` 쿠키 데이터)으로 돌아서 백엔드 없이 프론트만 띄우거나 e2e를 돌릴 수 있습니다.

**폴더 구성.**
- `features/<도메인>/` — 도메인 로직. 결제·구독은 `features/subscription/`, 크레딧은 `features/credit/`입니다.
  - `api.ts`: 서버 전용 읽기·쓰기 함수. 백엔드 모드와 목업 모드를 여기서 가릅니다.
  - `actions.ts`: 폼이 부르는 서버 액션(입력 검사 → API 호출 → 화면 갱신).
  - `types.ts`: 타입과 순수 함수(예: 만료일 계산 `renewedExpiry`, 혜택 입력 해석 `parseBenefits`). 단위 테스트가 이 파일을 확인합니다.
  - `pg.ts`, `toss-window.ts`: 결제 대행사 값·결제 팝업 규칙.
- `app/(site)/…/page.tsx` — 페이지. 화면 조각은 같은 폴더의 `_components/<이름>/<이름>.tsx`와 `.module.css` 한 쌍으로 둡니다.
- `demo/` — 목업 데이터. `e2e/pages.ts`는 새 페이지를 등록하는 목록입니다.

**페이지가 만들어지는 방식.**
- 페이지는 서버 컴포넌트이고, 로그인 정보를 읽는 부분은 `Suspense` 안에 둡니다. 접근 권한은 `requireMember`(로그인 필요, 아니면 로그인으로 보내고 돌아올 주소를 남김)와 `requireAdmin`(운영자 아니면 접근 불가 화면)으로 처리합니다.
- 쓰기는 서버 액션입니다. 폼은 `useActionState`로 결과(성공 문구, 오류)를 받고, 저장 뒤 `revalidatePath`로 같은 화면의 서버 값을 다시 읽습니다.

**페이지 구성.**

| 화면 | 주소 | 읽는 데이터(`api.ts`) | 주요 조각·액션 |
| --- | --- | --- | --- |
| 구독 소개 | `/subscription` | `getSubscriptionIntro` | 플랜 카드(무료·구독 혜택) |
| 구독 관리 | `/my/subscription` | `getSubscriptionOverview`, `getPaymentHistory` | 구독 상태, 결제 안내, 만료 안내, 결제 내역 |
| 결제 | `/my/subscription/checkout` | `getCheckoutInfo` | `CheckoutForm`(수단 선택), 서버 액션 `payForSubscription` |
| 토스 팝업 | `/my/subscription/checkout/toss` | 없음(부모 창이 값을 메시지로 전달) | `TossPopup` |
| 결제창 복귀 | `/my/subscription/checkout/result` | `approveCashPayment` | 승인 호출, 실패 카드 |

**결제 팝업 구성.** `CheckoutForm`의 `usePaymentPopup`이 제출 즉시 팝업을 열고 서버 액션이 돌려준 주소로 보냅니다. 결제창에서 돌아오는 화면(`checkout`, `result`, `complete`)에는 `PopupReturn`이 붙어서, 팝업이면 부모 창에 주소를 알리고 닫습니다. 주소 허용 목록과 메시지 검사는 `pg.ts`에 있습니다.

## 6. 백엔드 구조와 서비스 로직

**계층.** `controller`(요청 받기, 응답 감싸기) → `service`(인터페이스)와 `impl`(규칙) → `repository`(Spring Data JPA) → `entity`. 요청·응답은 `dto/request`, `dto/response`에 두고 요청 DTO가 값 하나짜리 검사를 합니다. 위치는 회원 API는 `controller/my`, 운영자 API는 `controller/admin`이고, 서비스도 `service/my`, `service/admin`으로 나뉩니다. 결제 대행사 호출은 `global/client/pg/`(`KakaoPayGateway`, `TossPaymentsGateway`)에 있고 `PaymentGateways`가 `provider`로 고릅니다. 운영자 API(`/api/v1/admin/**`)는 `SecurityConfig`가 `ADMIN`만 허용하고, 플랜 조회는 로그인 없이 읽습니다.

**동시성 규칙.** 돈이 움직이는 서비스는 행을 잠그는 순서를 같게 합니다. 결제(크레딧·현금), 출금 신청, 운영자의 구독 부여·회수, 소급 지급은 **회원 행 → 지갑 행** 순서이고, 운영자 출금 처리는 **요청 행 → 지갑 행** 순서입니다. 순서가 같으면 교착이 없고, 두 요청이 같은 값을 읽고 서로 덮어쓰는 일이 없습니다. 이 순서는 처음부터 같지는 않았습니다. 결제와 운영자의 구독 부여·해제가 서로 다른 잠금을 쓰고 있어서 같은 구독 종료일을 읽고 기간이 겹칠 수 있다는 것을 발견했고, #204에서 결제도 회원 행을 먼저 잠그도록 고쳐 같은 회원 행 잠금으로 맞췄습니다.

**서비스별 로직.**

| 서비스 | 하는 일 |
| --- | --- |
| `CreditService` | 잔액(이벤트·적립·잠금·승인 대기)과 파생 값(결제 가능, 출금 가능, 총합)을 계산하고 장부를 최신순으로 줍니다. 받은/쓴 필터와 개수 제한이 있습니다. |
| `CashoutService`(회원) | 지갑을 잠근 뒤 적립에서 잠김으로만 옮깁니다(장부 없음). 회원 행도 먼저 잠가서 탈퇴 신청과 순서를 맞춥니다. 내역에서 끝난 건의 계좌는 가립니다. |
| `CashoutService`(운영자) | 요청 행 → 지갑 행을 잠그고 `PAID`면 잠긴 금액 차감과 장부, `REJECTED`면 적립 복귀(사유 필수). 같은 요청을 두 번 처리하지 못합니다. |
| `SubscriptionService` | 구독 상태는 날짜(`start_at <= 지금 < end_at`)로 판단합니다. 만료일은 빈틈없이 이어지는 기간 중 가장 늦은 `end_at`입니다. 결제 화면 값(이용 시작 = max(지금, 가장 늦은 `ACTIVE` 만료일), 끝 = 시작 + 기간)과 결제 가능 크레딧도 줍니다. |
| `SubscriptionChecker` | 다른 기능이 쓰는 구독 확인 도구. 토큰에 구독 여부를 넣지 않고 요청마다 읽어서 결제와 만료가 바로 반영됩니다(`isActive`, `require` → 아니면 403). |
| `PaymentService` | `pay`: 현금이면 400. 회원 행 잠금 → 운영자 거절 → 지금 파는 플랜 → 지갑 생성·잠금 → 5초 안 중복이면 409 → 크레딧 부족이면 409 → 구독·결제 저장 → 이벤트 크레딧부터 차감하고 장부 기록. `completePgPayment`: PG 승인 뒤 같은 저장을 합니다. |
| `PgPaymentService` | `ready`: 플랜과 돌아올 주소를 검사하고 중복을 막은 뒤, 서버가 금액을 정해 결제 시도(`payment_attempts`, 10분 유효)를 저장하고 결제창 정보를 줍니다. `approve`는 세 토막입니다(아래). |
| `PlanService` / `AdminPlanService` | 지금 파는 플랜(같은 등급의 가장 큰 `version`), 무료 플랜 조회(없으면 `FREE`와 빈 혜택). 운영자는 새 버전 등록과 무료 플랜 저장(없으면 만들고 있으면 고침)을 합니다. |
| `AdminSubscriptionService` | 이메일로 회원 구독 조회, 결제 없이 부여, 끝나지 않은 기간 회수. 같은 회원 행을 잠가서 결제와 서로 기간을 덮어쓰지 않습니다. |
| `SignupCreditService` | 가입 크레딧 지급 `grant`와 소급 지급 `grantToExistingMember`. 실행기가 회원마다 부릅니다. |

**현금 결제 승인(세 토막).** PG를 부르는 동안 회원 행을 잡고 있지 않도록 나눴습니다.
1. 회원 행을 잠그고 시도를 검증합니다(내 시도인지, 10분 안인지, 토스가 돌려준 금액이 서버 금액과 같은지). 통과하면 `APPROVING`으로 바꾸고 커밋합니다. 같은 시도를 다른 요청이 다시 승인하지 못합니다.
2. 잠금 밖에서 PG 승인을 부릅니다. PG가 거절하면 시도를 `FAILED`로 바꿉니다.
3. 회원 행 → 지갑 행을 다시 잠그고 결제·구독을 저장한 뒤 `APPROVED`로 바꿉니다. 승인에는 항상 서버가 정한 금액만 씁니다.

## 10. 발표 예상 질문과 답변

답변은 말로 하는 길이로 적었고, 코드와 문서에서 확인한 내용만 썼습니다. 못 한 부분은 못 했다고 말하는 쪽으로 정리했습니다.

### 설계 선택

**Q1. 무료 플랜을 왜 `plans`에 행으로 넣지 않고 `free_plans`라는 별도 테이블로 뒀나요?**
`plans`에 넣으면 판매 목록(`GET /api/v1/plans`)에 섞여서 결제 대상이 되고, 구독이 생기면 구독 중으로 계산됩니다. 무료는 가격도 기간도 버전도 없는 "표시용 조건"이라 행 하나짜리 별도 테이블로 분리했습니다. 구독·결제 코드는 이 테이블을 아예 모릅니다. 대신 혜택을 쉼표로 이어 저장하는 규칙은 `plans`와 같게 맞췄습니다.

**Q2. 플랜 가격이나 혜택을 바꾸면 기존 행을 고치지 않고 새 행을 만드는 이유가 뭔가요?**
이미 구독한 회원은 산 당시의 조건을 그대로 가져야 해서입니다. 행을 고치면 예전 결제와 구독이 바뀐 조건을 가리키게 됩니다. 그래서 `version`을 올린 새 행을 만들고, 지금 파는 플랜은 같은 등급에서 가장 큰 버전으로 정합니다. `(tier, version)`은 unique입니다.

**Q3. 구독이 만료되면 상태를 바꾸는 배치는 없나요?**
없습니다. 구독 중인지는 요청할 때마다 `start_at <= 지금 < end_at`로 판단합니다. 배치를 두면 배치가 늦거나 죽었을 때 상태가 틀어지는 문제가 생기는데, 날짜로 계산하면 그럴 일이 없습니다. 그래서 상태 값은 `ACTIVE`와 `CANCELLED` 둘만 있습니다. 토큰에도 구독 여부를 넣지 않고 매번 읽어서, 결제나 만료가 바로 반영됩니다.

**Q4. 이벤트 크레딧과 적립 크레딧을 왜 나눴나요?**
쓸 수 있는 범위가 다르기 때문입니다. 이벤트 크레딧(가입 보상)은 구독 결제에는 쓰지만 현금으로 바꿀 수 없고, 적립 크레딧(테스트로 번 것)은 출금할 수 있습니다. 한 숫자로 합치면 이벤트로 받은 돈이 출금되는 문제가 생깁니다. 결제할 때는 이벤트 크레딧부터 쓰고 모자란 만큼 적립에서 뺍니다(적립 크레딧도 결제에 쓸 수 있습니다).

**Q5. 출금 신청은 장부에 안 남기고 지급할 때만 남기는 이유는요?**
장부에는 총잔액이 실제로 바뀐 일만 남기도록 정했습니다. 출금 신청은 적립에서 잠김으로 옮기는 것뿐이라 총잔액이 안 바뀌고, 반려도 잠김에서 적립으로 되돌릴 뿐입니다. 지급할 때 잠긴 금액이 실제로 빠지므로 그때 한 줄이 남습니다. 이렇게 하면 장부 합계가 항상 잔액과 맞습니다(이벤트 합 = `eventCredit`, 적립 합 = `earnedBalance + lockedBalance`).

### 결제와 트랜잭션

**Q6. 결제에서 동시에 두 번 눌리거나 두 요청이 겹치면 어떻게 되나요?**
돈이 움직이는 서비스는 행을 잠그는 순서를 **회원 행 → 지갑 행**으로 통일했습니다(비관적 락, `FOR UPDATE`). 같은 회원의 결제 두 건은 순서대로 처리되고, 각자 잠근 뒤에 잔액과 가장 늦은 구독 만료일을 읽으니 서로 덮어쓰지 않습니다. 운영자의 구독 부여·회수도 같은 회원 행을 잠급니다. 여기에 더블클릭 방지로 직전 결제 후 5초 안이면 409로 거절합니다. 처음에는 결제와 운영자 작업의 잠금이 달랐고, 그것을 #204에서 같은 회원 행 잠금으로 맞췄습니다.

**Q7. 낙관적 락이 아니라 비관적 락을 쓴 이유는요?**
돈과 구독 기간은 충돌했을 때 재시도로 풀기보다 한 줄로 세워 처리하는 편이 단순하고 안전하다고 판단했습니다. 충돌이 잦지는 않아서 대기 비용도 작습니다. 다만 잠금 순서를 어기면 교착이 생기므로, 모든 돈 관련 코드가 같은 순서를 지키게 했습니다.

**Q8. 현금 결제 승인을 왜 세 토막으로 나눴나요?**
외부 PG(카카오페이·토스)를 호출하는 동안 DB 트랜잭션과 행 잠금을 잡고 있으면 PG가 느릴 때 같은 회원의 다른 작업이 다 막힙니다. 그래서 ① 시도를 검증해 `APPROVING`으로 바꾸고 커밋, ② 잠금 밖에서 PG 승인 호출, ③ 결제·구독 저장과 `APPROVED` 전환으로 나눴습니다. ①에서 `APPROVING`이 되기 때문에 같은 시도를 다른 요청이 다시 승인하지 못합니다.

**Q9. PG는 승인했는데 ③에서 저장이 실패하면 돈만 나가는 것 아닌가요?**
맞습니다. 그 경우 시도는 `APPROVING`으로 남고 오류 로그만 남기며 자동 취소는 하지 않습니다. 사람이 PG 쪽을 확인해 처리해야 하는 한계로 인지하고 있습니다. 이 상황은 테스트(#249-S12)로 재현해 "구독·결제는 남지 않고 시도는 `APPROVING`으로 남는다"를 확인했습니다. 다음 단계로는 `APPROVING`에 오래 머문 시도를 찾아 PG 조회·취소로 정리하는 것을 생각하고 있고, 지금 구현에는 없습니다.

**Q10. 결제 금액을 브라우저에서 받지 않고 서버가 정하는 이유는요?**
브라우저가 보낸 금액은 조작할 수 있기 때문입니다. 결제 준비 때 서버가 금액을 정해 결제 시도(`payment_attempts`)에 저장하고, 승인에는 항상 그 서버 값만 씁니다. 토스가 돌려준 금액은 서버 금액과 같은지 검사하는 데만 쓰고, 시도는 10분 안에만 유효합니다.

**Q11. 환불은 되나요?**
구현하지 않았습니다. 결제 상태에 `REFUNDED` 값은 있지만 처리 흐름은 없습니다. 환불 규칙(기간 비례, 크레딧 복구 등)이 정해지지 않아서 범위에서 뺐습니다.

### 가입 크레딧

**Q12. 가입 크레딧을 가입과 같은 트랜잭션에서 주면, 지급 코드가 틀릴 때 가입이 다 막히지 않나요?**
그 위험을 알고 골랐습니다. 가입은 먼저 확정하고 지급은 따로 시도하는 방법도 있었지만, 그러면 가입 직후 크레딧이 안 보이거나 지급이 조용히 실패한 회원이 생깁니다. 같은 트랜잭션이면 지급이 실패할 때 가입도 되돌아가서 "회원은 있는데 지갑이 없는 상태"가 새로 생기지 않습니다. 이 롤백은 테스트(`SignupCreditRollbackTest`)로 확인했습니다.

**Q13. 이미 가입한 회원에게는 어떻게 지급했고, 두 번 지급되지는 않나요?**
설정(`CREDIT_SIGNUP_BONUS_BACKFILL=true`)을 켜고 서버를 시작하면 한 번 도는 실행기를 만들었습니다. 이미 받았는지는 새 컬럼 없이 장부에 "가입 크레딧" 이벤트 행이 있는지로 가려서, 켜 둔 채 다시 시작해도 중복 지급이 없습니다. 관리자·탈퇴·파기 회원은 빼고, 지급 직전에 회원 행을 잠가 상태를 다시 확인합니다(그사이 탈퇴한 회원 방지). 이 부분은 PR 리뷰에서 지적받아 고쳤습니다. 배포 서버에서 실제로 돌리는 것은 병합·배포 뒤로 남아 있습니다.

### 프론트엔드

**Q14. 왜 브라우저가 백엔드를 직접 부르지 않고 Next 서버를 거치나요?**
토큰을 httpOnly 쿠키에 두고 Next 서버가 Bearer로 붙여 호출하는 구조(BFF)라서, 토큰이 자바스크립트에 노출되지 않습니다. 또 서버 컴포넌트에서 데이터를 미리 읽어 화면을 그릴 수 있습니다. `AUTH_MODE=backend`가 아니면 목업 데이터로 돌아서 백엔드 없이 프론트만 개발하고 e2e를 돌릴 수 있게 한 점도 장점입니다.

**Q15. 결제창을 팝업으로 연 이유와, 팝업이 막히면 어떻게 하나요?**
새 페이지로 이동하면 사용자가 원래 화면을 잃고 돌아오기 어려워서, PC에서는 원래 창 가운데에 작은 팝업으로 열고 결과는 원래 창에서 보여 주도록 했습니다. 팝업은 클릭 직후(서버 응답 전)에 열어야 차단되지 않아서, 제출 순간에 빈 창을 먼저 열고 서버 응답 뒤에 주소를 넣습니다. 막히면 차단을 풀고 "결제하기"를 다시 누르라고 안내합니다. 모바일은 현재 창에서 이동하는데, 모바일 흐름은 직접 확인하지 못했습니다.

**Q16. 팝업과 부모 창이 메시지를 주고받으면 보안 문제는 없나요?**
부모 창은 자기가 연 팝업에서 온 메시지만 받습니다(보낸 창과 팝업 이름을 함께 검사). 돌아올 주소도 `/my/subscription/checkout` 아래 허용 목록에 있는 것만 받습니다. 토스 결제에 쓰는 값은 주소에 싣지 않고 메시지로만 전달합니다.

### 마무리 질문

**Q17. 운영자가 결제 없이 구독을 주는 기능은 위험하지 않나요?**
시연·확인용으로만 만든 기능입니다. 운영자(`ADMIN`)만 쓸 수 있고, 결제와 크레딧에는 아무것도 남기지 않습니다. 실제 결제한 기간도 같이 취소되는 등 결제 기록과 어긋날 수 있어서, 실제 회원에게 쓰지 않는다고 문서에 명시했습니다.

**Q18. 이 파트에서 가장 어려웠던 점이나 아쉬운 점은 무엇인가요?**
가장 어려웠던 것은 돈이 움직이는 코드의 정합성, 즉 잠금 순서와 외부 PG 호출을 트랜잭션에서 분리하는 일이었습니다. 아쉬운 점은 세 가지입니다. PG 승인 후 저장 실패를 자동으로 복구하지 못하는 것, 환불을 구현하지 못한 것, 모바일 결제 흐름과 실제 배포 환경 검증이 끝나지 않은 것입니다.

**Q19. 어떻게 검증했나요?**
백엔드는 결제·크레딧·출금·가입 크레딧(롤백, 소급 지급, 동시 요청 포함)을 포함해 테스트 571개가 통과합니다. 프론트는 타입 검사, 린트, 구조 검사, 단위·e2e 테스트와 빌드로 확인했고, 서버를 연결한 화면은 Docker 확인용 스택에서 직접 눌러 봤습니다. 결제창은 카카오페이·토스 테스트 환경에서 실제로 결제해 확인했습니다.

### 동시성·출금 추가 질문

**Q20. 동시성 문제를 실제로 발견하고 고친 적이 있나요?**
네, 한 번 있었습니다. 결제와 운영자의 구독 부여·해제가 서로 다른 잠금을 쓰고 있어서, 두 작업이 같은 "가장 늦은 구독 종료일"을 읽고 기간이 겹치거나 서로 덮어쓸 수 있었습니다. 이를 발견해 #204에서 결제도 회원 행을 먼저 잠그도록 고쳐 같은 회원 행 잠금으로 맞췄습니다. 지금은 결제, 현금 결제 저장, 운영자 구독 부여·해제가 모두 회원 행 → 지갑 행 순서입니다.

**Q21. 모든 코드가 잠금 순서를 지키는지는 어떻게 보장하나요?**
순서를 서비스 클래스 주석에 남겨 두었고, 같은 순서를 쓰는 기능은 동시 요청 테스트로 확인합니다. 다만 순서를 코드나 도구가 강제하지는 못해서, 돈이나 구독 기간을 새로 다루는 기능은 같은 순서를 지켜야 한다는 약속이 필요합니다. 리뷰에서 확인해야 하는 부분이라는 한계를 알고 있습니다.

**Q22. 출금의 동시 요청은 어떻게 확인했나요?**
세 가지를 테스트로 확인했습니다. 같은 회원이 동시에 신청해도 잔액을 넘지 않는 것(#67-S5), 운영자가 같은 출금 요청을 동시에 처리하면 한쪽만 적용되는 것(#68-S9), 탈퇴 신청과 출금 신청이 동시에 와도 하나만 처리되는 것(#84-S21)입니다. 방식은 신청 때 회원 행과 지갑 행을, 운영자 처리 때 요청 행과 지갑 행을 순서대로 잠그는 것입니다.

**Q23. 직전 결제 5초 거절이 있는데 왜 행 잠금도 필요한가요?**
역할이 다릅니다. 5초 규칙은 같은 요청이 반복되는 더블클릭을 막습니다. 행 잠금은 서로 다른 요청이 같은 잔액과 구독 종료일을 읽고 덮어쓰는 문제를 막습니다. 5초가 지난 두 요청이 겹쳐도 차례로 처리되어 두 번째 이용 시작이 첫 번째 끝과 같아지는 것을 테스트(#71-S8)로 확인했습니다.

### 꼬리 질문에 대비한 한 줄 정리

- 잠금 불일치 발견·수정: #204(결제도 회원 행을 먼저 잠금)
- 출금 동시성 테스트: #67-S5(동시 신청), #68-S9(같은 요청 동시 처리), #84-S21(탈퇴·출금 경합)
