# ORM과 JPA — 개념부터 API 설계 관점까지

지금까지는 JDBC로 SQL을 직접 작성해서 데이터베이스를 다뤄왔다. ORM과 JPA를 배우면서 "SQL을 더 이상 직접 만들지 않아도 되는 이유"와 "그럼에도 여전히 SQL을 알아야 하는 이유"를 함께 정리한다.

## 1. ORM이란 — 같은 데이터를 담는 두 구조를 매핑한다

자바 쪽 엔티티 클래스와 데이터베이스 테이블은 겉보기엔 다른 언어, 다른 문법으로 되어 있지만 사실 **같은 데이터를 담는 구조**다. 속성명이 카멜 표기냐 스네이크 표기냐 같은 컨벤션 차이만 있을 뿐, 담고 있는 값과 의미는 동일하다.

지금까지는 이 두 구조 사이에 데이터를 옮기기 위해 JDBC로 SQL을 직접 작성했다. 하지만 두 구조가 결국 같은 데이터라면, "자바 엔티티 구조를 보고 SQL을 자동으로 만들어주는 도구"가 있어도 이상하지 않다 — 이것이 ORM(Object-Relational Mapping)이다. **엔티티 클래스의 정보(필드명, 타입)를 읽어서, 그에 대응하는 SQL을 대신 만들어주는 기술**이라고 정리할 수 있다.

리플렉션 API로 엔티티 정보를 꺼내 SELECT문을 직접 만들어본 경험이 이미 있다면, ORM은 바로 그 작업을 표준화하고 자동화한 라이브러리라고 이해하면 된다.

## 2. SQL을 몰라도 되는가 — 자동화는 늘 있어 왔다

"이제 SQL을 안 해도 되나요?"라는 질문은 처음 나오는 질문이 아니다. 과거 어셈블리로 프로그램을 만들던 시절, C 언어 같은 번역기(컴파일러)가 등장했을 때도 "번역기가 만드는 코드는 최적화가 안 되어 있으니 어셈블리를 배워야 한다"는 반발이 있었다. 하지만 지금 대부분의 개발자는 어셈블리를 몰라도 문제없이 개발한다.

ORM도 같은 흐름이다. 다만 완전히 손을 놓을 수는 없다 — ORM이 만들어내는 SQL에는 한계가 있고, 그 한계를 만나는 예외적인 상황에서는 결국 SQL(또는 SQL을 닮은 쿼리 형태)을 직접 다룰 수 있어야 한다. 그래서 지금 쓰는 자바의 ORM은 **SQL을 아예 몰라도 되는 완성형이 아니라, SQL 지식이 약간은 필요한 미완성형**이라고 보는 게 정확하다. (참고로 마이크로소프트의 Entity Framework처럼 SQL을 거의 몰라도 되는 완성형 ORM도 다른 플랫폼에는 존재한다.)

## 3. 엔티티만 본다 — 오브젝트 DB라는 관점

ORM을 제대로 쓴다는 것은, 개발자가 **관계형 데이터베이스의 테이블 구조를 더 이상 신경 쓰지 않고, 자바 엔티티 구조만 바라보며 개발한다**는 뜻이다.

- 엔티티에 데이터를 저장하면 ORM이 알아서 테이블에 반영한다.
- 엔티티 클래스 구조를 정의하면 ORM이 알아서 테이블을 만든다(`CREATE TABLE`을 직접 칠 필요가 없다).
- 테이블이 실제로 어떻게 생겼는지조차 몰라도 개발이 가능하다.

이런 관점에서 보면 엔티티들의 집합을 "오브젝트 DBMS"라고 부르기도 한다. 관계형 데이터베이스가 테이블로 이루어진 저장소라면, 엔티티 집합은 객체로 이루어진 저장소인 셈이다. 중요한 건 하나만 골라 일관되게 쓰는 것이다. 어설프게 알아서 어떤 때는 엔티티로, 어떤 때는 SQL을 직접 짜는 식으로 섞어 쓰면 오히려 더 혼란스러워진다.

## 4. JPA란 — 통일된 설정 표준

ORM 역할을 하는 라이브러리는 하나가 아니다. Hibernate, EclipseLink, DataNucleus, OpenJPA, ObjectDB 등 여러 구현체가 존재한다. 이들은 원래 각자 다른 방식으로 "엔티티를 SQL로 바꾸기 위한 설정"을 정의하고 있었는데, 어느 시점부터 이 설정 방식을 통일하게 되었고, 그 통일된 설정 표준이 바로 **JPA(Java Persistence API)**다.

즉 JPA는 ORM 구현체가 아니라, **엔티티·테이블·컬럼·아이디 같은 매핑 정보를 어떻게 적을지에 대한 표준 규격**이다. JDBC가 DBMS마다 제각각이던 연결 API를 하나로 통일했던 것과 같은 구조로 이해하면 된다 — JDBC가 "연결 방식"을 통일했다면, JPA는 "매핑 설정 방식"을 통일했다. 구현체는 바꿔 쓸 수 있지만, 설정은 JPA 표준 방식을 따른다.

JPA는 원래 Java EE(엔터프라이즈 에디션)에서 쓰이던 설정 방식이었다. Hibernate 같은 구현체들은 원래 JPA를 쓰지 않고 각자의 설정 방식을 가지고 있었지만, 이후 JPA 표준을 받아들이면서 지금의 형태가 되었다.

## 5. 왜 Java EE 대신 Hibernate를 쓰는가

Java EE 안에도 서블릿을 포함한 엔터프라이즈 웹 개발 요소들과 자체 영속성 기술(EJB)이 이미 존재한다. 그런데도 Hibernate를 따로 쓰게 된 배경은 크게 두 가지다.

- **무겁고 복잡한 EJB**: 초기 Java EE의 영속성 기술(EJB 2.x 엔티티 빈)은 설정이 복잡하고 무거운 애플리케이션 서버(WebLogic 같은 상용 제품이 많았다)를 필요로 했다. 이에 대한 가벼운 대안으로 2001년경 Hibernate가 등장해 널리 쓰였고, 이후 JPA 표준(2006년, Java EE 5)이 만들어질 때 오히려 Hibernate의 방식이 상당 부분 반영되었다.
- **Oracle에 대한 반감**: 자바는 Sun Microsystems가 만들어 무료로 공개한 플랫폼이고, 이후 OpenJDK와 JCP(Java Community Process)를 통해 여러 기업이 함께 발전시켜 왔다. 그런데 2010년 Oracle이 Sun을 인수하면서 자바와 MySQL(Sun이 2008년에 인수해 둔 상태)까지 함께 가져갔고, 이후 Oracle JDK의 상업적 사용을 유료 구독으로 바꿨다. "다 같이 키운 걸 가져가서 돈을 받는다"는 반감이 커졌고, Java EE 자체도 2017년 Eclipse 재단으로 넘어가 Jakarta EE로 이름이 바뀌었다. 이런 흐름 속에서 특정 벤더에 묶이지 않는 독립 구현체(Hibernate)와 Spring 조합이 사실상 표준으로 자리 잡았다.

> 참고: 무료 버전이 사라진 것은 아니다. OpenJDK 기반 JDK(Temurin, Amazon Corretto 등)는 지금도 무료이고, MySQL도 Community Edition은 여전히 무료 오픈소스다.

Spring Boot가 기본으로 쓰는 `spring-boot-starter-data-jpa`도 설정은 JPA 표준을 따르되, 실제 구현체로는 Hibernate를 사용한다. 여러 구현체 중 Hibernate를 쓰는 이유는 Oracle, MySQL, PostgreSQL, H2 등 다양한 DBMS에 대해 보편적으로 가장 무난하게 좋은 성능을 내기 때문이다(DBMS별로 보면 더 특화된 구현체가 있을 수 있지만, 전체 평균을 보면 Hibernate가 가장 균형 잡혀 있다).

## 6. 설계 관점 재확인 — 날것 API와 화면용 API는 다르다

ORM·JPA를 배우면서 자연스럽게 다시 짚이는 지점이 있다 — **API에는 성격이 다른 두 종류가 있다는 것**이다.

- **날것(raw) 데이터를 제공하는 API**: 공공 API나 오픈 API처럼, 특정 화면을 염두에 두지 않고 순수한 데이터 자체를 제공하는 API다. 이런 경우에는 업무 로직을 만들 필요가 없으므로, 엔티티 구조를 거의 그대로 서비스로 만들어 전달해도 된다. 이때는 엔티티와 서비스가 1:1로 대응한다.
- **화면에 입힐 데이터를 제공하는 백엔드 API**: 지금 만들고 있는 관리자 화면·사용자 화면처럼, 특정 화면이 필요로 하는 형태로 가공된 데이터를 제공하는 API다. 이때는 화면(페이지)이 주인공이 되고, 그 페이지를 책임지는 컨트롤러와 서비스가 1:1로 대응한다 - 서비스 1:1 원칙과 "페이지는 주인공" 원칙이 바로 이 두 번째 경우를 전제로 한 것이다.

이 둘을 혼동하면 설계가 꼬인다. 지금 만들고 있는 게 날것 데이터 제공용인지, 화면을 위한 백엔드 API인지를 먼저 분명히 하는 것이 설계의 출발점이다.
