# Docker — 배포를 위한 경량 가상화

## 1. 도커란 무엇인가

도커(Docker)는 애플리케이션을 실행하기 위한 경량화된 가상화 환경이다. 기존 가상 머신(VM)과 달리 게스트 운영체제(OS)를 포함하지 않고 호스트 OS의 커널을 공유하여, 실행에 필요한 최소한의 환경만 제공하는 것이 특징이다.

**도커의 목적: 배포**

도커의 본질적인 목적은 배포다. 애플리케이션 코드와 이를 실행하는 데 필요한 모든 의존성(라이브러리, 설정, 런타임 등)을 하나의 패키지로 묶어, 어디서든 똑같이 실행되게 하는 것이 도커가 해결하려는 핵심 문제다.

**컨테이너 비유**

실행에 필요한 모든 환경을 같이 실어나르는 컨테이너라는 이미지로 흔히 설명된다.

## 2. 왜 도커를 사용하는가

**배포 환경의 문제: "내 로컬에서는 되는데 서버에서는 안 된다"**

개발자는 로컬 머신에서 애플리케이션을 개발하고 테스트할 때는 정상적으로 동작하던 것이, 실제 운영 환경으로 배포한 후 오류가 발생하는 문제를 흔히 경험한다.

그 이유는 일반적으로 다음과 같은 경우가 많다.

- 서버에 필요한 라이브러리 버전이 다름
- OS 버전 차이 (예: Ubuntu 20.04 vs 22.04)
- 환경 변수 설정 차이
- "It works on my machine" 현상

**"그럼 VM 이미지를 통째로 배포하면 되지?"**

이런 문제를 해결하기 위해서 도커가 나오기 이전에는 가상 컴퓨터를 사용하던 적이 있었다. 가상 컴퓨터 상에서 개발하고, 그 작업환경을 그대로 운영서버로 통째로 옮기면 아무런 문제가 발생하지 않기 때문에 개발과 배포가 자연스러워지고 영속성을 가질 수 있었다.

하지만 개발용 가상 머신 환경을 그대로 운영 서버로 배포하는 것은 오버 스펙이라는 문제가 있었다. 불필요한 메모리와 리소스를 과도하게 소비하는 단점이 있었기 때문이다.

**VM으로 해결할 때의 한계**

- 부팅 시간: 게스트 OS를 부팅하는 데 수 분(3~10분)이 걸린다.
- 이미지 크기: OS 커널과 시스템 파일이 포함되어 있어 수 GB(Gigabytes) 단위다.
- 하드웨어 종속성: 특정 하드웨어 가상화 환경(KVM, VirtualBox 등)에 종속될 수 있으며, 리소스 오버헤드가 크다.

**도커가 이 문제를 어떻게 해결하는가**

도커는 개발 환경을 시뮬레이션하는 가상 머신(VM)과는 다르다. 특정 애플리케이션이 정상적으로 동작하는 데 필요한 최소한의 환경만 패키징하여 배포하는 경량 실행 환경이다. VM처럼 독립된 실행 공간을 제공하되, 게스트 OS 부팅 등 불필요한 리소스 오버헤드를 제거한 것이 핵심이다.

- 이미지 크기: 호스트 OS 커널을 공유하므로, 애플리케이션과 필요한 라이브러리만 포함한다. MB(Megabytes) 단위다.
- 시작 시간: OS 부팅 과정이 없으므로, 프로세스를 시작하는 수준으로 밀리초(Milliseconds) 단위로 시작한다.
- 밀도(Density): 호스트 커널을 공유하므로, 같은 서버에 훨씬 많은 컨테이너 인스턴스를 실행할 수 있다.

**기존 방식과 도커의 장점 대조**

| 구분 | 직접 설치 (Bare Metal) | VM | Docker (Container) |
|---|---|---|---|
| 설립 시간 | 수 시간 (환경 구축) | 수 분 (OS 부팅) | 수 밀리초 |
| 이미지/패키지 크기 | - | 수 GB | 수 MB |
| 격리 수준 | 없음 | 하드웨어/OS 수준 | 프로세스 수준 |
| 일관성 | 낮음 (환경 차이) | 높음 | 매우 높음 |
| 리소스 효율 | 높음 | 낮음 | 매우 높음 |

## 3. 언제부터 사용하게 되었는가

**리눅스 컨테이너(LXC) 기술의 배경**

도커 이전에도 컨테이너 기술은 존재했다. LXC(Linux Containers)는 네임스페이스와 cgroups를 직접 활용하여 저수준 컨테이너를 관리하는 기술이었다. 하지만 LXC는 CLI가 복잡하고, 사용법이 난해하여 일반 개발자가 쉽게 사용하기 어려웠다.

**2013년 3월: 도커 오픈소스 공개**

- 도커의 등장: 2013년 3월, 솔리드코어(Solidcore)의 엔지니어들이 개발한 도커(Docker)가 오픈소스로 공개되었다.
- LXC 기반: 도커는 내부적으로 LXC를 기반으로 했지만, 더 사용자 친화적인 CLI와 Docker Hub라는 중앙 레지스트리를 제공했다.
- 핵심 혁신: "Just do it"이라는 슬로건처럼, 복잡한 컨테이너 설정을 숨기고 `docker run` 한 줄로 컨테이너를 실행할 수 있게 했다.

**컨테이너의 표준화 및 확장**

- 클라우드 네이티브 표준: 도커의 성공 이후, 컨테이너는 클라우드 네이티브(Cloud Native) 개발의 표준이 되었다.
- 오케스트레이션 도구 등장: 수백, 수천 개의 컨테이너를 관리하기 위해 Kubernetes(K8s) 같은 오케스트레이션 도구가 등장했다.
- 확장: 도커는 더 이상 "도커"만의 기술이 아니라, 컨테이너 생태계의 대명사가 되었다. (CNCF, OCI 표준 등)

**Dockerfile → 이미지 → 컨테이너 흐름**

도커의 핵심 개념인 Dockerfile, 이미지(Image), 컨테이너(Container)의 관계는 다음과 같이 이해할 수 있다.

- **Dockerfile**: 이미지의 레시피. 실행하고 싶은 어플리케이션의 환경을 설정하는 파일로써 어떤 OS를 사용할지, 어떤 패키지를 설치할지, 어떤 설정을 할지 정의한다.
- **Image**: Dockerfile을 빌드하여 생성된 정적(Static) 아카이브. 실행 준비가 된 상태의 스냅샷이다. 즉, 가상 컴퓨터의 이미지 파일이다.
- **Container**: 이미지를 실행하여 생성된 동적(Dynamic) 인스턴스. 실제로 메모리에 올라와서 프로세스로 실행되는 "가상 컴퓨터"다.

**VM(가상 머신)과의 차이**

VM과 컨테이너(도커)의 근본적인 차이는 가상화의 수준에 있다.

| 구분 | VM (Virtual Machine) | Docker (Container) |
|---|---|---|
| 가상화 대상 | 하드웨어 + 게스트 OS (Guest OS) | 프로세스 (Process) |
| 커널 | 게스트 OS가 자체 커널을 가짐 | 호스트 OS 커널을 공유 |
| 격리 수준 | 하드웨어/OS 수준 격리 | 프로세스 수준 격리 (네임스페이스) |
| 용도 | 개발부터 실행까지 전체 작업 환경 제공 | 실행에 집중 |
| 부하 | 높음 (OS 부팅 필요) | 낮음 (프로세스 시작 수준) |

- VM: 게스트 OS의 커널까지 가상화하여 독립적인 운영체계를 제공한다. 따라서 "개발 환경"과 "실행 환경"을 모두 시뮬레이션할 수 있다.
- 도커: 호스트 OS의 커널을 그대로 공유하고, 프로세스 수준에서만 시야를 제한(격리)한다. 따라서 OS 부팅 과정이 없어 훨씬 가볍고 빠르게 실행된다.

**컨테이너의 기술적 기반: 네임스페이스와 cgroups**

도커가 "가상 컴퓨터"처럼 보이지만 실제로는 호스트 OS 위에서 실행되는 프로세스인 이유는 Linux 네임스페이스(Namespace)와 cgroups(Control Groups) 기술 덕분이다.

- 네임스페이스(Namespace): 프로세스가 인식하는 리소스(프로세스 ID, 네트워크, 파일 시스템 등)의 범위를 제한하여, 컨테이너 내부 프로세스가 호스트 시스템의 다른 리소스를 볼 수 없도록 시야를 격리하는 역할을 한다.
- cgroups(Control Groups): 프로세스 그룹이 사용할 수 있는 CPU, 메모리, 디스크 I/O 등의 리소스 사용량을 제한하여, 특정 컨테이너가 호스트 시스템의 자원을 과도하게 점유하지 못하도록 통제한다.

이 두 가지 기술이 결합되어, 독립된 환경처럼 동작하면서도 실제 하드웨어를 가상화하지 않는 경량화된 컨테이너 실행이 가능해진다.

**1. 네임스페이스 (Namespace): "무엇을 볼 수 있는가?"**

- 왜 필요한가?
  - 컨테이너 내부의 프로세스가 호스트 시스템의 다른 프로세스나 파일을 볼 수 없도록 시야를 제한해야 한다.
  - 컨테이너 내부에서는 `ps` 명령어로 자신의 프로세스만 보이고, 네트워크 인터페이스도 자신의 것만 보이며, 파일 시스템 루트(`/`)도 컨테이너 전용으로 보이게 해야 한다.
- 어떻게 동작하는가?
  - 프로세스가 보고 듣는 리소스의 범위를 정의한다.
  - 주요 네임스페이스:
    - PID: 프로세스 ID 공간. 컨테이너 내부 프로세스는 호스트의 PID를 알 수 없음.
    - Network: 네트워크 인터페이스, IP 주소, 라우팅 테이블 등을 격리.
    - Mount: 파일 시스템 마운트 포인트 격리. 컨테이너는 자신의 루트 파일 시스템만 볼 수 있음.
    - User: 사용자 ID 격리. 컨테이너 내 root는 호스트의 root와 다름.

**2. cgroups (Control Groups): "얼마나 쓸 수 있는가?"**

- 왜 필요한가?
  - 네임스페이스가 시야를 제한한다면, cgroups는 리소스 사용량을 통제한다.
  - 컨테이너가 호스트의 CPU, 메모리, 디스크 I/O를 무한정 사용해서 다른 컨테이너나 호스트 시스템을 망가뜨리는 것을 방지해야 한다.
- 어떻게 동작하는가?
  - 프로세스 그룹에 리소스 사용 한도(Quota)를 설정한다.
  - 예: "이 컨테이너는 CPU를 최대 2코어, 메모리를 최대 512MB까지만 사용하라."
  - 한도를 초과하면 프로세스가 스로틀링(Throttling)되거나 OOM(Killed)될 수 있다.

요약: 네임스페이스는 격리(Isolation)를, cgroups는 제한(Limitation)을 제공한다. 이 두 기술의 조합이 컨테이너를 가능하게 한다.

## 4. 마무리

- 도커의 목적: 배포. 애플리케이션과 의존성을 묶어 어디서든 똑같이 실행되게 하는 것.
- VM과의 차이: VM은 게스트 OS까지 가상화하여 전체 환경을 제공하지만, 도커는 호스트 커널을 공유하여 실행에 집중하는 경량 가상화다.
- 기술적 기반: 네임스페이스(시야 제한)와 cgroups(리소스 통제)가 컨테이너를 가능하게 한다.
- 역사: LXC에서 도커로, 그리고 Kubernetes 등 오케스트레이션 도구로 확장되어 클라우드 네이티브 개발의 표준이 되었다.
