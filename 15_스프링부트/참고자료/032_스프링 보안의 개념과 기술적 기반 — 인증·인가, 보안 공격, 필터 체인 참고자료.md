# 스프링 보안의 개념과 기술적 기반 — 인증·인가, 보안 공격, 필터 체인

스프링 보안을 차근차근 알아보는 첫 자료다. 이번에는 스프링 보안이 무엇이고 앞으로 어떤 내용을 다룰지 간단히 살펴보고, 자세한 내용은 이후 자료에서 천천히 다룬다.

## 1. 스프링 보안이란 무엇인가

스프링 보안(Spring Security)은 웹 애플리케이션의 보안을 책임지는 프레임워크다. 웹 서버와 서블릿 컨테이너 사이, 요청(request)과 응답(response)이 오가는 길목에 서서 보안 처리를 한다. 보안 설정은 **Java Config**(자바 설정 클래스)나 **XML**로 할 수 있다.

```
웹 서버 ⇄ [스프링 보안] ⇄ 서블릿 컨테이너(Servlet들)
              ↑
       Java Config / XML 설정
```

이 프레임워크로 다음과 같은 안전망을 구축할 수 있다.

- **인증(Authentication)**과 **인가/허가(Authorization)** 처리
- 공통 보안 공격 방어
  - CSRF(Cross-Site Request Forgery)
  - 세션 고정(Session Fixation)
  - 클릭재킹(Clickjacking)
  - XSS(Cross-Site Scripting) 등

### 1-1. 인증과 인가

보안 시스템의 가장 기본적인 두 축은 인증과 인가(허가)다.

**인증(Authentication)** — "당신은 누구인가?"

- 원격에서 웹 애플리케이션으로 요청이 들어오면, 서버는 요청한 사람이 누구인지 검증해야 한다.
- 사용자가 제공한 **자격 증명**(아이디/패스워드, OAuth2 토큰, JWT 등)을 확인해서, 시스템 안의 유효한 **주체(Principal)**인지 확인하는 과정이 인증이다.
- 인증이 정상적으로 끝나면, 그 인증 정보를 바탕으로 **사용자 정보와 권한 정보 등을 등록**하는 단계까지 포함한다.

**인가(Authorization)** — "당신에게 이 자원에 대한 권한이 있는가?"

- 인증된 사용자라면, 인증 단계에서 등록한 정보를 이용해 이 자원을 쓸 권한이 있는지 판단해야 한다. 이것이 인가(허가)다.
- 인증된 사용자가 가진 **권한 목록(Authorities)**을 바탕으로 특정 URL 호출, 서비스 메서드 실행, 파일 다운로드 등의 행위를 허용할지 거부할지 결정한다.

스프링 시큐리티는 인증 과정에서 인증 정보를 **SecurityContext**에 저장하고, 이것을 참조해서 인가 검사를 진행한다.

```
요청 → [인증] 누구인가? → 인증 정보를 SecurityContext에 저장
                                   ↓
       [인가] SecurityContext의 권한 목록을 보고 허용/거부 결정
```

### 1-2. CSRF(Cross-Site Request Forgery)

CSRF(사이트 간 요청 위조)는 사용자의 의지와 상관없이, 공격자가 의도한 대로 **다른 사이트(Cross Site)의 정보를 수정·삭제하게 만드는** 공격이다.

**정상적인 경우** — 폼을 준 서버에게 POST를 보낸다.

```
브라우저 ── GET /가입폼 ──────→ 서버
브라우저 ←──── 가입폼 ─────── 서버
브라우저 ── POST ────────────→ 서버 (같은 서버)
```

입력 폼 문서를 준 서버와 POST를 처리하는 서버가 **같은 사이트(Same Site)**다.

**비정상적인 경우** — 위조된 폼을 받아서 다른 사이트로 POST를 보낸다.

```
브라우저 ── GET /가입폼 ──────→ 공격자 서버
브라우저 ←──── 위조된 폼 ───── 공격자 서버
브라우저 ── POST ────────────→ 원래 서버 (다른 사이트로!)
```

이렇게 다른 사이트로 위조된 요청을 보내게 하는 방식을 CSRF라고 한다.

**공격이 성립하는 조건과 흐름**

이 공격은 사용자가 원래 사이트에 로그인한 적이 있고, 그쪽의 세션이나 쿠키 같은 **인증 자격 증명이 브라우저에 남아 있을 때** 통한다.

```
[사용자 브라우저]          [공격자 사이트]          [타깃 서버]
      │ 1. 피싱/악성 페이지 방문 →│                       │
      │← 2. 위조된 폼/스크립트 응답│                       │
      │   (자동 POST 제출 코드 포함)                       │
      │ 3. 위조된 POST 요청 전송 ─────────────────────────→│
      │   (기존 세션 쿠키가 자동으로 함께 전송 → 공격 성공)  │
```

1. 사용자가 공격자가 만든 피싱/복제 사이트에 접속하거나, 이메일·게시판 등의 악성 링크/스크립트를 클릭한다.
2. 그 페이지에는 타깃 사이트로 POST를 자동 제출하는 코드가 들어 있다.
3. 브라우저는 타깃 사이트로 요청을 보낼 때 그 사이트의 **인증 쿠키를 자동으로 함께 보낸다.**

결국 사용자는 자신도 모르는 사이에 원래 사이트로 비밀번호 변경, 송금, 회원 정보 수정 같은 악의적인 POST 요청을 보내게 된다.

> **추가 설명 — 스프링 시큐리티의 CSRF 방어**: 자료에는 방어 방법이 빠져 있다. 스프링 시큐리티는 기본으로 **CSRF 토큰**을 쓴다. 서버가 폼을 줄 때 예측할 수 없는 토큰 값을 숨겨서 함께 주고, POST·PUT·DELETE처럼 데이터를 바꾸는 요청이 올 때 그 토큰이 맞는지 `CsrfFilter`가 검사한다. 공격자의 위조된 폼에는 이 토큰이 없으므로 요청이 거부된다. 쿠키는 브라우저가 자동으로 실어 보내지만, 토큰은 진짜 폼에만 들어 있다는 점이 핵심이다. 이 밖에 쿠키의 `SameSite` 속성으로 다른 사이트에서 시작된 요청에 쿠키가 실리지 않게 하는 방법도 함께 쓴다.

### 1-3. 세션 고정(Session Fixation)

웹 서버는 클라이언트를 식별하기 위해 **세션 ID를 쿠키로 발급**하고, 요청이 올 때마다 함께 오는 그 ID로 클라이언트를 알아본다.

- **쿠키**: 웹 서버가 브라우저(클라이언트)에게 저장해 달라고 요청한 텍스트 데이터다. 이 데이터는 그 서버로 요청할 때마다 **항상 함께 전달**된다.
- **세션**: 웹 클라이언트가 웹 서버에 데이터를 저장할 수 있도록 허락된 기간이다. 그 기간 동안 서버에 값을 저장할 수 있는 공간을 **세션 저장소**라고 한다.

> **추가 설명 — 세션을 공간으로 보면 더 쉽다**: 세션은 보통 "기간"보다 **서버 쪽에 클라이언트별로 마련된 저장 공간**으로 설명한다. 서버는 클라이언트마다 세션 저장소를 하나씩 만들고, 그 저장소를 찾는 열쇠(세션 ID)만 쿠키로 브라우저에 건넨다. 그래서 세션 ID라고 부르는 것이고, 이 저장소에는 정해진 유효 시간(타임아웃)이 있다.

피트니스 센터에서 회원 카드를 발급받는 것과 비슷하다. 회원을 알아보기 위해 카드를 발급하고, 다음부터 방문할 때마다 그 카드를 들고 와서 회원임을 확인받아야 한다.

브라우저 개발자 도구의 Network 탭에서 요청의 Cookies를 보면, 서버가 발급한 식별 ID가 쿠키에 들어 있는 것을 확인할 수 있다.

```
Request Cookies
  JSESSIONID   823BC2DB38ADDFFEF2A9E6786CE21405   ← 톰캣이 발급한 세션 ID
```

그런데 사용 기간이 남아 있는 동안 누군가 이 ID를 도용해서 쓴다면 어떻게 될까?

> 원문 바로잡기 — 자료는 "유효한 세션 ID를 도용하는 공격"을 세션 고정이라고 설명했는데, 이것은 **세션 하이재킹(Session Hijacking)**에 가깝다. **세션 고정**은 순서가 반대다. 공격자가 **자기가 미리 알고 있는 세션 ID**를 피해자의 브라우저에 심어 두고(고정), 피해자가 그 ID를 가진 채로 로그인하기를 기다린다. 피해자가 로그인하면 그 세션은 "인증된 세션"이 되는데, 공격자는 이미 그 ID를 알고 있으므로 그대로 피해자 행세를 할 수 있다. 그래서 방어책이 아래처럼 **로그인할 때 세션 ID를 바꾸는 것**이다. 로그인 전에 심어 둔 ID는 로그인과 동시에 쓸모가 없어진다.

스프링 시큐리티는 사용자가 로그인(인증)에 성공할 때마다 기존 세션을 무효화하고 새 세션 ID를 발급하거나, 세션의 내용은 유지한 채 세션 ID만 바꾸는 방식으로 세션 고정 공격을 막는다. `sessionFixation()` 설정으로 다음 전략을 고를 수 있다.

| 전략 | 동작 |
|---|---|
| `changeSessionId` (기본값) | 기존 세션을 그대로 두고 **세션 ID만** 새로 발급한다 |
| `newSession` | 완전히 새로운 세션을 만들고, 기존 세션의 속성은 **옮기지 않는다** |
| `migrateSession` | 새로운 세션을 만들고, 기존 세션의 속성을 **모두 복사**해 옮긴다 |
| `none` | 아무것도 하지 않는다 (방어 해제) |

> **추가 설명 — 스프링 시큐리티 6의 설정 문법**: 자료의 `sessionManagement().sessionFixation()`은 예전 체이닝 방식이다. 스프링 시큐리티 6에서는 람다 방식으로 쓴다. 기본값이 이미 `changeSessionId`이므로 따로 설정하지 않아도 방어는 켜져 있다.
>
> ```java
> http.sessionManagement(session -> session
>         .sessionFixation(fixation -> fixation.changeSessionId()));
> ```

### 1-4. 클릭재킹(Clickjacking)

클릭재킹은 공격자가 **투명한 `<iframe>`** 안에 타깃 웹사이트를 띄워 두고, 그 위에 악성 버튼이나 링크를 겹쳐 놓아서, 사용자가 자신도 모르게 타깃 사이트의 기능을 클릭하게 만드는 공격이다. 여기서 공격자는 타깃 사이트의 주인이 아니라, 그 사이트를 쓰는 **사용자를 속이는 제3자**(피싱 사이트 운영자)다.

```
┌─────────────────────────────────┐
│ [공격자의 피싱 사이트 — 보이는 화면] │
│   축하합니다! 100% 당첨 이벤트       │
│        [ 무료 경품 받기 ]  ← 클릭    │
└─────────────────────────────────┘
          ↓ 같은 위치에 겹쳐 있음
┌─────────────────────────────────┐
│ [투명한 <iframe> — my-bank.com]   │
│ (사용자가 로그인한 상태)            │
│        [ 송금 확정 ] ← 실제 클릭됨   │
└─────────────────────────────────┘
```

예를 들어 공격자가 "경품 당첨! 아래 버튼을 클릭하세요"라는 피싱 사이트를 만들고, 이벤트 버튼 바로 위에 투명하게 처리한 은행 사이트의 '송금 확정' 버튼을 겹쳐 놓는다. 이미 은행에 로그인해 있던 사용자가 경품을 받으려고 버튼을 누르면, 실제로는 투명한 은행 사이트의 버튼을 누르게 되어 자신도 모르게 송금을 실행한다.

스프링 시큐리티는 **응답 헤더**로 이를 막는다. `X-Frame-Options: DENY`를 기본으로 붙여서, 외부 사이트의 `<iframe>` 안에서 애플리케이션 페이지가 그려지는 것을 원천 차단한다. 같은 사이트 안에서만 허용하려면 `SAMEORIGIN`으로 바꿀 수 있다.

> 원문 바로잡기 — 자료는 `X-Frame-Options`와 CSP의 `frame-ancestors`를 **둘 다 자동으로** 설정한다고 했지만, 스프링 시큐리티가 기본으로 붙이는 것은 `X-Frame-Options: DENY`뿐이다. CSP(`Content-Security-Policy`) 헤더는 기본으로 붙지 않으므로, `frame-ancestors`를 쓰려면 개발자가 직접 설정해야 한다. 기본값도 "DENY 또는 SAMEORIGIN"이 아니라 **DENY**다.

### 1-5. XSS(Cross-Site Scripting)

XSS(크로스 사이트 스크립팅)는 웹 애플리케이션의 입력 폼이나 URL 파라미터 등에 **악의적인 자바스크립트 코드를 심어서**, 다른 사용자의 브라우저에서 그 스크립트가 실행되게 만드는 공격이다. 이를 통해 세션 쿠키 탈취, 악성 코드 유포, 페이지 변조 등이 일어날 수 있다.

스프링 시큐리티가 제공하는 방어 수단은 다음과 같다.

- **X-XSS-Protection 헤더**: 브라우저에 내장된 XSS 필터를 다루는 응답 헤더다.
- **Content-Security-Policy(CSP) 지원**: 스크립트, 스타일, 이미지 등을 어디서 불러올 수 있는지 엄격하게 제한하는 CSP 정책을 헤더로 구성할 수 있게 지원한다. 허락되지 않은 출처의 악성 스크립트 실행을 막는다.
- **HttpOnly 쿠키**: 세션 쿠키에 `HttpOnly` 속성을 붙여서, 자바스크립트(`document.cookie`)로 쿠키를 읽어 가는 시도를 막는다.

> 원문 바로잡기 — 자료는 `X-XSS-Protection: 1; mode=block`을 기본으로 붙여 스크립트를 감지하면 렌더링을 멈춘다고 했는데, 이것은 예전 버전 이야기다. 최신 브라우저들은 이 내장 XSS 필터(XSS Auditor)를 이미 없앴고, 오히려 이 필터가 새로운 공격 통로가 되기도 했다. 그래서 스프링 시큐리티 6은 기본으로 **`X-XSS-Protection: 0`(필터 끄기)**을 보낸다. 지금의 XSS 방어는 이 헤더가 아니라 **출력할 때 HTML 이스케이프**(타임리프 `th:text` 등)와 **CSP**가 중심이다.
>
> 또 세션 쿠키(`JSESSIONID`)의 `HttpOnly`는 스프링 시큐리티가 아니라 **톰캣(서블릿 컨테이너)과 스프링 부트**가 기본으로 켜 두는 설정이다(`server.servlet.session.cookie.http-only`, 기본값 `true`).

지금까지 설명한 것들은 사실 인증 모듈을 직접 만들면서 방어할 수도 있다. 하지만 스프링이 제공하는 프레임워크를 쓰면 직접 구현할 필요 없이 **몇 번의 설정만으로** 해결할 수 있다.

## 2. 스프링 보안 처리의 실행 흐름

스프링 보안은 내부 동작을 감추고 있어서, 개발자는 몇 가지 설정만 하면 된다. 그래도 어떤 동작이 숨어 있는지 가볍게 들여다보는 것도 나쁘지 않다.

```
HTTP 요청
   ↓
┌─ 서블릿 컨테이너 (Tomcat 등) ─────────────────────┐
│  DelegatingFilterProxy   (서블릿 필터 영역)          │
│     ↓                                              │
│  ┌─ 스프링 빈 영역 ─────────────────────────┐      │
│  │  FilterChainProxy                         │      │
│  │     ↓                                     │      │
│  │  SecurityFilterChain (인증/인가 보안 필터 모음) │ │
│  └───────────────────────────────────────────┘      │
│     ↓                                              │
│  ┌─ 스프링 MVC 영역 ─────────────────────────┐      │
│  │  DispatcherServlet → Controller(비즈니스 로직) │  │
│  └───────────────────────────────────────────┘      │
└────────────────────────────────────────────────────┘
```

1. 클라이언트의 HTTP 요청을 처음 받는 것은 **톰캣**이다. 톰캣은 스프링 IoC에 있는 필터 객체를 호출해야 하는데, IoC에서 객체를 꺼내는 일은 톰캣이 할 수 없다.
2. 그래서 스프링은 IoC의 필터 객체를 꺼내 호출해 주는 **`DelegatingFilterProxy`**를 만들어서 톰캣이 호출할 수 있는 자리에 둔다.
3. `DelegatingFilterProxy`가 호출한 **`FilterChainProxy`**는 스프링 IoC에 있는 보안 필터들을 실행하는데, 이때 **`SecurityFilterChain`**이 실행된다.
4. 이 보안 체인은 요청이 스프링 컨트롤러에 도착하기 전에 요청 내용이나 헤더 정보를 확인해서, 인증을 요구하거나 요청을 허가한다.

이 부분을 아래에서 좀 더 자세히 알아본다.

## 3. 스프링 보안을 가능하게 하는 기술적 기반

스프링 보안은 **서블릿 필터(Servlet Filter)** 기술을 기반으로 동작한다.

### 3-1. 서블릿 필터 체인(Servlet Filter Chain)

서블릿 필터 체인은 서블릿 컨테이너(Tomcat, Jetty 등)가 직접 만들고 관리하는 **필터들의 연속된 묶음**이다.

```
웹 서버 ⇄ WAS ⇄ [필터][필터][필터] ⇄ Servlet
                 └── FilterChain ──┘
```

클라이언트의 HTTP 요청이 최종 서블릿(`DispatcherServlet`)에 도착하기 **전에**, 그리고 서블릿이 만든 응답이 클라이언트로 돌아가기 **전에** 필터 코드가 실행된다. 필터로는 다음과 같은 공통 전처리·후처리 작업을 한다.

- 인코딩 변경
- XSS 방어
- 로깅
- 요청/응답 변형 등

여러 필터가 체인 형태로 이어져 있어서, 각 필터는 자기 로직을 실행한 뒤 `chain.doFilter()`를 호출해 다음 필터로 요청을 넘긴다. 이 내용은 다음 자료에서 직접 연습해 본다.

### 3-2. DelegatingFilterProxy

톰캣과 스프링은 각자 자기 생명주기 안에서 쓰는 객체들을 담는 **컨테이너**를 따로 가지고 있다.

- **서블릿 컨테이너**: 서블릿 객체, 필터 객체, 리스너 객체 등
- **스프링 IoC 컨테이너**: DI를 위한 여러 객체(빈)

그런데 이 두 컨테이너는 하나로 공유해서 쓸 수 없다. 즉, 톰캣은 스프링 IoC 컨테이너에 등록된 빈을 **직접 꺼내 호출할 수 없다.**

```
┌─ 서블릿 컨테이너 ─────────┐            ┌─ 스프링 컨테이너 ─────────────┐
│ Filter                    │            │ Spring Bean                   │
│  ├ FilterA                │   위임      │  ├ FilterChainProxy           │
│  ├ DelegatingFilterProxy ═╪═══════════→│  │   └ SecurityFilterChain(들) │
│  └ FilterB                │ (Delegate) │  └ CustomBeans...             │
└───────────────────────────┘            └───────────────────────────────┘
```

이 문제를 풀기 위해 두 영역을 잇는 **다리** 역할의 객체가 필요한데, 그것이 `DelegatingFilterProxy`다. 스프링 프레임워크(Spring Web)가 만든 클래스로, 서블릿 컨테이너의 생명주기와 스프링의 `ApplicationContext`를 연결하려고 만들어졌다.

- 서블릿 컨테이너에는 **일반 필터처럼 등록**되어 요청을 먼저 받는다.
- 하지만 보안 로직을 직접 처리하지 않고, 스프링에 등록된 보안 전용 필터(`FilterChainProxy`)에게 요청을 **넘겨주기만** 한다.
- 이렇게 위임(Delegate)하기 때문에 서블릿 영역에서도 스프링의 의존성 주입(DI) 같은 기능을 그대로 쓸 수 있다.

> **추가 설명 — 이름 그대로 읽기**: Delegating(위임하는) + Filter(필터) + Proxy(대리인). 톰캣 눈에는 평범한 필터 하나로 보이지만, 실제 일은 스프링 빈에게 넘기는 **대리인 필터**라는 뜻이다. 스프링 부트에서는 이 등록 과정도 자동으로 해 주므로, 개발자가 `DelegatingFilterProxy`를 직접 다룰 일은 거의 없다.

### 3-3. FilterChainProxy

`DelegatingFilterProxy`에게서 일을 넘겨받아 **실제로 처리하는 주인공**이며, 스프링이 관리하는 빈이다. 내부에 여러 개의 `SecurityFilterChain`(보안 필터 목록)을 가지고 있어서, 들어온 요청의 URL 경로에 맞는 필터들을 찾은 뒤 순서대로 실행한다.

서블릿 컨테이너 쪽에서 보면 필터 하나처럼 보이지만, 안에서는 스프링 시큐리티의 모든 보안 필터 목록을 감싸서 관리하는 **핵심 진입점**이다. 구체적인 역할은 다음과 같다.

**① 요청 URL 매칭과 보안 필터 체인 선택**

- `FilterChainProxy`는 `SecurityFilterChain`의 목록(`List<SecurityFilterChain>`)을 가지고 있다.
- 요청이 들어오면 각 `SecurityFilterChain`의 `RequestMatcher`를 차례로 비교해서, 요청 경로(URL, HTTP 메서드 등)에 **가장 먼저 맞는 단 하나의 필터 체인**을 고른다.

**② 보안 필터의 순차 실행**

- 고른 `SecurityFilterChain` 안에는 역할이 다른 보안 필터들이 정해진 순서대로 들어 있다.
  - `CsrfFilter` — CSRF 토큰 검사
  - `UsernamePasswordAuthenticationFilter` — 폼 로그인(아이디/비밀번호) 인증
  - `BearerTokenAuthenticationFilter` — 토큰(JWT 등) 인증
  - `AuthorizationFilter` — 인가 검사
- `FilterChainProxy`는 이 필터들을 순서대로 호출해서 인증, 인가, 공통 보안 위협 방어 로직을 실행한다.

> 원문 바로잡기 — 자료는 인가 필터로 `FilterSecurityInterceptor`를 들었지만, 스프링 시큐리티 6에서는 이 필터가 더 이상 권장되지 않고 **`AuthorizationFilter`**로 바뀌었다. 위 목록은 최신 이름으로 고쳐 적었다.

**③ 보안 컨텍스트 초기화와 예외 처리**

- 요청 처리 전후로 `SecurityContextHolder`를 관리해서, 이전 요청의 흔적이 남아 비즈니스 로직에 영향을 주지 않도록 보안 컨텍스트를 정리한다.
- 필터 체인 안에서 생긴 인증·인가 예외(`AuthenticationException`, `AccessDeniedException`)를 모아서, 적절한 응답(로그인 페이지로 리다이렉트, 401/403 에러 응답 등)으로 바꿔 주는 전역 보안 제어 역할을 한다.

| 예외 | 의미 | 응답 |
|---|---|---|
| `AuthenticationException` | 인증 실패 — 누군지 모름 | 로그인 페이지로 리다이렉트 또는 401 |
| `AccessDeniedException` | 인가 실패 — 누군지는 알지만 권한 없음 | 403 |

## 4. 주요 구현체와 핵심 구성 요소

스프링 보안의 내부 구조를 이루는 핵심 인터페이스와 구현체는 다음과 같다.

| 구성 요소 | 설명 |
|---|---|
| `SecurityFilterChain` | 보안 처리를 맡은 여러 보안 필터들의 묶음. URL 패턴에 따라 서로 다른 필터 체인을 적용할 수 있다. Spring Boot 3.x / Spring Security 6.x에서는 `SecurityFilterChain` 빈을 **직접 등록**하는 방식을 쓴다 |
| `SecurityContextHolder` & `SecurityContext` | 지금 실행 중인 스레드의 보안 컨텍스트를 저장하는 공간. 인증이 끝나면 인증 객체가 `SecurityContext`에 저장되어 애플리케이션 어디서든 참조할 수 있다 |
| `Authentication` | 인증된 주체의 정보(Principal), 자격 증명(Credentials), 부여된 권한 목록(Authorities)을 담는 객체 |
| `AuthenticationManager` | 인증 요청을 처리하는 핵심 인터페이스. 실제 인증 로직은 등록된 `AuthenticationProvider`들에게 위임한다 |

```
SecurityContextHolder
  └ SecurityContext
      └ Authentication
          ├ Principal    — 누구인가 (사용자 정보)
          ├ Credentials  — 무엇으로 증명했나 (비밀번호 등)
          └ Authorities  — 무엇을 할 수 있나 (ROLE_ADMIN 등)
```

> **추가 설명 — "현재 스레드"의 의미**: 톰캣은 요청 하나를 스레드 하나로 처리한다. `SecurityContextHolder`는 기본으로 `ThreadLocal`에 보안 컨텍스트를 담기 때문에, 같은 요청을 처리하는 동안에는 컨트롤러든 서비스든 어디서나 `SecurityContextHolder.getContext().getAuthentication()`으로 "지금 로그인한 사람"을 꺼낼 수 있다. 요청이 끝나면 `FilterChainProxy`가 이것을 비워서, 같은 스레드가 다음 요청을 처리할 때 이전 사용자 정보가 섞이지 않게 한다.

서블릿 필터가 생소하다면 **사용자 정의 필터를 직접 만들어 체인에 추가해 보는 것**이 이해에 도움이 된다. 필터가 요청을 어떻게 가로채고 제어하는지 직접 확인할 수 있다.
