# 쿠키의 의미와 쿠키를 이용한 로그인 상태 유지

지난 자료에서는 스프링 시큐리티의 필터를 쓰지 않고, 컨트롤러와 서비스로 사용자의 아이디와 비밀번호를 검증하는 기본 로그인 로직을 직접 구현해 보았다. 하지만 그 로직에는 **치명적인 허점**이 있다.

로그인 버튼을 눌러 인증을 마쳐도, 다른 페이지로 이동하거나 화면을 새로고침하면 서버는 이 사용자가 **방금 로그인에 성공한 사용자라는 사실을 기억하지 못한다.**

이번 자료에서는 서버가 클라이언트를 식별하고 상태를 유지하는 원리를 알아보고, 이를 바탕으로 세션을 활용한 로그인 상태 유지와 로그아웃 구현 방법을 알아본다.

> **추가 설명 — 이 자료의 범위**: 소개 글에는 세션과 로그아웃 구현까지 언급되어 있지만, 실제 본문은 **쿠키**까지만 다루고 마지막에 "그래서 세션이 등장했다"로 끝난다. 세션을 이용한 로그인 상태 유지와 로그아웃은 다음 자료의 내용이다.

## 1. 클라이언트 식별의 문제

웹의 바탕이 되는 HTTP 프로토콜은 상태를 유지하지 않는 **Stateless(무상태)** 특징을 가진다.

```
[클라이언트] ── 요청 1: 로그인 요청 ──────→ [서버] "로그인 성공!"
[클라이언트] ←─ 응답 1: 로그인 성공 ─────── [서버]

[클라이언트] ── 요청 2: 마이페이지 요청 ──→ [서버] (이전 상태를 전혀 기억하지 못함)
[클라이언트] ←─ 응답 2: "누구신가요?" ───── [서버]
         "어라?"
```

그래서 클라이언트가 요청을 보낼 때마다 서버는 이를 **완전히 새로운 요청**으로 취급한다. 로그인에 성공한 뒤 다음 페이지를 요청할 때, 클라이언트가 자신을 입증할 정보를 매번 함께 보내지 않으면 서버는 로그인 여부를 확인할 길이 없다.

그렇다면 서버는 어떻게 개별 클라이언트를 구분할 수 있을까?

- **IP 주소로 식별할 수 있을까?** 아니다. 같은 와이파이나 회사 네트워크를 쓰는 여러 사용자는 **같은 공인 IP를 공유**한다. 그래서 IP만으로는 개별 사용자를 구분할 수 없다.
- **컴퓨터나 브라우저 정보로 식별할 수 있을까?** 그것도 아니다. 같은 종류의 컴퓨터나 브라우저를 쓰는 사용자는 수없이 많다.

결국 클라이언트를 명확히 식별하려면, 서버가 클라이언트에게 일종의 **'표식(식별자)'을 발급**해 주고, 클라이언트가 **매 요청마다 그 표식을 지참해 보여 주는** 방식이 필요하다.

> **추가 설명 — 왜 일부러 무상태로 만들었나**: 서버가 모든 클라이언트와의 연결과 상태를 계속 붙잡고 있으면, 접속자가 많아질수록 서버 자원이 버티지 못한다. 요청 하나를 처리하고 바로 잊어버리면 서버는 훨씬 많은 사용자를 감당할 수 있고, 서버를 여러 대로 늘리기도 쉽다. 무상태는 결함이 아니라 **확장성을 위한 선택**이고, 필요한 상태만 쿠키 같은 장치로 따로 얹는 것이다.

## 2. 쿠키(Cookie)를 통한 클라이언트 식별

웹에서 쓰이는 이 '표식'의 대표적인 장치가 바로 **쿠키(Cookie)**다. 쿠키는 서버가 **HTTP 응답 헤더**를 통해 클라이언트에게 전달하는 작은 데이터 조각이다.

브라우저는 서버에게서 받은 쿠키를 저장해 두었다가, 이후 그 서버로 보내는 요청의 헤더에 쿠키를 **자동으로** 담아 전송한다.

```
[서버] ── 응답 헤더  Set-Cookie: clientId=user-12345 ──→ [브라우저] 쿠키 저장
[브라우저] ── 요청 헤더  Cookie: clientId=user-12345 ──→ [서버] "아하! user-12345님이구나!"
```

이것은 **피트니스 센터의 회원권**에 비유할 수 있다. 회원이 방문할 때마다 본인 확인 과정을 거치는 대신, 발급받은 회원권만 내밀고 빠르게 입장하는 회원권 시스템과 같다.

| 순서 | 피트니스 센터 | 웹 |
|---|---|---|
| 1 | 최초 방문, 본인 확인 | 첫 요청(로그인 등) |
| 2 | 회원권 발급 | 응답 헤더 `Set-Cookie` |
| 3 | 재방문 때 회원권 제시 | 요청 헤더 `Cookie` |
| 4 | 회원 확인 후 입장 | 서버가 쿠키 값으로 클라이언트 식별 |

### 2-1. 쿠키 생성과 전달 코드

이번에는 스프링 컨트롤러에서 쿠키를 만들어 클라이언트에 전달하는 방법을 알아본다. 먼저 `controller` 패키지에 데모용 컨트롤러 파일(`CookieDemoController.java`)을 추가한다.

```
src/main/java/com/example/security
└─ controller
   ├─ admin/
   ├─ AuthController.java
   ├─ CookieDemoController.java   ← 추가
   ├─ HomeController.java
   └─ MenuController.java
```

이 파일에 다음 내용을 붙여 넣는다.

```java
package com.example.security.controller;

import jakarta.servlet.http.Cookie;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class CookieDemoController {

    @GetMapping("/set-cookie")
    public String setCookie(HttpServletResponse response) {
        // 1. "clientId"라는 이름으로 쿠키 생성
        Cookie cookie = new Cookie("clientId", "user-12345");

        // 2. 응답 헤더에 쿠키 추가
        response.addCookie(cookie);

        return "쿠키가 발급되었습니다.";
    }
}
```

앞에서 쿠키는 응답 헤더를 통해 클라이언트로 전달되는 작은 텍스트 데이터라고 했다. 스프링에서는 **서블릿 API의 `Cookie` 객체**로 쿠키를 만든다. 만든 쿠키는 `HttpServletResponse` 객체의 `addCookie()` 메서드로 응답 헤더에 추가해 전달한다.

> **추가 설명 — HttpServletResponse는 어디서 오나**: 컨트롤러 메서드의 매개변수에 `HttpServletResponse`를 선언하면, 스프링의 프론트 컨트롤러(`DispatcherServlet`)가 지금 처리 중인 응답 객체를 넣어 준다. `@RestController`이므로 반환한 문자열은 응답 본문이 되고, 쿠키는 그와 별개로 **응답 헤더**에 붙는다.

쿠키를 쓸 때 주의해야 할 특징과 제약은 다음과 같다.

- **문자열 데이터만 저장 가능**: 쿠키는 HTTP 헤더를 통해 평문(Plain Text)으로 전송되므로, 객체나 숫자 같은 다른 타입을 직접 저장할 수 없고 **문자열만** 지원한다.
- **특수문자 및 한글 제한**: 공백, 세미콜론(`;`), 쉼표(`,`) 같은 특수문자는 HTTP 응답 헤더의 구분자로 해석되어 파싱 오류를 일으킬 수 있다. 그래서 공백, 특수문자, 한글 등을 값으로 보낼 때는 **`URLEncoder`로 인코딩한 뒤** 저장해야 한다.

> **추가 설명 — 인코딩과 디코딩 코드**: 톰캣은 쿠키 값에 공백이나 한글이 들어 있으면 쿠키를 만드는 시점에 `IllegalArgumentException`("An invalid character was present in the Cookie value")을 낸다. 저장할 때 인코딩하고, 꺼낼 때 디코딩한다.
>
> ```java
> // 저장할 때
> String encoded = URLEncoder.encode("홍 길동", StandardCharsets.UTF_8);  // %ED%99%8D+...
> response.addCookie(new Cookie("name", encoded));
>
> // 꺼낼 때
> String name = URLDecoder.decode(encodedValue, StandardCharsets.UTF_8);
> ```
>
> 숫자를 저장하려면 `String.valueOf(1000)`처럼 문자열로 바꿔 넣고, 꺼낼 때 `Integer.parseInt()`로 되돌린다.

이후 과정을 확인하기 위해 프로젝트를 실행하고 랜딩 페이지에 접속한 뒤, 브라우저 개발자 도구(F12)의 **Application 탭 → Cookies** 항목을 확인한다. 지금은 쿠키가 하나도 없다.

이제 **Network 탭**을 선택하고 주소란에 `http://localhost:8080/set-cookie`를 입력한 뒤 Enter 키를 누른다. 그러면 서버가 응답할 때 HTTP 응답 헤더에 `Set-Cookie: clientId=user-12345` 형태의 정보가 담긴다.

> **추가 설명 — 화면의 Set-Cookie가 더 긴 이유**: 강의 화면의 응답 헤더에는 `Set-Cookie: clientId=user-12345; Expires=Mon, 19 Oct 2026 14:38:15 GMT; Max-Age=3600; Path=/`처럼 옵션이 더 붙어 있다. 위 코드에 `cookie.setMaxAge(3600)`과 `cookie.setPath("/")`를 추가한 버전으로 실행했기 때문이다. 옵션 없이 실행하면 `Set-Cookie: clientId=user-12345`만 보인다. 각 옵션의 의미는 4장에서 다룬다.

서버의 응답으로 `Set-Cookie` 헤더가 클라이언트에 전달되면 브라우저는 그 값을 **브라우저 안에 저장**한다. Application 탭의 Cookies 창을 다시 보면 `clientId`(값 `user-12345`)가 생긴 것을 확인할 수 있다.

이 쿠키를 받은 브라우저는 내부 저장소에 쿠키를 보관하고, 이후 서버에 요청을 보낼 때마다 `Cookie: clientId=user-12345` 헤더를 **자동으로** 포함해 보낸다.

## 3. 쿠키를 활용한 상태 저장: 사용자 선택 상태 유지하기

쿠키는 단순히 식별자 역할만 하는 것이 아니라, 사용자의 간단한 **설정 정보나 상태**를 저장하는 데도 쓸 수 있다. 사용자가 원하는 웹 페이지 배경색을 고르면 그 값을 쿠키에 저장해 두고, 다시 방문했을 때 저장된 배경색을 유지하는 간단한 예제로 쿠키의 동작을 확인해 본다.

### 3-1. 배경색 설정 컨트롤러 구현

```java
package com.example.security.controller;

import jakarta.servlet.http.Cookie;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.CookieValue;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestParam;

@Controller
public class ThemeController {

    // 쿠키를 읽어 페이지 배경색을 설정하는 매핑
    @GetMapping("/theme")
    public String showThemePage(
            @CookieValue(name = "bgColor", required = false, defaultValue = "white") String bgColor,
            Model model) {

        // 읽어온 쿠키 값을 뷰로 전달
        model.addAttribute("bgColor", bgColor);
        return "theme";
    }

    // 사용자가 선택한 배경색을 쿠키에 저장하는 매핑
    @PostMapping("/theme")
    public String saveTheme(@RequestParam("bgColor") String bgColor, HttpServletResponse response) {
        Cookie cookie = new Cookie("bgColor", bgColor);

        response.addCookie(cookie);
        return "redirect:/theme";
    }
}
```

### 3-2. theme.html 뷰 작성

```html
<!DOCTYPE html>
<html xmlns:th="http://www.thymeleaf.org">
<head>
    <meta charset="UTF-8">
    <title>테마 설정</title>
</head>
<body th:style="'background-color: ' + ${bgColor} + ';'">
    <h1>페이지 배경색 설정</h1>
    <p>현재 선택된 배경색: <strong th:text="${bgColor}">white</strong></p>

    <form action="/theme" method="post">
        <label><input type="radio" name="bgColor" value="white" checked> 하얀색</label>
        <label><input type="radio" name="bgColor" value="lightblue"> 연파랑</label>
        <label><input type="radio" name="bgColor" value="lightgreen"> 연초록</label>
        <button type="submit">저장</button>
    </form>
</body>
</html>
```

`@CookieValue` 어노테이션을 쓰면 클라이언트가 요청 헤더에 담아 보낸 `bgColor` 쿠키의 값을 편리하게 꺼낼 수 있다. 이처럼 쿠키를 사용하면 서버 쪽에 DB 저장 없이도 사용자별 상태 값을 간편하게 유지할 수 있다.

> **추가 설명 — 동작 흐름**
>
> 1. `GET /theme` — 처음에는 `bgColor` 쿠키가 없으므로 `defaultValue`인 `white`가 들어간다.
> 2. 라디오 버튼으로 색을 골라 저장 → `POST /theme` — 서버는 그 색을 `bgColor` 쿠키로 설정하고 `redirect:/theme`.
> 3. 브라우저가 `GET /theme`을 다시 요청하면서 `Cookie: bgColor=lightblue`를 함께 보낸다.
> 4. `@CookieValue`가 그 값을 꺼내 모델에 담고, 타임리프가 `<body>`의 `background-color`에 넣는다.
>
> 쿠키는 **브라우저마다** 따로 저장되므로, 크롬에서 바꾼 색은 다른 브라우저에서는 보이지 않는다.

> **추가 설명 — @CookieValue의 옵션**: `defaultValue`를 지정하면 자동으로 `required = false`가 되므로, 위 코드의 `required = false`는 생략해도 된다. `defaultValue`도 `required = false`도 없이 쓰면, 쿠키가 없을 때 **400 Bad Request**(필수 쿠키 누락) 오류가 난다.

> **추가 설명 — 이 예제의 쿠키는 브라우저를 닫으면 사라진다**: `saveTheme()`에서 `setMaxAge()`를 지정하지 않았으므로 이 쿠키는 4-2의 **세션 쿠키**다. 브라우저를 완전히 종료했다가 다시 열면 배경색이 white로 돌아간다. 다시 방문해도 유지되게 하려면 `cookie.setMaxAge(60 * 60 * 24)`(하루)처럼 기간을 정하고 `cookie.setPath("/")`를 함께 지정한다.

## 4. 쿠키의 스코프와 생명주기

쿠키는 모든 요청마다 항상 전달되는 것이 아니라, 정해진 **유효 범위(Scope)**와 **저장 기간(Life Cycle)**에 따라 동작이 달라진다. 필요 이상으로 많은 요청에 쿠키가 실리면 네트워크 부담이 생기고 보안상 노출 위험도 커지므로, 알맞은 스코프와 생명주기를 정하는 것이 중요하다.

### 4-1. 쿠키의 스코프(Scope)

쿠키의 스코프는 클라이언트가 어떤 **요청 경로(Path)**나 **도메인(Domain)**에 접근할 때 그 쿠키를 함께 보낼지 정하는 유효 범위다.

**Path(경로)**: 특정 URL 경로와 그 하위 경로 요청에만 쿠키를 보내도록 지정한다. 기본값은 쿠키를 생성한 요청의 경로다.

```java
Cookie cookie = new Cookie("pathCookie", "value");
cookie.setPath("/admin"); // /admin, /admin/users 등 /admin 하위 경로 요청 시에만 쿠키 전송
```

> 원문 바로잡기 — Path 기본값: 정확히는 쿠키를 생성한 요청 경로 **그 자체가 아니라, 그 경로의 상위 디렉터리**다(마지막 `/` 앞까지). 예를 들어 `/admin/settings`에서 만든 쿠키의 기본 Path는 `/admin`이고, `/set-cookie`나 `/theme`처럼 한 단계짜리 주소에서 만든 쿠키는 `/`가 된다. 이 기본값 때문에 예상과 다른 경로에서 쿠키가 안 보일 수 있으니, 사이트 전체에서 쓸 쿠키는 `setPath("/")`로 **직접 지정**하는 것이 안전하다.

**Domain(도메인)**: 쿠키가 전송될 도메인 범위를 지정한다. 도메인을 명시적으로 설정하면 그 도메인의 서브도메인(예: `api.example.com`, `www.example.com`) 사이에서도 쿠키를 공유할 수 있다.

```java
Cookie cookie = new Cookie("domainCookie", "value");
cookie.setDomain("example.com"); // example.com 및 모든 서브도메인에서 쿠키 공유
```

> **추가 설명 — Domain을 지정하지 않으면**: 쿠키를 보낸 **그 호스트에만** 전송된다(host-only 쿠키). `www.example.com`이 Domain 없이 만든 쿠키는 `api.example.com`으로는 가지 않는다. 또 Domain은 **자기 도메인과 그 상위 도메인까지만** 지정할 수 있다. `example.com` 서버가 `naver.com`으로 가는 쿠키를 만들 수는 없다. 브라우저가 이런 쿠키는 무시한다.

### 4-2. 쿠키의 생명주기(Life Cycle)

쿠키는 브라우저 저장소에 보관되는 기간에 따라 **세션 쿠키(Session Cookie)**와 **영속 쿠키(Persistent Cookie)**로 나뉜다. 생명주기는 `setMaxAge()` 메서드로 **초 단위**로 정한다.

| 구분 | 조건 | 저장 위치 | 언제 사라지나 |
|---|---|---|---|
| **세션 쿠키** | 만료 시간(`Max-Age`나 `Expires`)을 지정하지 않음 | 메모리 | 브라우저를 닫을 때 |
| **영속 쿠키** | 만료 시간을 명시적으로 지정 | 하드디스크 등 파일 | 지정한 유효 기간이 지날 때 (브라우저를 닫아도 유지) |

```java
Cookie cookie = new Cookie("rememberMe", "user-id");
cookie.setMaxAge(60 * 60 * 24 * 7); // 7일간 쿠키 유효 (7일 = 60초 * 60분 * 24시간 * 7일)
```

> 원문 바로잡기 — 세션 쿠키가 사라지는 시점: 원문은 "브라우저 **탭이나 창**을 닫으면 자동으로 삭제된다"고 했지만, 탭 하나나 창 하나를 닫는 것으로는 지워지지 않는다. **브라우저 프로세스 전체가 종료**되어야 사라진다. 또 크롬의 "시작할 때 이전 페이지 이어서 열기" 설정이 켜져 있으면 브라우저가 세션 쿠키까지 복원해서, 닫았다 열어도 남아 있을 수 있다.

> **추가 설명 — 세션 쿠키와 서버 세션은 다른 것이다**: 이름이 비슷하지만, 여기서 말하는 "세션 쿠키"는 **브라우저 세션(브라우저가 열려 있는 동안)**만 사는 쿠키라는 뜻이다. 다음 자료에서 다룰 **서버 세션**(서버에 사용자 정보를 저장하는 방식)과는 다른 개념이다. 다만 서버 세션의 ID를 담는 `JSESSIONID` 쿠키가 보통 세션 쿠키로 발급되기 때문에 둘이 자주 함께 등장한다.

> **추가 설명 — Expires와 Max-Age**: `Expires`는 "이 날짜·시각까지"라는 **절대 시각**, `Max-Age`는 "지금부터 몇 초"라는 **상대 시간**이다. 둘 다 있으면 `Max-Age`가 우선한다. 서블릿의 `setMaxAge()`를 쓰면 톰캣이 두 헤더를 함께 만들어 준다(강의 화면의 `Expires=...; Max-Age=3600`이 그 결과다).

### 4-3. 쿠키 삭제 방법

서버에서 클라이언트에 저장된 쿠키를 바로 삭제하려면, 삭제할 쿠키와 **같은 이름, 같은 Path, 같은 Domain**을 가진 쿠키를 만든 뒤 **만료 시간(Max-Age)을 0**으로 설정해 응답으로 보낸다.

```java
Cookie cookie = new Cookie("bgColor", null); // 삭제할 쿠키 이름 지정
cookie.setMaxAge(0); // 만료 시간을 0으로 설정하여 즉시 삭제
cookie.setPath("/"); // 기존 쿠키와 동일한 Path 지정

response.addCookie(cookie);
```

브라우저는 Max-Age가 0인 쿠키 응답을 받으면, 기존에 저장해 둔 같은 이름의 쿠키를 즉시 파기한다.

> **추가 설명 — Path가 다르면 지워지지 않는다**: 브라우저는 쿠키를 **이름 + Path + Domain**의 조합으로 구분한다. 그래서 `/admin` 경로로 만든 쿠키를 지우면서 `setPath("/")`로 보내면, 브라우저는 "다른 쿠키"로 보고 원래 쿠키를 그대로 둔다. 삭제가 안 될 때는 Application 탭에서 원래 쿠키의 Path와 Domain을 먼저 확인한다. 서버는 브라우저에 있는 쿠키를 직접 지울 수 없고, 이렇게 **"만료된 같은 쿠키로 덮어쓰라"고 요청**하는 방식만 가능하다.

## 5. 쿠키의 보안 옵션

쿠키는 클라이언트(브라우저) 쪽에 저장되고 매 요청마다 HTTP 헤더로 전송되기 때문에 보안상 매우 취약한 구조를 가진다. 악의적인 사용자가 쿠키 값을 직접 조작하거나, XSS(Cross-Site Scripting)·CSRF(Cross-Site Request Forgery) 같은 공격으로 쿠키 안의 민감한 정보를 탈취할 위험이 있다.

> 원문 바로잡기 — CSRF는 쿠키를 훔치는 공격이 아니다: 쿠키를 **읽어서 빼내는** 것은 XSS의 위험이다. CSRF는 쿠키를 훔치지 않고, 브라우저가 쿠키를 **자동으로 실어 보낸다는 점을 악용**해서 사용자 모르게 요청을 보내게 하는 공격이다. 공격자는 쿠키 값을 끝까지 모르지만, 요청은 사용자의 쿠키와 함께 서버에 도착한다. 그래서 막는 옵션도 다르다. XSS 탈취는 `HttpOnly`, CSRF는 `SameSite`가 맡는다.

스프링을 비롯한 웹 생태계는 이런 보안 위협을 줄이기 위해, 쿠키를 만들 때 쓸 수 있는 주요 보안 옵션들을 제공한다.

### 5-1. HttpOnly 속성

`HttpOnly` 속성은 자바스크립트의 `document.cookie`를 통한 쿠키 접근을 **차단**하는 옵션이다.

- **보안 목적**: 해커가 웹 사이트에 악성 자바스크립트를 삽입해 실행시키는 **XSS 공격에 성공하더라도**, 브라우저가 자바스크립트의 쿠키 접근을 금지하므로 민감한 쿠키 정보의 탈취를 막을 수 있다.
- **사용 방법**:

```java
Cookie cookie = new Cookie("secretToken", "xyz123");
cookie.setHttpOnly(true); // HttpOnly 설정
```

> **추가 설명 — 직접 확인해 보기**: 개발자 도구 Console 탭에서 `document.cookie`를 입력하면 지금 페이지의 쿠키가 문자열로 나온다. `HttpOnly`를 켠 쿠키는 이 목록에서 빠진다. 단, Application 탭에는 그대로 보이고 서버로도 정상 전송된다. 막히는 것은 **스크립트의 접근뿐**이다. 톰캣이 발급하는 `JSESSIONID`는 기본으로 `HttpOnly`가 켜져 있다.

### 5-2. Secure 속성

`Secure` 속성은 암호화된 통신 채널인 **HTTPS** 프로토콜을 쓸 때만 브라우저가 쿠키를 서버로 보내도록 제한하는 옵션이다.

- **보안 목적**: HTTP 평문 통신 과정에서 일어날 수 있는 네트워크 패킷 감청(Sniffing) 공격으로부터 쿠키 데이터가 노출되는 것을 막는다.
- **사용 방법**:

```java
Cookie cookie = new Cookie("secureToken", "abc987");
cookie.setSecure(true); // Secure 설정
```

> **추가 설명 — localhost에서는**: 원칙대로라면 `http://localhost:8080`은 HTTPS가 아니므로 `Secure` 쿠키가 전송되지 않아야 한다. 하지만 크롬·파이어폭스 같은 최신 브라우저는 개발 편의를 위해 **`localhost`를 예외로** 취급해서 HTTP에서도 `Secure` 쿠키를 주고받는다. 실제 서버(도메인)에 배포하면 HTTPS가 아닌 한 전송되지 않는다.

### 5-3. SameSite 속성

`SameSite` 속성은 서로 다른 사이트 사이(Cross-Site)의 요청에서 쿠키를 보낼지 말지 제어하는 옵션이다.

- **보안 목적**: 사용자가 모르는 사이에 제3의 악성 사이트에서 본래 사이트로 위조된 요청을 보내도록 유도하는 **CSRF 공격**을 막는 데 효과적이다.
- **속성 값 종류**:

| 값 | 동작 |
|---|---|
| `Strict` | 같은 사이트의 요청에서만 쿠키를 보낸다. 다른 사이트에서 링크를 클릭해 이동할 때도 쿠키가 전송되지 않으므로 가장 엄격하지만, 사용자 경험이 떨어질 수 있다 |
| `Lax` | 기본적으로 `Strict`와 비슷하지만, 다른 사이트에서 이동하는 안전한 요청(예: 일반 `<a>` 링크를 통한 GET 요청)에는 쿠키 전송을 허용한다 (최근 주요 브라우저의 기본값) |
| `None` | 사이트가 다른 모든 요청에도 쿠키를 보낸다. 이 값을 쓸 때는 반드시 `Secure` 속성이 `true`여야 한다 |

> **추가 설명 — Strict가 불편한 이유**: 메일에 온 쇼핑몰 링크를 눌렀다고 하자. `Strict`라면 다른 사이트(메일)에서 넘어온 요청이므로 로그인 쿠키가 실리지 않아, 분명 로그인해 둔 사이트인데 **로그인이 풀린 것처럼** 보인다. `Lax`는 이런 링크 이동(GET)에는 쿠키를 보내고, 다른 사이트에서 몰래 보내는 POST(CSRF의 전형적인 모양)에는 보내지 않는다. 그래서 대부분 `Lax`를 쓴다.

> **추가 설명 — "도메인"이 아니라 "사이트"**: SameSite의 기준은 정확한 도메인이 아니라 **사이트**(등록 가능한 도메인, 예: `example.com`)다. `www.example.com`과 `api.example.com`은 도메인은 다르지만 같은 사이트로 본다. 또 "주요 브라우저의 기본값이 Lax"라는 것은 크롬 계열 기준이다. SameSite를 지정하지 않은 쿠키를 크롬은 `Lax`로 취급하지만, 모든 브라우저가 똑같지는 않으므로 **명시적으로 지정**하는 것이 안전하다.

- **사용 방법(`ResponseCookie` 활용)**: 서블릿의 기본 `Cookie` 객체는 `SameSite` 메서드를 직접 제공하지 않는 경우가 많아서, 스프링 5 이상에서는 `ResponseCookie` 클래스를 활용하는 방식을 권장한다.

```java
ResponseCookie cookie = ResponseCookie.from("sessionId", "session-5678")
        .path("/")
        .httpOnly(true)
        .secure(true)
        .sameSite("Lax") // SameSite 설정
        .maxAge(60 * 60)
        .build();

response.addHeader(HttpHeaders.SET_COOKIE, cookie.toString());
```

> **추가 설명 — ResponseCookie 코드 읽기**: `ResponseCookie`는 쿠키 객체가 아니라 **`Set-Cookie` 헤더 문자열을 만들어 주는 도구**다. `cookie.toString()`의 결과가 `sessionId=session-5678; Path=/; Max-Age=3600; Expires=...; Secure; HttpOnly; SameSite=Lax` 같은 헤더 값이 되고, 그것을 `addHeader()`로 응답에 직접 붙인다. 그래서 `addCookie()`가 아니라 `addHeader()`를 쓴다. 메서드를 이어 붙이는 빌더 방식이라 옵션을 한눈에 보기 좋다.

> **추가 설명 — 서블릿 Cookie로도 가능해졌다**: 스프링 부트 3(자카르타 서블릿 6.0)부터는 `Cookie`에 `setAttribute()`가 생겨서 `cookie.setAttribute("SameSite", "Lax")`로도 지정할 수 있다. 또 `JSESSIONID` 같은 세션 쿠키의 옵션은 코드 대신 `application.yml`의 `server.servlet.session.cookie.same-site`, `http-only`, `secure` 설정으로 정한다.

## 6. 마무리

이번 자료에서는 클라이언트를 식별하고 상태를 유지하기 위한 핵심 장치인 **쿠키(Cookie)**의 개념과 활용법, 그리고 주요 보안 옵션을 알아보았다.

쿠키를 활용하면 **무상태(Stateless)**인 HTTP 환경에서도 사용자를 식별하고, 간단한 설정이나 상태 값을 유지할 수 있다. 하지만 쿠키는 기본적으로 클라이언트 브라우저로 보내져 저장되는 데이터이므로, **변조와 탈취 위험에 항상 노출**되어 있다. 그래서 쿠키에는 사용자 인증 정보나 개인정보 같은 **민감한 데이터를 직접 저장하는 것을 피해야** 한다.

이런 쿠키의 보안적 한계를 극복하고 민감한 정보를 안전하게 다루기 위해 등장한 개념이 바로 **세션(Session)**이다.

> **추가 설명 — 쿠키 옵션 한눈에 보기**
>
> | 옵션 | 정하는 것 | 서블릿 `Cookie` | `ResponseCookie` |
> |---|---|---|---|
> | Path | 어느 경로로 보낼지 | `setPath("/")` | `.path("/")` |
> | Domain | 어느 도메인으로 보낼지 | `setDomain(...)` | `.domain(...)` |
> | Max-Age | 언제까지 살아 있을지 (0이면 삭제) | `setMaxAge(초)` | `.maxAge(초)` |
> | HttpOnly | 스크립트 접근 차단 (XSS 대비) | `setHttpOnly(true)` | `.httpOnly(true)` |
> | Secure | HTTPS에서만 전송 (감청 대비) | `setSecure(true)` | `.secure(true)` |
> | SameSite | 다른 사이트 요청에 보낼지 (CSRF 대비) | `setAttribute("SameSite", ...)` (서블릿 6.0+) | `.sameSite("Lax")` |
>
> 쿠키 값 자체를 사용자가 **얼마든지 고칠 수 있다**는 점도 기억해야 한다. 개발자 도구에서 `clientId=user-12345`를 `user-99999`로 바꾸면 서버는 그대로 믿는다. 쿠키에 "누구인지"를 직접 적는 대신, 서버가 정보를 갖고 **추측할 수 없는 ID만** 쿠키로 주는 것이 세션 방식이다.
