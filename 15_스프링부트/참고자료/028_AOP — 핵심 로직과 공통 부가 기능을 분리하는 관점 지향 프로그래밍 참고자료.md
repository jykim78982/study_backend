# AOP — 핵심 로직과 공통 부가 기능을 분리하는 관점 지향 프로그래밍

**AOP**(Aspect-Oriented Programming, 관점 지향 프로그래밍)는 애플리케이션의 **핵심 로직**과 여러 곳에서 **공통으로 반복되는 부가 기능**을 분리해서 따로 모듈로 만드는 프로그래밍 방식이다.

AOP는 객체지향 프로그래밍(OOP)을 **대체하는 것이 아니라**, OOP만으로는 깔끔하게 없애기 어려운 중복 코드를 해결해주는 **보완재**다. 스프링의 `@Transactional`이 바로 AOP로 만들어진 기능이다.

## 0. 한 문장 비유로 먼저 이해하기

식당 주방장(핵심 로직)은 요리만 해야 한다. 그런데 매 요리마다 "손 씻기 → 요리 → 위생 기록 남기기 → 조리 시간 기록"을 주방장이 직접 하면 요리보다 잡무가 더 많아진다.

그래서 주방 입구에 **보조 직원(프록시)**을 둔다. 주문이 들어오면 보조 직원이 먼저 받아서 손 씻기와 시간 기록을 챙기고, 요리 자체는 주방장에게 넘긴다. 요리가 끝나면 보조 직원이 위생 기록을 남긴다. 주방장은 보조 직원이 있는 줄도 모르고 **요리에만 집중**한다.

- **주방장** = 핵심 로직(Target)
- **손 씻기, 시간 기록, 위생 기록** = 공통 부가 기능(Advice)
- **어떤 요리에 이 절차를 적용할지 정한 규칙** = Pointcut
- **보조 직원** = 프록시(Proxy)

AOP는 이 "보조 직원"을 스프링이 자동으로 만들어 세워주는 기술이다.

## 1. AOP가 탄생한 이유 (문제 상황)

웹 애플리케이션을 만들다 보면 회원 가입, 주문 처리, 게시글 등록처럼 **서로 다른 로직**에서 **똑같은 코드**를 반복해서 실행해야 하는 경우가 생긴다.

- **횡단 관심사 (Cross-cutting Concerns)**: 시스템 전반에 걸쳐 공통으로 적용되는 부가 기능. 예) 로깅, 트랜잭션 처리, 보안·권한 검사, 실행 시간 측정, 캐싱
- **핵심 관심사 (Core Concerns)**: 각 클래스가 수행해야 하는 고유한 비즈니스 로직. 예) 회원 가입 처리, 결제 로직

"횡단"이라는 이름은 아래 그림처럼 부가 기능이 여러 서비스를 **가로로 관통**하기 때문에 붙었다.

```
                 MemberService   OrderService   MenuService
                 ┌───────────┐  ┌───────────┐  ┌───────────┐
  로깅        ───┼───────────┼──┼───────────┼──┼───────────┼──▶
  트랜잭션    ───┼───────────┼──┼───────────┼──┼───────────┼──▶   ← 횡단 관심사 (가로)
  실행시간측정 ───┼───────────┼──┼───────────┼──┼───────────┼──▶
                 │ 회원 가입  │  │ 주문 생성  │  │ 메뉴 등록  │   ← 핵심 관심사 (세로)
                 └───────────┘  └───────────┘  └───────────┘
```

OOP는 기능을 **세로(클래스 단위)**로 잘 나누지만, 이렇게 **가로로 걸친 기능**은 클래스 하나로 묶기 어렵다. AOP는 이 가로 방향 기능을 따로 떼어내는 방법이다.

### AOP를 사용하지 않을 때의 문제점

```java
// AOP 적용 전: 핵심 로직과 부가 기능이 섞여 있음
public void createOrder(OrderRequest request) {
    long startTime = System.currentTimeMillis();   // [부가 기능] 실행 시간 측정 시작
    log.info("주문 생성 시작");                      // [부가 기능] 로깅

    try {
        // [핵심 로직] 실제 주문 생성 및 저장
        orderRepository.save(request.toEntity());
    } catch (Exception e) {
        log.error("주문 생성 에러 발생", e);          // [부가 기능] 예외 로깅
        throw e;
    }

    long executionTime = System.currentTimeMillis() - startTime; // [부가 기능] 실행 시간 계산
    log.info("주문 생성 완료 (소요시간: {}ms)", executionTime);
}
```

핵심 로직은 `orderRepository.save(...)` **한 줄**인데, 나머지가 전부 부가 기능이다.

- **코드 중복**: 모든 서비스 메서드마다 실행 시간 측정, 로깅, 트랜잭션 시작·종료 코드를 복사-붙여넣기 해야 한다.
- **가독성 저하**: 비즈니스 로직보다 부가 기능 코드가 더 길어져, 이 메서드가 **원래 무엇을 하는지** 파악하기 어렵다.
- **유지보수 저하**: 로그 형식을 바꾸려면 이 코드가 들어간 **모든 파일**을 일일이 고쳐야 한다. 한 곳이라도 빠뜨리면 일관성이 깨진다.
- **실수 가능성**: 새 메서드를 만들 때 부가 기능을 깜빡 빼먹어도 아무도 모른다.

> **OOP로는 왜 안 될까?** 공통 코드를 부모 클래스로 올리거나(상속), 별도 클래스의 메서드로 빼서 호출(위임)할 수는 있다. 하지만 그래도 각 메서드 안에 "시작할 때 이거 호출, 끝날 때 저거 호출"이라는 코드는 **여전히 남는다.** 또 자바는 단일 상속이라 공통 부모를 여러 개 둘 수도 없다. 호출 코드 자체를 없애려면, 메서드 **바깥**에서 앞뒤를 감싸는 방법이 필요하다. 그게 AOP다.

## 2. AOP를 적용했을 때의 변화

AOP를 적용하면 공통 부가 기능(Aspect)을 **딱 한 곳**에 작성해두고, 원하는 지점에 **투명하게**(대상 코드가 모르게) 적용시킨다.

```java
// AOP 적용 후: 순수 비즈니스 로직만 남음
public void createOrder(OrderRequest request) {
    // [핵심 로직] 실제 주문 생성 및 저장
    orderRepository.save(request.toEntity());
}
```

- 핵심 로직이 매우 명확해진다.
- 부가 기능을 수정할 때 **AOP 클래스 하나만** 바꾸면 애플리케이션 전체에 일괄 적용된다.
- 새 서비스 메서드를 만들어도 규칙(Pointcut)에 해당하면 **자동으로** 부가 기능이 붙는다.

이미 우리는 AOP를 쓰고 있다. 서비스 메서드에 `@Transactional` 한 줄만 붙이면 트랜잭션 시작·커밋·롤백 코드 없이도 트랜잭션이 처리되는 것이 바로 이 원리다.

## 3. AOP 핵심 용어 정리

| 용어 | 의미 | 쉽게 비유하자면 |
|---|---|---|
| **Aspect** (관점) | 공통 부가 기능을 모듈화한 단위. **Advice + Pointcut**을 묶은 것 | "공통 기능 묶음" (예: `ExecutionTimeAspect`) |
| **Advice** (부가 기능) | 실제로 실행될 부가 기능 코드 그 자체, 그리고 **언제** 실행할지 | "무엇을, 언제 할 것인가?" (예: 메서드 앞뒤로 시간을 잰다) |
| **Target** (대상) | Advice가 적용될 대상 객체 | "누구에게 적용되는가?" (예: `OrderService`) |
| **Join Point** (연결점) | Advice를 끼워 넣을 수 있는 **후보 지점** | "적용 가능한 후보 지점들" |
| **Pointcut** (지점 선별) | Join Point 중에서 실제로 Advice를 적용할 지점을 **골라내는 표현식** | "정확히 어느 메서드에 적용할 것인가?" |
| **Weaving** (위빙) | Advice를 Target에 실제로 **엮어 넣는** 과정 | 보조 직원을 주방 입구에 배치하는 일 |
| **Proxy** (프록시) | Weaving 결과로 만들어진, Target을 감싼 대리 객체 | 보조 직원 |

**Join Point와 Pointcut의 관계**: Join Point는 "꽂을 수 있는 콘센트 전부", Pointcut은 "그중 이번에 플러그를 꽂을 콘센트를 고르는 규칙"이다.

> **보충 — 스프링 AOP의 Join Point는 "메서드 실행"뿐이다**: 원본 자료는 Join Point를 "메서드 호출, 객체 생성 등 모든 실행 지점"이라고 설명한다. 이는 AOP 일반 개념(그리고 AspectJ라는 전문 AOP 도구)에서의 정의다. **스프링 AOP는 프록시 방식이라 "스프링 빈의 메서드 실행"만 Join Point로 지원한다.** 생성자 호출, 필드 접근, `static` 메서드에는 적용할 수 없다. 웹 백엔드에서 필요한 대부분의 부가 기능은 메서드 단위로 충분하다.

> Advice를 "조언"으로 직역하는 경우가 많은데, 의미상 "**대상에 덧붙이는 부가 기능**"으로 이해하는 것이 쉽다.

## 4. Advice의 5가지 동작 시점

Advice는 **핵심 로직(타깃 메서드)이 실행되는 시점**을 기준으로 다섯 가지로 나뉜다.

```
            @Before
               │
               ▼
     ┌───── 타깃 메서드 실행 ─────┐
     │                            │
  정상 종료                    예외 발생
     │                            │
@AfterReturning             @AfterThrowing
     │                            │
     └────────── @After ──────────┘   (둘 중 어느 쪽이든 항상 실행)

@Around: 위 전체를 바깥에서 감싼다
```

| Advice | 실행 시점 | 할 수 있는 것 | 사용 예 |
|---|---|---|---|
| `@Before` | 타깃 메서드 실행 **전** | 파라미터 확인, 예외를 던져 실행을 막기 | 권한 검사, 입력 로그 |
| `@AfterReturning` | 타깃 메서드가 **정상 종료**된 후 | 반환값 읽기 | 결과 로그 |
| `@AfterThrowing` | 타깃 메서드 수행 중 **예외 발생** 시 | 예외 정보 읽기 | 에러 로그, 알림 |
| `@After` | 정상·예외 상관없이 **무조건** 완료 후 | `finally` 블록과 같음 | 리소스 정리 |
| `@Around` | 실행 **전후 전체**를 감싼다 | 실행 여부 결정, 파라미터·반환값 변경, 예외 처리 | 실행 시간 측정, 트랜잭션, 캐시 |

> **@Around가 가장 강력하지만, 꼭 필요할 때만 쓴다**: `@Around`는 나머지 네 가지를 모두 흉내 낼 수 있다. 대신 `joinPoint.proceed()`를 **직접 호출해야 타깃 메서드가 실행**되고, 그 반환값을 **직접 return해야** 호출한 쪽이 결과를 받는다. 깜빡하면 타깃 메서드가 아예 실행되지 않거나 결과가 `null`이 되는 버그가 생긴다. 실행 전에 로그만 남기면 된다면 `@Before`처럼 **필요한 만큼만 강력한 것**을 고르는 것이 안전하다.

```java
@Before("execution(* com.newcafe.backend.service..*(..))")
public void logBefore(JoinPoint joinPoint) {
    log.info("호출: {} 인자: {}", joinPoint.getSignature().toShortString(),
             Arrays.toString(joinPoint.getArgs()));
}

@AfterReturning(pointcut = "execution(* com.newcafe.backend.service..*(..))", returning = "result")
public void logReturn(JoinPoint joinPoint, Object result) {
    log.info("반환: {} → {}", joinPoint.getSignature().toShortString(), result);
}

@AfterThrowing(pointcut = "execution(* com.newcafe.backend.service..*(..))", throwing = "ex")
public void logException(JoinPoint joinPoint, Exception ex) {
    log.error("예외: {} → {}", joinPoint.getSignature().toShortString(), ex.getMessage());
}
```

`JoinPoint`로는 지금 실행되는 메서드의 정보(이름, 인자, 대상 객체)를 얻을 수 있다. `@Around`만 실행을 직접 제어해야 하므로 그 하위 타입인 `ProceedingJoinPoint`(`proceed()` 메서드가 있음)를 받는다.

## 5. Spring AOP 실전 구현 예시

모든 서비스 메서드의 실행 시간을 자동으로 측정해 출력하는 Aspect다.

**1) 의존성 추가** (Spring Boot 3 기준, `build.gradle.kts`)

```kotlin
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-aop")
}
```

> `@Transactional`은 이 의존성 없이도 동작한다. 트랜잭션 기능은 스프링 내부의 AOP 기반 기능을 직접 쓰기 때문이다. `@Aspect`로 **우리가 직접 Aspect를 만들 때** 이 의존성이 필요하다. (Spring Boot 4부터는 이름이 `spring-boot-starter-aspectj`로 바뀌었다.)

**2) Aspect 작성**

```java
@Slf4j
@Aspect       // 이 클래스는 Aspect(Advice + Pointcut 묶음)다
@Component    // 스프링 빈으로 등록해야 스프링이 찾아서 적용한다
public class ExecutionTimeAspect {

    // Pointcut: com.newcafe.backend.service 패키지와 그 하위의 모든 클래스, 모든 메서드
    @Around("execution(* com.newcafe.backend.service..*.*(..))")
    public Object logExecutionTime(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.nanoTime();
        try {
            return joinPoint.proceed();          // 실제 타깃 메서드 실행 + 결과 반환
        } finally {
            long ms = (System.nanoTime() - start) / 1_000_000;
            log.info("{} 실행 시간: {}ms", joinPoint.getSignature().toShortString(), ms);
        }
    }
}
```

원본 예시에서 바꾼 점:

- **`try-finally`**: 원본은 `proceed()` 다음 줄에서 시간을 계산하므로, 타깃 메서드가 **예외를 던지면 시간 로그가 남지 않는다.** `finally`에 두면 성공·실패 모두 기록된다.
- **`System.nanoTime()`**: 경과 시간을 잴 때는 `currentTimeMillis()`(현재 시각, 시스템 시계 조정에 영향을 받음)보다 `nanoTime()`(경과 시간 측정용)이 정확하다.
- **`System.out.println` → `log`**: 실무에서는 로거를 써야 로그 레벨 조절, 파일 저장이 가능하다.

**3) 결과**: 서비스 코드는 한 줄도 바꾸지 않았는데, 서비스 메서드가 호출될 때마다 이런 로그가 찍힌다.

```
MenuService.getMenus() 실행 시간: 12ms
OrderService.createOrder(..) 실행 시간: 37ms
```

## 6. Pointcut 표현식 읽는 법

### 6-1. execution — 메서드 모양으로 고르기

```
execution(  *        com.newcafe.backend.service..*  .  *   (..)  )
           반환타입    패키지.클래스                    메서드  파라미터
```

| 조각 | 뜻 |
|---|---|
| `*` (반환 타입) | 반환 타입 상관없음 |
| `com.newcafe.backend.service..` | 이 패키지와 **하위 패키지 전부** (`..`이 하위 포함) |
| `*` (클래스) | 모든 클래스 |
| `.*` (메서드) | 모든 메서드 |
| `(..)` | 파라미터 개수·타입 상관없음 |

| 예시 | 대상 |
|---|---|
| `execution(* com.newcafe.backend.service.MenuService.*(..))` | `MenuService`의 모든 메서드 |
| `execution(* com.newcafe.backend.service..*.find*(..))` | 서비스 패키지에서 이름이 `find`로 시작하는 메서드 |
| `execution(public * *(..))` | 모든 public 메서드 |
| `execution(* *(Long))` | 파라미터가 `Long` 하나인 메서드 |

### 6-2. 그 밖의 지정자

| 지정자 | 고르는 기준 | 예 |
|---|---|---|
| `within(...)` | 특정 패키지·클래스 안의 모든 메서드 | `within(com.newcafe.backend.service..*)` |
| `@annotation(...)` | 특정 어노테이션이 붙은 메서드 | `@annotation(com.newcafe.backend.aop.LogTime)` |
| `@within(...)` | 특정 어노테이션이 붙은 클래스의 메서드 | `@within(org.springframework.stereotype.Service)` |
| `bean(...)` | 스프링 빈 이름 | `bean(*Service)` |

`&&`, `||`, `!`로 조합할 수 있다. 예) `within(com.newcafe.backend.service..*) && !execution(* *.get*(..))`

### 6-3. 어노테이션으로 "붙인 곳에만" 적용하기 (실무에서 많이 씀)

패키지 전체에 적용하는 대신, **직접 만든 어노테이션을 붙인 메서드에만** 적용하면 의도가 코드에 드러나서 읽기 쉽다. `@Transactional`도 이 방식이다.

```java
// 1. 표시용 어노테이션 만들기
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)       // 실행 중에도 어노테이션 정보가 남아 있어야 AOP가 읽을 수 있다
public @interface LogTime {}

// 2. Aspect: @LogTime이 붙은 메서드에만 적용
@Around("@annotation(com.newcafe.backend.aop.LogTime)")
public Object logTime(ProceedingJoinPoint joinPoint) throws Throwable { ... }

// 3. 원하는 메서드에 붙이기
@LogTime
public List<MenuResponse> getMenus() { ... }
```

### 6-4. Pointcut 재사용 — @Pointcut

같은 표현식을 여러 Advice에서 쓴다면 이름을 붙여 재사용한다.

```java
@Aspect
@Component
public class LoggingAspect {

    @Pointcut("execution(* com.newcafe.backend.service..*(..))")
    private void serviceLayer() {}                     // 몸체는 비워둔다. 이름표 역할

    @Before("serviceLayer()")
    public void before(JoinPoint jp) { ... }

    @AfterThrowing(pointcut = "serviceLayer()", throwing = "ex")
    public void onError(JoinPoint jp, Exception ex) { ... }
}
```

## 7. Spring AOP의 동작 원리 — 프록시 패턴

스프링은 AOP를 구현할 때 **프록시**(Proxy, 대리 객체)를 사용한다.

```
[클라이언트(컨트롤러)] ──> [Spring AOP 프록시] ──> [실제 타깃 객체(진짜 서비스)]
                               │
                               ├─ 1. 공통 부가 기능 실행 (Advice)
                               └─ 2. 진짜 객체의 핵심 로직 호출 (proceed)
```

1. 애플리케이션이 시작될 때, 스프링은 빈을 만들면서 "이 빈에 적용할 Aspect가 있나?"를 Pointcut으로 검사한다.
2. 적용 대상이면 진짜 객체를 감싼 **프록시 객체를 만들어, 진짜 객체 대신 컨테이너에 등록**한다.
3. 컨트롤러가 서비스를 주입받으면 실제로는 **프록시**를 받는다. 컨트롤러는 그 사실을 모른다.
4. 컨트롤러가 메서드를 호출하면 프록시가 먼저 받아 부가 기능을 실행하고, 진짜 객체의 메서드를 호출한다.

**직접 만든 프록시로 이해하기**: 스프링이 해주는 일을 손으로 흉내 내면 이렇다.

```java
// 진짜 서비스
public class OrderService {
    public void createOrder(OrderRequest req) { orderRepository.save(req.toEntity()); }
}

// 손으로 만든 프록시: 진짜 서비스를 상속하고, 앞뒤에 부가 기능을 끼운다
public class OrderServiceProxy extends OrderService {
    private final OrderService target;
    public OrderServiceProxy(OrderService target) { this.target = target; }

    @Override
    public void createOrder(OrderRequest req) {
        long start = System.nanoTime();           // Advice
        try {
            target.createOrder(req);              // 진짜 로직 호출 (= proceed)
        } finally {
            log.info("{}ms", (System.nanoTime() - start) / 1_000_000);  // Advice
        }
    }
}
```

이런 클래스를 서비스마다, 메서드마다 직접 만들 수는 없으니, 스프링이 **실행 중에 자동으로** 만들어준다(**런타임 위빙**). 컨테이너가 객체 생성을 대신 맡고 있기 때문에(IoC), 진짜 객체 대신 프록시를 슬쩍 끼워 넣을 수 있는 것이다.

**프록시를 만드는 두 가지 방법**

| 방식 | 원리 | 조건 |
|---|---|---|
| **JDK 동적 프록시** | 타깃과 **같은 인터페이스**를 구현한 프록시를 만든다 | 타깃이 인터페이스를 구현해야 함 |
| **CGLIB** | 타깃 **클래스를 상속**한 프록시를 만든다 | 인터페이스 없어도 됨. 대신 `final` 클래스·메서드는 불가 |

스프링 부트는 기본적으로 **CGLIB**를 사용한다(인터페이스가 있어도). 인터페이스 없이 클래스만 있는 서비스에도 AOP를 적용할 수 있게 하려는 것이다. 디버거로 주입받은 서비스 객체를 보면 클래스 이름이 `OrderService$$SpringCGLIB$$0`처럼 찍히는데, 이게 프록시다.

> 참고로 Spring Data JPA의 리포지토리 구현체는 **JDK 동적 프록시**로 만들어진다. 리포지토리는 인터페이스(`MenuRepository`)만 있고 구현 클래스가 아예 없기 때문이다. 프록시라는 같은 기술이 스프링 곳곳에서 쓰인다.

## 8. 프록시 방식이라서 생기는 주의점

프록시는 **바깥에서 들어오는 호출만** 가로챌 수 있다. 이것만 기억하면 아래 주의점이 모두 이해된다.

| 주의점 | 이유 |
|---|---|
| **같은 클래스 내부 호출에는 적용되지 않는다** | `this.methodB()`는 프록시를 거치지 않고 진짜 객체 안에서 바로 호출된다 |
| **`final` 클래스·메서드에는 적용되지 않는다** | CGLIB는 상속으로 프록시를 만드는데 `final`은 상속·재정의할 수 없다 |
| **`private` 메서드에는 적용되지 않는다** | 바깥에서 호출할 수 없으니 프록시가 가로챌 수도 없다 |
| **스프링 빈이 아니면 적용되지 않는다** | `new OrderService()`로 직접 만든 객체는 컨테이너를 거치지 않아 프록시가 없다 |
| **`static` 메서드에는 적용되지 않는다** | 객체가 아니라 클래스에 속하므로 프록시로 감쌀 수 없다 |

**내부 호출 문제 예시** — `@Transactional`에서 가장 흔한 실수다.

```java
@Service
public class OrderService {

    public void placeOrder(OrderRequest req) {
        // ... 검증 ...
        this.saveOrder(req);          // ❌ 프록시를 거치지 않음 → @Transactional 적용 안 됨
    }

    @Transactional
    public void saveOrder(OrderRequest req) { ... }
}
```

```
컨트롤러 ──> [프록시] ──> placeOrder() ──this.──> saveOrder()
               ↑                                   ↑
         여기서만 AOP 적용                  프록시를 안 거침 → 트랜잭션 없음
```

해결 방법은 트랜잭션이 필요한 메서드를 **바깥에서 호출되는 메서드**(`placeOrder`)에 붙이거나, `saveOrder`를 **다른 빈으로 분리**해 주입받아 호출하는 것이다.

## 9. 여러 Aspect의 실행 순서

한 메서드에 Aspect가 여러 개 걸리면(예: 실행 시간 측정 + 트랜잭션 + 로깅) 순서가 정해져 있지 않을 수 있다. 순서가 중요하면 `@Order`로 지정한다. **숫자가 작을수록 바깥쪽**(먼저 시작해서 나중에 끝남)이다.

```java
@Aspect @Component @Order(1)
public class ExecutionTimeAspect { ... }   // 가장 바깥: 트랜잭션 시간까지 포함해서 잰다

@Aspect @Component @Order(2)
public class LoggingAspect { ... }
```

```
ExecutionTimeAspect 시작 → LoggingAspect 시작 → 타깃 메서드 → LoggingAspect 끝 → ExecutionTimeAspect 끝
```

## 10. 스프링이 AOP로 제공하는 기능들

직접 Aspect를 만들 일은 생각보다 적다. 스프링이 자주 쓰는 횡단 관심사를 이미 AOP로 만들어 어노테이션으로 제공하기 때문이다.

| 어노테이션 | 부가 기능 | 프록시가 하는 일 |
|---|---|---|
| `@Transactional` | 트랜잭션 | 메서드 시작 전 트랜잭션 시작, 정상 종료 시 커밋, 런타임 예외 시 롤백 |
| `@Cacheable` | 캐싱 | 같은 인자로 다시 호출되면 메서드를 실행하지 않고 저장된 결과 반환 |
| `@Async` | 비동기 실행 | 메서드를 다른 스레드에서 실행하고 바로 반환 |
| `@PreAuthorize` | 권한 검사 (Spring Security) | 실행 전 권한이 없으면 예외 |
| `@Retryable` | 재시도 (Spring Retry) | 예외가 나면 정해진 횟수만큼 다시 실행 |

`@Transactional`의 프록시를 의사 코드로 쓰면 이렇다.

```java
// 스프링이 만드는 트랜잭션 프록시의 개념 코드
public void transfer(...) {
    TransactionStatus tx = transactionManager.getTransaction(...);  // 커넥션 얻고 자동 커밋 끄기
    try {
        target.transfer(...);                 // 진짜 서비스 로직
        transactionManager.commit(tx);
    } catch (RuntimeException | Error e) {
        transactionManager.rollback(tx);
        throw e;
    }
}
```

트랜잭션 처리에서 "계층을 나누면 커넥션 관리와 커밋 코드가 흩어진다"던 문제를, 스프링은 이렇게 **부가 기능을 프록시로 떼어내는 AOP**로 해결했다.

## 11. 한 줄 정리

- **AOP**: 여러 곳에 반복되는 부가 기능(횡단 관심사)을 핵심 로직에서 떼어내 한 곳에 모으는 방법. OOP의 보완재.
- **Aspect** = **Advice**(무엇을·언제) + **Pointcut**(어디에). Target에 엮어 넣는 과정이 **Weaving**.
- Advice 시점: `@Before`, `@AfterReturning`, `@AfterThrowing`, `@After`, `@Around`(가장 강력, `proceed()` 호출과 반환 필수).
- 스프링 AOP는 **프록시**로 동작한다. 컨테이너가 진짜 객체 대신 프록시를 주입하고, 프록시가 부가 기능을 실행한 뒤 진짜 객체를 호출한다.
- 프록시는 **바깥에서 들어오는 public 메서드 호출**만 가로챈다. 내부 호출, `private`, `final`, 빈이 아닌 객체에는 적용되지 않는다.
- `@Transactional`, `@Cacheable`, `@Async` 같은 스프링 기능이 모두 AOP로 만들어져 있다.
