# 컨트롤러를 이용한 로그인 직접 구현

이번 자료에서는 스프링 보안을 사용하지 않고, 맨땅에서 직접 인증과 인가 기능을 구현해 본다.

## 1. 직접 로그인 구현이 필요한 이유

스프링 보안을 적용하면 로그인 폼 생성, 인증 요청 처리, 세션 관리 등이 내부에서 자동으로 처리된다. 그러나 내부 동작을 모른 채 설정만 사용하면 로그인 실패 처리, 성공 후 리다이렉트, 권한 검증 같은 세부 흐름을 이해하기 어려울 수 있다.

컨트롤러와 서비스로 사용자 입력을 받고 인증을 수행하는 과정을 직접 구현해 보면 다음을 명확히 파악할 수 있다.

- HTTP 요청과 응답의 흐름
- 세션과 쿠키
- 앞으로 **시큐리티 필터가 대신하게 될 로직**이 무엇인지

## 2. 로그인 폼과 인증 처리 구현

이전 자료의 첨부 예제 파일에서 리소스를 확인한다.

```

├─ static/css/site.css
└─ templates
   ├─ admin/
   ├─ index.html
   ├─ login.html
   ├─ menu.html
   └─ signup.html
```

이 내용에서 눈여겨볼 부분은 `form` 태그다.

- `action` 속성은 `/login` 경로를 지정하고,
- 요청 방식은 `POST`이며,
- 각 입력 필드의 `name` 속성(`username`, `password`)이 잘 지정되어 있는지 확인한다.

> **추가 설명 — name이 곧 서버의 변수 이름**: 폼을 제출하면 브라우저는 `name=값` 쌍을 URL 인코딩 방식(`application/x-www-form-urlencoded`)으로 묶어 본문에 담는다. 위 폼이라면 `username=newlec%40newlecture.com&password=1234`처럼 간다(`@`는 `%40`으로 인코딩된다). 서버의 `@RequestParam("username")`은 이 **`name` 값**과 맞아야 한다. `id`(`email`)는 `label`과 연결하는 용도일 뿐 서버로 가지 않는다.

> **추가 설명 — 데모 계정 안내와 실제 코드가 다르다**: 폼 아래의 데모 계정(`admin / admin123`, `customer / user123`)은 아래 서비스 코드와 맞지 않는다. 서비스는 `newlec@newlecture.com / 1234`만 통과시킨다. 게다가 입력란이 `type="email"`이라서 `admin`처럼 `@`가 없는 값은 브라우저가 **제출 자체를 막는다.** 이 실습에서는 `newlec@newlecture.com / 1234`로 테스트한다.

이제 인증을 처리하는 서버 코드를 작성한다.

### 2-1. AuthController 구현하기

사용자가 로그인 페이지에서 username과 password를 입력하고 로그인 버튼을 누르면 서버에 POST 요청이 전달된다. 그것을 입력받아 인증 서비스로 요청을 전달한 뒤, 그 결과에 따라 리디렉션한다. 리디렉션의 의미는 뒤에서 자세히 알아본다.

```java
    @PostMapping("/login")
    public String login(@RequestParam("username") String username,
                        @RequestParam("password") String password) {

        boolean isAuthenticated = authenticationService.authenticate(username, password);

        if (isAuthenticated) {
            return "redirect:/";
        } else {
            return "redirect:/login?error=true";
        }
    }
```

`AuthController.java` 전체 코드는 다음과 같다.

```java
package com.example.security.controller;

import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestParam;

import com.example.security.service.AuthenticaionService;


/**
 * 로그인 / 회원가입 페이지
 */
@Controller
public class AuthController {

	private final AuthenticaionService authenticaionService;

	public AuthController(AuthenticaionService authenticaionService) {
		this.authenticaionService = authenticaionService;
	}

	@GetMapping("/login")
	public String login() {
		return "login";
	}

    @PostMapping("/login")
    public String login(@RequestParam("username") String username,
                        @RequestParam("password") String password) {

        boolean isAuthenticated = authenticaionService.authenticate(username, password);

        if (isAuthenticated) {
            return "redirect:/";
        } else {
            return "redirect:/login?error=true";
        }
    }


	@GetMapping("/signup")
	public String signup() {
		return "signup";
	}
}
```

`POST /login` 메서드는 제출된 username과 password를 받아 **서비스 계층에 검증을 맡긴다.** 인증에 성공하면 메인 페이지인 `/`로 리다이렉트하고, 실패하면 에러 파라미터를 붙여 로그인 페이지로 다시 보낸다.

> 원문 바로잡기 — 클래스 이름 오타: 전체 코드는 `AuthenticaionService`(t 빠짐)를 import하는데, 아래 2-2의 서비스 클래스 이름은 `AuthenticationService`다. 이름이 다르면 **컴파일 오류**가 난다. 강의 화면의 실제 파일은 `AuthenticaionService.java`였으므로, 둘 중 한쪽으로 통일해야 한다. 올바른 철자는 `AuthenticationService`다. 또 `RequestBody` import는 쓰이지 않으므로 지워도 된다.

> **추가 설명 — 같은 이름의 메서드 두 개**: `login()`이 두 개지만 매개변수가 달라서(오버로딩) 자바 문법상 문제없다. 스프링은 메서드 이름이 아니라 `@GetMapping`/`@PostMapping`으로 요청을 구분한다. 같은 `/login` 주소라도 **GET은 폼을 보여 주고, POST는 제출을 처리**한다.

> **추가 설명 — @RequestParam 생략**: 폼의 `name`과 매개변수 이름이 같으면 `@RequestParam("username")`을 생략하고 `String username`만 써도 된다. 이름이 다를 때만 `@RequestParam("키이름")`으로 연결한다.

다음은 사용자가 입력한 정보가 유효한지 검증하는 비즈니스 로직을 구현한 서비스 클래스다.

### 2-2. AuthenticationService 구현하기

컨트롤러에서 요청한 인증 서비스를 구현한다.

```java
package com.example.security.service;

import org.springframework.stereotype.Service;

@Service
public class AuthenticationService {

    public boolean authenticate(String username, String password) {
        // 실제 환경에서는 DB의 사용자 정보 및 암호화된 비밀번호와 비교
        if ("newlec@newlecture.com".equals(username) && "1234".equals(password)) {
            return true;
        }
        return false;
    }
}
```

서비스 계층은 사용자가 입력한 아이디와 비밀번호가 실제 사용자 정보와 일치하는지 확인하는 업무를 맡는다. 실무처럼 구현하려면 데이터베이스를 이용하는 것이 바람직하지만, 이 코드에서는 지면 관계상 상수로 된 비밀번호를 사용했다.

> **추가 설명 — 상수를 앞에 두는 이유**: `"newlec@...".equals(username)`처럼 문자열 상수를 앞에 두면, `username`이 `null`이어도 `NullPointerException` 없이 `false`가 된다. `username.equals(...)`로 쓰면 `null`일 때 예외가 난다.

> **추가 설명 — 실제 환경이라면**: 주석의 "암호화된 비밀번호"는 정확히는 **해시**다. DB에는 비밀번호를 그대로 저장하지 않고 BCrypt 같은 해시 함수로 바꾼 값을 저장하며, 로그인할 때 입력값을 같은 방식으로 바꿔 비교한다. 스프링 시큐리티에서는 이 일을 `PasswordEncoder`가 맡는다.

## 3. 리디렉션이란?

**리디렉션(Redirect)**은 서버가 클라이언트(웹 브라우저)에게 **요청한 URL 대신 다른 URL로 이동하라**는 응답을 보내는 방식이다.

POST 요청 뒤에는 그 결과를 리디렉션으로 처리하는 경우가 일반적이다. 이해를 돕기 위해 주민센터(행정복지센터)에서 주민등록등본을 발급받는 과정에 비유해 볼 수 있다.

주민센터에서 등본을 떼려면 먼저 신청서를 받아야 한다. 신청서를 작성해 제출 창구에 낸다. 신청서를 받은 직원은 접수를 마친 뒤 "접수되었으니 저쪽 수령 창구에 가서 받아 가세요"라고 안내한다. **제출하는 창구와 결과를 받는 창구가 나뉘어 있기** 때문이다.

웹에서 POST 요청과 리디렉션도 같은 방식이다.

```
[클라이언트 / 브라우저]                              [서버]
        │ 1. 신청서 제출 (POST /login) ─────────────→ │ (로그인 처리)
        │ ←──── 2. 저쪽 창구로 가세요 (302 Found)      │
        │           Location: /                        │
        │ 3. 결과 수령 요청 (GET /) ─────────────────→ │ (메인 페이지 반환)
```

### 3-1. 리디렉션 방법 들여다보기

POST 요청 처리가 끝난 뒤 리디렉션이 어떻게 이루어지는지 좀 더 자세히 보자.

서버는 POST 처리가 정상적으로 마무리되면 `302 Found` 같은 **300번대 HTTP 상태 코드**와 함께, 이동할 URL을 **`Location` 헤더**에 담아 응답한다.

브라우저는 이 응답을 받아 `Location`의 URL로 다시 **GET 요청**을 보낸다. 로그인할 때 보내는 POST도 같은 이유로 리디렉션으로 처리한다.

로그인 처리에 리디렉션을 쓰는 핵심 이유는 다음과 같다.

- **POST/Redirect/GET(PRG) 패턴 적용**: POST 응답으로 화면을 직접 반환하면, 새로고침할 때 같은 로그인 요청이 **다시 전송**되는 문제가 생긴다. 리디렉션으로 GET 요청으로 바꿔 주면 이런 양식 재전송 문제를 막을 수 있다.
- **상태 변화 반영**: 인증 성공 후 메인 페이지로 이동, 실패 후 에러 파라미터를 붙인 로그인 페이지로 이동처럼, 상태 변화를 **URL 수준에서 명확히 나눌** 수 있다.

> **추가 설명 — 302와 303**: 원래 HTTP 규격에서 302는 "같은 방식으로 다른 주소에 다시 요청하라"는 뜻이었다. 하지만 브라우저들이 오래전부터 302를 받으면 **GET으로 바꿔** 요청해 왔고, 스프링의 `redirect:`도 기본으로 302를 보낸다. "POST 처리 후 결과는 GET으로 보라"는 뜻을 정확히 나타내는 코드는 **303 See Other**다. 실무에서는 302로도 문제없이 동작한다.

> **추가 설명 — 개발자 도구로 확인**: Network 탭에서 Doc 필터를 켜면 요청 두 개가 보인다.
>
> | 요청 | 상태 | 확인할 곳 |
> |---|---|---|
> | `POST /login` | 302 Found | 응답 헤더의 `Location: http://localhost:8080/login?error=true` |
> | `GET /login?error=true` | 200 OK | 브라우저가 `Location`을 보고 스스로 보낸 요청 |

### 3-2. 스프링에서 리디렉션 방법

스프링 MVC에서는 **문자열 접두사**나 **전용 객체**로 리디렉션할 수 있다.

#### 1. `redirect:` 접두사 사용 (가장 일반적인 방식)

POST를 처리한 뒤 리디렉션할 주소 앞에 `redirect:` 접두사를 붙이면, 스프링은 응답 헤더에 302 상태 값과 "이 주소로 GET 요청을 다시 하라"는 주소를 담아 클라이언트에게 보낸다.

```java
@PostMapping("/login")
public String login(...) {
    if (isAuthenticated) {
        return "redirect:/"; // 메인 페이지로 리디렉션
    }
    return "redirect:/login?error=true"; // 에러 쿼리 파라미터를 포함하여 로그인 페이지로 리디렉션
}
```

그러면 클라이언트는 헤더에 있는 주소를 확인해 다시 GET 요청을 하고 문서를 받는다. 위의 경우 인증에 성공하면 루트 페이지(`/`)를 다시 요청하고, 실패하면 `/login?error=true`를 요청한다.

이 밖에도 아래 방법들이 있지만, 특별한 일이 없으면 **이 방식으로만** 리디렉션한다. 다음 방식들은 예외적인 상황에서만 쓰고 많이 쓰이지는 않는다.

#### 2. `RedirectView` 객체 반환

반환 타입을 `RedirectView`로 지정해서, 리디렉션할 URL을 객체로 명시적으로 만들어 반환할 수 있다.

```java
@PostMapping("/login")
public RedirectView login(...) {
    if (isAuthenticated) {
        return new RedirectView("/");
    }
    return new RedirectView("/login?error=true");
}
```

> **추가 설명 — 결과는 같다**: `redirect:` 접두사를 쓰면 스프링이 내부에서 `RedirectView`를 만들어 처리한다. 즉 두 방식은 결과가 같고, 접두사 쪽이 더 짧을 뿐이다. `RedirectView`는 상태 코드를 바꾸는 등 세부 설정을 직접 해야 할 때 쓴다.

#### 3. `RedirectAttributes`를 활용한 데이터 전달

리디렉션할 때 파라미터를 안전하게 전달해야 하면 `RedirectAttributes` 객체를 매개변수로 받아 활용할 수 있다.

| 메서드 | 전달 방식 |
|---|---|
| `addAttribute` (쿼리 파라미터 추가) | URL 뒤에 쿼리 스트링(예: `?status=success`) 형태로 전달된다 |
| `addFlashAttribute` (플래시 속성 추가) | URL에 파라미터가 **드러나지 않는다.** 세션에 잠시 저장되었다가 리디렉션된 페이지에서 **한 번만** 조회된 뒤 바로 사라진다. 로그인 실패 메시지 같은 일회성 데이터를 전달할 때 유용하다 |

```java
@PostMapping("/login")
public String login(@RequestParam String username, @RequestParam String password, RedirectAttributes redirectAttributes) {
    boolean isAuthenticated = authenticationService.authenticate(username, password);

    if (isAuthenticated) {
        return "redirect:/";
    } else {
        redirectAttributes.addFlashAttribute("errorMessage", "아이디 또는 비밀번호가 올바르지 않습니다.");
        return "redirect:/login";
    }
}
```

> **추가 설명 — 플래시 속성 꺼내 쓰기**: 플래시 속성은 리디렉션된 요청의 **모델에 자동으로 들어간다.** 그래서 `GET /login` 컨트롤러는 따로 할 일이 없고, 템플릿에서 바로 꺼내 쓰면 된다.
>
> ```html
> <p th:if="${errorMessage}" th:text="${errorMessage}" class="error"></p>
> ```
>
> 쿼리 파라미터 방식(`?error=true`)과 비교하면, 플래시 방식은 주소창이 깔끔하고 새로고침하면 메시지가 사라진다. 대신 잠깐이라도 **세션을 사용**한다는 점이 다르다.

## 4. 실행 테스트 및 직접 인증 처리의 의미

애플리케이션을 실행하고 웹 브라우저에서 로그인 흐름을 테스트한다.

1. 브라우저에서 `http://localhost:8080/login`에 접속해 로그인 페이지가 나오는지 확인한다.
2. 잘못된 계정 정보를 입력하고 전송하면 `http://localhost:8080/login?error=true`로 리다이렉트되며 에러 메시지가 표시된다.
3. 올바른 계정 정보(`newlec@newlecture.com` / `1234`)를 입력하면 인증에 성공해 메인 페이지인 `/`로 이동한다.

> 원문 바로잡기 — 에러 메시지 표시: 위에 실린 `login.html`에는 에러를 보여 주는 부분이 **없다.** 그래서 `?error=true`로 돌아와도 화면에는 아무 변화가 없다. 메시지를 보이려면 폼 위에 다음 한 줄을 추가해야 한다(타임리프에서 쿼리 파라미터는 `param`으로 꺼낸다).
>
> ```html
> <p th:if="${param.error}" class="error">아이디 또는 비밀번호가 일치하지 않습니다.</p>
> ```

이처럼 직접 구현한 방식에서는 컨트롤러가 HTTP 요청을 받아 서비스에서 검증하고, 결과에 따라 리다이렉트를 나눈다.

스프링 시큐리티를 도입하면 이 컨트롤러 영역의 처리 로직이 **서블릿 필터 체인 단계로 옮겨져** 자동화된다. 직접 구현 방식을 이해하는 것은, 나중에 시큐리티가 제공하는 `UsernamePasswordAuthenticationFilter` 등의 동작 구조를 파악하는 기반이 된다.

> **추가 설명 — 직접 구현과 스프링 시큐리티 대응**
>
> | 직접 구현 | 스프링 시큐리티 |
> |---|---|
> | `@PostMapping("/login")` 컨트롤러 메서드 | `UsernamePasswordAuthenticationFilter`가 **컨트롤러에 오기 전에** `POST /login`을 가로채 처리 |
> | `@RequestParam("username")`, `("password")` | 기본으로 `username`, `password`라는 이름의 파라미터를 읽는다. 위 폼의 `name`이 이 이름인 이유다 |
> | `AuthenticationService.authenticate()` | `AuthenticationManager` → `UserDetailsService`로 사용자 정보를 찾고 `PasswordEncoder`로 비밀번호 비교 |
> | `redirect:/` | 성공 핸들러가 원래 가려던 페이지나 `/`로 리다이렉트 |
> | `redirect:/login?error=true` | 실패 핸들러가 기본으로 **`/login?error`**로 리다이렉트 |
> | (없음) 인증 상태 유지 | `SecurityContext`를 세션에 저장해 다음 요청에서도 로그인 상태 유지 |
> | (없음) "로그인 상태 유지" 체크박스 | `rememberMe()` 설정으로 처리 (기본 파라미터 이름 `remember-me`) |
>
> 직접 구현에서는 로그인에 성공해도 그 사실을 **어디에도 저장하지 않으므로** 다음 요청에서 서버는 이 사용자를 기억하지 못한다. 이 빈틈을 쿠키와 세션으로 채우는 것이 다음 단계다.
