# 트랜잭션 — 논리적 작업 단위와 @Transactional 롤백 원리

트랜잭션을 "논리적인 작업 단위"라고 부르는 이유, 엔티티가 테이블을 만드는 `ddl-auto` 설정, 그리고 `@Transactional`이 실패한 작업을 어떻게 전부 되돌리는지 정리한다.

## 1. 트랜잭션은 "논리적인" 작업 단위다

트랜잭션을 "일괄 처리"라고 말하는 것도 틀린 말은 아니다. 하지만 일괄 처리는 **처리 방식**에 대한 이야기이고, 트랜잭션 자체는 **작업 단위**다. 주문, 결제, 수강신청, 회원가입처럼 우리가 만드는 기능은 모두 **한 번에 이뤄져야 할 업무 단위**다.

이 작업 단위를 흔히 **논리적인** 단위라고 부른다. 논리의 반대말은 **물리**다.

| 구분 | 의미 | 예 |
|---|---|---|
| **물리적** | 실제로 존재하고 직접 실행되는 것 | 리포지토리의 `save()`, `delete()`가 실행하는 SQL 하나하나 |
| **논리적** | 실제 실행 요소들을 묶어서 하나처럼 표현한 것 | 서비스의 `주문하기()` — 안에서는 여러 SQL이 실행되지만 하나의 업무로 본다 |

함수를 만들 때와 같은 이야기다. C나 자바가 제공하는 연산자가 아니라, 내가 함수로 만들어 원하는 이름을 붙이고 새 명령어처럼 쓰면 그것은 **내가 정의한 논리적인 명령어**가 된다. 트랜잭션도 마찬가지로, 기존의 물리적인 명령어(SQL)들을 엮어서 만든 **업무 명령어**다.

문제는 이 논리적인 단위가 "한 번에 실행된다"는 보장이 저절로 생기지 않는다는 점이다. SQL 하나하나는 각자 실행되기 때문이다. 이 보장을 가능하게 하는 작업이 **트랜잭션 처리**다.

> **정리**: 리포지토리 = 물리적 단위(실제 SQL), 서비스 메서드 = 논리적 단위(업무). 트랜잭션은 이 서비스 단위를 "전부 성공 아니면 전부 취소"로 묶는 것이다.

## 2. 테이블은 엔티티가 만든다 — ddl-auto

이제는 `CREATE TABLE`을 직접 쓰지 않는다. UNIQUE, NOT NULL, CHECK 같은 제약조건도 DB에 직접 걸지 않는다. **엔티티에 설정한 내용**이 테이블을 만드는 원천이 되고, 테이블의 생성·삭제 시점은 `spring.jpa.hibernate.ddl-auto` 설정 하나로 정해진다.

| 값 | 시작할 때 | 종료할 때 |
|---|---|---|
| `create` | 기존 테이블을 **지우고** 새로 만든다 | 그대로 둔다 |
| `create-drop` | 지우고 새로 만든다 | **테이블을 삭제**한다 |
| `update` | 없는 테이블·컬럼을 **추가**한다. 기존 컬럼이나 데이터는 지우지 않는다 | 그대로 둔다 |
| `validate` | 엔티티와 테이블이 맞는지 **검사만** 한다. 다르면 시작 실패 | — |
| `none` | 아무것도 하지 않는다 | — |

- `update`는 엔티티에 필드를 추가하면 부팅하면서 `ALTER TABLE ... ADD COLUMN`을 알아서 실행한다. 반대로 엔티티에서 필드를 지워도 DB 컬럼은 지우지 않는다.
- `create-drop`은 실행했다가 테스트하고 바로 지우고 싶을 때 쓴다.

> 강의에서는 "운영할 때는 일반적으로 `update`를 많이 쓴다"고 했지만, 실무 운영 DB에서는 `update`를 쓰지 않는 것이 원칙이다. `update`는 컬럼 이름 변경을 "새 컬럼 추가"로 처리해 데이터가 옛 컬럼에 남거나, 의도치 않은 변경이 운영 DB에 바로 반영될 수 있다. 운영에서는 `validate`나 `none`으로 두고, 스키마 변경은 SQL 스크립트나 **Flyway·Liquibase** 같은 마이그레이션 도구로 기록하며 적용한다. `create`·`create-drop`·`update`는 개발·테스트용이다.

**SQL은 그래도 알아야 한다**: SQL을 직접 쓰는 일은 점점 줄고 있다. 그렇다고 몰라도 되는 것은 아니다. SQL을 알아야 도구가 무엇을 해주는지 이해할 수 있고, 문제가 생겼을 때 막다른 길에 서지 않는다.

## 3. 트랜잭션이 없으면 — 절반만 반영된다

서비스 메서드 하나에서 카테고리 두 개를 연달아 저장하는데, 두 번째가 제약조건 위반으로 실패한다고 하자.

```java
public void createTwo() {
    categoryRepository.save(new Category("Copy", "copy"));  // ① 성공
    categoryRepository.save(new Category(null, "copy-x"));  // ② name이 NULL → NOT NULL 위반
}
```

②에서 오류가 나지만 **①은 이미 DB에 들어가 있다.** 업무 하나(카테고리 두 개 만들기)가 절반만 반영된 상태다. 사람이 실행 결과를 하나하나 보지 않으면 모른다. 이미 **결함이 DB에 반영**된 것이다.

오류가 나면 나머지 작업까지 모두 **원래대로 되돌려야** 하는데, 이것을 직접 구현하기가 어렵다.

## 4. @Transactional 한 줄로 해결

```java
@Transactional
public void createTwo() {
    categoryRepository.save(new Category("Copy2", "copy2"));  // ①
    categoryRepository.save(new Category(null, "copy2-x"));   // ② NOT NULL 위반 → 예외
}
```

②에서 같은 오류가 나지만, 이번에는 **①까지 함께 되돌려진다**(롤백). 다른 서버를 띄울 필요도, 다른 설정도 필요 없이 `@Transactional` 한 줄이면 된다. 엔터프라이즈 개발에서 스프링이 널리 쓰이게 된 큰 이유 중 하나가 이것이다.

> **추가 설명 — 롤백되는 예외**: 스프링의 `@Transactional`은 기본적으로 **런타임 예외(`RuntimeException`)와 `Error`**가 발생했을 때 롤백한다. 제약조건 위반은 `DataIntegrityViolationException`(런타임 예외)으로 올라오므로 롤백된다. 체크 예외(`Exception`을 직접 상속)는 기본적으로 롤백되지 않으며, 필요하면 `@Transactional(rollbackFor = Exception.class)`로 지정한다.

## 5. 어떻게 가능한가 — 커넥션 공유와 임시 기록

트랜잭션이 없을 때는 `save()` 하나하나가 **각자의 트랜잭션**으로 실행되어 바로 커밋된다. 원본에 곧바로 쓰는 것과 같다.

트랜잭션을 걸면 DB에게 이렇게 요청하는 셈이다.

1. 바로 원본에 반영하지 말고 **임시로 기록**해 둔다.
2. 모두 올바르면 **커밋할 때 한 번에** 반영한다.
3. 오류가 나면 임시 기록을 **모두 버린다**(롤백).

이것이 가능하려면 ①과 ②가 **같은 DB 연결(커넥션)**을 써야 한다. 연결이 닫히지 않은 채로 그 연결을 물고 가서, 마지막에 그 연결로 커밋이나 롤백을 해야 두 작업이 하나처럼 처리된다. `@Transactional`은 메서드가 시작될 때 커넥션을 하나 열어 그 메서드 안의 모든 리포지토리 호출이 **같은 커넥션을 공유**하게 하고, 메서드가 끝나면 커밋, 예외가 나면 롤백한다.

| | 트랜잭션 없음 | `@Transactional` |
|---|---|---|
| 커넥션 | `save()`마다 따로 | 메서드 전체가 하나를 공유 |
| 반영 시점 | `save()` 할 때마다 즉시 커밋 | 메서드가 정상 종료될 때 한 번에 커밋 |
| 중간에 오류 | 앞의 작업은 이미 반영됨 | 앞의 작업까지 모두 롤백 |

> **추가 설명 — "임시 종이"의 실제 모습**: DB는 커밋 전의 변경도 실제 테이블에 기록하지만, 그 변경은 **커밋되기 전까지 다른 트랜잭션에게 보이지 않게** 관리한다(PostgreSQL은 행의 여러 버전을 두는 MVCC 방식). 롤백하면 그 변경은 무효 처리된다. 그래서 "임시로 쓴다"는 비유가 결과적으로 맞다.

그렇다면 메서드에 어노테이션 하나 붙였을 뿐인데, 누가 커넥션을 열고 커밋·롤백 코드를 메서드 앞뒤에 넣어 주는 걸까? 이 원리가 **AOP**다. `@Transactional`에는 전파(`propagation`) 같은 추가 옵션도 있는데, 이 옵션들을 언제 쓰는지도 AOP 원리를 알고 나서 보는 것이 좋다.

## 6. 한 줄 정리

- 트랜잭션은 물리적인 SQL들을 묶어 만든 **논리적인 업무 단위**이며, 이 단위가 한 번에 실행되도록 보장하는 것이 트랜잭션 처리다.
- `ddl-auto`는 엔티티로 테이블 생명주기를 관리한다. `create-drop`·`create`·`update`는 개발용, 운영은 `validate`/`none` + 마이그레이션 도구.
- `@Transactional`이 없으면 실패 전의 작업이 DB에 남고, 있으면 **같은 커넥션**으로 묶여 전부 롤백된다.
- 기본 롤백 대상은 런타임 예외다. 제약조건 위반(`DataIntegrityViolationException`)은 롤백된다.
