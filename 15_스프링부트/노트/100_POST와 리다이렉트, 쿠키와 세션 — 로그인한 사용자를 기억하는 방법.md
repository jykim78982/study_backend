# POST와 리다이렉트, 쿠키와 세션 — 로그인한 사용자를 기억하는 방법

스프링 보안은 아주 쉬우면서도 강력한 라이브러리이고, **필터**라는 개념으로 만들어져 있다. 성에 들어오려면 반드시 대문을 지나야 하듯, 필터는 지나가는 모든 요청을 통제하는 대문 역할을 한다.

그런데 그 필터 안에서 무슨 일이 벌어지는지 이해하려면 **인증과 인가**, 그리고 **쿠키와 세션**을 알아야 한다. 그래서 이번에는 스프링 보안 모듈을 걷어 낸 상태에서 **로그인을 직접 구현**해 보면서 이 개념들을 하나씩 익힌다.

## 1. 로그인 직접 구현하기

### 흐름

```
사용자 ── GET /login ──→ 컨트롤러 ── login.html(로그인 폼) 반환
사용자 ── POST /login (username, password) ──→ 컨트롤러
                                                  ↓ "인증됐니?"
                                              인증 서비스 → true / false
                                                  ↓
                                        컨트롤러: 결과에 따라 어디로 갈지 안내
```

- **컨트롤러**는 홀 서빙이다. 사용자의 입력을 받아 서비스에 업무를 맡기고, 결과를 사용자에게 전달할 뿐 직접 업무를 처리하지 않는다.
- **인증 로직**(아이디·비밀번호가 맞는지 판단)은 **서비스 계층**이 맡는 것이 바람직하다. 서비스가 "인증됐다/안 됐다"를 알려 주면 컨트롤러는 그 이후의 행동만 정하면 된다.

### 인증 서비스

원래는 데이터베이스에서 사용자 리포지토리로 그 사용자의 정보를 꺼낸 뒤 비교해야 한다. 여기서는 학습 주제가 아니므로 사용자 정보를 코드에 **고정**해 둔다.

```java
@Service
public class AuthenticationService {

    public boolean authenticate(String username, String password) {

        if ("newlec@newlecture.com".equals(username) && "1234".equals(password))
            return true;

        return false;
    }
}
```

로그인 폼의 아이디 입력란이 `type="email"`이라서, 이메일 형태가 아니면 브라우저가 전송을 막는다. 그래서 아이디는 이메일로 온다고 보고 비교한다.

> **추가 설명 — 왜 상수를 앞에 두나**: `username.equals("newlec@...")`와 `"newlec@...".equals(username)`은 결과가 같아 보이지만, `username`이 `null`이면 앞의 방식은 `NullPointerException`이 난다. 문자열 상수는 절대 `null`이 아니므로, **상수를 앞에 두면** `null`이 와도 그냥 `false`가 된다. 그래서 "실수를 줄인다"는 이유로 이 방식을 많이 쓴다. 다만 강사는 이런 사소한 스타일 논쟁에 시간을 쓰기보다, AI가 둘 중 하나를 고르면 그대로 두는 정도로 넘어가자고 했다.

### 컨트롤러

```java
@Controller
public class AuthController {

    private final AuthenticationService authenticationService;

    public AuthController(AuthenticationService authenticationService) {
        this.authenticationService = authenticationService;
    }

    @GetMapping("/login")
    public String login() {
        return "login";                 // templates/login.html
    }

    @PostMapping("/login")
    public String login(String username, String password) {

        boolean isAuthenticated = authenticationService.authenticate(username, password);

        if (isAuthenticated)
            return "redirect:/";        // 성공 → 랜딩 페이지로
        else
            return "redirect:/login?error=true";  // 실패 → 로그인 페이지로, 오류 표시
    }
}
```

- 폼이 `application/x-www-form-urlencoded`로 `username=...&password=...`를 보내면, 스프링은 **매개변수 이름만 맞춰 두면** 값을 자동으로 넣어 준다.
- 폼의 키 이름과 변수 이름이 다르면 `@RequestParam("키이름")`으로 연결하고, 같으면 생략해도 된다.

## 2. POST는 페이지를 주지 않는다 — 리다이렉트

### 인증 결과에 따라 무엇을 리턴할까

인증 결과를 받은 컨트롤러는 `if`/`else`에서 각각 무엇을 리턴해야 할까? 지금까지 사용자에게 돌려준 것은 **문서(페이지)**나 **데이터** 둘 중 하나였다. 이번에는 둘 다 아니다. **상태 코드 302**와 함께 **"이 주소로 다시 요청하세요"**라는 정보를 돌려준다. 이것이 **리다이렉트(redirect)**다.

| 요청 | 의미 | 응답 |
|---|---|---|
| GET | "이거 주세요" | 달라는 것(페이지나 데이터)을 준다 |
| POST | "이거 받으세요"(제출) | 받은 뒤 **어디로 가라고 안내**한다 |

POST는 뭘 달라는 요청이 아니다. 달라고 하지도 않았는데 상자를 줘 버리면 이상하다. 그래서 제출을 받은 다음에는 **다음에 갈 곳을 안내**하면 된다.

> **비유 — 주민센터**: 등본을 떼러 가면 먼저 신청서를 받는다(GET). 개인정보를 적어 제출한다(POST). 그러면 직원이 그 자리에서 등본을 주는 게 아니라 "접수됐습니다. 저쪽 창구에 가서 받으세요"라고 안내한다(리다이렉트). 손님은 그 창구로 가서 다시 요청(GET)해서 등본을 받는다.

### 스프링에서 리다이렉트하기

`@Controller`의 메서드가 문자열을 반환하면 원래는 **뷰(템플릿) 이름**이다. 그런데 앞에 **`redirect:` 접두사**를 붙이면 페이지가 아니라 **주소**가 되고, 스프링은 그 주소를 사용자에게 전달한다. 사용자에게 루트 페이지를 주는 것이 아니라, "루트 페이지로 다시 요청하세요"라는 정보를 주는 것이다.

### 실패했을 때도 안내한다

실패했을 때도 문서를 주지 않는다. 다시 로그인 페이지로 가라고 안내한다. 그런데 그냥 `redirect:/login`만 하면, 사용자는 로그인 버튼을 눌렀는데 아무 설명 없이 같은 로그인 페이지가 다시 뜬다. 뭘 잘못했는지 모르니 화가 난다.

그래서 **`?error=true` 같은 상태 값을 붙여** 보낸다. 페이지(JSP든 타임리프든)는 이 값을 보고 "아이디 또는 비밀번호가 일치하지 않습니다" 같은 메시지를 보여 준다. 똑같은 로그인 페이지인데, 아까는 없던 빨간 안내 문구가 하나 보이게 된다.

> **추가 설명 — 타임리프에서 오류 문구 표시**: 쿼리 파라미터는 `param`으로 꺼낼 수 있다.
>
> ```html
> <p th:if="${param.error}" style="color:red">아이디 또는 비밀번호가 일치하지 않습니다.</p>
> ```

### 개발자 도구로 확인하기

틀린 비밀번호로 로그인하고 개발자 도구의 **Network** 탭을 보면 요청이 너무 많이 보인다. 필터에서 **Doc**을 고르면 CSS·자바스크립트·폰트가 사라지고 두 개만 남는다.

| 순서 | 요청 | 상태 코드 | 핵심 |
|---|---|---|---|
| 1 | `POST /login` | **302 Found** | 응답 헤더 `Location: http://localhost:8080/login?error=true` |
| 2 | `GET /login?error=true` | 200 OK | 브라우저가 `Location`의 주소로 **스스로 다시 요청** |

302는 오류가 아니다. "처리했으니 알려 드리는 주소로 가 보세요"라는 뜻이고, 그 주소는 **`Location`** 헤더에 담겨 온다. 서버가 어디로 가라고 지시하고, 클라이언트는 그 지시대로 다시 요청하는 것이다. 앞으로 계속 들여다볼 화면이니 Network 탭 보는 법에 익숙해져야 한다.

> **꼭 기억할 것 — POST는 페이지를 주지 않는다.** POST를 처리한 뒤에는 다른 곳으로 보낸다.

> **추가 설명 — PRG 패턴**: 이 방식을 **Post → Redirect → Get(PRG)** 패턴이라고 한다. POST 요청에 바로 페이지를 돌려주면, 사용자가 새로고침할 때 브라우저가 **POST를 다시 보내서** 같은 주문·결제·글쓰기가 두 번 처리될 수 있다. 리다이렉트로 GET 요청을 거치게 하면, 마지막 요청이 GET이 되므로 새로고침해도 페이지만 다시 받아 온다.

## 3. 인증은 했는데 — 서버는 나를 기억하지 못한다

### 인증과 인가

- **인증**: "너 누구야?"에 답하는 것이다. "아, 내가 아는 사람이구나. 회원 맞네." 지금 만든 인증 서비스가 바로 인증 로직이다.
- 스프링 보안을 쓰면 이 인증 로직(오른쪽의 서비스)을 **직접 구현하지 않는다.** 스프링 보안이 대신 구현해 준다.

### 문제 — 관리자 페이지에 아무나 들어온다

로그인에 성공해서 메인 페이지로 왔다. 그런데 이 상태로 관리자 페이지로 가 보면, 로그인하지 않은 손님도 똑같이 들어올 수 있다. 내가 인증을 했기 때문에 들어온 것인지, 원래 아무나 들어오는 곳인지 구분할 방법이 없다. 관리자 페이지에 개나 소나 들어오는 것이다.

인증을 했다면 다음 두 가지가 되어야 한다.

- 사용자는 **자기가 인증한 사용자라는 것을 증명**할 수 있어야 한다.
- 문서를 주는 서버는 이 사용자가 **인증했는지, 권한이 있는지** 알고 그에 맞게 문서를 줘야 한다.

### 로컬 앱과 웹의 차이

- **로컬 애플리케이션**이라면 로그인한 뒤 "이 사용자는 인증됨"이라는 상태를 **전역 변수** 어딘가에 저장해 두고 계속 쓰면 된다.
- **웹**은 다르다. 요청 하나가 응답으로 돌아가면 **연결이 끝난다.** 로그인을 처리한 요청과, 리다이렉트된 다음 요청이 같은 사람인지 서버는 전혀 구분하지 못한다.

### 요청만 봐서는 사용자를 식별할 수 없다

요청의 General 헤더와 Request 헤더를 다 뒤져 봐도 나를 **유일하게** 구분해 줄 값이 없다. 요청 주소도, 브라우저 정보(User-Agent)도 다른 사람과 같을 수 있다.

> **IP로는 왜 안 되나**: 공유기를 쓰는 집에서는 집 안의 모든 기기가 **공유기의 IP 하나**로 요청을 보낸다. 같은 집에서 같은 사이트에 접속하면 서버 눈에는 모두 같은 IP라서 구분할 수 없다.

그래서 서버가 직접 **"다음에 올 때 이거 들고 와. 내가 너를 알아볼 수 있게 번호를 매겨 줄게"**라고 하는 방식을 쓴다. 이것이 **쿠키**다.

## 4. 쿠키 — 서버가 브라우저에 맡겨 두는 작은 데이터

### 쿠키 발급과 전송

**쿠키**는 서버가 필요에 따라 **브라우저에 저장해 두는 작은 데이터 조각**이다. 서버가 쿠키를 주면 브라우저는 그것을 가지고 있다가, **그 서버에 요청할 때마다** 자동으로 실어 보낸다.

쿠키 연습용 컨트롤러다(강의 코드를 바탕으로 재구성).

```java
@RestController
public class CookieDemoController {

    @GetMapping("/set-cookie")
    public String setCookie(HttpServletResponse response) {

        Cookie cookie = new Cookie("clientId", "user-12345");
        // cookie.setMaxAge(60 * 60 * 24);   // 옵션은 필수가 아니다
        // cookie.setPath("/");
        response.addCookie(cookie);         // 응답 헤더에 쿠키를 붙인다

        return "쿠키가 발급되었습니다.";
    }
}
```

- `@RestController`라서 반환한 문자열이 그대로 브라우저 화면에 나온다.
- 쿠키를 이렇게 `Cookie` 객체로 만드는 것은 스프링이 **서블릿 방식**을 그대로 이어받았기 때문이다. 다른 플랫폼은 설정 방법이 다르지만, 결국 하는 일은 **응답 헤더에 쿠키를 붙이는 것**이다.

| 단계 | 개발자 도구에서 보이는 것 |
|---|---|
| `GET /set-cookie` 응답 | 응답 헤더 **`Set-Cookie: clientId=user-12345`** — "이 쿠키 갖고 있어" |
| 이후 `GET /menu` 등 다른 요청 | 요청 헤더 **`Cookie: clientId=user-12345`** — 브라우저가 알아서 실어 보냄 |

쿠키를 한 번 받으면, 그 쿠키를 폐기하기 전까지 **어떤 페이지를 요청하든** 계속 가지고 온다. 서버는 이것으로 클라이언트를 식별한다. 쿠키 목록은 개발자 도구의 **Application → Cookies**에서 볼 수 있다.

> **추가 설명 — DevTools 자동 재시작**: 프로젝트에 DevTools를 넣었다면 소스가 바뀔 때 자동으로 재시작해야 하는데, WSL 환경에서는 이게 잘 안 되는 경우가 있다. 그럴 때는 기다리지 말고 직접 재시작하는 것이 확실하다.

### 쿠키는 식별용만이 아니다 — 테마 색 저장하기

식별 예시로 설명하다 보니 오해하기 쉬운데, 쿠키는 그냥 **서버가 클라이언트에 저장하는 작은 데이터**다. 어떤 용도로 쓸지는 서버가 정한다. 보통은 사용자의 **특징이나 선호도**("이 사람이 좋아하는 색은 이거구나", "이런 페이지를 자주 보는구나")를 남기는 데 쓴다.

배경색을 쿠키로 기억하는 예제다(강의 코드를 바탕으로 재구성).

```java
@Controller
public class ThemeController {

    @GetMapping("/theme")
    public String theme(@CookieValue(value = "bgColor", defaultValue = "white") String bgColor,
                        Model model) {
        model.addAttribute("bgColor", bgColor);   // 쿠키가 없으면 white
        return "theme";                            // templates/theme.html
    }

    @PostMapping("/theme")
    public String changeTheme(String bgColor, HttpServletResponse response) {
        Cookie cookie = new Cookie("bgColor", bgColor);
        cookie.setMaxAge(60 * 60 * 24);   // 60초 × 60분 × 24시간 = 하루
        cookie.setPath("/");              // 모든 경로에서 전송
        response.addCookie(cookie);
        return "redirect:/theme";          // POST 후 리다이렉트
    }
}
```

```html
<body th:style="'background:' + ${bgColor}">
  <form method="post" action="/theme">
    <select name="bgColor">
      <option value="lightblue">lightblue</option>
      <option value="lightgreen">lightgreen</option>
      <option value="white">white</option>
    </select>
    <button>변경</button>
  </form>
</body>
```

1. 색을 골라 제출하면 POST가 일어나고, 서버는 그 색을 **쿠키로 설정**한 뒤 리다이렉트한다.
2. 리다이렉트된 GET 요청에는 쿠키가 실려 오고, 컨트롤러는 쿠키 값을 꺼내 **모델**에 담는다(쿠키가 없으면 기본값 white).
3. 페이지는 모델 값을 `background` 스타일에 넣는다.

값을 바꾸지 않는 한 브라우저는 같은 쿠키를 계속 보내므로 **새로고침해도 색이 유지**된다. 그런데 쿠키는 **브라우저마다 따로** 저장되므로, 크롬에서 연초록으로 바꿔도 다른 브라우저에서는 기본색인 흰색으로 나온다.

> 원문 바로잡기 — 강의에서 `theme.html`을 만들기 전에 `/theme`을 요청하면 404가 날 거라고 했는데 실제로는 **500**이 났다. 500이 맞다. 404는 **요청한 주소를 처리할 컨트롤러가 없을 때** 나는 것이고, 지금은 컨트롤러는 있고 그 컨트롤러가 가리킨 **템플릿 파일을 찾지 못한 서버 내부 오류**(타임리프의 `TemplateInputException`)이기 때문이다.

> **곁다리 — 쿠키 동의 창**: 사이트에서 "쿠키 저장을 허용하시겠습니까?"를 묻는 것은 유럽의 규제 때문이다. 유럽에서 서비스하려면 쿠키를 저장하기 전에 동의를 받아야 한다. 웬만한 서버라면 비밀번호 같은 민감한 정보를 쿠키에 담지 않으므로, 허용해도 실제 위험은 크지 않고 거부하는 이유는 대개 찝찝함이다.

## 5. 쿠키를 인증에 쓰면 — 무엇이 불안한가

쿠키로 인증 상태를 관리한다는 것은, 서버가 **"인증을 통과한 사용자는 이런 쿠키를 가지고 있다"**고 약속하는 것이다. `clientId=user-4789`처럼 사용자마다 다른 식별자를 심어 보내면, 그 쿠키를 가진 요청을 인증된 사용자로 본다.

**불안한 점**: 서버가 확인하는 것은 쿠키 값 하나뿐이다. 누군가 그 값을 **훔치기만 하면 그 사람 행세**를 할 수 있다.

이것은 쿠키 대신 나중에 배울 **토큰**을 써도 다르지 않다. 로그인한 정보를 가진 값이 내 컴퓨터 어딘가에 있고, 그걸 빼가면 그 사용자로 인식된다.

- 옆자리 사람이 **물리적으로** 빼갈 수도 있다.
- 와이파이를 함께 쓰는 장소에서 빼가려는 시도도 있다.
- 그래서 자리를 비울 때는 **로그아웃**하거나 화면을 잠그는 습관이 중요하다.

> 원문 바로잡기 — 강의에서 "자리를 비운 사이 쿠키를 빼가는 것"을 세션 고정(Session Fixation) 공격이라고 했는데, 이미 발급된 세션 ID를 훔쳐 쓰는 것은 **세션 하이재킹(Session Hijacking)**이다. 세션 고정은 반대로, 공격자가 **미리 알고 있는 세션 ID를 피해자에게 심어 두고** 피해자가 그 ID로 로그인하기를 기다리는 공격이다. 스프링 시큐리티는 로그인할 때 세션 ID를 새로 바꿔서 이것을 막는다.

## 6. 쿠키의 옵션 — 어디로, 언제까지, 누가 읽나

Application 탭의 쿠키 목록에는 Name, Value 말고도 여러 열이 있다.

### Domain — 어느 서버로 보내나

`localhost`에서 받은 쿠키는 네이버에 갈 때 가져가지 않는다. 쿠키는 **그 쿠키를 준 서버(도메인)로 갈 때만** 전송된다. 네이버에서 받은 쿠키는 네이버로만 간다.

### Path — 어느 경로로 보내나

같은 서버라도 모든 주소로 가는 것은 아니다. **Path 이하의 경로**로 요청할 때만 간다.

| Path | 전송되는 요청 |
|---|---|
| `/` | 그 서버의 **모든** 경로 |
| `/aa` | `/aa`와 `/aa/...` 아래 경로만. `/menu`로는 가지 않는다 |

페이지 전체에서 쓰는 쿠키라면 Path를 `/`로, 특정 영역에서만 쓰려면 그 경로로 정한다.

### Expires / Max-Age — 언제까지 살아 있나

| 설정 | Expires 열 표시 | 저장 위치 | 브라우저를 닫으면 |
|---|---|---|---|
| 기한 없음 | **Session** | 메모리 | **사라진다** |
| `setMaxAge(60*60*24)` | 만료 날짜 (예: 하루 뒤) | 브라우저의 쿠키 저장소 **파일** | 남아 있다. 재부팅해도 기한까지 유지 |

`clientId`(Session)와 `bgColor`(하루)를 둔 채 브라우저를 닫았다 열면 `clientId`는 사라지고 `bgColor`는 남아 있다. 이때 창 하나만 닫는 것이 아니라 **브라우저 프로세스 전체**가 종료되어야 한다.

> **추가 설명 — 그래도 남아 있는 경우**: 크롬의 "시작할 때 이전 페이지 이어서 열기" 설정이 켜져 있으면, 브라우저가 기한 없는 쿠키까지 복원해서 닫았다 열어도 남아 있을 수 있다. 실습 결과가 다르면 이 설정을 확인한다.

### HttpOnly — 자바스크립트가 읽을 수 있나

`new Cookie()`로 만든 쿠키의 `HttpOnly` 기본값은 `false`다. 이때는 페이지의 자바스크립트가 `document.cookie`로 쿠키를 읽을 수 있다. 공격자가 사용자를 꼬드겨 스크립트를 실행시키기만 하면, 옆에서 지켜볼 필요도 없이 쿠키를 빼내 그 사용자 행세를 하며 계좌 이체 등을 할 수 있다.

`setHttpOnly(true)`로 켜면 쿠키는 **브라우저가 서버로 보낼 때만** 쓰이고, 스크립트로는 읽을 수 없다.

> 원문 바로잡기 — 강의에서는 "검색해서 들어간 **다른 사이트**의 스크립트가 내 쿠키를 읽을 수 있다"고 했는데, 브라우저의 **동일 출처 정책** 때문에 다른 사이트의 스크립트는 `localhost`나 은행 사이트의 쿠키를 `document.cookie`로 읽을 수 없다. 진짜 위험은 **XSS**다. 공격자가 게시글이나 입력값을 통해 **바로 그 사이트 안에** 악성 스크립트를 심으면, 그 스크립트는 그 사이트의 쿠키를 읽을 수 있다. `HttpOnly`는 바로 이 경우를 막는다. 참고로 톰캣이 발급하는 세션 쿠키(`JSESSIONID`)는 기본으로 `HttpOnly`가 켜져 있다.

> **추가 설명 — 쿠키 옵션 코드로 정리**
>
> | 메서드 | 옵션 |
> |---|---|
> | `setMaxAge(초)` | 유효 기간 |
> | `setPath("/")` | 전송할 경로 |
> | `setDomain(...)` | 전송할 도메인 |
> | `setHttpOnly(true)` | 스크립트에서 읽기 금지 |
> | `setSecure(true)` | HTTPS일 때만 전송 |
>
> 무엇을 설정할지는 업무에 따라 필요할 때 정하면 된다.

## 7. 세션 — 사용자 정보는 서버에 둔다

### 쿠키에 사용자 정보를 다 담던 시절

예전에는 로그인한 뒤 페이지마다 필요한 사용자 정보(이메일, 레벨, 프로필 사진 등)를 **전부 쿠키에 담아** 다녔다. 그러면 DB를 조회하지 않고도 페이지마다 프로필을 그릴 수 있었다. 하지만 이런 정보가 매번 네트워크를 오가는 것이 맞나 하는 찜찜함도 있고, 네트워크 자원에 대한 부담도 있었다.

그래서 **사용자 정보는 브라우저가 아니라 서버에 저장하자**는 생각이 나왔다. 이것이 **세션**이다.

### 왜 "세션(기간)"이라고 부르나

사전에서 session을 찾으면 "기간"이라는 뜻이 나온다. 서버에 저장하는 것과 기간이 무슨 관계일까?

서버가 사용자를 위해 메모리 공간을 내줬는데, 그 사용자가 **언제 다시 올지 모른다.** 피트니스 센터 사물함에 물건을 잔뜩 넣어 두고 연락이 끊긴 회원과 같다. 사물함은 **한정된 자원**이라 무한정 맡아 둘 수 없다. 그래서 **"이 기간 안에 다시 요청이 안 오면 지운다"**는 조건을 단다.

즉, 세션은 **서버에 저장한 데이터를 쓸 수 있는 기간**이고, 서버에 저장한 정보가 있을 때 의미가 생긴다. 흔히 "세션 정보"라고 부르는 것은 세션 기간 동안 쓸 수 있도록 서버에 저장된 데이터를 말한다. 이 방식은 지금도 쇼핑몰이나 공공 프로젝트에서 널리 쓰인다.

> **추가 설명 — 세션 유효 기간**: 이 "기간"은 마지막 요청으로부터 일정 시간 동안 요청이 없으면 끝나는 방식이다. 스프링 부트(톰캣)의 기본값은 **30분**이고, `server.servlet.session.timeout`으로 바꿀 수 있다.

### 세션 ID와 쿠키

```
[클라이언트]                                [서버]
   │ 1. 로그인 요청 (ID/PW) ───────────────→ │ 인증 성공
   │                                        │ 세션 생성 (메모리에 사용자 정보 저장)
   │ ←─────────── 2. 응답 (쿠키: JSESSIONID) │
   │ 3. 다음 요청 (JSESSIONID) ─────────────→ │ 세션 ID로 메모리 조회
   │ ←─────────── 4. 응답 (인증된 사용자 처리) │
```

서버에는 수많은 사용자의 세션 데이터가 쌓이므로, 어느 데이터가 누구 것인지 알려면 **결국 쿠키가 필요하다.** 다만 쿠키에는 사용자 정보 대신 **그 데이터를 찾을 수 있는 아이디(세션 ID)만** 담아 보낸다. 사용자 정보 자체는 서버가 안전하게 관리하고, 브라우저와 서버 사이에는 세션 ID만 오간다.

### 서버의 네 가지 저장소

서버에는 값을 저장하는 저장소가 네 가지 있다. 사용 방법은 모두 같고(`setAttribute`/`getAttribute`), **범위(scope)**만 다르다.

| 저장소 | 쓸 수 있는 범위 | 수명 |
|---|---|---|
| **page** (PageContext) | 그 페이지 안 | 페이지 처리 동안 |
| **request** | 포워딩 관계에 있는 서블릿끼리 (한 서블릿이 다른 서블릿을 호출할 때 값 공유) | 요청 하나 동안 |
| **session** | 모든 URL, 단 **세션 ID가 같은 사용자만** | 세션 기간 동안 |
| **application** | 모든 URL, **모든 사용자가 공유** | 프로그램 시작부터 끝까지 |

- **세션** 저장소에 값을 담으면, 세션 객체가 **세션 ID를 발급**하고 그 ID별로 데이터를 **분리·격리**한다.
- 개인화된 데이터는 **session**에, 모든 사용자를 위한 데이터는 **application**에 저장한다.

### 스프링에서 세션 객체 얻기

스프링의 프론트 컨트롤러(`DispatcherServlet`)는 **리플렉션**으로 컨트롤러 메서드의 매개변수를 들여다보고, 선언한 대로 알맞은 값을 채워 준다. 매개변수의 순서나 종류, 이름이 하나로 정해져 있는 것이 아니다.

```java
// 1) 스프링이 꺼내 주는 대로 받기
public String login(String username, String password) { ... }

// 2) 요청 객체를 직접 받아서 내가 꺼내기
public String login(HttpServletRequest request) {
    String username = request.getParameter("username");
    ...
}
```

세션 객체를 얻는 방법도 마찬가지다.

```java
// 가장 원시적인 방법 — request에서 직접 꺼내기
HttpSession session = request.getSession();

// 스프링다운 방법 — 매개변수로 달라고 하기
@PostMapping("/login")
public String login(String username, String password, HttpSession session) { ... }
```

프론트 컨트롤러가 가진 것은 사실 **요청(request)과 응답(response)**뿐이다. 매개변수에 `HttpSession`이 있으면 "request에 이걸 꺼내는 getter가 있네" 하고 `getSession()`을 대신 호출해서 넣어 준다. `username`이 있으면 `getParameter("username")`을 대신 해 준다. 쓰는 사람이 편하도록 만드는 쪽이 고생한, 서비스 정신이 좋은 프레임워크다. 그러니 직접 `request`에서 꺼내기보다 **스프링이 넣어 주는 방식**을 쓰는 것이 스프링을 제대로 활용하는 것이다.

### 인증에 성공했을 때만 세션에 담는다

```java
@PostMapping("/login")
public String login(String username, String password, HttpSession session) {

    boolean isAuthenticated = authenticationService.authenticate(username, password);

    if (isAuthenticated) {
        session.setAttribute("point", 1000);   // 이 사용자의 포인트는 1000
        return "redirect:/";
    }

    return "redirect:/login?error=true";
}
```

세션에 사용자 정보를 담는 것은 **인증이 성공했을 때만** 해야 하므로 `if` 안에 둔다. 담는 순간 사용자를 식별하는 **세션 키(세션 ID)**가 만들어지고, 이것이 쿠키(`JSESSIONID`)로 사용자에게 전달된다. 로그인 후 Network 탭의 응답 헤더(`Set-Cookie`)와 Application 탭의 쿠키 목록에서 직접 확인해 본다.

> 원문 바로잡기 — 강의에서는 "세션에 값을 **저장하는 순간** 세션 ID가 발급되고, 저장한 적이 없으면 발급되지 않는다"고 했다. 정확히는 세션 객체가 **만들어지는 순간**, 즉 `request.getSession()`이 처음 호출될 때 발급된다. 그런데 매개변수에 `HttpSession`을 선언하면 스프링이 메서드를 호출하기 **전에** `getSession()`을 불러 주므로, 위 코드는 **로그인에 실패해도** 세션이 만들어지고 `JSESSIONID`가 발급된다. 정말 성공했을 때만 만들고 싶다면 `HttpServletRequest`를 받아서 `if` 안에서 `request.getSession()`을 호출하면 된다.

## 8. 한 줄 정리

- 로그인 흐름: **GET**으로 폼을 받고 **POST**로 제출 → 인증 판단은 **서비스**가, 이후 안내는 **컨트롤러**가 한다.
- **POST는 페이지를 주지 않는다.** `redirect:`로 302와 `Location`을 보내 다음 갈 곳을 안내한다. 실패하면 `?error=true`처럼 상태를 함께 보낸다.
- 웹은 요청이 끝나면 연결이 끊겨 **서버가 사용자를 기억하지 못한다.** IP로도 구분할 수 없다.
- **쿠키**는 서버가 브라우저에 맡겨 두는 작은 데이터다. Domain·Path가 맞는 요청마다 자동으로 실려 가고, 기한이 없으면 브라우저를 닫을 때 사라진다. `HttpOnly`는 스크립트가 읽지 못하게 한다.
- 쿠키 하나로 인증하면 **훔치는 순간 사칭**이 가능하다. 자리를 비울 때는 로그아웃한다.
- **세션**은 사용자 정보를 서버에 두고 **세션 ID만 쿠키로** 주고받는 방식이다. "세션"은 그 데이터를 쓸 수 있는 기간이라는 뜻이다.
- 서버 저장소는 page·request·session·application 네 가지이고 범위만 다르다. 개인 데이터는 session, 공용 데이터는 application에 둔다.
