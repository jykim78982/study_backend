# 트랜잭션 전파 — 서비스가 서비스를 호출할 때

`@Transactional`의 기본 기능인 **원자성(롤백)**은 이미 확인했다. `@Transactional`에는 추가 옵션이 있는데, 그중 중요한 것이 **전파(propagation)**와 **고립(isolation, 격리 수준)**이다. 이 노트는 전파 옵션을 다룬다. 격리 수준은 강의에서 학습 주제로 언급만 하고 구체적으로 다루지 않았다. 전파 옵션은 **서비스가 다른 서비스를 호출할 때** 필요한 옵션이다.

## 1. 다시 보기 — 트랜잭션은 누가, 어떻게 처리하나

### 트랜잭션 기능은 DB에 있다

트랜잭션은 **논리적인 작업 단위(업무 단위)**다. 이 단위는 쪼개지면 안 되고(원자성), 일관성이 있어야 하고, 고립되어야 하며, 영구히 저장되어야 한다(ACID).

이것을 실제로 처리하는 것은 스프링이 아니라 **데이터베이스**다. DB는 SELECT·INSERT·UPDATE·DELETE를 하나씩 바로 반영할 수도 있지만, `BEGIN` ~ `COMMIT`으로 묶어서 **모두 확인한 다음 한 번에** 반영하는 기능을 제공한다.

우리는 DB를 자바(JDBC)로 쓰므로, JDBC API에도 그 기능이 있어야 한다. 있다.

```java
Connection conn = dataSource.getConnection();
conn.setAutoCommit(false);        // 바로 반영하지 말고 모아 둬 (트랜잭션 시작)
try {
    // SELECT, UPDATE, DELETE ...
    conn.commit();                // 문제없으면 한 번에 반영
} catch (Exception e) {
    conn.rollback();              // 오류가 나면 모아 둔 것을 버린다
}
```

### 리포지토리를 만들면서 생긴 문제

리포지토리는 왜 만들었을까? 리포지토리가 없으면 서비스가 **어떤 DB를 쓰는지, 어떤 SQL을 써야 하는지** 같은 데이터 소스의 사정에 영향을 받는다. 리포지토리는 그 데이터 소스를 숨겨서, 서비스가 **업무에만 몰입**할 수 있게 재료를 대신 구해 오는 역할을 한다.

> **총판 비유**: 음식점을 차리면 모든 재료상의 연락처와 주문 방법을 제각각 알아야 했다. 그런데 **총판**이 생겨서 "재료는 내가 구해 줄게, 나한테만 말해"라고 하면 주문 방법이 하나로 단순해진다. 리포지토리가 총판이다. 서비스는 리포지토리에게 **자바로 말하고 자바로 받으면** 된다. 원재료를 어디서, 어떤 기술로 가져오는지는 몰라도 된다.

그런데 리포지토리를 쓰면서 문제가 생겼다. 서비스가 리포지토리 A로 INSERT를 하고 리포지토리 B로 DELETE를 하면, 각 리포지토리 메서드가 **따로 연결하고, 따로 커밋하고, 끊어 버린다.** 두 작업이 커넥션을 공유하지 않으니 하나로 묶어 커밋할 수 없다. B에서 오류가 나도 A는 "저는 이미 커밋했는데요"가 된다. 이미 저장된 것은 되살릴 방법이 없다.

해결 방법은 둘 중 하나다.

1. 리포지토리를 버리고 서비스에서 JDBC를 직접 써서 `BEGIN` ~ `COMMIT`을 다 한다. → 리포지토리를 포기하기 어렵다.
2. 리포지토리를 쓰면서 **커넥션을 공유**하게 만든다. → `@Transactional`이 하는 일이다.

### @Transactional이 붙으면 일어나는 일

`@Transactional`이 붙으면 AOP 방식으로 메서드의 **앞머리와 뒷머리**에 처리가 붙는다.

1. 설정 파일의 연결 정보로 만들어진 **`DataSource`** 객체가 IoC 컨테이너에 있다. 모든 리포지토리는 여기서 `getConnection()`으로 커넥션을 얻는다.
2. 앞머리에서 커넥션을 하나 얻어 `setAutoCommit(false)`를 하고, 이 커넥션을 **현재 스레드가 공유하는 커넥션**으로 담아 둔다.
3. 그 스레드 안에서 리포지토리들이 커넥션을 얻으면, 새 커넥션이 아니라 **이 공유 커넥션**을 받는다. 그래서 아직 DB에 반영되지 않은 상태로 작업이 쌓인다.
4. 뒷머리에서 오류가 없으면 `commit()` → 전체가 한 번에 반영되고, 오류가 났으면 `rollback()` → 전체가 원래대로 돌아간다.

```
@Transactional function1()
 ├─ [앞] getConnection() → setAutoCommit(false) → 스레드에 공유 커넥션으로 등록
 ├─ repoA.update()  → getConnection() → 공유 커넥션을 받음
 ├─ repoB.delete()  → getConnection() → 같은 공유 커넥션을 받음
 └─ [뒤] 정상: commit() / 오류: rollback()
```

실제 코드를 하나하나 들여다볼 필요는 없다. 자동차 기어가 어떻게 맞물리는지 몰라도, 기어의 **역할**과 **조작법**을 알면 운전할 수 있는 것과 같다. "그렇게 동작하겠구나" 정도면 충분하다.

## 2. @Transactional은 어디에 붙이나 — 서비스에만

### 리포지토리에는 붙이지 않는다

리포지토리 메서드는 INSERT, UPDATE, DELETE, SELECT처럼 **단일 업무**다. 트랜잭션은 **두 개 이상의 작업**을 하나로 묶을 때 필요하다. 리포지토리에 `@Transactional`을 붙였다는 것은 그 리포지토리 메서드가 단일 업무가 아니라는 뜻이고, 이는 **업무 로직을 리포지토리에 넣었다**는 신호다. 리포지토리에 붙어 있는 것을 보면 "왜 붙였지?" 하고 의심해야 한다.

> **추가 설명 — Spring Data JPA 리포지토리에는 이미 붙어 있다**: 우리가 만드는 리포지토리 인터페이스에 직접 붙이지 않을 뿐, 그 구현체인 `SimpleJpaRepository`에는 `@Transactional`이 붙어 있다(클래스에는 `readOnly = true`, `save`·`delete` 같은 변경 메서드에는 일반 `@Transactional`). 그래서 서비스에 트랜잭션이 없어도 `save()` 하나는 자기 트랜잭션으로 실행되고, 서비스에 트랜잭션이 있으면 기본 전파 옵션(REQUIRED)에 따라 **서비스의 트랜잭션에 참여**한다. "리포지토리에 붙이지 않는다"는 것은 **우리가 업무 로직 단위로 붙이지 않는다**는 뜻이다.

### 컨트롤러에도 붙이지 않는다

컨트롤러에 붙여도 오류는 나지 않는다. 하지만 `@Transactional`은 **업무 로직**에 쓰는 것이고, 업무 로직은 서비스에 있다. 컨트롤러에 붙인다면 업무 로직을 잘못 이해한 것이다.

| 계층 | `@Transactional` | 이유 |
|---|---|---|
| Controller | ❌ | 서빙만 한다. 업무 로직이 없다 |
| **Service** | ⭕ | 여러 리포지토리 작업을 묶는 **업무 로직 단위** |
| Repository | ❌ (직접 붙이지 않음) | 단일 작업이다 |

다만 현실에서는 "서비스는 손대지 말래"처럼 제약이 있어서, 알면서도 리포지토리에 업무 로직 비슷한 것을 넣는 예외가 생기기도 한다. 이런 예외가 쌓이면 오래 유지보수한 프로그램이 **누더기**가 되고, 결국 새로 만들어야 하는 날이 온다. 원칙은 **서비스에 붙인다**이다.

### DB가 아닌 작업은 롤백되지 않는다

서비스가 리포지토리 세 개를 쓰는데, 그중 하나는 DB가 아니라 **파일**에 쓰는 리포지토리라면? `@Transactional`을 붙이면 파일 쓰기도 롤백될까?

**절대 롤백되지 않는다.** 트랜잭션은 **DB가 지원하는 기능**이고 스프링은 그것을 이용할 뿐이므로, 파일 쓰기나 외부 API 호출 같은 작업은 트랜잭션에서 빠진다. 트랜잭션으로 묶고 싶다면 모두 DB에 두어야 한다. 이것 때문에라도 DB를 쓰는 경우가 많다.

그래서 파일이나 외부 API가 섞이면 현장에서는 골치가 아프다. 정해진 해법은 없고 회사마다 방식이 다르다.

- 에러가 난 부분을 파일 등에 기록해 두고, 나중에 사람이 확인해서 지운다.
- 에러가 날 때 실행될 별도의 보상 로직을 만들어 트리거처럼 달아 둔다.

> **추가 설명 — 커밋된 뒤에 실행하기**: 메일 발송이나 파일 저장처럼 되돌릴 수 없는 작업은, 트랜잭션이 **성공적으로 커밋된 다음에** 실행하도록 미루는 방법을 많이 쓴다. 스프링에서는 `@TransactionalEventListener`(기본값 `AFTER_COMMIT`)로 "커밋이 끝나면 이 작업을 해라"를 걸 수 있다. 그러면 DB가 롤백된 경우에는 파일이나 메일 작업이 아예 실행되지 않는다.

## 3. 서비스가 서비스를 호출해도 되나?

**사용할 수 있다.** 하지만 큰 위험이 있어 조심해서 써야 한다.

A 서비스가 B 서비스를 쓰고, B 서비스가 다시 A 서비스를 쓰면 **순환 구조**가 된다. 부품이 제품이 되고 제품이 부품이 되는, "너는 나의 상사이고 나는 너의 부하"인 이상한 관계다.

### 서비스도 주인공이 있다

테이블(엔티티)마다 그것이 **주인공인 페이지**가 있고, 그 페이지를 담당하는 서비스가 있다. 그래서 서비스는 최소한 테이블 수만큼 있다. 각 서비스는 자기 주인공뿐 아니라 **곁다리**도 함께 서비스한다. 그러다 보면 "이건 저 서비스에 이미 있는데 굳이 내가 또 만들어야 해?"라는 상황이 생기고, 다른 서비스를 쓰게 된다.

### 방향 규칙 — 부모 쪽(위)으로만

엔티티에는 부모와 자식이 있다.

- **Key 엔티티(KE)**: 문장의 주어나 목적어에 해당하는, 원래부터 관리 대상이거나 관리 주체인 엔티티. 사용자, 메뉴, 카테고리 등. **최상위 부모**이며 자식이 되지 않는다.
- **행위(관계) 엔티티(AE)**: Key 엔티티들이 **행위**를 해서 만들어지는 엔티티. 찜, 주문, 결제 등. 행위에는 **순서**가 있다. 주문을 해야 결제를 한다.

```
[사용자] [메뉴]      ← Key 엔티티 (부모)
    └──┬──┘
     [찜]  [주문]    ← 행위 엔티티
             │
           [결제]    ← 다음 행위 (자식)
```

결제 내역 페이지를 만들다 보면 **주문 내역**도 함께 보여 줘야 할 때가 있다. 이때 결제 서비스가 주문 서비스를 쓰는 것은 **자식 → 부모(위) 방향**이라 괜찮다.

반대로 주문 내역을 보여 주면서 결제 내역을 가져올 일은 일반적으로 없다. 주문할 때는 아직 결제가 일어나지 않았기 때문이다. 메뉴가 없으면 찜이 있을 수 없으니, 메뉴 페이지에서 찜 내용을 보여 줄 일도 없다. **부모가 자식을 가져와야 한다면, 페이지를 잘못 만들고 있는 것은 아닌지** 의심해 봐야 한다.

| 방향 | 가능 여부 |
|---|---|
| 자식 서비스 → 부모 서비스 (결제 → 주문) | ⭕ 단방향이면 사용 가능 |
| 부모 서비스 → 자식 서비스 (주문 → 결제) | ❌ 역주행. 양방향(순환)이 될 위험 |

물론 사용자가 꼭 원하는 기능 때문에 예외가 생길 수 있고, 그때는 꼼수가 필요하다. 위 내용은 **가이드 기준**이다.

> **추가 설명 — 순환 참조는 시작부터 막힌다**: 두 서비스가 생성자 주입으로 서로를 참조하면, 스프링 부트는 애플리케이션 시작 시 `The dependencies of some of the beans in the application context form a cycle` 오류를 내고 실행을 거부한다(스프링 부트 2.6부터 순환 참조가 기본적으로 금지되었다). 방향 규칙을 지키면 이 문제가 생기지 않는다.

## 4. 전파 옵션이 필요한 이유

서비스가 서비스를 호출하면 이런 상황이 된다.

```
[Controller] → @Transactional A서비스.method()      ← 여기서 공유 커넥션 생성
                 ├─ repo.save()                       ← 공유 커넥션 사용
                 └─ @Transactional B서비스.method()   ← 어? 나도 @Transactional인데…
                      └─ repo.save()                     커넥션을 새로 만들어? 같이 써?
```

A가 이미 트랜잭션을 시작해서 공유 커넥션을 만들어 두었는데, 호출된 B에도 `@Transactional`이 붙어 있다. B가 앞머리에서 커넥션을 **새로** 만들어 `setAutoCommit(false)`를 하면 커넥션이 두 개가 되어 하나의 트랜잭션이 유지되지 않는다. **A의 트랜잭션을 B에게 전파할 것이냐, 하지 않을 것이냐**를 정하는 것이 **전파 옵션**이다.

- 서비스가 서비스를 호출하지 않는다면(컨트롤러 → 서비스 → 리포지토리만 있다면) 전파 옵션은 **신경 쓸 필요가 전혀 없다.** 컨트롤러가 서비스를 호출할 때는 트랜잭션(공유 커넥션)이 없으므로, 서비스가 새로 만들어서 쓰고 끝내면 된다.
- 전파 옵션은 **호출당하는 쪽(B)**에 설정한다. 처음 시작하는 쪽은 어차피 트랜잭션을 새로 시작해야 하므로 고민할 것이 없다. "트랜잭션을 물고 들어왔을 때 **나는** 어떻게 할 것인가"를 정하는 옵션이다.

## 5. 전파 옵션 종류

```java
@Transactional(propagation = Propagation.REQUIRED)   // 기본값이라 생략해도 같다
public void saveRequired(...) { ... }
```

| 옵션 | 호출한 쪽에 트랜잭션이 **있으면** | **없으면** |
|---|---|---|
| **REQUIRED** (기본값) | 그 트랜잭션에 **참여**한다 (같은 커넥션) | 새로 만든다 |
| **REQUIRES_NEW** | 기존 트랜잭션을 **잠시 멈추고**, 새 트랜잭션을 만든다 | 새로 만든다 |
| SUPPORTS | 참여한다 | 트랜잭션 없이 실행한다 |
| MANDATORY | 참여한다 | **예외**를 던진다 |
| NOT_SUPPORTED | 기존 트랜잭션을 멈추고 트랜잭션 없이 실행한다 | 트랜잭션 없이 실행한다 |
| NEVER | **예외**를 던진다 | 트랜잭션 없이 실행한다 |
| NESTED | 기존 트랜잭션 안에 **세이브포인트**를 두고 실행한다. 내부만 부분 롤백 가능 | 새로 만든다 |

수업에서 다룬 핵심은 **REQUIRED**와 **REQUIRES_NEW**다.

### 5-1. REQUIRED — "만든 게 있으면 같이 쓸게"

```
컨트롤러가 직접 호출:   [C] → B.method()  → 물고 온 게 없으니 B가 새로 만든다
서비스가 호출:          [C] → A → B.method() → A가 만든 공유 커넥션을 같이 쓴다 (참여)
```

A와 B의 작업이 **하나의 커넥션, 하나의 트랜잭션**으로 묶인다. 어디서 오류가 나든 **전체가 한 번에 롤백**된다.

### 5-2. REQUIRES_NEW — "네가 만들었어도 나는 새로 만들 거야"

```
A.method()  ── 커넥션①로 트랜잭션 시작
 ├─ repo ①  ─┐
 ├─ repo ②  ─┤ 커넥션①
 ├─ B.method() (REQUIRES_NEW)
 │    ├─ 커넥션①을 잠시 멈춤(suspend)
 │    ├─ 커넥션②로 새 트랜잭션 시작
 │    ├─ repo ③ ─ 커넥션②
 │    └─ 커넥션② commit  ← B의 작업은 여기서 확정
 │    └─ 커넥션① 다시 이어서
 ├─ repo ④  ─┐
 └─ repo ⑤  ─┘ 커넥션① → 끝에서 commit 또는 rollback
```

B는 자기만의 단위로 **먼저 커밋해 버리고**, A는 멈췄던 자기 트랜잭션을 이어 간다.

| 상황 | 결과 |
|---|---|
| B는 성공, 그 뒤 A(④, ⑤)에서 오류 | A만 롤백. **B(③)는 이미 커밋되어 롤백되지 않는다** |
| B에서 오류 → 예외가 A로 전파되어 A도 실패 | B 롤백, A도 롤백 (전체 실패) |
| B에서 오류 → A가 `try-catch`로 잡고 계속 진행 | B만 롤백, A는 정상 커밋 가능 |

"이런 일이 언제 필요하지?"는 **업무 로직에 따라** 다르다. 지금은 이런 옵션이 있다는 것만 알고, 나중에 서비스를 만들다가 "이런 경우에 쓸 수 있겠네"라고 떠올리면 된다.

> **추가 설명 — REQUIRES_NEW가 쓰이는 예**: 주문이 실패해도 **실패 이력(로그)은 남겨야** 하는 경우가 대표적이다. 이력을 저장하는 서비스 메서드를 REQUIRES_NEW로 두면, 바깥 주문 트랜잭션이 롤백되어도 이력은 별도로 커밋되어 남는다. 단, 새 트랜잭션은 **커넥션을 하나 더** 쓰므로, 동시 요청이 많으면 커넥션 풀이 빨리 바닥날 수 있다.

## 6. 강의 예제 — 카테고리 서비스가 메뉴 서비스를 호출

> **주의**: 이 예제는 전파 옵션을 보여 주기 위한 **억지 예제**이고, 방향 규칙을 **어기고 있다.** 카테고리가 부모, 메뉴가 자식인데 **부모(카테고리 서비스)가 자식(메뉴 서비스)을 쓰는 역주행**이다. 이 코드를 보고 "이렇게 하는구나"라고 오해하면 안 된다.

카테고리를 하나 등록하면서 메뉴도 같이 넣는 예제다.

```java
@Service
public class CategoryService {

    private final CategoryRepository categoryRepository;
    private final MenuService menuService;            // 서비스가 서비스를 사용 (역주행)

    // 생성자 생략

    @Transactional
    public Category createWithMenu(String categoryName, String categorySlug,
                                   String menuName, int menuPrice) {
        Category category = categoryRepository.save(new Category(categoryName, categorySlug));

        try {
            menuService.saveRequired(menuName, menuPrice);   // 전파 옵션이 REQUIRED인 메서드
        } catch (Exception e) {
            System.out.println("메뉴 저장 실패: " + e.getMessage());
        }
        return category;
    }
}
```

```java
@Service
public class MenuService {

    @Transactional(propagation = Propagation.REQUIRED)    // 기본값. 생략해도 같다
    public void saveRequired(String name, int price) {
        // 메뉴 저장, 조건에 따라 예외 발생
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveRequiresNew(String name, int price) {
        // 같은 로직, 전파 옵션만 다름
    }
}
```

**누가 누구를 쓰고 있나?** 카테고리 서비스가 메뉴 서비스를 쓰고 있다. 그러면 전파 옵션은 **호출당하는 메뉴 서비스** 쪽에 설정한다.

**`@Transactional`이 없다면**: 카테고리는 저장되고, 메뉴 저장에서 오류가 나도 카테고리는 롤백되지 않는다. 그래서 카테고리 서비스 메서드에 `@Transactional`을 붙인다.

> **추가 설명 — REQUIRED인데 try-catch로 잡으면 커밋될까?**: 위 예제처럼 REQUIRED로 참여한 메뉴 서비스에서 예외가 나고, 카테고리 서비스가 그 예외를 `try-catch`로 잡아 정상 종료하면 "카테고리는 커밋되겠지"라고 생각하기 쉽다. 그렇지 않다. 같은 트랜잭션에 참여한 메뉴 서비스의 프록시가 예외를 보는 순간 그 트랜잭션 전체에 **"롤백만 가능(rollback-only)"** 표시를 해 둔다. 그래서 카테고리 서비스가 끝나며 커밋을 시도하면 `UnexpectedRollbackException`이 발생하고 **카테고리까지 롤백**된다. 하나의 트랜잭션은 일부만 커밋할 수 없기 때문이다.
>
> | 메뉴 서비스 옵션 | 메뉴에서 예외 + 카테고리가 try-catch로 잡음 |
> |---|---|
> | REQUIRED | 전체 롤백 + `UnexpectedRollbackException` |
> | REQUIRES_NEW | 메뉴만 롤백, **카테고리는 커밋** |
>
> "메뉴가 실패해도 카테고리는 남기고 싶다"면 REQUIRES_NEW를 써야 한다. 이것이 두 옵션의 차이가 실제로 드러나는 지점이다.

> **추가 설명 — 같은 클래스 안에서는 전파 옵션이 무시된다**: 전파 옵션은 **프록시를 거쳐 호출될 때만** 적용된다. 카테고리 서비스 안에서 `this.saveSomething()`처럼 같은 클래스의 다른 메서드를 부르면, 그 메서드에 REQUIRES_NEW를 붙여도 프록시를 거치지 않아 새 트랜잭션이 만들어지지 않는다. 다른 빈(서비스)을 통해 호출해야 한다.

## 7. 한 줄 정리

- 트랜잭션 기능은 **DB**에 있고, 스프링은 `@Transactional`로 서비스 메서드 안의 리포지토리들이 **공유 커넥션**을 쓰게 만들어 준다.
- `@Transactional`은 **서비스에만** 붙인다. 리포지토리는 단일 작업, 컨트롤러는 서빙만 한다.
- 트랜잭션은 **DB 작업만** 되돌린다. 파일·외부 API는 롤백되지 않는다.
- 서비스가 서비스를 호출할 수는 있지만, **자식 → 부모(위) 방향, 단방향**으로만 쓴다.
- **전파 옵션**은 서비스가 서비스를 호출할 때, **호출당하는 쪽**에 정한다. 기본값 **REQUIRED**는 "있으면 참여, 없으면 생성", **REQUIRES_NEW**는 "항상 새로 만들고 먼저 커밋"이다.
