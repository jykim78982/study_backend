# API URL 설계 — 페이지 단위 스케치와 주인공·곁다리 규칙

화면 하나를 만들 때 API가 몇 개 필요한지 어떻게 가늠하는지, 그리고 여러 테이블이 한 화면에 섞여 나올 때 URL을 어떤 기준으로 정하는지를 정리한다.

## 1. 페이지를 먼저 스케치해야 API 개수가 보인다

머릿속 상상만으로 API를 설계하면 팀원끼리 서로 다른 그림을 그리게 되어 오해가 생기기 쉽다. 그래서 화면을 만들기 전에 **UI 스케치(와이어프레임)**를 먼저 그려본다. 형식에 얽매일 필요는 없다 — 그림판으로 대충 선을 긋는 정도로도 충분하다. 설계·기획은 그 자체가 목적이 아니라 구현을 원활하게 하기 위한 끄적거림일 뿐이므로, 여기에 너무 많은 시간과 비용을 쓰면 정작 구현할 에너지가 부족해진다.

페이지 하나와 API 하나는 **1:1이 아니다.** 페이지 하나를 만드는 데 필요한 API 개수는, 그 화면을 이루는 **컴포넌트(콘텐츠를 담은 섹션)의 수**로 가늠할 수 있다. 다만 컴포넌트 수와 API 수가 항상 정확히 일치하지는 않는다 — 예를 들어 "가격대 필터"처럼 자주 바뀌지 않고 데이터베이스로 관리할 필요가 없는 정적인 값은 그냥 화면(마크업)에 박아두면 되므로 별도 API가 필요 없다. 반대로 카테고리처럼 언제든 추가·변경될 수 있는 값은 데이터베이스에서 가져와야 하므로 API가 필요하다. 그래서 컴포넌트를 나열한 뒤 "이 컴포넌트가 정말 서버 데이터가 필요한가"를 하나씩 따져야 실제 API 개수가 나온다.

## 2. 페이지 주소와 API 주소는 다른 것이다

메뉴 목록 페이지의 **페이지 URL**은 `/MenuList`처럼 사용자가 브라우저에서 보는 주소다. 이때 상세 페이지로 이동하는 URL에는 `아이디`나 `슬러그(slug)`를 쓸 수 있는데, 선택 기준은 다음과 같다.

- 검색엔진에 노출될 필요가 없는 페이지라면 **아이디**로 충분하다.
- 검색엔진(SEO)에 노출되어야 하는 페이지라면 **슬러그**가 낫다. 슬러그를 쓰면 주소 자체에 메뉴명(또는 키워드)이 그대로 드러나서 가독성이 좋아지고, 검색엔진이 그 단어를 URL에서부터 인식하기 때문에 검색 노출에도 유리하다.

이 페이지 URL과는 별개로, 그 페이지가 화면을 채우기 위해 호출하는 **API URL**을 따로 설계해야 한다. 이 둘을 혼동하면 안 된다 — 페이지 이동은 하이퍼링크(라우팅)의 문제이고, API 호출은 데이터를 가져오는 문제다.

## 3. "주인공"과 "곁다리" — API URL을 정하는 핵심 규칙

한 화면에 여러 테이블의 데이터가 함께 나올 때, 가장 먼저 판단해야 할 것은 **"이 화면의 주인공이 누구인가"**다. 조인(JOIN)에서 "어느 테이블을 주인공(기준)으로 두고 어느 테이블을 곁들일 것인가"를 먼저 정해야 하는 것과 같은 원리다.

- 메뉴 목록 페이지라면 주인공은 **메뉴**다. 이 화면에 카테고리가 함께 보이더라도, 카테고리는 이 화면에서는 **곁다리(카메오)**일 뿐이다.
- 곁다리로 등장하는 리소스는 다른 여러 화면에도 반복해서 나타난다 — 카테고리는 메뉴 목록 화면뿐 아니라 랜딩 페이지, 관리자 페이지 등 여러 곳에 카메오로 출연한다. 그래서 카테고리를 "항상 독립된 최상위 API(`/categories`)"로만 다루면, 그 API가 어느 화면에서 왜 필요한지 URL만 보고는 알 수 없게 된다.

**규칙**: URL은 항상 **주인공을 앞에 두고, 곁다리는 주인공 뒤에 하위 경로로 붙인다.**

```
GET /api/v1/menus              # 주인공 단독 — 메뉴 목록
GET /api/v1/menus/categories   # 메뉴가 주인공인 화면에서 곁다리로 등장하는 카테고리
```

이렇게 하면 URL만 보고도 "메뉴가 주인공인 컨텍스트에서 쓰이는 카테고리 조회"라는 것이 명확해진다. 이 두 API 모두 구현 주체는 같은 컨트롤러(메뉴 컨트롤러)가 맡는다.

**API에는 항상 버전을 명시**한다(`/api/v1/...`). 나중에 API 규격이 바뀌어도 이전 버전(`v1`)을 유지한 채 새 버전(`v2`)을 나란히 둘 수 있기 때문이다.

## 4. 상세 페이지 — 여러 테이블이 섞여도 주인공은 하나다

상세 페이지 하나에도 실제로는 여러 테이블이 관여한다. 화면에 보이는 요소들을 하나씩 따져보면 대략 이렇게 나뉜다.

- **메뉴 테이블에 있는 것**: 이름, 가격, 설명처럼 메뉴 본연의 속성.
- **별도 테이블로 빠지는 것(1:N 관계)**: 이미지가 여러 장이면 이미지 테이블, 옵션(사이즈 등)이 여러 개면 옵션 테이블 — 한 컬럼에 여러 값을 담을 수 없다는 1차 정규화 원칙과 같은 이유다.
- **완전히 다른 성격의 목록**: "함께 보면 좋은 메뉴(추천 메뉴)"는 AI가 자동으로 골라주는 것이 아니라, **관리자가 직접 선별해서 관리하는 별도의 추천 테이블**에서 나온다.
- **로그인한 사용자에 따라 달라지는 것**: "좋아요" 여부처럼 "내가 좋아한 적이 있는가"를 나타내는 데이터는 그 슬러그(메뉴) 자체의 속성이 아니라, **로그인 여부와 회원 정보에 의존하는 데이터**다.

상세 페이지도 같은 규칙을 따른다 — 먼저 **주인공을 찾는다.** 목록 페이지와 달리 상세 페이지의 주인공은 "메뉴 목록"이 아니라 **메뉴 하나(슬러그로 식별되는 개별 메뉴)**다.

```
GET /api/v1/menus/{slug}               # 주인공 — 메뉴 상세
GET /api/v1/menus/{slug}/images        # 곁다리 — 이미지 목록 (복수형)
GET /api/v1/menus/{slug}/options       # 곁다리 — 옵션 목록
GET /api/v1/menus/{slug}/recommends    # 곁다리 — 추천 메뉴 목록
```

주인공(`/menus/{slug}`)을 물고, 그 뒤에 곁다리들을 이어 붙이는 패턴이 반복된다. 이미지·옵션·추천처럼 그 자체로 "여러 개"를 나타내는 곁다리는 복수형으로 쓴다.

## 5. 컴포넌트 단위로 API를 쪼개서 독립적으로 가져올 수도 있다

곁다리로 등장하는 요소 중에는, 화면상 별도의 컴포넌트로 완전히 분리해서 **그 컴포넌트가 자기 데이터를 스스로 가져오게** 만들 수도 있다. 예를 들어 "추천 메뉴" 섹션은 상세 페이지 API에 얹혀 함께 내려받지 않고, 별도 컴포넌트로 떼어내어 그 컴포넌트가 독립적으로 `/api/v1/menus/{slug}/recommends`를 호출하게 만들 수 있다. "너는 네 데이터를 네가 알아서 가져오고, 나는 너를 조립만 하겠다"는 방식이다.

## 6. 사용자별로 달라지는 데이터는 따로 관리한다

"좋아요" 여부처럼 **로그인 상태와 회원 정보에 따라 내용이 달라지는 데이터**는, 메뉴 자체의 데이터와 한 덩어리로 묶지 않고 별도로 취급한다. 로그인하지 않은 사용자에게는 이 값 자체가 존재할 수 없고(체크되지 않은 상태), 로그인한 사용자에게는 "이 회원이 이 메뉴를 좋아한 적이 있는가"를 조회해야 하므로, 다른 곁다리 데이터와는 조회 조건 자체가 다르다. 그래서 이런 데이터는 별도의 API(또는 별도 컴포넌트)로 분리해서 관리하는 것이 자연스럽다.

## 7. 정리

| 판단 기준 | 규칙 |
|---|---|
| API 개수 산정 | 화면의 컴포넌트(섹션) 수를 기준으로 삼되, DB 관리가 필요 없는 정적 값은 제외한다 |
| 페이지 URL vs API URL | 페이지 이동(라우팅)과 데이터 조회(API)는 서로 다른 주소 체계다 |
| 상세 페이지 식별자 | SEO 노출이 필요 없으면 ID, 필요하면 슬러그 |
| API 버전 | URL에 `/api/v1/...`처럼 버전을 항상 명시한다 |
| 주인공/곁다리 | 화면의 주인공 리소스를 URL 최상위에 두고, 곁다리는 주인공 뒤에 하위 경로로 붙인다 |
| 곁다리가 여러 화면에 출연 | 곁다리를 독립된 최상위 API로 만들지 않고, 주인공마다 하위 경로로 각각 노출한다 |
| 사용자별 데이터 | 로그인 여부·회원 정보에 따라 달라지는 데이터는 별도 API/컴포넌트로 분리한다 |

결국 API URL 설계도 "유즈케이스 단위로 DTO를 나눈다"는 원칙과 같은 뿌리를 갖는다 — **화면이 요구하는 실제 시나리오(누가 주인공이고, 누가 그 컨텍스트에서만 곁다리로 필요한가)**를 먼저 파악한 뒤에야, 그에 맞는 URL과 API 개수가 정해진다.
