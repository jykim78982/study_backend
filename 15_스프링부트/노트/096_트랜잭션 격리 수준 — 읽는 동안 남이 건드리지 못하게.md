# 트랜잭션 격리 수준 — 읽는 동안 남이 건드리지 못하게

ACID의 I, **고립성(격리성, Isolation)**을 다룬다. `@Transactional(isolation = ...)`으로 정하는 격리 수준이 무엇을 막아 주는지, 왜 수준이 높을수록 느려지는지, 그리고 DBMS마다 기본값이 어떻게 다른지를 정리한다. 실습 없이 **개념으로** 알아 두면 되는 내용이다.

## 1. 목록만 가져오는데 트랜잭션이 필요할까?

메뉴 목록을 가져오는 서비스에는 트랜잭션이 필요할까? "입력이나 수정은 에러가 날 수 있지만, 가져오기만 하는데 무슨 에러가?"라고 생각하기 쉽다. 답은 **절대적으로 필요하다**이다.

서비스는 주인공 데이터만 가져오지 않는다. **곁다리** 데이터도 가져와서 조립한다.

```
[A 컨트롤러] → [A 서비스] ─┬─ A 리포지토리 (주인공: 메뉴)
                           ├─ B 리포지토리 (곁다리: 카테고리)
                           └─ C 리포지토리 (곁다리)      ← 조립하는 동안
                                                            [C 서비스]가 이 데이터를 지우거나 고친다면?
```

- 내가 한창 조립하는 동안 다른 서비스가 C 데이터를 **지워 버렸다.** 나는 모르고 조립해서 응답했다. 사용자가 그 항목을 클릭하면 404나 500 에러가 난다.
- 처음 가져올 때는 아메리카노가 4,500원이었는데, 다른 작업을 하고 다시 가져오니 5,000원이다. 같은 작업 안에서 데이터가 달라졌다.

이런 일을 막으려면 "**내가 작업하는 동안 너희들 건드리지 마**"가 필요하다. 내 작업이 다른 작업의 영향을 받지 않게 떼어 놓는 것, 이것이 **고립(격리)**이다.

### 전파 옵션과 다른 점

| | 전파 옵션 | 격리 수준 |
|---|---|---|
| 필요한 곳 | 다른 서비스에게 호출될 수 있는 **도메인 부모** 서비스 | 위치와 상관없이 **트랜잭션마다 개별적으로** |
| 정하는 것 | 트랜잭션을 이어서 쓸지, 새로 만들지 | 다른 트랜잭션의 변경을 어디까지 볼지 |

## 2. 격리 수준 옵션

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
public List<MenuResponse> getMenus() { ... }
```

| 옵션 | 의미 |
|---|---|
| `DEFAULT` | 아래 넷 중 **사용하는 DBMS의 기본값**을 쓴다 (스프링 기본값) |
| `READ_UNCOMMITTED` | 커밋되지 않은 데이터도 읽는다 |
| `READ_COMMITTED` | **커밋된** 데이터만 읽는다 |
| `REPEATABLE_READ` | 트랜잭션 안에서 **다시 읽어도 같은** 데이터를 읽는다 |
| `SERIALIZABLE` | 트랜잭션들이 **한 줄로 차례대로** 실행된 것처럼 처리한다 |

`DEFAULT`가 따로 있는 이유는 **DBMS마다 기본값이 다르기 때문**이다. 트랜잭션은 DBMS의 기능이라서, DBMS가 트랜잭션을 지원하지 않으면 이 옵션은 아무 의미가 없다. 특정 수준을 직접 지정하면 DBMS와 상관없이 그 수준을 쓰고, `DEFAULT`면 DBMS가 정한 수준을 따른다.

격리 수준은 **읽기**에 대한 옵션이다. "커밋된 것만 읽는다", "다시 읽어도 같은 것을 읽는다"처럼, 다른 트랜잭션이 바꾸는 데이터를 **내가 읽을 때** 무엇을 보게 할지를 정한다.

## 3. 읽기 이상 현상 세 가지

### 커밋 전 데이터는 어디에 있나

트랜잭션을 지원하는 DBMS는 변경 내용을 원본 데이터에 바로 확정하지 않는다. 커밋 전까지는 **아직 확정되지 않은 상태**로 두었다가, **커밋**하는 순간 반영을 확정한다. 한 번 커밋되면 롤백할 수 없다.

> **추가 설명**: 실제 구현은 DBMS마다 다르다. Oracle·MySQL은 원본을 고치되 이전 값을 **언두(undo) 영역**에 보관하고, PostgreSQL은 행의 **새 버전**을 따로 만들어 둔다. 어느 쪽이든 "커밋 전 데이터와 커밋된 데이터가 구분되어 존재한다"는 점은 같다.

메뉴 서비스와 카테고리 서비스가 **비슷한 시간에** 같은 메뉴 테이블에 접근하는 상황에서 다음 현상들이 생길 수 있다.

### Dirty Read — 쓰레기를 읽는다

다른 트랜잭션이 업데이트를 시작했지만 아직 **커밋하지 않은** 데이터를 읽는 것이다. "업데이트하려고 준비 중인 것까지 먼저 보고 싶다"는 얼리어답터 같은 읽기다.

문제는 그 트랜잭션이 **커밋된다는 보장이 없다**는 점이다. 진행하다 오류가 나서 롤백되면, 나는 **존재한 적 없는 데이터**를 읽은 것이 된다.

```
트랜잭션 A: UPDATE 아메리카노 가격 = 5000  (커밋 전)
트랜잭션 B:        SELECT 가격 → 5000     ← 읽었다
트랜잭션 A: ROLLBACK                      ← 5000원은 존재한 적이 없는 값이 됨 (실제는 4500)
```

### Non-repeatable Read — 다시 읽을 수 없다

한 트랜잭션 안에서 **같은 행을 두 번 읽었는데 값이 다른** 것이다.

```
트랜잭션 B: SELECT 아메리카노 가격 → 4500
트랜잭션 A: UPDATE 아메리카노 가격 = 5000; COMMIT
트랜잭션 B: SELECT 아메리카노 가격 → 5000   ← 아까와 다르다
```

> 원문 바로잡기 — 강의에서는 "읽었던 데이터가 롤백으로 없어져서 다시 읽을 수 없는 것"으로 설명했는데, 롤백 때문에 생기는 것은 Dirty Read 쪽이다. Non-repeatable Read는 다른 트랜잭션이 **정상적으로 커밋한** 수정·삭제 때문에, 커밋된 데이터만 읽어도 생긴다.

### Phantom Read — 유령을 읽는다

**같은 조건으로 여러 행을 다시 조회했는데 행의 개수가 달라지는** 것이다. 아까 120건이었는데 다시 세니 121건이 되어 있다. 다른 트랜잭션이 조건에 맞는 행을 **새로 넣거나 지웠기** 때문이다. "아까 분명히 없었는데?" 하고 유령처럼 나타나는 행이다.

| 현상 | 원인 | 한 줄 |
|---|---|---|
| Dirty Read | 남의 **커밋 전** 변경을 읽음 | 롤백되면 없는 값을 읽은 셈 |
| Non-repeatable Read | 남이 **같은 행**을 수정·삭제하고 커밋 | 같은 행을 다시 읽으니 값이 다름 |
| Phantom Read | 남이 조건에 맞는 행을 **추가·삭제**하고 커밋 | 다시 조회하니 건수가 다름 |

## 4. 수준별로 막아 주는 것

| 격리 수준 | Dirty Read | Non-repeatable Read | Phantom Read | 속도 |
|---|---|---|---|---|
| READ UNCOMMITTED | 발생 | 발생 | 발생 | 가장 빠름 |
| READ COMMITTED | **방지** | 발생 | 발생 | ↓ |
| REPEATABLE READ | 방지 | **방지** | 발생 | ↓ |
| SERIALIZABLE | 방지 | 방지 | **방지** | 가장 느림 |

### READ UNCOMMITTED는 언제 쓸까

실시간으로 바뀌는 게시판의 **댓글이나 커뮤니티**처럼, 잘못된 값을 잠깐 보여 줘도 큰 피해가 없는 곳에서는 써도 상관없다. 반대로 **결제 금액**처럼 금전·업무상 피해를 줄 수 있는 데이터에는 쓰지 않는다. 결제하다 실패해 롤백될 금액을 사용자에게 보여 주면 안 되기 때문이다.

> **추가 설명**: READ UNCOMMITTED를 일부러 쓰는 경우는 드물다. PostgreSQL은 이 수준을 지정해도 **READ COMMITTED와 똑같이** 동작해서 Dirty Read가 아예 일어나지 않는다. Oracle은 READ COMMITTED와 SERIALIZABLE만 지원한다.

## 5. 왜 아래로 갈수록 느려지나 — 잠금의 범위

"내가 처리하는 동안 너는 읽지 마"는 **화장실 문을 잠그는 것**과 같다.

| 잠그는 범위 | 화장실 비유 | 영향 |
|---|---|---|
| 내가 쓰는 **행(레코드)**만 | 내가 쓰는 변기 칸만 잠근다 | 다른 칸은 다른 사람이 쓸 수 있다 |
| **테이블** 전체 | 화장실 전체를 잠근다 | 빈 칸이 있어도 모두 밖에서 기다린다 |
| 그보다 더 넓게 | 건물을 잠근다 | 화장실을 안 쓰는 사람까지 기다린다 |

격리 수준이 높아질수록 잠그는 범위가 커지고, 기다리는 사람이 늘어난다.

- **READ COMMITTED**: 아직 커밋되지 않은 변경은 손대지 못하게 막는다. 그러면 Dirty Read는 사라진다. 하지만 커밋된 것은 열려 있으니, 다른 서비스가 중간에 바꾸고 커밋하면 다시 읽을 때 값이 달라진다(Non-repeatable Read). 건수가 달라지는 Phantom Read도 생긴다.
- **REPEATABLE READ**: 내가 읽은 **행만** 잠근다. 다른 행은 열어 두니 다른 사람도 쓸 수 있고, 내가 읽은 행은 다시 읽어도 같다.
- **SERIALIZABLE**: Phantom Read까지 막으려면 행이 새로 생기는 것도 막아야 하니 사실상 **테이블 전체**를 잠가야 한다. 성능이 크게 떨어진다.

### 잠그면 줄을 선다 — 동기화

동시 접속자 100명은 조금만 알려진 서비스라면 충분히 생긴다. 글을 하나 올리면 대부분 맨 위에 노출되니, 100명 중 99명이 **같은 행**을 읽으려 한다. 그 행에 락을 걸면 한 명이 끝날 때까지 99명이 **줄을 서야** 한다. 이렇게 줄 세우는 것을 **동기화**라고 한다. 동기화가 많아지면 성능과 서비스 품질이 떨어진다.

## 6. 잠그지 않고 해결하기 — 스냅샷

"다시 읽어도 같은 값"은 보장하면서 락은 걸고 싶지 않다. 그래서 DBMS는 **스냅샷**을 쓴다. 읽을 때 테이블을 잠그는 대신 **그 시점의 상태를 사진 찍듯 떠 놓고** 그것을 읽는다. 원본은 열어 두니 다른 트랜잭션이 바꿀 수 있다.

차이는 **스냅샷을 언제 찍고 언제 버리느냐**다.

```
트랜잭션 안에서:  1번 조회 ─── 2번 다른 작업 ─── 3번 다시 조회

READ COMMITTED   1번: 스냅샷 찍고 쓰고 버림       3번: 스냅샷 **새로** 찍음 → 그 사이 커밋된 변경이 보임
REPEATABLE READ  1번: 스냅샷 찍고 **보관**        3번: 1번에 찍은 스냅샷을 그대로 씀 → 같은 값
```

- **READ COMMITTED**: 조회할 때마다 커밋된 상태로 스냅샷을 찍고, 읽고 나면 버린다.
- **REPEATABLE READ**: 처음 찍은 스냅샷을 버리지 않고 **트랜잭션이 끝날 때까지** 유지한다.
- **SERIALIZABLE**: 테이블 전체에 대한 스냅샷이 필요해 부담이 크고 느리다. 정말 안전해야 하는 경우에만 쓴다.

> **추가 설명 — MVCC**: 이렇게 버전(스냅샷)으로 읽기와 쓰기가 서로를 막지 않게 하는 방식을 **MVCC**(Multi-Version Concurrency Control, 다중 버전 동시성 제어)라고 한다. PostgreSQL, Oracle, MySQL(InnoDB) 모두 MVCC를 쓴다. 락은 주로 **같은 행을 동시에 수정**할 때 쓰인다.

> **추가 설명 — 표준과 실제 DBMS의 차이**: 위 표는 SQL 표준 기준이다. 실제로는 스냅샷 방식 덕분에 PostgreSQL의 REPEATABLE READ는 Phantom Read도 일어나지 않는다. MySQL InnoDB의 REPEATABLE READ도 일반 조회에서는 Phantom Read가 거의 일어나지 않는다. 또 PostgreSQL의 SERIALIZABLE은 테이블을 통째로 잠그지 않는다. 스냅샷으로 실행하다가 충돌이 감지되면 한쪽 트랜잭션을 **실패시키고**, 애플리케이션이 다시 시도하게 한다.

## 7. DBMS별 기본 격리 수준

| DBMS | 기본 격리 수준 | 주로 쓰는 곳 |
|---|---|---|
| **PostgreSQL** | READ COMMITTED | 최근 3~4년 사이 시작한 신규 프로젝트에서 많이 쓴다 |
| **Oracle** | READ COMMITTED | 비용을 감당할 수 있는 회사, 오래전부터 쓰던 시스템 |
| **MySQL** (InnoDB) | REPEATABLE READ | 스타트업과 규모가 큰 업체 모두 많이 쓴다 |
| H2 | READ COMMITTED | 테스트·학습용 |

PostgreSQL과 MySQL은 둘 다 무료로 쓸 수 있으면서 전 세계에서 많이 쓰는 DBMS다. Oracle은 상용 시장에서 점유율이 있다. 대부분은 **DBMS의 기본값(`DEFAULT`)**이면 충분하고, 특별히 안전해야 하는 업무에서만 수준을 올린다.

> 강의에서 MySQL의 REPEATABLE READ를 보고 "성능을 더 신경 쓴 것 같다"고 했는데, 이 수준은 READ COMMITTED보다 **더 엄격한** 격리 수준이다. 성능보다는 일관성 쪽에 더 무게를 둔 기본값이다.

## 8. 다음 내용 — 스프링 시큐리티의 기반은 필터

이어서 **스프링 시큐리티**로 넘어간다. 라이브러리를 쓰기 전에 **세션, 쿠키, 인증**이 무엇인지 먼저 알아야 한다.

| 스프링 기능 | 이해하려면 알아야 할 기반 |
|---|---|
| DI | IoC 컨테이너 |
| 트랜잭션 | AOP |
| **시큐리티** | **필터** |

필터는 스프링의 기능이 아니라 **서블릿의 기능**이고, 스프링은 그것을 가져다 쓴다. 서블릿(톰캣) 라이브러리에서 우리가 직접 만들 수 있는 클래스는 세 가지다.

- **`HttpServlet`**: `extends` 해서 요청을 처리하는 서블릿을 만든다.
- **`Filter`**: 요청이 서블릿에 닿기 **전에** 먼저 거친다.
- **리스너(Listener)**: 이벤트와 관련된 것으로, 세션 이벤트 리스너와 애플리케이션 리스너 등이 있다.

## 9. 한 줄 정리

- 조회만 하는 서비스도 **곁다리를 조립하는 동안** 데이터가 바뀌지 않도록 트랜잭션(격리)이 필요하다.
- 격리 수준은 **읽기** 옵션이다. 낮을수록 빠르고, 높을수록 안전하지만 느리다.
- Dirty Read는 **커밋 전 값**, Non-repeatable Read는 **같은 행의 값 변경**, Phantom Read는 **건수 변경**이다.
- 잠그면 줄을 서야 하니, DBMS는 **스냅샷(MVCC)**으로 락 없이 읽는다. READ COMMITTED는 조회마다, REPEATABLE READ는 트랜잭션 동안 하나의 스냅샷을 쓴다.
- 기본값은 PostgreSQL·Oracle이 **READ COMMITTED**, MySQL이 **REPEATABLE READ**다. 보통은 `DEFAULT`로 충분하다.
