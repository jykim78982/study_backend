# 엔터프라이즈 애플리케이션 구조와 스프링의 역할 — 큰 그림 정리

지금까지 만든 애플리케이션의 구조와, 그 구조 곳곳에서 **스프링이 어떤 기능으로 도와주고 있는지**를 한 장의 그림으로 정리한다. 앞으로 배울 내용이 어디에 놓이는지도 함께 본다.

## 1. 기본 구조 — 스프링과 상관없는 골격

```
요청 ━▶ [Front Controller] ⇄ [Controller] ⇄ [Service] ⇄ [Dao] ⇄ (DB)
응답 ◀━                           ⇅
                                [JSP]
         ─────────────────── Java Runtime ───────────────────
```

기업용 애플리케이션의 백엔드는 이렇게 만든다. 이것은 **스프링과 전혀 상관없이**, 어떤 플랫폼과 어떤 언어를 쓰든 같은 구조다.

- **3계층 아키텍처**: Controller – Service – Dao(Repository). 기업용 애플리케이션의 가장 기본 골격이다. 이것을 확장한 아키텍처도 있지만 뼈대는 이것이다.
- **MVC**: 서버에서 페이지를 만드는 경우, 컨트롤러와 화면(View, JSP)을 나누고 그 사이에 데이터(Model)를 두는 방식이다. 스프링은 MVC를 **만든 것이 아니라 지원하는 것**이다.

### 컨트롤러의 역할 — 서빙만 한다

3계층으로 나누지 않은 MVC라면 컨트롤러가 사용자 요청에 대한 **주 업무**를 직접 처리한다. 3계층으로 나눈 뒤에는 업무를 서비스가 맡으므로, 컨트롤러는 요청을 받아 서비스에 전달하고 결과를 응답으로 내보내는 **홀 서빙**만 한다. "짜장면 두 그릇이요"를 주방에 전달하고, 나온 음식을 손님에게 가져다주는 역할이다.

## 2. 스프링이 도와주는 곳

```
         ┌──────────┐                     ┌──── AOP ────┐
         │          │                     │ Transaction │
요청 ━▶  │ Security │ ━▶ [Dispatcher] ⇄ [Controller] ⇄DI⇄ [Service] ⇄DI⇄ [Dao] ⇄ [Data Access] ⇄ (DB)
응답 ◀━  │ (Filter) │
         └──────────┘
```

| 위치 | 스프링 기능 | 바탕 개념 |
|---|---|---|
| Front Controller | **DispatcherServlet** (Spring Web MVC) | 프론트 컨트롤러 패턴 |
| 계층 사이 | **DI** | IoC |
| Dao ↔ DB | **Data Access** (JdbcTemplate, Spring Data JPA) | — |
| Service | **Transaction** (`@Transactional`) | AOP |
| 요청의 가장 앞 | **Security** | 필터 |

### 2-1. DispatcherServlet — 컨트롤러를 POJO로 만들어 준다

**POJO**라는 말은 그것과 반대되는 무언가가 있었다는 뜻이다. 예전에는 요청을 받고 응답하는 컨트롤러를 반드시 **서블릿 클래스**(`HttpServlet` 상속)로 만들어야 했다. 컨트롤러가 서블릿에 **종속**되어 자율성이 떨어졌다.

그래서 "컨트롤러를 서블릿으로부터 해방시키자"고 나온 것이 **프론트 컨트롤러**다. 서블릿은 하나만 두고, 모든 요청을 그 서블릿이 먼저 받아 POJO 컨트롤러들을 대신 호출한다. 스프링이 제공하는 그 서블릿이 **DispatcherServlet**이다. Dispatch는 "보낸다, 호출한다"는 뜻으로, 다른 객체를 호출해 주는 역할의 서블릿이라는 의미다.

이 덕분에 어떤 요청을 어느 컨트롤러가 받을지를 서블릿 규칙이 아니라 `@GetMapping` 같은 **스프링 스타일의 어노테이션**으로 정할 수 있게 되었다. 웹 기반 스프링을 쓸 때 우리가 가장 먼저, 나도 모르게 쓰고 있던 기능이 이것이다. 이 기능을 **Spring Web MVC**라고 한다.

### 2-2. DI와 IoC — 객체를 만들어 꽂아 준다

3계층은 계층 사이의 결합력이 **느슨해야**(Loose Coupling) 한다. 결합이 강하게(Tight) 이루어져 있으면 한쪽을 바꿀 때 다른 쪽도 바꿔야 하기 때문이다.

| 사용 방식 | 의미 | 결합 |
|---|---|---|
| **Composition** | 사용하는 쪽이 객체를 **직접 생성**해서 쓴다 (`new`) | 강함 |
| **Association** | 사용하는 쪽은 만들어진 객체를 **세팅(주입)받아** 쓴다 | 느슨함 |

느슨한 결합을 위해 **인터페이스 기반으로 Association**을 쓴다. 그런데 인터페이스만 쓴다고 결합력이 낮아지지는 않는다. **누군가는 구체적인 객체를 만들어 세팅해 줘야** 하고, 그 누군가는 구체 클래스를 알고 있으므로 구체 클래스를 바꿀 때 그 코드도 **수정 범위**에 들어간다.

그래서 "객체를 생성하는 코드를 우리 애플리케이션에서 아예 빼 버리자"는 생각이 나왔고, 그 일을 맡아 주는 것이 스프링이다. 스프링은 커다란 보따리(컨테이너)를 하나 가지고 "너희는 주문만 해. 내가 다 만들어서 꽂아 줄게"라고 한다. 이것이 **DI**이고, 그 컨테이너가 **IoC 컨테이너**다.

**IoC(Inversion of Control, 제어의 역전)**: 거창하게 들리지만 **내가 할 일을 외부에 맡기는 것(아웃소싱)**이다. "이건 내가 실행할 일이 아니야"라고 내 코드에서 빼 버린 것들이 모두 IoC다. IoC가 이루어지려면 반드시 **위임**이 일어난다.

- **스프링 DI**: 객체의 생성과 조립을 XML이나 어노테이션으로 컨테이너에 맡긴다.
- **자바스크립트 이벤트 처리**: 클릭하면, 로드되면 실행될 함수를 내가 직접 호출하지 않고 실행 환경에 던져서 "네가 실행해 줘"라고 맡긴다. **콜백 함수**가 바로 IoC다.

IoC라는 용어를 쓰면 고급 개발자처럼 느껴져서 많이 쓰지만, "외부에 맡긴다"로 평범하게 이해하면 된다.

### 2-3. Data Access — 반복되는 JDBC 코드를 줄여 준다

DB를 쓰려면 SQL을 작성하고, JDBC API로 연결 → 실행 → 결과 가져오기를 해야 했다. 이 작업이 반복적이고 패턴화되어 있어서 스프링이 **JdbcTemplate**을 제공했고, 예전에는 이것을 많이 썼다. 요즘은 **JPA**(스프링에서는 Spring Data JPA)를 설정해서 쓰는 경우가 많다.

```
[우리 코드] → Spring Data JPA → JPA(Hibernate) → JDBC API → DB
[우리 코드] → JdbcTemplate ─────────────────────▶ JDBC API → DB
```

> 강의에서는 "요즘은 JdbcTemplate을 직접 쓰지 않고 JPA 설정을 통해 간접적으로 쓴다"고 설명했는데, JPA 구현체인 Hibernate는 JdbcTemplate을 거치지 않고 **JDBC API를 직접** 사용한다. JdbcTemplate과 JPA는 JDBC 위에 놓인 **서로 다른 두 가지 길**이다. 맨 밑바닥에 JDBC API가 있다는 점은 같다.

어느 길을 쓰든 이 데이터 접근 코드는 **리포지토리(Dao)** 안에 둔다. 리포지토리는 어떤 DB를 쓰는지, 데이터가 어디에 있는지, 어떤 SQL을 쓰는지 같은 **데이터 접근의 세부 사정**을 서비스로부터 숨긴다. 그래서 서비스는 데이터 접근 기술에 신경 쓰지 않고 받은 데이터로 **업무 처리에만 집중**할 수 있다.

### 2-4. Transaction — 스프링이 세상에 퍼진 이유

DI와 함께, 스프링을 쓰게 된 **가장 큰 이유**가 트랜잭션이다. 이 기능이 아니었다면 스프링은 이만큼 알려지지 않았을 것이다.

스프링 이전에 엔터프라이즈에서는 **EJB**(Enterprise JavaBeans)로 트랜잭션을 처리했다.

- **EJB 컨테이너 기반 서버**를 따로 띄우고, 그 위에 Dao와 Service를 올려서 썼다.
- 톰캣 같은 웹 컨테이너도 따로 올려야 했고, 설정해서 올리고, 하나가 뻗으면 다 뻗었다.

그때 스프링이 "내 거 써 봐. 서버도 필요 없고 설정도 간단해. 그냥 **라이브러리**야"라고 등장했다. 써 보니 서버가 뻗는 일도 없고 `@Transactional` 한 줄로 롤백까지 되었다. 그래서 기업들이 스프링을 쓰기 시작했고, 스프링은 기업들이 쓰면서 필요해진 기능(웹, 데이터 접근, 시큐리티 등)을 계속 확장해 왔다.

> 강의에서는 "처음에는 DI와 트랜잭션 두 가지만 있었다"고 했는데, 2004년에 나온 스프링 1.0에도 이미 Web MVC, JDBC 추상화, AOP 모듈이 포함되어 있었다. 다만 기업들이 스프링을 선택한 **핵심 이유**가 DI와 선언적 트랜잭션이었다는 점은 맞다.

`@Transactional`을 가능하게 한 개념적 방법론은 **AOP**다. 트랜잭션이 어떻게 구현되었는지 모르고 그냥 쓰면, 실력을 의심받을 수 있다.

### 2-5. Security — 다음에 배울 것

트랜잭션 다음에 볼 것은 **대문을 만드는 일**이다. 요청이 오면 문지기를 세워 "넌 못 가, 넌 들어와도 돼"를 가르는 것이다. 스프링은 이것을 **Spring Security**로 깔끔하게 지원하며, 그 기술적 기반은 **필터**다. 필터는 DispatcherServlet보다 앞에서 요청을 먼저 받는다.

| 기능 | 구현 기반 |
|---|---|
| 트랜잭션 | AOP |
| 시큐리티 | 필터 |

## 3. 그 다음 — 규모가 커지면

여기까지(웹, DI, 데이터 접근, 트랜잭션, 시큐리티)를 하면 기업용 애플리케이션은 다 만들 수 있다. 규모가 커지면 개발보다 운영에 가까운 이야기가 따라온다.

- **도메인 기반 아키텍처**: 어댑터 계층을 두는 등 아키텍처를 도메인 중심으로 바꿔, 도메인 단위로 확장할 수 있게 한다.
- **마이크로서비스(MSA)**: 애플리케이션 전체를 복제해 서버를 늘리는 대신, **일부 서비스를 잘라서 다른 컴퓨터에 두는** 방식으로 트래픽을 분산한다. 트랜잭션이 억 단위, 조 단위로 일어나는 **글로벌 규모**에서나 필요하고, 일반적인 중소·중견 기업 애플리케이션까지 이렇게 갈 이유는 없다.

그보다 개발자가 먼저 갖출 것은 **자동화**다. AI 에이전트를 쓰는 것을 넘어 **에이전트를 만드는 것**도 생각보다 쉽다. 한 번 시작하면 "저것도 자동화해 볼까?"로 계속 이어진다.

## 4. 백엔드 API — 그냥 API와 무엇이 다른가

| | 그냥 API (Open API 등) | 백엔드 API |
|---|---|---|
| 기준 | **자원**을 제공하는 것 자체 | **화면**이 필요로 하는 데이터를 제공 |
| UI | 모른다 | 화면(UI/UX)이 있다 |
| URL | `/api/v1/menus` 처럼 **단층**. `/menus/categories` 같은 계층은 없다 | 페이지의 **주인공** 기준으로 만들고 **곁다리**가 이어진다 |
| 업무 로직 | 자원 제공에 초점 | 사용자가 요구하는 업무 로직을 담는다 |

예전에는 `/menus` 페이지 하나를 위해 API 하나가 메뉴 목록, 추천 목록, 카테고리를 전부 담아 주려고, 계층과 중첩이 깊은 데이터 구조를 만들었다. 그러려면 SQL에서 테이블을 15개씩 조인해야 했고, 느려지니 튜닝 기술이 발달했다. 지금은 그렇게 하지 않는다. **잘게 쪼갠다.**

```
/menus 페이지
 ├─ 주인공: 메뉴 목록     → GET /api/v1/menus
 ├─ 곁다리: 카테고리      → GET /api/v1/menus/categories
 └─ 곁다리: 추천 메뉴     → GET /api/v1/menus/recommends
```

화면도 통으로 만들지 않고 컴포넌트로 쪼개, 각 컴포넌트가 자기 API를 담당한다.

AI에게 "API 만들어 줘"라고 하면 그냥 API 쪽으로 끌고 가면서 "그 방식은 실무에서 추천하지 않습니다"라고 말하기도 한다. 이때는 "**나는 지금 백엔드 API를 말하는 거야**", "정말 그렇게 생각해?"라고 다시 짚어 주면 답이 달라진다.

## 5. 엔티티가 곧 테이블이다

이제는 테이블을 직접 만들지 않는다. **엔티티가 테이블**이다. 테이블을 직접 만들던 습관 때문에 엔티티와 테이블을 따로 생각하게 되는데, 그럴 필요가 없다. 도구의 추상화 수준이 올라가는 것을 따라가야 한다.

- DB를 잘할수록 오히려 그 방식을 움켜쥐고 "그래도 SQL을 할 줄 알아야 해"라며 변화를 부정하기 쉽다. AI 시대에 가장 큰 딜레마를 겪는 것은 AI 이전에 기술을 잘하던 사람들이다.
- 코드를 직접 작성하는 일은 언젠가 아예 없어질 수도 있다. 하지만 **아예 안 볼 수는 없다.** AI는 경계를 정해 주지 않으면 손대지 말아야 할 곳까지 손댄다. 규모가 커질수록 다른 곳을 넘나들지 않도록 툭툭 쳐 주는 사람이 반드시 필요하다.
- 그러려면 구조를 **개념적으로** 알아야 한다. "이게 뭐지? 왜 필요하지?"를 알고, 그룹을 물려받은 회장처럼 **지휘할 수 있는 수준**이면 된다.
- 받은 코드가 무슨 코드인지 모른다면 직접 타이핑하며 공부하고, 알고 있다면 그 정도면 충분하다.

## 6. 한 줄 정리

- 기업용 애플리케이션은 스프링과 상관없이 **Front Controller + 3계층(Controller–Service–Dao)** 구조로 만든다.
- 스프링이 돕는 곳: **DispatcherServlet**(컨트롤러를 POJO로), **DI**(객체 생성·조립을 컨테이너에 맡김), **Data Access**(JdbcTemplate·JPA), **Transaction**(AOP 기반), **Security**(필터 기반).
- **IoC**는 "내 할 일을 외부에 맡기는 것"이다. 스프링 DI도, 자바스크립트 콜백도 IoC다.
- 스프링은 **EJB 서버 없이 라이브러리만으로** 트랜잭션을 처리하게 해 주면서 퍼졌다.
- **백엔드 API**는 화면의 주인공을 기준으로 잘게 쪼갠다.
