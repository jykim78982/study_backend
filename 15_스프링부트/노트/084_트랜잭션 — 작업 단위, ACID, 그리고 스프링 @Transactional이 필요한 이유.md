# 트랜잭션 — 작업 단위, ACID, 그리고 스프링 @Transactional이 필요한 이유

트랜잭션이 무엇인지, 트랜잭션 처리가 왜 필요한지, DBMS와 JDBC는 이를 어떻게 지원하는지, 그리고 컨트롤러·서비스·리포지토리로 계층을 나누는 순간 왜 트랜잭션 처리가 어려워지고 스프링이 이를 어떻게 해결하는지 정리한다.

## 1. 트랜잭션 = 한 번에 이루어져야 할 작업 단위

트랜잭션(transaction)은 영어 사전에서 **거래, 매매, 처리**라는 뜻이다. 영어라서 우리에게는 이미지가 잘 그려지지 않는데, "하나의 거래"처럼 **하나의 작업 단위**로 떠올리면 된다.

**웹 트랜잭션으로 감 잡기**: 웹은 **요청과 응답이 하나의 작업 단위**다. 요청만 보내고 끝나는 일은 없고, 요청을 보내면 반드시 응답이 와야 한다. 이 요청-응답 단위가 매우 안정적으로 유지되기 때문에, 그 위에 얹어서 만든 것이 웹 개발이다.

우리가 사용하는 모든 것에는 이렇게 **한 번에 이루어져야 할 단위**가 있다. 이것이 트랜잭션이다.

## 2. 왜 트랜잭션 처리가 필요한가 — 결제 예시

사용자가 결제를 요청하면 계층별로 이렇게 흘러간다.

```
사용자 ──"결제해줘"──> Controller ──> Service ──> Repository (여러 번 호출)
                      (주문 전달만)    (결제 처리)   포인트 차감 / 주문 기록 / 적립 ...
```

- **컨트롤러**는 서빙 직원이다. 주문을 받아서 서비스에 전달할 뿐 직접 처리하는 일은 없다.
- **서비스**가 결제를 처리한다. 그런데 "결제" 한 방에 끝나는 함수는 없다. 리포지토리의 여러 함수를 조합해야 한다.

**사용자에게는 단일 업무인데, 서비스에게는 쪼개진 업무가 된다.** 그러면 이런 일이 생길 수 있다.

```
① 포인트 차감 — 성공
② 주문 기록   — 성공
③ 결제 내역   — 실패!
```

세 개 중 하나만 실패해도 결제는 **실패**다. 그런데 포인트는 이미 빠져나갔다. 결제는 안 됐는데 포인트만 깎인 것이다. 말이 안 된다. 실패했다면 깎인 포인트를 **원래대로 되돌려놔야** 한다.

> **트랜잭션 처리**: 개별 작업이 몇 개로 나뉘어 있든 상관없이, 하나의 트랜잭션이 **전부 성공하거나, 하나라도 실패하면 전부 실패한 것(처음 상태)으로** 일관되게 유지되도록 하는 것.

## 3. ACID — 트랜잭션이 지켜야 할 네 가지 성질

| 성질 | 뜻 | 결제 예시 |
|---|---|---|
| **A**tomicity (원자성) | 절대 **일부만** 실행되면 안 된다. 전부 되거나 전부 안 되거나. | 포인트 차감만 되고 결제가 안 되면 안 된다 |
| **C**onsistency (일관성) | 트랜잭션 전후의 데이터가 업무 규칙(도메인)에 맞는 **유효한 값**이어야 한다. | 포인트가 마이너스가 되면 안 된다 |
| **I**solation (격리성) | 트랜잭션이 진행되는 동안 **다른 트랜잭션이 끼어들면** 안 된다. | 내가 결제하는 중에 다른 작업이 같은 포인트를 바꿔버리면 안 된다 |
| **D**urability (지속성) | **커밋된 결과**는 장애가 나도 사라지지 않아야 한다. | 결제 완료 직후 정전이 나도 결제 내역은 남아야 한다 |

이 중 지속성은 DBMS가 알아서 보장하는 영역이라 개발자가 손댈 부분이 거의 없다. 개발자가 신경 써야 하는 것은 **원자성, 일관성, 격리성**이다. 셋 중 하나만 깨져도 말이 안 되는 결과가 나온다.

> **강의 내용 바로잡기 — 지속성은 어떻게 보장되나**: 강의에서는 "트랜잭션 중에 정전이 나면 임시 저장소의 내용을 보고 사람이 반영할지 판단한다"고 설명했다. 실제로는 사람이 판단하지 않는다. DBMS는 변경 내용을 데이터 파일에 쓰기 전에 **로그(WAL, Write-Ahead Log / redo log)**에 먼저 기록해 둔다. 장애 후 재시작하면 DBMS가 이 로그를 보고 **자동으로 복구**한다.
> - **커밋된** 트랜잭션 → 로그를 바탕으로 결과를 다시 반영해서 살려낸다(이것이 지속성).
> - **커밋되지 않은** 트랜잭션 → 자동으로 롤백해서 없던 일로 만든다(이것이 원자성).

> **보충 — 격리성은 "무조건 기다리게"만은 아니다**: 다른 트랜잭션을 전부 기다리게 하면 안전하지만 매우 느려진다. 그래서 DBMS는 **격리 수준(isolation level)**을 두고 안전성과 성능 사이에서 조절한다. PostgreSQL 같은 DBMS는 MVCC(다중 버전 동시성 제어)를 써서, 수정 중인 행에도 읽기는 막지 않고 이전 버전을 보여준다. 같은 행을 **동시에 수정**하려는 경우에만 락으로 기다리게 한다.

## 4. DBMS는 이미 트랜잭션을 지원한다 — COMMIT과 ROLLBACK

"세 개 중 하나가 실패하면 성공한 것까지 되돌린다"가 가능할까? 이 기능은 **이미 DBMS에 구현되어 있다.**

```sql
BEGIN;                                                    -- 트랜잭션 시작
SELECT point FROM members WHERE id = 1;                   -- 포인트 확인
UPDATE members SET point = point - 3000 WHERE id = 1;     -- 포인트 차감
INSERT INTO orders (member_id, menu_id) VALUES (1, 10);   -- 주문 기록
INSERT INTO payments (...) VALUES (...);                  -- 결제 내역
COMMIT;                                                   -- 전부 성공 → 확정
-- 중간에 실패하면 ROLLBACK;                               -- 전부 취소
```

- 트랜잭션을 시작하면 수정 사항이 바로 확정되지 않는다. 다른 트랜잭션이 볼 수 없는 **확정 전 상태**로 남아 있고, 수정 중인 행에는 **락**이 걸려 다른 트랜잭션이 바꾸지 못한다("잠깐, 내가 작업 중이니 끝날 때까지 손대지 마").
- **COMMIT**: 전부 성공했으면 변경을 확정하고 락을 푼다.
- **ROLLBACK**: 실패했으면 지금까지의 변경을 전부 버리고 락을 푼다.

## 5. JDBC로 트랜잭션 처리하기 — 자동 커밋 끄기

JDBC에도 같은 기능이 있다. JDBC는 기본이 **자동 커밋(auto-commit)**이라, SQL 한 문장을 실행할 때마다 그 즉시 커밋된다. 트랜잭션으로 묶으려면 자동 커밋을 끄고, 끝에서 직접 커밋한다.

```java
Connection con = dataSource.getConnection();
try {
    con.setAutoCommit(false);              // 자동 커밋 끄기 = 트랜잭션 시작

    PreparedStatement del = con.prepareStatement("DELETE FROM cart WHERE member_id = ?");
    del.setLong(1, memberId);
    del.executeUpdate();

    PreparedStatement ins = con.prepareStatement("INSERT INTO orders (member_id) VALUES (?)");
    ins.setLong(1, memberId);
    ins.executeUpdate();

    con.commit();                          // 둘 다 성공 → 한꺼번에 확정
} catch (SQLException e) {
    con.rollback();                        // 하나라도 실패 → 전부 취소
    throw e;
} finally {
    con.close();
}
```

**핵심은 같은 `Connection` 하나로 실행해야 한다는 것이다.** 트랜잭션은 커넥션 단위로 관리되기 때문에, DELETE와 INSERT가 같은 커넥션을 써야 하나로 묶인다.

## 6. 진짜 어려운 점 — 계층을 나누면 커넥션이 흩어진다

JDBC가 지원한다면 어려울 게 없어 보인다. 문제는 **리포지토리 계층**을 만들면서 생긴다.

```java
public class CartRepository {
    public void deleteByMemberId(Long memberId) {
        Connection con = dataSource.getConnection();   // 커넥션 열고
        // DELETE 실행
        con.close();                                   // 닫는다 → 이 함수의 작업은 여기서 끝
    }
}

public class OrderRepository {
    public void insert(Long memberId) {
        Connection con = dataSource.getConnection();   // 또 다른 커넥션
        // INSERT 실행
        con.close();
    }
}

public class OrderService {
    public void order(Long memberId) {
        cartRepository.deleteByMemberId(memberId);     // 커넥션 A에서 실행되고 끝
        orderRepository.insert(memberId);              // 커넥션 B에서 실행 — 여기서 실패하면?
    }
}
```

SQL이 함수로 나뉘어 객체로 빠지면서, **각 함수가 자기 커넥션을 열고 닫는다.** 리포지토리 안에서 자동 커밋을 꺼도, 함수가 끝날 때 그 함수의 작업은 이미 끝나 버린다. 서비스 입장에서는 두 함수가 **커넥션을 공유할 방법이 없으니** 하나의 트랜잭션으로 묶을 수가 없다. INSERT가 실패해도 이미 끝난 DELETE를 되돌릴 수 없다.

> **보충**: 자동 커밋을 끈 상태에서 커밋 없이 `close()`하면 어떻게 되는지는 드라이버마다 다르다(오라클은 커밋, PostgreSQL은 롤백). 어느 쪽이든 핵심은 같다. **서로 다른 커넥션의 작업은 하나의 트랜잭션으로 묶을 수 없다.**

**그럼 리포지토리를 안 만들면?** 계층을 나누지 않던 시절에는 서비스 메서드 안에서 커넥션 하나로 SQL을 쭉 실행하면 됐다. 리포지토리를 만들지 않으면 트랜잭션은 해결된다. 하지만 그건 **트랜잭션과 계층 중 하나를 포기하는 선택**이다. 둘 다 원한다면 커넥션을 누군가 대신 관리해줘야 한다.

## 7. EJB 서버의 해결 방법과 불편함

옛날 자바 엔터프라이즈(Java EE)에서는 **EJB**(Enterprise JavaBeans) 서버가 이 문제를 해결했다.

- **커넥션 관리**: 함수마다 커넥션을 열고 닫게 두지 않고, EJB 서버가 커넥션을 관리하며(커넥션 풀링) 여러 함수가 **같은 커넥션을 공유**하게 해준다.
- **커밋 시점 관리**: 누가 끝난 다음 누가 실행되고, **언제 커밋할지**를 EJB 서버가 맡아서 처리한다.

그런데 쓰기가 너무 불편했다.

- 톰캣 같은 웹 서버와 별도로 **EJB 서버를 띄워야** 한다.
- 트랜잭션에 참여할 객체를 EJB 서버에 등록하고, 객체마다 **XML 설정**을 손대고, 객체 간 관계까지 설정해야 한다.
- 설정이 조금만 잘못돼도 서버가 다운되고, 다시 켜서 설정을 뒤져 원인을 찾아야 한다.

## 8. 스프링의 해결 — @Transactional 한 줄

스프링은 별도의 서버도, 복잡한 설정도 필요 없다. **"이 작업 단위에는 트랜잭션이 필요합니다"라고 어노테이션 하나만** 붙이면 된다.

```java
@Service
public class OrderService {

    @Transactional
    public void order(Long memberId) {
        cartRepository.deleteByMemberId(memberId);
        orderRepository.insert(memberId);
        // 여기까지 전부 성공하면 커밋, 중간에 예외가 나면 전부 롤백
    }
}
```

이렇게 하면 서비스 메서드 하나가 **트랜잭션 단위**가 된다. 트랜잭션이 어디서 시작해서 어디서 끝나는지를 **트랜잭션 경계**라고 하는데, `@Transactional`은 이 경계를 **서비스의 업무 단위 메서드**에 맞춰 선언하는 것이다. 리포지토리 함수 하나하나가 아니라 "결제", "주문"처럼 사용자에게 하나인 업무가 경계가 된다. 메서드 안에서 호출하는 리포지토리 함수들이 같은 커넥션을 공유하고, 메서드가 정상적으로 끝나면 커밋, 예외가 나면 롤백된다. 지속성은 DBMS가 이미 보장하므로, 이 한 줄로 원자성을 지키는 단위 업무가 완성된다.

**어떻게 가능한가 (미리보기)**: 스프링은 `@Transactional`이 붙은 객체를 감싸는 **프록시**를 만들어서, 메서드 실행 전에 트랜잭션을 시작하고 커넥션을 **현재 스레드에 보관**해 둔다. 리포지토리들은 새 커넥션을 여는 대신 이 보관된 커넥션을 꺼내 쓴다. 메서드가 끝나면 프록시가 커밋 또는 롤백한다. 이렇게 핵심 로직 바깥에서 공통 기능을 끼워 넣는 방식을 **AOP**(관점 지향 프로그래밍)라고 하며, 다음에 자세히 다룬다.

> **보충 — 롤백되는 예외의 기준**: `@Transactional`은 기본적으로 **런타임 예외(`RuntimeException`)와 `Error`**가 발생할 때만 롤백한다. `IOException` 같은 체크 예외가 나면 롤백하지 않고 커밋한다. 체크 예외에도 롤백하려면 `@Transactional(rollbackFor = Exception.class)`처럼 지정한다. 또 예외를 메서드 안에서 `catch`로 잡아 삼켜버리면 스프링은 실패를 모르고 커밋한다.

## 9. 다음 단계 — 제약조건으로 실패를 만들어 확인하기

트랜잭션이 롤백되려면 실패, 즉 **예외**가 발생해야 한다. 실제로 확인하려면 DB 차원에서 오류가 나야 하는데, 이를 위해 **제약조건**(NOT NULL, UNIQUE, CHECK, 외래키 등)을 걸어두고 일부러 위반시켜 볼 것이다. 예를 들어 포인트 컬럼에 `CHECK (point >= 0)`을 걸면, 포인트가 마이너스가 되는 순간 DB가 오류를 내고 트랜잭션 전체가 롤백되는지 확인할 수 있다. 일관성(C)을 DB가 직접 지켜주는 장치가 바로 제약조건이다.

데이터 모델링 순서로 보면 개념 설계 → 논리 설계 → 물리 설계 → 구현 → 정규화까지 했고, 정규화 다음에 다뤄야 할 것이 제약조건이다.
