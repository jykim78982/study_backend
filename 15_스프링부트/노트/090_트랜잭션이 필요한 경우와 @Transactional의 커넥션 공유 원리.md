# 트랜잭션이 필요한 경우와 @Transactional의 커넥션 공유 원리

`@Transactional` 한 단어로 롤백까지 되는 것을 확인했다. 그렇다면 모든 서비스 메서드에 트랜잭션이 필요할까? 그리고 어노테이션 하나로 어떻게 여러 리포지토리 호출이 **같은 커넥션**을 쓰게 될까? 이 두 가지를 정리한다.

## 1. 트랜잭션이 필요 없는 작업도 있을까?

### 조회만 하는데도 트랜잭션이 필요할 수 있다

트랜잭션은 INSERT·UPDATE·DELETE처럼 **변경**이 있을 때만 필요하다고 생각하기 쉽다. 그렇지 않다.

서비스 메서드가 조회만 하는데, A를 조회하고 → 계산하고 → B를 조회하는 식으로 **여러 번 조회**한다고 하자. 첫 번째로 A를 읽은 뒤 두 번째를 읽는 사이에, **다른 사람이 A를 바꿔버리면** 어떻게 될까? 내 업무 로직은 이미 낡은 A 값을 기준으로 계산을 끝낸 상태다. 결과가 틀어진다.

- **혼자 쓰는 시스템**이라면 이런 일이 없으니 상관없다.
- **여러 사람이 동시에 쓰는 환경**에서는 조회할 때도 "나 아직 안 끝났어, 내가 읽는 동안 이거 바꾸지 마"라고 해야 한다.

이렇게 내 작업을 다른 작업의 영향으로부터 떼어놓는 것을 **고립(격리, Isolation)**이라고 하고, 이것도 트랜잭션의 일이다. ACID의 I가 바로 이것이다. 원자성(A)과는 상관없지만, 읽는 동안 값이 바뀌지 않아야 결과가 **일관성(C)**을 가진다.

`@Transactional`의 괄호 안에서 이 고립 수준을 설정할 수 있다.

```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
public Report makeReport() {
    Menu a = menuRepository.findById(1L).orElseThrow();  // 첫 번째 조회
    // ... 계산 ...
    Menu b = menuRepository.findById(1L).orElseThrow();  // 다시 조회해도 같은 값이 보장된다
    ...
}
```

> **추가 설명 — @Transactional만 붙인다고 다시 읽은 값이 같아지지는 않는다**: 고립 수준을 따로 지정하지 않으면 DB의 기본값을 따른다. PostgreSQL·Oracle의 기본값은 **READ COMMITTED**로, 같은 트랜잭션 안에서도 **다른 트랜잭션이 커밋한 변경은 다음 조회에 보인다.** 위 예처럼 "같은 행을 다시 읽어도 같은 값"을 보장하려면 `REPEATABLE_READ` 이상을 지정해야 한다(MySQL InnoDB는 기본값이 REPEATABLE READ다).
>
> | 고립 수준 | 막아주는 것 |
> |---|---|
> | READ UNCOMMITTED | 거의 없음 (커밋 안 된 값도 보임) |
> | READ COMMITTED | 커밋 안 된 값 읽기(Dirty Read) |
> | REPEATABLE READ | + 같은 행을 다시 읽었을 때 값이 바뀌는 것(Non-repeatable Read) |
> | SERIALIZABLE | + 조건에 맞는 행이 새로 생기거나 사라지는 것(Phantom Read). 가장 안전하지만 가장 느리다 |

> **추가 설명 — 조회 전용이면 readOnly**: 조회만 하는 서비스 메서드에는 `@Transactional(readOnly = true)`를 붙이는 경우가 많다. 이 트랜잭션은 변경이 없다고 알려주는 것이라, JPA는 변경 감지(스냅샷 비교)를 생략하고 flush를 하지 않아 조금 더 가볍게 동작한다.

### 트랜잭션을 생략해도 되는 경우

반대로 서비스 메서드가 **리포지토리 하나, SQL 하나**로 끝나는 아주 단순한 작업이라면 굳이 트랜잭션으로 묶지 않아도 된다. SQL 한 문장은 DB가 그 자체로 원자적으로 실행하고, Spring Data JPA 리포지토리의 기본 메서드(`save`, `delete` 등)에는 이미 자체 트랜잭션이 붙어 있기 때문이다.

트랜잭션이 필요한 것은 **여러 명령으로 이루어진** 서비스 메서드다.

- 여러 번 조회하는 사이에 앞에서 읽은 값이 바뀔 수 있다.
- 여러 번 수정하다가 두 번째에서 오류가 날 수 있다.

이런 작업은 묶어서 한 번에 처리되게 해야 한다. 실제로는 대부분의 서비스 메서드가 여기에 해당하므로 일반적으로 트랜잭션을 많이 건다. "필요 없는 작업은 안 해도 되지 않을까?"라는 질문을 던지고 실용적인 답을 찾는 태도는 좋다. 다만 그 판단을 하려면 트랜잭션이 **왜** 필요한지 알아야 한다.

## 2. 트랜잭션은 누가 하는가

트랜잭션은 사실 **스프링이 아니라 DBMS가** 해준다. DBMS가 COMMIT·ROLLBACK 기능을 제공하고, JDBC API도 커넥션 하나를 가지고 모든 작업을 끝낸 다음 `commit()`, 오류가 나면 `rollback()`을 하는 방법을 제공한다.

문제는 이 조건이다. **여러 작업이 같은 커넥션을 써야 한다.** 그런데 우리는 커넥션을 직접 다루지 않는다. 커넥션은 리포지토리 **안에** 있어서, 거기에 손을 넣어 "커넥션 내놔 봐"라고 꺼낼 방법이 없다. 리포지토리 메서드가 리턴되면서 커넥션은 닫히고 커밋되었을 텐데, 서비스 메서드 안의 리포지토리 호출 5~6개의 커넥션을 내가 다 꺼내서 관리할 수 있을까?

이것을 도와주는 것이 `@Transactional`이다. 그렇다면 이런 궁금증이 생겨야 한다.

- 이 설정이 어떻게 영향을 주는 거지?
- 어떻게 커넥션 **하나를 공유**하게 만드는 거지?

몰라도 `@Transactional`을 쓰는 데는 문제가 없다. 경력자 중에도 이 원리를 모르는 사람이 있다. 하지만 어떻게 동작하는지 알면 응용할 여유가 생긴다.

## 3. 어노테이션 하나로 어떻게 커넥션을 공유하나

### 리플렉션으로 읽고, 앞뒤에 곁다리를 붙인다

`@Transactional`이 붙어 있다는 것은 **리플렉션**으로 읽어낼 수 있다. "이 메서드는 트랜잭션이 필요하구나"를 알았다면, 핵심 로직의 앞뒤에 곁다리 업무를 붙이면 된다.

```
[앞] 커넥션(연결 객체)을 만들고 트랜잭션 시작
     핵심 로직: 리포지토리 호출 여러 번
[뒤] 커밋 또는 롤백
```

여기까지는 AOP로 가능할 것 같다. 그런데 의문이 남는다. 앞에서 만든 커넥션을 **리포지토리들에게 어떻게 들이밀지?** 리포지토리 메서드의 매개변수에 커넥션을 넣을 자리는 없다. 넣을 수 있다고 해도, 핵심 로직 코드에 커넥션을 넘기는 코드를 넣는 것은 바람직하지 않다.

### 답: 스레드에 공유 커넥션을 걸어 둔다

스프링은 커넥션을 **매개변수로 넘기지 않고**, 현재 실행 중인 **스레드에 걸어 둔다.**

1. 부트가 실행되면 `application.yml`의 연결 설정으로 **`DataSource`**(커넥션을 만들어 주는 객체)가 IoC 컨테이너에 담긴다. 모든 리포지토리는 이 `DataSource`에서 커넥션을 얻는다.
2. `@Transactional` 메서드가 시작되면, 앞쪽 곁다리가 `DataSource`에서 커넥션을 하나 얻어 자동 커밋을 끄고, 이것을 **현재 스레드가 이어지는 모든 곳에서 쓸 수 있는 공유 커넥션**으로 등록한다.
3. 리포지토리(JPA, JdbcTemplate 등)는 커넥션이 필요할 때 먼저 **"지금 스레드에 공유 커넥션이 있나?"**를 확인한다.
   - **있으면** 새로 만들지 않고 그 커넥션을 가져다 쓴다.
   - **없으면** 자기 커넥션을 새로 만든다(트랜잭션이 없을 때의 동작).
4. 그래서 서비스 메서드 안의 모든 리포지토리가 **같은 커넥션**을 쓰게 된다.
5. 메서드가 끝나면 뒤쪽 곁다리가 그 커넥션으로 **커밋**하거나, 예외가 났으면 **롤백**하고, 스레드에서 공유 커넥션을 떼어낸다.

```
요청 스레드
 └─ @Transactional createTwo()
     ├─ [앞] DataSource에서 커넥션 얻기 → setAutoCommit(false) → 스레드에 등록
     ├─ categoryRepository.save(①)  → "스레드에 공유 커넥션 있네" → 그걸 사용
     ├─ categoryRepository.save(②)  → 같은 커넥션 사용
     └─ [뒤] 정상: commit() / 예외: rollback() → 스레드에서 해제
```

> **추가 설명 — 실제 이름들**: 스레드마다 따로 값을 보관하는 자바 기능이 **`ThreadLocal`**이다. 스프링은 `TransactionSynchronizationManager`가 이 `ThreadLocal`에 현재 트랜잭션의 커넥션(JPA라면 `EntityManager`)을 보관한다. 트랜잭션의 시작·커밋·롤백은 **트랜잭션 매니저**(JPA는 `JpaTransactionManager`)가 맡는다. JdbcTemplate 같은 스프링의 템플릿 라이브러리는 커넥션을 얻을 때 `DataSourceUtils.getConnection()`을 거치는데, 이 메서드가 바로 "공유 커넥션이 있으면 그것을, 없으면 새로" 규칙을 구현한다. 요청 하나는 보통 스레드 하나에서 처리되므로, 스레드에 걸어 두면 그 요청 처리 동안 어디서든 같은 커넥션을 찾을 수 있다.

> **추가 설명 — 그래서 생기는 주의점**: 공유 커넥션은 **스레드**에 걸려 있으므로, `@Transactional` 메서드 안에서 새 스레드를 만들어(`new Thread`, `@Async` 등) DB 작업을 하면 그 작업은 같은 트랜잭션에 묶이지 않는다. 또 앞뒤에 곁다리를 붙이는 일은 **프록시**가 하므로, 같은 클래스 안에서 자기 메서드를 직접 호출하면 프록시를 거치지 않아 트랜잭션이 걸리지 않는다.

## 4. 앞으로의 흐름 — 개념과 구현체

기업용 애플리케이션을 만들려면 반드시 알아야 하는 것들이 있다. 그리고 각각에는 **개념**과 그 개념으로 만든 **구현체**가 짝으로 있다.

| 알아야 할 것 (구현) | 그 바탕이 되는 개념 |
|---|---|
| **DI** — 3계층 아키텍처에서 객체를 조립 | **IoC** |
| **트랜잭션** — `@Transactional` | **AOP** |
| **시큐리티** — 인증과 권한 | **필터** |

여기에 더해 MVC와 3계층 같은 **아키텍처**를 잘 알아야 한다. 개념과 실제 구현체를 함께 이해하는 것이 목표다.

수업 순서는 트랜잭션 옵션(전파, 격리 수준 등) → 시큐리티 → AOP 심화로 이어지고, 그 사이에 GitHub 러너와 Docker Compose로 CI/CD를 구성해 **푸시만 하면 자동으로 배포**되는 환경을 만든다. 구현한 내용을 리뷰를 거쳐 풀 리퀘스트로 올리는 것 자체가 발표가 된다.

## 5. 한 줄 정리

- 조회만 하는 작업도 **여러 번 읽는 동안 값이 바뀌면 안 된다면** 트랜잭션(고립)이 필요하다. 단, 기본 고립 수준(READ COMMITTED)으로는 다시 읽은 값이 바뀔 수 있으니 필요하면 수준을 올린다.
- SQL 하나로 끝나는 단순 작업은 트랜잭션을 생략할 수 있지만, 여러 명령으로 된 서비스 메서드는 묶어야 한다.
- 트랜잭션은 DBMS가 하고, 스프링은 **같은 커넥션을 공유**하게 만들어 준다.
- 스프링은 커넥션을 매개변수로 넘기지 않고 **스레드(ThreadLocal)에 걸어 두고**, 리포지토리는 "공유 커넥션이 있으면 그것을 쓴다".
- 개념과 구현체: IoC → DI, AOP → 트랜잭션, 필터 → 시큐리티.
