# 스프링 프레임워크 개요와 3계층 아키텍처 — Controller·Service·Repository, Entity와 DTO

스프링이 자바 SE 위에서 기업용 애플리케이션에 어떤 기능을 얹어주는지, 그리고 실제 백엔드를 만들 때 왜 Controller·Service·Repository 세 계층으로 나누는지, 그 사이를 오가는 데이터가 왜 Entity와 DTO로 이름이 달라지는지를 정리한다.

## 1. 스프링은 자바 SE 위에 무엇을 얹은 것인가

자바 SE(Java SE)는 파일 I/O, 콘솔 I/O, 네트워크 I/O, 스레드처럼 **일반적인 로컬 응용 프로그램**을 만들기 위한 API를 제공한다. 스프링은 그 위에 **분산형·기업형 응용 프로그램**을 만들기 위한 API를 얹은 것으로, 결합력을 낮추는 DI, 트랜잭션 처리, 로그 처리, 웹 서블릿, 시큐리티 등을 담당한다. 한마디로 "기업형 응용 프로그램을 보조하기 위한 쉬운 프레임워크"다.

웹을 만들기 위한 스프링의 모듈을 계층으로 그리면 다음과 같다.

| 계층 | 모듈 | 역할 |
|---|---|---|
| 최하단 | 느슨한 결합력과 인터페이스 | 모든 스프링 기능의 토대가 되는 설계 원칙 |
| 그 위 | DI | 객체를 생성·조립해주는 컨테이너 |
| 그 위 | MVC | 웹 요청을 처리하는 구조 |
| 그 위 | AOP, 트랜잭션 | 횡단 관심사·트랜잭션 처리 |
| 최상단 | Servlet Filter, 인증과 권한 | 요청이 들어오고 나갈 때의 보안 처리 |

## 2. Enterprise 애플리케이션의 기본 구조

기업형 웹 애플리케이션의 요청 흐름을 그리면 다음과 같은 층이 순서대로 놓인다.

```
[요청] → Security(Filter) → Front Controller(Dispatcher) → Controller
       → (DI) → Service → (DI) → Dao(Data Access) → DB
                    ↑              ↓
                   AOP/Transaction  (조회 결과)
       ← [응답] ← View(JSP/Thymeleaf) ←──────────┘
```

- **Security/Filter**: 요청이 들어오고 나갈 때 인증·권한을 검사한다.
- **Front Controller(Dispatcher)**: 모든 요청을 받아 알맞은 Controller로 위임하는 관문.
- **Controller → Service → Dao**: 입출력, 업무 로직, 데이터 접근이 계층별로 분리된 구조.
- **View**: 과거에는 JSP만 있었지만, 이후 Thymeleaf 같은 대안도 등장했다. 데이터 접근 계층도 시대에 따라 발전했다 — 처음엔 JDBC를 직접 썼고, SQL 작성 패턴이 반복되자 MyBatis가, 그 뒤 SQL조차 직접 쓰지 않는 JPA+Hibernate(JPA+HB)가 등장했다.

### 어떤 순서로 배울 것인가

스프링을 배우는 순서는 보통 Spring DI → Spring MVC → Spring Transaction → Spring AOP → Spring Security 순이며, 설정 방식도 시대에 따라 XML/애노테이션/Java Config(Spring 5.x)에서 지금의 Spring Boot(`properties`/`yaml`)로 옮겨왔다.

## 3. 왜 화면 로직을 서버(백엔드)로 가져가는가

프론트(React 등)에서 원격 DB의 원본 데이터(raw data)를 직접 받아, 클릭 이벤트 핸들러 안에서 그 데이터를 가공하고 톡(좋아요) 처리까지 다 하는 방식은 소규모 앱이 아니면 쓰지 않는다. 대신 다음처럼 역할을 나눈다.

- **클라이언트(프론트)**: 사용자와 상호작용하는 UI 담당. `handleMenuList()`, `handleToggleLike()`처럼 사용자 입력을 받는 핸들러만 가진다.
- **서버(백엔드)**: 실제 업무 로직을 담당. `getList()`, `toggleLike()`처럼 업무 기능을 제공한다.

클라이언트가 멀리 떨어진 서버의 기능을 직접 호출할 수 없으므로, 그 사이를 이어주는 존재가 필요하다 — 이것이 바로 **Controller**다. Controller는 원격에 있는 서버와 대화하기 위한 창구 역할만 하고, 실제 업무(데이터를 저장하고 조회하고 가공하는 일)는 **Service**가 갖고 있다.

## 4. 3계층 — Controller, Service, Repository

업무 로직(서비스)이 다루는 데이터가 하나의 테이블뿐이라면 굳이 계층을 나눌 필요가 없어 보이지만, 실제 업무는 여러 데이터 소스(파일, 여러 테이블, 원격 API 등)를 조합해야 하는 경우가 대부분이다. 이때 서비스(업무 로직을 만드는 사람) 입장에서 "데이터가 파일에 있는지, DB에 있는지, 어떤 형태로 저장돼 있는지"까지 알아야 한다면 너무 무거워진다.그래서 서비스는 데이터를 어떻게 가져오는지 몰라도 되도록 만들어야 한다. 이 역할을 맡는 것이 **리포지토리(Repository, 예전 이름은 DAO)**다 — 데이터 저장소를 관리하고, 서비스에게 CRUD 함수만 제공하는 대리자.

```
Controller  →  Service   →  Repository  →  DB
(입출력 I/O)   (업무 Business)  (데이터 Data)
```

- **Controller**: 사용자(또는 원격 클라이언트)와의 입출력만 담당.
- **Service**: 업무 로직을 담당. 여러 데이터 소스를 조합해 화면에 필요한 데이터를 만든다.
- **Repository**: 데이터 저장소 접근을 담당(`save()`, `fetchAll()`, `update()`, `delete()` 등).

업무가 아주 단순해서 단일 테이블·단일 업무로 끝나면 Service와 Repository의 함수 이름이 거의 같아지는 경우도 있지만(예: `update` → `update`), 실무에서는 하나의 업무가 여러 테이블·여러 데이터 소스에 걸치는 경우가 훨씬 많다.

## 5. Repository는 Entity를 반환하고, Service는 그것을 모델로 바꾼다

데이터베이스에서 가져오는 데이터는 **정규화되어 있다.** Repository가 DB에서 읽어온 레코드를 자바 객체로 옮겨 담을 때 쓰는 그릇이 **엔티티(Entity)**다 — 정규화된 테이블 하나에 대응하는, 자체 속성의 집합이다.

```
DB(정규화된 테이블) --entity--> Repository --entity--> Service --model(DTO)--> Controller
```

- 엔티티는 정규화돼 있어서 그 자체로는 "화면에 보여줄 데이터"가 아니다. 예를 들어 카테고리명을 화면에 보여주려면 카테고리 엔티티와 메뉴 엔티티를 조합해야 하는데, 정규화된 엔티티 하나만으로는 그 조합이 빠져 있다.
- **Service**는 여러 엔티티를 조합해 "화면에 출력할 최소한의 데이터"인 **모델(Model)**을 만든다. MVC의 M이 바로 이것이다.
- 서버 페이지(JSP처럼 View가 있는 구조)라면 이 모델이 View로 바로 전달되지만(M→V), 지금처럼 **API를 만드는 경우 View가 없으므로** 모델은 화면에 직접 소비되지 않는다. 대신 Controller가 이 모델을 원격(클라이언트)으로 전달하는데, 이렇게 **원격으로 전달되는 모델**을 부르는 이름이 따로 있다 — 바로 **DTO(Data Transfer Object)**다.

즉 "모델"이라는 개념 자체는 그대로지만, API를 만들 때는 그 모델을 관례적으로 DTO라고 부른다. 그래서 프로젝트 폴더도 `entity`(정규화된 데이터가 담기는 그릇)와 `dto`(원격으로 내보낼 데이터가 담기는 그릇)를 따로 두고, 이 둘은 목적이 다른 별개의 자료구조로 취급한다.

## 6. 정리

| 개념 | 핵심 |
|---|---|
| 스프링의 위치 | 자바 SE 위에 분산형·기업형 애플리케이션을 위한 API(DI, 트랜잭션, 로그, 웹, 보안 등)를 얹은 것 |
| Enterprise 앱 구조 | Security/Filter → Front Controller → Controller → Service → Repository → DB, 그리고 View(JSP/Thymeleaf) |
| 계층을 나누는 이유 | 껍데기(입출력)와 실제 업무(데이터 가공)를 분리해, 업무 로직이 데이터 소스의 형태를 몰라도 되게 한다 |
| Controller | 사용자(또는 원격 클라이언트)와의 입출력 담당. 원격 서비스와 대화하는 창구 |
| Service | 여러 데이터(엔티티)를 조합해 업무 로직을 처리하고 모델을 만든다 |
| Repository | 데이터 저장소 접근을 대리하는 창구. CRUD 함수만 제공 |
| Entity | 정규화된 테이블 하나에 대응하는 자료구조. Repository가 다룬다 |
| Model/DTO | Service가 여러 엔티티를 조합해 만든, 화면(또는 원격 클라이언트)에 필요한 최소 데이터. API에서는 이를 DTO라 부른다 |
