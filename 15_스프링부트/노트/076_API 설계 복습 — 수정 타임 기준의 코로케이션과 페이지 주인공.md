# API 설계 복습 — 수정 타임 기준의 코로케이션과 페이지 주인공

여러 조가 같은 관리자 메뉴 화면을 놓고 API와 DTO를 설계해본 결과를 리뷰하면서, 그 설계들을 관통하는 단 하나의 기준 — **수정 타임이 같은 것끼리 모아라** — 을 다시 정리한다. 이 기준이 폴더 구조, API 분리, 컨트롤러·서비스 관계까지 전부 똑같이 적용된다는 것을 확인한다.

## 1. 여러 조 설계에서 반복된 쟁점들

같은 화면(메뉴 목록 + 요약 카드 + 카테고리 필터)을 두고 여러 조가 설계했는데, 세부 선택은 갈렸지만 공통적으로 부딪힌 지점들이 있었다.

- **엔드포인트 이름**: `summary`로 할지 `status`로 할지 고민한 조가 많았다. "여러 상태를 집계해서 통계를 보여준다"는 의미에 더 가까운 쪽은 `summary`(또는 `stats`)다.
- **엔티티를 그대로 쓰면 안 되는 이유**: 카테고리 DTO의 속성(`id`, `name`, `sortOrder`)이 엔티티와 거의 같아 보여도, 엔티티를 그대로 끌어다 쓰면 입출력 계층(DTO가 사는 곳)과 저장 계층(엔티티가 사는 곳)이 한 몸으로 엮인다. 나중에 입출력 쪽만 필드를 추가/삭제하고 싶어도 엔티티까지 건드려야 하므로, 3계층을 나눈 의미 자체가 사라진다. "속성이 같으니 재사용하자"는 생각은 경계해야 한다.
- **뷰 전용 정보(상태별 색상)**: 백엔드가 "판매중"이라는 문자열만 내려주고 그 글자에 어떤 색을 입힐지는 프론트가 조건 처리하는 방식이 일반적이다. 다만 상태 종류가 나중에 늘어나면 프론트도 그만큼 분기를 추가해야 한다는 한계는 있다.
- **"신상품(New)" 뱃지**: 이걸 DB 컬럼(`isNew`)으로 그대로 내려줄지, 등록일 기준으로 프론트가 "최근 N일 이내"를 계산해서 표시할지로 의견이 갈렸다. 단순 "최근 등록"이면 프론트 계산도 가능하지만, "단종됐다가 재출시된 메뉴를 다시 신상품으로 홍보하는 시즌성 캠페인" 같은 업무 로직이 섞이면 등록일만으로는 표현할 수 없으므로 백엔드가 관리하는 게 맞다. 핵심은 "그 값이 순수한 날짜 계산인가, 아니면 업무 판단(기획)이 들어간 값인가"로 구분하는 것이다.
- **과도한 유연성 경계**: 한 조는 한 페이지에 보여줄 개수(`pageSize`)까지 요청 DTO에 포함시켜 프론트가 결정하게 했다. 의도(디자인이 바뀔 수 있다, 사용자가 나중에 표시 개수를 선택할 수도 있다)는 타당하지만, **지금 화면에 없는 기능까지 미리 대비하는 것은 오버 엔지니어링**이 될 수 있다. 예측이 확실할 때만 미리 유연하게 만들고, 불확실하면 지금 스펙에 맞춰 구현한 뒤 필요할 때 수정하는 편이 비용 대비 합리적이다.

## 2. 핵심 원칙 — 수정 타임이 같은 것끼리 모아라 (코로케이션)

이 모든 쟁점을 관통하는 질문은 하나다 — **"내가 이걸 수정하려고 할 때, 고쳐야 할 코드가 한곳에 모여 있는가, 아니면 여기저기 흩어져 있는가?"**

이 기준은 객체지향 이전, 구조적 프로그래밍 시절부터 이미 존재했다. 함수가 많아지면 어딘가에 수납해야 하는데, **기능별로 묶을지 데이터별로 묶을지**를 고민하게 된다. 둘 중 무엇을 고르든, 그 이유는 "직관적이라서"나 "남들이 그렇게 써서"가 아니라 **유지보수 — 즉 수정의 용이성** 때문이어야 한다. 수정이 용이하다는 것은 수정 타임(같은 이유로 같이 바뀌는 코드)이 같은 것들을 한곳에 모아둔다는 뜻이다.

같은 원리가 웹 퍼블리싱 역사에서도 그대로 드러난다.

- **옛날 방식**: `css/`, `html/` 폴더를 따로 두고 그 안에 파일들을 종류별로 모았다. 겉보기엔 깔끔해 보이지만, HTML 하나를 고치려면 CSS 폴더까지 왔다 갔다 해야 하고, 페이지 하나를 다른 곳으로 옮기려면 흩어진 파일들을 전부 찾아서 옮겨야 했다.
- **지금 방식(코로케이션, co-location)**: `index.html`과 `index.css`, `list.html`과 `list.css`처럼 **같이 수정될 일이 많은 파일을 같은 폴더에 옹기종기 모아둔다.** 결합력이 강한 것, 수정 타임이 같은 것끼리 묶는 구조가 결국 승자가 되었다.

이 기준은 "타입(종류)별로 나눌까, 용도(수정 단위)별로 나눌까"라는 질문에서 **항상 후자를 선택해야 한다**는 것을 보여준다.

**계층 구조와 코로케이션은 서로 다른 축의 질문이라는 점도 헷갈리면 안 된다.** "컨트롤러끼리, 서비스끼리, 리포지토리끼리 묶여 있는 지금 스프링 프로젝트 구조는 코로케이션 원칙에 어긋나는 것 아니냐"는 질문이 나올 수 있는데, 그렇지 않다. 계층을 나누는 것(Controller/Service/Repository)은 "책임의 종류"를 나누는 문제이고, 코로케이션은 "같은 책임 안에서 수정 단위를 어떻게 묶을 것인가"를 다루는 문제다. 즉 코로케이션은 계층 구조를 대체하는 게 아니라 **계층 내부에서** 적용되는 기준이다 — 예를 들어 서비스 계층 안에서 "메뉴와 관련된 모든 서비스 로직을 한곳에 모을 것인가, 기능별로 흩어 둘 것인가"를 결정할 때 코로케이션 원칙이 작동한다. (도메인 단위로 계층 자체를 묶는 방식은 헥사고널 아키텍처나 DDD처럼 완전히 다른 결의 이야기이며, 지금 당장 섞어 쓸 내용은 아니다.)

## 3. 페이지는 주인공이다 — 과거의 실패와 지금의 균형점

이 코로케이션 원칙을 API 설계에 적용하면 072번 노트의 "주인공/곁다리" 규칙이 왜 그렇게 정해졌는지가 더 분명해진다.

**아주 예전 방식**: 프론트 페이지 하나에 API 하나를 1:1로 대응시켰다. 메뉴 페이지면 그 페이지에 필요한 모든 데이터(메뉴 목록 + 카테고리 + 상태 통계)를 **하나의 거대한 DTO**에 전부 욱여넣어 한 번에 내려줬다. 문제는 분명했다 — 카테고리 하나만 바뀌어도 메뉴 목록까지 전부 다시 내려받아야 했고, 서버 부하도 컸으며, 화면의 일부만 갱신하고 싶어도 전체를 다시 가져와야 했다.

**쪼개기 시작하면서 생긴 새 고민**: 그러면 카테고리 데이터는 어디서 제공해야 할까? "카테고리는 카테고리답게 전담 컨트롤러에서 관리해야 한다"는 의견과 "메뉴 페이지에서만 쓰는 카테고리라면 메뉴 컨트롤러가 곁다리로 제공하면 된다"는 의견이 갈렸다.

**결론은 후자다.** 그 페이지가 사용할 모든 데이터(주인공 + 곁다리)는 **그 페이지를 책임지는 컨트롤러 하나가 전부 제공**해야 한다. 이유는 똑같다 — 이 페이지를 수정하려 할 때 고쳐야 할 코드가 여기저기(카테고리 컨트롤러, 메뉴 컨트롤러, 별도 통계 유틸)로 흩어지면 안 되기 때문이다. 페이지는 결코 하찮은 존재가 아니라, API 설계의 **결정권자(회장님)**이고, 컨트롤러는 그 결정권자의 업무를 수행하는 비서실(실무자)에 가깝다 — "업무를 수행하는 쪽이 결정권자에게 맞춰야지, 결정권자가 실무자 사정에 맞출 수는 없다"는 비유다.

## 4. 컨트롤러-서비스 관계: 1:1인가, 다대다인가

곁다리 데이터(카테고리, 상태 통계)를 컨트롤러가 제공해야 한다면, 그 데이터를 실제로 조립하는 **서비스 계층**은 어떻게 구성해야 할까? 두 가지 안이 맞붙었다.

**안 1 — 전문 서비스로 쪼개서 컨트롤러가 조합(다대다)**: 카테고리 전용 서비스, 상태 통계 전용 서비스를 각각 두고, 메뉴 컨트롤러가 이들을 호출해서 조립한다.

- 장점: 전문성 — "카테고리는 카테고리 서비스가 전담"이라는 명확함, 여러 컨트롤러에서 재사용 가능.
- 단점: 컨트롤러 하나가 여러 서비스와 의존 관계를 맺는 순간, 그 서비스들을 공유하는 다른 컨트롤러와도 간접적으로 엮이게 된다. 재사용을 위해 이름이 점점 길어지고(`findCategoriesForMenuController`처럼), 공통분모를 합치려다 보면 서로 다른 컨트롤러들이 같은 서비스 메서드를 두고 "이건 못 바꿔, 쟤도 쓰고 있어"라며 수정 범위가 걷잡을 수 없이 넓어진다.

**안 2 — 페이지(도메인)를 전담하는 서비스 하나가 곁다리까지 책임(1:1)**: 메뉴 컨트롤러는 메뉴 서비스 하나만 쓰고, 그 메뉴 서비스가 내부에서 카테고리 리포지토리·통계 쿼리까지 직접 처리한다.

- 장점: 메뉴 페이지와 관련된 수정은 전부 메뉴 서비스 한곳에 모인다 — 캡슐이 곧 수정 범위가 된다는 객체지향의 기본 원칙과 일치한다.
- 단점: 여러 컨트롤러가 비슷한 카테고리 조회 로직을 필요로 하면, 그 로직이 각 서비스에 중복으로 구현될 수 있다.

**결론은 안 2다.** "효율을 높이자고 코드를 공유시키는 선택"은 사실 **공유되는 두 존재를 하나로 묶어버리는 결정**과 같다. 여러 컨트롤러가 같은 전문 서비스에 의존하면, 그 서비스를 고칠 때마다 의존하는 모든 컨트롤러가 함께 영향을 받는 "한 몸" 상태가 된다. 반대로 서비스를 도메인(페이지의 주인공) 단위로 묶고 그 서비스가 자신에게 필요한 곁다리까지 전부 책임지게 하면, 수정 범위가 그 서비스 하나로 고립된다. (이 원칙을 더 밀어붙인 것이 **도메인 주도 설계(DDD)**이며, 도메인별로 서비스·컨트롤러·리포지토리까지 묶는 방식은 별도로 다룰 주제다.)

정리하면, API를 설계할 때 결정 순서는 다음과 같다.

1. 이 페이지의 **주인공(도메인)**이 무엇인지 정한다.
2. 그 주인공을 책임지는 **컨트롤러 하나**가 이 페이지에 필요한 주인공 데이터와 곁다리 데이터를 전부 제공한다.
3. 그 컨트롤러는 **전담 서비스 하나**만 사용하고, 그 서비스가 곁다리 데이터 조회까지 스스로 책임진다.
