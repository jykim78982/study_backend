# 전파 옵션 다시 보기 — 도메인 부모와 트랜잭션 부모, 테스트로 확인하기

전파 옵션을 **누가 갖는지**를 다시 정리하고, 메뉴 서비스가 카테고리 서비스를 호출하는 예제로 `REQUIRED`와 `REQUIRES_NEW`의 차이를 테스트로 확인한다. 이어서 `SUPPORTS`, `MANDATORY` 같은 나머지 옵션의 쓰임새를 본다.

## 1. ACID에서 이번에 다루는 위치

| ACID | 스프링에서 다루는 방법 |
|---|---|
| **A**tomicity (원자성) | `@Transactional` 하나만 붙이면 지켜진다 (이미 확인) |
| **C**onsistency (일관성) | **전파 옵션** — 서비스가 서비스를 부를 때 작업을 어디까지 한 덩어리로 묶을지 |
| **I**solation (고립성) | **격리 수준** — 읽는 동안 다른 트랜잭션의 영향을 막는다 |

> **추가 설명 — 전파 옵션과 ACID**: 전파 옵션이 정하는 것은 "어떤 작업들이 **같은 트랜잭션(같은 원자 단위)**에 들어가는가"이다. 그래서 원자성이 **어디까지 적용되는지**를 정하는 옵션으로 보는 설명도 많다. 강의는 업무적으로 함께 반영되어야 할 데이터가 함께 반영되도록 한다는 점에서 일관성과 연결해 설명했다.

## 2. 전파 옵션은 누가 갖나 — "부모"가 두 가지다

### 도메인 부모에게 붙인다

전파 옵션은 **도메인 단위로 봤을 때 부모** 쪽 서비스에 둔다. 기본값인 `REQUIRED`는 생략하므로, 따로 전파 옵션을 적는 곳은 부모 서비스다.

왜 부모일까? 서비스가 서비스를 호출하는 방향은 **자식 → 부모**다(결제 → 주문, 메뉴 → 카테고리). 그래서 부모 서비스는 두 곳에서 호출될 수 있다.

```
[Controller] ──────────────────▶ [부모 서비스]   ← 트랜잭션 없이 들어온다 (문제없음)
[Controller] → [자식 서비스] ──▶ [부모 서비스]   ← 자식이 연 트랜잭션(커넥션)을 물고 들어온다
```

- 컨트롤러만 나를 호출한다면 트랜잭션을 물고 오는 일이 없으니 전파 옵션이 필요 없다.
- 그런데 **자식 서비스도 나를 호출**할 수 있다. 자식이 이미 커넥션을 열어 둔 상태로 들어오면 "그 트랜잭션에 같이 탈까, 나는 새로 만들까?"를 정해야 한다. 이것 때문에 전파 옵션이 필요하다.

부모·자식은 상대적이다. 지금 자식인 서비스도 다른 누군가에게는 부모가 된다. 그래서 대체로 **도메인에서 위쪽에 있는 서비스들**이 전파 옵션을 갖게 된다.

### 트랜잭션 부모·자식은 반대다

트랜잭션의 호출 관계에서도 부모·자식이라는 말을 쓴다. 이때는 **트랜잭션을 먼저 만든 쪽**(호출한 쪽)이 부모, 그 트랜잭션에 들어오는 쪽(호출당한 쪽)이 자식이다.

| 관점 | 메뉴 서비스 (호출하는 쪽) | 카테고리 서비스 (호출당하는 쪽) |
|---|---|---|
| **도메인** | 자식 (메뉴는 카테고리에 속한다) | **부모** |
| **트랜잭션** | 부모 (트랜잭션을 먼저 만든다) | **자식** |
| 전파 옵션을 두는 곳 | | ⭕ |

결국 전파 옵션을 두는 곳은 **도메인 부모 = 트랜잭션 자식 = 호출당하는 쪽**으로 모두 같은 서비스다. 다만 말로 할 때 어느 부모인지 밝히지 않으면 정반대로 알아들을 수 있다.

> "부모에다가 전파 옵션 쓰는 거 맞지?" → (트랜잭션 부모로 알아들은 상대) "아니요, 부모에는 쓰면 안 됩니다."

AI에게 지시할 때도 마찬가지다. "부모 서비스"라고만 하면 AI가 헷갈릴 수 있으니, **도메인 단위의 부모**인지 **트랜잭션 호출 관계의 부모**인지 분명하게 풀어서 말해야 한다.

## 3. 예제 시나리오 — 메뉴를 등록하면서 카테고리도 등록

메뉴 서비스는 자기 주인공인 메뉴를 메뉴 리포지토리로 저장한다. 그런데 업무상 **카테고리가 없는 메뉴를 등록할 때 카테고리도 함께 등록**해야 한다고 하자.

정상이라면 메뉴 서비스가 카테고리 리포지토리를 직접 써도 된다. 하지만 카테고리 등록 로직이 **복잡하다**고 가정한다. 새로 만들면 업무 규칙을 어기거나 놓칠 수 있으니, 이미 있는 **부모(카테고리) 서비스를 가져다 쓴다**.

```java
@Service
public class CategoryService {

    @Transactional                                         // REQUIRED (기본값이라 생략)
    public Category createRequired(String name, String slug) { ... }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public Category createRequiresNew(String name, String slug) { ... }
}
```

```java
@Service
public class MenuService {

    @Transactional
    public void createWithCategoryRequired(String menuName, int price,
                                           String categoryName, String slug) {
        menuRepository.save(new Menu(menuName, price));          // 내 주인공 먼저 저장
        categoryService.createRequired(categoryName, slug);      // 부모 서비스 사용
    }

    @Transactional
    public void createWithCategoryRequiresNew(String menuName, int price,
                                              String categoryName, String slug) {
        menuRepository.save(new Menu(menuName, price));
        try {
            categoryService.createRequiresNew(categoryName, slug);
        } catch (DataIntegrityViolationException e) {
            System.out.println("카테고리 등록 실패: " + e.getClass().getSimpleName());
        }
    }
}
```

## 4. 테스트 만들기

### 테스트 파일 생성

VS Code에서 서비스 클래스를 열고 마우스 오른쪽 버튼 → **소스 작업(Source Action)** → **테스트 생성(Generate Tests)**을 고른다. 테스트할 메서드 두 개를 모두 선택하면 테스트 파일이 만들어진다.

### 테스트 클래스의 뼈대

```java
@SpringBootTest                 // 테스트마다 스프링(IoC 컨테이너)을 통째로 띄운다
@ActiveProfiles("test")         // application-test.yml 설정을 쓴다
class MenuServiceTest {

    @Autowired MenuService menuService;               // 테스트라서 간단히 필드 주입
    @Autowired MenuRepository menuRepository;
    @Autowired CategoryRepository categoryRepository;

    @BeforeEach                 // 각 테스트 실행 직전에 매번 실행
    void setUp() {
        menuRepository.deleteAll();       // 메뉴가 카테고리를 참조하므로 메뉴부터 지운다
        categoryRepository.deleteAll();
        categoryRepository.save(new Category("음료", "beverage"));   // 일부러 충돌시킬 데이터
    }
}
```

- 서비스는 단독으로 실행할 수 없고 **IoC 컨테이너가 만들어 주입**해야 동작한다. 그래서 `@SpringBootTest`가 꼭 필요하다.
- `@ActiveProfiles("test")`를 쓰면 `application-` 뒤에 그 이름이 붙은 설정 파일(`application-test.yml`)을 찾아 쓴다. 생략하면 `application.yml`을 쓴다. 용도별로 `application-test2.yml`처럼 여러 개를 만들어 두고 골라 쓸 수도 있다.
- 필드 주입 대신 생성자 주입을 써도 된다. 테스트용이라 간단하게 처리했다.

### 먼저 빈 테스트로 환경 확인

본 테스트를 실행하기 전에 **아무 내용 없는 테스트 메서드**를 먼저 실행한다. 아무것도 안 하는 것 같지만 스프링이 부팅되면서 `ddl-auto: update` 설정에 따라 **엔티티를 기준으로 테이블이 만들어진다.** 본인 DB에 `category`와 `menu` 테이블이 생겼는지, 둘 다 비어 있는지 확인한다.

> **주의 — 반드시 개인 DB를 쓴다**: 강사가 준 프로젝트를 그대로 쓰면 설정 파일이 강사 DB를 가리키고 있다. 여러 명이 같은 DB에 테스트를 돌리면 결과가 서로 꼬여 확인할 수 없으니, 연결 정보를 **본인 DB로** 바꾼다.

### 오류를 일부러 내는 방법

처음 비어 있는 테이블에 넣으면 아무 오류도 나지 않는다. 롤백을 보려면 **카테고리 등록 중에 오류**가 나야 한다. 카테고리 엔티티를 보면 `slug`에 **UNIQUE 제약 조건**이 걸려 있다.

```java
@Column(unique = true)
private String slug;
```

`setUp()`에서 `("음료", "beverage")`를 미리 넣어 두고, 테스트에서 `("신규 음료", "beverage")`를 넣으면 slug가 겹쳐 `DataIntegrityViolationException`이 난다. 테이블 구조는 DB 도구를 열지 않아도 **엔티티를 보면 된다.** 이 테이블은 엔티티로 만들어졌기 때문이다.

## 5. REQUIRED — 함께 롤백된다

```java
@Test
void createWithCategoryRequired() {
    System.out.println("========== 전파 테스트 시작: REQUIRED ==========");
    try {
        menuService.createWithCategoryRequired("아메리카노", 4500, "신규 음료", "beverage");
    } catch (Exception e) {
        System.out.println("예외 발생: " + e.getClass().getSimpleName());   // 이름만 짧게
    }
    System.out.println("메뉴 건수: " + menuRepository.count());
    System.out.println("카테고리 건수: " + categoryRepository.count());
}
```

- 출력 앞뒤에 `=====`를 붙인 것은 스프링 로그에 묻혀 안 보이는 것을 막기 위해서다.
- `e.getMessage()`는 호출 경로가 길게 찍히므로, `e.getClass().getSimpleName()`으로 **예외 이름만** 출력했다.
- `count()`는 직접 구현한 것이 아니라 Spring Data JPA 리포지토리가 이미 제공하는 메서드다. DB를 열지 않고도 건수로 결과를 확인할 수 있다.

**흐름**: 카테고리 서비스는 기본 옵션(`REQUIRED`)이라, 메뉴 서비스가 연 트랜잭션에 "아, 네가 만들었구나. 내 것도 거기 묶어서 같이 해"라며 **참여**한다. 카테고리에서 오류가 나면 같은 트랜잭션에 있던 메뉴 저장도 **함께 롤백**된다.

| 결과 | 값 |
|---|---|
| 예외 | `DataIntegrityViolationException` (slug 중복) |
| 메뉴 건수 | **0** (아메리카노는 롤백) |
| 카테고리 건수 | **1** (`setUp()`에서 넣은 "음료"만) |

slug를 `"new-beverage"`처럼 겹치지 않게 바꿔 실행하면 오류 없이 메뉴와 카테고리가 **둘 다** 들어가는 것도 확인해 본다.

## 6. REQUIRES_NEW — 안쪽만 롤백된다

테스트 코드는 같고, 호출하는 메서드만 `createWithCategoryRequiresNew`로 바꾼다. 실행 전에 결과를 먼저 예상해 본다.

```
메뉴 서비스  ── 커넥션① (setAutoCommit(false), 스레드에 보관)
 ├─ menuRepository.save()  → 커넥션① 참여
 ├─ categoryService.createRequiresNew()   "필요 없어, 나는 새로 할 거야"
 │    ├─ 커넥션①은 잠시 멈춤(suspend)
 │    ├─ 커넥션② 새로 만들어 사용
 │    └─ slug 중복 오류 → 커넥션② rollback
 ├─ 커넥션① 다시 이어서 (이 커넥션 안에서는 오류가 난 적 없음)
 └─ 커넥션① commit → 아메리카노 저장
```

| 결과 | 값 |
|---|---|
| 메뉴 건수 | **1** (바깥 트랜잭션은 커밋) |
| 카테고리 건수 | **1** (안쪽은 롤백, `setUp()`의 "음료"만 남음) |

결과가 1건, 1건이 아니라면 설정이 잘못되었을 가능성이 크다.

> **추가 설명 — 메뉴가 커밋되려면 예외를 바깥에서 잡아야 한다**: `REQUIRES_NEW`라도 안쪽에서 난 예외가 **메뉴 서비스 메서드 밖으로 그대로 던져지면**, 메뉴 서비스의 프록시도 예외를 보고 커넥션①을 롤백한다. 그러면 메뉴 건수도 0이 된다. 위 코드처럼 메뉴 서비스 안에서 `try-catch`로 카테고리 예외를 잡아야 "안쪽만 롤백, 바깥은 커밋"이 된다.
>
> 반대로 `REQUIRED`일 때 메뉴 서비스가 예외를 잡아 버리면, 같은 트랜잭션이 이미 **rollback-only**로 표시되어 있어 커밋 시점에 `UnexpectedRollbackException`이 나고 전체가 롤백된다. 이렇게 **예외를 잡았을 때** 두 옵션의 차이가 가장 분명하게 드러난다.

## 7. 나머지 전파 옵션 — 부모 입장에서 읽기

전파 옵션은 **도메인 부모 서비스의 입장**에서 "자식이 트랜잭션을 물고 왔을 때 / 컨트롤러가 그냥 불렀을 때 나는 어떻게 할까"를 정하는 것이다.

| 옵션 | 자식 서비스가 호출 (트랜잭션 있음) | 컨트롤러가 호출 (트랜잭션 없음) | 의미 |
|---|---|---|---|
| `REQUIRED` | 참여 | 새로 만든다 | 기본값 |
| `REQUIRES_NEW` | 기존 것을 멈추고 새로 만든다 | 새로 만든다 | "나는 항상 따로 할래" |
| `SUPPORTS` | 참여 | **트랜잭션 없이** 실행 | 나 혼자일 땐 트랜잭션이 필요 없지만, 자식이 끼워 넣으면 맞춰 준다 |
| `MANDATORY` | 참여 | **예외** | "컨트롤러는 나를 쓰지 마. 트랜잭션을 가진 자식만 부를 수 있어" |
| `NOT_SUPPORTED` | 기존 것을 멈추고 트랜잭션 없이 실행 | 트랜잭션 없이 실행 | "트랜잭션 처리 안 할 거야, 건들지 마" |

> **추가 설명**: `MANDATORY`인 메서드를 트랜잭션 없이 호출하면 `IllegalTransactionStateException`이 발생한다. 옵션 전체 목록(`NEVER`, `NESTED` 포함)은 앞서 정리한 전파 옵션 표와 같다.

커넥션을 어떻게 공유하는지 이해했다면, 옵션 이름과 설명만 읽어도 동작이 그려진다.

## 8. 전파 옵션을 AI에게 맡기면 안 되는 이유

트랜잭션은 신입 면접에서 거의 반드시 묻는 주제다. 그런데 전파 옵션 설정을 AI에게 맡기면 잘할까?

- AI는 **범용 지식**을 가지고 있다. 우리 회사의 **업무**를 모른다.
- 전파 옵션에는 "모든 회사에 통하는 정답"이 없다. 어떤 작업을 함께 롤백할지, 따로 남길지는 **업무 규칙**이 정한다.
- AI는 **일괄 변경**하는 성향이 있다. A 서비스의 옵션만 바꿔 달라고 했는데 다른 서비스까지 바꿔 놓고 "실무에서는 이렇게 많이 씁니다"라고 한다.

그래서 AI에게 맡기려면 먼저 **룰셋**을 빼곡하게 만들어 둬야 한다. "우리는 이런 업무가 있고, 이 업무에서 저 업무를 호출할 때 전파 옵션은 이것이다"를 정해 둔 다음 시키면 가능하다. 이렇게 업무를 미리 알려준 AI는 더 이상 범용 AI가 아니라 **우리 AI**가 된다.

## 9. 문제 해결 메모

| 증상 | 원인 | 해결 |
|---|---|---|
| `UnsupportedClassVersionError` | 프로젝트가 설치된 것보다 **높은 JDK**(21)로 빌드됨 | JDK 21 설치, 또는 Gradle의 Java 버전을 17로 낮춤 (Spring Boot 4.x는 17 이상이면 동작) |
| JDK를 바꿨는데 같은 오류 | 예전에 **컴파일된 결과**(`bin/`, `build/`)가 남아 있음 | 빌드 결과 폴더를 지우고 다시 빌드 |
| 테이블이 하나만 생김 | 부팅 중 오류로 DDL이 끝까지 실행되지 않음 | 콘솔 오류부터 확인 |
| 결과 건수가 예상과 다름 | 다른 사람 DB를 공유해서 씀 | 설정 파일의 DB 연결을 개인 DB로 변경 |
| 테스트 파일이 깨지거나 사라짐 | 클래스 전체를 덮어쓰며 도구가 꼬임 | 클래스 안쪽 메서드만 붙여 넣기 |

## 10. 한 줄 정리

- 전파 옵션은 **도메인 부모 = 트랜잭션 자식 = 호출당하는 쪽**에 둔다. 말할 때는 어느 "부모"인지 꼭 밝힌다.
- `REQUIRED`: 같은 트랜잭션에 참여 → 안쪽 오류에 **전체 롤백** (메뉴 0, 카테고리 1).
- `REQUIRES_NEW`: 커넥션을 새로 만들어 따로 처리 → 안쪽 예외를 바깥에서 잡으면 **안쪽만 롤백** (메뉴 1, 카테고리 1).
- `SUPPORTS`는 "있으면 참여, 없으면 트랜잭션 없이", `MANDATORY`는 "없으면 예외 — 컨트롤러는 나를 부르지 마".
- 전파 옵션은 **업무 규칙**으로 정한다. AI에게 맡기려면 그 규칙을 먼저 알려 줘야 한다.
