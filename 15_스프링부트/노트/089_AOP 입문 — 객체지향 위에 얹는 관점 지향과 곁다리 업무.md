# AOP — 객체지향 위에 얹는 관점 지향과 곁다리 업무

`@Transactional` 한 줄만 붙였는데 커넥션을 공유하고, 커밋하고, 오류가 나면 롤백까지 해준다. 메서드 안에는 그런 코드가 한 줄도 없는데 어떻게 가능할까? 이것을 이해하려면 **AOP**라는 방법론을 알아야 한다.

AOP는 처음 읽으면 잘 와닿지 않는다. 객체지향도 처음에는 필요성이 느껴지지 않아 이해하기 어려운 것처럼, 아직 그 문제를 겪어보지 않았기 때문이다. 그래도 개념은 알아야 하므로, 왜 이런 방법론이 나왔는지부터 정리한다.

## 1. OOP와 AOP — 앞 글자 하나 차이

| 약어 | 이름 | 무엇을 기준으로 코드를 나누나 |
|---|---|---|
| **OOP** | Object-Oriented Programming, 객체 지향 프로그래밍 | 객체(책임자·역할자) |
| **AOP** | Aspect-Oriented Programming, **관점 지향** 프로그래밍 | 관점(누구를 위한 코드인가) |

AOP가 나왔다고 객체지향을 버리고 새 방식으로 갈아타는 것이 아니다. **객체지향 프로그램은 그대로 두고**, 그 위에서 로직을 바라보는 **또 다른 방법론**이 하나 생긴 것이다.

## 2. 주 업무와 곁다리 업무

### 객체는 사용자의 요구에서 나온다

객체지향에서 객체는 **코드 안에 존재하는 책임자(역할자)**다. 그리고 객체가 만들어지는 가장 기본 원료는 **사용자의 요구**다. 사용자가 "주문하게 해 달라", "메뉴를 관리하게 해 달라", "로그인하게 해 달라"고 요구하면 그것이 객체와 메서드가 된다. 이것이 **주 업무 로직**이다.

### 사용자가 요구하지 않은 코드가 계속 늘어난다

그런데 프로그램을 만들다 보면 **사용자를 위한 것이 아닌 코드**가 자꾸 추가된다.

| 곁다리 코드 | 누구를 위한 것인가 | 사용자가 요구했나 |
|---|---|---|
| **로그** — 실행 순서 확인, 실행 시간 측정 | 개발자, 성능 튜닝 담당자 | ❌ 사용자는 로그가 뭔지도 모른다 |
| **트랜잭션 처리** — 커밋·롤백 | 데이터 일관성을 지켜야 하는 개발자 | ❌ 사용자는 "주문해 달라"고만 했다 |
| **보안** — 권한 확인 | 운영자, 보안 담당자 | ❌ |
| **모니터링** | 운영자 | ❌ |

사용자는 기능적인 이야기만 했다. 그런데 주문을 처리하다 보면 결제 포인트, 결제 수단이 결합되니 트랜잭션 코드가 들어가고, 어디가 느린지 알기 위해 로그 코드가 들어간다. 이렇게 **주 업무와 결이 다른 곁다리 업무**가 점점 많아진다. 곁다리 코드의 주인은 개발자일 수도, 운영자일 수도, 성능 튜닝 담당자일 수도 있다. 즉 **관점이 다른 역할자들의 코드**다.

> 이런 곁다리 업무를 공식 용어로 **횡단 관심사(Cross-cutting Concerns)**라고 한다. 여러 클래스와 메서드를 **가로질러(횡단)** 똑같이 필요한 관심사라는 뜻이다. 반대로 주 업무는 **핵심 관심사(Core Concerns)**라고 한다.

## 3. 곁다리 코드는 어디에 들어가나

메서드가 얼마나 오래 걸리는지 재서 병목을 찾는 로그를 넣는다고 하자. 함수의 어디쯤에 넣을까? 중간에 꽂아 넣지 않고, 대부분 **함수의 시작과 끝**에 넣는다.

```java
public void 주문하기() {
    long start = System.currentTimeMillis();          // 시작 시간 (곁다리)

    // ===== 주 업무 =====
    // 재고 확인, 주문 저장, 결제 처리 ...
    // ==================

    long end = System.currentTimeMillis();            // 끝 시간 (곁다리)
    System.out.println("주문하기 실행 시간: " + (end - start) + "ms");
}
```
가운데 주 업무의 **위아래에 곁다리 코드가 붙는** 모양이다. 트랜잭션도 똑같다. 시작할 때 커넥션을 열고 트랜잭션을 시작하고, 끝날 때 커밋하거나 롤백한다.

## 4. 곁다리 코드 구조의 두 가지 문제

### 문제 1: 모든 메서드에 똑같은 코드를 붙여야 한다

메서드마다 붙이는 빵(시작 시간 재기, 끝 시간 재기)은 **완전히 같은 코드**다. 그런데도 그것을 모든 메서드에 복사해서 붙여야 한다. 메서드가 수십 개면 수십 번 복사·붙여넣기를 해야 한다.

```java
public void 주문하기()   { 시간 측정 시작 ... 주 업무 ... 시간 측정 끝 }
public void 주문취소()   { 시간 측정 시작 ... 주 업무 ... 시간 측정 끝 }
public void 메뉴등록()   { 시간 측정 시작 ... 주 업무 ... 시간 측정 끝 }
// ... 똑같은 곁다리 코드가 메서드 수만큼 반복된다
```

### 문제 2: 뗐다 붙였다 하기가 너무 힘들다

테스트가 끝나면 그 로그 코드는 어떻게 할까? 제품을 사용자에게 줄 때 테스트용 로그를 그대로 출력하게 둘 수는 없으니 **빼야 한다.** 그러면 그 많은 메서드를 하나하나 다시 열어서 지워야 한다. 다시 테스트할 때는 또 붙여야 한다. 메서드가 10개만 되어도 짜증나는 일이다.

## 5. AOP — 곁다리 코드를 한 번만 만들고 자유롭게 뗐다 붙이는 방법

그래서 이런 관심이 생겼다. "이렇게 만들면 안 되겠다. **곁다리 코드를 만드는 방법**을 따로 강구하자."

- 곁다리 코드는 **한 번만** 만든다.
- 그 코드를 **어느 메서드에 붙일지**만 지정한다.
- 필요 없어지면 **쉽게 뗄 수 있다.** 메서드 코드는 손대지 않는다.

이렇게 **곁다리 업무를 주 업무 코드와 분리해 한 곳에서 만들고, 원하는 곳에 자유롭게 끼웠다 뺐다 하는 방법론**이 AOP다.

```
[AOP 없이]                                 [AOP 적용]
주문하기() = 곁다리 + 주 업무 + 곁다리       주문하기() = 주 업무만
주문취소() = 곁다리 + 주 업무 + 곁다리       주문취소() = 주 업무만
메뉴등록() = 곁다리 + 주 업무 + 곁다리       메뉴등록() = 주 업무만
                                            곁다리 코드 = 한 곳에 하나만
                                               → "서비스의 모든 메서드에 붙여라"라고 지정
```

## 6. @Transactional이 바로 AOP다

`@Transactional`은 스프링이 미리 만들어 둔 **트랜잭션 곁다리 코드**다. 메서드에 이 어노테이션을 붙이면 스프링이 그 메서드 앞뒤에 다음 코드를 끼워 넣는다.

```
[앞] 커넥션을 열고 트랜잭션 시작 → 이 커넥션을 메서드 안의 모든 리포지토리가 공유
     주 업무: categoryRepository.save(...) 여러 번
[뒤] 정상 종료면 커밋 / 예외가 나면 롤백 → 커넥션 반환
```

그래서 서비스 메서드에는 트랜잭션 코드가 한 줄도 없는데도 커밋과 롤백이 일어난다. 붙이면 트랜잭션이 걸리고, 지우면 빠진다. AOP가 말하는 "한 번만 만들고, 뗐다 붙였다 자유롭게"가 그대로 구현된 예다.

> **추가 설명 — 스프링은 어떻게 앞뒤에 끼워 넣나**: 스프링은 `@Transactional`이 붙은 빈을 컨테이너에 넣을 때, 원래 객체 대신 그 객체를 감싼 **프록시(대리 객체)**를 넣는다. 다른 객체가 서비스를 주입받으면 실제로는 프록시를 받는다. 프록시는 호출을 받으면 앞쪽 빵(트랜잭션 시작)을 실행하고, 진짜 서비스 메서드를 호출한 뒤, 뒤쪽 빵(커밋·롤백)을 실행한다. 이 방식 때문에 **같은 클래스 안에서 자기 메서드를 직접 호출**하면 프록시를 거치지 않아 `@Transactional`이 적용되지 않는 주의점이 생긴다.

## 7. 한 줄 정리

- **OOP**는 사용자의 요구(주 업무)를 기준으로 객체를 나누고, **AOP**는 그 위에서 **관점이 다른 역할자의 코드(곁다리 업무)**를 따로 다루는 방법론이다. OOP를 대체하지 않는다.
- 로그, 트랜잭션, 보안 같은 곁다리 업무는 메서드의 **시작과 끝**에 붙는 빵또아 구조라서, 같은 코드를 모든 메서드에 반복해야 하고 떼기도 힘들다.
- AOP는 이 코드를 **한 번만 만들고, 어디에 붙일지 지정해서 자유롭게 뗐다 붙이게** 한다.
- `@Transactional`은 스프링이 AOP로 제공하는 트랜잭션 이다.
