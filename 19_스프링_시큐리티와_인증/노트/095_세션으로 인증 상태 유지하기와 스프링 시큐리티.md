# 세션으로 인증 상태 유지하기와 스프링 시큐리티

## 1. 지금까지의 흐름 — 왜 맨땅으로 구현해 보나

스프링 보안에서 가장 중요한 일은 두 가지다.

| 단계 | 하는 일 |
|---|---|
| **인증** | 요청한 사용자가 **누구인지** 알아본다 |
| **인가** | 인증된 정보를 어딘가에 저장해 두고, 다음 요청이 올 때 **이 사용자가 이 페이지를 받을 수 있는지** 판단한다 |

인증과 인가는 웹만의 이야기가 아니다. 데이터베이스를 쓸 때도, 어떤 서버를 쓰든 늘 있다.

스프링 보안을 쓰면 인증 로직도, 인가 로직도 **직접 구현할 필요가 없다.** 설정만 하면 된다. 하지만 그 설정이 무엇을 대신해 주는지 모르고 쓰면 막히는 순간 손을 쓸 수 없다. 그래서 잠깐 뒤로 돌아가 인증과 인가를 직접 만들어 보면서 쿠키와 세션이 어떻게 엮이는지, 왜 보안 코드를 **필터**로 만드는지를 맛본 뒤에 스프링 보안으로 넘어간다.

- **인증**: 사용자가 보낸 아이디·비밀번호가 맞으면 메인으로, 틀리면 에러 표시와 함께 로그인 페이지로 돌려보낸다.
- **인가**를 하려면 요청이 올 때마다 "이 사람이 아까 인증한 그 사람"인지 확인할 수 있어야 한다. 그래서 인증된 사용자라는 **상태 값**을 계속 들고 오게 했고, 그때 쓴 것이 **쿠키**였다.
- 그런데 쿠키에 이름, 전화번호, 이메일, 프로필 사진, 포인트, 레벨까지 점점 많이 담다 보니, 오가는 길에 누군가 엿보거나 가로챌 수 있다는 부담이 생겼다. 그래서 **안전하게 서버에 보관하자**는 생각에서 세션을 쓰게 된다.

## 2. 세션은 저장소가 아니라 "기간"이다

"세션은 저장소인가, 스코프인가?" 세션은 **기간**이다.

### 왜 기간이 생기나

- 쿠키는 브라우저가 저장하고 관리한다(만료 시간을 늘리면 브라우저가 관리하는 파일에 저장된다).
- 민감한 정보를 서버에 두기로 하면, 서버는 전 세계 사용자의 데이터를 받아 줘야 한다. 하지만 서버의 자원은 **한정**되어 있다. 캐비닛을 빌려줄 수는 있지만 무한히 줄 수는 없다.
- 게다가 웹에는 **연결이라는 개념이 없다.** 요청이 한 번 왔다고 다음 요청이 이어진다는 보장이 없다. 브라우저를 닫았는지 컴퓨터를 껐는지 서버는 알 수 없다.

그래서 서버는 이렇게 말한다. "저장해 줄게. 그런데 30분 안에 다시 안 오면 지울 거야." 이 **기다리는 기간**이 세션이고, 다른 말로 **타임아웃**이라고도 한다. 세션이 살아 있는 동안은 "우리 관계가 아직 끝나지 않은 상태"라고 볼 수 있다.

### 세션은 늘어난다, 타임아웃은 고정이다

| 구분 | 동작 |
|---|---|
| 타임아웃 | 고정 (예: 20분) |
| 세션 | 늘어난다 |

타임아웃이 20분인데 사용자가 19분 59초에 다시 요청하면, 타임아웃이 다시 20분으로 **리셋**된다. 그만큼 전체 세션 기간은 길어진다.

> **추가 설명 — 기본 타임아웃**: 예시는 20분이었지만, 스프링 부트(톰캣)의 기본값은 **30분**이다. `application.yml`의 `server.servlet.session.timeout`으로 바꿀 수 있다.

### 서버 저장소 중 세션만 ID를 발급한다

서버에서 데이터를 저장하는 객체는 page, request, session, application 네 가지다. 그런데 이 중 **세션만** 쿠키를 만들어 낸다. 세션 객체의 생명주기를 보면 이유가 보인다.

- 세션 객체는 **사용자마다 하나씩** 만들어진다. 사용자가 100명이면 세션 객체도 100개다.
- 세션 ID를 발급하는 순간 생기고, 그 ID가 **타임아웃되는 순간 사라진다.** 사용자마다 타임아웃이 다르니 100개의 생성·소멸 시점도 모두 다르다.
- 그래서 세션을 쓰지 않으면 세션 ID는 **발급되지 않는다.** 인증을 했다고 자동으로 ID가 생기는 게 아니다. 인증 상태를 유지하려면 세션을 **꼭** 써야 하고, 스프링 보안도 기본으로 세션을 쓴다.

> **추가 설명 — 정확한 발급 시점**: 세션 ID는 값을 넣는 순간이라기보다 **세션 객체가 처음 만들어지는 순간**(`request.getSession()`이 처음 호출될 때) 발급된다. 실습 코드에서는 로그인 성공 시점에 세션을 처음 쓰기 때문에 결과적으로 같은 시점이 된다.

### 개발자 도구로 확인하기

1. Application 탭에서 쿠키를 지운다. 메뉴나 관리자 페이지를 돌아다녀도 세션 ID는 없다.
2. 비밀번호를 **틀리게** 로그인하면 세션에 아무것도 담지 않으므로 여전히 세션 ID가 없다. 만약 인증에 실패했는데도 세션에 무조건 담는다면 그건 버그다.
3. 제대로 로그인하면 세션을 쓰는 순간 응답 헤더에 `Set-Cookie: JSESSIONID=...`가 오고("이거 좀 담아 줄래?"), 리다이렉트 후에도 브라우저가 계속 이 값을 들고 다닌다.

### 세션 ID는 바뀌어야 한다

예전에는 세션 ID가 한번 발급되면 계속 같았다. 하지만 쿠키는 누구나 볼 수 있으므로 같은 ID를 오래 쓰면 위험하다. 스프링 보안은 이런 것까지 관리해 주지만, 지금 직접 만든 로그인은 세션 ID가 **고정**이라, 스프링 보안 없이 구현한다면 ID를 바꾸는 로직도 직접 넣어야 한다.

> 원문 바로잡기 — 강의에서는 "요즘은 세션이 조금만 바뀌어도 새로 발급해 준다"고 했는데, 톰캣이 값이 바뀔 때마다 ID를 바꿔 주는 것은 아니다. 스프링 시큐리티가 **로그인(인증)에 성공하는 순간** 세션 ID를 새로 바꾸는 것이다(세션 고정 공격 방어, 기본 전략 `changeSessionId`). 직접 구현한다면 로그인 성공 시 `request.changeSessionId()`를 호출하면 된다.

> **추가 설명 — "로그인 유지"를 켜도 세션 ID를 오래 쓰지 않는다**: 세션 타임아웃을 2주로 늘리면 서버가 오지 않는 사용자의 세션까지 들고 있어야 하고, `JSESSIONID`를 영속 쿠키로 만들면 ID 하나가 털리는 순간 2주 동안 그 사람으로 행세할 수 있다. 그래서 세션은 짧게 두고, 오래 가는 **remember-me 쿠키**를 따로 발급한다.
>
> ```
> 1. "로그인 유지" 체크 후 로그인 → 세션(JSESSIONID, 30분) + remember-me 쿠키(예: 2주)
> 2. 세션 만료 또는 브라우저를 닫았다 열기 → JSESSIONID 없음
> 3. 다음 요청의 remember-me 쿠키를 RememberMeAuthenticationFilter가 검증
>    → 자동으로 다시 인증하고 새 세션 생성(새 JSESSIONID)
> ```
>
> | 방식 | 쿠키에 담기는 것 | 특징 |
> |---|---|---|
> | 해시 기반(기본) | 아이디 + 만료 시각 + 서명(비밀번호와 서버 키로 만든 해시) | DB가 필요 없다. 쿠키가 털리면 만료 전까지 막기 어렵다(비밀번호를 바꾸면 무효) |
> | 영속 토큰 기반 | 시리즈 값 + 토큰 값(DB에 저장) | 쓸 때마다 **토큰을 새로 바꾼다.** 털린 쿠키가 쓰이면 탐지할 수 있어 권장된다 |
>
> ```java
> http.rememberMe(remember -> remember
>         .key("서버만 아는 비밀 키")
>         .tokenValiditySeconds(60 * 60 * 24 * 14)          // 2주
>         .tokenRepository(persistentTokenRepository()));   // 영속 토큰 방식일 때
> ```
>
> 로그인 폼에 `<input type="checkbox" name="remember-me">`를 두면 되고, 로그아웃하면 remember-me 쿠키도 함께 지워진다. 자동 로그인 상태는 직접 로그인한 상태보다 약하게 보고, 비밀번호 변경·결제 같은 기능은 `fullyAuthenticated()`로 막아 비밀번호를 다시 받는다. 프론트엔드를 분리한 JWT 구조에서는 **리프레시 토큰**이 같은 역할을 하고, 쓸 때마다 바꾸는 것(rotation)이 권장되는 점도 같다.

### 쿠키와 세션, 무엇을 고를까

| 정보 | 어디에 | 예 |
|---|---|---|
| 민감한 정보 | **세션**(서버), 쿠키에는 ID만 | 사용자 식별자, 역할, 개인정보 |
| 민감하지 않은 정보 | **쿠키** | 배경색, 비회원 장바구니 |

"이건 쿠키가 좋을까, 세션이 좋을까?"라는 질문을 받았을 때, 각각의 의미를 알고 스스로 선택할 수 있어야 한다.

## 3. 실습 환경 — H2 메모리 데이터베이스

수업에서 같이 쓰던 데이터베이스 계정이 외부에 노출되어 여기저기서 접속이 들어오는 바람에 더 이상 쓸 수 없게 되었다. 도커나 로컬 DB를 써도 되지만, 임시 실습용으로는 **H2**를 쓴다.

- **H2**는 테스트용 데이터베이스로, 주로 **메모리**에 올려 쓴다. 프로그램을 내리거나 재부팅하면 데이터가 사라진다(옵션으로 파일에 저장할 수도 있다).
- 운영 데이터용이 아니라 지금처럼 **스프링을 공부하거나 테스트**할 때 쓴다.

```groovy
// build.gradle
runtimeOnly 'com.h2database:h2'
```

```yaml
# application.yml
spring:
  application:
    name: security
  datasource:
    url: jdbc:h2:mem:security
    driver-class-name: org.h2.Driver
  h2:
    console:
      enabled: true
  jpa:
    hibernate:
      ddl-auto: update
    show-sql: true
    properties:
      hibernate:
        format_sql: true

server:
  port: 8080
```

> **추가 설명 — 위 설정은 일반적인 예시다**: 강의에서 나눠 준 설정 파일은 노트에 없어서, H2 메모리 DB의 일반적인 설정으로 적었다. JPA는 DB 연결이 안 되면 실행하자마자 바로 죽으므로, 실행이 되면 드라이버가 잘 붙은 것이다.

**라이브러리를 추가했는데 인식이 안 될 때**: WSL은 원격에 있는 컴퓨터라 VSCode가 바로 동기화하지 못할 때가 있다(맥은 파일 시스템을 공유해서 바로 된다). `Ctrl + Shift + P` → **Java: Clean Java Language Server Workspace**로 기존 빌드 내용을 내리고 다시 로드한다. 정 안 되면 DB를 쓰는 예제가 나오기 전까지 JPA 의존성과 DB 설정을 잠시 빼 두어도 된다(오류의 원인이 JPA의 DB 연결이기 때문이다).

## 4. 로그인 요청을 DTO로 받기

### DTO는 화면의 데이터다

DTO는 **화면에서 입력한 데이터**와 **화면에 출력할 데이터**를 원격으로 주고받는 그릇이다. 그래서 DTO를 떠올리면 늘 **화면**이 함께 떠올라야 한다. UI 없이 DTO는 생각할 수 없다.

화면(페이지) 수만큼 DTO가 생기므로, 하나의 `dto` 폴더에 모두 몰아넣으면 나중에 찾기 힘들다. 도메인별로 나눈다.

```
dto
├─ auth
│  └─ LoginRequest.java
└─ menu
   └─ ...
```

이름은 `LoginRequestDto`라고 해도 되지만, 이미 `dto` 폴더 안에 있으니 귀찮으면 `Dto`는 빼도 된다.

```java
@Getter
@Setter
public class LoginRequest {
    private String username;
    private String password;
}
```

### @ModelAttribute — URL 인코딩 데이터를 객체로

사용자가 데이터를 보내는 방식에 따라 받는 방법이 다르다.

| 보내는 방식 | 받는 방법 |
|---|---|
| URL 인코딩(`username=...&password=...`) → 낱개로 받기 | `String username, String password` 매개변수만 선언 |
| URL 인코딩 → **객체 하나로** 받기 | **`@ModelAttribute LoginRequest`** |
| JSON 본문 | `@RequestBody` |
| XML 본문(`<loginRequest><username>...</username></loginRequest>`) | `@RequestBody` (`jackson-dataformat-xml` 의존성 필요) |

URL 인코딩은 키·값이 낱개로 오는데 받는 쪽이 `LoginRequest` 하나라면, 스프링이 그냥은 맞춰 줄 수 없다. 앞에 `@ModelAttribute`를 붙이면 "이건 모델(뷰와 연관된 데이터)이야. 그 안의 setter를 써서 채워 줘"라는 뜻이 되어, 스프링이 `setUsername()`, `setPassword()`를 찾아 값을 넣어 준다.

연결 기준은 **이름**이다. 폼의 `<input name="username">`과 DTO의 `username` 필드처럼 이름이 같아야 값이 들어간다. 이름이 다르면 오류 없이 그 필드만 `null`로 남으므로, 값이 안 들어오면 먼저 이름부터 확인한다.

```java
@PostMapping("/login")
public String login(@ModelAttribute LoginRequest loginRequest, HttpSession session) {

    boolean isAuthenticated = authenticationService.authenticate(
            loginRequest.getUsername(), loginRequest.getPassword());

    if (isAuthenticated) {
        session.setAttribute("username", loginRequest.getUsername());
        session.setAttribute("role", "ADMIN");   // 역할(권한) 정보도 함께
        return "redirect:/";
    }
    return "redirect:/login?error=true";
}
```

> **추가 설명 — @ModelAttribute는 생략할 수 있다**: 스프링은 `String`·숫자 같은 단순 타입이 아닌 객체 매개변수에 어노테이션이 없으면 `@ModelAttribute`로 처리한다. 그래서 `LoginRequest loginRequest`만 써도 동작한다. 다만 명시해 두면 "폼 데이터를 객체로 받는다"는 의도가 코드에 드러난다. 값을 채울 때 setter를 쓰므로 **기본 생성자와 setter**가 있어야 한다(Lombok `@Getter @Setter`).

### 세션에는 식별자를 담는다

인증했다는 표시로 세션에 담는 것은 보통 **사용자를 식별할 수 있는 값**이다. 글을 쓰거나 무언가를 할 때 누가 했는지 식별자가 필요하기 때문이다. 아이디(username)가 식별자가 아니라면 사용자 ID(PK)를 담는다. 세션은 서버에 안전하게 보관되므로 주민등록번호 같은 식별자를 담아도 외부에 노출되지 않는다. 쿠키로는 노출되어도 괜찮은 세션 ID만 나간다.

## 5. 세션 값을 화면에 쓰기 — 로그인/로그아웃 버튼

로그인을 했는데 화면에는 여전히 "로그인" 버튼이 있다. 로그인한 사용자에게는 "로그아웃"이 보여야 한다.

### 지금 하는 방식은 서버 페이지 방식이다

이 페이지는 HTML처럼 보이지만 사실 **타임리프** 템플릿이다. JSP는 배웠지만 타임리프는 배우지 않았다. 앞으로 이 방식으로 만들지 않을 것이기 때문이다.

보안을 다루는 방식은 두 가지다.

| 방식 | 페이지를 만드는 곳 | 쓰이는 곳 |
|---|---|---|
| **서버 페이지(MVC)** | 서버가 모델을 뷰(JSP·타임리프)에 내려 문서를 만들어 줌 | 관공서, 기업 등에서 여전히 많이 씀. 동적인 부분은 jQuery나 DOM으로 처리 |
| **풀스택(프론트엔드 분리)** | 프론트엔드가 페이지를 만들고, 서버는 데이터(DTO)만 줌 | 최근 경향. 앞으로 우리가 쓸 방식 |

지금은 서버 페이지 방식에서 보안을 쓰는 법이고, "JSP나 타임리프로 만들 때는 이렇게 하는구나" 정도만 기억하면 된다. 컨트롤러 쪽 코드(세션 다루기)는 나중에 풀스택 API를 만들 때도 똑같이 쓴다.

> **모델과 DTO는 같은 데이터다**: 컨트롤러(C)가 만든 데이터를 **로컬의 뷰(V)**에 내려 주면 **모델**, 뷰를 거치지 않고 **원격(프론트엔드)**으로 바로 보내면 **DTO**다. 같은 모델 데이터가 어디로 가느냐의 차이일 뿐이다.

### 타임리프에서 조건 처리

```html
<!-- 로그인 안 된 상태 -->
<a th:if="${username == null}" href="/login" class="btn">로그인</a>

<!-- 로그인 된 상태 -->
<span th:if="${username != null}" th:text="${username} + '님 환영합니다'"></span>
<form th:if="${username != null}" action="/logout" method="post">
    <button class="btn">로그아웃</button>
</form>
```

`username`이라는 모델이 있으면 로그아웃, 없으면 로그인이 보인다. 그럼 `username` 모델은 누가 만들까? 랜딩 페이지 요청을 받는 **컨트롤러(HomeController)**가 세션에서 꺼내 모델에 담아 준다.

```
요청(쿠키: JSESSIONID) → HomeController → 쿠키의 ID로 세션 찾기 → 세션의 username 꺼내기
                                        → Model에 담기 → index.html(뷰)이 사용
```

### 세션 값 꺼내는 방법 세 가지

```java
// 1) 가장 편한 방법 — @SessionAttribute
@GetMapping("/")
public String home(@SessionAttribute(required = false) String username, Model model) {
    model.addAttribute("username", username);
    return "index";
}

// 2) HttpSession을 받아서 꺼내기
public String home(HttpSession session, Model model) {
    String username = (String) session.getAttribute("username");   // Object로 나오므로 형변환
    ...
}

// 3) 가장 손이 많이 가는 방법 — request에서 세션을 얻어 꺼내기
public String home(HttpServletRequest request, Model model) {
    String username = (String) request.getSession().getAttribute("username");
    ...
}
```

- 그냥 `String username`이라고만 쓰면 스프링은 요청 파라미터(쿼리 스트링)에서 찾는다. 세션에서 꺼내 달라는 표시가 **`@SessionAttribute`**다.
- 세션에 담긴 이름과 변수 이름이 다르면 `@SessionAttribute("userId") String username`처럼 이름을 지정하고, 같으면 생략해도 된다.
- `getAttribute()`는 `Object`를 돌려주므로 형변환(`(String)`)이나 `String.valueOf()`가 필요하다.
- 뷰에 내려 주려면 매개변수로 **`Model`**(스프링의 `org.springframework.ui.Model`)을 달라고 하고 `addAttribute()`로 담는다. 프론트 컨트롤러가 그 모델을 뷰에 전달해 준다.

가장 쉬운 방법을 기본으로 쓰되, 필요에 따라 유연하게 쓰면 된다.

> 원문 바로잡기 — `@SessionAttribute`는 기본이 `required = true`다. 로그인하지 않아 세션에 `username`이 없으면 **400 오류**(Missing session attribute)가 나서 랜딩 페이지가 열리지 않는다. 강의 중에 "유저 네임을 갖고 있지 않아서" 뜬 에러가 이것이다. 로그인 전에도 열려야 하는 페이지라면 위 코드처럼 `required = false`를 붙여야 한다.

> **추가 설명 — 이름이 비슷한 두 어노테이션**: `@SessionAttribute`(단수)는 세션에 있는 값을 **꺼내는** 것이고, `@SessionAttributes`(복수)는 컨트롤러 클래스에 붙여 모델 값을 세션에 **임시 보관**하는 전혀 다른 기능이다. 헷갈리기 쉬우니 단수형인지 확인한다.

## 6. 로그아웃 — POST와 invalidate

로그인했으면 로그아웃도 있어야 한다. 로그아웃은 **반드시 POST**로 매핑한다. 그렇지 않으면 나중에 위험이 생긴다.

```java
@PostMapping("/logout")
public String logout(HttpSession session) {
    session.invalidate();     // 세션 자체를 없앤다
    return "redirect:/";      // POST니까 페이지가 아니라 리다이렉트
}
```

- 로그아웃은 사용자에게 받을 데이터가 없으므로 DTO는 필요 없다.
- 로그아웃은 username만 필요 없어지는 게 아니라 **세션 자체**가 필요 없어지는 것이다. `invalidate()`를 호출하면 세션이 사라지고, 브라우저가 들고 있던 예전 세션 ID는 더 이상 의미가 없어진다.
- `request.getSession().invalidate()`로 써도 되지만, 세션을 바로 매개변수로 받아 호출해도 된다.

> **추가 설명 — 왜 GET이면 위험한가**: GET 로그아웃이라면 다른 사이트가 `<img src="https://우리사이트/logout">` 한 줄만 심어도, 그 페이지를 본 사용자가 자기도 모르게 로그아웃된다(CSRF). 상태를 바꾸는 요청은 GET으로 만들지 않는다는 원칙의 한 예다. 스프링 시큐리티도 기본으로 로그아웃을 POST로만 받는다.

## 7. 모든 페이지에 필요한 검사 — 그래서 필터

### 인증 다음은 인가

로그인했다면 인증은 끝났다. 이제 **인가**가 남았다. 페이지마다 두 가지를 알아야 한다.

1. 이 사용자가 **로그인했는가** → 세션의 `username`
2. 이 사용자가 **어떤 역할자인가** → 세션의 `role` (DB를 쓴다면 사용자 정보와 함께 역할도 저장해 둔다)

```java
String username = (String) session.getAttribute("username");   // 인증했음을 알려 준다
String role     = (String) session.getAttribute("role");       // 권한을 알려 준다

if (username == null) return "redirect:/login";
if (!"ADMIN".equals(role)) return "redirect:/";   // 또는 권한 없음 메시지
```

### 이 코드는 모든 컨트롤러에 필요하다

이 검사는 홈에만 필요한 게 아니다. **모든 URL**에서 이 사용자가 이 페이지를 볼 권한이 있는지 알아봐야 한다. 그러면 모든 컨트롤러마다 세션 값을 꺼내고 `if`로 검사하고, 권한이 없으면 메시지를 뿌리거나 리다이렉트해야 한다. 매우 비효율적이다.

이 코드는 항상 **업무 로직의 앞단**에 있다. 업무 로직(주인공)이 아니라 그 앞에 늘 따라붙는 **곁다리**다. 그래서 **크로스 커팅**해서 다른 곳으로 빼는 게 좋다.

```
[인증·인가 검사] → /           (홈)
[인증·인가 검사] → /menus      (메뉴)
[인증·인가 검사] → /admin/menus (관리자 메뉴)
  ↑ 곁다리: 모든 업무 로직 앞에 반복 → 한 곳으로 빼낸다
```

빼내는 방법은 두 가지다.

| 방법 | 설명 |
|---|---|
| **프록시(AOP)** | 컨트롤러 앞에 프록시를 두고 검사 코드를 옮긴다 |
| **필터** | 프록시 없이도 요청이 오갈 때 항상 앞에서 실행되는 환경. **스프링 보안은 필터를 쓴다** |

필터가 이미 그 역할을 해 주니 굳이 프록시를 쓸 필요가 없다. 즉 스프링 보안은 **필터를 이용한 AOP 방식**이라고 볼 수 있다. 한 곳에서 모든 조건 검사를 하면, 각 컨트롤러는 그 데이터가 정말 필요한 경우에만 가져다 쓰면 된다.

### 스프링 보안 = 남이 만든 보안 필터 + 설정

인증·인가를 필터로 만드는 것은 스프링만의 방식이 아니다. 스프링 보안을 쓰지 않는 개발자도 **무조건 필터**로 만든다. 예전에는 개발자나 회사마다 필터를 직접 만들어 썼다. 하지만 아무리 잘 만들어도 다른 프로젝트에 가서 "제가 만든 필터 쓰세요"라고 하면, 사람들은 "전 세계가 쓰는 스프링 거 쓰자"고 한다. 만들 능력이 없어서가 아니라, 내가 만들어 봤자 쓰이지 않으니 남이 만든 필터를 쓰게 된 것이다. 스프링이 그런 필터를 만들어 제공하는 것이 **스프링 시큐리티 프레임워크**다.

그런데 필터가 모든 것을 고정해 두었다면 아무도 쓰지 않았을 것이다. 어떤 주소를 누구에게 허락할지는 서비스마다 다르기 때문이다. 그래서 프레임워크는 기본 기능을 다 만들어 두고 **"이것만 설정해"** 하고 열어 둔 곳이 있다. 그것이 **스프링 보안 설정(config)**이다.

| 설정 블록 | 책임지는 것 | 지우면 |
|---|---|---|
| `SecurityFilterChain` | **인가** — 어떤 URL을 누구에게 허용할지 (로그인한 사용자만, 관리자만 등) | 기본값: 모든 요청에 로그인 요구 |
| `UserDetailsService` | **인증**에 쓸 사용자 정보 제공 | 기본 사용자 `user`와 임시 비밀번호가 콘솔에 뜸 |
| `PasswordEncoder` | 비밀번호 인코더 | — |

결국 우리가 책임질 것은 **URL 매핑 정보**와 **사용자 정보** 두 가지뿐이다.

> 원문 바로잡기 — 강의에서 `PasswordEncoder`는 "도구일 뿐, 보안 로직과는 별로 상관없다"고 했지만, 로그인할 때 입력한 비밀번호와 저장된 비밀번호를 **비교하는 데 쓰이는 인증의 일부**다. 사용자 정보에 `{noop}` 같은 접두사 없이 비밀번호를 넣는다면 `PasswordEncoder`가 있어야 비교할 수 있다. "보안 규칙(어디를 막을지)과는 상관없다"는 정도로 이해하면 맞다.

## 8. 직접 만든 인증 걷어 내고 스프링 보안 켜기

1. 주석 처리해 두었던 **스프링 보안 라이브러리 두 개**를 다시 살린다(직접 하거나 AI에게 추가해 달라고 해도 된다). 빨간 줄이 남으면 Java Clean을 한다.
2. 직접 만든 **로그인 처리, 로그아웃 처리를 지운다.** 남겨 두면 스프링 보안의 로그인·로그아웃과 **충돌**한다.
3. 더 이상 쓰지 않는 **`AuthenticationService`도 과감하게 지운다.** 쓰지 않는 코드를 남겨 두면 나중에 "이게 뭐지?" 하고 헷갈린다. 파일만 지우고 그것을 참조하던 코드를 남겨 두면 컴파일 오류가 나니, 참조하는 곳까지 정리한다.
4. 설정 파일의 블록도 모두 지워 본다. 설정이 아무것도 없는 상태는 설정 파일을 지운 것과 같다. 이 상태로 실행하면 처음 시큐리티를 붙였을 때처럼 **모든 페이지에 로그인 창**이 뜬다. 우리는 인증·인가 코드를 하나도 만들지 않았는데 이미 동작한다.
5. 콘솔의 임시 비밀번호를 복사해 `user`로 로그인한다.

로그인하면 쿠키에 `JSESSIONID`가 생긴다. 스프링 보안이 **세션**을 쓰고 있다는 뜻이다. 쿠키를 지우면(Application 탭에서 오른쪽 버튼 → Clear) 세션이 없으므로 다시 로그인하라고 한다.

> **추가 설명 — 로그인 후 400 오류가 뜬다면**: 홈 컨트롤러에 남아 있는 `@SessionAttribute String username` 때문이다. 이제 세션에 `username`을 넣던 직접 만든 로그인을 지웠으므로 그 값이 없다. 해당 매개변수를 지우거나 `required = false`를 붙인다. 스프링 보안에서 로그인한 사용자 정보는 세션 속성이 아니라 `SecurityContext`에서 꺼낸다.

매번 콘솔의 임시 비밀번호를 복사하는 것은 불편하다. **`UserDetailsService`로 사용자를 직접 제공**하면 내가 만든 사용자로 로그인할 수 있고, 기본 사용자가 필요 없어지므로 콘솔에 임시 비밀번호도 뜨지 않는다.

## 9. 한 줄 정리

- 스프링 보안의 핵심은 **인증**(누구인가)과 **인가**(이 페이지를 받아도 되는가)다. 직접 구현해 보는 이유는 설정이 무엇을 대신해 주는지 알기 위해서다.
- **세션은 기간**이다. 서버 자원은 한정되어 있고 웹에는 연결이 없으므로, 일정 시간(타임아웃) 안에 다시 오지 않으면 지운다. 요청이 오면 타임아웃이 리셋되어 세션이 늘어난다.
- 서버 저장소 중 **세션만** 사용자마다 객체가 생기고 세션 ID를 쿠키로 발급한다. 세션을 쓰지 않으면 ID도 없다.
- 민감한 정보는 세션(서버)에, 민감하지 않은 정보(배경색, 장바구니)는 쿠키에 둔다.
- 폼 데이터를 객체로 받을 때는 `@ModelAttribute`, 세션 값을 꺼낼 때는 `@SessionAttribute`(로그인 전에도 열리는 페이지면 `required = false`), 뷰에 내릴 때는 `Model`을 쓴다.
- 로그아웃은 **POST**로 받고 `session.invalidate()` 후 리다이렉트한다.
- 인증·인가 검사는 **모든 업무 로직 앞에 반복되는 곁다리**라 필터로 빼낸다. 스프링 보안은 이미 만들어진 보안 필터이고, 우리는 **URL별 허용 규칙**과 **사용자 정보**만 설정하면 된다.
