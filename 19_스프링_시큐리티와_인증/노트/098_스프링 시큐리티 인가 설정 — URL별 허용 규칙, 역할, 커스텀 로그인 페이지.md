# 스프링 시큐리티 인가 설정 — URL별 허용 규칙, 역할, 커스텀 로그인 페이지

## 1. 우리가 손볼 곳은 두 군데뿐

스프링 시큐리티는 **필터**를 쓰는 **프레임워크**다. 프레임워크라는 건 이미 다 구현해 두었다는 뜻이고, "이것만 고쳐 쓰면 돼" 하고 열어 둔 곳이 몇 개 있다. 그 열어 둔 곳은 생각보다 많지 않아서, 딱 두 가지만 잘 손보면 된다.

| 열어 둔 곳 | 스프링 시큐리티가 하는 말 | 담당 |
|---|---|---|
| `UserDetailsService` | "사용할 **사용자 정보**를 주세요" | 인증 |
| `SecurityFilterChain` | "인증 상태를 세션에 등록하는 건 내가 다 해 놨으니, **어느 URL을 누구에게 허락할지**만 알려 주세요" | 인가 |

사용자 정보는 지금처럼 빈으로 등록해 바로 제공할 수도 있고, 나중에 원하면 사용자를 돌려주는 서비스 객체를 따로 만들 수도 있다. 사용자를 하나도 주지 않으면 스프링 시큐리티는 기본 사용자 `user`와 콘솔의 임시 비밀번호로 버틴다.

## 2. 사용자 정보와 역할(role)

### 코드에 박아 둔 사용자

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}

@Bean
public UserDetailsService userDetailsService(PasswordEncoder passwordEncoder) {
    UserDetails user = User.builder()
            .username("user")
            .password(passwordEncoder.encode("user1234"))
            .roles("USER")                 // 일반 사용자
            .build();

    UserDetails admin = User.builder()
            .username("admin")
            .password(passwordEncoder.encode("admin1234"))
            .roles("USER", "ADMIN")        // 일반 사용자이면서 관리자
            .build();

    return new InMemoryUserDetailsManager(user, admin);   // 메모리에 둔 사용자 정보
}
```

- `PasswordEncoder` 빈으로 **BCrypt**를 등록하고, 사용자를 만들 때 `passwordEncoder.encode(...)`로 비밀번호를 암호화해서 저장한다. 로그인할 때도 스프링 시큐리티가 같은 인코더로 입력값을 비교한다.
- `userDetailsService(PasswordEncoder passwordEncoder)`처럼 매개변수로 받으면, 스프링이 위에서 등록한 인코더 빈을 넣어 준다.
- 로그인 페이지, 로그인 처리 코드는 스프링 시큐리티가 다 만들어 두었으므로 이것만으로 로그인이 된다.
- 문제는 사용자가 한 명 늘 때마다 **코드를 고쳐야** 한다는 것이다. 그래서 다음 단계에서는 사용자를 데이터베이스에서 가져온다(8절).

> **추가 설명 — `PasswordEncoder` 빈이 없으면**: 스프링 시큐리티는 기본 비교기(`DelegatingPasswordEncoder`)를 쓰는데, 이 비교기는 저장된 비밀번호 앞의 표시(`{bcrypt}...`, `{noop}...`)를 보고 방식을 고른다. 그래서 인코더 빈 없이 `.password("1234")`처럼 표시 없는 평문을 넣으면 로그인할 때 `There is no PasswordEncoder mapped for the id "null"` 에러가 난다. 인코더 빈 없이 평문으로 실습하려면 `.password("{noop}1234")`처럼 "암호화 안 함" 표시를 붙여야 한다. BCrypt는 같은 비밀번호도 암호화할 때마다 결과가 달라서(솔트), DB에 저장된 값을 봐도 원래 비밀번호를 알 수 없다. 다음 단계에서 사용자를 DB에 저장할 때도 이 방식으로 암호화해서 넣는다.

### 역할을 DB에 담는 두 가지 방식

관리자만 들어갈 수 있는 페이지를 만들려면 사용자에게 **역할**(role)이 있어야 한다. 사용자 정보를 DB에서 가져온다면 역할은 보통 둘 중 하나로 저장한다.

| 방식 | 구조 | 의미 |
|---|---|---|
| 회원 테이블의 컬럼 | `member(id, username, password, role)` | 한 사용자가 **역할 하나**(1:1) |
| 별도 테이블로 풀기 | `member` ─ `member_roles(member_id, role_id)` ─ `role` | 한 사용자가 **여러 역할**(다대다). 사용자이면서 관리자이면서 강사처럼 |

어느 쪽이든 결국 사용자의 역할 목록을 꺼내 `roles(...)`에 담아 주면 된다. 위 예시의 `admin`은 역할이 둘이니 다대다로 푼 경우, `user`는 하나뿐인 경우로 볼 수 있다.

## 3. SecurityFilterChain — URL별 허용 규칙

처음 스프링 시큐리티를 붙이면 **모든 페이지가 닫힌다.** "무조건 로그인을 통과하고 들어와"인 상태다. 이제 하나씩 열어 준다.

- 랜딩 페이지는 열어 둬도 된다.
- 어떤 페이지는 최소한 로그인을 해야 한다.
- 어떤 페이지는 관리자만 들어갈 수 있다.

필터는 우리가 직접 만든 게 아니다. 필터가 호출하는 이 메서드의 `http` 객체에 설정 정보를 담아 두기만 하면, 스프링 필터가 그 내용을 보고 인가 여부를 판단한다.

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/admin/**").hasRole("ADMIN")          // 관리자만
            .requestMatchers("/", "/menus/**", "/css/**").permitAll() // 누구나
            .anyRequest().authenticated()                            // 나머지는 로그인 필요
        )
        .formLogin(Customizer.withDefaults());                       // 로그인은 폼 로그인으로
    return http.build();
}
```

| 메서드 | 뜻 |
|---|---|
| `requestMatchers(...)` | 규칙을 적용할 URL 패턴. 반드시 `/`로 시작한다 |
| `permitAll()` | 로그인하지 않아도 누구나 |
| `authenticated()` | 로그인한 사용자라면 누구나 |
| `hasRole("ADMIN")` | `ADMIN` 역할을 가진 사용자만 |
| `hasAnyRole("ADMIN", "TEACHER")` | 나열한 역할 중 **하나라도** 가진 사용자 |
| `anyRequest()` | 위에서 걸리지 않은 나머지 전부 |
| `formLogin(...)` | 인증이 필요할 때 보낼 로그인 방식. 기본값은 스프링 시큐리티가 만든 로그인 페이지 |

### `*`와 `**`

메뉴 아래에 목록, 상세, 수정 페이지가 있다면 URL을 일일이 적기 귀찮다.

| 패턴 | 걸리는 URL |
|---|---|
| `/menus/*` | `/menus/list`, `/menus/1` — **한 단계**만 |
| `/menus/**` | `/menus/list`, `/menus/1/edit`, … — 그 아래 **모든 단계** |

> **추가 설명 — `hasRole`과 `ROLE_` 접두사**: `roles("ADMIN")`으로 만든 사용자는 내부적으로 `ROLE_ADMIN`이라는 권한을 갖고, `hasRole("ADMIN")`은 `ROLE_ADMIN`이 있는지 본다. 그래서 `hasRole("ROLE_ADMIN")`처럼 접두사까지 쓰면 오히려 `ROLE_ROLE_ADMIN`을 찾아 실패한다. 접두사 없이 권한 이름을 그대로 비교하고 싶으면 `hasAuthority("ROLE_ADMIN")`을 쓴다.

## 4. 규칙은 위에서부터, 처음 걸린 것 하나만

`requestMatchers`는 `switch` 문의 `case`처럼 계속 이어 붙일 수 있고, `anyRequest()`가 `default` 역할을 한다. 여러 개를 나열하면 **OR**로 합쳐진다. `/`도 열리고 `/menus/**`도 열린다.

여기서 중요한 것이 **순서**다. 요청이 오면 위에서부터 차례로 비교해서 **처음 걸린 규칙 하나만** 적용한다.

URL을 하나하나 여는 게 귀찮아서 이렇게 썼다고 해 보자.

```java
.requestMatchers("/**").permitAll()                // ① 전부 연다
.requestMatchers("/admin/**").hasRole("ADMIN")      // ② 관리자만
```

`/admin/menus`로 요청이 오면 ①에 먼저 걸려 그대로 통과한다. ②는 보지도 않는다. 강의에서 순서를 바꿔 실행해 보니, 로그인한 적도 없고 세션 ID도 없는데 관리자 페이지가 그냥 열렸다.

```java
.requestMatchers("/admin/**").hasRole("ADMIN")      // ① 좁고 엄격한 규칙을 먼저
.requestMatchers("/**").permitAll()                 // ② 넓은 규칙은 나중에
```

**권한이 필요한 중요한 규칙이 무조건 위로**, 넓게 여는 규칙은 아래로 간다. 순서를 바꾸면 큰일 난다.

### 역할자를 URL 앞에 두면 편하다

예전에 URL을 설계할 때 **역할자를 앞에 두라**(`/admin/...`, `/my/...`)고 했던 이유가 여기서 보인다.

```java
.requestMatchers("/admin/**").hasRole("ADMIN")      // 관리자 영역
.requestMatchers("/my/**").authenticated()          // 로그인한 회원 본인의 영역
.requestMatchers("/", "/menus/**", "/css/**").permitAll()
.anyRequest().authenticated()
```

`/admin/**`과 `/my/**`는 서로 겹치지 않아서 둘의 순서는 상관없다. 순서가 문제 되는 것은 **겹칠 때**뿐이다. 반대로 페이지를 넓게 펼쳐 두고 그 안에 권한이 필요한 URL을 섞어 두면, 여기서 하나하나 골라 적어야 한다.

## 5. 정적 리소스도 열어야 한다

`/`를 열고 실행하니 페이지는 나오는데 **디자인이 다 깨졌다.** CSS 파일도 요청 하나라서, 열어 준 URL 말고는 **전부 막히기** 때문이다.

```
src/main/resources/static/css/site.css   →   요청 URL: /css/site.css
```

```java
.requestMatchers("/css/**", "/js/**", "/images/**").permitAll()
```

설정은 다시 읽어야 하니 서버를 재시작한 뒤 새로고침하면 정상으로 보인다.

> **추가 설명 — 정적 리소스를 한 번에 열기**: 스프링 부트의 기본 정적 리소스 위치(`/css/**`, `/js/**`, `/images/**`, `/webjars/**`, 파비콘)를 한 번에 여는 방법도 있다.
>
> ```java
> .requestMatchers(PathRequest.toStaticResources().atCommonLocations()).permitAll()
> ```

## 6. 403 — 로그인은 했지만 권한이 없다

- `admin`으로 로그인해 `/admin/menus`에 가면 들어간다.
- 쿠키를 지우고 `user`(역할 `USER`)로 로그인해 `/admin/menus`에 가면, "아이디나 비밀번호가 틀렸다"가 아니라 **권한이 없다**는 응답이 와야 한다. 그게 **403 Forbidden**이다.

| 상태 | 뜻 | 스프링 시큐리티의 동작 |
|---|---|---|
| 401 | 누구인지 모른다(인증 안 됨) | 로그인 페이지로 보낸다 |
| 403 | 누구인지는 알지만 권한이 없다 | 권한 없음 응답 |

기본 403 화면은 볼품없다. 내가 만든 페이지를 띄우려면 HTML 하나와 설정 한 줄이면 된다.

> **추가 설명 — 403 페이지 만들기**: 가장 간단한 방법은 `src/main/resources/templates/error/403.html`을 만드는 것이다. 스프링 부트가 403 응답일 때 이 템플릿을 자동으로 보여 준다. 컨트롤러를 거쳐 원하는 화면으로 보내고 싶다면 설정에 페이지를 지정한다.
>
> ```java
> http.exceptionHandling(e -> e.accessDeniedPage("/access-denied"));
> // GET /access-denied 를 처리하는 컨트롤러와 템플릿을 만든다
> ```

> **추가 설명 — 로그인 뒤 엉뚱한 곳으로 가는 문제**: 강의에서 로그인 뒤 403 페이지가 아니라 이상한 페이지로 이동했는데, **개발자 도구를 띄워 둔 상태**라서 생긴 일로 보인다. 최근 Chrome은 개발자 도구를 열면 `/.well-known/appspecific/com.chrome.devtools.json` 같은 주소를 몰래 요청한다. 스프링 시큐리티는 로그인 전에 막힌 요청을 "로그인 뒤 돌아갈 주소"로 세션에 저장해 두는데, 이 요청이 저장되면 로그인 후 그 없는 주소로 보내 버린다. 개발자 도구를 닫고 다시 해 보거나, 그 경로를 `permitAll()`로 열어 두면 사라진다.

> 원문 바로잡기 — 강의에서는 로그아웃 기능이 없다며 쿠키를 지워 대신했는데, 스프링 시큐리티는 폼 로그인을 켜면 **로그아웃도 기본으로 제공**한다. `POST /logout`을 보내면 세션을 무효화하고 `/login?logout`으로 보낸다. CSRF 보호가 켜져 있어서 주소창에 `/logout`을 치는 GET 방식은 안 되고, 화면에 CSRF 토큰이 들어간 POST 폼 버튼을 둬야 한다(타임리프 `th:action="@{/logout}"`을 쓰면 토큰이 자동으로 들어간다).

## 7. 내가 만든 로그인 페이지 쓰기

스프링 시큐리티의 기본 로그인 페이지 대신 프로젝트에 이미 만들어 둔 로그인 페이지로 로그인하게 바꾼다.

```java
http.formLogin(form -> form
        .loginPage("/login")      // 인증이 필요하면 이 주소로 보낸다
        .permitAll()              // 로그인 페이지 자체는 누구나 볼 수 있어야 한다
);
```

| 역할 | 누가 처리하나 |
|---|---|
| `GET /login` (로그인 화면) | **내 컨트롤러**가 템플릿을 돌려준다 |
| `POST /login` (아이디·비밀번호 확인) | **스프링 시큐리티 필터**가 처리한다. 컨트롤러를 만들지 않는다 |
| 실패 | `/login?error`로 다시 보낸다 |

로그인 폼의 입력칸 이름은 스프링 시큐리티가 정해 둔 `username`, `password`에 맞춘다.

```html
<form th:action="@{/login}" method="post">
    <label>아이디</label>
    <input type="text" name="username">
    <label>비밀번호</label>
    <input type="password" name="password">
    <button>로그인</button>
</form>
```

- 원래 페이지는 아이디 칸이 `type="email"`이라, `user`처럼 이메일 형식이 아닌 아이디를 넣으면 **브라우저가 먼저 막았다**(프론트엔드 유효성 검사). `type="text"`로 바꾸고 이름표도 "이메일"에서 "아이디"로 바꿨다.
- 템플릿을 바꿨는데 안 바뀌면 재시작한다.

> 원문 바로잡기 — 강의에서 "라벨 바로 뒤에 input이 오면 누구의 라벨인지 다 아니까 `for`와 `id`는 필요 없다"며 뺐는데, HTML은 **위치만으로 라벨과 입력칸을 연결하지 않는다.** 연결하려면 `<label for="username">`과 `<input id="username">`처럼 `for`·`id`를 맞추거나, `<label>아이디 <input name="username"></label>`처럼 입력칸을 라벨 **안에** 넣어야 한다. 연결되어 있어야 라벨을 눌렀을 때 입력칸에 커서가 가고, 화면 낭독기도 어떤 칸인지 읽어 준다.

### API는 외우는 게 아니라 찾아 쓰는 것

`loginPage(...)`처럼 스프링이 정해 둔 위치에 정해 둔 키워드로 써야 하는 설정은 창의적인 게 아니라 **만들어 둔 도구를 갖다 쓰는 것**이다. 세탁기 버튼을 내 마음대로 만들지 않고 있는 대로 쓰는 것처럼. 예전에는 구글 검색으로 블로그를 찾아 복사해 쓰고, 자주 쓰는 것은 노트에 적어 두었다(그러다 노트를 검색하는 비용이 또 들었다). 지금은 AI에게 묻는다. 스프링은 버전마다 설정하는 방법이 조금씩 바뀌어서, "이 버전에 맞게" 써 달라고 하고 달라진 점이 있으면 다시 물어보면 된다. 중요한 것은 **그런 기능이 있다는 것을 알고**, 받은 코드를 이해하는 눈을 갖추는 것이다.

## 8. 다음 단계 — 사용자를 DB에서 가져오기

지금 사용자는 코드에 박혀 있다. 사용자가 늘 때마다 코드를 고칠 수는 없으니 **데이터베이스**를 쓴다. 쓸 DB는 앞에서 Docker Compose로 띄운 PostgreSQL 컨테이너다.

```bash
docker ps      # ncafe-db 컨테이너가 5432 포트로 떠 있는지 확인
```

DB 도구(DBeaver 등)에서 접속해 본다.

| 항목 | 값 |
|---|---|
| 호스트 | `localhost` |
| 포트 | `5432` |
| 데이터베이스 | `ncafe-db` |
| 사용자 / 비밀번호 | `ncafe` / `123` |

데이터베이스 이름을 잘못 적으면 접속이 안 되니 Compose 파일의 `POSTGRES_DB`와 똑같이 적는다. 접속되면 테이블은 아직 하나도 없다. 여기에 사용자·역할 테이블 세 개(사용자, 역할, 사용자-역할)를 만들고, 그 사용자로 인증을 처리하는 것이 다음 내용이다. 그 다음 날에는 세션 대신 **토큰(JWT) 기반 인증**을 다룬다.

> **추가 설명 — 그 밖에 스프링 시큐리티가 제공하는 것들**: 강의 중 "이 정도면 충분할까?"라는 질문에 나온 것들도 모두 설정으로 붙일 수 있다. 인증·인가 실패 시 내 에러 페이지 띄우기(6절), CSRF 보호(기본으로 켜져 있음), 로그인 유지(remember-me), 동시 로그인 수 제한, 비밀번호 암호화(`PasswordEncoder`) 등이다.

## 9. 한 줄 정리

- 스프링 시큐리티에서 손볼 곳은 **사용자 정보**(`UserDetailsService`, 인증)와 **URL별 허용 규칙**(`SecurityFilterChain`, 인가) 두 가지다.
- 처음에는 모든 URL이 닫혀 있다. `requestMatchers(...).permitAll()`, `.authenticated()`, `.hasRole("ADMIN")`으로 열고, 나머지는 `anyRequest()`로 정한다. `/**`는 그 아래 모든 단계다.
- 규칙은 **위에서부터 처음 걸린 것 하나만** 적용된다. 권한이 필요한 좁은 규칙을 위로, 넓게 여는 규칙을 아래로. 역할자를 URL 앞에 두면(`/admin`, `/my`) 규칙이 깔끔해진다.
- CSS 같은 **정적 리소스도 열어 줘야** 화면이 깨지지 않는다.
- 로그인은 했지만 권한이 없으면 **403**이다. `error/403.html`이나 `accessDeniedPage`로 내 페이지를 띄운다. 로그아웃은 기본 제공되는 `POST /logout`을 쓴다.
- `formLogin().loginPage("/login")`으로 내 로그인 페이지를 쓴다. 화면(GET)은 내 컨트롤러, 확인(POST)은 시큐리티 필터가 맡는다.
- 다음은 사용자를 Compose로 띄운 **PostgreSQL**에서 가져오는 것이다.
