# 인증 방식의 변화와 JWT — 세션에서 토큰으로, SAML·OAuth 2.0·BFF

## 1. 인증이란 — 사용자 식별

**인증**(Authentication)은 "지금 요청한 사람이 **누구인지 식별**하는 것"이다. 식별하는 방법은 여러 가지가 있고, 스프링 시큐리티는 그중 상당수를 지원한다.

| 인증 방식 | 설명 |
|---|---|
| Username and Password | 아이디와 비밀번호로 인증한다 (가장 고전적인 방식) |
| OAuth 2.0 Login | OpenID Connect 기반 로그인, 그리고 표준이 아닌 OAuth 2.0 로그인(예: GitHub) |
| SAML 2.0 Login | SAML 2.0으로 로그인한다 |
| Remember Me | 세션이 만료된 뒤에도 사용자를 기억한다 (로그인 유지) |
| JAAS Authentication | 자바 표준 인증 API(JAAS)로 인증한다 |
| Pre-Authentication Scenarios | 인증은 외부 장치(SiteMinder, Java EE 보안 등)가 하고, 스프링 시큐리티는 인가와 공격 방어만 맡는다 |
| X509 Authentication | 클라이언트 인증서(X.509)로 인증한다 |

이 노트에서는 아이디/비밀번호 → SAML 2.0 → OAuth 2.0 순으로 **인증 방식이 왜 바뀌어 왔는지**를 보고, 그 끝에서 우리가 쓸 **토큰(JWT)** 방식과 **BFF** 구조로 넘어간다.

## 2. 아이디/비밀번호 로그인과 세션

가장 고전적인 방식이다.

```
 브라우저 (로그인 폼)                       서버                     DB
 ──────────────────                     ──────                    ────
 아이디 / 비밀번호 ───── ① 로그인 요청 ────▶ 회원인가? 비밀번호 같은가? ◀──▶ 회원 정보
                                          │
                                          ▼ ② 인증 성공(authenticated)
                                     세션 저장소
                                     ┌───┬───┬───┐
                                     │102│   │   │  ← 사용자별 공간에 인증 정보 저장
                                     └───┴───┴───┘
           ◀── ③ 응답: 쿠키 sid=102, redirect ──
 다음 요청부터 쿠키 sid=102 를 들고 옴 → 서버는 102번 세션을 보고 "인증된 사용자"로 인가
```

1. 서버가 아이디/비밀번호를 받아 DB에서 **가입한 회원인지, 비밀번호가 같은지** 확인한다. 일치하면 **인증**된 것이다.
2. 인증 뒤에는 이 사용자에게 권한을 줘야(**인가**) 하므로, "인증했다"는 상태를 어딘가에 **유지**해야 한다. 고전적인 방법은 **서버의 세션**에 저장하는 것이다.
3. 세션은 사용자별로 나뉘어야 하므로 사용자별 **식별자**(세션 ID)를 발급하고, 이것을 **쿠키**로 브라우저에 보낸다.
4. 다음 요청부터 브라우저가 이 쿠키를 가져오면, 서버는 해당 세션의 인증 정보로 인가를 처리한다.

### 비밀번호는 해시로 저장한다 — `PasswordEncoder`

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

DB에는 사용자가 보낸 비밀번호(`123`)를 그대로 저장하지 않고, 그 **해시값**을 저장한다.

- **해시**: 원문을 뭉개서 만든 값이다. 원문이 같아야만 같은 값이 나오고, 해시값에서 원문을 **되살릴 수 없다**. 그래서 **단방향 암호화**라고 한다(되돌릴 수 있는 것은 양방향 암호화).
- 해시는 원문을 **식별하는 키**로만 쓴다. 서버는 비밀번호 자체를 갖고 있지 않으므로, 유출되어도 원래 비밀번호가 드러나지 않는다.
- 국내에서는 개인정보 보호 관련 법령이 비밀번호를 **일방향 암호화하여 저장**하도록 정하고 있어서, 평문 저장은 법 위반이 된다.

| 시점 | 하는 일 |
|---|---|
| 회원가입 | `encode(원문)`으로 해시를 만들어 저장 |
| 로그인 | 입력한 원문과 저장된 해시를 `matches()`로 비교 → 같으면 인증 |

> 원문 바로잡기 — "로그인할 때 입력값도 다시 해시로 만들어서 저장된 것과 같은지 비교한다"고 했다. 원리는 맞지만, BCrypt는 해시할 때마다 무작위 **솔트**를 섞기 때문에 `encode()`를 다시 호출하면 **매번 다른 값**이 나와서 그대로 비교하면 항상 틀린다. 저장된 해시 문자열(`$2a$10$` + 솔트 22자 + 해시 31자) 안에 **솔트가 같이 들어 있어서**, `matches()`가 그 솔트를 꺼내 **같은 솔트로** 입력값을 다시 해시한 뒤, 그 결과를 저장된 해시와 비교한다. 그래서 비교는 반드시 `matches()`로 한다.

> **추가 설명 — 솔트로 비교하는 원리**: 솔트는 **빼고** 검사하는 것도, **따로** 검사하는 것도 아니다. 다시 계산할 때 넣는 **재료**다.
>
> **① 솔트가 없으면** 같은 입력은 항상 같은 해시가 나온다.
>
> ```
> 해시("1111") → abc123     (언제 해도 abc123)
> 해시("1112") → x9k2pq     (한 글자만 달라도 완전히 다름)
> ```
>
> 그러면 비밀번호가 같은 사람끼리는 DB에 같은 값이 저장되고, 흔한 비밀번호의 해시를 미리 계산해 둔 표(**레인보우 테이블**)로 해시를 보자마자 원래 비밀번호를 알아낼 수 있다.
>
> **② 솔트를 넣으면** 회원가입할 때 무작위로 뽑은 솔트를 비밀번호에 섞어서 해시하고, 솔트와 해시를 **붙여서 같이 저장**한다.
>
> ```
> A씨 (비밀번호 1111)
>   솔트를 무작위로 뽑음    → "Qz7"
>   해시("1111" + "Qz7")   → m4t8w1
>   DB에 저장              → Qz7 + m4t8w1
>
> B씨 (비밀번호도 1111)
>   솔트를 무작위로 뽑음    → "k2P"
>   해시("1111" + "k2P")   → 7rn0ya
>   DB에 저장              → k2P + 7rn0ya
> ```
>
> 비밀번호가 같아도 저장된 값이 완전히 다르고, 미리 만든 표는 이 솔트를 모르고 만든 것이라 쓸모가 없다.
>
> **③ 로그인할 때**는 저장된 솔트를 꺼내 입력값에 **똑같이** 섞어서 다시 해시한다.
>
> ```
> A씨가 1111 입력
>   ① DB에서 A씨의 값을 가져옴           → Qz7 + m4t8w1
>   ② 앞부분에서 솔트를 읽음              → Qz7
>   ③ 입력값에 그 솔트를 섞어 다시 해시    → 해시("1111" + "Qz7") = m4t8w1
>   ④ 저장된 해시와 비교                 → m4t8w1 == m4t8w1 → 통과
>
> A씨가 1112 입력
>   ③ 해시("1112" + "Qz7") = p0z3cc
>   ④ p0z3cc != m4t8w1 → 실패
> ```
>
> 같은 솔트를 넣어야 회원가입 때와 **조건이 똑같아지고**, 그래야 남는 차이가 비밀번호뿐이다. 결과가 같으면 비밀번호가 같다는 뜻이 된다.
>
> **④ `encode()`를 다시 부르면** 솔트를 또 새로 뽑으므로(`"W9d"` → `2hq6sv`) 비밀번호가 맞는데도 저장된 값과 달라 실패한다.
>
> | | 솔트 | 쓰는 곳 |
> |---|---|---|
> | `encode(원문)` | **새로** 무작위로 뽑음 | 회원가입, 비밀번호 변경 |
> | `matches(원문, 저장된 값)` | 저장된 값에서 **꺼내서** 씀 | 로그인 |
>
> **⑤ 실제 BCrypt 문자열**에서는 위의 `Qz7 + m4t8w1`이 이런 모양이다.
>
> ```
> $2a$10$8.UnVuG9HHgffUDAlk8qfOUVGkqRzgVymGe07xd00DMxs.AQp.o.O
> │  │  │                     │
> │  │  └─ 솔트 22자 ──────────┘└─ 해시 31자 ──────────────────┘
> │  └─ 비용 10 (계산을 2¹⁰번 반복)
> └─ 버전 2a
> ```
>
> `matches()`는 앞의 **버전, 비용, 솔트**를 그대로 읽어 같은 조건으로 입력값을 계산하고, 그렇게 만든 문자열이 저장된 문자열과 같은지 비교한다.
>
> **⑥ 솔트가 다 보여도 괜찮은 이유**: 솔트는 비밀번호가 아니라 섞는 재료일 뿐이다. 해시는 되돌릴 수 없어서 솔트를 알아도 비밀번호를 거꾸로 계산할 수 없다. 공격자는 비밀번호를 하나씩 넣어 보는 수밖에 없는데, 솔트가 사람마다 달라서 **사람마다 처음부터 따로** 대입해야 한다. 게다가 BCrypt는 비용 값만큼 일부러 계산을 느리게 만들어서, 한 번 대입하는 데에도 시간이 오래 걸린다.

## 3. SAML 2.0 — 회사 안에서 한 번만 로그인 (SSO)

### 문제: 서버마다 로그인을 따로 해야 한다

처음에는 서버가 하나였고, **서비스를 제공하는 서버**(SP, Service Provider)가 **인증도 같이** 했다. 지금까지 우리가 써 온, 너무나 당연한 방식이다.

그런데 회사가 커지면 사업부나 계열사별로 서버를 따로 운영하게 된다. 같은 회사인데도 서버마다 **회원 정보를 따로 관리**하니, 사용자는 서비스마다 로그인을 따로 해야 한다.

```
 사용자 ──▶ 메일 서버   (SP 겸 인증) ─ DB(회원)
 사용자 ──▶ 쇼핑 서버   (SP 겸 인증) ─ DB(회원)     ← 같은 회사인데 계정이 셋
 사용자 ──▶ 클라우드 서버 (SP 겸 인증) ─ DB(회원)
```

OTT 서비스마다 아이디/비밀번호가 다른 것과 같다. 비밀번호를 똑같이 맞추기는 찜찜해서 서비스마다 다르게 하다 보면 자꾸 잊어버리고, 주기적으로 바꾸기까지 해야 해서 "비밀번호 찾기"만 반복하게 된다.

### 해결: 인증만 전담하는 서버(IdP)를 둔다

각 서버의 DB에서 **인증 정보를 빼낸다**. "너희는 인증하지 마, 내가 인증할게" 하는 **IdP**(Identity Provider, 신원 제공자)를 따로 둔다.

```
 사용자 ──▶ 메일 서버     (SP) ◀──┐
 사용자 ──▶ 쇼핑 서버     (SP) ◀──┼──▶ IdP (신원 제공자) ─ DB(회원)
 사용자 ──▶ 클라우드 서버 (SP) ◀──┘
```

1. 사용자가 SP에 접속하면, SP는 "나한테 오지 말고 IdP로 가세요" 하고 **IdP로 리다이렉트**한다.
2. IdP가 로그인 창을 띄우고, 아이디/비밀번호를 받아 인증한다.
3. IdP가 "이 사람은 인증되었다"는 결과를 다시 브라우저 리다이렉트를 통해 **SP에 전달**한다. 이 결과가 일종의 토큰인데, 그 **표기법**이 SAML(XML)이다.

| 항목 | 내용 |
|---|---|
| 이름 | Security Assertion Markup Language — "보안 주장을 담는 마크업 언어(XML)" |
| 주요 목적 | **웹 싱글 사인온(SSO)** — 하나의 계정으로 여러 웹 서비스에 접근 |
| 동작 방식 | SP가 IdP에게 인증을 **위임**하고, IdP는 인증 후 SP로 인증 결과를 전달 |
| 특징 | XML 기반 메시지, 브라우저 리다이렉션으로 SAML 요청과 응답을 전달, 주로 **엔터프라이즈** 환경에서 사용 |

**싱글 사인온**(SSO)이라는 용어가 이때 나왔다. 한 번 로그인하면 관련된 서비스를 모두 쓸 수 있다는 뜻이다. 대표적인 예가 마이크로소프트로, 예전에는 클라우드(OneDrive), 오피스, 게임 계정이 따로라 사용자가 불편했는데 "한 번만 로그인하면 우리 서비스를 모두 쓸 수 있다"로 바뀌었다.

## 4. OAuth 2.0 — 회사 밖까지 열린 SSO

### 문제: 인증 서버가 회사 안에 갇혀 있다

SAML의 IdP는 그 계열사들끼리만 약속해서 쓰는 **폐쇄형** 인증 센터였다. 그런데 인증 서버를 따로 둘 여력이 없는 **작은 사이트**가 많아졌고, 회사를 넘나드는 SSO가 필요해졌다. "협의만 되면 어느 회사든 한 번 로그인한 걸로 쓰면 안 되나?" 하는 생각에서 **개방형 SSO**가 나온다.

### 해결: 공인된 회사가 인증 서버를 공개한다

구글, 네이버, 마이크로소프트, 카카오 같은 회사가 인증 서버를 **공개**한다. 인증 서버 운영 비용은 들지만 얻는 것이 더 많다.

- 자기 회원이 늘어난다.
- 시장을 많이 가져갈수록 자기 계정의 신뢰도가 높아진다.
- 다른 서비스에서도 자기 계정이 쓰인다.

이것이 우리가 쓰는 "구글로 로그인", "카카오로 로그인"이다.

| 항목 | 내용 |
|---|---|
| 이름 | Open Authorization Protocol |
| 정의 | 서로 다른 애플리케이션이 사용자의 비밀번호나 계정을 노출하지 않고도 안전하게 자원에 접근하도록 설계된 방식 |
| 핵심 | **액세스 토큰 기반** — 비밀번호나 계정을 직접 공유하지 않고, 액세스 토큰으로 자원에 접근 |

### 네 가지 역할

```
                         ┌────────────────────────┐
 사용자 ◀──▶ 우리 서비스 ◀──▶ 구글 인가 서버 ─ DB(회원) │
 (Resource   (Client)     │ (Authorization Server) │
  Owner)       │          └────────────────────────┘
               │ 사용자 DB를 두지 않음
               ▼
          구글 API (Resource Server) — 사용자의 프로필, 사진, 일정 등
```

| 역할 | 뜻 | 예 |
|---|---|---|
| Resource Owner | 자원의 **주인** = 사용자 | 구글 계정을 가진 나 |
| Client | 사용자를 대신해 자원에 접근하려는 **애플리케이션** | 우리가 만든 서비스 |
| Authorization Server | 사용자를 인증하고 **토큰을 발급**하는 서버 | 구글 로그인 서버 |
| Resource Server | 토큰을 받고 **자원을 내주는** 서버 | 구글 API 서버 |

> 원문 바로잡기 — "클라이언트는 여러분들, 서버에 접속하는 사용자"라고 했지만, OAuth에서 사용자는 **Resource Owner**이고 **Client는 애플리케이션**(우리 서비스)이다. 또 Authorization Server는 "인증 서버"보다 "**인가** 서버"가 정확한 이름이다.

> 원문 바로잡기 — OAuth를 "오픈 인증 방식"이라고 불렀는데, 이름 그대로 OAuth는 **인가**(Authorization) 프로토콜이다. "이 앱이 내 자원에 접근해도 된다"는 **권한 위임**이 원래 목적이다. 여기에 "이 사람이 누구인가"를 알려 주는 **인증** 계층을 얹은 것이 **OpenID Connect**(OIDC)이고, 소셜 로그인은 보통 OIDC를 쓴다. 스프링 시큐리티 목록에 "OAuth 2.0 Login — OAuth 2.0 Log In with OpenID Connect"라고 적힌 이유다.

> **추가 설명 — 토큰 형식**: "공개형 토큰은 JWT 형식"이라고 했다. OIDC의 **ID 토큰**은 반드시 JWT이지만, OAuth의 **액세스 토큰** 형식은 표준이 정하지 않아서 JWT일 수도 있고 그냥 무작위 문자열일 수도 있다. SAML은 XML, OIDC는 JSON(JWT)이라는 **포장 방식**이 다를 뿐, "인증 정보를 토큰으로 넘긴다"는 생각은 같다.

## 5. 프론트/백엔드 분리 — 세션 방식의 한계

SSO와 별개로, **기술 구조**가 바뀌면서도 세션 방식이 어려워졌다.

| | 과거 (서버 중심 웹) | 현재 (풀스택) |
|---|---|---|
| 서버 | 스프링 서버 **하나** | 프론트엔드 서버(Next.js) + 백엔드 API 서버(스프링) |
| 화면 | 서버가 타임리프·JSP로 HTML을 완성해서 전달 | 프론트엔드 서버가 화면(UI) 생성 |
| 데이터 | 같은 서버가 처리 | 백엔드가 JSON으로 제공 |
| 인증 상태 | 서버 메모리(세션) + 쿠키(세션 ID) — **Stateful** | ? |

과거에는 브라우저와 서버 **둘만** 있었으니, 서버가 세션에 중요한 정보를 두고 브라우저에는 쿠키로 식별자 하나만 주면 됐다.

지금은 서버가 둘이다. 문서는 프론트엔드에게, 데이터는 백엔드에게 달라고 한다. 그러면 세션은 **어디에** 저장해야 할까?

- 프론트엔드에 저장하면 페이지는 줄 수 있지만, 백엔드는 그 세션을 모르니 데이터를 줄 수 없다.
- 백엔드가 "무조건 믿어 줄게" 하고 열어 두면, 밖에서 아무나 요청해도 열린다는 뜻이다. 백엔드도 보안이 필요하다.
- 두 서버가 세션을 **공유**하게 할 수는 있지만, 공유 공간 관리와 동기화가 어렵다. 사용자 수백, 수천 명이 동시에 오가는 상황에서 세션이 만료될 때 양쪽에서 같이 사라지게 하는 것부터 보통 일이 아니다.

게다가 앞으로는 API 서버도 여러 개로 나뉠 수 있다. 서버가 3개, 4개, 5개가 되면 그 모두가 인증 상태를 공유해야 한다.

### 쿠키로 보내면 되지 않을까?

쿠키는 **그 쿠키를 만든 서버**가 클라이언트에게 맡겨 둔 데이터다. 브라우저는 쿠키를 만든 서버(호스트)에게만 그 쿠키를 보낸다. 페이지 서버와 API 서버는 주소(호스트)가 다르니, 한쪽이 발급한 쿠키가 다른 쪽에는 가지 않는다.

### 결론: 상태를 서버에 두지 않는다 — Stateless + 토큰

- 인증 정보를 서버(세션)에 두지 말고 **클라이언트가 갖고 다니게** 한다. 이것이 **토큰**이다. 예전에 버스 탈 때 내던 토큰처럼, 들고 다니다가 보여 주는 증표다.
- 서버 어디에도 인증 상태를 저장하지 않으므로 **Stateless**(상태 비유지)라고 한다. 정확히는 클라이언트가 상태를 들고 다니는 방식이다.
- 토큰은 쿠키 대신 **요청 헤더**에 실어 보낼 수 있다.
- 토큰에 담는 인증 정보의 **형식**이 **JWT**다. 토큰 = 인증 정보, JWT = 그 정보를 담는 구조.

> **추가 설명 — "쿠키는 다른 서버로 못 간다"의 정확한 범위**: 쿠키는 "만든 서버에만" 간다기보다 **도메인 규칙**을 따른다. `Domain=example.com`으로 발급하면 `www.example.com`과 `api.example.com` 모두에 간다. 또 Nginx 하나로 프론트와 백엔드를 **같은 주소** 아래 묶으면(`/`는 Next.js, `/api`는 스프링) 브라우저 입장에서는 서버가 하나이므로 쿠키가 양쪽에 다 간다. 그래도 서버 측 **세션 저장소를 공유**해야 하는 문제는 그대로이므로, 토큰으로 가는 이유는 여전히 유효하다.

## 6. JWT 구조

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

```
1. 헤더
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.
2. 페이로드
eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ
.
3. 서명
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

실제 토큰은 줄바꿈 없이 `헤더.페이로드.서명`처럼 한 줄로 이어진, 점(`.`)으로 구분된 세 부분이다. https://jwt.io 에 붙여 넣으면 바로 풀어서 보여 준다.

| 부분 | 들어 있는 것 | 예 |
|---|---|---|
| 1. 헤더 (Header) | **서명 알고리즘**(`alg`)과 토큰 유형(`typ`) | `{"alg": "HS256", "typ": "JWT"}` |
| 2. 페이로드 (Payload) | 사용자 정보와 권한 등 데이터(**클레임**) | `{"sub": "1234567890", "name": "John Doe", "iat": 1516239022}` |
| 3. 서명 (Signature) | 위조 방지 및 발급자 확인용 값 | `HMACSHA256(BASE64URL(헤더) + "." + BASE64URL(페이로드), 비밀키)` |

자주 쓰는 표준 클레임은 다음과 같다.

| 클레임 | 뜻 |
|---|---|
| `iss` (issuer) | 토큰 **발급자** |
| `sub` (subject) | 토큰의 **주체** (보통 사용자 식별자) |
| `aud` (audience) | 토큰을 **받을 대상** 서비스 |
| `exp` (expiration) | **만료** 시간 |
| `iat` (issued at) | **발급** 시간 |

### 암호화가 아니라 인코딩이다

각 부분은 **Base64URL로 인코딩**된 것이라 암호문처럼 보이지만, 누구나 디코딩해서 내용을 볼 수 있다. Base64는 바이너리를 문서(텍스트)에 넣을 수 있도록 **문자로 바꾸는 인코딩**이다. HTML에 이미지를 `src="data:image/png;base64,..."`로 직접 박아 넣는 것도 같은 원리다.

> 원문 바로잡기 — "Base64는 암호화가 아니고 압축"이라는 말이 나왔다가 "압축이라고 하기는 좀 그렇다"고 정정되었다. Base64는 **압축도 아니다**. 3바이트를 4글자로 바꾸므로 오히려 크기가 약 **33% 늘어난다**. 단순히 **인코딩**이다.

그래서 페이로드에 **비밀번호 같은 민감한 정보를 넣으면 안 된다**. 내용 자체를 숨겨야 한다면 **JWE**(JSON Web Encryption)라는 암호화된 토큰 형식을 쓴다. 대신 이 토큰을 받는 모든 서버가 복호화 작업을 해야 한다.

### 그러면 무엇을 보고 토큰을 믿는가

JWT가 안전하다고 하는 근거는 **내용을 숨기는 것**이 아니라 **바뀌지 않았음을 증명하는 것**이다. 다른 서버가 발급한 토큰을 받은 서버는 두 가지를 확인한다.

**① 위조·변조되지 않았는가 — 서명 검증**

1. 받은 토큰의 헤더에서 서명 알고리즘(예: HS256)을 확인한다.
2. 헤더와 페이로드를 그 알고리즘과 **비밀키**로 다시 계산한다.
3. 계산 결과가 토큰의 서명과 다르면 → 위조·변조된 토큰이다.

**② 믿을 만한 토큰인가 — 클레임 검증**

서명이 맞으면 페이로드를 보고 판단한다.

- 내가 허용하는 **발급자**(`iss`)가 발급했는가
- 내가 **받을 대상**(`aud`)에 포함되는가
- 아직 **만료**(`exp`)되지 않았는가

이 조건이 모두 맞으면 토큰을 인정한다.

> 원문 바로잡기 — "누가 해도 이 원문을 이 알고리즘으로 돌리면 해시값이 나온다", "위조한 사람이 서명까지 위조해 버리면 못 막는다"고 했다. 여기서 빠진 것이 **비밀키**다. 서명은 그냥 해시가 아니라 **비밀키를 섞은 해시**(HMAC)이거나 **개인키로 만든 전자서명**(RS256 등)이다. 페이로드를 바꾼 사람이 서명을 다시 만들려면 발급 서버의 비밀키가 있어야 하므로, 키가 새지 않는 한 **서명까지 맞춘 위조는 불가능**하다. 그래서 검증하는 서버도 같은 비밀키(HS256)나 발급자의 공개키(RS256)를 갖고 있어야 한다.

> **추가 설명 — JWT의 진짜 약점은 탈취**: 내용을 바꾸는 것은 막을 수 있지만, 토큰을 **통째로 훔쳐서 그대로 쓰는 것**은 서명으로 막을 수 없다. 서명이 정상이니까 서버는 진짜 사용자로 본다. 그래서 다음 세 가지를 같이 쓴다.
> - **HTTPS**로 전송 중 가로채기를 막는다.
> - 액세스 토큰의 **만료 시간을 짧게** 잡는다(몇 분~몇십 분). 길게 로그인을 유지하려면 별도의 리프레시 토큰을 쓴다.
> - 브라우저에서는 자바스크립트가 읽을 수 없는 곳(**HttpOnly 쿠키**)에 보관한다(7절).
>
> 또 세션은 서버에서 지우면 바로 로그아웃되지만, JWT는 서버가 상태를 갖지 않으므로 **발급한 토큰을 만료 전에 무효로 만들기 어렵다**. 이 점도 만료 시간을 짧게 잡는 이유다.

## 7. 토큰을 어디에 담아 보내나 — 쿠키 vs 헤더

클라이언트가 서버로 데이터를 담아 보내는 곳은 크게 **쿠키**와 **헤더** 두 군데다.

| | 쿠키 | 헤더 (`Authorization`) |
|---|---|---|
| 기본 선택 | **특별한 이유가 없으면 쿠키**가 제일 좋다 | 쿠키를 쓸 수 없을 때 |
| 보내는 방식 | 브라우저가 자동으로 붙여 보냄 | 코드에서 직접 넣어야 함 |
| 한계 | 쿠키를 **만든 서버**(도메인)에게만 간다 | 어느 서버에든 보낼 수 있다 |

쿠키는 서버가 만들어 클라이언트에게 준 것이라, 그 서버와 대화할 때는 가장 편하다. 하지만 쿠키를 만들지 않은 **다른 서버**와도 같은 인증 정보를 공유해야 할 때가 있다. 그 서버에게는 쿠키가 가지 않으니 **헤더**로 보낸다.

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOi...
```

무조건 헤더가 정답은 아니다. 토큰을 발급한 서버와는 쿠키로 주고받고, 다른 서버에게만 헤더로 보내도 된다. 귀찮으면 둘 다 헤더로 보낼 수도 있다. **상황에 따라 판단하는 기준**을 갖고 있는 것이 중요하다.

> 원문 바로잡기 — "헤더에 베어러라고 하는 키가 있다"고 했는데, 헤더의 **이름(키)은 `Authorization`**이고 `Bearer`는 그 **값 앞에 붙는 인증 방식 표시**다. "이 토큰을 가진 사람(bearer)에게 권한을 준다"는 뜻이다.

> **추가 설명 — localStorage에 두면 안 되는 이유**: starter 프로젝트가 토큰을 브라우저의 **localStorage**에 저장한다며 이 방식은 쓰지 않겠다고 했다. localStorage는 자바스크립트로 누구나 읽을 수 있어서, 페이지에 악성 스크립트가 한 줄만 들어가도(XSS) 토큰을 훔쳐 갈 수 있다. **HttpOnly 쿠키**는 자바스크립트가 읽을 수 없어서 이 공격에 강하다. 다음에 볼 BFF + Auth.js 구조가 바로 토큰을 HttpOnly 쿠키에 두는 방식이다.

## 8. 인증 흐름은 세션이든 JWT든 같다

토큰을 쓰든 세션을 쓰든 스프링 시큐리티 안의 인증 흐름은 같다. 아래는 HTTP Basic 인증의 흐름이다.

```
SecurityFilterChain
  └─ BasicAuthenticationFilter  (인증 상태를 확인하는 필터)
        │ ① 요청에서 아이디/비밀번호를 꺼내 UsernamePasswordAuthenticationToken 생성
        ▼
     ② AuthenticationManager — 인증되었나?
        │
        ├─ ③ 실패 ─▶ SecurityContextHolder 비움
        │           RememberMeServices.loginFail()
        │           AuthenticationEntryPoint (다시 인증하라고 응답, 보통 401)
        │
        └─ ④ 성공 ─▶ SecurityContextHolder 에 인증 정보 저장
                    RememberMeServices.loginSuccess()
                    Continue Application (다음 필터, 컨트롤러로 진행)
```

- **SecurityContextHolder**: 인증 정보를 담아 두는 곳이다. 여기서 인증 정보를 꺼내면 **UserDetails**(사용자 정보)가 나온다.
- 컨트롤러에서 "지금 로그인한 사용자"를 얻을 때 꺼내는 곳이 여기다.
- UserDetails를 직접 확장한 **커스텀 UserDetails** 클래스를 만들면, 이름과 역할 외에 닉네임 같은 추가 정보도 여기에 담을 수 있다. UserDetails 타입으로 참조되므로 확장한 클래스도 그대로 들어간다.

> 원문 바로잡기 — "SecurityContextHolder가 곧 세션이라고 보면 된다"고 했는데, 정확히는 **요청 하나를 처리하는 동안** 인증 정보를 들고 있는 곳(스레드별 저장소)이다. 세션 방식에서는 요청이 끝날 때 이 내용을 **세션에 저장**해 두었다가 다음 요청에서 다시 꺼내 채운다. Stateless(JWT) 방식에서는 세션에 저장하지 않고, **매 요청마다 토큰을 검증해서** SecurityContextHolder를 새로 채운다. "세션처럼 인증 정보를 꺼내 쓰는 곳"이라는 이해는 맞지만 세션 자체는 아니다.

> 원문 바로잡기 — "UserDetails는 사용자 이름과 role 정보만 가지고 있다"고 했는데, 기본 `UserDetails`에는 **비밀번호**와 계정 상태 4가지(만료, 잠김, 비밀번호 만료, 활성화)도 들어 있다. 추가로 담고 싶은 정보가 있을 때 커스텀 UserDetails를 만든다는 흐름은 같다.

### 스프링 시큐리티 설정에서 달라지는 점

수업 프로젝트(ncafe)의 `SecurityConfig`를 보면 이전 실습과 달라진 곳이 보인다.

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http, ProblemDetailAuthHandlers authHandlers) throws Exception {
    http
            .csrf(csrf -> csrf.disable())
            .cors(Customizer.withDefaults())
            .formLogin(form -> form.disable())          // 폼 로그인이 사라짐
            .httpBasic(basic -> basic.disable())
            .sessionManagement(session -> session
                    .sessionCreationPolicy(SessionCreationPolicy.STATELESS))   // 세션을 쓰지 않음
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers("/api/user/**").permitAll()
                    .requestMatchers("/api/member/auth/**").permitAll()
                    .requestMatchers("/api/member/**").authenticated()
                    .requestMatchers("/api/admin/**").hasRole("ADMIN")
                    .anyRequest().denyAll())
            .oauth2ResourceServer(oauth2 -> oauth2      // 폼 로그인 대신 JWT 검증이 끼어듦
                    .jwt(jwt -> jwt.jwtAuthenticationConverter(jwtAuthenticationConverter())));
    return http.build();
}

/** 토큰의 "roles" 클레임을 ROLE_ 접두어 권한으로 바꾼다. hasRole("ADMIN")과 맞물린다. */
private JwtAuthenticationConverter jwtAuthenticationConverter() {
    JwtGrantedAuthoritiesConverter authorities = new JwtGrantedAuthoritiesConverter();
    authorities.setAuthoritiesClaimName("roles");
    authorities.setAuthorityPrefix("ROLE_");

    JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(authorities);
    return converter;
}

@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();          // 인코더는 그대로 있음
}
```

| 이전 실습 | 지금 |
|---|---|
| `UserDetailsService` 빈으로 사용자를 제공 | 사라짐 — 로그인은 `AuthService`가 직접 처리하고 JWT를 발급 |
| `formLogin` | 사라짐 — 대신 `oauth2ResourceServer().jwt()`가 **매 요청의 토큰을 검증** |
| 세션에 인증 상태 저장 | `STATELESS` — 세션을 만들지 않음 |
| `PasswordEncoder` | 그대로 — 로그인할 때 비밀번호 비교에 쓰임 |

- `JwtAuthenticationConverter`는 검증된 JWT를 스프링 시큐리티의 인증 정보로 바꾸는 변환기다. 여기서는 토큰의 `roles` 클레임을 `ROLE_ADMIN` 같은 권한으로 바꿔 `hasRole("ADMIN")`과 맞물리게 한다.
- 토큰 발급과 검증에 쓰는 도구(`JwtEncoder`, `JwtDecoder`)는 `JwtConfig`에 있다. HS256 비밀키(32바이트 이상)로 발급하고 같은 키로 검증한다.

> **추가 설명 — "authorization converter"**: "authorization converter를 만들어야 한다"고 한 것은 위 코드의 `JwtAuthenticationConverter`다. 이름 그대로 **Authentication**(인증 정보)으로 바꾸는 변환기다.

## 9. 프론트엔드 보안과 백엔드 보안 — BFF

### 보안이 필요한 곳은 두 군데

브라우저, Next.js(페이지 서버), 스프링 부트(API 서버)가 있다면 보안도 두 가지가 필요하다.

| 보안 | 막는 것 |
|---|---|
| **프론트엔드 보안** | 페이지 요청 — 로그인하지 않은 사용자에게 관리자 페이지를 주지 않는다 |
| **백엔드 보안** | 데이터(API) 요청 — 권한 없는 사용자에게 데이터를 주지 않는다 |

### SSR과 CSR의 요청 경로가 다르다

```
                    ┌──────────── Compose 네트워크 ──────────────┐
                    │                                            │
 브라우저 ──(80/443)──▶ Next.js ──── SSR 데이터 요청 ───▶ 스프링 API │
     │              │                                     ▲      │
     └────────────── CSR 데이터 요청 (직접 가려면 포트를 열어야 함) ──┘      │
                    └────────────────────────────────────────────┘
```

- **SSR**(서버 사이드 렌더링): 문서를 **Next.js 서버에서** 만든다. 만들 때 필요한 데이터도 Next.js가 요청하므로 **네트워크 안에서만** 오간다.
- **CSR**(클라이언트 사이드 렌더링): 문서를 **브라우저에서** 만든다. 브라우저가 데이터를 직접 요청해야 하므로, 스프링 API가 밖에 열려 있어야 한다. 그러면 백엔드에도 보안이 필요하다.

### 해결: 모든 요청을 Next.js를 통해서만 보낸다 — BFF

CSR이라도 데이터를 요청할 때 **Next.js를 거쳐서** 가게 하면 어떨까?

```
 브라우저 ──(443)──▶ Nginx ──▶ Next.js (BFF) ──▶ 스프링 API ──▶ PostgreSQL
                     ▲          │                 ▲              ▲
                 유일한 입구     │                 └─ 포트 안 열림 ─┘
                                └─ 페이지 + 데이터 요청 모두 여기서 처리
```

- 스프링 API는 Compose 네트워크 안에 **숨겨져** 포트도 열려 있지 않다. 밖에서 접근할 방법 자체가 없다.
- 밖에 노출되는 것은 Nginx(443, HTTPS) 하나뿐이고, DB도 안에 가둬 둔다.
- 프론트엔드 쪽만 철통같이 막아 두면, 백엔드 보안을 따로 걱정할 일이 크게 줄어든다.

이렇게 **프론트엔드를 위한 백엔드**를 하나 두고 모든 요청을 그곳으로 모으는 구조를 **BFF**(Backend For Frontend) 아키텍처라고 한다.

API에는 두 종류가 있다.

| | 범용 API | 백엔드 API |
|---|---|---|
| 고객 | 누구나 (공개 목적) | **우리 프론트엔드 하나** |
| 공개 | 공개해야 함 | 공개할 이유가 없음 → **숨긴다** |

우리가 만드는 스프링 API는 프론트엔드만 바라보는 백엔드 API이므로 굳이 공개할 필요가 없다. 숨기고 나면 남는 문제가 "CSR은 어떻게 백엔드에 가지?"인데, 이것을 BFF가 해결한다. 포트폴리오에서는 "백엔드 API를 고립시키고 BFF 방식으로 보안을 처리했다"고 설명하면 된다.

> **추가 설명 — 그래도 백엔드에 JWT를 거는 이유**: 백엔드가 숨겨져 있으면 이론상 백엔드 보안은 없어도 된다. 그래도 수업에서는 Next.js가 발급한 토큰을 스프링에도 **공유**해서 검증하게 한다. 혹시 모를 **뒷문**(설정 실수로 포트가 열리거나, 내부의 다른 컨테이너가 침해되는 경우)을 막기 위해서다. 또 스프링을 풀스택의 일부가 아니라 **단독 API 서버**로 쓸 때는 스프링 자체가 토큰을 발급하고 검증해야 한다. 이렇게 보안을 여러 겹으로 두는 것을 **심층 방어**라고 한다.

### 토큰은 누가 발급하나

프론트엔드와 백엔드 중 누가 토큰을 발급해야 할까? 수업에서는 **Next.js(BFF)가 발급**한다. BFF 구조에서는 모든 요청의 입구가 Next.js이기 때문이다. 스프링이 발급하는 경우는, 풀스택이 아니라 스프링이 **온전한 API 서버**로 쓰일 때다.

## 10. Next.js로 보는 서버 기능

Next.js는 브라우저에 페이지를 주는 도구이지만, 그 **자체가 서버**다. 브라우저는 샌드박스에 막혀 DB에 접근할 수 없지만, Next.js 서버는 가능하다. 그래서 Next.js는 **페이지도, API도** 만들 수 있다.

| | 하는 일 |
|---|---|
| SSR | Next.js 서버가 페이지를 만들어서 준다 |
| CSR | Next.js 서버가 JS를 주고, 브라우저가 페이지를 만든다 |
| API | Next.js 서버가 데이터를 준다 (Route Handler) |

규모가 아주 크지 않으면 Next.js만으로도 카페 앱 정도는 충분히 만든다. 요즘은 Next.js만으로 풀스택을 만드는 경우가 많고, 스프링을 쓰는 이유는 API를 여러 개로 나누기 쉽고 자바 언어와 생태계가 주는 **견고한 아키텍처** 때문이다.

### `page.tsx` 대신 `route.ts` — API 만들기

```
app/
└─ api/
   └─ menus/
      └─ route.ts      ← /api/menus 로 요청하면 데이터를 준다
```

```ts
// app/api/menus/route.ts
import { NextResponse } from "next/server";

const menus = [                                   // 더미 데이터
  { id: 1, name: "아메리카노", price: 4500 },
  { id: 2, name: "카페라떼", price: 5000 },
];

export async function GET() {                     // 함수 이름이 곧 처리할 HTTP 메서드
  return NextResponse.json(menus);
}

export async function POST(request: Request) {
  const body = await request.json();
  return NextResponse.json({ ...body, id: 3 }, { status: 201 });
}
```

- 폴더 안에 `page.tsx`를 두면 **페이지 주소**가 되고, `route.ts`를 두면 **데이터를 반환하는 API**가 된다. 스프링으로 치면 `@RestController`다.
- `export`한 함수의 **이름**(`GET`, `POST`, `PUT`, `DELETE` 등)이 그 HTTP 메서드의 요청을 처리한다.

> **추가 설명 — 같은 폴더에 둘 다 두면**: 한 폴더(같은 경로)에 `page.tsx`와 `route.ts`를 함께 둘 수 없다. 같은 주소가 페이지인지 API인지 정할 수 없기 때문이다. 그래서 API는 보통 `app/api/` 아래에 모아 둔다.

### 그 밖의 특수 파일

| 파일 | 역할 |
|---|---|
| `page.tsx` | 페이지 |
| `route.ts` | API (데이터) |
| `loading.tsx` | 페이지를 서버에서 만들어 오는 동안 잠깐 보여 줄 로딩 화면 |
| `not-found.tsx` | 페이지를 찾을 수 없을 때 자동으로 보여 줄 화면 |
| `error.tsx` | 에러가 났을 때 보여 줄 화면 |

> 원문 바로잡기 — `loading.tsx`는 "서버 사이드 렌더링일 때만 의미가 있고 클라이언트 사이드일 때는 전혀 통하지 않는다"고 했다. 정확히는 `loading.tsx`는 그 경로의 **서버 컴포넌트가 데이터를 받아 페이지를 만드는 동안** 보여지는 화면이다. 페이지를 이동할 때도 동작한다. 다만 페이지가 열린 뒤 브라우저에서 `useEffect`로 데이터를 받아오는 경우(순수 CSR 방식)는 Next.js가 그 대기 시간을 알 수 없으므로 `loading.tsx`가 나타나지 않는다. "서버에서 만드는 동안에만 보인다"로 이해하면 맞다.

### 미들웨어 — Next.js의 필터

스프링 필터처럼, 특정 경로로 가는 요청마다 **먼저 실행되는** 코드를 둘 수 있다.

```ts
// middleware.ts (app 폴더 밖, 프로젝트 루트)
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function middleware(request: NextRequest) {
  console.log("미들웨어 실행:", request.nextUrl.pathname);
  return NextResponse.next();                    // 원래 가려던 곳으로 진행
}

export const config = {
  matcher: ["/admin/:path*"],                    // /admin 과 그 아래 경로에서만 실행
};
```

- `matcher`에 적은 경로로 갈 때만 실행된다. 여러 개를 적을 수 있고, 포함되지 않은 경로에서는 실행되지 않는다. 스프링 시큐리티의 `requestMatchers`와 비슷하다.
- 실제로는 로그를 찍는 대신, 요청에서 **토큰을 꺼내** 인증이 안 됐으면 로그인 페이지로 보내고, 인증됐으면 통과시킨다.

> **추가 설명 — Next.js 16에서는 `proxy.ts`**: Next.js 16부터 `middleware.ts`는 **`proxy.ts`**로 이름이 바뀌었고, 함수 이름도 `middleware`에서 `proxy`로 바뀌었다. 기존 이름도 당분간 동작하지만 사용 중단(deprecated) 경고가 나온다. 수업 프로젝트(ncafe)가 Next.js 16을 쓰므로 새로 만든다면 `proxy.ts`로 만드는 것이 맞다. `matcher` 설정 방법은 같다.

## 11. Auth.js(NextAuth) — 토큰 발급과 검증을 맡기기

토큰을 직접 만들고 검증하려면 할 일이 많다. Next.js에서 가장 많이 쓰는 인증 모듈이 **Auth.js**(예전 이름 **NextAuth.js**)다.

- 설치는 패키지 한 줄이다.
- 인증 처리 파일(`auth.ts`)을 만들고, 로그인·로그아웃 요청을 받을 API 경로(`app/api/auth/[...nextauth]/route.ts`)에 연결하면 로그인, 토큰 발급, 쿠키 관리, 토큰 검증을 대신 해 준다.
- **Providers**(제공자)에 어떤 방식으로 로그인할지를 적는다. 아이디/비밀번호(Credentials), 구글, 깃허브, 카카오 등 다양한 제공자를 지원한다.

```ts
// auth.ts — 구조만 보는 예
import NextAuth from "next-auth";
import Credentials from "next-auth/providers/credentials";

export const { handlers, auth, signIn, signOut } = NextAuth({
  providers: [
    Credentials({ /* 아이디/비밀번호를 받아 사용자를 확인하는 코드 */ }),
  ],
  session: { strategy: "jwt" },          // 세션 대신 JWT를 HttpOnly 쿠키에 담는다
});
```

```ts
// app/api/auth/[...nextauth]/route.ts
import { handlers } from "@/auth";
export const { GET, POST } = handlers;   // /api/auth/* 요청을 Auth.js가 처리
```

> **추가 설명 — 버전 선택**: 그냥 최신으로 설치하면 `next-auth@5.0.0-beta.x`(Auth.js v5)가 들어간다. v5는 오랫동안 **베타**로 남아 있지만 Next.js App Router에 맞춰 만들어졌고, 위 코드(`auth.ts`에서 `handlers`를 내보내는 방식)도 v5 방식이다. 베타를 피하려고 정식 버전인 v4(`next-auth@4`)로 낮추면 설정 방법이 다르다(`authOptions`를 만들어 `NextAuth(authOptions)`를 라우트에서 직접 내보냄). 또 v4는 최신 Next.js(16)와 호환이 되는지 반드시 확인해야 한다. 어느 버전을 쓰든 공식 문서도 **그 버전의 것**을 봐야 한다.

## 정리

| 단계 | 문제 | 해결 |
|---|---|---|
| 아이디/비밀번호 + 세션 | — | 서버가 세션에 인증 상태 저장, 쿠키로 세션 ID 전달 (Stateful) |
| SAML 2.0 | 계열사 서버마다 로그인을 따로 해야 함 | 회사 안의 IdP에 인증을 위임, XML로 결과 전달 → **폐쇄형 SSO** |
| OAuth 2.0 / OIDC | 작은 사이트, 회사를 넘는 SSO 필요 | 구글·네이버 등이 인증 서버를 공개 → **개방형 SSO**, 토큰 기반 |
| 프론트/백 분리 | 서버가 둘 이상이라 세션 공유가 어려움 | 클라이언트가 **토큰**(JWT)을 들고 다님 → **Stateless** |
| 백엔드 노출 | CSR이 API를 직접 부르려면 포트를 열어야 함 | 모든 요청을 Next.js로 모음 → **BFF**, 백엔드는 숨김 |

- JWT = 헤더(알고리즘) . 페이로드(클레임) . 서명. **인코딩일 뿐 암호화가 아니므로** 민감한 정보는 넣지 않는다.
- JWT를 믿는 근거는 **비밀키로 만든 서명**(변조 확인)과 **발급자·대상·만료 시간**(클레임 확인)이다.
- 토큰은 기본적으로 쿠키, 쿠키가 가지 않는 서버에는 `Authorization: Bearer <토큰>` 헤더로 보낸다. 브라우저에서는 localStorage보다 HttpOnly 쿠키가 안전하다.
- 인증 흐름(필터 → AuthenticationManager → SecurityContextHolder)은 세션이든 JWT든 같고, JWT 방식은 세션 대신 **매 요청마다 토큰을 검증**해서 인증 정보를 채운다.
- 비밀번호는 `PasswordEncoder`(BCrypt)로 **단방향 해시**해서 저장하고, 로그인할 때 `matches()`로 비교한다.
