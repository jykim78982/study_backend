# 리다이렉트와 PRG 패턴 오답노트

### 1. POST/Redirect/Get(PRG) 패턴의 목적

**문제**: POST/Redirect/Get(PRG) 패턴의 주된 목적은 무엇인가?

1. 클라이언트가 동일한 POST 요청을 새로고침으로 반복 전송하는 문제를 줄이기 위함이다.
2. 쿠키를 안전하게 저장하기 위함이다.
3. 세션 데이터를 클라이언트로 전송하기 위함이다.
4. 서버에서 HTML을 직접 렌더링하기 위함이다.

**정답: 1번** (내가 고른 답: 2번)

**PRG 패턴이 등장한 배경 — 새로고침 중복 제출**

사용자가 폼을 채우고 제출(POST)했을 때, 서버가 처리를 마치고 **곧바로 HTML 화면을 응답**하면 문제가 생긴다. 결과 화면에서 사용자가 새로고침(F5)을 누르면, 브라우저는 **가장 마지막에 보낸 요청인 POST를 그대로 다시 보낸다.** 그러면 같은 주문이 두 번 결제되거나 같은 글이 두 번 등록된다.

**PRG 패턴의 해결 방법**

```
1. POST      사용자가 데이터를 제출한다
2. Redirect  서버는 처리를 마친 뒤 "결과 페이지로 가라"고 응답한다 (302 + Location 헤더)
3. GET       브라우저가 그 주소로 자동으로 GET 요청을 보내 결과 페이지를 받는다
```

이렇게 하면 브라우저의 **마지막 요청이 POST가 아니라 GET**이 된다. 새로고침을 여러 번 눌러도 결과 페이지를 다시 조회(GET)할 뿐, 같은 POST가 반복 전송되지 않는다.

```java
@PostMapping("/login")
public String login(String username, String password) {
    ...
    return "redirect:/";   // 페이지를 바로 주지 않고 GET으로 다시 오게 한다
}
```

**2번이 오답인 이유**: 쿠키를 안전하게 저장하는 것은 `HttpOnly`, `Secure`, `SameSite` 같은 **쿠키 속성**과 HTTPS가 맡는 일이다. 요청 방식의 흐름(POST → GET)을 조절하는 PRG 패턴과는 관계가 없다. 같은 시기에 로그인·리다이렉트·쿠키를 함께 배워서 섞이기 쉽지만, 리다이렉트는 **요청 흐름**의 문제이고 쿠키는 **클라이언트 식별·상태 저장**의 문제다.

**3번이 오답인 이유**: 세션 데이터는 **서버에** 보관되며 클라이언트로 전송되지 않는다. 클라이언트에는 세션을 찾기 위한 **세션 ID만** 쿠키(`JSESSIONID`)로 전달된다.

**4번이 오답인 이유**: 서버에서 HTML을 렌더링하는 것은 SSR이나 템플릿 엔진(타임리프 등)의 역할이다. 오히려 PRG는 POST 응답으로 HTML을 **바로 렌더링하지 않고** 리다이렉트로 돌려보내는 패턴이다.

| 보기 | 실제로 담당하는 것 |
|---|---|
| 1. 새로고침 중복 POST 방지 | **PRG 패턴** |
| 2. 쿠키 안전하게 저장 | 쿠키 속성(`HttpOnly`, `Secure`, `SameSite`), HTTPS |
| 3. 세션 데이터 전송 | (하지 않는다) 세션 데이터는 서버에, 세션 ID만 쿠키로 |
| 4. HTML 직접 렌더링 | 템플릿 엔진(SSR) |

**한 줄 요약**: PRG는 POST를 처리한 뒤 `redirect:`로 GET 요청을 거치게 해서, 새로고침해도 POST가 다시 전송되지 않게 하는 패턴이다. **"POST는 페이지를 주지 않는다."**
