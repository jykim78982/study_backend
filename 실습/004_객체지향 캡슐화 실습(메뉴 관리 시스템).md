# 객체지향 캡슐화 실습(메뉴 관리 시스템)

`ex6_oop` 폴더의 [`App.java`](../../java_basic/ex6_oop/App.java)와 [`entity/Menu.java`](../../java_basic/ex6_oop/entity/Menu.java)를 만들면서, 이전에 정리한 전역변수·static·캡슐화 개념을 실제 코드로 부딪혀 봤다.

## 1. 지금 구조 — 아직 캡슐화가 덜 된 상태

```java
package java_basic.ex6_oop.entity;

public class Menu {
    int id;
    String name;
    int price;
}
```

```java
package java_basic.ex6_oop;

public class App {
    public static void main(String[] args) {
        Menu[] menus = new Menu[3];
        ...
    }

    public static int inputMenu(Menu[] menus, int count) {
        ...
        Menu menu = new Menu();
        menu.id = ...;
        menu.name = ...;
        menu.price = ...;
        menus[count] = menu;
        ...
    }
}
```

- `Menu`는 `id`, `name`, `price`라는 **데이터**만 가지고 있고, 그 데이터를 다루는 **동작(함수)은 여전히 `App` 쪽에 있다** — 즉 "데이터를 관리하면서 서비스를 제공하는 역할자"가 아직 되지 못한 상태다. 이전에 짚은 "그냥 묶기만 하면 캡슐화인가?"라는 질문이 여기서 실감난다 — 지금은 데이터를 담는 상자(`Menu`)와 그 상자를 조작하는 코드(`App`)가 분리되어 있을 뿐, `Menu`가 자기 역할(메뉴 하나를 관리하는 일)을 스스로 서비스로 제공하고 있지는 않다
- `id`, `name`, `price`에 접근 제한자가 없어서 **default(패키지 접근)**로 열려 있다 — `App`이 다른 패키지(`java_basic.ex6_oop`)에 있는데도 `Menu`(`java_basic.ex6_oop.entity`)의 필드를 직접 건드릴 수 있으려면 `public`이 필요했다. 이건 캡슐화가 지향하는 "데이터는 역할자 안에 숨기고, 서비스로만 다루게 한다"는 방향과는 반대 방향이다 — 지금은 외부에서 필드를 마음대로 열고 고칠 수 있는 상태
- `main`, `inputMenu`, `printMenu` 모두 **`static` 메소드(전역함수)**다 — `App` 객체를 `new`로 만들지 않고도 `App.inputMenu(...)`처럼 바로 호출할 수 있는 구조다. 아직 "객체를 통해서만 쓸 수 있는 서비스"가 아니라, 사실상 전역함수에 더 가깝다

## 2. 더 캡슐화된 방향으로 가려면

지금 구조를 이전에 다룬 역할자 계층(UI ↔ 업무 ↔ 콜렉션 ↔ 엔티티)에 맞춰보면 이렇게 정리할 수 있다.

- `Menu`가 **엔티티** 역할자: 메뉴 하나의 데이터를 갖는다
- 메뉴 여러 개를 관리하는 배열 + `inputMenu`/`printMenu` 같은 로직을 **콜렉션** 역할자로 따로 묶어낼 수 있다 (예: `MenuList`라는 클래스를 만들어서, 그 안에 `Menu[]`와 입력·출력 메소드를 같이 두는 것)
- `App`의 `main`은 **UI(메뉴 관리 시스템의 진입점)** 역할만 남기고, 실제 데이터 조작은 콜렉션 역할자에게 맡기는 것이 UI↔업무↔콜렉션↔엔티티 계층에 더 가까운 형태다

즉 지금 `App.java`는 "함수로 기능을 나눴다"는 점에서는 이전에 다룬 구조화는 잘 되어 있지만, "데이터를 가진 역할자에게 그 데이터를 다루는 서비스까지 맡긴다"는 **캡슐화**의 기준으로 보면 아직 한 단계 더 나아갈 여지가 있다.
