# SQL SELECT 구절 연습

`menus` 테이블 하나로 SQL 논리적 실행 순서(Logical Query Processing Order)를 단계별로 확인하는 실습. 각 단계의 실제 쿼리와 결과는 [[008_SQL SELECT 구절 실습 쿼리 모음]]에 정리되어 있고, 이 노트는 각 단계의 **개념**만 정리한다.

## 0. 논리적 실행 순서 흐름

```
1. FROM / WHERE   — 행 단위 필터링
2. GROUP BY / 집계 함수 — 그룹화 및 연산
3. HAVING         — 그룹 집계 결과 필터링
4. SELECT         — 프로젝션, 별칭, 매핑
5. ORDER BY / 페이징 — 최종 정렬과 출력 개수 제어
```

이 순서는 `040` 노트에서 정리한 `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`와 동일한 흐름이다. 이번 실습은 이 다섯 단계를 하나씩 손으로 눌러보면서, 왜 이 순서가 SQL 문법 규칙을 만드는지 확인하는 데 목적이 있다.

## 1부. `WHERE` — 행 단위 필터링

논리적 실행의 첫 관문. 테이블 전체 행 중 조건식이 `TRUE`인 행만 다음 단계로 넘긴다.

1. **단일 비교 연산자**(`=`, `!=`, `<`, `>`, `<=`, `>=`) — 가장 기본적인 조건 하나로 거르기.
2. **논리 연산자 결합**(`AND`, `OR`, `NOT`) — `AND`는 교집합, `OR`는 합집합. 우선순위는 `AND`가 `OR`보다 높으므로, 의도한 그룹으로 묶으려면 괄호를 써야 한다.
3. **범위·이산 집합 검색**(`BETWEEN`, `IN`) — 반복되는 `OR`나 연속 범위 비교를 축약한 문법. `BETWEEN`은 상한·하한을 모두 포함하는 폐구간이다.
4. **3치 논리 결측치 검증**(`IS NULL`, `IS NOT NULL`) — `NULL`은 "값이 없는 상태(Unknown)"라서 `= NULL`로는 절대 비교할 수 없다. 반드시 `IS NULL`/`IS NOT NULL`을 써야 한다.
5. **와일드카드 패턴 매칭**(`LIKE`, `ILIKE`) — `%`는 0개 이상의 임의 문자, `_`는 정확히 한 글자. `ILIKE`는 PostgreSQL 전용 대소문자 무시 비교다.
6. **날짜 경계 조건 필터링** — 날짜 컬럼을 가공하지 않고 `DATE 'YYYY-MM-DD'` 리터럴로 경계값을 비교해야, 옵티마이저가 인덱스를 탈 수 있는 형태(SARGable Query)가 된다.

## 2부. `GROUP BY` / 집계 함수 — 그룹화 및 연산

`WHERE`를 통과한 개별 행들을 공통 기준 컬럼으로 묶어 요약 통계를 만드는 단계.

7. **단순 집계**(`COUNT`, `SUM`, `AVG`) — 개별 행 여러 개가 그룹당 값 하나로 압축된다.
8. **극값 계산**(`MIN`, `MAX`) — 그룹 내부의 최솟값·최댓값으로 분포 폭을 파악한다.
9. **`COUNT(*)` vs `COUNT(컬럼명)`** — `COUNT(*)`는 `NULL` 여부와 무관하게 행 전체 수를 센다. `COUNT(컬럼명)`은 그 컬럼 값이 `NULL`인 행을 집계에서 제외한다. 그래서 전체 행 수를 세려면 `NULL`이 들어갈 수 없는 식별자(`id`) 컬럼을 대상으로 세는 게 안전하다.
10. **조건부 집계**(`FILTER (WHERE ...)`) — 그룹 내부에서 특정 조건을 만족하는 행만 따로 집계하고 싶을 때 쓰는 PostgreSQL 확장 문법. 자세한 내용은 5부 뒤 심화 절 참고.

## 3부. `HAVING` — 그룹 집계 결과 필터링

`WHERE`는 `GROUP BY`보다 먼저 실행되므로 집계 함수를 조건으로 쓸 수 없다. 그룹화된 결과 자체를 다시 거르려면 `HAVING`이 필요하다.

11. **집계 기준 단순 조건**(`HAVING COUNT(*) >= n`) — 그룹별 건수를 기준으로 그룹 자체를 필터링한다.
12. **통계값 연산 기반 필터링**(`HAVING AVG(...)`, `HAVING MIN/MAX(...)`) — 평균·최댓값·최솟값 등 통계 연산 결과를 조건으로 그룹을 거른다.
13. **`WHERE`(사전 필터)와 `HAVING`(사후 필터)의 결합** — `WHERE`로 처리 대상을 먼저 줄여 I/O를 줄이고, 남은 데이터로 그룹핑한 뒤 `HAVING`으로 그룹 조건을 검증하는 흐름. `040` 노트 9절에서 다룬 "`WHERE`가 실행되는 시점엔 아직 집계도 별칭도 없다"는 문제가 바로 이 결합에서 드러난다.

## 4부. `SELECT` — 프로젝션과 매핑

`WHERE`·`GROUP BY`·`HAVING`을 모두 통과한 최종 데이터셋을, 클라이언트에 전달할 형태로 가공하는 단계. `040` 노트에서 "매핑"이라고 부른 작업이 바로 이것이다.

14. **산술 연산 매핑** — `price * 0.1`처럼 컬럼값을 참조해 세액·합계 같은 파생 값을 계산해 새 컬럼으로 추가한다.
15. **문자열 결합·변환**(`||`, `UPPER`, `LENGTH`) — 텍스트를 UI 레이블에 맞게 가공한다.
16. **결측치 대체 매핑**(`COALESCE`, `NULLIF`) — `SELECT` 단계에서 `NULL`을 기본값으로 치환하거나, 특정 값을 `NULL`로 바꿔 출력 인터페이스를 보정한다.
17. **조건 분기 매핑**(`CASE WHEN ... THEN`) — 컬럼 값을 기준으로 코드값을 라벨로 바꾸거나 구간별 등급을 매기는, 사실상 SQL판 `if-else`.

## 5부. `ORDER BY` / 페이징 — 최종 정렬과 출력 제어

`SELECT`로 프로젝션된 결과셋을 우선순위에 따라 정렬하고, 필요한 구간만 잘라내는 마지막 단계.

18. **복합 정렬**(`ORDER BY ... ASC/DESC, ...`) — 1차 기준이 같을 때 2차 정렬 기준이 동작한다.
19. **`SELECT` 별칭을 `ORDER BY`에서 참조** — `ORDER BY`는 논리적으로 `SELECT`보다 나중에 실행되므로, `WHERE`·`GROUP BY`에서는 못 쓰던 `SELECT`의 별칭을 여기서는 그대로 쓸 수 있다. `040` 노트 9절에서 "별칭은 `SELECT` 단계에서 정의된다"고 한 것과 정확히 대칭되는 근거다.
20. **`NULL` 정렬 위치 제어**(`NULLS FIRST`, `NULLS LAST`) — DB 기본 동작에 의존하지 않고 결측치의 출력 위치를 직접 지정한다.
21. **페이징**(`LIMIT`, `OFFSET`) — 정렬이 끝난 결과 집합에서 특정 구간만 잘라 응답한다. `OFFSET`으로 건너뛰고 `LIMIT`으로 개수를 제한한다.

## 6. 심화 — `FILTER` 절

`GROUP BY`로 묶은 그룹 안에서, 특정 조건을 만족하는 행만 따로 집계해야 할 때 쓰는 PostgreSQL/SQL:2003 표준 조건부 집계 문법.

- **기존 방식(모든 DBMS 호환)**: `COUNT(CASE WHEN 조건 THEN 1 END)`처럼, 조건에 안 맞는 행은 `CASE`로 `NULL`을 유도해 집계에서 자연히 빠지게 만드는 우회 방식.
- **PostgreSQL `FILTER` 방식**: 집계 함수 뒤에 `FILTER (WHERE 조건)`을 바로 붙인다. `CASE WHEN ... THEN 1 ELSE NULL END`를 안 써도 되니 훨씬 직관적이다.
- `FILTER`는 `COUNT`뿐 아니라 `SUM`, `AVG`, `MIN`, `MAX` 등 모든 집계 함수에 붙일 수 있고, 컬럼마다 서로 다른 조건을 걸 수 있다 — 단일 `GROUP BY` 하나로 여러 조건별 통계를 동시에 뽑는 복합 보고서를 만들 수 있다는 뜻이다.
- `HAVING` 절에도 `FILTER`가 붙은 집계식을 그대로 조건으로 쓸 수 있다 — "그룹 전체 집계"가 아니라 "그룹 내부의 조건부 집계 결과"를 기준으로 그룹을 걸러낼 때 유용하다.
- **DBMS 호환성이 필요할 때**는 `FILTER (WHERE 조건)`을 `CASE WHEN 조건 THEN ... END` 형태로 1:1 치환하면 된다(MySQL, Oracle 등은 `FILTER`를 지원하지 않는다).
