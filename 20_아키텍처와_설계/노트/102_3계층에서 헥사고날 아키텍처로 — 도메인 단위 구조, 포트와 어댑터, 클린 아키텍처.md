# 3계층에서 헥사고날 아키텍처로 — 도메인 단위 구조, 포트와 어댑터, 클린 아키텍처

3계층(Controller, Service, Repository)으로 만든 프로젝트가 커지면 어떤 불편이 생기는지 찾고, 그 불편을 해결하려고 나온 아키텍처들(도메인 중심 → 헥사고날 → 어니언 → 클린)을 한 줄기로 이해한다. 마지막에는 `notice`(공지사항) 도메인을 예로 폴더 구조를 잡는다.

> **핵심 한 줄**: 관련 기능을 **도메인 단위로 모으고**, 외부 기술(웹 프레임워크, DB 등)의 변화가 업무 로직으로 전파되지 않도록 **의존 방향을 관리**하는 것이다. 이름이나 유행이 아니라 **어떤 문제가 생기는지** 파악해서 프로젝트에 맞는 구조를 고른다.

---

## 1. 아키텍처 이름이 아니라 "불편한 점"을 먼저 본다

수업에서 보여 준 다섯 가지 이름이 있다.

- Hexagonal Architecture
- Onion Architecture
- Domain-Driven Design(DDD) / Domain Centric Architecture
- Vertical Slice Architecture
- Clean Architecture

이 이름들은 3계층 이후 현재까지 나온 아키텍처의 흐름을 거의 다 담고 있다. 그런데 이름을 외우는 것이 목적이 아니다. 아키텍처는 **우리가 만드는 프로그램에서 느끼는 불편함**이 쌓여서 나온 해결책이다. 그래서 필요한 것은 다음 두 가지다.

1. 불편한 점을 스스로 찾고, 그 해결책이 왜 나왔는지 **미루어 짐작하는 눈**.
2. 해결책이 우리 상황에 맞지 않으면 **버릴 수 있는 판단 기준**.

기준 없이 "헥사고날이 있다더라", "버티컬이 있다더라" 하고 따라가면, 왜 그렇게 해야 하는지 모른 채 용어 논쟁만 하게 된다.

## 2. 3계층은 무엇을 기준으로 나눴나

```
Controller   요청을 받는다
     │
Service      업무를 처리한다
     │
Repository   데이터를 가져온다
```

원래는 컨트롤러 하나에 다 넣어도 된다. 그런데 컨트롤러가 너무 빵빵해져서 **하던 일을 역할별로 나눈 것**이 3계층이다. 기준은 "이 코드가 하는 **역할**이 무엇인가"였다. 나누고 나니 요청 받기, 업무 처리, DB 접근이 깔끔하게 정리되어 안 나눈 것보다 훨씬 좋았다.

폴더로 보면 이런 모양이다.

```
menu/
├─ controller/     ← 컨트롤러가 전부 모여 있다
├─ service/        ← 서비스가 전부 모여 있다
└─ repository/     ← 리포지토리가 전부 모여 있다
```

### 규모가 커지면 생기는 불편

그때는 좋았지만, 코드가 쌓이면 이전에는 보이지 않던 문제가 나온다.

- 한 기능(예: 주문)을 고치려는데, 코드가 **컨트롤러 폴더, 서비스 폴더, 리포지토리 폴더**에 흩어져 있다. 수정할 때 사방팔방을 왔다 갔다 해야 한다.
- 파일이 많아질수록 찾아서 열고, 넣고, 옮기는 일이 점점 느리고 복잡해진다.
- 계층별로 코드가 한 덩어리처럼 커져서 서로 영향을 주고받는다.
- 새 기능(예: 제비뽑기, 협업 온도 추천)을 넣으려면 세 폴더를 모두 건드려야 한다. **새 기능은 새 기능대로 따로 만들 수는 없을까?**

## 3. 1단계 — 도메인 단위로 모으기 (도메인 중심 구조)

해결책은 단순하다. **같이 수정되는 것끼리 모은다.** 역할(계층)이 아니라 **도메인(기능)** 을 기준으로 폴더를 나눈다.

```
menu/            ← 메뉴 관리 기능은 이 안에만 있다
   (컨트롤러, 서비스, 리포지토리 …)
order/           ← 주문 기능은 이 안에만 있다
notice/          ← 공지사항 기능은 이 안에만 있다
```

- 메뉴를 고칠 때는 `menu` 폴더만, 주문을 고칠 때는 `order` 폴더만 열면 된다.
- 새 기능은 폴더 하나를 새로 만드는 것으로 **점증적으로 늘어난다.**
- 폴더 이름만 봐도 "어떤 기능이 만들어졌는지" 알 수 있다.

이것은 객체지향의 **캡슐화**와 같은 생각이다. 수정하는 내용이 한곳에 모여 있다는 것이다. 도메인 단위의 캡슐이 만들어진 셈이다. 이 흐름이 도메인 기반 설계(DDD, 도메인 센트릭)로 불린다.

> 원문 바로잡기 — 수업에서는 "도메인 폴더로 묶는 것"을 도메인 드리븐 디자인이라고 소개했지만, DDD는 폴더 구조의 이름이 아니라 **도메인을 모델링하는 방법론**(엔티티, 애그리거트, 바운디드 컨텍스트 등)이다. 여기서 다루는 것은 그중 "도메인 단위로 묶는다"는 한 측면이다.

> **추가 설명 — 이전 리뷰 피드백과의 연결**: 깃허브 리뷰에서 "그렇게 폴더를 나누면 안 된다"는 말을 들었더라도, 그것은 3계층을 기준으로 했을 때의 이야기다. 3계층에서 도메인 기반으로 옮기려면 도메인 폴더 안에 계층을 두는 방식이 맞다.

## 4. 2단계 — 도메인의 중심에는 엔티티를 두고, 바깥은 어댑터로 차단한다

도메인 폴더로 묶기만 하면 아직 설익었다. `menu/` 폴더 안의 코드는 각각 어떤 역할이고, 무엇이 **중심**일까?

### 4-1. 중심은 엔티티, 그 바깥은 업무 로직

`menu/`는 그 자체로 **메뉴를 관리하는 작은 어플리케이션**이다. 이 어플리케이션의 비즈니스 로직은 엔티티를 가지고 하는 일이므로 중심축은 `Menu` 엔티티다.

```
              ┌─ 어플리케이션 로직 ───────────────┐
   등록 ─────▶ │          ┌──────────────┐         │ ◀───── 조회
              │          │  Menu (주인공)  │         │
              │          │  이름 name      │         │
              │          │  가격 price     │         │
              │          └──────────────┘         │
              └──────────────────────────────┘
```

엔티티(주인공)를 가운데 두고, 그것을 이용하는 로직(등록하기, 조회하기 등)이 바깥을 감싼다.

### 4-2. 바깥은 자주 바뀐다

이 어플리케이션을 쓰려면 두 가지가 필요하다.

1. **들어오는 쪽**: 누군가 "등록해 줘", "조회해 줘"라고 호출해야 한다. 서블릿이든 스프링이든 화면(UI)이든, 사용자의 요청을 전달해 주는 껍데기가 있어야 한다.
2. **나가는 쪽**: 등록하고 조회하려면 외부의 **저장소(DB 등)** 를 이용해야 한다.

그런데 이 바깥 요소들은 **자주 바뀐다.** 윈도우 프로그램이었다가 웹이 되고, 웹 기술이 서블릿에서 스프링으로 바뀌고, DB가 오라클에서 SQL Server로 바뀔 수 있다. 외부 API나 장치가 바뀌었다고 해서 메뉴라는 순수한 업무 규칙이 같이 바뀌면 안 된다.

### 4-3. 수정이 전파되지 않도록 어댑터로 막는다

그래서 바깥과 안쪽 사이에 **차단 계층**을 하나 둔다. 이것이 **어댑터(Adapter)** 다.

```
  웹 ──⇄[ 어댑터 ]──▶  [ 등록 ┃ Menu ┃ 조회 ]  ◀──[ 어댑터 ]⇄── DB
 (바깥)                  (안쪽: 외부를 모른다)                  (바깥)
```

- 웹이 윈도우로 바뀌면 **웹 쪽 어댑터만** 고친다.
- DB가 오라클에서 SQL Server로 바뀌면 **DB 쪽 어댑터만** 고친다.
- 수정은 **바깥에서만** 일어나고, 안쪽의 업무 로직으로는 퍼지지 않는다.

계층을 하나 더 만드는 것은 귀찮다. 하지만 바깥이 바뀔 때마다 업무 로직을 전부 고치는 쪽이 훨씬 귀찮다.

### 4-4. 정리

| 원칙 | 내용 |
|---|---|
| 기준은 역할 → 도메인 | 계층(역할)이 아니라 도메인 단위로 폴더를 나눈다 |
| 중심에는 엔티티 | 엔티티가 주인공이고, 업무 로직이 그것을 감싼다 |
| 바깥은 어댑터로 차단 | 웹, DB 같은 외부는 어댑터가 막아서 안쪽에 영향을 주지 않는다 |

## 5. 의존성 규칙과 DI — 안쪽은 바깥을 모른다

어댑터로 막으려면 참조 방향을 지켜야 한다.

- **바깥 → 안쪽 참조는 가능하다.**
- **안쪽 → 바깥 참조는 불가능하다.**

그런데 안쪽의 업무 로직도 DB에서 데이터를 가져와야 하지 않나? 이때 **인터페이스와 역제어(DI)** 를 쓴다.

```
 안쪽(application)                              바깥(adapter)
 ┌──────────────────────┐                  ┌─────────────────────────┐
 │ NoticeService        │                  │ JpaNoticeRepository      │
 │   └ NoticeRepository │ ◀──── 구현 ────── │  (JPA로 실제 구현)        │
 │      (인터페이스)       │                  └─────────────────────────┘
 └──────────────────────┘
       ▲
       └─ 스프링이 구현체를 주입(DI)한다. 안쪽은 구현체를 만들지도, 알지도 못한다.
```

1. 안쪽에는 **인터페이스**만 둔다. "이런 일을 해 줘"라는 약속이다.
2. 실제 **구현체는 바깥(어댑터)** 에 둔다. DB가 바뀌면 구현체만 고친다.
3. 안쪽은 구현체를 `new`로 만들 필요 없이 **주입받아서** 쓴다. 그래서 스프링의 DI가 중요하다.

참조 방향은 이렇게 요약된다. 겉으로 보면 안쪽이 바깥 기능을 쓰는 것 같지만, 코드상으로는 **바깥의 구현체가 안쪽의 인터페이스에 의존한다.**

## 6. 헥사고날, 어니언, 클린은 모두 같은 생각에서 나왔다

### 6-1. 나온 순서와 특징 (수업 설명 기준)

| 이름 | 핵심 |
|---|---|
| 도메인 드리븐 / 도메인 센트릭 | 가장 먼저 나왔다. 도메인 단위로 모은다 |
| 헥사고날 | 안쪽 업무 로직을 가운데 두고, 들어오는 곳과 나가는 곳을 **포트**라는 폴더(in / out)로 나눈다. 그림이 육각형이라 이 이름이 붙었다 |
| 어니언 | 헥사고날과 같은 생각을 양파처럼 둥근 층으로 표현했다 |
| 버티컬 슬라이스 | 기능 단위로 수직으로 자른다. 같은 얘기에 이름만 하나 더 얹은 것으로 본다 |
| 클린 | 가장 마지막에 나왔고, 앞의 생각들을 **모두 포괄**한다 |

### 6-2. 육각형은 의미가 없다

헥사고날은 그림을 육각형으로 그렸을 뿐이다. 이 때문에 "포트는 6개가 아니다" 같은 논쟁이 벌어지지만 **육각형에는 의미가 없다.** 그래서 이후 둥근 형태의 어니언으로 표현이 바뀐다.

### 6-3. 이름보다 결과가 중요하다

이들은 서로 포함 관계를 주장하지 않고 각자의 생각이라고 하지만, 결국 거의 같은 구조를 말한다. 따라서 "어니언으로 했나, 헥사고날로 했나, 버티컬로 했나"는 중요하지 않다. 중요한 것은 **같은 구조를 이해하고 쓰는 것**이다.

> 도메인 단위로 모으고 + 어댑터 계층을 두고 + 외부에 있는 것을 주입받아 쓴다.

어떻게 만들고 쓸 것인지는 각자 판단할 문제이고, 누가 "왜 그렇게 했느냐"고 물으면 **자기 기준을 말할 수 있어야** 한다.

> 원문 바로잡기 — 수업에서는 시기를 "2000년대 중반", "2019~20년"처럼 넓게 말했다. 일반적으로 알려진 시기는 DDD 2003년경, 헥사고날 2005년경, 어니언 2008년경, 클린 아키텍처 2012년경(책은 2017년)이다. "클린이 가장 나중에 나왔고 앞의 것을 아우른다"는 순서 자체는 같다.

> 원문 바로잡기 — 버티컬 슬라이스는 "기능 단위로 수직 분할하고, 각 슬라이스가 자기 계층을 따로 갖는다"는 점을 내세우는 별도 구조이긴 하다. 도메인 단위로 묶는다는 점에서 위와 닮았다는 정도로 이해하면 충분하다.

## 7. 클린 아키텍처 살펴보기

### 7-1. 목표 다섯 가지

| 독립 대상 | 뜻 |
|---|---|
| UI | 윈도우, 콘솔, 웹 어느 것이든 업무 로직은 그대로 |
| 데이터베이스 | DB가 달라져도 업무 로직은 그대로 |
| 외부 에이전시·라이브러리·드라이버 | 외부가 달라져도 업무 로직은 그대로 |
| 프레임워크 | 특정 프레임워크에 묶이지 않는다 |
| 테스트 | 외부 없이도 업무 로직을 테스트할 수 있다 |

### 7-2. 대표 그림 — 네 개의 원

```
┌─ Frameworks & Drivers (Web, UI, DB, Devices, External Interfaces) ─────────┐
│  ┌─ Interface Adapters (Controllers, Gateways, Presenters) ──────────────┐ │
│  │  ┌─ Use Cases (Application Business Rules) ──────────────────────┐    │ │
│  │  │   ┌─ Entities (Enterprise Business Rules) ─┐                    │    │ │
│  │  │   │   중심: 가장 순수한 업무 규칙             │                    │    │ │
│  │  │   └────────────────────────────────────┘                    │    │ │
│  │  └───────────────────────────────────────────────────────────┘    │ │
│  └───────────────────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────────┘
        의존 방향: 바깥 원 ───▶ 안쪽 원 (반대는 안 된다)
```

| 원 | 이름 | 하는 일 |
|---|---|---|
| 가장 안쪽 | Entities | 기업 전체에서 통하는 순수 업무 규칙 |
| 두 번째 | Use Cases | 어플리케이션 단위의 업무 규칙 |
| 세 번째 | Interface Adapters | 컨트롤러, 게이트웨이, 프레젠터. 안과 밖의 데이터를 변환하고 요청을 중계 |
| 가장 바깥 | Frameworks & Drivers | 웹, UI, DB, 장치, 외부 인터페이스 |

### 7-3. 의존성 규칙 (Dependency Rule)

> 내부 계층은 외부 계층에 의존할 수 없고, 외부 계층이 내부 계층에 의존해야 한다.

- UI는 Use Case를 호출하지만, Use Case는 UI를 몰라야 한다.
- Use Case는 Repository를 호출하지만, Repository의 구현 방식(Supabase, MongoDB 등)은 몰라야 한다.

### 7-4. 관심사의 분리 — 계층별 역할

| 계층 | 역할 |
|---|---|
| Domain | 순수 비즈니스 규칙을 처리한다. 외부 기술이나 구현에 영향을 받지 않는다 |
| Application (Use Case) | 비즈니스 로직과 데이터를 UI가 필요로 하는 방식으로 처리한다 |
| Infrastructure | 데이터베이스, 외부 API 같은 구체적인 구현을 담당한다 |
| Interface Adapters | 외부와 내부를 연결하는 어댑터 역할로, 데이터를 변환하거나 요청을 중계한다 |

수업에서는 이 네 계층을 우리 구조에 이렇게 대응시켰다.

| 클린 아키텍처의 계층 | 우리 프로젝트에서 |
|---|---|
| Domain | `domain` 폴더 — 엔티티(예: `Notice.java`) |
| Application | `application` 폴더 — 서비스 |
| Interface Adapters | `adapter` 폴더 — 컨트롤러, 리포지토리 구현체 |
| Infrastructure | **만들지 않는다** (아래 8절 참고) |

> 원문 바로잡기 — 슬라이드의 "Domain / Application / Infrastructure / Interface Adapters" 설명은 클린 아키텍처 원 그림의 네 층(Entities / Use Cases / Interface Adapters / Frameworks & Drivers)과 이름이 다르다. 원 그림에서는 Infrastructure가 가장 바깥의 Frameworks & Drivers에 해당한다고 보면 된다.

### 7-5. 오른쪽 아래의 작은 도식 — 제어의 흐름

```
Controller ──▶ [Use Case Input Port] ◀── Use Case Interactor ──▶ [Use Case Output Port] ◀── Presenter
                 (인터페이스)               (업무 로직 구현)          (인터페이스)
         └──────────── Flow of control(제어의 흐름): Controller → Interactor → Presenter ────────────┘
```

- 컨트롤러가 호출하는 것은 구현이 아니라 **Input Port(인터페이스)** 다.
- 업무 로직은 결과를 **Output Port(인터페이스)** 로 내보내고, 그 구현이 Presenter다.
- 제어는 바깥에서 안으로 갔다가 다시 바깥으로 나오지만, **소스 코드의 의존 방향은 항상 안쪽을 향한다.** 이를 가능하게 하는 것이 인터페이스와 DI다.

## 8. 우리는 헥사고날로 간다 — 인프라 계층을 뺀 구조

클린 아키텍처는 Infrastructure 계층까지 포함한다. 그런데 이 계층이 애매하다.

- Infrastructure는 "외부 라이브러리 같은 구체적인 구현"인데, **내가 직접 만드는 것이 거기에 있느냐**가 문제다.
- 우리가 외부 API나 라이브러리를 가져다 쓰기만 하고 직접 만드는 외부 코드가 없다면, Infrastructure와 어댑터가 하는 일이 겹쳐서 구분이 모호해진다.
- 그러면 외부와 닿는 부분은 **어댑터만** 두면 된다. 이 구조가 **헥사고날**이다.

| | 클린 아키텍처 | 헥사고날 |
|---|---|---|
| 포트 | 있다 | 있다 |
| 어댑터 | 있다 | 있다 |
| Infrastructure 계층 | **있다** | 없다 |

포트와 어댑터는 클린 아키텍처에도 있다. 포트를 썼다고 헥사고날, 안 썼다고 클린인 것이 아니다. **인프라를 직접 만드는 프로젝트라면 클린이, 그렇지 않다면 헥사고날이 더 단순하다.** 우리는 인프라를 직접 만들지 않으므로 헥사고날로 다룬다.

수업에서는 이 구조를 국내 대기업과 해외 기업들이 널리 쓴다고 소개했다. (실제 도입 현황은 따로 확인한 것이 아니라 강사의 설명이다.)

## 9. 폴더 구조 — notice(공지사항) 도메인 예시

관리자가 공지사항을 관리하는 기능을 새로 만든다고 하자.

### 9-1. 도메인 폴더는 어디에 만드나

```
backend/
└─ admin/              ← 역할자(관리자)
   ├─ event/           ← 관리자가 관리하는 다른 도메인
   └─ notice/          ← 공지사항 관리 도메인 (폴더 이름은 소문자)
```

- 관리자가 관리하는 기능은 `admin` 아래에 둔다.
- 일반 사용자가 공지를 **조회**하는 기능은 역할자가 다르므로 `backend` 바로 아래의 `notice` 폴더에 따로 만든다.
- 이제 컨트롤러 폴더, 엔티티 폴더, 서비스 폴더를 각각 찾아가서 추가할 필요가 없다. **내 도메인 폴더 하나만 만들고 모든 것을 그 안에 둔다.**
- 엔티티를 모아 두던 `entity` 폴더도 만들지 않는다. 그 자리는 **`domain`** 폴더가 대신한다.

### 9-2. 구조 (공지 목록 조회 예)

```
com/ncafe/backend/
└─ admin/
   └─ notice/
      ├─ domain/
      │   └─ Notice.java                      ← 엔티티 (주인공)
      ├─ application/
      │   ├─ NoticeService.java               ← 서비스 (업무 로직)
      │   ├─ dto/
      │   │   └─ NoticeListResponse.java      ← 서비스가 반환하는 결과
      │   └─ port/
      │       ├─ in/                          ← (선택) 서비스를 호출하는 입구 인터페이스
      │       └─ out/
      │           └─ NoticeRepository.java    ← 바깥에 맡길 일의 약속(인터페이스)
      └─ adapter/
          ├─ in/web/
          │   ├─ NoticeController.java        ← 요청을 받는 컨트롤러
          │   └─ dto/
          │       └─ NoticeListRequest.java   ← 바깥에서 들어오는 요청
          └─ out/persistence/
              └─ JpaNoticeRepository.java     ← port/out의 JPA 구현체
```

### 9-3. 무엇을 어디에 두나

| 대상 | 위치 | 이유 |
|---|---|---|
| 엔티티 `Notice` | `domain/` | 업무의 중심 |
| 서비스 `NoticeService` | `application/` | 업무 로직 |
| 응답 DTO `NoticeListResponse` | `application/dto/` | 서비스가 **만들어 내는 결과물**이다 |
| 요청 DTO `NoticeListRequest` | `adapter/in/web/dto/` | 서비스가 반환하는 것이 아니라 **바깥에서 들어오는** 것이다 |
| 리포지토리 인터페이스 | `application/port/out/` | 안쪽이 쓸 도구는 안쪽에 있어야 한다. 서비스가 바깥에 맡길 일의 약속이다 |
| 리포지토리 구현체 | `adapter/out/persistence/` | 무엇으로 구현했는지(JPA 등)는 바깥만 알면 된다 |
| 컨트롤러 | `adapter/in/web/` | 애초에 바깥에 있는 존재다 |
| 서비스 호출 입구 인터페이스(선택) | `application/port/in/` | 컨트롤러가 인터페이스로 서비스를 쓰게 하고 싶을 때. 서비스는 이를 구현한다 |

- **나가는 포트(`port/out`)** 는 안쪽이 바깥을 쓰기 위한 인터페이스이고, **들어오는 포트(`port/in`)** 는 바깥이 안쪽의 기능을 쓰기 위한 인터페이스다.
- `port/in`은 반드시 만들어야 하는 것은 아니다. 수업에서는 서비스 클래스 자체를 컨트롤러가 쓰는 형태도 보여 주었다.
- 응답 DTO가 안쪽에 있고 요청 DTO가 바깥에 있는 이유는 의존 방향 때문이다. 바깥이 안쪽의 응답 DTO를 쓰는 것은 괜찮지만, **안쪽이 바깥의 요청 DTO를 알면 안 된다.**

**포트와 어댑터 용어 정리**

포트는 안쪽에 두는 **인터페이스**, 어댑터는 바깥에 두는 **구현**이다. 방향(들어오느냐, 나가느냐)에 따라 이름이 나뉜다.

| 용어 | 방향 | 하는 일 | 이 예시에서 |
|---|---|---|---|
| 인바운드 어댑터 | 바깥 → 안쪽 | 외부 요청을 받아 애플리케이션 기능을 호출한다 | `NoticeController`, 요청 DTO (`adapter/in/web`) |
| 인바운드 포트 | 바깥 → 안쪽 | 외부에 **제공하는** 애플리케이션 기능의 인터페이스 (선택) | `application/port/in` |
| 아웃바운드 포트 | 안쪽 → 바깥 | 애플리케이션이 저장소 등 외부 기능을 **이용하기 위한** 인터페이스 | `NoticeRepository` (`application/port/out`) |
| 아웃바운드 어댑터 | 안쪽 → 바깥 | 아웃바운드 포트를 실제 기술로 구현한다 | `JpaNoticeRepository` (`adapter/out/persistence`) |

- **DI**가 실제 구현체(아웃바운드 어댑터)를 애플리케이션에 주입하므로, 업무 로직은 구현 세부사항을 알 필요가 없다.
- 외부 기술이 바뀌면 **해당 어댑터를 주로 수정**하고, 내부 업무 로직으로 변경이 번지지 않게 하는 것이 목표다.

> 원문 바로잡기 — 슬라이드 화면의 파일명에 오타가 있다. `NoticieRepository` / `NotcieRepository`는 `NoticeRepository`, `NoticeListReqeust`는 `NoticeListRequest`가 맞다.

### 9-4. 호출 흐름

```
브라우저
  │ GET /api/admin/notices
  ▼
NoticeController (adapter/in/web)         ← NoticeListRequest로 요청을 받는다
  │
  ▼
NoticeService (application)               ← 업무 로직. NoticeListResponse를 만든다
  │ NoticeRepository(인터페이스)를 호출
  ▼
JpaNoticeRepository (adapter/out/persistence)   ← 스프링이 주입한 구현체. DB 접근
  │
  ▼
Notice (domain)  ←  DB의 한 행
```

## 10. 서비스를 하나로 둘지 쪼갤지는 선택의 문제다

`application`에 서비스를 어떻게 두느냐는 정해진 답이 없다.

| 방식 | 모양 | 특징 |
|---|---|---|
| 도메인당 서비스 하나 | `MenuService.java` 안에 등록, 조회, 수정, 삭제를 모두 구현 | 파일이 적다. 기능이 늘면 같은 파일을 계속 열어 고친다 |
| 유스케이스 단위로 쪼개기 | 조회, 삭제, 삽입을 각각 파일로 | 기능을 추가할 때 **확장만** 한다(기존 코드는 안 건드림). 이름이 달라지고 파일이 늘어난다 |

- 수업의 강사는 **함수 단위로 파일을 만들 수 있는 환경**(Next.js 같은 파일 기반 구조)에서는 유스케이스 단위로 쪼갠다고 했다.
- **자바에서는** 쪼개면 오버헤드가 크다고 느껴서 도메인당 서비스 하나로 모은다고 했다.
- 판단 기준은 **언어와 플랫폼**, 그리고 **기능의 크기와 복잡도**다. 기능이 작고 단순하면 하나로 모으고, 크고 복잡한 기능은 나누는 쪽이 낫다.
- 중요한 것은 어느 쪽이든 **내 기준이 있어야 한다**는 점이다. "그냥 그렇게 하는 걸로 알아서"는 이유가 될 수 없다.

## 11. 적용 계획

- 새 도메인(공지사항)부터 이 구조로 만든다. 한 사람이 도메인 폴더 하나를 맡으면 **그 폴더만 보고 구현**할 수 있다.
- 기존 ncafe 프로젝트(3계층)는 AI에게 시켜 헥사고날로 바꿀 수 있다. 이때 구조(domain / application / adapter, port in·out)를 **내가 먼저 이해하고 지시해야** AI가 엉뚱한 구조를 만들었을 때 따져서 바로잡을 수 있다.
- 먼저 함께 공부해 골격을 확인한 뒤, 각자 시스템 하나씩 맡아 구현해도 문제가 없다.

## 정리

| 질문 | 답 |
|---|---|
| 3계층의 기준은? | 컨트롤러가 하던 일을 **역할별**로 나눈 것 |
| 3계층의 한계는? | 기능 하나를 고치려면 계층 폴더 사이를 오가야 한다. 규모가 커질수록 흩어진다 |
| 해결은? | **도메인 단위**로 모은다. 같이 수정되는 것끼리 한곳에 둔다 |
| 도메인의 중심은? | **엔티티**. 업무 로직이 그것을 감싼다 |
| 바깥(웹, DB)이 바뀌면? | **어댑터**만 고친다. 안쪽은 바깥을 모른다 |
| 안쪽이 바깥을 쓰려면? | 안쪽에 **인터페이스(포트)** 를 두고, 구현은 바깥에 둔다. **DI**로 주입받는다 |
| 의존 방향은? | 바깥 → 안쪽만 허용. 안쪽 → 바깥은 금지 |
| 헥사고날, 어니언, 클린의 관계는? | 같은 생각의 다른 표현. 클린이 가장 포괄적이다 |
| 클린과 헥사고날의 차이는? | 클린은 Infrastructure 계층이 더 있다. 직접 만드는 인프라가 없으면 헥사고날(어댑터만)이 단순하다 |
| 폴더 구조는? | `도메인/` 아래 `domain`, `application`(+`dto`, `port/in·out`), `adapter`(`in/web`, `out/persistence`) |
