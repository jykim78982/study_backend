# 문자열 형 변환과 디버깅, 조건문

## 0. 학습 태도 메모

- **개념 우선 접근**: 실제 코드를 바로 수정하기보다 설계·개념을 먼저 이해하면 유지보수가 쉬워진다.
- **기존 코드 활용**: 산적한(쌓여 있는) 레거시 코드 위에서 변경할 때는 **원인 추적**과 **작은 단위로 검증**하는 습관이 필요하다.

## 1. 문자열 다루기 — 문자열 객체 서비스

### 형식 변환

**문자열 → 정수, 실수, 진리값** / **정수, 실수, 진리값 → 문자열** 양방향 변환이 가능하다.

```java
int x = Integer.parseInt("13");         // "13" 문자열을 정수로
double y = Double.parseDouble("3.443"); // "3.443" 문자열을 double 실수로
String sx = String.valueOf(13);         // 13을 문자열로
```

| 변환 방향 | 사용 메서드 |
|---|---|
| 문자열 → 정수 | `Integer.parseInt("13")` |
| 문자열 → 실수 | `Double.parseDouble("3.443")` |
| 문자열 → 진리값 | `Boolean.parseBoolean("true")` |
| 값 → 문자열 | `String.valueOf(13)` |

### 입력 버퍼 주의점

- `nextInt()`는 **int만 읽고**, 입력했던 `\r\n`(Enter)은 **버퍼에 남아 있다**.
- `nextLine()`은 `\r\n`을 만날 때까지 문자열을 읽는 기능이다.

> `nextInt()` 뒤에 `nextLine()`을 쓰면 버퍼에 남은 `\r\n`을 바로 읽어 빈 문자열이 나올 수 있으므로 주의.

## 2. 디버깅

### 로깅으로 흐름 확인

- 로그 레벨을 **DEBUG**로 올려 변수 값과 메서드 진입·종료를 찍어 흐름을 확인한다.
- 로그 메시지에 **요청 아이디나 사용자 식별자**를 함께 찍으면 여러 요청이 섞여도 추적하기 쉽다.

### 브레이크포인트 (Breakpoint)

**"여기서 잠깐 멈춰"라고 표시해두는 지점.**

- IDE(통합 개발 환경)에서 코드 줄 번호 왼쪽을 클릭하면 빨간 점이 생기고, 디버그 모드로 실행하면 프로그램이 그 줄에 **도달하는 순간(정확히는 그 줄을 실행하기 직전)** 멈춘다.
- 멈춘 상태에서 확인할 수 있는 것:
  - **변수 값**: 이 시점에 각 변수에 뭐가 들어있는지 (Variables 창)
  - **호출 스택(Call Stack)**: 어떤 메서드가 어떤 메서드를 불러서 여기까지 왔는지 경로
- `System.out.println`으로 값을 찍는 것과 목적은 비슷하지만, **코드를 수정하지 않고도** 모든 변수를 한 번에 볼 수 있다는 게 큰 차이.
- **조건부 브레이크포인트**로 특정 상황에서만 멈추게 하면 문제를 잡는 시간이 줄어든다.

> 💡 어디에 걸까? "여기까지는 정상인데, 이 다음부터 이상하다" 싶은 **경계 지점**에 거는 게 효율적. 의심 구간의 시작에 걸고 스텝 오버로 한 줄씩 내려가면서 어느 줄에서 값이 틀어지는지 찾는다.

### 스텝 오버 (Step Over)

브레이크포인트에서 멈춘 다음, **"현재 줄을 실행하고 다음 줄로 넘어가"**라는 명령. (IntelliJ에서 F8)

**디버깅할 때 주로 사용하게 될 기능** — 평소엔 스텝 오버로 한 줄씩 내려가며 변수 값을 관찰하는 게 기본이고, 메서드 내부가 궁금할 때만 스텝 인투로 들어간다.

- 이름이 "오버(over)"인 이유: 현재 줄에 **메서드 호출이 있어도 그 안으로 들어가지 않고**, 메서드를 통째로 실행한 뒤 결과만 받고 다음 줄로 **건너뛰기** 때문.

```java
int price = calculateTotal(items);  // ← 여기서 Step Over 하면
System.out.println(price);          // ← calculateTotal 내부를 거치지 않고 바로 여기로
```

- `calculateTotal` 안에서 무슨 일이 일어나는지는 안 보여주지만, 실행이 끝난 뒤 `price`에 담긴 **결과값은 확인**할 수 있다.
- 사용 패턴: 스텝 오버로 한 줄씩 내려가며 변수 값을 관찰하다가 → **어떤 줄을 지나는 순간 값이 이상해지면** → 그 줄(또는 그 줄이 호출하는 메서드 안)이 범인.

### 두 개를 조합한 기본 흐름

1. 의심 구간 시작에 **브레이크포인트**를 건다
2. 디버그 모드로 실행 → 그 지점에서 멈춤
3. **스텝 오버**로 한 줄씩 진행하면서 Variables 창의 변수 값 변화를 지켜본다
4. 값이 틀어지는 줄을 발견하면 원인 확정

> 참고: 스텝 오버 중 "이 메서드 **안**이 궁금한데?" 싶을 때 쓰는 게 **스텝 인투(Step Into, F7)**. 메서드 내부로 들어가서 한 줄씩 보는 기능.

## 3. 조건문 — if / else, switch

### if와 else는 한 문장이다

`if ~ else` 전체가 **하나의 문장**이다. 그래서 **중간에 다른 문장이 끼어들 수 없다.**

```java
if (조건)
    문장A;
// ← 여기에 다른 문장이 오면 if 문장이 끝나버려서, 아래 else는 짝을 잃고 컴파일 에러
else
    문장B;
```

### if / else if / else — 범위가 자동으로 나뉜다

위에서부터 순서대로 검사하고, **앞 조건에 걸린 값은 아래로 내려오지 않는다.** 인덱스 `i`가 0~29일 때:

| 조건 | 실제로 걸리는 범위 | 이유 |
|---|---|---|
| `if (i < 10)` | 0 ~ 9 | |
| `else if (i < 20)` | 10 ~ 19 | 0~9는 위에서 이미 걸러짐 |
| `else` | 20 ~ 29 | 나머지 전부 |

```java
if (i < 10)
    System.out.printf("%d: ** %d\n", i, num);
else if (i < 20)
    System.out.printf("%d: ^^ %d\n", i, num);
else
    System.out.printf("%d: %% %d\n", i, num);
```

### 반복문 안에서의 분기 — break와 continue

같은 "30번째에서 멈추기"도 여러 방식으로 쓸 수 있다.

```java
// 방식 1: 범위 안이면 출력, 벗어나면 탈출
if (i < 30)
    System.out.printf("%d:%d\n", i, num);
else
    break;

// 방식 2: 일단 출력하고, 끝에 도달하면 탈출
System.out.printf("%d:%d\n", i, num);
if (i == 30)
    break;

// 방식 3: continue로 건너뛰기 — 30 이상일 때만 출력됨
if (i < 30)
    continue;   // 다음 문장을 실행하지 않고 다음 반복으로 넘어간다

System.out.printf("%d:%d\n", i, num);
```

| 키워드 | 동작 |
|---|---|
| `break` | 반복문을 **완전히 빠져나간다** |
| `continue` | **이번 회차만 건너뛰고** 다음 반복으로 넘어간다 |

### ⚠️ 주의 — if 뒤에 세미콜론

```java
if (i >= 30);   // ← 세미콜론(빈 문장)이 if의 몸통이 되어 if가 여기서 끝난다

System.out.printf("%d:%d\n", i, num);   // 조건과 무관하게 항상 실행됨
```

- "30 이상이면 다음 내용을 실행"을 의도했지만, `;`가 **빈 문장**으로 if에 붙어버려 if는 아무 일도 하지 않는다.
- **컴파일 에러가 나지 않아서** 찾기 어려운 버그다. 이런 게 바로 브레이크포인트를 걸고 한 줄씩 확인해야 잡히는 유형.

### switch

값 하나를 여러 경우(case)와 비교할 때 사용한다.

```java
switch (name) {
    case value:
        // name이 value일 때 실행
        break;      // ← break가 없으면 아래 case까지 흘러내려 실행된다 (fall-through)

    default:
        // 어느 case에도 해당하지 않을 때 (if의 else 역할)
        break;
}
```

- 각 `case` 끝의 **`break`를 빼먹으면** 다음 case 코드까지 연달아 실행되므로 주의.

#### 메뉴 처리에는 switch가 적합하다

- `if / else-if`로 메뉴를 처리하면 **뒤쪽 케이스일수록 앞의 모든 비교를 통과해야** 도달한다. 메뉴가 많아질수록 불리하다.
- `switch`는 입력 값에 따라 **해당 case로 바로 점프**하는 구조라 메뉴 분기에 효율적이다.

#### fall-through와 break의 설계적 사용

- switch는 **"점프한 뒤 아래로 계속 실행되는"(fall-through)** 특성이 있다. 특정 case만 실행하고 빠져나오려면 `break`가 필수다.
- 반대로 **여러 case가 공통 처리를 공유**해야 한다면 break를 **의도적으로 생략**할 수도 있다 — 실수가 아니라 설계 수단이 되는 것.

| 요소 | 의미 | 주의점 |
|---|---|---|
| `case 값:` | 점프 가능한 **라벨**(분기 지점) | 콜론(`:`)은 세미콜론이 아니라 라벨 표기 |
| `break` | switch를 종료해 다음 case로의 연쇄 실행을 막음 | 없으면 fall-through로 다음 case 실행 |
| `default:` | 어떤 case에도 해당하지 않을 때의 기본 분기 | "없는 메뉴" 안내 같은 디폴트 처리에 적합 |

> ⚠️ switch 안의 `break`는 **"반복문 탈출"이 아니라 "switch 블록 탈출"**이다. 반복문 안에 switch가 있을 때 case에서 break를 써도 반복문은 계속 돈다.
