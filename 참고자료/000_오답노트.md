# 오답노트

## 자바 — 클래스패스와 리소스

### 1. 클래스패스 기반 리소스 접근

**문제**: 클래스패스 기반 리소스 접근에 대해 옳은 설명은?

1. `getResourceAsStream`은 항상 물리적 파일 경로를 반환한다.
2. `src/main/java`에 CSV 파일을 두는 것이 권장된다.
3. 리소스를 클래스 로더로 스트림 형태로 읽으면 운영체제 절대 경로 의존성을 줄일 수 있다.
4. 배포 후에도 항상 파일의 절대 경로를 직접 하드코딩하는 것이 안전하다.

**정답: 3번**

- `C:\Users\...` 같은 운영체제 절대 경로를 코드에 하드코딩하면, 실행 환경(Windows/Linux)이 바뀌거나 JAR/WAR로 압축 배포될 때 그 경로를 찾지 못해 오류가 난다.
- 클래스 로더로 리소스를 **스트림(`InputStream`)** 형태로 읽어오면, 실제 파일이 프로젝트 폴더 안에 있든 압축된 JAR 내부에 있든 상관없이 **클래스패스 기준**으로 안전하게 가져올 수 있다. `038` 노트에서 다룬 `ClassLoader`가 바로 이 역할을 한다.

**오답 정리**

- **1번**: `getResourceAsStream`은 경로 **문자열**이 아니라 바로 읽을 수 있는 **`InputStream`**을 반환한다. 경로 문자열이 필요하면 `getResource(...).getPath()`처럼 별도로 꺼내야 한다(`038` 노트 7장).
- **2번**: CSV 같은 정적 리소스 파일은 자바 소스가 들어가는 `src/main/java`가 아니라, Maven이 정해둔 `src/main/resources`에 두는 것이 표준이다(`038` 노트 7장).
- **4번**: 절대 경로 하드코딩은 다른 컴퓨터나 서버 환경에서 그대로 깨지는 매우 위험한 방식이다.

## 자바 — 예외 처리

### 1. 예외 처리 키워드의 역할

**문제**: 예외 처리 관련 키워드의 역할 설명 중 옳지 않은 것은?

1. `throw`는 현재 위치에서 예외 객체를 발생시킨다.
2. `RuntimeException` 계열은 컴파일러가 강제하지 않는다.
3. `throws`는 메서드 선언부에서 예외 전파 가능성을 명시한다.
4. `try-catch`는 예외를 호출자에게 무조건 전달하는 의미다.

**정답: 4번 (틀린 설명)**

- `try-catch`는 예외를 상위 호출자에게 떠넘기는 게 아니라, **현재 위치에서 그 예외를 직접 잡아 처리(복구·대응)하겠다**는 의미다(`039` 노트 6장).
- 예외를 상위 호출자에게 전달(전파)하고 싶을 때 쓰는 것은 `try-catch`가 아니라 **`throws`**다.

**옳은 보기 정리**

- **1번(`throw`)**: `throw new IllegalArgumentException();`처럼, 개발자가 의도적으로 예외 객체를 그 자리에서 즉시 발생시킨다(`039` 노트 4~5장의 `throw new 음수를_만드는_오류입니다();`와 같은 문법).
- **2번(`RuntimeException`)**: 언체크 예외라서, 컴파일러가 `try-catch`나 `throws` 선언을 강제하지 않는다(`039` 노트 7장). 대표적으로 `NullPointerException`, `IndexOutOfBoundsException`이 있다.
- **3번(`throws`)**: 메서드 시그니처 뒤에 붙여 "이 메서드를 호출하면 이 예외가 발생할 수 있으니 대비하라"고 **전파 가능성을 미리 알려주는** 선언이다(`039` 노트 5장).

## 자바 — 문자열 비교

### 1. 문자열 내용 비교에 써야 하는 방법

**문제**: 문자열 내용 비교를 위해 Java에서 사용해야 하는 것은?

1. `compareToIgnoreCase()` 항상
2. `==` 연산자
3. `equals()` 메서드
4. `equalsIgnoreCase()`만 사용

**정답: 3번**

- `String`은 기본 타입(Primitive Type)이 아니라 **참조 타입(Reference Type)** 객체다.
- `==`는 두 변수가 **메모리 상에서 같은 객체(주소)를 가리키는지**를 비교한다 — 내용이 완전히 같아도 서로 다른 객체라면 `false`가 나온다.
- `equals()`는 주소와 무관하게 **객체 안의 실제 문자열 내용**이 같은지 비교한다.

```java
String str1 = new String("hello");
String str2 = new String("hello");

System.out.println(str1 == str2);      // false (주소가 다름)
System.out.println(str1.equals(str2)); // true  (내용이 같음)
```

**오답 정리**

- **1번(`compareToIgnoreCase()`)**: 대소문자를 구분하지 않고 문자열의 사전순 크기 관계를 정수로 반환하는 메서드다(같으면 0, 크면 양수, 작으면 음수). 단순 동일성 비교 목적으로 "항상" 쓰기엔 오버헤드가 있고 용도에 맞지 않는다.
- **2번(`==`)**: 문자열의 내용이 아니라 참조 주소를 비교하므로 내용 비교에는 쓸 수 없다.
- **4번(`equalsIgnoreCase()`만 사용)**: 대소문자를 구분하지 않고 내용만 같으면 `true`를 반환하는 특수 목적 메서드다(예: `"HELLO".equalsIgnoreCase("hello")` → `true`). 대소문자까지 엄격히 구분해야 하는 일반적인 상황에는 쓸 수 없으므로 "만 사용한다"는 설명은 틀렸다.

## 데이터베이스 — SQL 집계와 그룹화

### 1. 집계 함수 사용에 관한 설명

**문제**: 집계 함수 사용과 관련된 설명으로 옳지 않은 것은?

1. 집계된 결과와 일반 컬럼을 함께 `SELECT`하려면 그 일반 컬럼은 `GROUP BY`에 포함되어야 한다.
2. 집계 이전의 행 조건은 `HAVING` 절에서 처리한다.
3. 대표적 집계 함수로 `SUM`, `AVG`, `MIN`, `MAX`, `COUNT`가 있다.
4. `COUNT(column)`는 해당 컬럼의 `NULL`을 제외하고 계산한다.

**정답: 2번**

- **1번(올바른 설명)**: `GROUP BY`를 쓰면 데이터가 그룹 단위로 압축되고, `SUM()`·`AVG()` 같은 집계 함수는 그룹당 결과값 하나만 만든다. 집계되지 않은 일반 컬럼을 그냥 `SELECT`에 쓰면, 그룹화된 한 행에 원본의 여러 행 값 중 무엇을 출력할지 DB가 판단할 수 없어 오류가 난다. 그래서 집계 함수를 쓰지 않은 일반 컬럼은 반드시 `GROUP BY`에 기준 컬럼으로 명시해야 한다(`040` 노트 8절).

  ```sql
  -- 에러 발생 (dept_id가 GROUP BY에 없음)
  SELECT dept_id, AVG(salary)
  FROM employees;

  -- 정상 작동 (dept_id를 GROUP BY에 포함)
  SELECT dept_id, AVG(salary)
  FROM employees
  GROUP BY dept_id;
  ```

- **2번(정답/틀린 설명)**: SQL 실행 순서는 `FROM → WHERE → GROUP BY → HAVING → SELECT`다(`040` 노트 9절). `WHERE`는 그룹화가 이루어지기 전, 원본 테이블의 개별 행을 대상으로 조건을 검사한다. `HAVING`은 `GROUP BY`로 그룹화·집계가 끝난 뒤, 그 집계 결과값(`SUM > 1000` 등)을 대상으로 조건을 검사한다. 즉 **집계 이전의 원본 행을 필터링하는 조건은 `HAVING`이 아니라 `WHERE` 절에서 처리해야 하므로 2번 설명은 틀렸다.**
