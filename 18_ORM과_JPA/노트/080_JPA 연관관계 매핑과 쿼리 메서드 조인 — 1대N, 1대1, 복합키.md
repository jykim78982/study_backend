# JPA 연관관계 매핑과 쿼리 메서드 조인 — 1대N, 1대1, 복합키

엔티티끼리 관계를 맺는 방법(1:N, 1:1), 다대다 관계에서 생기는 복합키를 표현하는 두 가지 방식, 그리고 관계가 설정된 엔티티를 쿼리 메서드로 조회할 때 조인이 어떻게 만들어지는지 정리한다.

## 1. 엔티티 매핑의 기본

관계 설정에 들어가기 전에 엔티티의 필수 설정을 짧게 다시 짚는다.

| 어노테이션 | 역할 |
|---|---|
| `@Entity` | 이 클래스가 JPA 엔티티임을 선언한다. |
| `@Table(name = "menus")` | 매핑할 테이블 이름을 지정한다. 생략하면 클래스 이름을 기준으로 정해진다(`Menu` → `menu`). |
| `@Id` | 주키(Primary Key) 필드를 지정한다. |
| `@GeneratedValue(strategy = GenerationType.IDENTITY)` | 주키 생성 전략. `IDENTITY`는 DB의 자동 증가 기능을 쓴다. |
| `@Column(name = "kor_name", nullable = false)` | 컬럼 이름, NULL 허용 여부, 길이 등을 지정한다. |

```java
@Entity
@Table(name = "menus")
public class Menu {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "kor_name", nullable = false)
    private String korName;

    @Column(name = "eng_name")
    private String engName;

    private Integer price;
}
```

부트 프로젝트가 시작될 때(`ddl-auto`가 `create` 등일 때) 이 설정을 읽어 다음 DDL을 만들고 실행한다.

```sql
create table menus (
    id bigint generated by default as identity,
    kor_name varchar(255) not null,
    eng_name varchar(255),
    price integer,
    primary key (id)
);
```

- `nullable = false` → `not null`이 붙는다.
- 길이를 지정하지 않은 `String`은 기본으로 `varchar(255)`가 된다.

> 강의 자료에는 `@Column(name = "eng_name")`이 없으면 컬럼명이 `engname`이 된다고 되어 있다. 이는 Hibernate만 단독으로 쓸 때의 동작이다. **Spring Boot는 기본 네이밍 전략으로 `engName`을 `eng_name`으로 자동 변환**하므로, 카멜 ↔ 스네이크 차이만 있다면 `@Column`이 없어도 `eng_name`이 된다.

## 2. 1:N 관계 — @ManyToOne, @OneToMany

JPA는 테이블 간의 1:1, 1:N, N:M 관계를 **객체 간의 관계**로 표현하는 어노테이션을 제공한다. 그중 가장 많이 쓰는 것이 1:N이다.

| 어노테이션 | 붙이는 곳 | 의미 |
|---|---|---|
| `@ManyToOne` | 자식(N) 엔티티 | 다(N)에서 하나(1)로 가는 방향. 자식 테이블에 부모의 주키를 참조하는 **외래키 컬럼**이 생긴다. |
| `@OneToMany` | 부모(1) 엔티티 | 하나(1)에서 다(N)로 가는 방향. `mappedBy`와 함께 쓰면 테이블에 아무것도 추가하지 않고, `@ManyToOne` 쪽 외래키를 그대로 이용한다. |

**회원(1) — 메뉴(N) 예시**: 메뉴를 등록한 회원을 기록한다면 회원 하나가 메뉴 여러 개를 가진다.

```java
@Entity
public class Member {                       // 부모 (1)
    @Id
    private Long id;
    private String name;
    private String username;

    @OneToMany(mappedBy = "member")         // Menu 엔티티의 member 필드를 가리킨다
    private List<Menu> menus;
}

@Entity
public class Menu {                         // 자식 (N)
    @Id
    private Long id;
    private String korName;

    @ManyToOne
    @JoinColumn(name = "member_id")         // menus 테이블의 실제 외래키 컬럼명
    private Member member;
}
```

두 설정에 들어가는 이름은 가리키는 대상이 다르다.

| 설정 | 적는 것 | 이 예시에서 |
|---|---|---|
| `mappedBy` | 자식 **엔티티의 필드명** (자바 쪽 이름) | `"member"` (`Menu.member` 필드) |
| `@JoinColumn(name)` | 자식 **테이블의 외래키 컬럼명** (DB 쪽 이름) | `"member_id"` (`menus.member_id` 컬럼) |

> 강의 자료에는 `@JoinColumn`에 "부모 테이블의 속성명"을 지정한다고 되어 있지만, 자료의 그림에서도 화살표가 가리키듯 **자식 테이블(메뉴)에 있는 실제 외래키 컬럼명**(`member_id`)을 적는 것이 맞다. 이 외래키가 부모의 어느 컬럼을 가리키는지는 생략하면 부모의 주키(`id`)로 정해진다.

**mappedBy 이름이 틀리면 시작부터 실패한다**: `mappedBy = "member"`인데 `Menu`에 `member`라는 필드가 없으면(예: 필드명이 `writer`), 애플리케이션 시작 시 이런 에러가 난다.

```
Collection 'kr.co.rland.rlandboot3.entity.Member.menus' is 'mappedBy' a property named 'member'
which does not exist in the target entity 'kr.co.rland.rlandboot3.entity.Menu'
```

"`Member.menus` 컬렉션이 대상 엔티티 `Menu`의 `member` 필드에 매핑되어 있다고 했는데, `Menu`에 그런 필드가 없다"는 뜻이다. `mappedBy`는 컬럼명이 아니라 **필드명**이라는 점을 다시 확인하게 해주는 에러다.

**카테고리(1) — 메뉴(N)에 적용하기**:

```java
@Entity
@Table(name = "categories")
public class Category {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    @OneToMany(mappedBy = "category")
    private List<Menu> menus = new ArrayList<>();
}

@Entity
@Table(name = "menus")
public class Menu {
    // ... 기존 필드들 ...

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "category_id")
    private Category category;
}
```

이 매핑으로 `menus` 테이블에 `category_id` 컬럼과 외래키 제약이 추가된다.

```sql
alter table menus add column category_id bigint;
alter table menus add constraint FK... foreign key (category_id) references categories(id);
```

> - 강의 자료의 `Category`에는 `@Table`이 없는데 DDL은 `categories`를 참조한다. `@Table`이 없으면 테이블 이름은 `category`가 되므로, `categories`를 쓰려면 위처럼 `@Table(name = "categories")`를 붙여야 한다.
> - 외래키 제약 이름은 따로 지정하지 않으면 Hibernate가 `FKxxxxxxxx` 같은 임의 이름을 만든다. 자료처럼 `fk_menu_category`로 하고 싶다면 `@JoinColumn(name = "category_id", foreignKey = @ForeignKey(name = "fk_menu_category"))`처럼 지정한다.
> - `@ManyToOne`의 기본 fetch 전략은 **EAGER**다. 필요할 때만 카테고리를 가져오려면 `fetch = FetchType.LAZY`를 직접 적어줘야 한다.

## 3. 1:1 관계 — @OneToOne

1:1 관계는 한 엔티티가 다른 엔티티 **하나와만** 연결되는 경우다. 1:1도 외래키로 매핑하는데, 1:N과 달리 양쪽 모두 "하나"라서 **외래키 컬럼을 어느 테이블에 둘지 직접 정해야** 한다.

- `@OneToOne`: 1:1 관계를 선언한다.
- `mappedBy`: 반대 방향 참조(역참조)를 설정할 때 쓴다. 외래키를 가진 쪽(연관관계의 주인)의 **필드명**을 적어서, 양쪽 엔티티가 서로를 참조할 수 있게 한다.

**외래키는 상세 정보 쪽에 둔다**: 회원(`Member`)과 회원 상세 정보(`MemberDetail`)라면, 상세 정보가 회원에 딸린 것이므로 `member_details` 테이블에 `member_id` 외래키를 두는 것이 자연스럽다.

```java
@Entity
@Table(name = "members")
public class Member {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String username;

    @OneToOne(mappedBy = "member")          // MemberDetail의 member 필드를 가리킨다
    private MemberDetail memberDetail;
}

@Entity
@Table(name = "member_details")
public class MemberDetail {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String address;

    @OneToOne
    @JoinColumn(name = "member_id")         // 외래키 컬럼은 이쪽 테이블에 생긴다
    private Member member;
}
```

```sql
create table member_details (
    id bigint generated by default as identity,
    address varchar(255),
    member_id bigint unique,
    primary key (id)
);

alter table member_details add constraint FK... foreign key (member_id) references members(id);
```

`Member`에는 `mappedBy`만 있고 `@JoinColumn`이 없으므로 `members` 테이블에는 외래키 컬럼이 생기지 않는다. 외래키는 `@JoinColumn`을 지정한 `MemberDetail` 쪽 테이블에만 생긴다.

> **보충**
> - 1:1이면 한 회원에 상세 정보가 둘 이상 붙으면 안 되므로 `member_id`에 **unique 제약**이 필요하다. Hibernate 6.2 이상은 `@OneToOne`의 외래키 컬럼에 unique 제약을 자동으로 붙인다(위 DDL의 `unique`).
> - `@OneToOne`도 기본 fetch 전략이 **EAGER**다. 또 외래키가 없는 쪽(`Member.memberDetail`)은 `LAZY`를 지정해도 Hibernate가 상세 정보가 있는지 확인하려고 조회를 해버리는 경우가 많다. 그래서 주로 조회를 시작하는 쪽에 외래키를 두는 설계도 함께 고민한다.
> - 자료에는 `@Table`이 없는데 DDL은 `member_details`, `members`를 쓴다. 위처럼 `@Table`을 붙여야 그 이름이 된다(없으면 `member_detail`, `member`).

## 4. 복합 주키 — @EmbeddedId vs @IdClass

다대다(M:N) 관계는 그 자체가 테이블이 되는 경우가 많다.

| 관계 | 테이블 |
|---|---|
| 회원이 메뉴를 **좋아한다** | `likes` |
| 회원이 메뉴를 **추천한다** | `rcmds` |
| 회원이 메뉴를 **주문한다** | `orders` |

이런 테이블은 두 개 이상의 컬럼을 합쳐 식별자로 쓰는 **복합키**를 쓰는 경우가 많다. JPA는 복합키를 표현하는 방법으로 `@EmbeddedId`와 `@IdClass` 두 가지를 제공한다.

> 같은 회원이 같은 메뉴를 여러 번 주문할 수 있는 `orders`는 `(member_id, menu_id)` 복합키로 만들면 두 번째 주문부터 중복키 에러가 난다. 복합키는 좋아요처럼 **그 조합이 딱 한 번만 존재하는** 테이블에 맞고, 주문은 자체 id(대리키)를 두는 것이 일반적이다.

### 방법 1 — @EmbeddedId

`@Embeddable`이 붙은 키 클래스를 엔티티 안에 **필드 하나로 통째로 넣어** 주키로 쓰는 방식이다.

```java
@Embeddable
public class LikeId implements Serializable {
    private Long memberId;
    private Long menuId;
    // equals(), hashCode() 구현 필수
}

@Entity
@Table(name = "likes")
public class Like {
    @EmbeddedId
    private LikeId id;

    private LocalDateTime createdAt;
}
```

### 방법 2 — @IdClass

키 클래스는 따로 만들되(`@Embeddable` 필요 없음), 엔티티에는 `@Id` 필드를 **각각** 두고 `@IdClass`로 키 클래스를 지정하는 방식이다. 키 클래스와 엔티티의 `@Id` 필드는 **이름과 타입이 같아야** 한다.

```java
public class LikeId implements Serializable {
    private Long memberId;
    private Long menuId;
    // equals(), hashCode() 구현 필수
}

@Entity
@Table(name = "likes")
@IdClass(LikeId.class)
public class Like {
    @Id
    private Long memberId;
    @Id
    private Long menuId;

    private LocalDateTime createdAt;
}
```

두 방식 모두 `likes` 테이블에 `member_id`, `menu_id` 컬럼이 생기고, 이 두 컬럼이 함께 복합 주키가 된다.

> **강의 자료 바로잡기**
> - **`@Table(name = "likes")`가 꼭 필요하다**: 자료의 `Like` 엔티티에는 `@Table`이 없다. 그러면 테이블 이름이 `like`가 되는데, `LIKE`는 SQL 예약어라서 `create table like (...)`부터 문법 에러가 난다.
> - 날짜 타입은 `DateTime`이 아니라 `LocalDateTime`이다.
> - 키 클래스는 `equals()`/`hashCode()`뿐 아니라 **`Serializable`도 구현**해야 한다(JPA 규격).
> - 자료의 조회 SQL에 `l0_.id`가 있는데, 복합키 테이블에는 `id` 컬럼이 없다. 실제로는 `member_id`, `menu_id`, `created_at`만 조회한다.

### 두 방식의 차이

**만들어지는 SQL은 같다**: DDL도, 기본 조회 쿼리도 사실상 같다.

```sql
-- @EmbeddedId, @IdClass 모두 같은 SQL
select l1_0.member_id, l1_0.menu_id, l1_0.created_at
from likes l1_0
where l1_0.member_id = ? and l1_0.menu_id = ?
```

**식별자 객체를 다루는 방식이 다르다**: JPA는 엔티티를 1차 캐시(영속성 컨텍스트)에 "식별자 → 엔티티" 형태로 저장한다. 이때 식별자는 두 방식 모두 `LikeId` 객체인데, 다루는 방식이 다르다.

| | `@EmbeddedId` | `@IdClass` |
|---|---|---|
| 식별자 객체 | 엔티티의 `id` 필드에 들어 있는 `LikeId` **그 자체** | 엔티티의 `memberId`, `menuId` 값을 꺼내 **`LikeId`를 만들어서** 사용 |
| 키 필드 접근 | `like.getId().getMemberId()` | `like.getMemberId()` |
| 쿼리 메서드 | `findByIdMemberId(Long memberId)` | `findByMemberId(Long memberId)` |
| JPQL | `l.id.memberId` | `l.memberId` |

```java
// @EmbeddedId 사용 시 — id 필드 안의 memberId를 타고 들어간다
List<Like> findByIdMemberId(Long memberId);

// @IdClass 사용 시 — 엔티티에 memberId가 바로 있다
List<Like> findByMemberId(Long memberId);
```

**어느 쪽을 고르나**:

- `@EmbeddedId`: 주키를 항상 **하나의 묶음**으로 다루고 싶을 때. 키가 객체 하나로 표현되어 일관성이 있다. 실무에서 더 많이 쓰이는 편이다.
- `@IdClass`: 키 필드를 엔티티의 다른 필드처럼 **각각 직접** 쓰고 싶을 때. 쿼리 메서드나 JPQL에서 경로가 짧아 읽기 편하다.

> 강의 자료에는 `@EmbeddedId`의 장점으로 "다른 엔티티가 이 복합키를 참조할 때 `@Embedded`를 재사용할 수 있다"고 되어 있다. 하지만 `@Embedded`는 일반 값 묶음을 컬럼으로 펼쳐 넣는 용도라서, 다른 엔티티의 복합키를 **외래키로 참조**할 때는 `@JoinColumns`로 컬럼 두 개를 지정하는 방식을 쓴다. 또 `Like`의 `memberId`, `menuId`를 실제 `Member`, `Menu` 엔티티 관계로도 연결하고 싶다면 `@ManyToOne`과 함께 `@MapsId`를 써서 "이 관계의 외래키가 곧 복합키의 일부"라고 알려준다.

## 5. 쿼리 메서드에서의 조인

관계 매핑을 설정했다면 쿼리 메서드에서 그 관계를 그대로 쓸 수 있다. 메서드 이름에 **연관 필드**(관계가 매핑된 필드)를 넣으면 Spring Data JPA가 알아서 조인 쿼리를 만든다.

### 연관 필드로 조회하기

`Menu`에는 `categoryName`이라는 필드가 없다. 하지만 `category` 필드가 있고, 그 `Category`에 `name`이 있으므로 `findByCategoryName`은 `menu.category.name`으로 해석된다.

```java
public interface MenuRepository extends JpaRepository<Menu, Long> {
    List<Menu> findByCategoryName(String name);
}
```

`menuRepository.findByCategoryName("커피")`를 호출하면 `menus`와 `categories`를 조인한 SQL이 만들어진다.

```sql
select m1_0.id, m1_0.category_id, m1_0.eng_name, m1_0.kor_name, m1_0.price
from menus m1_0
join categories c1_0 on c1_0.id = m1_0.category_id
where c1_0.name = ?
```

결과적으로 **카테고리가 있고, 그 이름이 "커피"인 메뉴**만 나온다. 카테고리가 없는 메뉴는 `c1_0.name = ?` 조건을 만족할 수 없으므로 빠진다.

> **보충**
> - 콘솔에 찍히는 조인 종류는 버전과 `optional` 설정에 따라 `left join`으로 나올 수도 있다. 하지만 WHERE 절에 카테고리 이름 조건이 걸리므로 결과는 inner join과 같다.
> - 강의 자료에는 "카테고리가 없는 메뉴도 포함하고 싶다면 `findByCategoryNameIsNull`을 쓴다"고 되어 있는데, 이 메서드는 **카테고리 이름이 NULL인 메뉴**를 찾는 것이라 의도와 다르다. 카테고리가 없는 메뉴만 찾으려면 `findByCategoryIsNull()`, "커피 카테고리이거나 카테고리가 없는 메뉴"처럼 둘을 합치려면 `@Query`에 `left join`을 직접 쓰는 것이 명확하다.
> - 자료의 `m0_`, `c1_` 같은 별칭은 Hibernate 5 형식이다. Spring Boot 3(Hibernate 6)에서는 `m1_0`, `c1_0`처럼 찍힌다.

### 여러 조건 조합

연관 필드 조건과 자기 필드 조건을 섞어도 조인은 자동으로 처리된다.

```java
List<Menu> findByCategoryNameAndPriceGreaterThan(String categoryName, Integer price);
```

```sql
select m1_0.id, m1_0.category_id, m1_0.eng_name, m1_0.kor_name, m1_0.price
from menus m1_0
join categories c1_0 on c1_0.id = m1_0.category_id
where c1_0.name = ?
  and m1_0.price > ?
```

이름이 애매할 때(예: `Menu`에 `categoryName` 필드도 있고 `category.name`도 있을 때)는 `findByCategory_Name`처럼 밑줄로 경계를 명시할 수 있다.

### Fetch와 Distinct

**연관 엔티티를 한 번에 가져오기 — fetch join**: `LAZY`로 설정된 연관 엔티티를 이번 조회에서만 **조인으로 한꺼번에** 가져오고 싶을 때가 있다. 메뉴 목록을 출력하면서 카테고리 이름도 같이 보여줘야 하는 경우다. `LAZY` 그대로 두면 메뉴마다 카테고리를 따로 조회하는 SQL이 추가로 나간다(메뉴 N개 → 추가 쿼리 N번, 흔히 **N+1 문제**라고 부른다).

```java
// 방법 1: JPQL의 join fetch
@Query("select m from Menu m join fetch m.category where m.price > :price")
List<Menu> findWithCategoryByPriceGreaterThan(@Param("price") Integer price);

// 방법 2: @EntityGraph로 함께 가져올 연관 필드 지정
@EntityGraph(attributePaths = "category")
List<Menu> findByPriceGreaterThan(Integer price);
```

> 강의 자료에는 "쿼리 메서드 이름에 `fetch` 키워드를 넣으면 즉시 로딩한다"고 되어 있지만, **쿼리 메서드 이름에는 `Fetch`라는 키워드가 없다.** 위처럼 `@Query`의 `join fetch`나 `@EntityGraph`를 써야 한다. 또 자료에는 "`@ManyToOne`의 기본 `FetchType.LAZY`를 무시한다"고 되어 있는데, `@ManyToOne`의 기본값은 `EAGER`이고, 위 방법들은 `LAZY`로 설정해둔 관계를 **이번 조회에서만** 함께 가져오는 것이다.

**중복 제거 — Distinct**: 1:N이나 N:M 관계를 **"다(N)" 쪽 기준으로 조인**하면 같은 엔티티가 결과에 여러 번 나올 수 있다.

- `findByCategoryName`처럼 메뉴(N)에서 카테고리(1)로 조인하면, 메뉴 하나당 카테고리가 하나이므로 메뉴 행이 중복되지 않는다.
- 반대로 메뉴가 태그 여러 개를 가지는 N:M 관계에서 태그 조건으로 조회하면, 한 메뉴가 조건에 맞는 태그 수만큼 여러 행으로 나올 수 있다.

```java
@Entity
public class Menu {
    @ManyToMany
    @JoinTable(name = "menu_tags",
            joinColumns = @JoinColumn(name = "menu_id"),
            inverseJoinColumns = @JoinColumn(name = "tag_id"))
    private List<Tag> tags = new ArrayList<>();
}

public interface MenuRepository extends JpaRepository<Menu, Long> {
    // 한 메뉴가 여러 태그를 가질 수 있으므로 중복 제거
    List<Menu> findDistinctByTagsName(String tagName);
}
```

```sql
select distinct m1_0.id, m1_0.category_id, m1_0.eng_name, m1_0.kor_name, m1_0.price
from menus m1_0
join menu_tags t1_0 on m1_0.id = t1_0.menu_id
join tags t1_1 on t1_1.id = t1_0.tag_id
where t1_1.name = ?
```

> 자료의 메서드 이름은 `findDistinctByTagName`인데, 쿼리 메서드 이름의 조건은 **엔티티 필드명**을 따라간다. `Menu`의 필드가 `tags`(복수형)라면 `findDistinctByTagsName`이어야 한다. 필드명과 다르면 앱이 시작될 때 `No property 'tag' found for type 'Menu'` 에러가 난다.

이처럼 쿼리 메서드 이름에 연관 필드와 키워드를 조합하면, Spring Data JPA가 조인을 포함한 SQL을 만들어줘서 복잡한 데이터 접근 로직을 간결하게 처리할 수 있다. 다만 조인 조건이 복잡해지거나 fetch join이 필요해지면 `@Query`(JPQL)로 넘어가는 것이 자연스럽다.
