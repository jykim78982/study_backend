# JPA 엔티티 상속 매핑 오답노트

### 1. @MappedSuperclass의 역할

**문제**: `@MappedSuperclass`에 대한 설명으로 옳은 것은?

1. 다중 상속을 지원하여 여러 엔티티를 동시에 상속할 수 있다.
2. 공통 매핑 정보를 상속하지만 자체적으로 테이블을 갖지 않는다.
3. 독립된 테이블로 관리되는 엔티티이다.
4. JPA에서 상속 전략을 자동으로 적용하는 어노테이션이다.

**정답: 2번**

여러 테이블에 공통으로 들어가는 컬럼이 있다. `created_at`(등록일시), `updated_at`(수정일시), `created_by`(작성자) 같은 것들이다. 이 필드를 모든 엔티티 클래스마다 일일이 쓰면 중복이 된다. 이때 **공통 필드와 그 매핑 정보만 부모 클래스에 모아두고, 자식 엔티티가 상속해서 쓰게** 해주는 어노테이션이 `@MappedSuperclass`다.

- **테이블이 안 생긴다**: 이 어노테이션이 붙은 클래스는 엔티티(`@Entity`)가 아니다. 그래서 이 클래스 이름으로 된 테이블은 만들어지지 않는다.
- **컬럼만 물려준다**: 자식 엔티티가 상속하면, 부모가 가진 필드가 **자식 엔티티의 테이블에 컬럼으로** 포함된다.

```java
// 공통 매핑 정보를 모아둔 부모 클래스
@Getter
@MappedSuperclass                       // 테이블로 생성되지 않음
public abstract class BaseTimeEntity {

    @CreationTimestamp                  // 저장될 때 Hibernate가 현재 시각을 채움
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @UpdateTimestamp                    // 수정될 때마다 현재 시각으로 갱신
    private LocalDateTime updatedAt;
}

// 자식 엔티티 (실제 members 테이블이 생성됨)
@Entity
@Table(name = "members")
public class Member extends BaseTimeEntity {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;
}
```

```sql
-- 결과: 부모 필드까지 포함된 테이블 하나만 생긴다 (base_time_entity 테이블은 없음)
create table members (
    id bigint generated by default as identity,
    name varchar(255),
    created_at timestamp(6),
    updated_at timestamp(6),
    primary key (id)
);
```

> **보충**
> - **`abstract`로 선언한다**: `BaseTimeEntity`는 혼자서 객체로 만들어 쓸 일이 없으므로 추상 클래스로 두는 것이 일반적이다.
> - **엔티티가 아니라서 조회 대상도 아니다**: `em.find(BaseTimeEntity.class, 1L)`이나 JPQL `select b from BaseTimeEntity b`는 쓸 수 없다. 조회는 항상 자식 엔티티(`Member`)로 한다.
> - **값은 자동으로 채워지지 않는다**: 필드만 선언해서는 `createdAt`이 `null`로 저장된다. 위처럼 Hibernate의 `@CreationTimestamp`/`@UpdateTimestamp`를 쓰거나, Spring Data JPA의 Auditing(`@EnableJpaAuditing` + `@EntityListeners(AuditingEntityListener.class)` + `@CreatedDate`/`@LastModifiedDate`)을 써야 값이 들어간다. `created_by` 같은 작성자 정보는 Auditing의 `@CreatedBy`로 채운다.
> - **컬럼 이름**: 필드명 `createdAt`은 Spring Boot의 기본 네이밍 전략에 따라 `created_at` 컬럼이 된다.

**1번이 오답인 이유**: 자바는 클래스 **다중 상속이 불가능**하다(`extends`는 하나만). `@MappedSuperclass`도 자바 클래스 상속을 그대로 이용하므로, 여러 부모를 동시에 상속할 수 없다. 인터페이스는 여러 개 구현할 수 있지만, 인터페이스에는 필드 매핑 정보를 담을 수 없어 이 용도로 쓸 수 없다.

> 이 단일 상속 제약 때문에, 모든 엔티티가 공통 부모(`BaseEntity`)를 상속하면 나중에 엔티티끼리 다른 상속이 필요해졌을 때 상속 자리가 이미 차 있다는 문제가 생긴다. 상속 자리를 비워두고 싶다면 공통 필드를 `@Embeddable` 클래스로 만들어 각 엔티티에 `@Embedded`로 넣는 **조합(composition)** 방식도 있다.

**3번이 오답인 이유**: 정반대의 설명이다. `@MappedSuperclass`는 엔티티가 아니고, 독립된 테이블에 매핑되지 않는다. 부모 클래스도 **엔티티이면서 테이블을 가져야** 한다면 부모에 `@Entity`와 `@Inheritance`를 붙이는 **상속 관계 매핑**을 써야 한다.

**4번이 오답인 이유**: JPA의 상속 관계 매핑 전략은 `@Inheritance(strategy = ...)`가 담당한다. `@MappedSuperclass`는 DB의 상속 구조와는 관계없이, 객체 쪽에서 **공통 필드를 물려주기 위한 도구**일 뿐이다.

**@MappedSuperclass vs @Inheritance 비교**

| | `@MappedSuperclass` | `@Entity` + `@Inheritance` |
|---|---|---|
| 부모가 엔티티인가 | ❌ | ⭕ |
| 부모 테이블 | 없음 | 전략에 따라 있음 |
| 부모 타입으로 조회 | 불가 | 가능 (`select i from Item i`로 자식까지 조회) |
| 목적 | 공통 **컬럼**(등록일, 수정일 등) 재사용 | 데이터 자체의 **상속 관계**(상품 → 음료·디저트) 표현 |

`@Inheritance`의 전략은 세 가지다.

| 전략 | 테이블 구조 |
|---|---|
| `JOINED` | 부모 테이블 + 자식 테이블을 따로 두고 조인으로 합쳐 조회 |
| `SINGLE_TABLE` | 부모·자식을 테이블 하나에 모두 넣고 구분 컬럼(`dtype`)으로 종류를 나눔 (기본값) |
| `TABLE_PER_CLASS` | 자식마다 부모 컬럼까지 포함한 독립 테이블. 부모 타입 조회가 비효율적이라 잘 안 씀 |

**한 줄 요약**: `@MappedSuperclass`는 엔티티도 테이블도 아닌 "공통 필드 제공용 부모 클래스"로, 상속받은 자식 엔티티의 테이블에 컬럼만 물려준다. 부모 자체를 테이블로 관리하는 상속 전략은 `@Inheritance`의 역할이다.
