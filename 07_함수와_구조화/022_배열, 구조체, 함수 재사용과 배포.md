# 배열, 구조체, 함수 재사용과 배포

## 1. 배열 — 같은 값을 순차적으로 놓아둔 공간

배열은 **같은 타입의 값을 순서대로 나란히 배치해둔 공간**이다.

### C의 접근 방식 — 주소를 직접 연산

C에서는 배열 원소에 접근할 때 **주소를 직접 계산**해서, 다음 주소로 이동하며 값을 넣는 방식을 쓴다.

```c
*(nums + 0) = 10;
*(nums + 1) = 20;
```

### Java의 접근 방식 — 인덱스 표기

```java
nums[0] = 10;
nums[1] = 20;
```

Java의 `[]` 표기는 내부적으로 결국 같은 주소 연산이지만, **개념을 잡기가 훨씬 쉽다** — 표현이 사람이 생각하는 방식("몇 번째 칸")에 더 가까워졌기 때문이다.

### 배열이 왜 필요한가

- **값의 일괄 관리**: 같은 종류의 값 여러 개를 하나의 이름으로 묶어서 관리할 수 있다.
- **메모리를 이용한 수정**: 각 값이 순서대로 이어진 메모리 공간에 있으므로, 인덱스(위치)만 알면 바로 찾아가서 값을 바꿀 수 있다.

## 2. 구조체 — 값들을 묶어서 표현한 것

**구조**란 여러 값을 묶어서 표현한 것이다.

- 다뤄야 할 값이 많아지면 → **수납(정리)**이 필요해진다
- 이때 값들을 그냥 흩어두지 않고, **묶어서 하나의 개체**로 표현하는 것이 구조체다
- 구조체는 **속성·특징들로 표현되는 묶음**이라고 볼 수 있다 — 데이터를 사람이 이해하기 쉬운 단위로 묶어서 사용하는 것

### 구조화

- 여러 속성·필드·컬럼으로 묶은 데이터를 위주로 사용하는 것이 구조화다
- **모든 데이터는 결국 구조화해서 사용해야 한다** — 흩어진 값 여러 개보다, 묶인 하나의 개체가 다루기 쉽다
- 구조체는 결국 **인간이 사물을 표현하는 방식(속성들의 묶음)을 코드로 그대로 가져온 것**이다

## 3. 함수 — 왜 쓰는가

- 코드가 길어지면 → 잘라서 함수로 만든다 → **가독성이 좋아지고 복잡도(난이도)가 낮아진다**
- 반복되는 부분도 함수로 잘라서 정의해두면, 다음에 또 필요할 때 **재사용**할 수 있다

### 함수가 호출될 때 — 매개변수의 공간

- **값 변수**를 넘기면: 그 값을 담을 **새 공간을 마련**한다 (복사본이 생김)
- **참조 변수**를 넘기면: 가리키는 대상을 위한 **새 공간을 마련하지 않는다** (원본 실체를 그대로 같이 가리킴)

이 차이는 [[021_함수 매개변수 전달 방식(Code1 vs Code2)]]에서 다룬 "값이 복사되느냐, 주소가 복사되느냐"와 같은 이야기다.

## 4. 코드 재사용과 배포

### 재생성 vs 재사용

- **재생성**: 코드 **파일(소스)**을 가져다가 다시 쓰는 것
- **재사용**: 이미 **배포된 실행 코드(컴파일된 결과물)**를 그대로 가져다 쓰는 것

재사용이 많아질수록, 다음 버전은 매번 새로 만들지 않아도 되니 **더 가볍고 빠르게** 만들 수 있다.

### main 함수가 있는 파일은 재사용할 수 없다

`main`을 가진 파일은 그 자체로 **독립 실행 프로그램의 진입점**이라서, 남이 부품처럼 가져다 쓸 대상이 되지 못한다. 반대로 `main`이 없는 파일은 "실행되는 앱"이 아니라 "다른 앱이 가져다 쓰는 부품" 후보가 된다.

**예: `Code.java`(진입점)와 `Menu.java`(부품)**

```
Code.java  --(컴파일)-->  Code.class   (main 있음 — 실행 진입점)
Menu.java  --(컴파일)-->  Menu.class   (main 없음 — 재사용 후보)
```

여기서 `Menu.class`가 **실제로** 재사용 가능해지는지는, 컴파일만으로 끝나는 게 아니라 **어떻게 배포(패키징)되는지에 달려 있다** — 이어지는 배포 부분에서 다룬다.

### 배포 — jar로 묶기

컴파일된 결과물을 배포할 때는 일반적으로 **압축한 뒤 `.jar` 확장자**로 배포한다.

1. zip 유틸리티로 `Code.class`, `Menu.class` 등을 `app.zip`으로 압축
2. 확장자를 `.zip` → `.jar`로 변경 → `app.jar`
3. 그 안에는 **메타데이터 파일**(예: 어떤 클래스가 진입점인지 알려주는 `MANIFEST.MF`)이 추가로 필요할 수도 있다

### 재사용하려면 따로 jar로 묶어야 한다

`Code.class`와 `Menu.class`가 **같이** `app.jar`로 묶여 배포되면, 그 `app.jar`는 실행용 앱 하나로 취급된다 — 다른 프로그램이 그 안에서 `Menu.class`만 콕 집어서 가져다 쓸 수는 없다. `app.jar`는 "실행하는 대상"이지 "부품을 꺼내 쓰는 창고"가 아니기 때문이다.

그래서 `Menu.class`를 진짜로 재사용하려면, `Code.class`와 묶지 않고 **`Menu.class`만 따로 `Menu.jar`로 압축**해둬야 한다. 그래야 다른 프로그램이 `Menu.jar`를 클래스패스에 추가해서 그 안의 `Menu` 클래스를 부품처럼 가져다 쓸 수 있다.
