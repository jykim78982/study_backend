# 세션을 이용한 로그인 상태 유지와 로그아웃 구현

지난 자료에서는 쿠키를 사용해 클라이언트를 식별하고 간단한 설정값을 기억하는 방법을 알아보았다. 하지만 쿠키에 로그인 정보나 비밀번호 같은 중요한 정보를 직접 담아 주고받는 것은 매우 위험하다.

이번 자료에서는 쿠키의 보안상 한계를 극복하고, 서버가 사용자의 접속 상태를 안전하게 관리하는 **세션(Session)**의 개념과 이를 통한 로그인·로그아웃 구현 방법을 다룬다.

## 1. 쿠키의 한계와 세션의 필요성

웹은 요청과 응답이 끝나면 연결을 끊어 버리는 특징이 있다. 따라서 로그인한 사용자가 다른 페이지로 이동해도 서버는 이 사용자가 로그인했던 사용자인지 알지 못한다.

이 문제를 해결하기 위해 로그인 성공 여부를 쿠키에 저장해 보낼 수도 있다. 하지만 클라이언트에 저장되는 쿠키는 다음과 같은 위험을 가진다.

- **데이터 위변조 가능성**: 사용자가 브라우저 개발자 도구에서 쿠키 값을 임의로 변경할 수 있다. 예를 들어 `role=USER`를 `role=ADMIN`으로 바꾸기만 하면 관리자가 된다.
- **민감 정보 노출**: 쿠키에 사용자 아이디나 권한 정보를 직접 담으면 네트워크 도청이나 악성 스크립트에 의해 정보가 유출될 수 있다.

이러한 문제를 해결하기 위해 등장한 개념이 바로 **세션(Session)**이다.

```
[클라이언트(브라우저)]                                   [서버]
        │ 1. 로그인 요청 (ID/PW)                         │
        │ ────────────────────────────────────────────▶ │ 인증 성공
        │                                               │ 세션 생성 (메모리에 사용자 정보 저장)
        │ 2. 응답 (쿠키: JSESSIONID)                     │
        │ ◀──────────────────────────────────────────── │
        │ 3. 다음 요청 (JSESSIONID)                      │
        │ ────────────────────────────────────────────▶ │ 세션 ID로 메모리 조회
        │ 4. 응답 (인증된 사용자 처리)                    │
        │ ◀──────────────────────────────────────────── │
```

세션은 중요 정보(사용자 식별 정보)를 클라이언트가 아닌 **서버 메모리**에 안전하게 저장하도록 한다. 브라우저가 들고 다니는 것은 의미 없는 무작위 문자열인 **세션 ID**뿐이다.

원래 세션이란 용어는 어떤 공간이나 서비스를 이용할 수 있도록 허락받은 **'기간'**을 의미한다. 웹 서버에서 이 용어를 사용하는 이유 역시 사용자 정보를 서버에 저장할 때 해당 저장 공간을 일정 기간 동안만 유지하기 때문이다.

그런데 흔히 세션을 서버 저장소 자체로 표현하여 "세션에 저장했다"라거나 "세션 값"이라고 말하는 경우도 있는데, 이는 '세션 유효 기간 동안 서버의 세션 메모리 영역에 데이터를 보관한다'는 복잡한 과정을 줄여서 설명한 용어이다.

```
[요청 1] ──▶ 세션 생성 (만료 시간 설정: 30분)
               │
               │ 30분 이내
               ▼
[요청 2] ──▶ 만료 시간 리셋 (다시 30분 연장)
               │
               │ 30분 경과 (새 요청 없음)
               ▼
            세션 자동 폐기 (Timeout)
```

사용자가 웹 서버에 데이터를 저장하면 **만료 시간(Timeout)**이 설정된다. 이 기간 안에 새로운 요청이 오지 않으면 서버는 해당 사용자의 데이터를 자동으로 폐기한다. 만약 만료 시간이 지나기 전에 요청이 들어오면 만료 시간은 다시 초기화된다.

> **추가 설명 — 만료 시간 설정**: 스프링 부트(내장 톰캣)의 기본 만료 시간은 **30분**이다. `application.yml`에서 바꿀 수 있다.
>
> ```yaml
> server:
>   servlet:
>     session:
>       timeout: 20m   # 단위 생략 시 초. 1분 미만은 1분으로 처리된다
> ```
>
> 코드에서 세션마다 따로 정하려면 `session.setMaxInactiveInterval(초)`를 쓴다. 이름 그대로 **"요청이 없는(inactive) 시간"의 최댓값**이라, 요청이 올 때마다 다시 세는 것이다.

## 2. 서버 저장소 4가지

서블릿이나 스프링 웹 서버 환경에서 데이터를 저장하는 데 사용되는 저장 객체는 다음처럼 크게 4가지가 있다.

- 페이지 내에서만 사용하는 **PageContext** 객체
- Forward 관계에서 사용하는 두 서블릿 사이에서만 사용하는 **Request** 객체
- 모든 경로에서 한 명의 사용자만 개인적으로 사용하는 **Session** 객체
- 모든 경로에서 모든 사용자가 함께 사용하는 **ServletContext**(Application) 객체

> 원문 바로잡기 — 원문에서는 네 번째도 "Session 객체"라고 적혀 있는데, 모든 사용자가 함께 쓰는 저장소는 **ServletContext**(JSP에서는 `application`)다. 오타로 보인다.

이 객체들에 데이터를 저장하는 사용 방법은 모두 동일하지만, 사용 범위와 생명주기가 서로 다르다.

| 저장소(스코프) | 사용 범위 | 생명주기 |
|---|---|---|
| PageContext (page) | JSP 한 페이지 안 | 페이지 처리가 끝나면 사라진다 |
| Request (request) | 요청 하나(forward로 넘긴 서블릿·JSP까지) | 응답이 나가면 사라진다 |
| Session (session) | 한 사용자의 모든 요청 | 만료 시간이 지나거나 `invalidate()`하면 사라진다 |
| ServletContext (application) | 모든 사용자의 모든 요청 | 웹 애플리케이션이 내려갈 때 사라진다 |

```java
request.setAttribute("key", value);          // 요청 영역
session.setAttribute("key", value);          // 세션 영역
servletContext.setAttribute("key", value);   // 애플리케이션 영역
// 꺼낼 때는 모두 getAttribute("key"), 지울 때는 removeAttribute("key")
```

특히 Session 객체는 특정 사용자 전용 데이터를 안전하게 다루기 위한 독특한 메커니즘을 가진다. Session 객체에 데이터를 저장하면 서버는 클라이언트를 식별하기 위한 고유 키(**JSESSIONID**)를 생성하여 쿠키로 응답한다. 브라우저는 이후 요청마다 이 쿠키를 함께 전송하므로, 서버는 각 사용자에게 독립된 전용 저장 공간을 제공할 수 있게 된다.

> **추가 설명 — 정확한 발급 시점**: JSESSIONID는 `setAttribute()`로 값을 넣을 때가 아니라 **세션 객체가 처음 만들어질 때**(`request.getSession()`이 처음 호출될 때) 발급된다. 아래 예제에서는 둘이 바로 이어져 있어 같은 시점처럼 보일 뿐이다. 그래서 값을 꺼내기만 하려고 `getSession()`을 호출해도 세션이 새로 생긴다. 스프링 시큐리티를 켜면 로그인 페이지를 여는 순간 CSRF 토큰을 세션에 담기 때문에, 로그인 전에도 JSESSIONID가 생긴다.

그럼 이제 Session 객체를 이용하는 방법을 알아보기로 하자.

## 3. AuthController 확장: 로그인 성공 시 세션 생성

이전 AuthController에서 로그인 검증이 성공했을 때 `HttpSession`을 생성하고 로그인 정보를 저장하도록 로직을 수정한다.

**LoginRequest.java 파일**

```java
package com.example.security.dto.auth;

import lombok.Data;
import lombok.NoArgsConstructor;

@Data
@NoArgsConstructor
public class LoginRequest {
    private String username;
    private String password;
}
```

> **추가 설명 — `@Data`와 비밀번호**: `@Data`는 `toString()`도 만들어 주는데, 여기에 `password`가 그대로 찍힌다. `log.info("{}", loginRequest)` 한 줄로 비밀번호가 로그에 남을 수 있으니, 비밀번호를 담는 DTO는 `@Getter @Setter`만 쓰거나 해당 필드에 `@ToString.Exclude`를 붙인다.

**AuthController.java 파일**

```java
package com.example.security.controller;

import com.example.security.dto.auth.LoginRequest;
import com.example.security.service.UserService;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpSession;
import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.ModelAttribute;

@Controller
public class AuthController {

    private final UserService userService;

    public AuthController(UserService userService) {
        this.userService = userService;
    }

    @PostMapping("/login")
    public String login(@ModelAttribute LoginRequest loginRequest, HttpServletRequest request) {
        // 1. 사용자 검증
        boolean isAuthenticated = userService.authenticate(loginRequest.getUsername(), loginRequest.getPassword());

        if (!isAuthenticated) {
            return "redirect:/login?error";
        }

        // 2. 세션 생성 (기존 세션이 있으면 반환, 없으면 신규 생성)
        HttpSession session = request.getSession();

        // 3. 세션에 로그인 사용자 정보 저장
        session.setAttribute("loginUser", loginRequest.getUsername());

        return "redirect:/";
    }
}
```

`request.getSession()`을 호출하면 서버는 내부적으로 JSESSIONID 쿠키가 넘어왔는지 확인한다. 쿠키가 없거나 유효하지 않다면 새로운 세션을 생성하고 응답 헤더에 JSESSIONID 쿠키를 실어 보낸다. `session.setAttribute()`를 통해 세션 공간에 원하는 객체나 정보를 저장할 수 있다.

| 호출 | 세션이 있을 때 | 세션이 없을 때 |
|---|---|---|
| `request.getSession()` / `getSession(true)` | 기존 세션 반환 | **새로 만든다** |
| `request.getSession(false)` | 기존 세션 반환 | `null` 반환 (만들지 않음) |

컨트롤러 매개변수에 `HttpSession session`을 선언해도 된다. 스프링이 `request.getSession()`과 같은 방식(없으면 생성)으로 넣어 준다.

로그인 전에는 개발자 도구의 Application → Cookies에 아무것도 없지만, 로그인을 한 후에 Session 객체에 값을 저장하면 세션 ID가 `JSESSIONID` 쿠키로 저장된다.

> **추가 설명 — 주소창에 `;jsessionid=...`가 붙는 이유**: 로그인 직후 주소가 `localhost:8080/;jsessionid=C7AB30E7...`처럼 바뀌는 경우가 있다. 세션을 처음 만든 응답에서는 서버가 **브라우저가 쿠키를 받아 줄지 아직 모르기 때문에**, 쿠키와 함께 리다이렉트 URL에도 세션 ID를 붙여 보내는 것이다(URL 재작성). 다음 요청에 쿠키가 따라오면 서버는 쿠키가 된다는 걸 알고 더 이상 붙이지 않는다.
>
> 세션 ID가 주소에 드러나면 링크 공유, 브라우저 기록, 서버 로그, `Referer` 헤더로 새어 나갈 수 있어 위험하다. 쿠키로만 주고받도록 설정해 두는 것이 좋다.
>
> ```yaml
> server:
>   servlet:
>     session:
>       tracking-modes: cookie
> ```
>
> 스프링 시큐리티는 기본으로 URL에 세션 ID를 붙이지 않고, `;`이 들어간 요청 주소도 거부한다.

> **추가 설명 — 로그인 성공 시 세션 ID 바꾸기**: 위 코드는 로그인 전에 이미 세션이 있었다면 **그 세션을 그대로** 쓴다. 공격자가 미리 받아 둔 세션 ID를 피해자에게 심어 두면, 피해자가 로그인한 뒤 공격자도 같은 ID로 로그인된 상태가 된다(세션 고정 공격). 그래서 로그인에 성공하면 세션 ID를 새로 바꾼다.
>
> ```java
> HttpSession session = request.getSession();
> request.changeSessionId();   // 저장된 값은 그대로 두고 ID만 새로 발급
> session.setAttribute("loginUser", loginRequest.getUsername());
> ```
>
> 스프링 시큐리티는 로그인에 성공하면 이 처리를 자동으로 한다.

## 4. HomeController 작성: 로그인 상태 확인

> 원문 바로잡기 — 원문에서는 이 절의 번호도 "3."으로 앞 절과 겹쳐 있어, 이후 번호를 하나씩 밀어서 적었다.

서버 메모리에 보관된 세션 정보를 읽어 와 로그인한 사용자와 비로그인 사용자가 볼 화면을 다르게 처리할 수 있다. 스프링 MVC가 제공하는 `@SessionAttribute` 애노테이션을 사용하면 세션에 저장된 값을 손쉽게 가져올 수 있다.

### 4-1. 컨트롤러 구현

```java
package com.example.security.controller;

import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.SessionAttribute;

@Controller
public class HomeController {

    @GetMapping("/")
    public String home(
            @SessionAttribute(name = "loginUser", required = false) String loginUser,
            Model model) {

        // 세션에 저장된 사용자 정보가 없다면 비로그인 상태로 간주
        if (loginUser == null) {
            return "index";
        }

        // 세션에 정보가 있다면 모델에 전달하여 로그인 화면 구성
        model.addAttribute("username", loginUser);
        return "index";
    }
}
```

`required = false` 옵션을 지정하면 세션이 없거나 `loginUser` 속성이 없어도 에러가 발생하지 않고 `null`이 들어오게 된다.

> **추가 설명 — `required`를 빼면**: `@SessionAttribute`의 기본값은 `required = true`다. 로그인 전이라 세션에 `loginUser`가 없으면 **400 Bad Request**(Missing session attribute)가 나서 메인 페이지가 열리지 않는다. 로그인 전에도 열려야 하는 페이지에는 반드시 `required = false`를 붙인다. 또 `@SessionAttribute`는 세션을 **새로 만들지 않는다.** 그래서 비로그인 사용자가 메인 페이지를 열어도 JSESSIONID가 생기지 않는다.

> **추가 설명 — 이름이 다른 이유**: 세션에는 `loginUser`라는 이름으로 넣었고, 뷰에는 `username`이라는 이름으로 내려 준다. 세션 속성 이름과 모델 속성 이름은 서로 상관이 없으니, 타임리프에서는 **모델에 담은 이름**(`username`)으로 꺼내야 한다. 덧붙여 `model.addAttribute()`에 `null`을 넣어도 뷰에서는 없는 값과 똑같이 보이므로, 위 코드의 `if` 없이 바로 `model.addAttribute("username", loginUser)`만 써도 결과는 같다.

### 4-2. index.html 뷰 연동

```html
<!DOCTYPE html>
<html xmlns:th="http://www.thymeleaf.org">
<head>
    <meta charset="UTF-8">
    <title>메인 페이지</title>
</head>
<body>
    <h1>메인 페이지</h1>

    <!-- 비로그인 사용자에게 보이는 영역 -->
    <div th:if="${username == null}">
        <p>로그인이 필요합니다.</p>
        <a href="/login">로그인 하러 가기</a>
    </div>

    <!-- 로그인한 사용자에게 보이는 영역 -->
    <div th:if="${username != null}">
        <p><strong th:text="${username}">사용자</strong>님 환영합니다!</p>
        <form action="/logout" method="post">
            <button type="submit">로그아웃</button>
        </form>
    </div>
</body>
</html>
```

이제 로그인에 성공하면 페이지를 이동하거나 새로고침을 하더라도 서버가 JSESSIONID를 통해 세션을 계속 찾아내므로 로그인 상태가 유지된다.

> **추가 설명 — 뷰에서 세션을 바로 꺼낼 수도 있다**: 타임리프에서는 `${session.loginUser}`처럼 세션 속성을 바로 읽을 수도 있다(타임리프 3.1부터 `#session` 같은 객체는 빠졌지만 `session.` 접두사는 쓸 수 있다). 하지만 그러면 뷰가 세션 속성 이름까지 알아야 한다. 이 예제처럼 **컨트롤러가 세션에서 꺼내 모델에 담아 주면**, 뷰는 모델만 보고 세션을 다루는 일은 컨트롤러가 맡게 되어 역할이 깔끔하다.

## 5. 로그아웃 처리와 세션 무효화

로그아웃은 서버에 저장된 세션 정보를 완전히 삭제하여 접속 상태를 끊는 과정이다. 세션을 무효화하면 서버는 해당 세션 ID와 매핑된 메모리를 제거한다.

AuthController에 로그아웃 요청을 처리하는 메서드를 추가한다.

```java
    @PostMapping("/logout")
    public String logout(HttpServletRequest request) {
        // false 옵션: 세션이 존재하면 가져오고, 없으면 null 반환 (새로 생성하지 않음)
        HttpSession session = request.getSession(false);

        if (session != null) {
            // 세션 및 저장된 모든 데이터 완전 삭제
            session.invalidate();
        }

        return "redirect:/";
    }
```

`session.invalidate()`가 호출되면 서버 내의 해당 세션 정보가 즉시 파기된다. 이후 클라이언트가 기존 JSESSIONID를 가지고 다시 요청을 보내더라도 서버는 해당 세션을 찾을 수 없으므로 비로그인 상태로 처리하게 된다.

> **추가 설명 — 왜 `getSession(false)`인가**: 로그아웃은 세션을 **없애려는** 요청인데, `getSession()`을 쓰면 세션이 없을 때 오히려 새로 만들어 버린다. 그래서 있으면 가져오고 없으면 아무것도 하지 않는 `getSession(false)`를 쓴다. 로그아웃처럼 **읽거나 지우기만 하는 곳**에서는 항상 `false`를 쓰는 습관을 들인다.

> **추가 설명 — 브라우저의 JSESSIONID 쿠키는 남는다**: `invalidate()`는 서버의 세션만 지운다. 브라우저에는 옛 JSESSIONID 쿠키가 남아 있지만, 서버에서 찾을 수 없으니 의미 없는 값이 된다. 다음에 세션을 만들 때 새 ID로 덮어쓴다. 쿠키까지 바로 지우고 싶다면 이름·경로가 같은 쿠키를 `Max-Age=0`으로 내려 보낸다.

> **추가 설명 — 왜 POST인가**: 로그아웃을 GET으로 만들면 다른 사이트가 `<img src="https://우리사이트/logout">` 한 줄만 심어도 그 페이지를 본 사용자가 자기도 모르게 로그아웃된다(CSRF). 상태를 바꾸는 요청은 GET으로 만들지 않는다. 그래서 뷰에서도 링크가 아니라 `<form method="post">` 버튼으로 로그아웃을 보낸다.

## 6. 주의할 사항: 접근 제어(권한 검사)의 한계

지금까지 세션을 이용하여 로그인 상태를 유지하고 화면에 반영하는 방법을 다루었다.

그러나 이 방식만으로는 보안상 한계가 존재한다. 컨트롤러에서 단순히 로그인 상태를 확인하여 뷰를 다르게 보여 주는 것일 뿐, 로그인하지 않은 사용자가 특정 URL(예: `/admin`, `/dashboard`)을 주소창에 직접 입력하여 들어오는 요청 자체를 강제로 차단하지는 못하기 때문이다.

URL에 대한 직접적인 접근 제어나 권한 검사는 각 컨트롤러마다 일일이 작성하는 대신, 요청이 컨트롤러에 도달하기 전에 통과하는 **필터(Filter)**나 **인터셉터(Interceptor)** 단계에서 처리해야 한다. 다음 자료에서는 이러한 한계를 극복하기 위해 서블릿 필터를 활용한 접근 제어 구현을 다룬다.

> **추가 설명 — 필터와 인터셉터**:
>
> | 구분 | 필터(Filter) | 인터셉터(HandlerInterceptor) |
> |---|---|---|
> | 소속 | 서블릿 표준 | 스프링 MVC |
> | 실행 위치 | `DispatcherServlet` **앞** | `DispatcherServlet` 안, 컨트롤러 **앞** |
> | 막을 수 있는 범위 | 정적 파일까지 포함한 모든 요청 | 컨트롤러로 가는 요청 |
> | 대표 사용처 | 인증·인가, 인코딩, CORS — **스프링 시큐리티** | 로그인 확인, 로깅처럼 컨트롤러 정보가 필요한 공통 처리 |
>
> 인증·인가를 직접 만든다면 둘 다 쓸 수 있지만, 실무에서는 필터 기반인 **스프링 시큐리티**를 쓴다. 지금까지 세션에 직접 넣고 꺼내던 로그인 정보도 스프링 시큐리티에서는 `SecurityContext`가 세션에 저장해 관리한다.
