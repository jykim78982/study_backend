# 서블릿 필터와 스프링 보안 필터 체인의 이해

앞 자료에서 말한 것처럼 스프링 보안은 **서블릿 필터(Servlet Filter)**를 이용해 구현되어 있다.

물론 우리가 쓸 필터는 서블릿 컨테이너에 담긴 필터가 아니라 **스프링 IoC 컨테이너에 담긴 필터**다. 하지만 실행 방식이나 필요성은 똑같다.

그래서 이번에는 필터가 무엇이고 어떻게 동작하는지 이해하는 시간을 갖는다. 서블릿에서 필터를 써 본 적이 있다면 이 자료는 건너뛰어도 된다.

서블릿 컨테이너의 필터 요청이 스프링 IoC 컨테이너에 담긴 필터로 이어지는 원리(`DelegatingFilterProxy` → `FilterChainProxy`)가 낯설다면 앞 자료를 다시 참고한다.

## 1. 서블릿 필터란 무엇인가

서블릿 필터는 클라이언트의 HTTP 요청이 최종 서블릿(스프링의 경우 `DispatcherServlet`)에 도착하기 **전**이나, 서블릿이 응답을 보낸 **후**에 요청과 응답을 **가로채서** 특정 작업을 하는 객체다.

웹 애플리케이션에서는 주로 다음 작업에 필터를 쓴다.

| 용도 | 예 |
|---|---|
| 요청/응답 데이터 인코딩 설정 | 모든 요청의 문자 인코딩을 UTF-8로 일괄 변환 |
| 보안 및 인증 검사 | 로그인 여부 확인, API 토큰 검증, 권한 확인 |
| 로깅 및 감사(Audit) | 요청 시간, 클라이언트 IP, 요청 URL 등 접근 기록 |
| XSS 및 보안 공격 방어 | 입력값의 악성 스크립트 태그 걸러내기 |

## 2. 왜 필터를 사용하는가

로그 저장, 인코딩, 로그인 여부 확인, 접근 권한 검사 같은 작업은 **거의 모든 컨트롤러 메서드에서 공통으로** 필요하다. 이런 로직을 컨트롤러마다 직접 쓰면 코드가 중복되고 관리하기 어려워진다.

```
[클라이언트] -> [서블릿 필터] -> [DispatcherServlet] -> [컨트롤러]
```

필터를 쓰면 애플리케이션의 **핵심 비즈니스 로직**과 **공통 코드**(로깅, 인코딩, 보안/검증 로직)를 완전히 분리할 수 있다. 요청이 컨트롤러로 가기 전에 공통 검사를 하고, 조건에 맞지 않는 요청은 컨트롤러까지 **도달하지 못하게 미리 차단**할 수 있다.

## 3. 실습 프로젝트 환경 설정

실제로 필터를 만들어서 어떻게 동작하는지 간단히 실습해 본다.

먼저 첨부 파일 `security.zip`의 압축을 풀고 VSCode로 폴더를 연다. 프로젝트 구조는 다음과 같다.

```
security
├─ build.gradle
└─ src/main
   ├─ java/com/example/security
   │  ├─ config
   │  ├─ controller
   │  ├─ filter
   │  ├─ service
   │  └─ SecurityApplication.java
   └─ resources
      ├─ static/css
      ├─ templates
      └─ application.yml
```

`application.yml`을 열고 앞으로 스프링 보안을 다룰 때 쓸 데이터베이스 계정을 설정한다. 데이터베이스가 없으면 별도 문서를 참고한다.

```yaml
spring:
  application:
    name: security
  datasource:
    url: jdbc:postgresql://서버주소:5432/데이터베이스
    username: 계정
    password: "비밀번호"
  jpa:
    hibernate:
      ddl-auto: update
    show-sql: true
    properties:
      hibernate:
        format_sql: true

server:
  port: 8080
```

> **추가 설명 — 설정 항목**: `ddl-auto: update`는 엔티티에 맞춰 테이블을 만들거나 컬럼을 추가해 주는 옵션이다(기존 데이터는 지우지 않는다). `show-sql`과 `format_sql`은 JPA가 실행하는 SQL을 콘솔에 보기 좋게 출력한다. 비밀번호를 큰따옴표로 감싸 두면 특수문자가 들어 있어도 YAML이 문자열로 읽는다.

이제 프로젝트를 실행해서 `http://localhost:8080`에 접속해 랜딩 페이지(Brew & Bloom 카페 소개 화면)가 잘 뜨는지 확인한다.

## 4. 첫 서블릿 필터 구현하기

`jakarta.servlet.Filter` 인터페이스를 구현해서, 요청과 응답이 지나가는 과정을 로그로 남기는 기본 필터를 만든다. 위치는 `filter` 패키지의 `FirstFilter.java`다.

**FirstFilter.java**

```java
package com.example.security.filter;

import jakarta.servlet.*;
import jakarta.servlet.http.HttpServletRequest;
import java.io.IOException;

import org.springframework.stereotype.Component;

@Component
public class FirstFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {

        HttpServletRequest httpRequest = (HttpServletRequest) request;
        String requestURI = httpRequest.getRequestURI();

        System.out.println("[FirstFilter] 전처리: 요청 URI -> " + requestURI);

        // 다음 필터 또는 서블릿(Controller) 호출
        chain.doFilter(request, response);

        System.out.println("[FirstFilter] 후처리: 응답 전달 완료 -> " + requestURI);
    }
}
```

> **추가 설명 — 코드 읽기**
>
> | 코드 | 의미 |
> |---|---|
> | `@Component` | IoC에 담는다. 스프링 부트는 IoC에 담긴 `Filter` 객체를 찾아 **모든 URL(`/*`)에 자동으로 등록**한다 |
> | `implements Filter` | 서블릿 필터가 되려면 이 인터페이스의 `doFilter()`를 구현해야 한다 |
> | `(HttpServletRequest) request` | 매개변수 타입은 HTTP 전용이 아닌 `ServletRequest`라서, URI 같은 HTTP 정보를 꺼내려면 형변환한다 |
> | `chain.doFilter()` **위** | 전처리 — 요청이 컨트롤러로 가기 전에 실행 |
> | `chain.doFilter()` **아래** | 후처리 — 컨트롤러가 일을 마치고 응답이 돌아오는 길에 실행 |

부트 프로젝트를 실행하고 메인 페이지를 요청한 뒤 터미널 창을 확인한다.

```
[FirstFilter] 전처리: 요청 URI -> /
[Ljava.lang.String;@4261c237
[FirstFilter] 후처리: 응답 전달 완료 -> /
[FirstFilter] 전처리: 요청 URI -> /css/site.css
[FirstFilter] 후처리: 응답 전달 완료 -> /css/site.css
```

> **추가 설명 — 출력 읽기**
>
> - 전처리와 후처리 사이에 찍힌 `[Ljava.lang.String;@4261c237`은 필터가 아니라 **컨트롤러**가 찍은 출력이다(문자열 배열을 그대로 `println`하면 이렇게 나온다). 필터의 전처리 → 컨트롤러 → 필터의 후처리 순서로 실행된다는 것이 눈에 보인다.
> - `/` 요청이 끝난 뒤 `/css/site.css`가 또 필터를 지난다. 브라우저가 HTML을 받고 그 안에 연결된 CSS를 **별도 요청**으로 가져오기 때문이다. 필터는 페이지 요청뿐 아니라 CSS·이미지 같은 정적 파일 요청에도 모두 실행된다.

이제 `chain.doFilter(request, response)`를 주석 처리하고 재시작한 뒤 다시 페이지를 요청해 본다. 브라우저에는 **빈 화면**만 뜬다.

`chain.doFilter(request, response)`를 호출하지 않으면 다음 필터나 컨트롤러로 요청이 전달되지 않고 흐름이 중단된다.

```
[클라이언트] ──→ [FirstFilter] ──✕──→ [DispatcherServlet] ──→ [컨트롤러]
                     │
                 chain.doFilter() 미호출
                     ↓
               요청 중단/차단 (여기서 바로 응답이 돌아감)
```

> **추가 설명 — 왜 빈 화면인가**: 필터가 다음으로 넘기지도 않고 응답에 아무것도 쓰지도 않았으니, 서버는 **내용이 비어 있는 응답**(상태 코드 200)을 그대로 돌려준다. 컨트롤러가 실행되지 않았으므로 터미널에도 전처리·후처리 로그만 남고 컨트롤러 출력은 없다. 실제 보안 필터는 이렇게 막을 때 6장처럼 **상태 코드와 메시지를 직접 써서** 돌려준다.

그림처럼 `doFilter()`를 호출하지 않으면 서블릿으로 요청이 이어지지 않는다. 그런데 서블릿으로 이어질 거라면 `doServlet()`이어야 할 것 같은데, `doFilter()`를 호출하는 이유는 무엇일까?

앞서 말한 것처럼 필터는 **여러 겹으로** 만들어질 수 있기 때문이다. 다음 장에서 알아보지만 참고 정도로만 보자.

> **추가 설명 — chain.doFilter()의 "다음"**: 필터는 자기 뒤에 무엇이 있는지 모른다. `chain`(필터 체인 객체)이 그 순서를 알고 있다. 그래서 필터는 "체인아, 다음으로 넘겨 줘"라고만 하고, 체인은 뒤에 필터가 남아 있으면 **다음 필터의 `doFilter()`**를, 더 이상 없으면 **서블릿**(`DispatcherServlet`)을 호출한다. 필터 입장에서는 다음이 필터든 서블릿이든 똑같이 `chain.doFilter()` 하나로 넘기면 되는 것이다.

## 5. 여러 개의 필터를 체인으로 연결하기

필터는 하나만 쓰는 것이 아니라 여러 개를 연속으로 배치해서 **필터 체인(Filter Chain)**을 만들 수 있다. 스프링 부트에서는 `FilterRegistrationBean`으로 필터의 등록과 실행 순서를 제어한다.

두 번째 필터를 추가로 만들고 등록 과정을 확인한다.

**SecondFilter.java**

```java
package com.example.demo.filter;

import jakarta.servlet.*;
import jakarta.servlet.http.HttpServletRequest;
import java.io.IOException;
import org.springframework.stereotype.Component;

@Component
public class SecondFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {

        HttpServletRequest httpRequest = (HttpServletRequest) request;
        String requestURI = httpRequest.getRequestURI();

        System.out.println("  [SecondFilter] 전처리: 요청 URI -> " + requestURI);

        chain.doFilter(request, response);

        System.out.println("  [SecondFilter] 후처리: 응답 전달 완료 -> " + requestURI);
    }
}
```

**FilterConfig.java**

```java
package com.example.demo.config;

import com.example.demo.filter.FirstFilter;
import com.example.demo.filter.SecondFilter;
import org.springframework.boot.web.servlet.FilterRegistrationBean;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class FilterConfig {

    @Bean
    public FilterRegistrationBean<FirstFilter> firstFilterRegister() {
        FilterRegistrationBean<FirstFilter> registrationBean = new FilterRegistrationBean<>();
        registrationBean.setFilter(new FirstFilter());
        registrationBean.addUrlPatterns("/*");
        registrationBean.setOrder(1); // 첫 번째 순서 설정
        return registrationBean;
    }

    @Bean
    public FilterRegistrationBean<SecondFilter> secondFilterRegister() {
        FilterRegistrationBean<SecondFilter> registrationBean = new FilterRegistrationBean<>();
        registrationBean.setFilter(new SecondFilter());
        registrationBean.addUrlPatterns("/*");
        registrationBean.setOrder(2); // 두 번째 순서 설정
        return registrationBean;
    }
}
```

`setOrder()`로 **숫자가 작을수록 먼저** 실행되도록 순서를 지정한다.

> 원문 바로잡기 — 패키지 이름: 4장의 `FirstFilter`는 `com.example.security.filter`인데, 5장부터는 `com.example.demo...`로 적혀 있다. 이 실습 프로젝트에서 그대로 따라 한다면 `com.example.security.filter`, `com.example.security.config`처럼 **프로젝트 패키지에 맞춰** 바꿔야 한다. 패키지가 `SecurityApplication`이 있는 패키지 바깥에 있으면 컴포넌트 스캔에 걸리지 않는다.

> 원문 바로잡기 — `@Component`와 `FilterRegistrationBean`을 함께 쓰는 문제: 위 코드는 필터 클래스에 `@Component`를 붙여 둔 채, `FilterConfig`에서 `new FirstFilter()`로 **또 하나** 만들어 등록한다. 스프링 부트는 `@Component`로 IoC에 담긴 필터도 자동 등록하므로, 같은 필터가 **두 번 등록되려고** 한다(이름이 같아서 한쪽 등록이 무시되었다는 로그가 남거나, 설정에 따라 필터가 두 번 실행될 수 있다). 등록 방법은 하나만 고른다.
>
> | 방법 | 할 일 | 순서 지정 |
> |---|---|---|
> | `@Component`만 사용 | 필터 클래스에 `@Component` | 클래스에 `@Order(1)` 같은 어노테이션 |
> | `FilterRegistrationBean` 사용 | 필터 클래스에서 `@Component`를 **뺀다** | `setOrder(1)` — URL 패턴도 함께 지정 가능 |
>
> URL 패턴까지 정해야 한다면 `FilterRegistrationBean` 쪽이 맞다. `@Component`만 쓰면 항상 모든 URL에 걸린다.

> **추가 설명 — 실행 결과 예상**: 순서대로 등록되면 요청 하나에 대해 다음처럼 출력된다. 들어갈 때는 1 → 2 순서, 나올 때는 **2 → 1** 순서다. 체인이 안쪽으로 파고들었다가 거꾸로 빠져나오기 때문이다(양파 껍질 구조).
>
> ```
> [FirstFilter] 전처리: 요청 URI -> /
>   [SecondFilter] 전처리: 요청 URI -> /
>     (컨트롤러 실행)
>   [SecondFilter] 후처리: 응답 전달 완료 -> /
> [FirstFilter] 후처리: 응답 전달 완료 -> /
> ```

## 6. 보안 필터 간접 경험하기 (토큰 검증 및 차단)

스프링 시큐리티가 요청을 검증하고 차단하는 방식을 간접적으로 경험해 보기 위해, HTTP 헤더의 인증 토큰이 맞는지 검사하는 **보안 모의 필터**를 만든다.

**SecurityMockFilter.java**

```java
package com.example.demo.filter;

import jakarta.servlet.*;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;

public class SecurityMockFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {

        HttpServletRequest httpRequest = (HttpServletRequest) request;
        HttpServletResponse httpResponse = (HttpServletResponse) response;

        String authHeader = httpRequest.getHeader("X-AUTH-TOKEN");

        // /admin 경로 진입 시 토큰 검증 수행
        if (httpRequest.getRequestURI().startsWith("/admin")) {
            if (authHeader == null || !authHeader.equals("VALID_TOKEN")) {
                System.out.println("[SecurityMockFilter] 인증 실패: 접근 거부");
                httpResponse.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
                httpResponse.getWriter().write("401 Unauthorized: Invalid or missing token.");
                return; // chain.doFilter를 호출하지 않고 요청 중단
            }
        }

        System.out.println("[SecurityMockFilter] 인증 성공: 통과");
        chain.doFilter(request, response);
    }
}
```

> **추가 설명 — 코드 흐름**
>
> 1. 요청 헤더에서 `X-AUTH-TOKEN` 값을 꺼낸다.
> 2. 요청 URI가 `/admin`으로 시작하면 토큰을 검사한다.
> 3. 토큰이 없거나 `VALID_TOKEN`이 아니면 **상태 코드 401**과 메시지를 응답에 직접 쓰고 `return`한다. `chain.doFilter()`까지 가지 않으므로 컨트롤러는 실행되지 않는다.
> 4. 검사를 통과했거나 `/admin`이 아닌 요청이면 `chain.doFilter()`로 넘긴다.
>
> `/public` 요청은 검사 자체를 하지 않는데도 "인증 성공: 통과"가 찍힌다. 실습용이라 로그를 단순하게 쓴 것이고, 정확히는 "검사 대상 아님 또는 인증 성공 → 통과"라는 뜻이다.

> **추가 설명 — 이 필터는 등록이 필요하다**: `SecurityMockFilter`에는 `@Component`가 없으므로, 이대로는 IoC에 담기지 않아 **실행되지 않는다.** 5장의 `FilterConfig`에 등록 빈을 하나 더 추가해야 한다.
>
> ```java
> @Bean
> public FilterRegistrationBean<SecurityMockFilter> securityMockFilterRegister() {
>     FilterRegistrationBean<SecurityMockFilter> registrationBean = new FilterRegistrationBean<>();
>     registrationBean.setFilter(new SecurityMockFilter());
>     registrationBean.addUrlPatterns("/*");
>     registrationBean.setOrder(3);
>     return registrationBean;
> }
> ```
>
> 이렇게 하면 `addUrlPatterns("/admin/*")`처럼 **URL 패턴으로 대상을 좁히는** 방법도 쓸 수 있다. 그러면 필터 안의 `startsWith("/admin")` 검사 없이도 `/admin`과 `/admin/...` 요청에만 필터가 걸린다(서블릿 규칙상 `/admin/*`는 `/admin` 자체도 포함한다).

**테스트용 Controller**

```java
package com.example.demo.controller;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class TestController {

    @GetMapping("/public")
    public String publicPage() {
        return "누구나 접근 가능한 페이지입니다.";
    }

    @GetMapping("/admin")
    public String adminPage() {
        return "인증된 관리자만 접근 가능한 페이지입니다.";
    }
}
```

### 실행 결과 분석

| 요청 | 필터 동작 | 결과 |
|---|---|---|
| `GET /public` | 토큰 검사 없이 통과 | 컨트롤러의 정상 응답 수신 |
| `GET /admin` (헤더 없음) | 검증 실패, `chain.doFilter()` 호출 안 함 | 컨트롤러에 도달하지 않고 **401 Unauthorized** 응답 |
| `GET /admin` (`X-AUTH-TOKEN: VALID_TOKEN`) | 인증 통과 | 컨트롤러 실행 |

> **추가 설명 — 직접 확인하기**: 브라우저 주소창으로는 헤더를 넣기 어려우므로 터미널에서 `curl`로 확인한다. `-i`는 응답 상태 코드와 헤더까지 보여 주는 옵션이고, `-H`는 요청 헤더를 넣는 옵션이다.
>
> ```bash
> curl -i http://localhost:8080/public
> curl -i http://localhost:8080/admin
> curl -i -H "X-AUTH-TOKEN: VALID_TOKEN" http://localhost:8080/admin
> ```

이처럼 스프링 시큐리티도 내부적으로 `SecurityFilterChain`에 수많은 보안 필터를 등록해 두고, 비즈니스 로직에 요청이 도달하기 **전에** 인증과 인가를 검사해 차단하는 **같은 원리**로 동작한다.

> **추가 설명 — 모의 필터와 스프링 시큐리티 비교**
>
> | 모의 필터 | 스프링 시큐리티 |
> |---|---|
> | 필터 하나가 URL 검사와 토큰 검사를 모두 함 | 역할별 필터 여러 개(CSRF 검사, 로그인 인증, 토큰 인증, 인가 검사 등)가 체인으로 이어짐 |
> | `startsWith("/admin")`을 코드로 직접 비교 | `SecurityFilterChain` 설정에서 URL별 규칙을 선언 |
> | `"VALID_TOKEN"` 문자열과 직접 비교 | 세션, JWT 등 실제 인증 정보를 확인하고 `SecurityContext`에 저장 |
> | 실패하면 401을 직접 씀 | 인증 실패는 로그인 페이지/401, 인가 실패는 403으로 자동 변환 |
