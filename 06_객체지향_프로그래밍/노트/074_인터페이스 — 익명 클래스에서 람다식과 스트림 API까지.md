# 인터페이스 — 익명 클래스에서 람다식과 스트림 API까지

## 1. 인터페이스의 두 가지 얼굴

인터페이스는 "약속"이라는 점에서는 항상 같지만, 그 약속이 가리키는 대상은 두 종류로 나뉜다.

- **캡슐의 약속**: 어떤 역할·책임을 가진 캡슐(클래스) 전체의 형태를 약속하는 인터페이스. 예를 들어 리포지토리 역할을 약속했다면, 그것을 구현하는 쪽은 리포지토리라는 이름을 가진 캡슐 하나가 존재해야 한다.
- **추상 메서드의 약속**: 캡슐 전체가 아니라, 완성하지 못한 특정 기능 하나만을 구멍 내서 약속하는 인터페이스. 캡슐 전체가 아니라 일부 기능에만 구멍을 낸다는 점이 다르다.

추상 클래스에서 추상 메서드를 만드는 이유를 떠올려보면 이 구분이 더 분명해진다. 추상 클래스는 자식들의 공통 부모인데, 기능은 공통으로 가지고 있어야 하지만 그 기능의 구현까지는 공통으로 만들어줄 수 없는 경우가 있다. 이럴 때 "이 부분은 너(자식)가 책임져라"라고 위임하는 것이 추상 메서드다. 즉 추상 메서드는 자식이 책임져야 할 약속이다.

그런데 이 위임을 꼭 상속(자식)에게만 넘겨야 하는 것은 아니다. 미완성된 기능을 자식에게 위임하는 대신, **외부에서 그 기능을 인터페이스로 만들어 주입받게** 할 수도 있다. 이렇게 하면 자식을 낳지 않고도, 필요한 구현체를 갈아 끼우는 방식으로 기능을 완성할 수 있다. 이 주입 통로는 아래 `JFrame` 사례처럼 setter(정확히는 `addXxx` 형태의 메서드) 하나로 열어둘 수도 있고, 생성자를 통해 만들 때부터 구현체를 넘겨받게 할 수도 있다 — 어느 쪽이든 "완성되지 못한 기능을 외부에서 채워 넣는다"는 본질은 같다.

두 약속의 차이는 "메서드가 몇 개냐"가 아니라, **그 약속이 무엇을 대신하고 있느냐**에 있다.

캡슐의 약속은 "이런 일을 하는 독립적인 존재(역할자)가 하나 있을 것이다"라는 약속이다. 그 역할자가 할 수 있는 일의 전체 목록을 인터페이스로 정의해놓은 것이다. 예를 들어 `List`는 "데이터를 순서대로 관리하는 목록 관리자"라는 역할 전체를 약속한다. `add`, `get`, `size`, `remove` 같은 메서드들은 서로 무관한 것들이 아니라 "목록을 관리한다"는 하나의 정체성을 이루는 조각들이다. 그래서 이 인터페이스를 구현하는 쪽(`ArrayList`, `LinkedList`)은 독자적인 캡슐(클래스)이 되어야 하고, 프로그램 안에서 "목록 그 자체"로 취급된다.

추상 메서드의 약속은 반대로, 이미 존재하는 어떤 역할자(캡슐)가 자기 일을 하다가 혼자서는 결정할 수 없는 부분 하나를 남겨두고, 그 빈 구멍을 채워달라고 요청하는 약속이다. 예를 들어 `List`(정확히는 `list.sort()`를 제공하는 캡슐)는 "정렬"이라는 서비스는 스스로 다 할 수 있다. 배열을 어떻게 돌면서 값을 바꿔치기할지, 몇 번 비교할지 같은 알고리즘은 전부 알고 있다. 그런데 딱 하나, "두 값 중 뭐가 더 큰가"만큼은 스스로 결정할 수 없다 — 그건 데이터의 성격(숫자냐 문자열이냐 커스텀 객체냐)에 달려 있기 때문이다. 그래서 그 판단 하나만 인터페이스(`Comparator`)로 빼서 "이것만 채워서 다오"라고 요청한다. 이때 `Comparator`를 구현하는 것은 독립적인 존재(역할자)가 아니라, 그 순간 그 자리에 끼워 넣을 "부품" 하나일 뿐이다. 그래서 이름 있는 클래스로 만들 필요 없이 익명 클래스나 람다식으로 그 자리에서 바로 채워 넣고 버려도 무방하다.

| 구분 | 캡슐(역할자)의 약속 | 추상 메서드(일부 기능)의 약속 |
|---|---|---|
| 약속의 단위 | 서로 연관된 메서드 묶음 = "하나의 정체성" | 메서드 하나(대개) = "하나의 판단/동작" |
| 구현체의 성격 | 독립적으로 존재하는 캡슐(객체) | 다른 캡슐 안에 끼워 넣는 부품 |
| 이름의 필요성 | 반드시 필요 (그 자체가 의미 있는 존재) | 없어도 무방 (한 번 쓰고 버려질 수 있음) |
| 구현 방식 | 별도 클래스로 정의 | 익명 클래스, 람다식으로 즉석 처리 가능 |
| 예시 | `List`, `Map`, `Repository`, `Service` | `Comparator`, `Runnable`, `Function`, `MouseListener`(개별 메서드 관점) |

한 문장으로 요약하면, 전자는 "이런 **존재**가 되어달라"는 약속이고, 후자는 "이런 **동작 하나**를 대신 결정해달라"는 약속이다. 후자이기 때문에 아래에서 다룰 것처럼 외부 클래스 → 내부 클래스 → 익명 클래스 → 람다식 → 메서드 레퍼런스까지 계속 줄여올 수 있는 것이고, 전자(`List`)였다면 애초에 그런 축약이 불가능했을 것이다.

## 2. JFrame의 사례 — 추상 클래스 대신 인터페이스로 기능을 꽂아 넣기

`JFrame`은 자기가 결정할 수 없는 부분들을 군데군데 구멍으로 남겨둔 클래스다. 예를 들어 마우스 클릭에 반응해서 무슨 일을 할지는 `JFrame`이 미리 정해줄 수 없다. `JFrame`을 쓰는 사람마다 원하는 동작이 다르기 때문이다.

이 구멍을 추상 메서드로 만들었다면 `JFrame`도 추상 클래스가 되어야 하고, 매번 자식 클래스를 상속받아 그 구멍을 메꿔야 한다. 하지만 `JFrame`은 추상 클래스가 아니다. 대신 `addMouseListener`라는 메서드(사실상 setter)에 `MouseListener` 인터페이스를 구현한 객체를 넘겨받는 방식을 쓴다.

```java
public class App {
    private static JFrame parent;

    public static void main(String[] args) {
        JFrame frame = new JFrame();
        parent = frame;
        frame.setSize(500, 400);
        frame.addMouseListener(new MouseHandler());
        frame.setVisible(true);
    }
}

class MouseHandler implements MouseListener {
    @Override
    public void mouseClicked(MouseEvent e) {
        System.out.println("haha");
    }

    @Override
    public void mousePressed(MouseEvent e) {}

    @Override
    public void mouseReleased(MouseEvent e) {}

    @Override
    public void mouseEntered(MouseEvent e) {}

    @Override
    public void mouseExited(MouseEvent e) {}
}
```

이름은 `add`지만 실질적으로는 setter다. `JFrame`이 스스로 완성할 수 없는 기능(마우스 처리)을, 자신을 상속받은 자식이 아니라 **자신을 사용하는 쪽**에서 인터페이스 구현체를 만들어 꽂아 넣게 하는 방식이다. 이렇게 특정 기능만 인터페이스로 빼면, 그 인터페이스를 구현한 객체를 갈아 끼우는 것만으로 기능이 달라지는 구조를 만들 수 있다 — 이것이 다형성이 실전에서 드러나는 전형적인 모습이다.

## 3. MouseListener를 직접 구현하기 번거로운 이유와 MouseAdapter

`MouseListener` 인터페이스는 마우스와 관련된 이벤트(클릭, 눌림, 뗌, 들어옴, 나감 등) 메서드 5개를 한 덩어리로 묶어놓은 인터페이스다. 자바는 인터페이스를 구현할 때 그 안의 메서드를 원하는 것만 골라서 구현할 방법이 없다 — 묶여 있는 5개면 5개를 전부 구현해야 한다.

그런데 실제로는 마우스 클릭 하나만 필요한 경우가 대부분이다. 이 불편함을 해결하기 위해 자바는 `MouseListener`를 이미 구현해 놓은 클래스인 `MouseAdapter`를 제공한다. `MouseAdapter`는 인터페이스가 아니라 클래스이며, `MouseListener`의 메서드 5개를 전부 빈 블록으로 구현해 놓았다. 이 어댑터를 상속받으면, 필요한 메서드만 골라서 오버라이드하면 된다.

```java
class MouseHandler extends MouseAdapter {
    @Override
    public void mouseClicked(MouseEvent e) {
        System.out.println("haha");
    }
    // 나머지 4개는 구현하지 않아도 됨 — MouseAdapter가 이미 빈 블록으로 채워둠
}
```

정리하면 인터페이스를 직접 구현하는 것은 "필수" 방식이고, 어댑터 클래스를 상속받는 것은 "선택" 방식이다. 어댑터라는 중간 계층을 하나 두는 것만으로, 다 갖출 필요 없이 필요한 것만 골라 쓰는 구조가 만들어진다.

## 4. 별도 클래스를 만들기 애매한 "땜빵용" 구현 — 중첩 클래스에서 익명 클래스로

`MouseHandler`처럼 마우스 이벤트를 처리하는 구현체는 리포지토리나 서비스처럼 독자적인 역할·책임을 가진 캡슐이 아니다. 그저 `JFrame`이 비워둔 구멍 하나를 메꾸기 위한 "땜빵용" 구현일 뿐이다. 이런 땜빵을 매번 별도의 클래스 파일로 만들면, 프로젝트 전체에 땜빵용 클래스 이름들이 여기저기 널브러지게 되어 오히려 구조가 지저분해진다.

그래서 자바는 이 문제를 단계적으로 해결해왔다.

**1단계 — 메서드 안에 중첩 클래스로 정의하기**

이 구현체를 쓰는 곳(예: `main` 메서드) 근처에서, 이름은 아무렇게나 지어서 그 자리에서 바로 정의한다. 어차피 그 메서드 안에서만 쓰이고 다른 곳에서는 쓸 일이 없기 때문에, 클래스 이름이 중요하지 않다.

```java
public class App {
    public static void main(String[] args) {
        class AAA extends MouseAdapter {
            @Override
            public void mouseClicked(MouseEvent e) {
                System.out.println("haha");
                JOptionPane.showMessageDialog(parent, "haha");
            }
        }

        JFrame frame = new JFrame();
        parent = frame;
        frame.setSize(500, 400);
        frame.addMouseListener(new AAA());
        frame.setVisible(true);
    }
}
```

**2단계 — 클래스 이름조차 없애기: 익명 클래스**

그런데 정작 필요한 것은 "이 클래스를 재사용하는 것"이 아니라 "구현체 하나를 채워서 그 자리에서 한 번 꽂는 것"이다. 그렇다면 클래스 이름을 짓는 절차 자체가 불필요하다. 자바는 이 필요성을 받아들여, 인터페이스나 클래스를 상속하는 구현체를 이름 없이 바로 정의하고 그 자리에서 바로 객체화하는 문법을 제공한다. 이것이 **익명 클래스(Anonymous Class)**다.

```java
JFrame frame = new JFrame();
parent = frame;
frame.setSize(500, 400);
frame.addMouseListener(new MouseAdapter() {
    @Override
    public void mouseClicked(MouseEvent e) {
        System.out.println("haha");
        JOptionPane.showMessageDialog(frame, "haha");
    }
});
frame.setVisible(true);
```

`new MouseAdapter() { ... }` 형태로, 상속(또는 인터페이스 구현)과 객체화, 그리고 오버라이드 구현을 한 번에 처리한다. 이 안에서 사용할 재료들(바깥의 `frame` 변수 등)도 자연스럽게 참조할 수 있어서, 구현이 훨씬 깔끔해진다. 이렇게 캡슐로서의 의미가 없는 "땜빵용" 구현은 별도 클래스를 만들지 않고 익명 클래스로 그 자리에서 처리하는 것이 자바의 일반적인 관례가 되었다.

## 5. 데이터 정렬 문제로 보는 익명 클래스 — Comparator

익명 클래스는 GUI 이벤트 처리뿐 아니라, 데이터 정렬처럼 "특정 함수만 잠깐 필요한" 모든 상황에서 널리 쓰인다.

배열을 정렬하는 기본 방법은 다음과 같다.

```java
int[] ages = {10, 20, 30, 43, 23, 45, 12, 32, 42};
Arrays.sort(ages);

String sortedAges = Arrays.toString(ages);
System.out.println(sortedAges);
// [10, 12, 20, 23, 30, 32, 42, 43, 45] — 오름차순
```

문제는 `Arrays.sort(int[])`는 오름차순만 지원한다는 점이다. 내림차순을 원하거나, 비교 기준이 복잡한 커스텀 객체를 정렬하려면 "어떻게 비교할지"를 직접 알려줘야 한다. 자바스크립트라면 비교 함수 하나를 그대로 넘기면 되지만, 자바는 함수만 딱 떼어서 전달하는 방법이 없다. 그래서 "비교하는 방법"을 인터페이스(`Comparator`)로 약속해두고, 그 인터페이스를 구현한 객체를 전달하는 방식을 쓴다.

```java
int[] ages = {10, 20, 30, 43, 23, 45, 12, 32, 42};
Arrays.sort(ages, new Comparator<Integer>() {
    @Override
    public int compare(Integer a, Integer b) {
        return b - a; // 내림차순
    }
});

String sortedAges = Arrays.toString(ages);
System.out.println(sortedAges);
```

여기서도 이 `Comparator` 구현체는 정렬 한 번에만 쓰이는 땜빵용 구현이므로, 별도 클래스를 만들지 않고 익명 클래스로 바로 넘겨준다.

## 6. 익명 클래스의 비용 문제와 람다식의 등장

익명 클래스는 클래스를 안 만들어도 된다는 점에서 진일보했지만, 여전히 코드가 장황하다. `new Comparator<Integer>() { @Override public int compare(...) { ... } }`처럼 형식적인 껍데기가 많아서, 정작 중요한 로직(`b - a`) 한 줄에 비해 비용이 너무 크다.

자바스크립트 같은 언어는 함수를 값처럼 전달할 수 있기 때문에 화살표 함수 하나로 끝나는 일을, 자바는 인터페이스 구현 → 객체화 → 전달이라는 절차를 거쳐야 했다. 이 격차를 줄이기 위해 등장한 것이 **람다식(Lambda Expression)**이다.

```java
int[] ages = {10, 20, 30, 43, 23, 45, 12, 32, 42};
Arrays.sort(ages, (a, b) -> b - a); // 내림차순
```

람다식은 익명 클래스의 껍데기(인터페이스명, 메서드명, `return`, 중괄호)를 모두 벗겨내고, 매개변수와 반환식만 남긴 표현이다. `->` 오른쪽이 반환값이라는 것이 문법으로 정해져 있기 때문에 `return`과 중괄호도 생략할 수 있다. 다만 자바는 형식(타입)을 까다롭게 따지는 언어라서, 매개변수 타입은 인터페이스 정의에 맞춰 자동으로 추론된다.

## 7. 문자열 비교와 숫자 비교의 차이

정수는 `b - a`처럼 뺄셈으로 크고 작음을 비교할 수 있지만, 문자열은 뺄셈이 불가능하다. 문자열끼리 크기를 비교할 때는 `String`이 제공하는 `compareTo` 메서드를 사용한다.

```java
String[] nums = {"2", "54", "11", "23", "46", "100", "49"};
Arrays.sort(nums, (String a, String b) -> a.compareTo(b)); // 오름차순
```

숫자는 전체 자릿수(값의 크기)로 비교하지만, 문자열은 앞 글자부터 순서대로 비교한다(사전식 비교). 그래서 숫자로 이루어진 문자열이라도 정수처럼 정렬되지 않고, `"100"`이 `"2"`보다 앞에 오는 등 결과가 다르게 나타날 수 있다. 어떤 자료형을 비교하느냐에 따라 비교 방식 자체가 달라지기 때문에, 그 비교 로직을 매번 외부에서 전달해야 하는 것이다.

## 8. 람다식도 불편할 때 — 메서드 레퍼런스

비교 로직이 이미 존재하는 메서드 하나를 그대로 호출하는 것뿐이라면, 람다식조차 더 줄일 수 있다. "어떤 메서드를 쓸지"만 알려주면, 자바가 알아서 첫 번째 인자로 그 메서드를 호출해주는 문법이 **메서드 레퍼런스(Method Reference, `Class::method`)**다.

```java
String[] nums = {"2", "54", "11", "23", "46", "100", "49"};

// 람다식
Arrays.sort(nums, (String a, String b) -> a.compareTo(b));

// 메서드 레퍼런스 — 완전히 동일한 의미, 더 짧음
Arrays.sort(nums, String::compareTo);
```

`String::compareTo`는 "각 요소가 가진 `compareTo` 메서드를 그대로 호출해서 비교에 쓰겠다"는 뜻이다. 다만 순서를 바꿔야 하는 경우(예: 내림차순)처럼 인자 순서를 직접 조정해야 할 때는 메서드 레퍼런스를 쓸 수 없고, 람다식이나 익명 클래스로 돌아가야 한다. 우선순위는 **메서드 레퍼런스 → 람다식 → 익명 클래스** 순으로, 가능한 한 앞쪽 방식을 쓰는 것이 코드를 가장 깔끔하게 만든다.

## 9. 함수형 인터페이스(`@FunctionalInterface`) — 람다로 표현 가능한 조건

모든 인터페이스가 람다식으로 표현 가능한 것은 아니다. 람다식은 함수 하나만 표현할 수 있기 때문에, **약속된 메서드가 단 하나뿐인 인터페이스만** 람다로 표현할 수 있다. `MouseListener`처럼 메서드가 5개인 인터페이스는 람다로 표현할 수 없다.

이런 "람다로 표현되기 위한" 인터페이스를 정의할 때는 `@FunctionalInterface` 어노테이션을 붙여둘 수 있다.

```java
@FunctionalInterface
interface ExamCompare {
    int compare(int a, int b);
}
```

이 어노테이션 자체가 람다식을 가능하게 만드는 것은 아니지만(붙이지 않아도 메서드가 하나면 람다로 쓸 수 있다), 마치 `abstract` 키워드가 "이 클래스는 객체화하면 안 된다"는 규칙을 컴파일러가 강제하게 만들듯, `@FunctionalInterface`는 "이 인터페이스에 메서드를 두 개 이상 추가하면 안 된다"는 규칙을 컴파일러가 강제하게 만드는 안전장치다.

## 10. Java 8과 스트림 API — 여왕벌과 부재료들

자바스크립트에 ES6 전후를 완전히 다른 언어처럼 구분하는 기준점이 있듯이, 자바에도 그런 분기점이 있다. 바로 **Java 8**이다. Java 8에서는 다음과 같은 기능들이 한꺼번에 추가되었다.

- Lambda expression
- Method References
- Functional interface
- Interface Default and static methods
- Optional class
- Unsigned Integer Arithmetic
- New Date Time API
- Repeating Annotations
- Effectively Final Variables
- **Stream API**

이 중 개별 항목 하나하나는 그렇게 무게감이 크지 않다. 이 변화들은 사실 하나의 기능을 지원하기 위해 언어 자체가 어쩔 수 없이 함께 바뀐 "부재료"들이고, 그 중심에 있는 "여왕벌"이 바로 **Stream API**다. 지금까지 정리한 익명 클래스 → 람다식 → 메서드 레퍼런스 → 함수형 인터페이스의 흐름은 전부 Stream API를 쓰기 위한 사전 준비였던 셈이다.

Java는 원래 응용 프로그램(윈도우/콘솔/웹)을 만들기 위한 언어로 출발했다. 그런데 시대가 흐르면서 "프로그램을 만드는 것"과는 결이 다른 요구가 커졌다 — 이미 가지고 있는 데이터 더미에서 원하는 조건에 맞는 것만 골라내고, 다른 형태로 바꾸고, 합계·평균 같은 값으로 요약하는 **데이터 분석** 작업이다. 이런 작업은 엑셀이나 SQL의 `WHERE`, `GROUP BY`가 하는 일과 본질적으로 같다 — "무엇을 원하는지"만 말하면 나머지 처리는 도구가 알아서 해주는 방식이다.

기존 자바에는 이런 작업을 위한 전용 도구가 없어서, 개발자가 매번 `for`문을 돌며 조건문으로 걸러내고 임시 변수에 담아 값을 바꾸는 코드를 직접 작성해야 했다. 자바는 이 공백을 메우기 위해 컬렉션에 함수형 스타일의 연산(map-reduce 계열)을 추가했는데, 이것이 Stream API다. 즉 Stream API가 "제공하는 것"은 새로운 문법이 아니라, **컬렉션이나 배열에 이미 들어있는 데이터를 필터링·변환·집계해서 원하는 결과로 뽑아내는 데이터 분석 기능** 그 자체다.

## 11. 스트림 API 개요 — 소스, 중간 연산, 최종 연산

Stream API는 배열이나 컬렉션 같은 데이터 소스로부터 스트림 객체를 얻어, 그 위에서 필터링·정렬·매핑·집계 같은 연산을 연이어 적용할 수 있게 해준다.

```java
int[] ages = {10, 20, 30, 43, 23, 45, 12, 32, 42};
IntStream agesStream = IntStream.of(ages);

int[] result = agesStream
        .filter(a -> a > 20)   // 중간 연산: 20보다 큰 것만
        .sorted()              // 중간 연산: 오름차순 정렬
        .map(a -> a / 10 * 10) // 중간 연산: 십의 자리로 변환
        .toArray();             // 최종 연산: 다시 배열로

System.out.println(Arrays.toString(result));
```

각 연산 단계에서 "무엇을 기준으로 필터링할지", "무엇으로 변환할지" 같은 판단 로직이 필요한데, 이 로직을 앞서 정리한 **람다식**으로 전달한다. 실제로는 인터페이스를 구현한 객체가 전달되는 것이지만, 문법적으로 함수를 넘기는 것처럼 보이기 때문에 "functional-style operation"이라고 부른다.

스트림이 제공하는 연산은 크게 Filtering, Mapping, Sorting, Calculating, Reduction, Collecting, Matching 등으로 나뉘며, 배열이든 컬렉션이든 일단 스트림 객체(`IntStream`, `Stream<T>` 등 자료형에 따라 종류는 다름)를 얻기만 하면 이후의 사용법은 동일하다. 정리하면 스트림 API는 "어떻게 반복할지"를 직접 코딩하는 대신, "무엇을 원하는지"만 연산으로 이어 붙이는 데이터 분석 도구이며, 그것을 가능하게 하려고 익명 클래스의 무거움을 람다식으로, 람다식의 번거로움을 메서드 레퍼런스로 줄여온 것이 Java 8의 핵심 줄기다.
