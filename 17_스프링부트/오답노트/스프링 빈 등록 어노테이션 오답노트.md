# 스프링 빈 등록 어노테이션 오답노트

### 1. 빈 등록 어노테이션이 아닌 것

**문제**: 다음 코드에서 스프링이 의존성을 주입할 수 있도록 클래스를 IoC에 빈(Bean)으로 등록하는 어노테이션으로 적절하지 않은 것은 무엇인가?

1. `@Component`
2. `@Service`
3. `@Repository`
4. `@Entity`

**정답: 4번**

**컴포넌트 스캔 대상 — `@Component` 가족**

스프링은 시작할 때 패키지를 훑으며(컴포넌트 스캔) 특정 어노테이션이 붙은 클래스를 찾아 객체로 만들고 IoC 컨테이너에 **빈**으로 등록한다. 그 기준이 되는 것이 `@Component`이고, 나머지는 `@Component`를 품고 있는 **역할별 이름표**다.

| 어노테이션 | 계층 | `@Component` 외에 더해 주는 것 |
|---|---|---|
| `@Component` | 범용 | — |
| `@Controller` / `@RestController` | 표현(웹) | 요청 매핑 대상이 된다 |
| `@Service` | 비즈니스 | 역할 표시(기능상 차이 없음) |
| `@Repository` | 데이터 접근 | DB 예외를 스프링의 `DataAccessException`으로 바꿔 준다 |
| `@Configuration` | 설정 | 안의 `@Bean` 메서드로 빈을 등록한다 |

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Component              // ← @Service 안에 @Component가 들어 있다
public @interface Service { ... }
```

**`@Entity`는 스프링이 아니라 JPA 것이다**

`@Entity`는 `jakarta.persistence` 패키지의 어노테이션으로, **"이 클래스는 DB 테이블과 매핑되는 엔티티다"**라고 JPA(하이버네이트)에게 알리는 표시다. 스프링의 컴포넌트 스캔 대상이 아니다.

| 구분 | 관리하는 쪽 | 만들어지는 방식 | 개수 |
|---|---|---|---|
| 빈(`@Service` 등) | 스프링 IoC 컨테이너 | 애플리케이션 시작 시 컨테이너가 생성·주입 | 보통 **하나**(싱글톤) |
| 엔티티(`@Entity`) | JPA 영속성 컨텍스트 | `new`로 만들거나, 조회할 때 JPA가 생성 | 데이터(행)마다 **여러 개** |

엔티티는 회원 한 명, 주문 한 건처럼 **데이터 하나하나**를 나타내므로 싱글톤 빈이 될 수 없다. 서비스에 엔티티를 생성자로 주입받는 일은 없고, 리포지토리로 **조회해서** 얻는다.

> **헷갈리기 쉬운 점**: `@Entity` 클래스를 찾는 것도 "스캔"이라 부른다(엔티티 스캔). 스프링 부트가 `@SpringBootApplication` 아래 패키지에서 엔티티를 찾아 JPA에 넘겨 주지만, 이는 빈 등록이 아니라 **JPA에 매핑 정보를 알려 주는** 것이다. 반대로 엔티티의 리포지토리 인터페이스(`JpaRepository` 상속)는 스프링 데이터 JPA가 구현체를 만들어 **빈으로 등록**한다.

**정리**: 빈 등록 어노테이션은 `@Component`와 그것을 품은 `@Controller`·`@Service`·`@Repository`·`@Configuration`이다. `@Entity`는 JPA의 테이블 매핑 표시이고, 엔티티 객체는 데이터마다 따로 만들어지므로 빈이 아니다.
