# 유니온 파일 시스템 — OverlayFS의 동작 원리와 등장 배경

유니온 파일 시스템(Union FS)은 "여러 개의 서로 다른 디렉토리를 하나로 겹쳐서, 마치 하나의 디렉토리인 것처럼 보여주는" 마운트 방식이다. 도커는 이 중에서도 주로 **OverlayFS**라는 구현체를 사용한다.

## 1. OverlayFS의 4가지 구성 요소

- **lowerdir**: 읽기 전용 레이어. 여러 개를 쌓을 수 있다(이미지의 각 Dockerfile 명령어가 레이어 하나씩). 아래에 있을수록 더 먼저 만들어진 레이어다.
- **upperdir**: 읽기/쓰기 레이어. 컨테이너가 실행되는 동안 생기는 유일한 쓰기 가능 레이어다.
- **merged**: 컨테이너 내부에서 실제로 보이는 통합된 뷰. lowerdir + upperdir을 겹쳐서 하나의 파일 시스템처럼 보여주는 결과물이다. 컨테이너 안의 프로세스는 이 merged 뷰만 본다.
- **workdir**: OverlayFS가 내부적으로 파일을 옮기거나 병합하는 작업을 할 때 쓰는 임시 공간. 사용자가 직접 건드릴 일은 없다.

## 2. 핵심 동작 원리 — Copy-up

가장 중요한 개념은 **"읽기 전용 레이어는 절대 직접 수정되지 않는다"**는 것이다. 그래서 하위 레이어에 있는 파일을 수정해야 할 때는 다음 과정을 거친다.

1. 수정하려는 파일이 lowerdir에만 있고 upperdir에는 없다.
2. 그 파일을 **upperdir로 통째로 복사**한다 (이걸 copy-up이라고 부른다).
3. 이후의 수정은 복사된 upperdir 쪽 파일에 적용된다. lowerdir의 원본은 그대로 남아있지만, merged 뷰에서는 upperdir의 수정된 버전이 우선적으로 보이므로 "수정된 것처럼" 보인다.

**copy-up의 단위는 파일 전체다.** "수정이 필요한 파일만 골라서 복사한다"는 것은 맞지만(안 건드리는 파일은 복사되지 않는다), 그 파일을 복사할 때는 바뀐 부분(바이트)만 복사되는 게 아니라 **파일 하나를 통째로** upperdir에 복사한 뒤 그 사본에서 수정이 이루어진다. 그래서 큰 파일을 컨테이너 안에서 조금씩 자주 수정하면, 매번 그 큰 파일 전체가 복사되는 비용 때문에 느려질 수 있다 — OverlayFS의 잘 알려진 성능 트레이드오프다.

## 3. 삭제는 "지우는 것"이 아니라 "숨기는 것"

lowerdir의 파일은 직접 지울 수 없으므로, 삭제도 특수한 방식으로 처리된다.

- **파일 삭제**: upperdir에 **whiteout 파일**이라는 특수한 마커를 만든다. merged 뷰는 이 마커를 보고 "이 이름의 파일은 없는 것"으로 처리해서 보여준다. lowerdir의 실제 파일은 그대로 디스크에 남아있지만, 겉보기엔 사라진 것처럼 동작한다.
- **디렉토리 삭제**: 파일 하나하나에 whiteout을 거는 대신, 그 디렉토리 자체를 **opaque directory**로 표시한다. 이러면 lowerdir에 있던 그 디렉토리의 내용은 통째로 안 보이게 되고, upperdir에 새로 생긴 내용만 보인다.

## 4. 왜 이런 구조를 쓰는가 — 공유와 불변성

같은 이미지로 컨테이너를 여러 개 띄워도, 그 컨테이너들이 보는 lowerdir(읽기 전용 레이어들)는 물리적으로 디스크에 **단 하나만** 존재한다. 어차피 아무도 그걸 고칠 수 없기 때문에, 여러 컨테이너가 안전하게 같이 참조할 수 있는 것이다.

반대로 생각하면, lowerdir가 수정 가능했다면 컨테이너 A가 거기 있는 파일을 바꾸는 순간 그걸 같이 쓰는 컨테이너 B, C도 전부 영향을 받아버린다. 그래서 "원본은 절대 못 건드리게 잠가놓고(읽기 전용), 각자 건드릴 수 있는 부분(upperdir)만 컨테이너별로 따로 준다"는 구조가 되었고, 그 덕분에 다음 세 가지가 동시에 성립한다.

- **공유가 안전해진다**: 원본이 불변이니 여러 컨테이너가 같은 레이어를 함께 참조해도 충돌이 없다.
- **디스크가 절약된다**: 컨테이너를 10개 띄워도 OS 파일을 10번 복사할 필요 없이, 작은 upperdir 10개만 더 생긴다.
- **생성이 빨라진다**: 컨테이너를 새로 띄울 때 하는 일이 "그 큰 lowerdir를 복사하는 것"이 아니라 "빈 upperdir 하나를 준비하는 것"뿐이라서 거의 즉시 끝난다.

즉 "원본이 변하지 않는다"는 성질(불변성) 자체가 "여러 컨테이너가 같이 써도 안전하다"는 결론을 만들어내는 전제 조건이다.

## 5. 등장 배경 — 도커보다 먼저 있었던 Live CD 문제

유니온 파일 시스템은 도커보다 훨씬 오래된 기술이고, 처음 등장한 계기는 **"읽기 전용 매체(CD/DVD)로 부팅하는 Live CD/Live USB 환경"**이었다.

**원래 문제 — CD로 부팅한 OS인데 수정이 필요하다**

1990년대~2000년대 초 Knoppix 같은 Live CD 리눅스 배포판은 운영체제 전체가 CD-ROM 안에 들어있었다. CD에 구워진 데이터는 당연히 물리적으로 쓰기가 불가능하다. 그런데 운영체제가 정상적으로 동작하려면 임시 파일 생성, 설정 변경, 패키지 설치 같은 "쓰기 작업"이 끊임없이 필요하다.

- CD 자체를 수정할 수는 없다.
- 그렇다고 CD의 전체 내용을 RAM이나 다른 저장장치로 통째로 복사해 두면, 부팅 시간도 느려지고 메모리도 많이 든다.

**해법 — 읽기 전용 레이어 위에 쓰기 가능한 레이어를 "겹쳐" 보여주자**

여기서 나온 아이디어가 유니온 파일 시스템이다. CD(읽기 전용)를 하나의 레이어로 놓고, 그 위에 RAM 디스크나 USB 같은 작고 빠른 쓰기 가능한 레이어를 하나 더 얹어서, 두 레이어를 합친 뷰를 사용자에게 보여주는 방식이다.

- 파일을 "수정"하면 실제로는 CD의 원본은 그대로 두고, RAM 레이어에 수정된 버전을 따로 기록한다.
- 사용자 입장에서는 평범하게 쓰기가 가능한 하나의 파일 시스템처럼 보인다.
- CD는 절대 훼손되지 않으니, 재부팅하면 항상 깨끗한 초기 상태로 돌아간다.

이 개념을 구현한 초기 기술이 **UnionFS**(2003년경, Stony Brook University 연구 프로젝트)였고, 이후 Knoppix·Ubuntu의 Live 세션 등에서 널리 쓰인 **aufs**(Another UnionFS)로 이어졌다. 더 거슬러 올라가면 1994년 4.4BSD의 "union mount"라는 개념도 있는데, 이건 설치 CD 위에 추가 패키지를 설치할 때 원본 설치 미디어를 건드리지 않고 겹쳐 보여주는 용도로 쓰였다.

**도커로 이어진 흐름**

이후 **OverlayFS**가 2014년경 리눅스 커널에 정식으로 병합되면서 더 가볍고 성능 좋은 표준 구현체가 되었고, 도커는 바로 이 OverlayFS를 가져다가 "읽기 전용 CD" 자리에 "읽기 전용 이미지 레이어"를, "RAM 레이어" 자리에 "컨테이너의 upperdir"를 대입했다.

즉 본질은 똑같다 — "원본은 건드리지 않고 보존하면서, 그 위에 변경사항만 얇게 얹어 보여준다"는 아이디어가 처음엔 CD 부팅 환경의 문제를 풀기 위해 나왔고, 도커는 그 아이디어를 컨테이너 이미지 문제에 그대로 재활용한 것이다.
