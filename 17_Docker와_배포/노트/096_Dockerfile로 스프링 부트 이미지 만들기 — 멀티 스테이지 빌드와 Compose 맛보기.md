# Dockerfile로 스프링 부트 이미지 만들기 — 멀티 스테이지 빌드와 Compose 맛보기

## 1. 가상 머신과 도커

### 구조의 차이

```
   가상 머신(VM)                       도커
┌─────────┬─────────┐         ┌─────────┬─────────┐
│  앱 A   │  앱 B   │         │  앱 A   │  앱 B   │
│ 게스트OS │ 게스트OS │         │(컨테이너)│(컨테이너)│
├─────────┴─────────┤         ├─────────┴─────────┤
│    하이퍼바이저     │         │    도커 엔진       │
├───────────────────┤         ├───────────────────┤
│     호스트 OS      │         │     호스트 OS      │
└───────────────────┘         └───────────────────┘
```

| 구분 | 가상 머신 | 도커 컨테이너 |
|---|---|---|
| 중간 계층 | **하이퍼바이저**가 가상 운영체제를 돌린다 | **도커 엔진**이 컨테이너를 돌린다 |
| 자원 할당 | 설치할 때 메모리·디스크를 **떼어 준다**(호스트 1000GB 중 32GB를 주면 호스트는 968GB만 쓴다) | 미리 떼어 달라고 하지 않는다. 필요한 만큼 호스트 자원을 쓴다 |
| 시스템 파일 | OS마다 시스템 라이브러리가 **각각** 로드된다 | 읽기 전용 파일은 **하나를 공유**한다 |
| 껐을 때 — 메모리 | 반환된다(일시 정지·상태 저장이면 메모리 내용이 디스크에 저장된다) | 프로세스가 끝나므로 **반환된다** |
| 껐을 때 — 디스크 | 다시 쓰려고 가상 디스크를 **그대로 차지한다**(한번 늘어난 크기는 줄지 않는다) | 컨테이너의 **쓰기 레이어만** 남는다(이미지 레이어는 원래 공유). `docker rm`하면 쓰기 레이어도 사라지고, 볼륨만 남는다 |
| 사용감 | 원격 접속하면 진짜 컴퓨터와 차이를 못 느낀다. 그 안에서 작업도 한다 | 최소한의 라이브러리만 있다. **실행 전용**이다 |

### 읽기 전용은 공유하고, 쓰는 데이터는 볼륨으로

- 리눅스 컨테이너 100개를 띄워도, 실행을 담당하는 **읽기 전용 시스템 파일**은 하나를 함께 쓴다(유니온 파일 시스템). VM이라면 100개가 다 따로 로드된다.
- 사용자가 쓰는 데이터처럼 **쓰기가 필요하고 계속 유지되어야 하는 것**은 컨테이너 안에 두지 않고 **볼륨**으로 빼서 호스트와 공유한다.

> 원문 바로잡기 — 강의에서는 "유니파이드 파일 시스템은 쓰기가 안 되고 읽기 전용만 된다"고 했는데, 정확한 이름은 **유니온 파일 시스템**(도커는 OverlayFS)이다. 이미지의 레이어들은 읽기 전용으로 겹쳐 공유하고, 그 위에 **컨테이너마다 얇은 쓰기 레이어**가 하나씩 올라간다. 그래서 컨테이너 안에도 쓸 수는 있지만, 컨테이너를 지우면 그 쓰기 레이어도 함께 사라진다. 지켜야 하는 데이터를 볼륨으로 빼는 이유가 이것이다.

### 컨테이너는 실행 전용, 작업 환경이 아니다

컨테이너는 "주로 **실행만 전문으로 하는** 가벼운 가상 환경"이다. 컨테이너 안에 이것저것 설치해서 작업 환경처럼 쓰기 시작하면 공유되는 부분이 점점 줄고 컨테이너가 비대해져, 결국 가상 머신과 차이가 없어진다. 그래서 **도커 컨테이너는 배포를 위한 실행 환경이지, 작업을 위한 환경이 아니다.**

> 원문 바로잡기 — 강의 중 "가상 머신은 도커 컨테이너, 하이퍼바이저 역할을 하는 게 도커"라고 비유했는데, 이해를 돕는 비유일 뿐 구조가 같지는 않다. 컨테이너에는 **커널이 없다.** 모든 컨테이너가 호스트의 리눅스 커널을 함께 쓰고, 격리는 커널 기능(네임스페이스·cgroups)으로 한다. 컨테이너 안의 "우분투", "알파인"은 커널을 뺀 사용자 영역 파일(라이브러리·명령어)만 담긴 것이다. 컨테이너가 가볍고 빨리 뜨는 이유다.

## 2. 왜 리눅스, 왜 WSL인가

### OS는 소프트웨어 때문에 고른다

OS를 고르는 진짜 이유는 편해서나 익숙해서가 아니라 **그 위에서 돌려야 할 소프트웨어가 그 OS에서만 제대로 돌기 때문**이다. 게임이나 한글 때문에 윈도우를 쓰는 것처럼.

- 개발자가 쓰는 도구는 대부분 **유닉스·리눅스에서 나온 소프트웨어**다. 윈도우나 맥에서도 지원하지만 에뮬레이터를 끼우는 식이라 한계가 있고, 아예 안 되는 것도 있다.
- 서버 프로그램은 거의 **리눅스를 대상으로** 만들어진다. 그래서 개발자 중에는 아예 리눅스 데스크톱을 쓰는 사람도 꽤 있다.
- **도커는 리눅스 네이티브**다. 그래서 일부러 WSL로 리눅스를 설치하고, 그 위에서 도커를 돌린다.

### WSL은 네트워크로 연결된 다른 컴퓨터다

```
윈도우(호스트 OS)
 └─ 하이퍼바이저
     └─ WSL(가상 머신) ── Ubuntu
                            └─ 도커 엔진
                                 └─ 컨테이너
```

- WSL 자체는 리눅스가 아니라 **리눅스를 설치해 돌리는 윈도우의 환경**이고, 그 안에 Ubuntu가 들어 있다.
- 탐색기에서 보이는 리눅스 폴더는, 집에서 동생 컴퓨터의 공유 폴더를 네트워크 드라이브로 잡은 것과 같다. **원격 컴퓨터의 파일을 드라이브처럼 보여 주는 것**이지 내 디스크의 폴더가 아니다(`\\wsl$\Ubuntu\...`).
- 그래서 라이브러리를 추가해도 VSCode가 바로 동기화하지 못하는 일이 생긴다.

## 3. Dockerfile, 이미지, 컨테이너

### 노드로 비유하면

| 도커 | 노드 | 하는 일 |
|---|---|---|
| **Dockerfile** | `package.json` | 무엇을 받아서 어떻게 조립할지 적어 둔 **설치 정보** |
| **이미지** | `node_modules`가 채워진 프로젝트 | 실제로 다 받아서 조립해 둔, **실행할 준비가 된** 상태 |
| **컨테이너** | 실행 중인 프로그램 | 이미지를 실제로 띄운 **인스턴스** |

프로젝트를 다른 컴퓨터로 옮길 때 `node_modules`는 빼고 가져간다. `package.json`에 정보가 있으니 `npm install`로 다시 받으면 되기 때문이다. GitHub에 `node_modules`를 올리지 않는 것도 같은 이유다.

도커도 마찬가지다. 수백 MB짜리 **이미지를 GitHub에 올리지 않는다.** 몇 KB짜리 **Dockerfile**만 공유하고, 받는 쪽에서 이미지를 만든다.

"Dockerfile은 설계도"라는 설명은 알고 나면 맞는 말이지만, 처음 들으면 막연하다. **"어떤 OS를 받아서, 내 프로젝트를 어느 디렉터리에 넣고, 어떻게 실행할지"를 적은 설치 정보**라고 이해하면 쉽다.

### Dockerfile에 담기는 것

1. **어떤 OS(베이스 이미지)를 쓸지** — 이미지를 만들 때 그 OS를 다운로드한다.
2. **내 프로젝트(빌드 결과물)를 그 OS의 어느 디렉터리에 둘지**
3. **컨테이너가 켜질 때 무엇을 실행할지**

### 스톱된 컨테이너와 이미지는 다르다

| 명령 | 하는 일 |
|---|---|
| `docker run` | 이미지로 **컨테이너를 새로 만들고** 실행까지 한 번에 |
| `docker stop` | 실행 중인 컨테이너를 멈춘다 |
| `docker start` | 멈춘 컨테이너를 다시 실행한다(새로 만들지 않는다) |

컨테이너는 실행 중(running)일 수도, 멈춘(stopped) 상태일 수도 있다. 그럼 멈춘 컨테이너는 다시 이미지가 된 걸까? 아니다.

- **이미지**는 한 번도 실행한 적이 없는 상태다.
- **멈춘 컨테이너**는 실행되고 있지는 않지만, **실행했을 때의 상태와 설정이 그대로 남아 있다.**

## 4. 베이스 이미지 고르기 — 어떤 JDK를 쓸까

### 맨땅의 OS 대신 JDK가 깔린 OS

맨 리눅스 이미지를 가져와 JDK를 직접 설치해도 되지만, **JDK가 이미 탑재된 이미지**를 가져오는 편이 훨씬 편하다.

```bash
docker search java
```

별이 많은 공식 `java` 이미지가 나오지만 설명 첫머리에 **DEPRECATED**라고 적혀 있다. 더 좁혀서 찾는다.

```bash
docker search eclipse-temurin
docker search --filter is-official=true eclipse-temurin   # 공식 이미지만
```

누구나 이미지를 만들어 Docker Hub에 올릴 수 있기 때문에, 비공식 이미지가 섞여 나온다. `--filter is-official=true`로 **공식 이미지만** 고른다. 우리는 개발할 때 쓰고 있는 JDK와 같은 **Eclipse Temurin**을 쓴다. 개발 환경과 같은 것을 써야 하기 때문이다.

### 태그로 버전과 크기를 고른다

| 이미지:태그 | 내용 |
|---|---|
| `eclipse-temurin` | 태그를 안 쓰면 `latest`. 어떤 JDK 버전이 들었는지 알 수 없다 |
| `eclipse-temurin:21-jdk` | JDK 21 (컴파일러 포함, 빌드용) |
| `eclipse-temurin:21-jre` | JRE 21 (실행만, 더 가볍다) |
| `eclipse-temurin:21-jre-alpine` | **알파인** 리눅스 기반. 불필요한 것을 다 빼서 더 다이어트한 버전 |

### 곁다리 — JDK는 누구의 것인가

자바를 만든 회사는 **썬 마이크로시스템즈**다. 스팍 스테이션(워크스테이션)과 그 위에서 도는 유닉스 계열 OS **솔라리스**, 각종 네트워크 장비를 만들며 1990년대를 누렸다.

- 인텔 CPU가 멀티태스킹을 지원하게 되자, 리누스 토르발스가 PC에서 도는 유닉스 같은 OS를 만들기 시작했다. 처음엔 허술했지만 전 세계 개발자들이 함께 고쳐 나가며 **리눅스**가 견고해졌다.
- 비싼 스팍 대신 값싼 인텔 PC + 리눅스로도 충분하다는 분위기가 퍼지고, 썬이 인텔용 솔라리스까지 내자 오히려 스팍이 팔리지 않게 되었다. 결국 썬은 쇠퇴하고 **오라클이 인수**했다.
- 자바는 처음부터 여러 회사가 함께 만들어 가는 구조였다. 회원사들이 개선안을 제안하면 커뮤니티가 검토해 다음 버전에 반영한다. 다만 **배포본**을 만들어 내놓는 곳은 사실상 오라클뿐이었다.
- 오라클이 상업적 사용에 비용을 요구하자, 회원사들이 **같은 소스로 무료 배포본**을 만들기 시작했다. 대표적인 것이 Eclipse 재단(Adoptium)의 **Temurin**, 레드햇의 OpenJDK 빌드 등이다.

그래서 "어떤 JDK를 쓸지"는 곧 **어떤 배포본을 쓸지**를 고르는 문제다.

## 5. 가장 단순한 Dockerfile — 로컬에서 빌드한 JAR 넣기

### 먼저 JAR 만들기

`build.gradle`이 있는 프로젝트 루트에서 빌드한다. 지금까지는 `./gradlew bootRun`으로 **실행**만 했고, 배포본(JAR)은 만든 적이 없다.

```bash
./gradlew build          # BUILD SUCCESSFUL이 나와야 한다
ls build/libs            # security-0.0.1-SNAPSHOT.jar
```

코드에 오류가 있으면 빌드가 안 되니 그것부터 잡는다.

### Dockerfile

프로젝트 루트(빌드 파일이 있는 곳)에 `Dockerfile`을 만든다. **철자가 정확해야 하고 확장자는 없다.**

```dockerfile
FROM eclipse-temurin:21-jdk                                # 1. 베이스 이미지(OS + JDK 21)
WORKDIR /app                                               # 2. 작업 디렉터리
COPY build/libs/security-0.0.1-SNAPSHOT.jar app.jar        # 3. 빌드 결과물을 app.jar로 복사
ENTRYPOINT ["java", "-jar", "app.jar"]                     # 4. 컨테이너가 켜질 때 실행할 명령
```

| 명령 | 하는 일 |
|---|---|
| `FROM` | 가져올 베이스 이미지. 항상 맨 앞 |
| `WORKDIR` | 리눅스 안의 작업 디렉터리를 정한다(없으면 만든다). 이후 명령은 모두 여기서 실행된다. 이름은 마음대로 |
| `COPY 소스 목적지` | 호스트의 파일을 이미지 안으로 복사한다. 목적지를 `app.jar`로 쓰면 이름도 바뀐다 |
| `ENTRYPOINT` | **컨테이너가 부팅되자마자** 실행할 명령. 지금 실행하라는 게 아니라 "켜지면 제일 먼저 이걸 해라"다 |

- `ENTRYPOINT`는 명령과 인자를 **배열로 쪼개서** 쓴다. `java -jar app.jar` → `["java", "-jar", "app.jar"]`
- `WORKDIR`을 정했으니 경로 없이 `app.jar`라고 쓴다. `WORKDIR`이 없다면 `/app/app.jar`처럼 경로를 다 써야 한다.

> **추가 설명 — `*.jar`로 쓰면 실패할 수 있다**: 스프링 부트 3의 `./gradlew build`는 `build/libs`에 실행용 JAR와 함께 `-plain.jar`(의존성 없는 일반 JAR)도 만든다. `COPY build/libs/*.jar app.jar`처럼 와일드카드를 쓰면 두 파일이 걸려 "목적지가 디렉터리여야 한다"는 오류가 난다. 파일 이름을 정확히 쓰거나, `build.gradle`에서 `jar { enabled = false }`로 plain JAR를 끄거나, `./gradlew bootJar`로 실행용 JAR만 만든다.

> **추가 설명 — ENTRYPOINT와 CMD**:
>
> | 구분 | ENTRYPOINT | CMD |
> |---|---|---|
> | 역할 | 컨테이너의 **고정된 실행 명령** | 기본 명령 또는 **기본 인자** |
> | `docker run 이미지 xxx`로 뒤에 무언가를 붙이면 | `xxx`가 **인자로 덧붙는다** | `xxx`가 CMD를 **통째로 대체한다** |
> | 함께 쓰면 | `ENTRYPOINT ["java", "-jar", "app.jar"]` + `CMD ["--spring.profiles.active=prod"]` → CMD가 기본 인자가 된다 | |
>
> 애플리케이션 하나를 실행하는 이미지는 실행 명령이 바뀔 일이 없으니 `ENTRYPOINT`로 고정하고, 바꿔 끼울 만한 옵션만 `CMD`로 두는 것이 일반적이다. 둘 다 배열 형식(exec 형식)으로 써야 `java`가 1번 프로세스가 되어 `docker stop`의 종료 신호를 바로 받는다.

### 이미지 빌드

Dockerfile이 있는 경로에서 실행한다. `run`이 아니라 **`build`**다.

```bash
docker build -t backend:latest .
```

- `-t 이름:태그` — 이미지 이름과 버전. 이름은 `backend`, `my-backend` 등 마음대로
- 마지막 `.` — **빌드할 위치**(Dockerfile과 COPY할 파일이 있는 곳). 빼먹기 쉽다

### 이미지 확인과 삭제

```bash
docker images                 # 이미지 목록 (backend 약 833MB)
docker images backend         # 이름으로 좁혀 보기
docker rmi backend            # 이미지 삭제 (= docker image rm backend)
docker rmi -f backend         # 컨테이너가 쓰고 있어서 안 지워질 때 강제 삭제
```

## 6. 컨테이너 실행과 포트 포워딩

### 콘솔에 뜬다고 로컬에서 도는 게 아니다

```bash
docker run backend
```

`Tomcat started on port 8080` 로그가 터미널에 뜨지만 브라우저에서 `localhost:8080`이 열리지 않는다. 터미널에 출력이 보일 뿐, 앱은 **도커 안의 컨테이너에서** 돌고 있기 때문이다.

```
예전: 호스트 ── ./gradlew bootRun ── 앱 (호스트의 8080)
지금: 호스트 ── 도커 ── 컨테이너 ── 앱 (컨테이너의 8080)
```

컨테이너는 격리된 네트워크를 가지므로, 호스트의 포트와 컨테이너의 포트를 **연결(포트 포워딩)**해 줘야 한다.

```bash
docker run -p 8080:8080 backend      # 호스트 8080 → 컨테이너 8080
docker run -p 3012:8080 backend      # 호스트 3012 → 컨테이너 8080
```

`-p 호스트포트:컨테이너포트` 순서다. 두 번째처럼 하면 앱은 컨테이너 안에서 여전히 8080으로 뜨지만, 브라우저에서는 `localhost:3012`로 들어가야 열린다.

### 윈도우에서는 두 번 넘어간다

윈도우에는 도커가 직접 들어가지 않으므로, 가상 리눅스(WSL)를 깔고 거기에 다시 도커를 깔았다. 그래서 원래는 **두 단계 포워딩**이 필요하다.

```
브라우저(윈도우) ─ 8080 ─▶ WSL(Ubuntu) ─ 8080 ─▶ 도커 컨테이너 ─▶ 앱
```

예전에는 이걸 손으로 열어야 해서 고생이 많았는데, 지금은 **WSL에서 열린 포트를 윈도우의 `localhost`로 자동 포워딩**해 준다. 그래서 `-p`만 지정하면 윈도우 브라우저에서 바로 열린다. 이런 번거로움 때문에 가능하면 개발 환경을 리눅스로 하는 편이 덜 골치 아프다(리눅스에서도 VSCode는 잘 돌아간다).

> **추가 설명 — 자주 쓰는 실행 옵션**:
>
> ```bash
> docker run -d -p 8080:8080 --name my-backend backend   # -d: 백그라운드 실행, --name: 컨테이너 이름
> docker ps            # 실행 중인 컨테이너 (-a: 멈춘 것까지)
> docker logs -f my-backend
> docker stop my-backend && docker start my-backend
> docker rm my-backend # 컨테이너 삭제
> ```
>
> `--name` 없이 `run`을 반복하면 매번 새 컨테이너가 쌓이니, 안 쓰는 컨테이너는 `docker ps -a`로 확인해 지운다.

## 7. 멀티 스테이지 빌드 — 빌드도 도커 안에서

### 단순한 방식의 불편함 두 가지

1. **호환성 확신이 없다.** 내 WSL에서 빌드한 결과물이 실제 실행 환경과 완전히 같은 환경에서 만들어진 것은 아니다.
2. **사전 작업이 필요하다.** 이미지를 만들기 전에 매번 내가 직접 빌드해 둬야 한다.

또 JDK 이미지로 실행하면 실행에 필요 없는 **컴파일러 등이 함께 들어가** 무겁다.

### 빌드용 리눅스와 실행용 리눅스를 나눈다

```dockerfile
# 1단계: 빌드용 — JDK가 있는 리눅스. 빌드할 때만 쓰고 버린다
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
COPY . .
RUN ./gradlew bootJar --no-daemon

# 2단계: 실행용 — JRE만 있는 가벼운 리눅스. 이게 최종 이미지가 된다
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /app/build/libs/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

- `AS build` — 첫 번째 단계에 **별칭**을 붙인다.
- 1단계에서 프로젝트 전체를 복사해 **실제 실행 환경과 같은 JDK로 빌드**한다. JAR는 내 컴퓨터가 아니라 **1단계 컨테이너 안**(`/app/build/libs`)에 만들어진다.
- `COPY --from=build` — 1단계의 결과물만 쏙 빼서 2단계로 가져온다. 1단계의 JDK, 소스, Gradle 캐시는 최종 이미지에 들어가지 않는다.
- `EXPOSE 8080` — 이 컨테이너가 8080을 쓴다는 **문서 표시**다. 실제로 포트를 여는 것은 여전히 `docker run -p`다.

실행 방법은 똑같다. `docker build`하면 알아서 빌드해서 이미지가 만들어지고, `docker run`하면 실행된다. 결과 이미지는 **833MB → 약 567MB**로 줄었다(알파인 JRE를 쓰면 더 줄어든다). **실행에 필요한 것만 갖춘 환경**을 만드는 것이 핵심이다. 실무에서는 이 방식이 일반적이다.

> **추가 설명 — 멀티 스테이지 빌드에서 자주 막히는 곳**:
> - **`gradlew` 실행 권한**: 윈도우에서 만든 프로젝트는 `gradlew`에 실행 권한이 없어 `Permission denied`가 날 수 있다. `RUN chmod +x gradlew && ./gradlew bootJar --no-daemon`으로 쓴다. 줄바꿈이 CRLF여도 실행이 안 되므로 LF로 맞춘다.
> - **`.dockerignore`**: `COPY . .`는 `build/`, `.gradle/`, `.git/`까지 다 보낸다. 프로젝트 루트에 `.dockerignore`를 두고 이런 폴더를 빼면 빌드가 빨라진다.
> - **plain JAR**: 여기서는 `bootJar`로 실행용 JAR만 만들었기 때문에 `*.jar`가 하나만 걸린다.
> - **테스트**: `./gradlew build`로 빌드하면 테스트도 돈다. 테스트가 DB 연결을 요구하는데 빌드 단계에는 DB가 없으면 실패하니, 그럴 땐 `bootJar`를 쓰거나 `build -x test`로 테스트를 뺀다.

## 8. Docker Compose — 여러 컨테이너를 하나로 묶기

### 컨테이너마다 따로 관리하면 불편하다

앞으로는 백엔드뿐 아니라 프론트엔드와 데이터베이스도 있다. Dockerfile이 3개가 되고, 실행하려면 `docker run`을 세 번, 내릴 때도 세 번 해야 한다.

**Docker Compose**는 여러 컨테이너를 **하나의 네트워크로 묶어서** 한 번에 관리한다.

- `up` 한 번이면 프론트·백엔드·DB가 다 올라가고, `down` 한 번이면 다 내려간다.
- 묶인 컨테이너들은 **자기들만의 격리된 네트워크**를 갖는다. 다른 Compose 묶음에서 같은 포트(예: 3000)를 써도 내부적으로는 충돌하지 않는다. 클라우드 서버 한 대에 여러 프로젝트를 올려도 된다.
- 필요하면 Nginx 같은 것도 함께 얹을 수 있다.

### docker-compose.yaml

프로젝트의 가장 바깥 루트에 `docker-compose.yaml`을 만든다. 이것도 **철자가 틀리면 안 된다.** 지금까지 데이터베이스용으로 따로 만들었던 설정은 버리고, 이제부터 DB는 Compose로 띄운다.

```yaml
version: '3.8'

services:
  # 1. PostgreSQL 데이터베이스 상자 설정
  postgres-db:
    image: postgres:16
    container_name: my-postgres
    environment:
      POSTGRES_DB: mydatabase
      POSTGRES_USER: myuser
      POSTGRES_PASSWORD: mypassword
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data

  # 2. 스프링 부트 백엔드 앱 상자 설정
  backend-app:
    build: .
    container_name: my-backend
    ports:
      - "8080:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres-db:5432/mydatabase
      SPRING_DATASOURCE_USERNAME: myuser
      SPRING_DATASOURCE_PASSWORD: mypassword
    depends_on:
      - postgres-db

# 3. 데이터베이스 데이터를 보존하기 위한 공간 선언
volumes:
  postgres_data:
```

### 컨테이너는 이름으로 서로를 찾는다

같은 Compose 네트워크 안에서는 **IP가 아니라 이름으로 접속**한다. 백엔드가 DB에 붙을 때 주소를 `localhost`가 아니라 `db`로 쓰는 이유다.

```
jdbc:postgresql://db:5432/ncafe
                  └─ 서비스 이름이 곧 호스트 이름
```

백엔드 컨테이너 안에서 `localhost`는 **백엔드 컨테이너 자신**이다. DB는 다른 컴퓨터(컨테이너)이므로 그 이름으로 찾아가야 한다.

> 원문 바로잡기 — 강의에서는 "컨테이너 이름이 주소가 된다"고 했는데, Compose 네트워크에서 기본 주소가 되는 것은 **서비스 이름**(`services:` 아래의 키, 위 예시의 `db`)이다. `container_name`은 `docker ps` 목록에 보이는 이름이고, 이 이름으로도 접속은 되지만 보통은 서비스 이름을 쓴다.

```bash
docker compose up -d      # 전부 빌드·실행 (-d: 백그라운드)
docker compose ps
docker compose logs -f backend
docker compose down       # 전부 중지·삭제 (볼륨은 남는다. -v를 붙이면 볼륨까지 삭제)
```

> **추가 설명 — 파일 이름과 명령어**: 요즘 Compose는 `compose.yaml`을 기본 이름으로 권장하지만 `docker-compose.yaml`도 그대로 인식한다. 명령어도 예전의 `docker-compose`(하이픈)보다 도커에 내장된 `docker compose`(띄어쓰기)를 쓴다.

Compose로 프론트엔드와 백엔드를 함께 올리고, 내리고, 공유하는 것은 다음 수업에서 이어서 한다.

## 9. 한 줄 정리

- 도커는 **실행 전용의 경량 가상 환경**이다. 컨테이너는 호스트 커널을 함께 쓰고, 읽기 전용 파일은 공유하며, 지켜야 할 데이터는 **볼륨**으로 뺀다.
- 개발 도구와 서버 소프트웨어는 대부분 리눅스 태생이고, **도커는 리눅스 네이티브**다. 그래서 윈도우에서는 WSL 위에 도커를 올린다.
- **Dockerfile**(설치 정보, `package.json`) → `docker build` → **이미지**(실행 준비 완료) → `docker run` → **컨테이너**(실행 인스턴스). GitHub에는 Dockerfile만 올린다.
- 멈춘 컨테이너는 이미지가 아니다. 실행했던 상태가 남아 있다.
- 베이스 이미지는 공식(`is-official=true`)이고 개발 환경과 같은 JDK 배포본(**Temurin**)으로, 태그로 버전을 고정한다.
- Dockerfile의 기본 세트는 `FROM` → `WORKDIR` → `COPY` → `ENTRYPOINT`. 이미지는 `docker build -t 이름:태그 .`로 만든다.
- 컨테이너는 격리된 네트워크라 `-p 호스트:컨테이너`로 **포트 포워딩**해야 브라우저에서 열린다.
- 실무에서는 **멀티 스테이지 빌드**로 JDK 컨테이너에서 빌드하고, JRE 컨테이너에는 결과 JAR만 넣는다.
- 여러 컨테이너는 **Docker Compose**로 하나의 네트워크에 묶어 `up`/`down`으로 관리하고, 컨테이너끼리는 **서비스 이름**으로 찾는다.
