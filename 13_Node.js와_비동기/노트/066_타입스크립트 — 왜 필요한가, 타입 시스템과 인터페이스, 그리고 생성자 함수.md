# 타입스크립트 — 왜 필요한가, 타입 시스템과 인터페이스, 그리고 생성자 함수

타입스크립트가 왜 등장했고 자바스크립트의 어떤 문제를 해결하는지, 그리고 원시 타입·객체 타입·`any`/`unknown`·유니온·리터럴·enum·interface 같은 타입스크립트의 타입 시스템을 다룬다. 마지막으로 자바스크립트가 객체지향을 어떻게 흉내 내는지(생성자 함수, `this`, `new`)를 살펴본다.

## 1. 타입스크립트란 — 자바스크립트의 상위집합

타입스크립트(TS)는 마이크로소프트가 만든, **자바스크립트에 타입을 얹은 상위집합(Superset)** 언어다. 리액트뿐 아니라 Vue·Angular 등 모든 프론트엔드 플랫폼에서 사실상 표준으로 쓰이고 있으며, 특정 플랫폼에 종속되지 않는다.

타입스크립트 코드(`.ts`) 자체는 브라우저에서 직접 실행될 수 없다. 브라우저가 이해하지 못하는 키워드(타입 표기)를 갖고 있기 때문에, 반드시 **번역기(컴파일러)**를 거쳐 순수 자바스크립트로 변환된 뒤에야 실행된다.

```
TypeScript code → [compiler] → JavaScript code
```

이 변환 과정을 컴파일이라 부를지 트랜스파일이라 부를지 논쟁이 있었다 — 전통적으로 컴파일러는 고급 언어를 하위 계층(기계어 등)으로 낮추는 도구를 가리키고, 타입스크립트는 고급 언어에서 고급 언어(자바스크립트)로 옆으로 이동하므로 엄밀히는 **트랜스파일러**다. 다만 요즘은 이런 구분 없이 그냥 컴파일러라고도 부른다.

중요한 점은 타입 표기가 **소스 코드일 때만 의미가 있다**는 것이다. 컴파일 과정에서 문법 오류(타입 위반)를 잡아주는 역할을 다 하고 나면, 결과물인 자바스크립트에는 타입 정보가 전혀 남지 않는다 — 개발할 때만 있는 주석 같은 존재다.

## 2. 왜 쓰는가 — 자바스크립트 타입 없음의 문제

자바스크립트에는 `string`, `number`, `boolean` 같은 타입이 존재하긴 하지만, 변수를 선언할 때 "이 변수는 이 타입이어야 한다"고 강제한 적이 없다. 정수형 변수처럼 보이는 곳에 문자열도, 객체도 아무렇게나 대입할 수 있다 — 마치 모든 변수가 자바의 `Object`형인 것과 같다.

함수도 마찬가지다. 매개변수를 두 개 선언한 함수에 인자를 하나만 줘도, 열 개를 줘도 자바스크립트는 오류를 내지 않는다.

```js
function greet(person, date) {
    console.log(`Hello ${person}, today is ${date}!`);
}

greet("Brendan"); // 오류 없음 — date는 undefined
```

이런 언어적 유연함은 실수를 그대로 통과시킨다는 문제로 이어진다. 사람은 컨디션에 따라 실수를 저지르기 마련인데, 자바스크립트는 그 실수를 잡아줄 장치가 없다. 확장자를 `.ts`로 바꾸면, 컴파일(번역) 과정에서 이런 실수를 다른 정적 타입 언어 수준으로 깐깐하게 검사해준다.

```
tsc hello.ts
hello.ts:6:1 - error TS2554: Expected 2 arguments, but got 1.
```

## 3. 설치와 컴파일

```
npm install -g typescript   # 전역 설치 (모든 프로젝트에서 사용)
tsc hello.ts                # hello.ts → hello.js로 번역
```

파일 확장자를 `.ts`로 저장해야 타입스크립트 컴파일러가 번역 대상으로 인식한다. 문법 자체는 기존 자바스크립트 구문을 그대로 쓰되, 타입 표기가 추가된다.

### 3-1. tsconfig.json — 출력 디렉토리와 파일명 생략

번역 결과물(`.js`)이 원본 `.ts`와 같은 디렉토리에 생기면, 같은 스코프에 있는 것으로 취급되어 이름 충돌(같은 블록 스코프 안에 타입이 중복 선언된 것으로 인식) 문제가 생길 수 있다. 매번 `tsc hello.ts --outDir dist`처럼 옵션을 주는 게 번거로우므로, 프로젝트 루트에 `tsconfig.json` 설정 파일을 두고 출력 디렉토리를 고정해둔다.

```json
{
  "compilerOptions": {
    "outDir": "./dist"
    // ... 다른 컴파일 옵션들 ...
  }
}
```

`tsconfig.json`이 있으면 파일명을 지정할 필요 없이 해당 디렉토리에서 `tsc`만 실행해도, 설정된 옵션대로 폴더 안의 모든 `.ts` 파일을 번역해 지정된 출력 디렉토리에 넣어준다.

## 4. 원시 타입(Primitive types)

자바스크립트가 원래 갖고 있던 기본 타입을 그대로 지원한다.

| 타입 | 의미 |
|---|---|
| `string` | 문자열 |
| `number` | 숫자(정수, 실수 등) |
| `boolean` | 참/거짓 값 |
| `null` | 값이 없는 상태 |
| `undefined` | 정의되지 않은 값 |
| `bigint` | 큰 정수 (ES2020부터) |
| `symbol` | 고유한 심볼 값 (ES6부터) |

변수 선언 시 콜론(`:`)으로 타입을 명시하면, 이후 다른 타입의 값을 대입할 수 없게 된다.

```ts
let msg: string = "hello world";
msg = 2; // Error: Type '2' is not assignable to type 'string'
```

타입스크립트는 "types on the left"(`int x = 0;` 같은 C류 문법)를 쓰지 않는다 — 타입 표기는 항상 타입이 붙는 대상 **뒤**에 온다.

## 5. 객체 타입 정의 — 익명 객체 타입과 타입 별칭(Type Aliases)

객체 형태의 타입은 중괄호로 각 속성의 타입을 나열해서 즉석으로("익명 객체 타입") 정의할 수 있다.

```ts
const user: { name: string; age: number; } = { name: "Alice", age: 30 };
```

매번 이렇게 풀어 쓰면 길어지므로, `type` 키워드로 이 형태에 이름을 붙여 재사용할 수 있다 — 이를 **타입 별칭(Type Alias)** 이라 부른다.

```ts
type User = {
    name: string;
    age: number;
};

const user: User = { name: "Alice", age: 30 };
```

여기서 중요한 개념 구분이 하나 있다 — `type` 키워드 자체가 타입을 "정의"하는 게 아니라, `=` 오른쪽에 있는 구조가 실제 타입 정의이고, `type 이름 = ...`은 그 정의에 **다른 이름(별칭)을 붙이는 것**이다. 그래서 기존 원시 타입도 별칭을 새로 만들 수 있다.

```ts
type str = string;
const hello: str = "Hello, world!";

type ID = number;
```

배열 타입은 원소 타입 뒤에 대괄호를 붙여 표기한다.

```ts
let nums: number[] = [1, 2, 3];
let names: string[] = ['홍길동', '홍길순'];
```

## 6. Special types — `any`와 `unknown`

변수 선언 시 타입을 아예 지정하지 않으면, 타입이 없는 게 아니라 암묵적으로 **`any`** 타입이 매칭된다(자바의 `Object`형과 비슷한 개념). 컴파일러가 문맥에서 타입을 추론할 수 없을 때도 기본적으로 `any`로 취급한다(`noImplicitAny` 옵션과 관련).

```ts
let msg: any = "hello world";
msg = 2;                 // 허용됨
msg.toUpperCase();        // 컴파일 시점엔 오류 없음 — 하지만 msg가 숫자면 런타임 오류
```

`any`의 문제는, 담긴 값이 실제로 무엇인지 검사하지 않고도 아무 메서드나 호출할 수 있어서, 실수를 그대로 런타임까지 끌고 간다는 점이다. 이를 보완하는 것이 **`unknown`** 이다 — 뭐든 담을 수 있다는 점은 `any`와 같지만, 실제로 값을 사용하려면 반드시 타입을 검사(조건 처리)하도록 강제한다.

```ts
let msg: unknown = "hello world";
msg.toUpperCase(); // Error: Object is of type 'unknown'

if (typeof msg === "string")
    msg.toUpperCase(); // OK — 조건 검사 후에는 허용
```

즉 `any`를 써야 하는 상황이라면 되도록 `unknown`으로 대체하고, 사용 시점에 타입 검사를 강제하는 편이 안전하다.

### 6-1. Type Assertions — 검사 없이 타입을 단언하기

조건 검사를 매번 거치기 번거로울 때, 개발자가 "이 값의 타입은 내가 확실히 안다"고 직접 단언(assert)해서 검사를 생략할 수 있다.

```ts
let value: unknown = "Hello";
console.log((value as string).toUpperCase()); // 강제로 string으로 취급
```

`as` 키워드로 타입을 단언하면 `unknown`이 걸어둔 안전장치를 개발자 책임 하에 우회하는 것이다.

## 7. Union Types — 둘 이상의 타입을 함께 허용

값이 하나의 확정된 타입만 가질 수 없는 경우가 있다 — 예를 들어 문자열 변수의 초기값으로 "아직 값이 없음"을 표현하려면 `null`이나 `undefined`도 함께 담을 수 있어야 한다. 단일 타입만 지정해서는 이런 값을 담을 수 없으므로, 파이프(`|`)로 여러 타입을 나열하는 **유니온 타입**을 쓴다.

```ts
let value: string | undefined = "Hello";
value = "42";     // 가능
value = false;    // 오류 — boolean은 유니온에 없음

type ID = number | undefined;
const value: ID = 1234;
```

`NaN`과 `null`은 서로 다른 값이자 다른 타입이며, `number`와 `NaN`도 별개의 타입으로 다뤄진다는 점도 유니온을 이해할 때 함께 기억해둘 부분이다.

## 8. Literal Types — 값 자체를 타입으로

문자열이나 숫자 리터럴이 타입 표기 위치에 그대로 올 수도 있다. 이 경우 그 변수는 **명시된 값만** 담을 수 있는 타입이 된다.

```ts
let x: "hello" = "hello";
x = "hello";  // OK
x = "howdy";  // Error
```

숫자로도 같은 방식이 가능하다 — 여러 값을 파이프로 나열하면 "이 값들 중 하나만" 허용하는 열거형처럼 쓸 수 있다.

```ts
let level: 0 | 1 | 2 | 3 | 4 = 0;
level++;
level++;
// level = 30; // 오류 — 0~4 범위 밖
```

`number` 타입만으로는 범위를 한정할 수 없다(마이너스든 100이든 다 허용되므로). 리터럴 타입은 "레벨은 0단계부터 4단계까지만 있다" 같은 제약을 타입 수준에서 걸 수 있게 해준다.

## 9. Enum — 이름 붙은 상수의 집합

리터럴 타입이 "값을 나열해서 그것만 허용"하는 방식이라면, **enum**은 값을 나열하는 동시에 각 값에 사람이 읽기 쉬운 **이름**을 붙여 그룹화하는 문법이다.

과거에는 방향 같은 코드값을 숫자로만 관리해서(`var N=1; var S=5;` 등) 어떤 숫자가 어떤 의미인지 기억하기 어려웠고, 이를 문자화하려고 변수를 썼지만 변수는 언제든 값이 바뀔 수 있다는 문제(`S = 7;`처럼)가 있었다. `const`로 바꾸면 값 변경은 막을 수 있지만, 여전히 개별 변수 여러 개로 흩어져 있다는 한계가 남는다. `enum`은 이런 상수 집합을 하나의 이름 아래 그룹핑해서 정의한다.

```ts
enum Direction {
    Up,
    Down,
    Left,
    Right,
}
// Up은 0부터 시작해서 이후 멤버가 1씩 자동 증가한다

enum Level {
    입문,
    초급,
    중급,
    고급,
    특급
}

let level1: Level = Level.입문;
```

첫 번째 멤버에 시작 숫자를 직접 지정하면, 이후 멤버는 그 숫자부터 1씩 증가한다. 단순히 담을 수 있는 값의 범위만 제한하고 싶다면 리터럴 타입으로 충분하지만, 값들을 의미 있는 이름으로 그룹화해서 `Color.RED`처럼 점 표기로 꺼내 쓰고 싶다면 `enum`이 더 직관적이다.

## 10. 함수의 매개변수·반환 타입

함수도 매개변수마다 타입을 지정할 수 있고, 객체를 통째로 전달할 때는 그 구조를 타입으로 미리 정의해두면 편하다.

```ts
interface Point {
    x: number,
    y: number
}
function print(p: Point) {
    console.log(`x:${p.x}, y:${p.y}`);
}
print({ x: 2, y: 3 });
```

반환 타입은 매개변수 목록을 닫는 괄호 뒤, 함수 몸체 앞에 콜론으로 표기한다.

```ts
function add(x: number, y: number): number {
    return x + y;
}
```

반환값의 타입이 선언과 다르면 이 시점에서도 컴파일 오류로 잡아준다.

## 11. Interface vs Type Alias — 실무에서는 interface를 더 쓴다

객체 형태의 타입을 정의하는 방법은 `type`(별칭) 말고 `interface`로도 가능하다.

```ts
type Point1 = { x: number; y: number; };

interface Point2 {
    x: number;
    y: number;
}
```

둘의 결정적인 차이는 **확장(상속) 가능 여부**다. 자바에서 인터페이스가 `extends`로 다른 인터페이스를 확장할 수 있는 것처럼, 타입스크립트의 `interface`도 다른 인터페이스를 확장할 수 있다. 반면 `type`으로 만든 별칭은 그 자체로는 상속 개념이 없다 — 확장하려면 기존 내용을 다시 풀어서 새로 결합해야 한다.

```ts
interface Point {
    x: number;
    y: number;
}

interface Point3D extends Point {
    z: number;
}

const p: Point3D = { x: 1, y: 2, z: 3 };
```

`Point3D`는 `Point`가 가진 `x`, `y`를 그대로 물려받고 `z`만 추가로 정의한 것이다 — `Point`를 다시 풀어 쓸 필요 없이 `extends`로 이어 붙이기만 하면 된다.

이 차이 때문에 실무에서는 대체로 이렇게 구분해서 쓴다.

- 단순히 값을 담는 그릇 역할로, 이후 확장할 계획이 없다면 → `type`
- 나중에 다른 구조와 결합하거나 확장될 가능성이 있다면 → `interface`

다만 절대적인 규칙은 아니고 상황에 맞게 유연하게 선택하면 된다. 실무에서는 인터페이스를 쓰는 비중이 훨씬 높은 편이다(체감상 8~90%).

## 12. 자바스크립트의 Class — 생성자 함수와 `this`

자바스크립트는 원래 캡슐화·상속·다형성을 언어 차원에서 지원하지 않는다 — 클래스라는 정의 자체가 없고, 은닉성(private)도 지원하지 않아 모든 것이 노출·확장 가능한 구조다. 그럼에도 자바스크립트 생태계의 모든 라이브러리는 객체 지향적으로 구성되어 있고, 개발자들은 이 언어로 객체지향을 흉내 내는 관용적인 패턴을 만들어왔다. 그 첫 단추가 **생성자 함수**다.

```js
function Exam() {
    kor = 1;
    eng = 2;
    math = 3;

    console.log(kor, eng, math);
    console.log('this', this.kor, this.eng, this.math);
}

let exam1 = Exam();       // 그냥 호출
let exam2 = new Exam();   // 생성자로 호출
```

함수 이름이 대문자로 시작하는 것은 일반 함수(동사, 소문자 시작)와 구분해 "이 함수는 생성자 용도로 쓴다"는 관례적 표시다. 이 함수를 호출하는 방법은 두 가지다.

- **그냥 호출**(`Exam()`): 일반 함수 호출과 같다. 함수 안에서 값을 반환하지 않으므로 결과는 `undefined`다. `this`는 가리키는 대상이 없어 전역 객체(Node.js에서는 `global`)를 가리키게 되고, `kor`/`eng`/`math` 같은 선언 없는 대입은 전역 객체의 속성으로 만들어진다.
- **`new`를 통한 호출**(`new Exam()`): 방금 생성된 빈 객체가 만들어지고, 함수 안의 `this`가 그 객체를 가리키게 된다. 함수가 끝나면 `this`가 가리키던 그 객체가 자동으로 반환된다 — 그래서 `exam2`에는 `kor`/`eng`/`math`를 속성으로 가진 객체가 담긴다.

즉 같은 함수라도 `new`로 호출하느냐에 따라 "그냥 실행되는 함수"와 "객체를 생성하고 초기화하는 생성자"라는 전혀 다른 역할로 쓰인다는 것이 자바스크립트가 클래스 없이 객체지향을 흉내 내는 방식의 출발점이다.
