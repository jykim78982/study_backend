# 리액트 컴포넌트 생명주기 — 서버·클라이언트 실행, 하이드레이션, useEffect와 상태 변수

## 1. 서버 컴포넌트는 "날 것"으로 보면 서버가 만든 페이지가 보인다

브라우저 렌더링을 거치지 않고 서버 응답 원문을 그대로 보면, 이미 완성된 HTML 안에 컴포넌트가 만든 내용(`<h1>`, `<div>` 등)이 그대로 박혀 있다. 이는 브라우저의 자바스크립트가 나중에 만든 게 아니라 **서버가 이미 문서를 만들어서 보냈다**는 뜻이다. 이렇게 서버가 완성된 문서를 만들어 전달하는 방식이 서버 사이드 렌더링(SSR)이며, 이 결과물은 검색엔진 크롤러(구글봇 등)가 곧바로 읽을 수 있다.

이 서버 렌더링을 수행하는 주체는 리액트가 아니라 **Next.js**다. 컴포넌트를 만드는 문법(JSX, 함수형 컴포넌트)은 리액트 규칙을 그대로 따르지만, 그 컴포넌트를 서버에서 실행해 완성된 문서로 바꾸는 능력은 Next.js가 리액트 서버 컴포넌트 위에 구현한 것이다.

## 2. `"use client"`의 진짜 의미

컴포넌트 파일 맨 위에 `"use client"`를 쓰면 "이 컴포넌트는 서버에서 건드리지 말고 클라이언트에서 다뤄라"라는 뜻처럼 보이지만, 정확히는 다르다.

- 아무것도 쓰지 않으면 기본값은 **서버 컴포넌트**다. 이 말은 "서버에서만 실행된다"는 뜻이 아니라 "Next.js(서버)도 읽어서 실행해도 된다"는 뜻이며, 실제로는 서버에서 한 번 실행되고 끝난다.
- `"use client"`를 쓰면 "클라이언트에서도 실행하겠다"는 선언이 된다. 이 컴포넌트는 서버에서 한 번 렌더링되어 초기 HTML을 만드는 데도 쓰이고, 이후 브라우저에 전달된 스크립트 안에서 다시 한 번 실행된다.

즉 `"use client"`가 붙으면 서버·클라이언트 양쪽에서 실행되어 콘솔 로그가 두 번(서버 터미널, 브라우저 콘솔) 찍히고, 붙지 않으면 서버에서만 실행되어 서버 쪽에만 로그가 찍힌다.

## 3. 스크립트는 왜 완성된 페이지를 따라가는가 — 하이드레이션

서버가 이미 완성된 문서를 보냈다면 스크립트를 또 보낼 필요가 없어 보이지만, 실제로는 페이지와 함께 스크립트도 전달된다. 그 이유는 브라우저에서 벌어지는 **동적인 부분**(클릭 이벤트, 상태 변화에 따른 화면 갱신 등)을 처리해야 하기 때문이다.

브라우저에 도착한 스크립트는 이미 존재하는 문서를 지우고 새로 만드는 것이 아니라, 서버가 만들어 보낸 문서 구조가 자신이 예상한 것과 일치하는지 확인한 뒤 그 위에 이벤트 리스너 등을 붙이는 작업만 한다. 이 작업을 **하이드레이션(Hydration)**이라 한다.

과거 리액트를 JSP·PHP·ASP 같은 서버 페이지 기술 위에 얹으려 했을 때는, 리액트가 서버가 만든 내용을 통째로 지우고 다시 그리는 방식으로 동작해 화면이 한 번 깜빡이는 문제가 있었다. 하이드레이션은 이 문제를 피해 **기존 문서는 그대로 두고 필요한 이벤트만 덧붙이는** 방식으로 동작한다.

## 4. 마운트(Mount)와 언마운트(Unmount)

브라우저는 `window.onload`처럼 문서 전체가 완성되는 시점을 기준으로 삼지만, 컴포넌트는 문서 전체와 무관하게 특정 노드 위치(예: `<body>` 안 특정 영역)에 붙었다 떨어졌다 하면서 페이지 내용을 바꾼다.

- 컴포넌트가 문서 트리의 특정 노드에 자리를 잡는 것 — **마운트**
- 그 컴포넌트가 다른 컴포넌트로 교체되며 자리에서 떨어져 나가는 것 — **언마운트**

컴포넌트 생명주기(마운트/업데이트/언마운트)는 이렇게 페이지 전체의 로드 이벤트와는 별개로, 노드 단위로 반복해서 발생한다.

## 5. useEffect — 생명주기와 연결된 후크 함수

`useEffect`는 리액트의 후크(Hook) 함수 중 하나로, 컴포넌트 생명주기의 특정 시점에 실행할 콜백 함수를 등록한다. 후크 함수는 컴포넌트가 가진 변수를 클로저로 공유하면서, 서버가 아니라 반드시 **클라이언트에서만** 실행된다 — 서버 컴포넌트에는 "마운트"라는 개념 자체가 없기 때문이다. 그래서 `useEffect`를 쓰는 컴포넌트는 자동으로 클라이언트 코드로 포함되어 브라우저에 전달된다.

두 번째 인자(의존성 배열)의 유무와 내용에 따라 호출 시점이 달라진다.

| 두 번째 인자 | 실행 시점 |
|---|---|
| 아예 없음 | 렌더링될 때마다(업데이트마다) 매번 실행 |
| 빈 배열 `[]` | 마운트될 때 **딱 한 번**만 실행 |
| 값이 든 배열 `[count]` | 마운트 시 1회 + 배열 안의 값이 바뀔 때마다 실행 |

같은 조건(같은 값이 바뀔 때 실행해야 하는 로직)이면 의존성 배열에 여러 값을 나란히 넣어 하나의 `useEffect`로 묶을 수 있고, 조건이 다르면 `useEffect`를 여러 개로 나눠 작성한다.

## 6. 상태 변수 vs 일반 변수

화면에 값을 반영하려고 일반 변수(`let count = 0`)를 그대로 증가시키고 렌더링에 사용하면, 콘솔에는 값이 계속 증가하는데도 **화면은 갱신되지 않는다.** 일반 변수를 바꾸는 것만으로는 리액트가 "다시 그려야 한다"는 사실을 알 수 없기 때문이다.

리액트에서 화면 갱신에 영향을 줘야 하는 값은 반드시 `useState`로 만든 **상태 변수**를 통해 관리해야 한다.

```js
const [count, setCount] = useState(0);
```

- `count`는 현재 상태값을 읽기만 하는 변수다. 직접 대입해서 바꿀 수 없다.
- `setCount`는 값을 바꾸고 리액트에게 "화면을 다시 그려라"라고 알리는 함수다.

값을 갱신할 때는 두 가지 방식이 있다.

```js
setCount(count + 1);       // 현재 렌더링된 count를 그대로 사용
setCount(c => c + 1);      // 갱신 직전의 최신 값을 리액트가 넘겨준다
```

클릭이 빠르게 여러 번 연속 발생하는 상황에서는 `count`를 직접 참조하는 방식이 아직 반영되지 않은(렌더링 이전) 값을 참조해 엇박자가 날 수 있다. 함수형 업데이트(`c => c + 1`)는 리액트가 관리하는 최신 값을 넘겨받아 계산하므로 이런 문제가 없어 더 안전하다.

**모든 화면 표시 값이 상태 변수여야 하는 것은 아니다.** 서버에서 한 번 가져와 화면에 그대로 뿌리기만 하고 이후 그 값 자체의 변화가 다시 화면에 반영될 필요가 없다면 일반 변수로도 충분하다. 반대로 사용자의 조작(카테고리 선택, 검색어 입력 등)에 따라 값이 바뀌고 그 변화가 다시 요청이나 렌더링에 영향을 줘야 한다면 상태 변수로 관리해야 한다.

## 7. 정해진 개수만큼 반복하기 — `Array.from`

값을 가진 배열이 아니라 "개수"만 있을 때, 그 개수만큼 반복하려면 `Array.from({ length })`으로 빈 배열을 만든다.

```js
Array.from({ length: count }).map((_, index) => (
  <div key={index}>hello {index}</div>
));
```

- `{ length: count }`는 배열 자체가 아니라 `length` 속성만 가진 유사 배열 객체이며, `Array.from`이 이를 이용해 `count`개의 `undefined` 항목을 가진 배열을 만들어 준다.
- 반복되는 요소마다 리액트가 개별 노드를 식별할 수 있도록 `key`를 반드시 지정해야 한다. 값 자체가 필요 없다면 관례상 `_`로 표기하고, 인덱스를 `key`로 사용한다.

## 8. 실습 코드 — `test/lifecycle/page.js`

```js
"use client"

import { useEffect, useState } from "react"

export default function LifeCyclePage(){
    const [count, setCount] = useState(0);
    console.log("Page 상단 출력");

    // 마운트될 때 1회만 호출
    useEffect(() => {
        console.log("Mounted");
    }, []);

    // count가 바뀔 때마다 호출 - 횟수는 알 수 없다
    useEffect(() => {
        console.log("count 수 만큼 서버에서 데이터 요청");
    }, [count]);

    return <main>
        <h1>컴포넌트 생명주기</h1>
        <div>
            <button onClick={() => {
                setCount(c => c + 1);
            }}>count + 1</button>
        </div>
        <div>count : {count}</div>
        <div>
            {
                Array
                .from({ length: count})
                .map((_, index) => <div key={index}>hello {index}</div>)
            }
        </div>
    </main>
}
```

이 코드에서 `"Page 상단 출력"`은 컴포넌트 함수 본문이 실행될 때마다(렌더링될 때마다) 찍히고, `"Mounted"`는 최초 마운트 시 한 번만, `"count 수 만큼 서버에서 데이터 요청"`은 마운트 시 1회와 `count`가 바뀔 때마다 찍힌다.

## 9. 데이터를 가져오는 위치와 검색엔진 노출

데이터 패치(`fetch`)를 어디서 실행하느냐에 따라 검색엔진 노출 여부가 갈린다.

- `useEffect` 안에서 데이터를 가져오면, 그 로직은 클라이언트 컴포넌트에 포함되어 **브라우저에서만** 실행된다. 서버는 데이터가 없는 빈 문서를 보내고, 실제 내용은 마운트된 뒤 브라우저에서 채워진다.
- 서버 컴포넌트에서 `await fetch(...)`로 데이터를 가져와 렌더링하면, 서버가 데이터가 채워진 완성된 문서를 만들어 보낸다.

크롤러는 브라우저에서 실행되는 `useEffect`를 기다려주지 않고, 서버가 보낸 문서를 있는 그대로 읽고 떠난다. 그래서 이 차이가 문제가 되는지 여부는 그 페이지가 검색에 노출될 필요가 있는지에 달려 있다.

- **노출되어야 하는 페이지**: 메인 페이지, 상품·메뉴 목록, 상세 페이지처럼 불특정 방문자가 검색을 통해 찾아올 수 있어야 하는 페이지. `useEffect` 패치를 쓰면 크롤러는 데이터가 채워지기 전의 빈 문서만 보게 되므로, 데이터 패치를 **서버 컴포넌트 본문**에서 수행해야 한다.
- **노출되지 않아도(오히려 되면 안) 되는 페이지**: 로그인 페이지, 회원가입 페이지, 로그인해야만 볼 수 있는 마이페이지, 관리자 페이지처럼 특정 사용자만 접근해야 하는 페이지. 크롤러가 그 내용을 읽든 말든 상관이 없으므로 `useEffect`에서 클라이언트 패치를 해도 무방하다(오히려 관리자 페이지가 검색에 노출되면 보안 문제가 된다).

**클라이언트 컴포넌트의 `useEffect`에서 패치**

```js
"use client"

import { useEffect, useState } from "react"

export default function MenusPage() {
    const [menus, setMenus] = useState([]);

    useEffect(() => {
        fetch('http://localhost:8080/api/menus')
            .then(res => res.json())
            .then(data => setMenus(data));
    }, []);

    return <main>
        <h1>메뉴</h1>
        <ul>
            {menus.map(menu => <li key={menu.id}>{menu.korName}</li>)}
        </ul>
    </main>
}
```

`useEffect`는 마운트된 뒤 브라우저에서만 실행되므로, 서버는 `menus`가 아직 빈 배열인 상태의 문서(`<ul></ul>`만 있는 빈 목록)를 그대로 보낸다. 검색엔진 크롤러는 이 빈 문서만 보고 떠나므로 메뉴 목록 내용이 검색에 노출되지 않는다.

**서버 컴포넌트 본문에서 직접 패치 (실제 `ncafe` 메뉴 페이지)**

```js
export default async function MenusPage({ searchParams }) {
    const params = await searchParams;
    const name = params.name || '';

    const getMenus = async () => {
        let url = 'http://localhost:8080/api/menus';
        if (name) url += `?name=${name}`;
        const res = await fetch(url);
        const data = await res.json();
        return data;
    };

    const menus = await getMenus();

    return (
        <main>
            <h1>메뉴</h1>
            <ul>
                {menus.map((menu) => (
                    <li key={menu.id}>{menu.korName} - {menu.price}원</li>
                ))}
            </ul>
        </main>
    );
}
```

`"use client"`가 없으므로 이 컴포넌트는 서버에서 실행된다. `await fetch(...)`로 받아온 `menus`가 이미 채워진 상태로 HTML을 완성해 보내기 때문에, 크롤러도 실제 메뉴 이름과 가격이 담긴 문서를 그대로 읽을 수 있다.

이때 목록 데이터(`menus`)는 한 번 가져와 그대로 렌더링할 뿐 이후 그 값 자체가 사용자 조작으로 다시 바뀌지 않으므로, 상태 변수가 아니라 일반 변수로도 충분하다 — 반면 검색어·카테고리처럼 사용자가 바꾸는 값은 상태 변수(또는 위 예시처럼 URL 쿼리 파라미터인 `searchParams`)로 관리해 그 변화가 다시 서버 요청으로 이어지게 한다.

## 10. 정리

| 개념 | 핵심 |
|---|---|
| `"use client"` | "클라이언트에서도 실행" 선언. 서버 실행을 막는 게 아니라 클라이언트 실행을 추가한다 |
| 하이드레이션 | 서버가 만든 문서를 지우지 않고, 그 위에 이벤트만 덧붙이는 작업 |
| 마운트/언마운트 | 컴포넌트가 문서 트리의 특정 노드에 붙고 떨어지는 것 |
| `useEffect` | 클라이언트에서만 실행되는 생명주기 후크. 의존성 배열로 실행 시점을 제어 |
| 상태 변수 | `useState`로 만들며, 값이 바뀌면 리액트가 화면을 다시 그린다 |
| 일반 변수 | 값이 바뀌어도 화면에 자동 반영되지 않는다 — 재렌더링에 영향 없는 값에 사용 |
| 데이터 패치 위치 | 검색 노출이 필요하면 서버 컴포넌트에서, 클라이언트 전용 로직이면 `useEffect`에서 |
