# Next.js 중첩 레이아웃과 라우트 그룹

`<a>` 대신 `Link`를 쓸 때의 상대 경로 함정, 컴포넌트를 어디에 둘지, 페이지마다 다른 레이아웃이 필요할 때의 중첩 레이아웃과 라우트 그룹을 다룬다.

## 1. `<a>` 태그의 문제 — 페이지 전체 새로고침

`<a>` 태그는 외부 링크로 이동할 때만 쓴다. 앱 안에서 페이지를 이동할 때 `<a>`를 쓰면 페이지 전체가 새로고침된다.

```html
<!-- ❌ 앱 내부 이동에 a 태그 -->
<a href="/">home</a>
<a href="http://localhost:3000">home</a>

<!-- ✅ Next.js가 제공하는 Link -->
<Link href="/">home</Link>
```

## 2. 상대 경로의 함정

`Link`를 쓰더라도 `href`에 상대 경로를 적으면 문제가 생길 수 있다. `<Link href="menus">`처럼 상대 경로로 적으면, **현재 페이지의 경로를 기준으로** 목적지를 찾기 때문이다. 예를 들어 `/`에서는 `menus`가 `/menus`로 잘 찾아가지만, `/admin/menus`에서 같은 상대 경로 `menus`를 쓰면 `/admin/menus`를 기준으로 다시 `menus`를 찾으려 해서 엉뚱한 경로가 된다. 공통 헤더처럼 **모든 페이지에서 똑같이 나타나는 링크**는 페이지마다 기준 경로가 다르므로, 반드시 `<Link href="/menus">`처럼 **절대 경로**로 써야 한다.

## 3. 컴포넌트를 어디에 둘 것인가 — 코로케이션

컴포넌트를 분리해서 파일로 만들 때, Next.js는 두 가지 방식을 제안한다.

1. `app/` 밖에 `components/` 같은 전용 폴더를 만들어 몰아둔다.
2. 그 컴포넌트를 사용하는 페이지(또는 그 페이지들의 가장 가까운 공통 상위) **근처에** 둔다.

실무에서 더 권장되는 방식은 2번이다. 자바스크립트·HTML·CSS가 하나의 기능을 위해 서로 근처에 모여 있는 것이 페이지를 오갈 때 탐색 시간을 줄여준다 — 이렇게 관련된 코드를 가까이 두는 방식을 **코로케이션(Colocation)**이라 부른다. Angular나 Vue의 SFC(싱글 파일 컴포넌트)는 애초에 이 방식을 기본으로 채택하고 있다.

`app/` 밖(예: 전역 `components/`)에 두는 경우는, 지금 이 프로젝트뿐 아니라 **다음에도 재사용할 라이브러리성 컴포넌트**로 분리하고 싶을 때다. 특정 페이지에서만 쓰는 컴포넌트라면 그 페이지 근처에 두는 것이 원칙이다.

### 3-1. 컴포넌트 파일이 URL로 요청되지 않는 이유

`app/` 안(라우트 영역)에 컴포넌트 파일을 두면 "이 파일도 URL로 요청되는 거 아닐까" 걱정할 수 있지만, 그렇지 않다. Next.js의 앱 라우터는 **폴더 경로**를 URL로 매핑하지만, 그 경로에서 실제로 응답을 만드는 것은 오직 `page.js`라는 정해진 이름의 파일뿐이다. 폴더 안에 다른 이름의 컴포넌트 파일이 있어도 `page.js`가 아니므로 URL로 요청할 수 없다.

다만 이름이 마음에 걸린다면, 파일명 앞에 언더스코어(`_`)를 붙여 라우팅 후보에서 아예 제외되는 비공개 폴더로 만드는 방법도 있다.

### 3-2. 컴포넌트 이름 짓기 — 두 단어 이상 권장

라우트 영역(`app/` 안) 안의 폴더·`page.js`는 URL 규칙에 맞춰 소문자로 쓴다. 하지만 직접 만든 컴포넌트를 `header`처럼 소문자로 지으면, JSX는 이를 사용자 정의 컴포넌트가 아니라 HTML 표준 태그 `<header>`로 그대로 해석해버린다 — 즉 이름이 헷갈리는 수준이 아니라, 애초에 내가 만든 함수가 아니라 브라우저 내장 태그가 렌더링되어 컴포넌트로 쓸 수조차 없게 된다.

다만 JSX는 대소문자를 구분해서 태그를 해석한다 — 소문자로 시작하는 태그는 HTML 표준 태그로, 대문자로 시작하는 태그는 사용자 정의 컴포넌트로 인식한다. 그래서 `Header`처럼 첫 글자만 대문자로 지정하면 HTML의 `<header>`와 완전히 구분되어 이름이 겹칠 걱정 없이 쓸 수 있다.

```jsx
// components/Header.js
export default function Header() {   // 대문자로 시작, 파일명도 대문자
  return ( /* ... */ );
}
```

다만 대문자로 시작하는 것만으로는 부족하다고 보고, 가능하면 `NcafeHeader`처럼 두 단어 이상으로 지어 식별성을 더 높이는 것을 권장한다.

## 4. 레이아웃은 "틀"만 담당한다

`layout.js`는 각 페이지가 공통으로 갖는 틀(방 구조)을 정의하는 자리이지, 페이지의 실제 내용을 대신 채우는 자리가 아니다. 레이아웃에 머리글·바닥글을 두고 `{children}` 자리만 페이지 내용으로 바꿔 끼우도록 구성해야, 페이지 파일에는 그 페이지만의 콘텐츠(예: `<main>`)만 남는다.

```jsx
// app/layout.js — 방의 틀
<Header />
{children}
<Footer />
```

```jsx
// app/page.js — 그 방에 채워 넣는 콘텐츠만
export default function Home() {
  return <main>...</main>;
}
```

## 5. 중첩 레이아웃(Nested Layout)

Next.js의 레이아웃은 페이지마다 존재할 수 있고, 하위 폴더에 레이아웃을 추가하면 상위 레이아웃 **안에 겹쳐서** 적용된다 — 이를 **중첩 레이아웃**이라 부른다.

예를 들어 메뉴 목록 페이지에만 사이드바(`aside`)가 필요하다면, 다른 페이지에는 영향을 주지 않도록 `app/menus/layout.js`를 새로 만든다.

```jsx
// app/menus/layout.js
export default function MenusLayout({ children }) {
  return (
    <div style={{ display: 'flex' }}>
      <aside>
        <h2>사이드 메뉴</h2>
      </aside>
      <div>{children}</div>
    </div>
  );
}
```

이렇게 하면 `/menus`로 들어온 요청은 루트 레이아웃(`Header`/`Footer`) 안에 다시 `MenusLayout`(사이드바)이 겹쳐 씌워지고, 그 안에 `app/menus/page.js`가 최종적으로 꽂힌다. 반면 `/`(루트) 요청은 `app/menus/layout.js`의 영향을 전혀 받지 않는다 — 레이아웃은 **자신이 속한 폴더 트리의 하위 경로에만** 영향을 주는 계층 구조이기 때문이다.

## 6. 레이아웃 "대체"가 필요할 때 — 라우트 그룹

중첩 레이아웃은 상위 레이아웃 **안에 겹쳐지는** 방식만 지원한다. 하지만 관리자 페이지(`/admin/...`)처럼 머리글·바닥글 자체가 완전히 달라져야 하는 경우는 겹치는 것이 아니라 **통째로 다른 레이아웃으로 바뀌어야** 한다. Next.js는 이런 "대체" 관계를 직접 지원하지 않으므로, 중첩 모델 안에서 이를 흉내 내는 방법이 필요하다.

방법은 루트 레이아웃을 완전히 비워두고, 실제 공통 UI(헤더·바닥글)는 그 아래 폴더 두 개로 각각 내려보내는 것이다.

```
app/
├── layout.js          ← 아무 것도 없이 {children}만
├── admin/
│   ├── layout.js      ← 관리자 전용 헤더·바닥글
│   ├── components/
│   │   └── AdminHeader.js
│   └── menus/page.js
└── (anon)/
    ├── layout.js       ← 메인 사이트 헤더·바닥글
    ├── components/
    │   └── NcafeHeader.js
    ├── page.js
    └── menus/page.js
```

문제는 `admin`처럼 실제 폴더를 만들면 URL에 그 이름이 그대로 들어간다는 점이다(`/admin/menus`는 의도한 대로지만, 메인 사이트 쪽도 구분을 위해 폴더를 만들면 `/anon/menus`처럼 원치 않는 세그먼트가 URL에 끼어든다). 이를 해결하는 것이 **라우트 그룹**이다 — 폴더 이름을 소괄호로 감싸면(`(anon)`), 그 폴더는 레이아웃을 나눌 때만 쓰이고 **URL 경로에서는 빠진다**.

```
app/(anon)/menus/page.js   → 실제 URL은 /menus (anon은 빠짐)
app/admin/menus/page.js    → 실제 URL은 /admin/menus
```

이렇게 하면 메인 사이트용 페이지들은 `(anon)/layout.js`의 헤더·바닥글을, 관리자 페이지들은 `admin/layout.js`의 헤더·바닥글을 각각 적용받으면서도, 메인 사이트 쪽 URL에는 불필요한 세그먼트가 남지 않는다.

## 7. 정리

| 원칙 | 내용 |
|---|---|
| 이동 | 앱 내부 이동은 `Link`, 공통 링크는 반드시 절대 경로로 작성 |
| 컴포넌트 위치 | 재사용 라이브러리가 아니라면 사용하는 페이지 근처에 두는 코로케이션 원칙 |
| 레이아웃 역할 | `layout.js`는 틀만, 콘텐츠는 `page.js`가 담당 |
| 중첩 | 하위 폴더에 `layout.js`를 추가하면 상위 레이아웃 안에 겹쳐지는 중첩 레이아웃 |
| 대체 | 레이아웃을 완전히 갈아 끼워야 할 땐 라우트 그룹 `(이름)` 폴더로 URL에 영향 없이 레이아웃만 분리 |
