# Next.js - 컴포넌트 분리

디렉터리 구조와 라우팅을 정했다면, 그다음은 **하나의 페이지 안에서 화면을 어떻게 나눌 것인가**의 문제다. 메뉴 목록 페이지(카테고리 필터 + 가격 필터 + 메뉴 카드 목록)를 예로 컴포넌트 분리 기준, 데이터 패치 방식, 서버 페이지의 상태 관리 방식을 정리한다.

## 1. 컴포넌트는 어떤 기준으로 나누는가 — 보이는 대로, 계층을 생각하며

컴포넌트를 나누는 기준은 특별한 이론이 아니라 **화면에 보이는 대로** 나누는 것이다. 이미 헤더·메인·푸터로 나뉘어 있는 페이지라면, 그 메인 블록 안에서도 콘텐츠 단위(카테고리 필터, 가격 필터, 메뉴 목록)로 나눌 수 있다.

이때 반드시 **계층(트리)**을 먼저 생각해야 한다. 메인을 나눌 때 "메인 안에 A, 메인 안에 B"처럼 같은 층위로 나눌지, "메인 안에 A, A 안에 B"처럼 중첩시킬지에 따라 구조가 완전히 달라진다. 처음에는 콘텐츠 단위로 큰 덩어리(이 예시에서는 카테고리 필터·가격 필터·메뉴 목록 세 개)만 나누고, 그 안이 복잡하다 싶으면 그 컴포넌트 내부에서 스스로 더 잘게 나누면 된다 — 구조적 프로그래밍에서 함수를 점진적으로 쪼개듯, 컴포넌트도 필요할 때마다 그 안에서 분리하면 된다.

## 2. AI에게 맡길 때 — 기존 프로젝트의 관례부터 읽게 한다

컴포넌트 분리 작업 자체는 AI에게 맡기는 것이 효율적이지만, 그전에 반드시 **현재 프로젝트가 이미 따르고 있는 관례**를 AI가 먼저 읽고 파악하게 해야 한다. AI는 새 코드를 만들 때 그 프로젝트의 맥락이 아니라 자신이 가장 흔하게 학습한 방식을 기본값으로 삼기 쉽기 때문이다.

대표적인 예가 CSS 시스템이다. 기존 코드가 CSS Modules(유틸리티 클래스가 아니라 의미 있는 이름의 클래스)를 쓰고 있는데도, AI가 이를 미리 확인하지 않으면 자신이 가장 익숙한 Tailwind 방식으로 새 컴포넌트를 만들어버릴 수 있다. 그러면 본체는 CSS Modules, 새로 뽑아낸 컴포넌트는 Tailwind가 되어 스타일 체계가 어긋난다.

이 원칙은 CSS에만 해당하지 않는다. 네이밍 규칙, 폴더·파일 구조, API 응답 형식, 상태관리 패턴, 에러 처리 방식 등 프로젝트마다 이미 정해져 있는 어떤 관례든 마찬가지다. AI에게 특정 작업을 시키기 전에 "이 프로젝트는 이런 방식을 쓰고 있으니 그걸 따르라"고 먼저 인식시키지 않으면, AI는 자신이 아는 일반적인 방식과 프로젝트 고유의 방식을 섞어버려 코드베이스 안에 서로 다른 스타일이 뒤섞이게 된다.

또한 AI에게 나눠달라고 지시할 때는 원하는 결과를 구체적으로 확인해야 한다. AI는 "구현해달라고 한 적 없는" 것까지 스스로 판단해 실행하는 경향이 있어서, 의도한 세 덩어리(카테고리 필터·가격 필터·메뉴 목록) 대신 엉뚱한 단위(예: 메뉴 카드 하나)로 쪼개거나 엉뚱한 폴더에 컴포넌트를 만들어 놓는 경우가 흔하다. 그래서 처음에는 조심스럽게, 결과를 검증해가며 진행해야 한다.

## 3. 형제가 아니라 트리 — 컴포넌트끼리 직접 지시하지 않는다

컴포넌트를 나눠서 같은 부모 아래 나란히 배치하면 겉보기엔 "형제"처럼 보이지만, 실제로는 부모가 그 컴포넌트들을 각각 소유(포함)하고 있는 구조다. 이 상태에서 한 컴포넌트가 다른 형제 컴포넌트를 직접 참조해서 동작을 지시하게 만들면, 컴포넌트 사이의 관계가 트리가 아니라 그물망이 되어버린다.

- 트리 구조를 지키려면, 형제끼리 서로 지시하는 대신 **부모가 중간에서 제어**해야 한다.
- A 컴포넌트에서 발생한 사용자 이벤트(예: 카테고리 클릭)가 B 컴포넌트(메뉴 목록)에 영향을 줘야 한다면, A가 B를 직접 호출하는 게 아니라 A가 부모에게 알리고, 부모가 그 내용을 B에게 전달하는 방식으로 처리한다.

## 4. 데이터는 각자 책임진다 — 부모가 다 가져와서 내려주지 않는다

컴포넌트를 나눈 뒤 각 컴포넌트가 필요로 하는 데이터(카테고리 목록, 메뉴 목록 등)를 누가 가져올 것인가도 정해야 한다.

- **부모가 전부 가져와서 자식에게 내려주는 방식**은 지양한다. 부모와 자식이 데이터 형태로 강하게 묶이고, 자식이 스스로 독립적으로 동작할 수 없게 된다.
- **각 컴포넌트가 자기 데이터는 자기가 가져오는 방식**이 바람직하다. 분리된 컴포넌트는 이름만 나뉜 것이 아니라, 실제로 "수술"(자기가 필요한 걸 스스로 해결하는 것)까지 할 수 있어야 진짜로 분리된 것이다.

즉 부모가 API를 호출해 데이터를 준비한 뒤 `props`로 넘겨주던 방식에서, 카테고리 필터·메뉴 목록 컴포넌트가 각자 자신의 API를 호출하는 방식으로 바뀐다. 컴포넌트 사이에 불필요한 데이터 전달 경로가 있으면 있을수록 결합도가 올라가므로, 서로 주고받는 것은 최소화하는 편이 좋다.

## 5. 그런데 페이지만 가질 수 있는 것 — `searchParams`

모든 데이터를 각자 책임지게 하고 싶어도, **URL 쿼리 스트링(주소 뒤의 `?category=1`, `?price=...` 같은 값)은 오직 페이지 컴포넌트만 전달받을 수 있다.** 일반 컴포넌트는 URL을 직접 가질 수 없기 때문에, URL을 따라오는 값은 반드시 페이지가 받은 뒤 자식에게 넘겨주는 방식으로만 쓸 수 있다.

예를 들어 메뉴 목록 페이지에서, 현재 선택된 카테고리를 하이라이트하려면 그 값(`currentCategoryId`)이 필요하다. 이 값의 출처는 컴포넌트 자신의 데이터가 아니라 URL의 쿼리 스트링이므로, 페이지가 `searchParams`에서 꺼내 `props`로 자식에게 전달해야 한다. 이 경우는 컴포넌트 자급자족 원칙의 예외가 아니라, 애초에 페이지만 가질 수 있는 값이기 때문에 어쩔 수 없이 페이지가 대신 받아 전달하는 것이다.

## 6. `searchParams`는 Promise다 — 타입 정의와 `await`

최신 버전의 Next.js에서 페이지 컴포넌트가 받는 `searchParams`는 객체가 아니라 **Promise로 감싸진 값**이다. 페이지 함수 자체가 `async`이기 때문에, 매개변수로 들어오는 값도 비동기로 다뤄야 한다.

```typescript
interface MenusPageProps {
  searchParams: Promise<{
    category?: string;
    price?: string;
  }>;
}

export default async function MenusPage({ searchParams }: MenusPageProps) {
  const { category, price } = await searchParams;
  const currentCategoryId = category ? parseInt(category, 10) : null;
  const currentPrice = price || null;

  // ...
}
```

- 쿼리 스트링으로 들어오는 값은 전부 문자열이므로, 타입도 `string`(선택적이면 `string?`)으로 정의한다. 숫자로 써야 한다면 `parseInt` 등으로 직접 변환해야 한다.
- `searchParams`를 `props` 타입 안에 중첩해서 정의하는 이유는, 페이지 컴포넌트가 받는 매개변수가 `searchParams` 하나만이 아니라 다른 것(예: 동적 라우트의 `params`)도 함께 올 수 있는 구조이기 때문이다. 그래서 페이지 전체의 `props` 타입 안에 `searchParams`라는 이름의 속성 하나로 자리를 잡아둔다.
- `searchParams`가 Promise이므로, 그 안의 값을 쓰려면 반드시 `await searchParams`로 먼저 풀어낸 다음 구조 분해해야 한다. 바로 `searchParams.category`처럼 점을 찍어 쓸 수 없다.

## 7. 컴포넌트 나누기 후 데이터 흐름 다시 보기

정리하면, 앞서 나눈 카테고리 필터 · 가격 필터 · 메뉴 목록 세 컴포넌트는 다음과 같이 동작한다.

| 컴포넌트 | 데이터 | 출처 |
|---|---|---|
| 카테고리 필터 | 카테고리 목록 | 스스로 API 호출 |
| 카테고리 필터 | 현재 선택된 카테고리(하이라이트용) | 페이지가 `searchParams`에서 꺼내 `props`로 전달 |
| 메뉴 목록 | 메뉴 데이터 | 스스로 API 호출(필터 조건은 URL 값을 반영) |

각 컴포넌트가 스스로 해결할 수 있는 데이터는 스스로 가져오게 하고, URL이라는 페이지의 전유물에서만 나오는 값만 페이지가 대신 받아 내려준다.

## 8. 서버 컴포넌트가 다시 그려지는 방식 — RSC 요청

클릭할 때마다 브라우저 화면은 깜빡임 없이 바뀌지만, 실제로는 새로고침이 아니라 **서버가 그 페이지를 다시 만들어서 내려주는 것**이다. 브라우저 개발자 도구의 네트워크 탭을 보면, 카테고리를 클릭할 때마다 확장자가 없는 대신 `rsc`라는 표시가 붙은 요청이 발생한다. `RSC`는 React Server Component의 약자로, 서버가 새로 렌더링한 컴포넌트 결과물을 가리키는 식별자다.

즉 헤더·푸터는 그대로 두고, 클릭에 영향을 받는 메뉴 페이지 부분만 서버에서 처음부터 다시 만들어져서 내려온다. 이때 서버가 "지금 어떤 카테고리가 선택됐는지"를 알 수 있는 유일한 단서는 **URL의 쿼리 스트링**이다. 클릭 → URL의 쿼리 스트링 변경 → 서버가 그 값을 읽어 페이지를 다시 생성 → 그 결과를 RSC 형태로 내려받아 화면 갱신, 이 흐름이 서버 페이지에서 "클릭했더니 화면이 바뀌었다"의 실체다.

## 9. 서버 페이지의 상태는 곧 URL이다

서버 페이지에서는 클라이언트 컴포넌트처럼 `useState`로 상태를 들고 있지 않는다. 대신 **화면의 모든 상태(선택된 카테고리, 가격대, 페이지 번호 등)를 URL의 쿼리 스트링에 담아 관리**한다. 구글 검색 결과 페이지마다 내용이 다른 이유도, 그 페이지들의 URL(쿼리 스트링)이 서로 다르기 때문이다.

이 방식의 중요한 함의는, **URL 전체를 공유해야 같은 화면 상태를 재현할 수 있다**는 것이다. 어떤 메뉴가 마음에 들어 친구에게 공유하고 싶다면, 카테고리·가격 등 현재 화면 상태를 결정하는 쿼리 스트링까지 포함한 완전한 URL을 전달해야 상대방도 같은 화면을 보게 된다. 주소창의 경로(`/menus`)만 같고 쿼리 스트링이 다르면, 겉보기엔 "같은 페이지"처럼 보여도 실제로는 다른 화면이다.

새 상태 변수가 추가될 때마다(카테고리, 가격대, 페이지 번호 등), 이를 URL에 반영할지 빠뜨리지 않았는지 항상 점검해야 서버 페이지의 상태 관리가 일관되게 유지된다.

## 10. 어디까지 URL에 반영할 것인가 — 선택의 문제

Next.js 같은 프레임워크로 서버 페이지를 만드는 근본적인 이유는 **검색엔진 노출(SEO)**이다. 검색에 노출되어야 하는 상태 변화는 반드시 URL에 반영해서 서버가 그 상태로 페이지를 다시 만들 수 있게 해야 한다.

다만 모든 상호작용을 검색에 노출할 필요는 없다. 다음 두 방향 중 선택할 수 있다.

- **모든 상태 변화를 URL에 반영**: 카테고리 변경, 가격대 변경 등 모든 조작이 쿼리 스트링에 담기고, 그때마다 서버가 페이지를 새로 만든다. 검색엔진이 각 상태의 조합까지 색인할 수 있다는 장점이 있다.
- **초기 화면만 서버로 제공하고 이후는 클라이언트에서 처리**: 페이지 URL을 `/menus`처럼 고정하고, 초기 데이터만 서버 컴포넌트로 내려준 뒤, 그 안의 상호작용(필터 클릭 등)은 `"use client"`가 붙은 클라이언트 컴포넌트가 상태 변수로 처리한다. 이 경우 초기 진입 화면만 검색에 노출되고, 이후 조작에 따른 화면 변화는 노출되지 않는다.

어느 쪽을 선택할지는 그 페이지에서 어떤 상태까지 검색 노출이 필요한지에 달려 있으며, 프로젝트를 진행하며 상황에 맞게 판단해야 하는 부분이다.

## 11. 배열 맨 앞에 항목 추가하기 — 스프레드 연산자

카테고리 목록 앞에 API가 내려주지 않는 "전체" 항목을 추가로 끼워 넣어야 할 때, 기존 배열을 그대로 새 배열 안에 넣으면 배열이 중첩되어 버린다. 이때 스프레드 연산자로 기존 배열을 펼쳐 넣으면 중첩 없이 하나의 배열로 합쳐진다.

```javascript
const categoriesWithAll = [
  { id: 0, name: '전체', count: totalCount },
  ...categories, // 기존 배열을 펼쳐서 뒤에 이어붙인다
];
```

`전체` 항목의 `id`는 DB에서 온 값이 아니므로 임의로 `0`을 부여하고, `count`는 각 카테고리의 개수를 모두 더한 총합(`totalCount`)을 서버가 계산해 내려준 값을 그대로 사용한다.

## 12. 조건부로 클래스 이름 붙이기

목록 항목 중 현재 선택된 하나만 강조(하이라이트)하려면, 그 항목에만 추가 클래스를 붙이는 조건부 표현을 쓴다.

```jsx
<li
  className={`list-item ${isActive ? 'list-active' : ''}`}
>
```

`isActive`가 참인 항목에만 `list-active` 클래스가 덧붙고, 나머지는 기본 클래스(`list-item`)만 유지된다. 이 `isActive` 값은 반복 중인 항목의 id와 페이지에서 전달받은 현재 선택 값(`currentCategoryId`)을 비교해 계산한다.

## 13. 정리

| 개념 | 핵심 |
|---|---|
| 컴포넌트 분리 기준 | 화면에 보이는 대로, 계층(트리)을 먼저 생각하고 나눈다 |
| AI에게 맡길 때 | 프로젝트 고유의 관례(예: CSS Modules 같은 CSS 시스템)부터 읽게 하지 않으면 AI가 익숙한 방식(예: Tailwind)으로 잘못 만들 수 있다 |
| 컴포넌트 간 통신 | 형제끼리 직접 지시하지 말고, 반드시 부모를 거쳐 트리 구조를 유지한다 |
| 데이터 패치 | 각 컴포넌트가 자기 데이터는 스스로 가져오는 것이 기본 원칙 |
| `searchParams`의 예외 | URL 값은 페이지만 받을 수 있어, 페이지가 받아 자식에게 내려줘야 한다 |
| `searchParams`의 타입 | `Promise<{...}>`로 정의하고 `await`로 풀어서 사용한다 |
| RSC 요청 | 클릭 시 새로고침 없이 서버가 페이지를 다시 만들어 내려주는 방식 |
| 서버 페이지의 상태 | `useState`가 아니라 URL(쿼리 스트링)이 곧 상태다 |
| 상태 노출 범위 선택 | 모든 상태를 URL에 반영(SEO 우선)할지, 초기 화면만 서버로 주고 이후는 클라이언트 상태로 처리할지 선택 |
