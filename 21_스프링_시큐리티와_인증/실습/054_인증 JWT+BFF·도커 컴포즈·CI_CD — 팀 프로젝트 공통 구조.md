## 1부. BFF — 토큰을 브라우저에 주지 않는 인증

### 1. 흔한 방식과 그 문제

JWT를 쓰는 웹앱을 처음 만들면 보통 이렇게 된다.

동작은 한다. 그런데 네 가지 문제가 따라온다.

1. **토큰이 브라우저 자바스크립트 손에 있다.** localStorage든 일반 쿠키든 자바스크립트가 읽을 수 있다. 페이지에 외부 스크립트 하나만 끼어들어도(XSS) 토큰을 통째로 가져간다. 토큰을 가진 사람은 그 사용자다.
2. **백엔드가 인터넷에 열려 있어야 한다.** 브라우저가 직접 부르니 백엔드 주소가 공개되고, 도메인이 다르면 CORS 설정도 해야 한다.
3. **토큰 갱신 로직이 클라이언트에 있다.** "만료되면 리프레시로 다시 받고, 실패하면 로그아웃" 같은 코드가 모든 fetch 앞에 붙는다. 화면마다 반복된다.
4. **서버 컴포넌트가 못 쓴다.** Next.js의 서버 컴포넌트는 서버에서 렌더링되는데, 토큰이 브라우저 저장소에 있으면 서버는 토큰을 모른다. 로그인 상태에 따라 다른 HTML을 서버에서 만들 수가 없다.

### 2. BFF가 무엇인가

BFF(Backend for Frontend)는 프론트엔드 전용 서버를 하나 더 두는 구조다. 우리 구조에서는 Next.js 서버가 그 역할을 한다. Next.js는 화면만 그리는 것이 아니라 서버 코드도 실행한다. 그 서버 쪽을 인증의 중간자로 쓴다.

핵심은 한 문장이다. **브라우저는 Next.js만 알고, 토큰은 Next.js 서버가 다룬다.** 백엔드는 브라우저에서 보이지 않는다. Next.js 컨테이너가 같은 네트워크 안의 `backend:8080`을 부를 뿐이다.

그러면 브라우저는 자기가 로그인했다는 것을 어떻게 유지하는가. **쿠키**다. 다만 자바스크립트가 못 읽는 쿠키다.

### 3. HttpOnly 쿠키

쿠키에는 옵션이 있다. 우리는 네 개를 쓴다.

| 옵션 | 뜻 | 왜 |
|------|----|----|
| HttpOnly | 자바스크립트(`document.cookie`)로 읽을 수 없다. 브라우저가 요청에 자동으로 붙이기만 한다 | XSS가 있어도 토큰을 읽어 갈 수 없다. 1절의 첫 문제가 사라진다 |
| Secure | HTTPS에서만 전송된다 | 네트워크에서 토큰이 읽히지 않는다. 운영에서는 켠다 |
| SameSite=Lax | 다른 사이트에서 시작된 요청에는 (대부분) 붙지 않는다 | CSRF를 크게 줄인다 |
| Path=/ | 사이트 전체에서 쓴다 | |

로그인에 성공하면 Next.js 서버가 백엔드에서 받은 액세스 토큰과 리프레시 토큰을 각각 HttpOnly 쿠키로 브라우저에 내려 준다. 브라우저는 그 값을 볼 수 없고, 다음 요청부터 자동으로 Next.js 서버에 붙여 보낸다. Next.js 서버는 쿠키에서 토큰을 꺼내 백엔드를 부를 때 `Authorization: Bearer` 헤더로 바꿔 싣는다.

겉으로는 전통적인 세션 쿠키와 같아 보인다. 차이는 서버에 세션 저장소가 없다는 것이다. 쿠키 안에 든 것이 JWT 자체라서, Next.js 서버도 스프링도 "이 사용자가 누구인지"를 쿠키만 보고 안다. 서버를 여러 대로 늘려도 공유할 세션이 없다.

### 4. 토큰 두 개와 Redis

JWT를 아는 사람은 액세스 토큰과 리프레시 토큰을 안다. 우리 구조에서 정한 것만 적는다.

- **액세스 토큰**은 짧다(30분). 사용자 아이디(`sub`)와 역할(`role`: USER 또는 ADMIN)이 들어 있다. 모든 백엔드 요청에 실린다.
- **리프레시 토큰**은 길다(14일). `sub`만 있고 역할이 없다. 액세스 토큰을 다시 받는 데에만 쓴다. 역할이 없으므로 이것을 액세스 토큰처럼 헤더에 실어도 백엔드는 인증으로 인정하지 않는다.

리프레시 토큰은 서버가 기억한다. 백엔드가 발급할 때 Redis에 `refresh:{username}` → 토큰 으로 저장하고, 수명과 같은 TTL을 건다. 재발급 요청이 오면 서명·만료를 확인한 뒤 Redis에 있는 것과 같은지 대조한다. **로그아웃은 Redis에서 지우는 것이다.** 그래서 로그아웃하면 리프레시 토큰이 즉시 무효가 된다.

"JWT는 서버가 상태를 안 가지는 게 장점인데 왜 Redis에 저장하나"라는 질문이 나온다. 순수한 무상태 JWT는 로그아웃을 할 수 없다. 토큰이 만료될 때까지 유효하다. 14일짜리 리프레시 토큰이 유출되면 14일 동안 막을 수 없다. 그래서 수명이 긴 리프레시 토큰만 서버가 기억하는 타협을 한다. 액세스 토큰은 30분이라 저장하지 않고, 요청마다 Redis를 조회하지도 않는다. Redis를 보는 것은 재발급과 로그아웃 때만이다. 2부에서 Redis가 왜 이 일에 맞는지 다시 본다.

### 5. Next.js 안에서 누가 무엇을 하나

Next.js에는 서버에서 돌아가는 코드가 네 종류 있다. 각각 인증에서 맡는 일이 다르다.

| 어디 | 무엇 | 인증에서 하는 일 |
|------|------|------------------|
| 서버 액션 (Server Action) | 폼 제출을 서버 함수로 받는 것 | 로그인: 아이디·비밀번호를 받아 백엔드 `/api/auth/login`을 부르고, 받은 토큰 둘을 HttpOnly 쿠키로 설정하고, 원래 가려던 페이지로 보낸다. 로그아웃: 백엔드 `/api/auth/logout`을 부르고 쿠키를 지운다 |
| `proxy.ts` (Next 15까지는 `middleware.ts`) | 모든 요청이 페이지에 닿기 전에 한 번 실행되는 문지기 | 보호 경로(`/my`, `/admin` 등)에 로그인 쿠키가 없으면 `/login?next=원래경로`로 돌려보낸다. 액세스 토큰이 만료됐고 리프레시 토큰이 있으면 먼저 재발급해서 쿠키를 갈아 끼우고 통과시킨다. `/admin`은 역할이 ADMIN일 때만 통과 |
| 서버 컴포넌트 | 서버에서 렌더링되는 React 컴포넌트 | 쿠키에서 토큰을 읽어 백엔드를 부르고, 결과를 HTML로 만든다. 공통 함수 `backendFetch(path)`가 "쿠키 → Authorization 헤더" 변환을 맡는다. 화면 코드는 백엔드 주소도 토큰도 모른다 |
| Route Handler (`app/api/**/route.ts`) | Next.js 서버가 제공하는 HTTP 엔드포인트 | 브라우저에서 돌아가는 클라이언트 컴포넌트가 데이터를 가져올 때 부르는 창구. 받은 요청을 `backendFetch`로 백엔드에 중계하고 상태 코드를 그대로 돌려준다. 브라우저 입장에서는 같은 도메인의 `/api/...`를 부르는 것이다 |

여기서 브라우저가 백엔드를 직접 부르는 길은 하나도 없다. 서버 컴포넌트는 서버에서 부르고, 클라이언트 컴포넌트는 Route Handler를 거친다. 백엔드 주소(`BACKEND_URL`)는 Next.js 서버의 환경 변수이고 브라우저 번들에는 들어가지 않는다. 그래서 CORS 설정이 필요 없고 백엔드 포트를 열 필요도 없다.

`proxy.ts`가 재발급을 맡는 이유도 짚어 둔다. 서버 컴포넌트는 응답 쿠키를 새로 쓸 수 없다(이미 HTML을 보내는 중이다). 그래서 쿠키를 바꿀 수 있는 유일한 자리인 `proxy.ts`가, 페이지에 가기 전에 토큰을 정리해 둔다. 서버 컴포넌트에 도착하는 토큰은 항상 유효하다.

### 6. 흐름 네 가지

사용자는 30분마다 토큰이 바뀌는 것을 모른다. 14일 동안 접속이 없으면 리프레시 토큰이 만료되어 다시 로그인한다.

### 7. 백엔드에서 정해진 것

백엔드(스프링)는 토큰을 발급하고 검증한다. 세션은 만들지 않는다. 구조는 다음과 같다.

- **SecurityConfig:** CSRF 끔(쿠키 기반 세션이 없으므로 CSRF 토큰도 없다), STATELESS, 경로 규칙. `/api/auth/**`는 공개, 로그인 없이 보여야 하는 조회(GET) API는 메서드를 명시해 공개, `/api/admin/**`은 ADMIN만, 나머지는 로그인 필수.
- **JWT 필터:** 요청마다 `Authorization: Bearer` 토큰을 읽어 유효하면 스프링 시큐리티의 인증 객체로 바꿔 넣는다. `role` 클레임이 없는 토큰(리프레시)은 무시한다.
- **인증 API 셋:** `POST /api/auth/login`, `/refresh`, `/logout`. 사용자 조회는 팀이 이미 가진 사용자 테이블을 쓴다. 비밀번호는 BCrypt.
- **에러 응답 통일:** 인증 안 됨은 401, 권한 부족은 403. 둘 다 `{status, error, message, path, timestamp}` 한 가지 JSON 모양이다. 스프링 기본 설정은 둘 다 403에 HTML을 주므로 반드시 바꾼다. 프론트는 "status와 message를 읽는다" 하나만 알면 된다.

권한의 최종 판정은 백엔드가 한다. `proxy.ts`가 `/admin`을 막는 것은 화면 껍데기에 들어가지 못하게 하는 1차 관문이고, 데이터는 백엔드가 403으로 막는다. 프론트 검사를 우회해도 데이터는 못 가져간다.

### 8. 얻는 것과 대가

| 얻는 것 | 대가 |
|---------|------|
| 토큰이 브라우저 자바스크립트에 노출되지 않는다 | 백엔드 호출이 Next.js 서버를 한 번 더 거친다(수 ms) |
| 백엔드를 인터넷에 열지 않는다. CORS 없음 | 클라이언트 컴포넌트의 데이터 요청마다 Route Handler 하나가 필요하다 |
| 토큰 갱신이 `proxy.ts` 한 곳에 있다 | Next.js 서버가 반드시 있어야 한다(정적 호스팅 불가) |
| 서버 컴포넌트가 로그인 상태를 알고 렌더링한다 | |
| 로그아웃이 즉시 효력을 가진다 | Redis가 필요하다 |

## 2부. 도커 컴포즈에 무엇이 들어가고 왜 필요한가

### 1. 서비스 여섯 개

컴포즈 파일(`compose.yaml`) 하나로 뜨는 것은 이것들이다.

하나씩 왜 있는지 본다.

#### frontend — Next.js

1부의 BFF 서버다. 운영용 이미지는 `next build`의 standalone 산출물만 담아 작고, 개발 모드에서는 소스 폴더를 컨테이너에 마운트해 `next dev`를 돌려 코드를 고치면 바로 반영된다. 환경 변수 `BACKEND_URL=http://backend:8080`으로 백엔드를 찾는다. `backend`는 컴포즈가 붙여 주는 서비스 이름이고 컨테이너 네트워크 안에서 DNS 이름처럼 쓰인다. 브라우저에 열리는 포트는 이것 하나다(운영에서는 nginx 뒤로 숨는다).

#### backend — 스프링 부트

JWT 발급·검증과 업무 API. jar 하나를 JRE 이미지에서 실행한다. 설정은 전부 환경 변수로 받는다. DB 주소(`DB_HOST=postgres`), Redis 주소(`REDIS_HOST=redis`), `JWT_SECRET`. `application.yml`에는 `${REDIS_HOST:localhost}`처럼 기본값은 로컬 개발용, 컨테이너에서는 컴포즈가 덮어쓴다. 같은 이미지가 개발·운영 어디서든 환경 변수만 바꿔 돈다. 운영에서는 포트를 열지 않는다. frontend만 부르기 때문이다.

#### postgres — 영구 데이터

사용자, 업무 데이터가 들어가는 DB. 팀이 이미 MySQL 등 다른 DB를 쓰면 그것을 그대로 쓰면 된다. 중요한 것은 세 가지다.

1. **컨테이너로 띄운다.** 팀원마다 DB를 설치하고 버전·포트·비밀번호를 맞추는 일이 없어진다. `docker compose up`이면 같은 DB가 뜬다.
2. **named volume에 데이터를 둔다.** 컨테이너는 지워져도 볼륨은 남는다. `docker compose down`은 볼륨을 남기고, `down -v`만 지운다.
3. **healthcheck를 걸고** backend가 `depends_on: condition: service_healthy`로 기다린다. DB가 준비되기 전에 스프링이 뜨면 연결 실패로 죽기 때문이다.

#### redis — 리프레시 토큰 저장소

Redis는 메모리에 키-값을 저장하는 서버다. 디스크 DB보다 수십 배 빠르고, 키마다 수명(TTL)을 걸면 시간이 지나면 저절로 지워진다. 리프레시 토큰 저장에 정확히 맞는다.

- 토큰은 14일 뒤에 어차피 버려야 한다. TTL을 14일로 걸면 만료 정리 코드가 필요 없다.
- 토큰 대조는 "키 하나 읽기"다. 테이블·인덱스·SQL이 필요 없다.
- 백엔드 프로세스 밖에 있다. 백엔드 메모리(Map)에 두면 백엔드를 재시작할 때마다 전원이 로그아웃된다. Redis에 두면 백엔드를 재배포해도 로그인이 유지된다. 3부의 블루그린에서 백엔드가 두 벌이 되는데, 둘이 같은 Redis를 보므로 어느 쪽이 받아도 토큰을 안다.

메모리라서 Redis가 죽으면 토큰이 사라지는가. `--appendonly yes`(AOF)로 디스크에 기록하게 하고 볼륨을 붙이면 재시작해도 남는다. 설령 날아가도 결과는 "다시 로그인"이지 데이터 손실이 아니다.

"그냥 DB 테이블에 넣으면 안 되나"에 대한 답은 "된다, 그러나 수명 관리와 정리를 직접 해야 하고, 느리다"다. 세션처럼 짧게 살고 자주 읽히는 것은 Redis, 오래 남아야 하는 것은 DB가 각자의 자리다.

#### adminer — DB 들여다보기 (개발용)

브라우저에서 DB 테이블을 보는 작은 웹 도구다. `localhost:8082`에서 서비스 이름 `postgres`로 접속한다. 운영 컴포즈에는 넣지 않는다. DB에 웹 입구를 하나 더 여는 것이기 때문이다.

#### nginx — 리버스 프록시 (로컬에서는 선택, 운영에서는 필수)

리버스 프록시는 클라이언트 요청을 대신 받아 뒤의 서버에 넘기는 서버다. 우리 구조에서 nginx가 알아야 할 뒤쪽 서버는 frontend 하나다(브라우저는 Next.js만 부르니까). 하는 일은 셋이다.

1. **HTTPS 종단.** 인증서를 들고 TLS를 푸는 일을 nginx가 하고, 뒤의 Next.js는 평범한 HTTP로 돈다. 로컬에서는 mkcert로 만든 localhost 인증서로 `https://localhost`를 띄운다(`profiles: ["https"]`로 필요할 때만). 운영에서는 Let's Encrypt 인증서다.
2. **한 포트로 여러 팀.** 운영 호스트에서 443은 하나인데 팀은 여럿이다. nginx가 Host 헤더(`team1.도메인`)를 보고 어느 팀에 넘길지 정한다.
3. **전환 지점.** 3부 블루그린에서 새 버전과 옛 버전을 바꾸는 일은 nginx가 보내는 곳을 바꾸는 것이다.

HTTPS가 필요한 이유는 보안 일반론만이 아니다. 1부의 Secure 쿠키는 HTTPS가 아니면 브라우저가 보내지 않는다. 운영 이미지를 HTTP 서버에 올리면 로그인이 되는 듯하다가 다음 요청에서 쿠키가 빠져 로그아웃된 것처럼 보인다.

### 2. 컴포즈가 해 주는 것

- **이름으로 찾기.** 같은 컴포즈 안의 서비스는 자동으로 한 네트워크에 묶이고 서비스 이름이 호스트 이름이 된다. `backend:8080`, `redis:6379`. 컨테이너 안에서 `localhost`는 그 컨테이너 자신이므로 쓰면 안 된다.
- **환경 변수와 `.env`.** 컴포즈 파일의 `${POSTGRES_PASSWORD:-기본값}`은 같은 폴더의 `.env`에서 값을 읽는다. `.env`는 커밋하지 않고 `.env.example`에 자리만 남긴다. 운영에서 꼭 있어야 하는 값은 `${JWT_SECRET:?메시지}`로 적어 없으면 아예 뜨지 않게 한다.
- **포트 바인딩.** `8080:8080`은 호스트의 모든 주소에 연다. `127.0.0.1:3101:80`은 호스트 안에서만 접속할 수 있다. 운영에서 팀 nginx는 후자로 열고 호스트 nginx만 거쳐 들어오게 한다. 도커는 포트를 열 때 호스트 방화벽(ufw)을 우회하므로, 바인드 주소를 적는 습관이 안전장치다.
- **프로젝트 이름.** `COMPOSE_PROJECT_NAME=team1`이면 컨테이너·볼륨·네트워크 이름 앞에 `team1`이 붙는다. 한 호스트에서 여러 팀이 같은 컴포즈 파일을 띄워도 섞이지 않는다.

### 3. 개발 모드와 운영 모드

같은 뼈대로 두 가지 모양을 만든다.

| | 개발 (`compose.yaml` + `compose.override.yaml`) | 운영 (`compose.prod.yaml`) |
|--|--------------------------------------------------|----------------------------|
| 명령 | `docker compose up -d` (override는 자동으로 합쳐진다) | 블루그린 스크립트가 다룬다 (3부) |
| 이미지 | 로컬 빌드. dev 타깃 | GitHub Actions가 만들어 올린 이미지를 받는다 |
| 소스 | 폴더를 마운트해 핫 리로드 | 없음. 이미지 안의 산출물만 |
| 열린 포트 | 3000, 8080, 5432, 6379, 8082 | nginx의 `127.0.0.1:310N:80` 하나 |
| adminer | 있음 | 없음 |
| frontend/backend | 한 벌 | blue, green 두 벌 |

### 4. 이미지는 어떻게 만드나

Dockerfile은 이미지를 만드는 절차다. 멀티스테이지로 쓴다. 빌드 단계(JDK, Gradle, 또는 Node와 전체 `node_modules`)와 실행 단계(JRE만, standalone만)를 나누어, 최종 이미지에는 실행에 필요한 것만 남긴다. 이미지가 작아지고 빌드 도구가 운영에 실리지 않는다. 의존성 설치 층을 소스 복사보다 앞에 두어, 소스만 바뀌었을 때 라이브러리 다운로드를 다시 하지 않게 한다. `.dockerignore`로 `node_modules`, `build`, `.env`가 이미지에 들어가지 않게 한다. 실행은 root가 아닌 사용자로 한다.

## 3부. CI/CD와 GitHub Actions

### 1. CI/CD가 무엇인가

배포를 손으로 하면 이렇다. 서버에 SSH로 들어가 `git pull`, 빌드, 재시작. 팀원 여럿이 번갈아 고치는 프로젝트에서 금방 문제가 된다.

- 누가 언제 무엇을 올렸는지 남지 않는다. "서버에 있는 코드가 main인가?"에 답할 수 없다.
- 테스트를 돌리지 않고 올리게 된다. 깨진 코드가 서버에서 발견된다.
- 서버에서 빌드한다. 느리고, 빌드가 실패하면 서버에 반쪽 상태가 남는다.

**CI**(Continuous Integration, 지속적 통합)는 코드가 저장소에 들어올 때마다 자동으로 빌드하고 테스트하는 것이다. 깨진 코드가 main에 들어오기 전에 잡는다. **CD**(Continuous Deployment, 지속적 배포)는 그 통과한 코드를 자동으로 서버에 올리는 것이다. 둘을 이어 놓은 것을 **파이프라인**이라 부른다. 사람이 하는 일은 `git push`까지다.

### 2. GitHub Actions가 무엇인가

GitHub Actions는 GitHub이 빌려주는 컴퓨터에서, 저장소에 적어 둔 절차를 자동으로 실행해 주는 서비스다. 저장소의 `.github/workflows/` 폴더에 YAML 파일을 두면 그것이 절차다. 공개 저장소는 무료고 비공개도 월 2,000분이 무료다.

용어를 알아 두면 YAML이 읽힌다.

| 용어 | 뜻 |
|------|----|
| 워크플로(workflow) | YAML 파일 하나. 파이프라인 하나 |
| 이벤트(on) | 언제 도는가. push, pull_request, 수동(workflow_dispatch) |
| job | 독립적으로 실행되는 작업 묶음. 각 job은 새 컴퓨터(runner) 에서 돈다 |
| runner | GitHub이 빌려주는 빈 Ubuntu 가상 머신. JDK도 Node도 없어서 매번 설치한다 |
| step | job 안의 한 줄. 명령을 직접 치거나(run) 남이 만든 동작을 가져다 쓴다(uses) |
| action | 재사용 가능한 step. `actions/checkout`(코드 받기), `actions/setup-java`, `docker/build-push-action` 등 |
| needs | job 순서. `needs: test`면 test가 성공해야 시작 |
| if | 조건. main 브랜치일 때만 등 |
| matrix | 같은 job을 값만 바꿔 병렬로 여러 번. backend와 frontend 이미지를 동시에 빌드 |
| secrets | 저장소 설정에 넣어 두는 비밀값. 워크플로에서 `${{ secrets.이름 }}`으로 쓰고 로그에는 `***`로 가려진다 |
| GITHUB_TOKEN | 워크플로마다 자동 발급되는 임시 토큰. 이미지 저장소 로그인에 쓴다 |
| permissions | 그 토큰에 줄 권한. 이미지를 올리려면 `packages: write` |
| 캐시 | Gradle·npm이 받은 라이브러리를 다음 실행에 재사용. 몇 분을 아낀다 |

### 3. 우리 파이프라인 — 세 job

1. **test:** 어느 브랜치에 push해도, PR을 열어도 돈다. 팀원이 자기 브랜치에서 작업할 때도 테스트가 돌아 PR에 녹색 체크가 뜬다. 하나라도 실패하면 빨간불이고 뒷 단계는 돌지 않는다.
2. **build-push:** main에만. 손 배포에서는 서버에서 빌드했지만 이제 GitHub 컴퓨터에서 빌드한다. 완성된 이미지를 레지스트리에 올린다(다음 절).
3. **deploy:** Secrets에 둔 호스트 주소·계정·SSH 키로 호스트에 들어가 `git pull --ff-only`(컴포즈 파일이나 스크립트가 바뀌었을 수 있으니)와 `bash deploy/blue-green.sh deploy`를 친다. 호스트는 빌드하지 않고 받기만 한다.

실패는 job이 빨간불로 보인다. test 실패는 코드 문제다. deploy 실패는 호스트 문제이거나 새 버전이 헬스체크를 통과하지 못한 것인데, 이때 서비스는 멀쩡하다. 블루그린이 전환하지 않았기 때문이다(7절).

### 4. 컨테이너 레지스트리 — GHCR

도커 이미지는 파일이 아니라 git에 넣을 수 없다. 이미지를 올리고 받는 저장소가 컨테이너 레지스트리다. Docker Hub가 유명하지만, GitHub 저장소와 붙여 쓰기에는 GHCR(GitHub Container Registry, `ghcr.io`)이 편하다. 워크플로 안에서 `GITHUB_TOKEN`으로 로그인되어 비밀번호를 따로 만들 필요가 없고, 이미지가 저장소의 Packages 탭에 보인다.

- **이름:** `ghcr.io/<소유자>/<저장소>-backend`, `-frontend`. 전부 소문자. 워크플로가 저장소 이름에서 자동으로 만든다.
- **태그:** `latest`(늘 최신)와 `sha-<커밋 7자리>`(어느 커밋의 이미지인지). 호스트는 평소 `latest`를 받고, 되돌릴 때 `sha-...`를 지정한다.
- **공개/비공개:** 호스트가 받으려면 패키지를 Public으로 바꾸거나 호스트에서 `docker login ghcr.io`를 한다. 이미지에는 소스가 아니라 빌드 산출물만 있어 공개해도 저장소가 공개되는 것은 아니다.

### 5. 호스트 — 공용 서버의 구조

호스트는 여러 팀이 나눠 쓰는 Ubuntu 한 대다. 호스트 관리자가 준비해 둔다. 팀이 알아야 할 것은 다음이다.

- 팀 계정 `teamN`으로 SSH 접속한다. docker 그룹에 있어 sudo 없이 도커를 쓴다. 홈에 저장소를 받아 둔다. GitHub Actions의 deploy도 이 계정으로 들어온다.
- 팀 도메인 `teamN.도메인`. HTTPS는 호스트 nginx가 끝낸다(인증서는 certbot이 Let's Encrypt에서 받아 자동 갱신). 그 뒤 팀의 포트로 HTTP로 넘긴다.
- 팀 포트 `310N`. 팀 nginx(컴포즈 안의 컨테이너)가 `127.0.0.1:310N`에만 열려 있다. 밖에서 `서버IP:3101`로 들어오는 길은 없다.
- nginx가 두 층이다. HTTPS를 받은 호스트 nginx가 `X-Forwarded-Proto: https`를 만들어 붙이고, 팀 nginx는 그 값을 그대로 넘긴다. Next.js는 이 헤더로 자기가 HTTPS 뒤에 있음을 알고 Secure 쿠키를 내린다. 팀 nginx가 이 값을 http로 덮어쓰면 로그인이 되지 않는다. **가장 흔한 사고다.**
- 팀 격리는 리눅스 계정, `COMPOSE_PROJECT_NAME`, `127.0.0.1` 바인딩 세 가지로 한다. 한 팀의 컨테이너가 다른 팀의 포트나 볼륨에 닿지 않는다.
- `.env` 초안이 홈에 있다. `COMPOSE_PROJECT_NAME=teamN`, `TEAM_PORT=310N`, DB 비밀번호, `JWT_SECRET`(무작위), `IMAGE_PREFIX`(이미지 이름 앞부분), `IMAGE_TAG`. 복사해서 저장소 폴더의 `.env`로 쓴다. `JWT_SECRET`은 팀마다 다르다. 같으면 한 팀의 토큰이 다른 팀 백엔드에서도 통한다.

### 6. 열쇠 — SSH 키와 Secrets

deploy job이 호스트에 들어가려면 GitHub이 팀 계정으로 SSH 접속할 수 있어야 한다. 비밀번호가 아니라 키 쌍이다.

1. 팀원 하나가 배포 전용 키 쌍을 만든다(`ssh-keygen -t ed25519`). 개인 용도 키를 쓰지 않는다. 유출되면 이것만 바꾸면 되게.
2. 공개 키를 호스트 팀 계정의 `~/.ssh/authorized_keys`에 한 줄 추가한다.
3. 개인 키 내용을 저장소 Settings → Secrets에 `DEPLOY_SSH_KEY`로 넣는다. 함께 `DEPLOY_HOST`(호스트 주소), `DEPLOY_USER`(teamN).

Secrets는 넣은 뒤 다시 볼 수 없고, 워크플로 파일에는 이름만 적힌다. 그래서 워크플로 파일에는 저장소 이름도, 팀 번호도, 호스트 주소도, 비밀값도 없다. 어느 팀 저장소에 복사해도 고칠 곳이 없고 공개 저장소에 두어도 된다. 팀마다 다른 것은 전부 Secrets(GitHub 쪽)와 `.env`(호스트 쪽)에 있다.

### 7. 블루그린 — 끊김 없는 배포와 되돌리기

컨테이너를 새 이미지로 바꾸는 가장 단순한 방법은 "옛것을 지우고 새것을 켠다"(`docker compose up -d`)다. 스프링이 다시 뜨는 10~20초 동안 로그인과 API가 실패하고, Next.js가 교체되는 몇 초는 nginx가 502를 낸다. 새 버전에 문제가 있어도 옛 버전은 이미 사라졌다.

블루그린 배포는 frontend와 backend를 두 벌(blue, green) 두고 한 벌만 트래픽을 받게 하는 방식이다.

![[blue-green-deploy.png]]

배포 스크립트(`deploy/blue-green.sh deploy`)가 하는 일은 순서가 전부다.

1. 지금 트래픽을 받는 색(예: blue)을 확인한다.
2. 쉬는 색(green)에 새 이미지를 받아 띄운다. blue는 건드리지 않는다. 사용자는 계속 blue를 쓴다.
3. green의 frontend 안에서 자기 API를 불러 헬스체크한다. 백엔드까지 통과해 200이 나와야 한다. 최대 60초 기다린다.
4. 통과하면 nginx의 upstream을 green으로 바꾸고 `nginx -s reload`. reload는 처리 중인 요청을 끝낸 뒤 워커를 교체하므로 실패하는 요청이 없다.
5. blue를 멈춘다(지우지 않는다).

헬스체크에 실패하면 전환하지 않는다. green을 멈추고 종료 코드 1로 끝난다. deploy job은 빨간불이지만 사이트는 blue가 계속 받고 있다. "배포 실패 = 장애"가 아니다.

되돌리기는 두 가지다. `bash deploy/blue-green.sh rollback`은 멈춰 둔 이전 색을 다시 켜서(이미지를 바꾸지 않고 그대로) 헬스체크 뒤 전환한다. 몇 초다. `IMAGE_TAG=sha-abc1234 bash deploy/blue-green.sh deploy`는 특정 커밋의 이미지를 쉬는 색에 띄워 전환한다.

**상태는 색 밖에 둔다는 원칙**이 여기서 중요하다. PostgreSQL과 Redis는 한 벌이고 두 색이 같이 쓴다. blue에서 로그인한 사용자가 green으로 넘어가도 Redis의 리프레시 토큰이 그대로 있어 로그아웃되지 않는다. 1부 4절에서 토큰을 백엔드 메모리가 아니라 Redis에 둔 결정이 여기서 값을 한다.

같은 DB를 두 버전이 보므로 스키마 변경에 규칙이 생긴다. 컬럼 추가는 한 번에 해도 되지만, 삭제·이름 변경은 두 배포에 나눈다. 먼저 새 컬럼을 추가해 두 버전이 다 쓰게 만들고, 다음 배포에서 옛 컬럼을 지운다. 전환 전후에 아직 켜져 있는 옛 버전이 깨지지 않게 하기 위해서다.

### 8. 팀이 실제로 하는 일

구조가 갖춰진 뒤 팀의 일상은 이것뿐이다.

| 언제 | 무엇 |
|------|------|
| 처음 한 번 | 배포 키 만들어 호스트와 Secrets에 등록. 호스트 팀 계정에서 저장소 clone, `.env` 채우기. Packages 공개 |
| 개발 | 브랜치에서 작업 → push(test가 돈다) → PR → 리뷰 → merge |
| 배포 | main에 merge되면 자동. Actions 탭에서 세 job 녹색 확인. `https://teamN.도메인` 새로 고침 |
| 문제 | rollback 또는 `IMAGE_TAG=sha-...`로 되돌림. 로그는 호스트에서 `docker compose -f compose.prod.yaml logs backend-<색>` |
| 확인 | 호스트에서 `bash deploy/blue-green.sh status` — 활성 색과 컨테이너 상태 |

| `proxy.ts` (middleware) | 모든 요청 앞에서 도는 Next.js 문지기. 보호 경로와 토큰 갱신 |
| Route Handler | Next.js 서버의 `/api/...` 엔드포인트. 클라이언트 컴포넌트가 백엔드 대신 부르는 창구 |
| STATELESS | 서버가 세션을 만들지 않음. 요청마다 토큰으로 판단 |
| Redis | 메모리 키-값 저장소. TTL로 자동 만료. 리프레시 토큰 저장 |
| named volume | 컨테이너가 지워져도 남는 도커 데이터 저장소 |
| healthcheck | 컨테이너가 "준비됨"인지 확인하는 명령. `depends_on`이 기다리는 기준 |
| 리버스 프록시 | 요청을 대신 받아 뒤 서버에 넘기는 서버. nginx |
| X-Forwarded-Proto | 프록시가 "원래 요청은 https였다"고 뒤 서버에 알리는 헤더 |
| CI / CD | push마다 자동 빌드·테스트 / 통과한 코드를 자동 배포 |
| 워크플로, job, step, runner | Actions의 절차 파일, 작업 묶음, 한 줄, 실행 컴퓨터 |
| GHCR | GitHub의 컨테이너 이미지 저장소 `ghcr.io` |
| Secrets | 저장소에 넣는 비밀값. 워크플로에서 이름으로만 참조 |
| 블루그린 | 두 벌 중 한 벌만 트래픽. 새 버전을 쉬는 벌에 올려 검증 뒤 전환 |
| upstream | nginx가 요청을 넘기는 뒤쪽 서버 목록. 전환은 이 목록을 바꾸는 것 |
| 롤백 | 이전 버전으로 되돌림 |
