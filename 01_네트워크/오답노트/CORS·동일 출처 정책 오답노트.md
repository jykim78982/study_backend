# CORS·동일 출처 정책 오답노트

### 1. 서버 환경에서 백엔드로 요청할 때와 브라우저 클라이언트에서 다른 출처의 Spring 서버에 요청할 때의 차이는 무엇인가?

**문제**: 서버 환경에서 백엔드로 요청할 때와 브라우저 클라이언트에서 다른 출처의 Spring 서버에 요청할 때의 차이는 무엇인가?

1. 서버 환경은 동일 출처 정책의 영향을 직접 받고, 브라우저는 전혀 영향을 받지 않는다.
2. 두 환경 모두 동일하게 CORS 설정이 항상 필요하다.
3. 브라우저에서는 항상 CORS 설정이 필요 없고, 서버에서만 CORS를 설정해야 한다.
4. 서버 환경에서는 일반적으로 동일 출처 정책 영향을 직접 받지 않지만, 브라우저에서 다른 출처로 요청하면 CORS 설정이 필요할 수 있다.

**정답: 4번**

- SOP(동일 출처 정책)와 CORS는 "서버"가 아니라 **"웹 브라우저"가 사용자를 보호하기 위해 강제하는 보안 정책**이다. 이 하나만 기억하면 나머지는 다 따라 나온다.
- **1번이 오답인 이유**: 정반대로 서술되어 있다. 영향을 받는 쪽은 브라우저이고, 서버 환경(서버 대 서버 통신)은 영향을 받지 않는다.
- **2번이 오답인 이유**: 서버 대 서버 통신(Node.js, Spring, Python, curl 등)에는 검사 주체인 "브라우저"가 없으므로 CORS 설정 없이도 자유롭게 통신된다.
- **3번이 오답인 이유**: 다른 출처로 요청할 때 브라우저에서 에러 없이 응답을 받으려면, 서버가 `Access-Control-Allow-Origin` 같은 CORS 허용 헤더를 내려줘야 한다. 즉 브라우저 쪽 요청이 CORS 설정과 무관한 게 아니라, 오히려 CORS 설정이 필요해지는 쪽이 바로 이 경우다.

**상황별 동작 방식**

| 상황 | 주체 | 동작 |
|---|---|---|
| 브라우저 → 다른 출처 서버 (예: `localhost:3000` → `api.com:8000`) | 브라우저 | 응답 헤더에 `Access-Control-Allow-Origin`이 없으면 브라우저가 응답을 차단하고 콘솔에 CORS 에러를 낸다 |
| 서버 → 다른 출처 서버 (예: Node.js/Next.js 서버 컴포넌트 → Spring) | 없음(서버 프로세스끼리 직접 통신) | 검사할 브라우저가 없으므로 CORS 설정이 없어도 정상적으로 데이터를 주고받는다 |

브라우저가 다른 출처로 요청을 보내면, 서버는 정상적으로 응답을 돌려준다 — 요청 자체가 막히는 게 아니라, **브라우저가 응답을 받은 뒤 자바스크립트에 그 데이터를 넘겨주지 않고 버리는 것**이다. 반면 서버 프로세스가 다른 서버에 요청할 때는 이런 검사 단계 자체가 존재하지 않는다.

**실무 팁 — 프록시로 CORS 우회하기**

백엔드의 CORS 설정을 당장 바꾸기 어렵다면, 브라우저가 같은 출처의 프론트엔드 서버에만 요청하고, 그 서버가 서버 대 서버 통신으로 백엔드에 다시 요청을 전달하게 만들 수 있다.

```
[브라우저] --(같은 출처 요청)--> [Next.js 서버/프록시] --(서버 대 서버, CORS 제약 없음)--> [Spring 백엔드]
```

브라우저 입장에서는 요청 대상이 항상 같은 출처이므로 CORS 검사 자체가 발생하지 않는다.
