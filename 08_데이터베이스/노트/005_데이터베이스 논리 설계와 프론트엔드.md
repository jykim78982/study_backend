# 데이터베이스 논리 설계 & 프론트엔드

지난 [07-12_ERD 개념 설계](07-12_ERD%20개념%20설계.md)에서 다룬 **개념 설계**(엔티티/속성/관계를 말랑하게 스케치하는 단계)에 이어, 이번엔 그걸 **실제 테이블 구조**로 구체화하는 **논리 설계** 단계를 배웠다.

---

## 1. 💡 핵심 원리 — 개념 설계와 논리 설계의 차이

| 단계 | 하는 일 | 산출물 |
|---|---|---|
| 개념 설계 | 어떤 데이터가 필요하고 서로 어떻게 얽혀있는지 큰 그림 그리기 | ERD(엔티티/속성/관계) |
| 논리 설계 | 개념 설계를 실제 DB에 옮길 수 있는 형태로 구체화 | 테이블, 컬럼, PK/FK, 타입 |

개념 설계에서 "엔티티"였던 것은 논리 설계에서 "테이블"이 되고, "속성"은 "컬럼"이, "관계"는 "외래키(FK)" 또는 "조인 테이블"이 된다.

---

## 2. 관계를 테이블로 구현하는 방법

### 1대N 관계 → 외래키

**N쪽 테이블**에 FK 컬럼을 하나 추가해서 1쪽을 참조한다.

```
고객(PK 아이디, 이름)
주문(PK 아이디, 상태, FK 고객아이디)   ← N쪽인 주문이 FK를 가짐
```

### N대N 관계 → 조인 테이블 + 복합키

테이블 두 개만으로는 표현이 안 되므로, 중간에 **조인 테이블**을 하나 더 만들고 양쪽 FK를 합쳐 **복합키(Composite Key)**로 쓰거나, 별도의 단일 PK를 둔다.

```
메뉴(PK 아이디, 이름, 가격)
주문(PK 아이디, 상태, FK 고객아이디)
주문상세(PK 아이디, FK 주문아이디, FK 메뉴아이디, 수량)   ← 조인 테이블
```

---

## 3. 📝 예제 — 카페 앱 주문·장바구니·결제 흐름

카페 앱(cafe-app) ERD를 예로 논리 설계 규칙을 실습했다.

- **행위 속성**(수량처럼 "관계 자체"에 붙는 정보)은 조인 테이블에 넣는다 → `주문상세.수량`, `장바구니.수량`
- **FK 배치 규칙**: 항상 **N쪽(자식) 테이블**이 FK를 갖는다. 1쪽(부모)은 FK를 받지 않는다.
- **중복 방지**: 메뉴 이름·가격 같은 정보를 주문상세에 그대로 복사해 넣지 않고, `FK 메뉴아이디`로 참조만 한다. (단, 주문 시점 가격처럼 나중에 바뀌면 안 되는 값은 예외적으로 스냅샷 저장)

```
결제(PK 아이디, 금액, 일시, 수단)
주문(PK 아이디, 번호, 상태, FK 고객아이디, FK 결제아이디)
주문상세(PK 아이디, FK 주문아이디, FK 메뉴아이디, 수량)
```

## 4. ⚠️ 식별관계 vs 비식별관계

| 구분 | 정의 | 예 |
|---|---|---|
| **식별관계** | 자식 테이블의 PK 안에 부모 FK가 포함됨 → 부모 없이는 자식이 존재할 수 없음 | 주문상세(PK가 `주문아이디+메뉴아이디` 조합) |
| **비식별관계** | 부모 FK가 그냥 일반 컬럼(PK 아님) → 자식이 독립적으로 존재 가능 | 주문(FK 고객아이디는 그냥 컬럼, 주문 자체는 고유 PK를 따로 가짐) |

**헷갈리지 않는 기준**: "이 자식 행이 부모 없이 혼자 의미가 있는가?"
- 의미 없음(부모에 완전히 종속) → 식별관계
- 의미 있음(그냥 누구 소유인지 표시만 하는 것) → 비식별관계

## 5. 프론트엔드 — 랜딩 페이지 레이아웃 조정

카페 앱 메인 페이지의 **히어로 섹션**과 **인기 메뉴 카드** 간격을 다듬었다.

- 섹션 간 간격은 `margin`보다 **부모에 `gap`을 주는 방식**(flex/grid)이 안전하다 — margin은 인접 요소끼리 상쇄(collapse)되는 경우가 있어서 예상과 다르게 붙거나 벌어질 수 있음
- 반응형은 뷰포트가 좁아질 때 카드 grid의 `grid-template-columns` 열 개수를 줄이는 방식으로 처리 (예: 데스크톱 4열 → 태블릿 2~3열 → 모바일 1~2열)

---

## 6. 백엔드 연동 — Supabase 가입/테이블 생성/대시보드

정적 페이지(localStorage)만 쓰던 카페 앱에 실제 백엔드를 붙이기 위해 Supabase를 도입했다.

1. **가입**: supabase.com에서 회원가입 후 새 프로젝트 생성 (프로젝트별로 고유한 `project_ref`가 발급됨)
2. **테이블 생성**: 대시보드의 **Table Editor**에서 컬럼과 타입을 지정해 테이블 생성, 또는 **SQL Editor**에서 `CREATE TABLE` 직접 실행
3. **대시보드 활용**:
   - **Table Editor**: 데이터를 스프레드시트처럼 직접 조회/수정
   - **Authentication**: 회원 가입/로그인 계정 관리, 이메일 인증 여부 확인
   - **SQL Editor**: 쿼리 직접 실행, 마이그레이션 작성

> 참고: Supabase Auth는 기본적으로 회원가입 시 **이메일 인증**을 요구한다. 개발 중 매번 인증 메일을 확인하기 번거로우면 Authentication → Providers → Email에서 "Confirm email" 옵션을 꺼둘 수 있다.
