# 제약 조건 — 도메인·엔티티·릴레이션 제약과 정규식

데이터베이스의 무결성을 지키기 위한 제약 조건을 도메인·엔티티·릴레이션 세 단계로 나눠 정리하고, 값의 형식을 정밀하게 검사하는 정규식까지 다룬다.

## 0. 무결성이란

데이터베이스의 가장 중요한 특징을 세 글자로 말하면 **무결성**이다. 무결성이란 **데이터가 정해진 규칙에 맞고, 서로 모순 없이 일관된 상태를 유지하는 것**이다. 결함(잘못된 값, 중복, 끊어진 참조)이 없는 상태라고 보면 된다.

무결성을 지키는 첫 번째 방법은 **중복을 없애는 것**이고, 그래서 정규화가 중요하다. 하지만 정규화로 구조를 다듬었다고 결함이 사라지는 것은 아니다. 정규화는 **구조**를 다듬을 뿐, 그 구조 안에 **잘못된 값이 들어오는 것**까지 막아주지는 않는다. 그 마지막 빈틈을 막는 것이 제약 조건이다. 제약 조건은 데이터가 실제로 들어오려고 할 때 "잠깐, 넌 안 돼"라고 막아서는 **최종 방어선**이다.

## 1. 제약 조건의 위치 — 설계의 마감 처리

```
개념 설계 → 논리 설계 → 정규화 → 물리 설계·구현 → 제약 조건
                         (구조를 다듬는 일)          (들어오는 값을 막는 일)
```

- **정규화**는 테이블 **구조**를 결함이 적게 만드는 일이다.
- **제약 조건**은 그 구조에 **데이터가 들어올 때** 결함 있는 값을 막는 일이다. 구현이 끝난 테이블에 마지막으로 거는 대문의 수문장이다.

제약 조건은 무엇을 지키느냐에 따라 세 범주로 나눈다. 아래로 갈수록 범위가 넓어진다.

| 범주 | 지키는 대상 | 제약 |
|---|---|---|
| **도메인** 제약 | 컬럼 하나하나의 값이 올바른가 | 자료형·길이, `NOT NULL`, `DEFAULT`, `CHECK` |
| **엔티티** 제약 | 행(레코드) 하나하나가 식별 가능한가 | `PRIMARY KEY`, `UNIQUE` |
| **릴레이션**(참조) 제약 | 테이블 사이의 참조가 올바른가 | `FOREIGN KEY` |

컬럼 값이 모두 올바라도 행이 중복될 수 있고, 행이 모두 식별 가능해도 존재하지 않는 부모를 가리킬 수 있다. 그래서 세 단계를 **모두** 거쳐야 결함이 없는 데이터가 된다.

## 2. 도메인이란 — 컬럼에 들어갈 수 있는 유효한 값의 범위

"도메인"은 쓰이는 곳마다 뜻이 다르다.

| 분야 | 도메인의 뜻 |
|---|---|
| 인터넷 | `naver.com` 같은 주소 |
| 업무·설계 | 내가 다루는 업무 분야 (도메인 지식, 도메인 로직) |
| **데이터베이스** | **특정 컬럼(속성, 필드)에 들어갈 수 있는 값의 범위** |

모든 컬럼에는 도메인이 있고, 컬럼에는 그 도메인에 맞는 값만 들어가야 한다.

| 컬럼 | 도메인 예시 |
|---|---|
| 학번 | **문자열**, 8자리, 정해진 조합 규칙(입학년도 + 학과 + 번호 등) |
| 이름 | 문자열, 숫자가 들어가면 안 됨 |
| 납입금 | 0 이상의 정수 (음수면 장학금이 되어버린다) |
| 납입일 | 실제로 존재하는 날짜 |

> **학번은 왜 숫자가 아니라 문자열인가**: 학번 `20201234`를 "이천이십만 천이백삼십사"라고 읽지 않는다. "이공이공 일이삼사"라고 **글자처럼** 읽는다. 계산(더하기, 평균)에 쓰지 않고, 맨 앞의 `0`도 의미가 있을 수 있다. 이런 값은 숫자처럼 생겼어도 **문자열**로 다룬다. 전화번호, 우편번호도 마찬가지다.

**도메인 제약 조건**이란 각 컬럼이 이 유효 범위 안의 값만 갖도록 보장하는 제약이다. 그중 가장 기본은 **자료형과 길이**인데, 너무 당연해서 보통 제약 조건으로 따로 거론하지 않을 뿐 그 자체가 도메인 제약이다. 자료형과 길이를 넘어서는 것으로 `NOT NULL`, `DEFAULT`, `CHECK` 세 가지를 다룬다.

## 3. NOT NULL — 필수 컬럼 지정

데이터베이스는 **NULL 허용이 기본**이다. 자료형과 길이만 선언하면, 값을 넣지 않은 컬럼에는 NULL이 들어간다. 반드시 값이 있어야 하는 **필수 컬럼**에 NULL이 들어가면 도메인에 맞지 않는 값이 들어간 것이고, 그건 결함이다.

```sql
CREATE TABLE test (
    id    VARCHAR(50)  NOT NULL,     -- 필수
    email VARCHAR(200) NULL,         -- 선택 (NULL은 생략해도 기본값)
    phone CHAR(13)     NOT NULL      -- 필수
);

INSERT INTO test (id) VALUES ('222');
-- PostgreSQL: ERROR: null value in column "phone" of relation "test" violates not-null constraint
-- Oracle:     ORA-01400: NULL을 ("HR"."TEST"."PHONE") 안에 삽입할 수 없습니다
```

게시판이라면 제목은 꼭 있어야 하니 제목 컬럼에 `NOT NULL`을 붙인다. NOT NULL을 거는 일은 곧 **필수 컬럼을 선별하는 일**이다.

**이미 만든 테이블에 추가하기**: 이미 NULL이 들어 있는 행이 있으면 제약을 걸 수 없으므로, 먼저 값을 채운 다음 건다. 구조를 바꿀 때는 `ALTER`, 데이터를 바꿀 때는 `UPDATE`다.

```sql
UPDATE test SET email = 'blank@null.com' WHERE email IS NULL;   -- 데이터 정리 (UPDATE)

-- 구조 변경 (ALTER) — DBMS마다 문법이 다르다
ALTER TABLE test MODIFY email VARCHAR2(200) NOT NULL;           -- Oracle
ALTER TABLE test ALTER COLUMN email SET NOT NULL;               -- PostgreSQL
```

> 위 코드의 두 `ALTER` 줄은 같은 일(email 컬럼에 NOT NULL 추가)을 한다. Oracle 줄은 `MODIFY` 키워드로 컬럼을 다시 정의하면서 Oracle 전용 타입 `VARCHAR2`까지 함께 적고, PostgreSQL 줄은 타입은 그대로 두고 `ALTER COLUMN ... SET NOT NULL`로 제약만 붙인다. 같은 목적인데 DBMS마다 문법이 이렇게 다르다. 이런 **벤더별·버전별 문법 차이는 외우지 않아도 된다.** 요즘은 DB 도구의 체크박스로 설정하거나 AI에게 시키면 된다. 중요한 것은 "NOT NULL 제약이 있고, 나중에 ALTER로 추가할 수도 있다"는 **개념**을 알고, 누군가 쓴 SQL을 보고 "아, NOT NULL이 걸려 있구나"라고 읽을 수 있는 것이다.

## 4. DEFAULT — 필수지만 사람이 입력하면 안 되는 컬럼

필수 컬럼이면 `NOT NULL`을 건다. 그러면 누군가 값을 넣어야 한다. 그런데 **필수인데 사람이 입력하게 하면 안 되는** 컬럼이 있다.

| 컬럼 | 사람이 입력하면 안 되는 이유 |
|---|---|
| **등록일(생성일자)** | 정확한 시각을 입력할 수 없고, 무엇보다 **위조**가 가능하다. 어제 쓴 글을 100년 전에 쓴 글로 만들 수 있으면 안 된다. |
| **조회수** | 실제로 조회되어야 올라가는 값이다. 사용자가 직접 넣으면 안 된다. |
| **관리자가 부여하는 비밀번호** | 사용자가 정하는 게 아니라 시스템이 초기값을 준다. |

또 사용자가 **입력하지 않아도 되도록 편의를 주는** 경우도 있다. 프로필 이미지가 필수인데 지금 사진이 없다면, 기본 이미지를 넣어두고 나중에 바꾸게 하는 식이다.

이럴 때 쓰는 것이 `DEFAULT`다. 값을 넣지 않으면 지정한 기본값이 들어간다. 그래서 **`NOT NULL` + `DEFAULT`**는 자주 함께 쓰인다.

```sql
CREATE TABLE notices (
    seq     VARCHAR(10)   PRIMARY KEY,
    title   VARCHAR(300)  NOT NULL,
    content VARCHAR(4000),
    regdate TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,   -- 등록일: 현재 시각 (Oracle은 SYSDATE)
    hit     INT           NOT NULL DEFAULT 0                    -- 조회수: 0부터
);

INSERT INTO notices (seq, title) VALUES ('1', '공지');   -- regdate=지금, hit=0 자동 입력
```

```sql
-- 이미 만든 테이블에 추가
ALTER TABLE test MODIFY pwd VARCHAR2(200) DEFAULT '111';     -- Oracle
ALTER TABLE test ALTER COLUMN pwd SET DEFAULT '111';         -- PostgreSQL
```

> 위 `ALTER` 예시처럼 `pwd`(비밀번호) 컬럼에 기본값 `'111'`을 주는 것은 DEFAULT 문법을 보여주기 위한 예시일 뿐, 올바른 사용은 아니다(강의에서도 "올바르지 않은 예"라고 짚었다). 사용자가 정하는 비밀번호에 기본값을 주는 것은 맞지 않고, 실제로 비밀번호는 원문이 아니라 해시로 저장해야 한다.

> 기본값이 들어가는지 확인하려고 INSERT를 쓸 때, 컬럼명을 따옴표로 감싸면 문법 오류가 난다.
>
> ```sql
> INSERT INTO test ("UID", 'PHONE') VALUES ('NEWLEC', '222');   -- ❌ 작은따옴표는 값(문자열)에만 쓴다
> INSERT INTO test (id, phone)     VALUES ('NEWLEC', '222');   -- ✅ 컬럼명은 따옴표 없이 → pwd에는 '111'이 들어간다
> ```

> DEFAULT는 INSERT에서 그 컬럼을 **생략했을 때만** 적용된다. `NULL`을 직접 넣으면 기본값이 아니라 NULL이 들어간다(그리고 NOT NULL이면 거부된다).

## 5. CHECK — 값이 들어왔다고 다 유효한 건 아니다

자료형, 길이, NOT NULL, DEFAULT까지 갖춰도 결함은 남는다. 전화번호 칸에 "가나다라마바사"를 넣으면 문자열이고 길이도 맞고 NULL도 아니지만, 전화번호가 아니다. 가입이 귀찮은 사용자는 전화번호도 `AAA`, 이메일도 `AAA`로 채운다. 서비스 입장에서는 결함이다.

그래서 값이 **들어왔는지**를 넘어 **올바른 형태인지**를 검사하는 것이 `CHECK` 제약이다. 도메인 제약의 하이라이트다. `CHECK` 키워드와 괄호 안에 조건식을 쓴다.

```sql
CREATE TABLE test (
    id    VARCHAR(50)  NULL,
    phone VARCHAR(200) NOT NULL CHECK (phone LIKE '010-%-____'),
    email VARCHAR(500) NULL
);
```

### 5-1. 제약 조건에 이름 붙이기

```sql
-- 컬럼 옆에 이름과 함께
phone VARCHAR(200) NOT NULL CONSTRAINT ck_test_phone CHECK (phone LIKE '010-%-____'),

-- 테이블 끝에 몰아서 정의
CREATE TABLE test (
    id    VARCHAR(50),
    phone VARCHAR(200) NOT NULL,
    email VARCHAR(500),
    CONSTRAINT ck_test_phone CHECK (phone LIKE '010-%-____')
);
```

이름을 붙이면 제약 위반 에러에 그 이름이 찍혀서 어떤 규칙을 어겼는지 바로 알 수 있고, 나중에 제약을 지우거나 바꿀 때도 이름으로 가리킬 수 있다.

> **끝에 몰아서 정의할 때 흔한 실수**: 컬럼 옆에 있던 제약을 통째로 끝으로 옮기면서 `NOT NULL`까지 함께 옮기면 문법 오류가 난다.
>
> ```sql
> CONSTRAINT ck_test_phone CHECK (phone LIKE '010-%-____') NOT NULL   -- ❌
> ```
>
> `NOT NULL`은 **컬럼 정의에만** 쓸 수 있고, 테이블 끝의 제약 목록에는 쓸 수 없다. 위 코드처럼 `NOT NULL`은 `phone` 컬럼 옆에 남겨두고 `CHECK`만 끝으로 옮긴다.

### 5-2. LIKE 패턴의 한계

`LIKE`는 비교 연산 중에서도 **패턴을 비교**하는 연산자다. `=`는 값이 정확히 같은지를 보고, `LIKE`는 특수 문자를 이용해 모양을 본다.

| LIKE 기호 | 뜻 |
|---|---|
| `%` | 아무 글자 0개 이상 |
| `_` | 아무 글자 정확히 1개 |

그런데 이 두 기호로는 정밀하게 막을 수 없다.

```
phone LIKE '010-2365-%'    → '010-2365-adfgd-fgdfgdfgdfgsdf'   통과 (길이 제한 없음, 아무 글자나)
phone LIKE '010-2365-____' → '010-2365-adfg'                     통과 (4글자이긴 한데 숫자가 아님)
```

`_`를 4개 써서 길이는 맞췄지만, **그 자리에 숫자만 오게** 하는 방법이 없다. 그래서 더 정밀한 패턴 도구인 **정규식**이 필요하다.

## 6. 정규식 — 모든 언어에서 통하는 패턴 표현식

**정규식**(정규 표현식, Regular Expression, regex)은 문자열의 패턴을 기호로 표현하는 방법이다. 데이터베이스 전용이 아니라 **언어와 플랫폼을 떠나 공통으로 쓰는 표준적인 방식**이다. 자바스크립트에서 입력값을 검사할 때, 자바에서 문자열을 찾을 때, 크롤링으로 화면에서 특정 패턴을 뽑을 때, 데이터에서 패턴을 찾을 때 모두 정규식을 쓴다. 정리가 잘 된 자료로는 MDN의 Regular expressions 문서가 있다(한국어 번역은 어색한 곳이 있어 영문으로 보는 편이 낫다).

### 6-1. 한 글자 패턴 — 대괄호

```
[0123456789]   → 이 자리에는 0~9 중 한 글자만 온다
[0-9]          → 연속된 범위는 하이픈으로 줄인다
\d             → 숫자(digit) 한 글자. [0-9]와 같다
\D             → 숫자가 아닌 한 글자 (대문자 = 반대, 여집합)
```

`[xyz]`는 "이 자리에는 x 또는 y 또는 z 중 **한 글자**"라는 뜻이다. 대괄호 하나가 **한 글자 자리**를 나타낸다. `[^xyz]`처럼 안에 `^`를 쓰면 "x, y, z를 **뺀** 나머지 글자 중에서 한 글자"다.

`\d`처럼 역슬래시 뒤에 글자를 붙인 줄임 표현이 있고, **대문자로 쓰면 반대(여집합)**가 된다.

| 줄임 | 뜻 | 반대 |
|---|---|---|
| `\d` | 숫자 (digit) | `\D` 숫자가 아닌 것 |
| `\w` | 단어 문자 (영문, 숫자, `_`) | `\W` 단어 문자가 아닌 것 |
| `\s` | 공백 (스페이스, 탭, 줄바꿈) | `\S` 공백이 아닌 것 |
| `.` | 아무 글자 하나 (줄바꿈 제외) | — |

### 6-2. 반복 횟수 — 수량자

`\d\d\d\d`처럼 같은 것을 반복해서 쓰는 대신, 뒤에 **횟수**를 붙인다. 수량자는 **바로 앞의 한 덩어리**에 적용된다.

| 수량자 | 뜻 | 예 |
|---|---|---|
| `*` | 0개 이상 | `\d*` |
| `+` | 1개 이상 | `\d+` |
| `?` | 0개 또는 1개 | `-?` (하이픈이 있어도 되고 없어도 됨) |
| `{n}` | 정확히 n개 | `\d{4}` → 숫자 4개 |
| `{n,}` | n개 이상 | `\d{3,}` |
| `{n,m}` | n개 이상 m개 이하 | `\d{3,4}` → 숫자 3~4개 |

```
\d{4}      → 숫자 4개
\d\d{3}    → 숫자 1개 + 숫자 3개 = 숫자 4개 ({3}은 바로 앞의 \d에만 붙는다)
\d{3,6}    → 숫자 3~6개
```

### 6-3. 시작과 끝 — 앵커

`~`(PostgreSQL 정규식 연산자)는 기본적으로 **문자열 어딘가에** 패턴이 있는지를 찾는다. 그래서 앞뒤에 다른 글자가 붙어도 통과한다.

```sql
SELECT 'asdfasdf010-2365-5684asdf' ~ '010-\d{4}-\d{4}';     -- true (중간에 패턴이 있으니까)
SELECT 'asdfasdf010-2365-5684asdf' ~ '^010-\d{4}-\d{4}$';   -- false
SELECT '010-2365-5684'             ~ '^010-\d{4}-\d{4}$';   -- true
```

| 앵커 | 뜻 |
|---|---|
| `^` | 문자열의 **시작** (대괄호 밖에서) |
| `$` | 문자열의 **끝** |

`^`만 쓰면 시작은 고정되지만 끝은 열려 있어서 뒤에 뭔가 붙어도 통과한다. **`^...$`로 양쪽을 막아야** "정확히 이 모양만" 허용된다. CHECK 제약에 쓰는 정규식은 거의 항상 `^`와 `$`로 감싼다.

> `^`는 위치에 따라 뜻이 다르다. 대괄호 **밖**에서는 "시작", 대괄호 **안 맨 앞**(`[^...]`)에서는 "제외"다.

### 6-4. 전화번호 정규식 만들기

옛날 휴대폰 번호는 통신사 번호가 `010`, `011`, `016`, `017`, `018`, `019` 여섯 가지였고, 가운데 자리가 3자리인 번호도 있었다. 이 여섯 가지만 정확히 허용하는 패턴은 이렇다.

```
^01[016789]-\d{3,4}-\d{4}$
```

| 조각 | 뜻 |
|---|---|
| `^01` | `01`로 시작 |
| `[016789]` | 세 번째 자리는 0, 1, 6, 7, 8, 9 중 하나 (2~5는 안 됨) |
| `-\d{3,4}` | 하이픈 + 숫자 3~4개 |
| `-\d{4}$` | 하이픈 + 숫자 4개로 끝 |

### 6-5. 이메일 정규식 읽어보기

```
^[\w.+-]+@[\w-]+\.[\w.]+$
```

| 조각 | 뜻 |
|---|---|
| `[\w.+-]+` | 단어 문자(`\w`)와 `.`, `+`, `-` 중 아무거나 1글자 이상 |
| `@` | `@` 하나 |
| `[\w-]+` | 도메인 이름 (단어 문자와 `-`) |
| `\.` | 점 문자 그대로 |
| `[\w.]+$` | 최상위 도메인 등으로 끝 |

**왜 `\w+`가 아니라 `[\w.+-]+`일까**: `\w`에는 `.`, `+`, `-`가 들어 있지 않다. 그런데 이메일 아이디에는 `hong.gildong`, `user+tag`처럼 이 기호들이 들어갈 수 있다. 그래서 대괄호로 묶어서 "`\w`에 해당하는 글자 **또는** `.` `+` `-`"로 범위를 넓힌 것이다.

**대괄호 안의 점은 그냥 점이다**: 대괄호 **밖**의 `.`은 "아무 글자"지만, 대괄호 **안**에 들어가면 특수한 의미를 잃고 **점 문자 그 자체**가 된다. 그래서 `[\w.]`는 "단어 문자 또는 점"이다. 반대로 대괄호 밖에서 점 문자를 뜻하려면 `\.`처럼 역슬래시로 이스케이프한다.

### 6-6. DBMS별 정규식 사용법

```sql
-- PostgreSQL: ~ 연산자
ALTER TABLE members ADD CONSTRAINT ck_members_phone
    CHECK (phone ~ '^010-\d{4}-\d{4}$');

-- Oracle: REGEXP_LIKE 함수
ALTER TABLE members ADD CONSTRAINT ck_members_phone
    CHECK (REGEXP_LIKE(phone, '^010-[0-9]{4}-[0-9]{4}$'));
```

| DBMS | 정규식 비교 방법 |
|---|---|
| PostgreSQL | `~`(대소문자 구분), `~*`(무시), `!~`(불일치) 연산자 |
| Oracle | `REGEXP_LIKE(컬럼, '정규식')` 함수 |
| MySQL | `REGEXP` 또는 `REGEXP_LIKE()` |

역시 DBMS마다 쓰는 법이 다르다. 외우지 않고, "이 DBMS에서는 정규식을 이렇게 쓰는구나" 정도로 이해하고 필요할 때 찾거나 AI에게 시킨다.

> **보충 — `\w`의 범위는 엔진마다 다르다**: 자바스크립트와 자바의 `\w`는 영문·숫자·밑줄(`[A-Za-z0-9_]`)만이지만, PostgreSQL의 `\w`는 한글 같은 다른 언어 글자도 포함한다. 프론트·백엔드·DB에서 같은 정규식을 쓸 때 결과가 달라질 수 있으므로, 범위를 확실히 하려면 `[A-Za-z0-9_]`처럼 직접 적는 것이 안전하다.

### 6-7. 정규식은 어디서나 쓴다

```html
<!-- HTML: input의 pattern 속성에 정규식만 넣으면 브라우저가 검사해준다 -->
<input type="tel" name="phone" pattern="010-\d{4}-\d{4}" required>
```

```javascript
// 자바스크립트
/^010-\d{4}-\d{4}$/.test("010-2365-5684");   // true
```

```java
// 자바 (문자열 안에서는 역슬래시를 두 번)
"010-2365-5684".matches("^010-\\d{4}-\\d{4}$");   // true
```

> HTML `pattern` 속성은 값 **전체**가 패턴과 일치해야 통과하므로, `^`와 `$`를 쓰지 않아도 양쪽이 고정된 것처럼 동작한다.

## 7. 유효성 검사는 어디서 해야 하나 — 프론트, 백엔드, DB

정규식은 HTML, 자바스크립트, 자바, DB 어디서든 쓸 수 있다. 그럼 세 곳에서 다 검사해야 할까? 강의에서는 투표 결과 "프론트에서만"이 가장 많았다.

**한 곳에만 두자는 쪽 (강의의 의견)**:

- 같은 규칙을 세 곳에 두면 **업무 로직의 중복**이다. 규칙 하나를 바꾸려면 세 곳을 다 고쳐야 하고, 담당자가 다르면 매번 회의를 해야 하고, 맞추다가 오히려 버그가 생긴다.
- 프론트에서 이미 걸러진 값을 백엔드가 가공하다 도메인을 벗어난 값으로 만들었다면, 그건 **백엔드 로직의 버그**이지 DB가 막을 문제가 아니다.
- 프론트를 거치지 않고 백엔드나 DB에 직접 들어오는 것은 **우회(해킹)**다. 해킹은 보안이라는 다른 방식으로 막아야지, 그걸 가정하며 업무 로직을 복잡하게 만드는 건 이상하다.
- 강의자도 DB에는 CHECK를 잘 걸지 않는 편이라고 했다. 다만 **정답은 없고**, 상황에 맞게 선택하면 된다.

**여러 곳에 두자는 쪽**: 정밀하게 결함을 막으려는 관점이다. 한 계층에만 의존하면 **다른 경로로 들어온 데이터가 검증을 우회할 수 있다**는 걱정에서 나온다. 강의에서는 "이해는 되지만 유연한 사고는 아닐 수 있다"고 표현했다.

| | 여러 계층에 중복 검증 | 한 계층에 집중 |
|---|---|---|
| 장점 | 어느 경로로 들어와도 막힌다 | 규칙이 한 곳에 있어 수정이 쉽다 |
| 단점 | 규칙을 바꿀 때 모든 곳을 함께 고쳐야 하고, 한 곳이라도 빠뜨리면 **계층마다 규칙이 어긋난다** | 그 계층을 거치지 않은 데이터는 막지 못한다 |

결국 하나의 정답이 아니라, **프로젝트 상황과 계층별 책임**을 따져 정한다. 특히 DB에 CHECK 같은 제약을 걸지 말지는 개인이 정하지 말고 **팀이 논의해서** 정할 사항이다.

> **보충 — 실무에서 흔한 기준**: 실무에서는 보통 **백엔드 검증은 필수**로 본다. REST API는 브라우저만 호출하는 게 아니라 Postman, `curl`, 모바일 앱, 다른 서버 등 **누구나 직접 호출할 수 있는 공개 입구**라서, 프론트를 거치지 않는 요청이 정상적인 경로로도 들어오기 때문이다. 그래서 흔히 이렇게 역할을 나눈다.
>
> | 위치 | 역할 |
> |---|---|
> | 프론트엔드 | 사용자에게 즉시 피드백을 주는 **사용성** (예: "형식이 올바르지 않습니다") |
> | 백엔드 | **실제 규칙 검사** (Bean Validation `@Pattern`, `@Email` 등) |
> | DB | 데이터의 **절대 불변 규칙**만 (포인트 ≥ 0, 중복 금지, 참조 무결성 등) |
>
> 중복 관리가 부담이라면 규칙을 한 곳(예: 백엔드)에 두고 프론트는 단순 안내만 하는 식으로 줄일 수 있다. 결국 중요한 것은 강의에서 말한 것처럼 **팀이 이유를 갖고 기준을 정하는 것**이다.

**논쟁하는 태도**: 강의에서 의견을 물었을 때, 반론을 받자 위축되는 모습이 아쉬웠다는 이야기가 있었다. 내 의견을 말했으면 빠르게 머리를 굴려 근거를 세우고 끝까지 논리적으로 주장해 보는 연습이 필요하다.

## 8. 엔티티 제약 — PRIMARY KEY와 UNIQUE

도메인 제약으로 모든 컬럼에 올바른 값이 들어왔다. 그럼 결함이 없는가? 아니다.

**엔티티란**: 테이블은 컬럼을 정의한 **형식**이다. 그 형식에 맞춰 실제로 들어간 **레코드 한 줄(행 하나)**이 엔티티다. 테이블이 엔티티가 아니라, **테이블에 들어 있는 데이터 한 행**이 엔티티다. 어디서 찾은 어려운 말("속성의 집합", "테이블의 객체화") 대신 "레코드 한 줄"처럼 내가 이해한 그림으로 말할 수 있어야 한다.

**엔티티의 결함 — 중복**: 컬럼 값이 하나하나 다 올바라도, **똑같은 행이 두 번, 세 번 들어가면** 결함이다. 도플갱어가 생긴 것이라 어느 행인지 **식별할 방법이 없어진다.** 삭제하려 해도, 수정하려 해도 특정할 수 없다.

그래서 **최소한 하나의 컬럼은 중복되지 않는다**는 제약을 건다. 모든 컬럼이 달라야 할 필요는 없고, 식별 가능한 키가 하나라도 있으면 된다.

| 제약 | 뜻 | 예 |
|---|---|---|
| `PRIMARY KEY` | "이 컬럼이 **식별키**다". 중복과 NULL을 허용하지 않음. 테이블당 하나 | `id`, `seq` |
| `UNIQUE` | 식별키는 아니지만 **중복되면 안 되는** 컬럼 | 이메일, 닉네임 |

**UNIQUE가 따로 필요한 이유**: PK는 테이블에 하나뿐이다. 그런데 PK가 아닌 컬럼 중에도 중복되면 안 되는 것이 있다. 닉네임(대화명)이 겹치면 누가 누군지 헷갈리고, 이메일이 겹치면 회원이 중복된 것이다. 이런 컬럼에 `UNIQUE`를 건다.

```sql
CREATE TABLE notices (
    seq     VARCHAR(10)   PRIMARY KEY,                      -- 기본키
    title   VARCHAR(300)  NOT NULL,
    writer  VARCHAR(50)   NOT NULL UNIQUE,                  -- NOT NULL + UNIQUE
    content VARCHAR(4000),
    regdate TIMESTAMP     DEFAULT CURRENT_TIMESTAMP,
    hit     INT           DEFAULT 0
);
```

> 위 코드의 `writer UNIQUE`는 UNIQUE 문법을 보여주기 위한 예시다. 실제로 공지사항의 `writer`(작성자)에 UNIQUE를 걸면 **한 사람이 공지를 하나밖에 못 쓰게** 된다. UNIQUE는 "업무상 정말로 겹치면 안 되는 값"에만 건다.

**자동 증가 — PK를 위한 기본값**: DB 도구의 컬럼 설정 화면에는 Not Null, Primary Key, UNIQUE 체크박스와 함께 **Auto Increment**(자동 증가)가 있다. PK에 일반 `DEFAULT`를 주면 같은 값이 계속 들어가 중복이 생긴다. 자동 증가는 값을 **1씩 늘려서** 넣어주므로, PK를 위한 특별한 기본값이라고 볼 수 있다. PostgreSQL에서는 `GENERATED BY DEFAULT AS IDENTITY`(또는 `SERIAL`)로 만든다.

## 9. 릴레이션(참조) 제약 — FOREIGN KEY

컬럼 값도 올바르고, 행도 중복 없이 식별된다. 그래도 아직 결함이 남는다. **관계에서의 참조 결함**이다. "내 부모는 누구다"라고 했는데 그 부모가 **가짜**이거나 **존재하지 않는** 경우다.

**참조는 자식이 한다**: 참조키(외래키)는 **언제나 자식이 갖는다.** 부모가 자식을 참조하는 일은 없다. 회원(`users`)과 공지(`notice`)라면 공지가 자식이고, 공지의 `writer` 컬럼이 회원의 `id`를 참조하는 외래키다.

```
users (부모)                 notice (자식)
id       name                seq  title         writer
NEWLEC   뉴렉        ◀───    1    ORACLE 개요    NEWLEC
YJS      유재석              2    SQL 구문       NEWLEC
JUNG     정형돈              3    DML 사용하기   NEWLEC
KANG     강호동              4    DML 사용하기   DRAGON   ← 회원에 DRAGON이 없다!
                             5    DML 사용하기   DRAGON   ← 참조 결함
```

**아우터(OUTER)는 열이 아니라 행이다**: 조인했을 때 **짝을 찾지 못한 행**이 아우터다. 위 그림에서 공지 쪽 아우터는 4, 5번 행이다. 존재하지 않는 부모(DRAGON)를 가리키고 있다. 처음부터 없는 부모를 가짜로 넣었거나, 부모(회원)가 삭제됐는데 공지의 참조를 정리하지 않아 결함으로 남은 상태다.

**외래키 제약을 걸면** 자식 행이 들어올 때 DB가 부모 테이블에 그 값이 실제로 있는지 확인하고, 없으면 INSERT를 거부한다.

```sql
CREATE TABLE notices (
    seq     VARCHAR(10),
    title   VARCHAR(300) NOT NULL,
    writer  VARCHAR(50)  NOT NULL,
    regdate TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    hit     INT          DEFAULT 0,

    CONSTRAINT notices_seq_pk    PRIMARY KEY (seq),
    CONSTRAINT notices_writer_fk FOREIGN KEY (writer) REFERENCES members (id)
);
```

`FOREIGN KEY (writer) REFERENCES members (id)`: "이 테이블의 `writer`는 `members` 테이블의 `id`를 가리킨다"는 뜻이다. 이렇게 하면 **처음부터** 없는 부모를 지정해서 들어오는 것을 막을 수 있다. DB 도구에서는 Foreign Key 탭에서 이름, 참조할 부모 테이블, 부모 컬럼을 지정하면 된다.

### 9-1. 부모가 바뀌거나 사라질 때 — 참조 동작 옵션

처음 넣을 때는 부모가 있었는데, **나중에 부모가 삭제되거나 키가 바뀌면** 어떻게 할까? 자식은 아무 짓도 안 했는데 부모가 먼저 떠나버리는 상황이다. 이때 할 일을 `ON DELETE`, `ON UPDATE` 옵션으로 정한다(흔히 캐스케이드 옵션이라고 부른다).

| 옵션 | 부모가 삭제(수정)되면 | 비유 |
|---|---|---|
| `NO ACTION` (**기본값**) | 자식이 있으면 부모 삭제를 **거부** | "내가 있는데 어딜 가? 지울 거면 나부터 정리하고 가." |
| `CASCADE` | 자식도 **함께** 삭제(수정) | 부모를 따라간다 |
| `SET NULL` | 자식의 참조를 **NULL**로 | "참조하는 부모가 없다"로 남긴다 |

**NO ACTION**: 자식부터 지우거나 다른 부모로 옮겨야만 부모가 사라질 수 있다. 가장 안전한 기본값이다.

**CASCADE — 위험하지만 꼭 필요한 곳이 있다**: 부모가 지워지면 자식도 따라 지워지므로 반드시 검토하고 써야 한다. 그래도 이런 곳에는 잘 맞는다.

- **댓글**: 게시글을 지웠는데 댓글만 남아 있으면 아무 쓸모가 없다.
- **메뉴의 옵션 정보**: 메뉴를 지우면 그 메뉴의 크기·온도 옵션도 함께 사라져야 한다.

**SET NULL — 컬럼이 NULL을 허용해야 쓸 수 있다**: 부모가 지워지면 자식의 참조를 NULL로 바꾸는 방식이라, 외래키 컬럼에 `NOT NULL`이 걸려 있으면 쓸 수 없다(부모를 지우는 순간 NOT NULL 위반으로 실패한다). 예를 들어 "카테고리가 지워지면 메뉴는 남기고 미분류로 두자"고 정했다면, `menus.category_id`는 NULL을 허용해야 한다. 반대로 "메뉴는 반드시 카테고리가 있어야 한다"는 규칙이라면 SET NULL이 아니라 NO ACTION이 맞다. **컬럼의 NULL 허용 여부와 업무 규칙을 함께** 봐야 한다.

**ON UPDATE**: 카테고리 테이블처럼 부모가 지워지는 건 막고(`ON DELETE NO ACTION`), 부모의 키 값이 **바뀌면** 자식의 참조도 따라 바뀌게(`ON UPDATE CASCADE`) 따로 설정할 수도 있다.

> **보충**: 실무에서는 PK를 자동 증가 번호 같은 **대리키**로 두고 **값을 바꾸지 않는 것**이 원칙이라 `ON UPDATE`가 실제로 동작할 일은 드물다. 또 회원이 탈퇴해도 보통 회원 행(키)을 실제로 지우지 않는다. 그 회원이 남긴 주문, 결제, 게시글 같은 기록과 연결이 끊기면 어떤 문제가 생길지 모르기 때문이다. 대신 상태 컬럼만 "탈퇴"로 바꾸는 **논리 삭제**를 많이 쓴다.

어떤 옵션을 쓸지는 혼자 정하지 말고 팀과 논의하고, **AI 조원에게도 물어본다.** "이 관계는 삭제할 때 어떤 옵션이 좋을까?" → 답을 듣고 → "내 생각은 다른데, 이런 경우는 어떻게 해?"처럼 대화하며 결정한다.

## 10. 정리 — 세 단계의 방어선과 트랜잭션

| 단계 | 질문 | 제약 |
|---|---|---|
| 도메인 | 각 컬럼 값이 올바른가? | 자료형·길이, NOT NULL, DEFAULT, CHECK(정규식) |
| 엔티티 | 각 행이 식별 가능한가(중복이 없나)? | PRIMARY KEY, UNIQUE |
| 릴레이션 | 참조하는 부모가 실제로 있나? | FOREIGN KEY (+ 참조 동작 옵션) |

세 가지 제약을 모두 거쳐야 결함 없는 데이터베이스가 된다.

**문법보다 개념**: 제약 조건 문법은 DBMS와 버전마다 조금씩 다르다. 외울 필요 없다. 요즘은 DB 도구의 체크박스나 탭으로 설정하거나 AI에게 "이 컬럼을 PK로, 이 컬럼에 UNIQUE를 걸어줘"라고 시키면 된다. 중요한 것은 **어떤 제약이 있는지, 어디에 왜 걸어야 하는지**를 판단할 수 있는 개념과 논리다.

**다음: 트랜잭션**: 제약 조건이 가장 큰 영향을 주는 곳이 **트랜잭션**이다. 예를 들어 "글을 등록하면 포인트를 주는" 이벤트에서, 글 등록은 성공했는데 포인트 지급이 제약 조건 위반으로 실패하면 어떻게 될까? 제약 위반은 예외를 일으키고, 그 예외로 트랜잭션 전체가 롤백되는지를 확인하는 것이 다음 단계다.
