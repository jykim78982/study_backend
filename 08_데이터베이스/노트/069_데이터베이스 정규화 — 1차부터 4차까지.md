# 데이터베이스 정규화 — 1차부터 4차까지

정규화(Normalization)가 왜 필요한지, 그리고 1~4차 정규화가 각각 어떤 형태의 중복을 없애는 것인지를 정리한다.

## 1. 정규화란 — "표준화"는 곧 "중복 제거"

데이터베이스가 등장하기 전에는 부서마다 파일로 데이터를 따로 들고 있었다. 학번·이름·납입금·납입일을 담은 파일과, 학번·이름·도서명·대여일을 담은 파일이 각자 존재하면, "학번-이름"이라는 정보가 여러 파일에 중복 저장된다. 중복이 있으면 한쪽만 수정되고 다른 쪽은 갱신되지 않는 **불일치(결함)**가 발생한다.

데이터베이스가 여러 부서의 데이터를 한곳에 모아 관리하는 이유가 바로 이 중복·결함을 없애기 위해서다. 그래서 "데이터베이스에서 말하는 테이블의 가장 표준화된 방식은 무엇인가"라는 질문에 대한 답은 **중복이 제거된 형태**이며, 그 표준을 맞추는 작업이 곧 **정규화**다.

정규화는 원래 1~6차까지 있지만, 실무에서는 물론 정보처리기사 시험에서도 5·6차 정규화는 다루지 않는다. 모델링을 제대로 했다면 4차 정규화까지 위반이 발생할 일도 드물다. 여기서는 1~4차 정규화의 핵심만 정리한다.

## 2. 1차 정규화 — 원자 값이 아닌 도메인을 분해한다

**원자 값(Atomic Value)**이란 더 이상 쪼갤 수 없는 하나의 값을 말하고, **도메인(Domain)**은 어떤 컬럼에 들어갈 수 있는 유효한 값의 범위를 말한다(예: `나이` 컬럼의 도메인에 `-3`은 포함되지 않는다).

1차 정규화 위반은 **한 컬럼에 값이 여러 개 들어갈 수 있는 경우**다. 예를 들어 메뉴 테이블에 다음과 같은 컬럼이 있다고 하자.

```
메뉴(아이디, 한글명, 영문명, 가격, 이미지, 설명, 종류, 크기, 아이스유무, 재료명, 재료가격, 재료유효기간, 재료칼로리)
```

- `종류`나 `아이스유무`처럼 하나의 값만 가질 수 있는 컬럼은 문제가 없다(커피면서 빵일 수는 없고, 아이스이면서 뜨거울 수도 없다).
- 하지만 `재료명`처럼 한 메뉴(예: 카페라떼)가 원두·우유 등 **여러 개의 값**을 가질 수 있는 컬럼은 1차 정규화 위반이다.
- `크기`도 한 메뉴가 tall·grande·venti 여러 사이즈를 지원한다면, 한 행에 `tall,grande`처럼 콤마로 여러 값을 욱여넣는 것은 데이터베이스 입장에서 관리할 수 없는 데이터다 — 수정·삭제·추가를 하려면 SQL만으로는 안 되고 별도 알고리즘이 필요해지기 때문이다.

**해결**: 여러 개의 값을 가질 수 있는 속성은 부모에서 빼내 자식 테이블로 만든다.

```
메뉴(아이디, 한글명, 영문명, 가격, 설명, 종류, 아이스유무)
재료(아이디, 명, 가격, 유효기간, 칼로리, 메뉴아이디(FK))
```

다만 이것이 절대 규칙은 아니다. 콤마로 여러 값을 담는 방식을 예외적으로 옵션처럼 쓰는 경우도 실무에는 있다 — 다만 "왜 그렇게 정규화를 위반해서 설계했는가"를 설명할 수 있어야 한다.

## 3. 2차 정규화 — 부분적 함수 종속을 제거한다

**함수(Function)**는 여기서 **키(Key)**를 뜻한다. 어떤 데이터든 키를 통해 간접적으로 찾아가며, 기본키(PK)와 외래키(FK) 둘 다 이 "함수"에 해당한다. **함수 종속**이란 키로 식별되는 속성들의 관계를 말한다.

2차 정규화는 **키가 복합키(여러 컬럼으로 이루어진 키)인 테이블**에서만 발생할 수 있는 문제다. 복합키의 **일부에만** 종속되는 속성이 섞여 있으면 **부분적 함수 종속**이라 부르고, 이것이 2차 정규화 위반이다.

예를 들어 회원과 메뉴가 다대다(M:N)로 "추천"한다는 업무를 모델링하면, 다대다 관계는 그 자체로 엔티티가 될 수 없으므로 회원아이디+메뉴아이디를 복합키로 갖는 자식 테이블(식별 관계)이 만들어진다.

```
추천(회원아이디(PK,FK), 메뉴아이디(PK,FK), 일자, 이유, 연락처, 매뉴명)
```

여기서 `연락처`는 회원 쪽 정보이고 `매뉴명`은 메뉴 쪽 정보다. 즉 복합키 전체가 아니라 `회원아이디`(일부)에만 종속된 속성이 섞여 들어와 있는 것 — 이것이 부분적 함수 종속이다.

**해결**: 복합키의 일부에만 종속된 속성은 원래 자기 테이블(부모)로 되돌려 보낸다. `연락처`는 회원 테이블로, `메뉴명`은 메뉴 테이블로 옮기고, `추천` 테이블에는 추천 자체에 온전히 종속되는 속성(일자, 이유)만 남긴다.

> 참고로 몇 대 몇 관계인지는 정해진 규칙이 아니라 업무 자체가 결정한다. "회원 하나가 메뉴 여러 개를 추천할 수 있는가", "메뉴 하나가 여러 회원에게 추천될 수 있는가"를 각각 따져서 1:N, N:1, M:N 여부가 정해지고, M:N일 때만 별도의 식별 관계 테이블(복합키)이 필요해진다.

## 4. 3차 정규화 — 이행적 함수 종속을 제거한다

**이행적(전이적) 함수 종속**이란, 기본키가 아닌 속성(주로 외래키)을 통해 **간접적으로만** 식별되는 속성이 테이블에 섞여 있는 경우를 말한다. 정상적인 테이블은 기본키 하나로 모든 속성을 한 번에 식별할 수 있어야 하는데, 그렇지 않고 "이 속성을 보려면 다른 속성을 한 번 더 거쳐야" 하는 상태다.

2차 정규화가 **복합키(식별 관계)** 안에서 벌어지는 문제라면, 3차 정규화는 **비식별 관계**에서 벌어지는 문제라는 점이 다르다. 예를 들어 2차 정규화에서 부분적 함수 종속이었던 속성을 복합키가 아니라 일반 외래키(비식별 관계)로 내려보내면, 그 속성은 기본키가 아닌 외래키를 거쳐야만 식별되는 이행적 함수 종속이 되어버린다.

```
주문(아이디(PK), 일자, 수량, 연락처, 매장명, 메뉴명, 회원아이디(FK), 메뉴아이디(FK))
```

여기서 `연락처`는 `아이디`로 바로 식별되는 게 아니라, `회원아이디(FK)`를 한 번 거쳐야 식별되는 값이다 — 이행적 종속.

**해결 방식은 2차 정규화와 사실상 같다**: 외래키를 거쳐야만 식별되는 속성은 그 외래키가 가리키는 원래 테이블로 옮긴다. 2차 정규화를 제대로 했다면 3차 정규화 위반이 따로 발생하기 어렵다 — 부분 함수 종속이던 것이 식별 관계 대신 비식별 관계로 내려가면 이행적 종속이 되는 것뿐, 본질은 같은 문제이기 때문이다.

## 5. 4차 정규화 — 다치 종속을 제거한다

**다치 종속(Multi-Valued Dependency)**은 한 속성이 복수의 값을 가질 때, 다른 속성과 "곱(product)" 형태로 튜플이 불필요하게 증식하는 현상이다. 실무에서 다대다(M:N) 관계를 정규화 없이(즉 연결 테이블 없이) 그대로 저장하려고 하면 이 현상이 나타난다.

**해결**: 다대다 관계는 그대로 두지 않고, 두 테이블 사이에 연결(교차) 테이블을 두어 각각 1:N, N:1 관계로 풀어낸다. 이 규칙은 이미 데이터 모델링 단계에서 다대다 관계를 항상 연결 테이블로 풀어왔기 때문에(2·3차 정규화에서 다룬 `추천`, `주문` 테이블이 바로 그 예), 모델링을 정상적으로 했다면 4차 정규화는 별도로 신경 쓰지 않아도 이미 지켜져 있는 경우가 대부분이다.

## 6. 정리

| 정규화 | 제거 대상 | 핵심 |
|---|---|---|
| 1차 정규화 | 원자 값이 아닌 도메인 | 한 컬럼에 여러 값이 들어가면 자식 테이블로 분리 |
| 2차 정규화 | 부분적 함수 종속 | 복합키(식별 관계)의 일부에만 종속된 속성을 원래 테이블로 되돌림 |
| 3차 정규화 | 이행적 함수 종속 | 비식별 관계에서 외래키를 거쳐야만 식별되는 속성을 원래 테이블로 되돌림 |
| 4차 정규화 | 다치 종속 | 다대다 관계를 연결 테이블로 풀어 튜플 증식을 막음 |

정규화 규칙을 외워서 기계적으로 적용하기보다, "이 속성이 정말 이 테이블의 키 전체에 종속되는가?"를 데이터가 실제로 들어간 모습을 상상하며 확인하는 것이 정규화의 본질이다. 모델링을 꼼꼼히 했다면 정규화 위반은 애초에 잘 발생하지 않는다.
