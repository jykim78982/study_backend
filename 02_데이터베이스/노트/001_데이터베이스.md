# 데이터베이스 기초 개념 정리

## 1. 데이터베이스와 무결성

데이터베이스의 핵심 목표 중 하나는 **무결성(Integrity)** 이다. 데이터가 정확하고 일관되게 유지되는 성질을 말한다.

무결성을 해치는 대표적인 원인은 **데이터 복사본, 즉 중복 데이터**이다. 같은 데이터가 여러 곳에 복사되어 있으면, 한쪽만 수정되고 다른 쪽은 그대로 남아 데이터가 어긋날 수 있다. 따라서 중복을 줄이는 것이 무결성 유지의 핵심이다.

```
중복 데이터 → 무결성 위협
     ↓ 정규화로 해결
중복 제거된 데이터 → 무결성 유지
```

---

## 2. 정규화와 관계형 DBMS

**관계형 DBMS**(예: PostgreSQL)는 중복 문제를 **정규화(Normalization)** 로 해결한다.

정규화란 **중복이 제거된, 잘 구조화된 데이터** 형태로 만드는 작업이다. 데이터를 적절히 나누고 관계로 연결하여, 같은 정보가 여러 번 저장되지 않게 한다. 결과적으로 무결성이 지켜진다.

---

## 3. 무엇을 저장할지는 업무가 결정한다

**저장할 데이터는 업무자(현업의 필요)가 결정한다.** 기술이 아니라 "무슨 일을 하는지"에서 출발한다는 뜻이다. 그 업무를 분석하면 자연스럽게 저장할 대상과 행위가 드러난다.

---

## 4. Entity(엔티티) — 저장할 데이터의 단위

**Entity**는 데이터베이스에 저장할 하나의 대상, 즉 **저장할 내용의 덩어리**이다. 관점에 따라 여러 이름으로 불린다.

```
Entity = 객체(object) = 테이블(table) = 구조체(struct)
```

**속성(Attribute)** 은 그 entity가 가진 세부 정보이다. 예를 들어 "상품"을 관리한다면 다음과 같다.

- **Entity**: 상품
- **속성**: 가격, 이미지, 스펙 등

같은 "Entity(개체)"라는 용어가 자바 객체지향에서는 전혀 다른 뜻으로 쓰인다. DB 설계에서는 저장할 데이터의 단위(위 의미)를 가리키지만, 자바 OOP에서는 역할명 자체(=클래스)를 가리키는 말로 쓰인다.

즉 **여러 속성이 모인 하나의 데이터 단위가 entity**이다. 상품이라는 entity가 가격·이미지·스펙 같은 속성들을 품고 있는 구조이다.

---

## 5. 대상, 행위자, 그리고 관계

업무를 분석하면 다음 요소들이 나온다.

| 요소 | 설명 |
|------|------|
| 대상 / 행위자 | 각각 하나의 entity가 됨. 이들을 구분하는 것이 **key(식별자)** |
| 행위 (= 관계) | 대상과 행위자 사이에 벌어지는 일. 이것을 **관계(relationship)** 라고 함 |
| 역할자 | 그 관계 속에서 특정 역할을 맡는 대상 |

정리하면, "누가(행위자) 무엇을(대상) 어떻게 한다(행위)"에서 **행위 = 관계**로 표현된다.

---

## 6. M:N 관계는 entity로 만든다

**대상과 행위자가 M:N(다대다)으로 엮이는 행위는, 그 자체를 별도의 entity로 등록한다.**

다대다 관계는 테이블 두 개만으로는 깔끔하게 표현되지 않는다. 그래서 그 "관계(행위)" 자체를 하나의 새로운 테이블(entity)로 만들어 중간에 둔다.

### 예시

```
학생(행위자) —— 수강(행위) —— 과목(대상)
   M                              N
```

한 학생이 여러 과목을 듣고, 한 과목을 여러 학생이 듣는 M:N 관계이다. 이때 "수강"이라는 행위를 별도 entity(수강 테이블)로 만들어 학생과 과목을 연결한다. 이 중간 테이블이 M:N을 풀어주는 역할을 한다.

---

## 7. 모델링이란? — 행위와 정보를 데이터 구조로 옮기는 설계

**데이터베이스 모델링**은 시스템의 실제 행위와 정보를 데이터 구조로 옮기는 설계 과정이다.

1. 요구사항을 **엔티티와 속성**으로 분해해 어떤 데이터를 저장할지 결정한다.
2. 엔티티 간 **관계**를 정의해 외래키·연관관계를 설계하고, **정규화**로 중복을 줄인다.
3. 실제 운영을 고려해 **인덱스, 조회 패턴, 응답성** 등을 반영한 물리적 설계로 보완한다.

즉 5~6장에서 다룬 entity·속성·관계·M:N 처리는 모두 이 모델링 과정의 각 단계에서 하는 일이다.

---

## 8. 비유 — 건축 설계도 그리기

모델링은 건축 설계도를 그리는 것과 같다.

| 건축 | 데이터베이스 |
|---|---|
| 고객의 사용 용도 | 요구사항 |
| 방 | 엔티티 |
| 방의 크기, 창문 같은 세부 | 속성 |
| 방 사이의 통로 | 관계 |

용도(요구사항)를 먼저 알아야 방(엔티티)이 몇 개 필요하고, 방마다 어떤 세부(속성)가 필요하며, 방들을 어떻게 연결(관계)할지가 정해진다.

---

## 9. 실무 흐름 — 개념적 → 논리적 → 물리적 모델

```
요구분석 → 개념적 모델(ER 다이어그램) → 논리적 모델(테이블·칼럼·키) → 물리적 모델(인덱스·파티셔닝·제약)
```

- **개념적 모델**: 엔티티와 관계를 ER 다이어그램으로 표현. 특정 DBMS나 타입에 아직 매이지 않는다.
- **논리적 모델**: 개념 모델을 실제 테이블·칼럼·PK/FK로 구체화한다.
- **물리적 모델**: 인덱스, 파티셔닝, 제약조건 등 운영 성능까지 고려해 보완한다.

---

## 10. 정규화의 핵심과 트레이드오프

정규화는 **1NF → 2NF → 3NF** 단계로 진행하며 중복과 이상현상(삽입·갱신·삭제 이상)을 줄인다.

**1NF (제1정규형) — 원자값(Atomic Value)으로 쪼개기**

한 칸(셀)에 값이 여러 개 들어가 있으면 안 된다. 각 컬럼은 더 이상 쪼갤 수 없는 단일 값만 가져야 한다.

```
[위반] 학생(이름, 수강과목)
철수 | 수학,영어,과학        ← 한 칸에 여러 값

[1NF 만족] 학생(이름, 과목)
철수 | 수학
철수 | 영어
철수 | 과학
```

**2NF (제2정규형) — 부분 함수 종속 제거**

기본키가 여러 컬럼으로 이루어진 복합키일 때 적용된다. 기본키 전체가 아니라 **기본키의 일부에만 종속된 컬럼**을 별도 테이블로 분리한다.

```
[위반] 수강(학번, 과목번호, 학생이름, 과목명, 점수)
기본키 = (학번, 과목번호)
- 학생이름은 학번에만 종속 (과목번호와 무관) → 부분 종속
- 과목명은 과목번호에만 종속 (학번과 무관) → 부분 종속

[2NF 만족]
학생(학번, 학생이름)
과목(과목번호, 과목명)
수강(학번, 과목번호, 점수)
```

**3NF (제3정규형) — 이행 함수 종속 제거**

기본키가 아닌 컬럼이, 또 다른 기본키 아닌 컬럼을 거쳐서 간접적으로 종속되는 경우를 제거한다.

```
[위반] 학생(학번, 학과번호, 학과사무실위치)
학번 → 학과번호 → 학과사무실위치  (학과사무실위치는 학번이 아니라 학과번호에 종속)

[3NF 만족]
학생(학번, 학과번호)
학과(학과번호, 학과사무실위치)
```

| 단계 | 핵심 규칙 |
|---|---|
| 1NF | 한 칸에는 값 하나만 (원자값) |
| 2NF | 복합키의 일부에만 종속된 컬럼 분리 (부분 종속 제거) |
| 3NF | 기본키 아닌 컬럼끼리의 종속 관계 제거 (이행 종속 제거) |

셋 다 결국 "같은 정보가 여러 곳에 중복 저장되지 않게" 만드는 과정이고, 단계가 올라갈수록 더 엄격한 기준으로 테이블을 쪼갠다.

다만 **과도한 정규화는 JOIN 비용을 늘린다.** 조회가 잦은 서비스라면 일부 데이터를 일부러 **비정규화**해서 성능을 확보하기도 한다. 정규화는 "무조건 끝까지"가 아니라 무결성과 조회 성능 사이의 트레이드오프다.

---

## 11. 관계 타입 — 1:1은 드물고, M:N은 조인 테이블로

- **1:1** 관계는 실무에서 드물게 등장한다.
- **1:N**과 **M:N**이 훨씬 자주 쓰인다. M:N은 (6장에서 다룬 대로) 별도의 조인 테이블(연결 entity)로 표현한다.

M:N을 조인 테이블 없이 **컬럼에 배열 형태로 저장**하면 질의(query)와 무결성 관리가 어려워진다.

---

## 12. 도메인 지식이 설계 품질을 결정한다

업무 흐름을 잘 알아야 **경계값, 식별자, 상태 전이** 등을 정확히 반영할 수 있다. 경력이 쌓일수록 설계 품질이 높아지는 것도 이런 도메인 지식이 축적되기 때문이다.

---

## 13. 성능을 고려한 물리적 설계 예시

| 서비스 특성 | 설계 방향 |
|---|---|
| 읽기 위주 | 인덱스, 캐시 활용 |
| 쓰기가 많음 | 파티셔닝, 비동기 처리 |

같은 데이터를 다루더라도 읽기/쓰기 패턴에 따라 물리적 설계 방향이 크게 달라진다.

---

## 14. 주의점 — 모델링은 이론으로 끝나지 않는다

요구사항이 변경되면 스키마도 함께 바뀐다. 그래서 설계 단계에서 **마이그레이션 계획과 데이터 이전 전략**까지 함께 세워야 한다. 모델링은 한 번 그리고 끝나는 문서가 아니라, 요구 변화에 맞춰 계속 갱신되는 살아있는 설계다.

---

## 15. 전체 흐름 요약

1. DB의 목표는 **무결성** 유지
2. 무결성을 해치는 **중복 데이터**를, 관계형 DBMS는 **정규화**로 제거 (단, 과도하면 JOIN 비용이 늘어 일부 비정규화로 절충하기도 함)
3. 무엇을 저장할지는 **업무**가 결정
4. 저장 단위는 **entity**(= 객체 = 테이블 = 구조체), 그 세부는 **속성**
5. 업무에는 **대상·행위자**(entity, key로 식별)와 **행위**(= 관계)가 있음
6. 특히 **M:N 관계인 행위는 별도 entity로** 등록하여 표현
7. 모델링은 **요구분석 → 개념적 모델 → 논리적 모델 → 물리적 모델** 순서로 진행
8. 물리적 설계에서는 **인덱스·조회 패턴·응답성**은 물론, 요구 변경에 대비한 **마이그레이션 전략**까지 함께 고려
