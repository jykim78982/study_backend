# RDBMS와 SQL 기초

## 1. 파일 시스템에서 데이터베이스로 — 결함이 만든 전환

과거에는 프로그램마다 **각자 파일을 하나씩 갖고 조작**하는 방식을 썼다. 데이터베이스와의 가장 큰 차이는 **데이터를 한곳에 모아뒀다는 것**이다.

데이터를 모으게 된 이유는 **결함(장애) 때문**이다. 각 프로그램이 데이터를 따로 갖고 있으면 서로 **싱크가 안 맞고**, 억지로 싱크를 맞추는 과정에서 결함이 계속 생겨난다. 이 결함을 해결하는 방법은 결국 하나다 — **데이터를 각자 갖지 않고 한곳에 모아두고, 필요할 때 참조하는 형식**으로 바꾸는 것.

```
각자 파일 보유 → 싱크 안 맞음 → 결함 발생
        ↓ 해결
데이터를 한곳에 모으고 참조하는 방식
```

## 2. 데이터를 모아두는 방식은 여러 가지가 있다 — 그중 관계형

"데이터를 모아두고 참조한다"는 아이디어를 실제로 구현하는 방법은 관점에 따라 여러 갈래로 나뉘었다.

- 계층형(Hierarchical)으로 보는 관점
- 네트워크형(Network)으로 보는 관점
- 객체지향(Object-oriented)의 형태로 보는 관점
- **관계(Relational)**로 보는 관점

우리가 지금 배우고 실무에서 주로 쓰는 것은 이 중 **관계형 데이터베이스(Relational Database)**다.

## 3. DBMS/RDBMS가 필요한 이유

데이터를 그냥 모아두기만 한다고 끝이 아니다. 여러 사용자가 동시에 접근할 때의 **동시성**, 대량 데이터를 다룰 때의 **성능**, 함부로 못 보게 막는 **보안** — 이 세 가지는 데이터를 모아둔 것만으로는 저절로 해결되지 않는다.

그래서 이걸 대신 관리해주는 **관리자(엔진)**가 필요하다. 이게 바로 **DBMS(DataBase Management System)**이고, 관계형 모델을 쓰는 DBMS를 **RDBMS**라고 부른다.

앞으로 데이터를 다룬다는 건 결국 **RDBMS와 대화하는 방식**으로 데이터를 관리한다는 뜻이다. RDBMS를 쓰기로 한 순간, 예전에 파일 시스템을 직접 다루던 API들은 더 이상 기억할 필요가 없다 — 그 역할을 이제 RDBMS가 대신하기 때문이다. 그리고 RDBMS와 대화하기 위해 RDBMS가 제공하는 **명령어 집합이 SQL**이다.

## 4. 왜 PostgreSQL을 많이 쓰는가 — RDBMS 제품 비교

- **MySQL**: 오픈소스이지만 상업적으로 쓰려고 하면 유료 라이선스에 걸리는 애매한 위치에 있다.
- **MariaDB**: MySQL을 클론해서 나온 제품. 한동안 MySQL의 대안으로 많이 쓰였다.
- **PostgreSQL**: 최근 AI와 맞물려 **벡터 데이터**로도 쓸 수 있다는 장점 때문에 겸사겸사 많이 쓰는 추세다.
- **Oracle**: 기업형 유료 시장에서는 여전히 강세다.

DBMS마다 제공하는 **자료형과 함수 종류에는 조금씩 차이**가 있을 수 있다는 걸 염두에 둬야 한다.

### 표준 SQL과 DBMS별 차이

미국에서 정한 **표준 SQL(ANSI SQL)**이 있지만, 이건 어디까지나 **가이드**일 뿐 모든 DBMS가 완벽히 따르지는 않는다. SQL의 "종류"가 여러 개로 갈라진 이유도 이것 — DBMS가 각자 따로 만들어지면서 서로 호환성이 떨어졌기 때문이다.

- 표준에서 가장 멀리 떨어져 있는 게 **Oracle**이다. 기능이 같으면 이름이라도 통일하면 좋을 텐데, 시장 점유율이 높은 입장에서는 **고객 이탈을 막기 위해 오히려 표준을 잘 안 따르는** 경향이 있다.
- **PostgreSQL**은 후발주자로 나오면서 ANSI 표준에 비교적 가깝게 맞춰져 있다.
- 예를 들어 Oracle은 정수든 실수든 구분 없이 **모두 `NUMBER`** 하나로 관리한다.
- ANSI도 버전이 올라가면서 계속 새 표준을 **제안**하지만, 그걸 실제로 따를지 말지는 어디까지나 **각 DBMS 개발사의 결정**이다.

자바 자료형과 DBMS 자료형을 완전히 다른 것으로 생각할 필요는 없다. **개념적으로는 같은 자료형인데, 표현하는 키워드나 다룰 수 있는 범위에 차이가 있을 뿐**이라고 보면 된다.

## 5. SQL 명령어의 세 가지 분류

먼저 짚어야 할 질문: 우리는 정수·실수·문자 같은 **낱개 데이터**만 다룰까, 아니면 그걸 묶어놓은 **나만의 데이터 구조**로 다룰까? 답은 후자다. 데이터베이스가 다루는 건 **구조화된 데이터**이고, 구조가 있으려면 반드시 **grouping(묶기)**이 뒤따른다.

이 구조를 다루는 SQL 명령어는 크게 세 그룹으로 나뉜다.

| 분류 | 이름 | 역할 |
|---|---|---|
| **DDL** | Data Definition Language | 데이터(테이블) 자체를 정의 |
| **DML** | Data Manipulation Language | 정의된 데이터를 조작(조회·삽입·수정·삭제) |
| **DCL** | Data Control Language | 데이터 접근 권한을 제어 |

**DDL — 데이터 정의하기**

- `CREATE`: 내가 다룰 데이터를 알려주는 것. "나는 `menu`라는 데이터를 이런 속성들로 쓰겠다"고 선언하는 단계.
- `ALTER`: 이미 정의한 것을 고치기.
- `DROP`: 정의한 것을 없애기.

이렇게 데이터를 **정의**하고 나면, 그다음부터 `DML`로 데이터를 가져오거나 조작할 수 있다.

**DCL — 접근 권한 제어**

관리자 입장에서 "이 사람은 데이터를 가져가도 된다/안 된다"를 제어하고 싶다면 `GRANT`(권한 부여)나 `REVOKE`(권한 회수)를 쓴다.

### 실무에서 얼마나 외워야 하나

- **DDL**(`CREATE`/`ALTER`/`DROP`): 프로젝트 하나에서 `CREATE TABLE`을 쓰는 횟수는 딱 한 번, 많아야 프로젝트 기간(6개월~1년) 동안 몇 번 안 된다. 그래서 구문을 달달 외울 필요는 없다 — **"무엇을 create할지 판단하는 능력"**(=모델링 능력)이 진짜 실력이고, 구문 자체는 필요할 때 찾아보는 정도면 충분하다. 각 명령어가 "무슨 역할을 하는지"만 알면 된다.
- **DML**(`INSERT`/`SELECT`/`UPDATE`/`DELETE`): 이건 **무조건 외워야 한다.** 요즘 시대에 SQL을 직접 타이핑할 일은 줄었어도, SQL을 모르고는 도구를 제대로 다루기 어렵기 때문이다.
- **DCL**(`GRANT`/`REVOKE`): 그다지 비중이 크지 않다. (예: "ncafe라는 계정에게 퍼블릭 스키마를 쓸 수 있는 권한을 줘라" → `GRANT`)

## 6. 네이밍 컨벤션

- **스네이크_표기법(snake_case)**을 쓴다. 예: `kor_name` (○), `korName` (✕)
- **테이블명은 복수형**을 쓴다. 예: `menus`

## 7. 자료형 — CHAR vs VARCHAR, 그리고 키 선택

### 문자열: 고정 길이 vs 가변 길이

문자열을 저장하는 방식은 두 가지다.

- **`CHAR(255)`**: 항상 255개 문자 공간을 그대로 쓴다. 예를 들어 "아메리카노"(5글자)만 저장해도 나머지 250개 공간은 그냥 비워둔 채 남는다.
  - **장점**: 각 데이터가 항상 같은 길이만큼 공간을 차지하므로, 지정된 길이만큼 건너뛰기만 하면 다음 데이터를 빠르게 찾을 수 있다.
  - **단점**: 실제로 쓰지 않는 공간이 많이 남아 비효율적일 수 있다.
- **`VARCHAR(255)`**: 최대 255개까지 저장할 수 있지만, 실제로 5글자만 쓰면 나머지 공간은 반환한다. 대신 각 값의 길이가 제각각이니 **구분자**를 써서 다음 데이터가 시작하는 위치를 표시한다.
  - **장점**: 공간 낭비가 없다.
  - **단점**: 다음 데이터가 정확히 "어디"에 있는지 고정된 위치로 알 수 없다 — 구분자를 순서대로 읽어가야 한다.

**어떤 컬럼을 고정으로, 어떤 컬럼을 가변으로 할지**는 이 기준으로 정하면 된다 — **모든 데이터가 항상 같은 길이를 갖는 컬럼만 고정(CHAR)으로 하고, 나머지는 전부 가변(VARCHAR)으로 한다.** 예를 들어 전화번호·주소·전공·취미 중에서, 길이가 늘 일정한 건 전화번호 정도다. (한국 휴대전화 번호 기준 `CHAR(11)`처럼, **넉넉하게 잡아두는 것**이 중요하다.)

### 키(식별자) 선택 — int, bigint, uuid

키를 정할 때는 보통 **정수(INT/INTEGER)**로 하는 게 다루기 편하다. 다만 고민해야 할 지점이 있다 — **`INT`로 할까, `BIGINT`로 할까?**

`INT`가 표현할 수 있는 범위는 약 **21억**이다. "게시글이 21억 개까지 쌓일 수 있을까?"를 미리 따져봐야 한다 — 처음 설계할 때 **담으려는 데이터가 21억 개로 충분한지**를 반드시 고려해야 한다.

- 로컬(내부용)에서만 쓰는 게시판이라면 `INT`로도 충분하다.
- 21억을 넘길 가능성이 있다면 `BIGINT`로 범위를 넓힌다.

정수와는 다른 선택지로 **`UUID`**도 있다. 여러 시스템에 공개되어 서로 아이디가 충돌하면 안 되는 상황이라면 `UUID`를 식별자로 쓰는 것도 가능하다.

즉 정답이 하나로 정해진 게 아니라, **상황에 맞게 골라 쓰는 것**이 핵심이다. (참고로 사용자 정보를 나타내는 아이디는 크게 두 가지 성격이 중요한데, 그중 하나가 "사용자를 식별하기 위한 키가 별도로 필요하다"는 것이다.)

## 8. DML — CRUD 네 가지

데이터를 조작할 때 쓰는 명령은 **CRUD** 네 가지다.

| 구분 | 명령어 |
|---|---|
| Create | `INSERT` |
| Read | `SELECT` |
| Update | `UPDATE` |
| Delete | `DELETE` |

우리가 도구(SQL 클라이언트)를 써서 화면으로 데이터를 넣고 뺐던 것과 똑같은 일을, 결국 **우리가 직접 만드는 화면(UI)이 저장 요청을 받아 SQL로 전달하는 방식**으로 구현하게 된다. 이게 우리가 실제로 하게 될 일이다.

### INSERT

멤버가 속성을 10개 갖고 있다면, 기본적으로는 다 채워서 넣는다. 원하는 속성만 지정해서 넣는 것도 가능하다.

- 문자열은 반드시 **작은따옴표(`'`)**로 감싼다.
- 지정한 컬럼 목록과 값(`VALUES`) 목록의 **개수와 순서가 정확히 일치**해야 한다.
- 값을 넣지 않은 컬럼에는 **`NULL`**이 들어간다. `NULL`은 "값이 없다"는 뜻으로 이해하면 된다.

```sql
INSERT INTO menus(kor_name, eng_name, price)
VALUES('쿨초코', 'coolchoco', 6500);
```

`INSERT`는 이 정도가 거의 전부다.

### SELECT — 가장 복잡한 명령

- `*`는 모든 컬럼을 가져오라는 뜻이다.
- 조회 결과의 컬럼명을 원하는 별칭(alias)으로 바꿔서 받을 수 있다. 예를 들어 결과를 받는 쪽(다른 언어)에서 Entity 클래스에 담고 싶은데, 언어마다 표기법(camelCase vs snake_case)이 다르다면, 전달할 때 컬럼명을 원하는 표기법으로 바꿔서 내려줄 수 있다.

```sql
SELECT * FROM menus;
-- 모든 컬럼을 그대로 조회

SELECT kor_name, price FROM menus;
-- 원하는 컬럼만 골라서 조회

SELECT kor_name AS korName, price AS val FROM menus;
-- AS로 별칭을 붙여서 컬럼명을 바꿔 받음

SELECT kor_name korName, price val FROM menus;
-- AS는 생략 가능 (별칭 지정은 동일)
```

특정 레코드만 조회하고 싶을 때도 `WHERE`를 쓴다.

```sql
SELECT id, kor_name korName, price val FROM menus WHERE id = 2;
-- WHERE로 id가 2인 행만 지목해서 조회
```

### DELETE — 큰일 나는 실수 주의!!!

`WHERE` 절 없이 `DELETE`를 실행하면 **테이블의 모든 행이 삭제된다** — 특정 대상을 지목하지 않았기 때문이다.

```sql
DELETE FROM menus;  -- ⚠️ 조건 없이 쓰면 전체 삭제!
```

그래서 반드시 특정 레코드(행)를 정확히 지목하는 `WHERE` 절을 함께 써야 한다 — 보통 식별이 잘 되는 `id`를 기준으로 쓴다. 삭제 후에는 `SELECT`로 결과를 확인한다.

### UPDATE — 여기서도 WHERE 절 필수

`UPDATE`도 `WHERE` 절 없이 쓰면 **모든 행이 업데이트**된다. 반드시 `WHERE` 절로 수정할 행의 조건을 지정해야 한다.

```sql
UPDATE menus SET price = 65000 WHERE id = 13;
```

## 9. SELECT가 할 수 있는 일 — 필터링·집계·정렬, 그리고 JOIN

`SELECT`가 가진 기능은 한정되어 있다. 결국 **필터링하기, 집계하기, 정렬하기** — 이게 전부다. (참고로 자바 심화 과정에서 배우는 Data Stream API도 필터링·정렬·집계·매핑이 기본 골격이라, 개념적으로 통한다.)

여기에 더해, 데이터베이스만이 갖고 있는 **무결성** 문제 때문에 추가로 **JOIN**이라는 개념이 필요해진다 — 정규화로 여러 테이블에 나눠 담은 데이터를, 조회할 때 다시 엮어서 보여줘야 하기 때문이다.

CRUD를 다룰 줄 알게 되면, 이 내용을 바탕으로 실제 코딩을 할 수 있어야 한다.

## 10. SQL을 직접 쓰는 건 우리가 할 일이 아니다 — 우리는 클라이언트를 만든다

SQL을 사람이 직접 입력하는 건 사실 우리가 할 일이 아니다. **우리가 할 일은 UI를 만드는 것** — 우리는 SQL 클라이언트(도구)를 **이용하는** 쪽이 아니라, 그런 **클라이언트를 만드는** 쪽이다.

다만 Oracle이든 MySQL이든, 결국 데이터를 다루는 건 SQL이기 때문에 SQL을 쓸 줄은 알아야 한다. SQL 문장을 입력하고 전달하려면 명령어를 입력할 수 있는 **사용자 환경**이 있어야 한다 — CLI 기반 환경도 가능하고, 우리가 실습에서 썼던 것 같은 Windows용 GUI 도구(SQL을 작성해서 전달하는 도구)도 가능하다.

이런 도구가 하는 일은 결국 세 가지다.

1. **접속**(connection)
2. **문장 실행**(SQL 전달)
3. **결과를 화면에 표시하기**

여기서 중요한 구조적 사실 — **DBMS가 제공하는 "연결 방법"과 "SQL 실행·결과 조회 방법"은 서로 다른 영역이다.**

- **연결(connection)**은 SQL과 무관하게, DBMS마다 별도의 **네트워크 프로그램**으로 이뤄진다.
- SQL 문장 자체는 DBMS가 달라도 비슷한 형태를 갖지만, 그 SQL을 실제로 **실행하고 결과를 받아오는 API**는 DBMS마다 따로 제공해줘야 한다.
- 그래서 이 API가 다르면, 그 API를 사용하는 **클라이언트 도구도 DBMS마다 달라질 수밖에 없다.**
