# 제약조건 — 도메인·체크·엔티티·관계 제약과 JPA·스프링에서의 활용

## 학습 목표

이번에 학습하는 내용은 제약조건에 대한 개념적인 내용이다. 실습은 별도로 준비되어 있으므로, 이 자료에서는 제약조건이 무엇인지를 눈으로 읽고 머리로 이해하는 것을 목적으로 한다. 이 자료를 읽고 나면 다음과 같은 것을 할 수 있다.

- 제약조건(Constraints)의 개념과 데이터 무결성 보장에서의 역할을 이해한다.
- 제약조건을 **도메인, 체크, 엔티티, 관계**의 네 가지 범주로 분류하고 각 범주의 특징을 설명한다.

## 1. 제약조건(Constraints)이란?

이 섹션에서는 정규화된 스키마 위에 데이터 무결성을 강제하기 위한 제약조건(Constraints)의 개념과 네 가지 범주(도메인, 체크, 엔티티, 관계)를 학습한다.

정규화(1NF~BCNF)는 데이터 중복을 제거하고 이상(anomaly)을 방지하기 위해 테이블 구조를 최적화하는 과정이다. 그러나 정규화된 스키마는 데이터의 **'형태'**만 정의할 뿐, 데이터의 **'의미'**와 **'비즈니스 규칙'**을 강제하지는 않는다. 예를 들어 `salary` 열을 `NUMBER` 타입으로 정의했다고 해서 음수 급여가 막히지는 않는다. 숫자이기만 하면 `-500`도 들어간다.

제약조건은 스키마 구조 위에 실제 비즈니스 규칙을 강제하는 메커니즘이다. 이는 **데이터 무결성(Data Integrity)**을 보장하여, 잘못된 데이터가 저장되거나 참조 관계가 깨지는 것을 방지한다. 제약조건은 크게 네 가지 범주, 즉 **도메인, 체크, 엔티티, 관계** 제약조건으로 분류된다.

| 범주 | 무엇을 지키나 | 사용하는 제약 |
|---|---|---|
| 도메인 제약조건 | 한 컬럼이 가질 수 있는 값의 범위 | 데이터 타입, 길이, `NOT NULL`, `DEFAULT` |
| 체크 제약조건 | 타입만으로 못 거르는 값의 조건(비즈니스 규칙) | `CHECK` |
| 엔티티 제약조건 | 행(row)의 중복 방지와 식별 | `PRIMARY KEY`, `UNIQUE` |
| 관계 제약조건 | 테이블 간 참조 무결성 | `FOREIGN KEY` |

> **보충 — 분류 방식은 자료마다 다르다**: `CHECK`도 결국 "컬럼이 가질 수 있는 값의 범위"를 정하는 것이라서, 많은 교재는 체크를 도메인 제약에 포함해 **도메인 / 엔티티 / 참조(관계)** 세 가지로 나눈다. 이 세 가지는 각각 **도메인 무결성, 개체 무결성, 참조 무결성**에 대응한다. 이 자료는 체크를 따로 떼어 네 가지로 본다.

> **보충 — `DEFAULT`는 엄밀히는 제약이 아니다**: `DEFAULT`는 잘못된 값을 **막는** 규칙이 아니라 값을 **채워주는** 설정이라, 표준 SQL에서는 제약조건으로 분류하지 않는다. 다만 컬럼 정의에 함께 쓰이고 데이터 품질에 영향을 주므로 보통 같이 다룬다.

### 1-1. 애플리케이션에서 검사하면 되지 않나? — DB에 규칙을 거는 이유

애플리케이션 코드에서도 "이메일이 중복인지 확인", "가격이 0 이상인지 확인"을 할 수 있다. 그런데도 DB에 제약조건을 거는 이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| **입구가 여러 개다** | 데이터는 우리 서버만 넣는 게 아니다. 관리자가 SQL 도구로 직접 넣기도 하고, 배치 프로그램이나 다른 서비스가 넣기도 한다. 코드 검증은 그 코드를 거친 데이터만 지킨다. DB 제약은 **누가 넣든** 지킨다. |
| **동시 요청을 막을 수 있다** | 회원가입에서 `existsByEmail()`로 확인 후 `save()`하는 사이에, 같은 이메일로 다른 요청이 끼어들면 둘 다 "중복 없음"으로 통과할 수 있다. `UNIQUE` 제약은 이런 경쟁 상황에서도 두 번째 INSERT를 DB가 거부한다. |
| **마지막 방어선이다** | 코드는 바뀌고 실수도 생긴다. 제약은 스키마에 남아 있는 한 항상 동작한다. |
| **스키마 자체가 문서가 된다** | `CHECK (salary >= 0)`을 보면 "급여는 음수가 될 수 없다"는 업무 규칙을 테이블 정의만 보고 알 수 있다. |

> 트랜잭션의 ACID 중 **일관성(Consistency)**, 즉 "트랜잭션 전후 데이터가 업무 규칙에 맞는 유효한 상태"를 DB가 직접 지켜주는 장치가 바로 제약조건이다.

## 2. 도메인 제약조건 (Domain Constraints)

도메인 제약조건은 특정 열(column)이 가질 수 있는 **값의 범위**를 의미한다. 이는 데이터 타입(Data Type), 길이 제한, 기본값(Default), NULL 허용 여부 등을 조합한 값의 유효 범위를 말한다. 모든 데이터는 정의된 도메인 내에 있어야 한다.

**도메인(Domain)**이란 특정 데이터 항목이 가질 수 있는 값의 집합을 의미한다. 이는 데이터 타입(예: 정수, 문자열), 허용되는 값의 범위(예: 18세 이상), 그리고 특수한 값(예: NULL)을 포함한다. 도메인 제약조건은 데이터가 정의된 도메인 안에서만 유효하도록 보장하여, 의미상 불가능한 값(예: 음수 나이)이 저장되는 것을 방지한다.

도메인 제약은 자료형과 길이로 거는 것 외에, `NOT NULL`과 `DEFAULT`로도 설정할 수 있다.

### 2-1. NOT NULL 제약조건

`NOT NULL` 제약조건은 필수 항목이 누락되는 일이 없도록, 특정 컬럼에 NULL 값이 저장되는 것을 막아 해당 열이 반드시 유효한 값을 가져야 함을 강제한다.

기본적으로 관계형 데이터베이스의 열은 NULL을 허용한다. 그러나 비즈니스 규칙상 필수적인 정보(예: 고객의 이름, 주문의 날짜)는 NULL일 수 없으므로, 스키마 설계 시 명시적으로 `NOT NULL` 제약조건을 적용해야 한다. 이 제약조건은 도메인 제약조건의 일종으로 분류되며, 데이터 타입·길이 제한과 함께 열의 유효한 값의 범위를 정의하는 데 사용된다.

`NOT NULL`은 단독으로 적용할 수도 있고, **기본 키(`PRIMARY KEY`)에는 암묵적으로 포함**되어 있다. `PRIMARY KEY`로 지정된 열은 NULL을 허용하지 않으므로 별도의 `NOT NULL` 선언이 필요하지 않다. 일반 열은 데이터 무결성을 위해 명시적으로 선언하는 것이 권장된다.

> **원본 자료 바로잡기 — `UNIQUE`에는 `NOT NULL`이 포함되지 않는다**: 원본에는 NOT NULL이 "기본 키 또는 대체 키(UNIQUE) 제약조건과 함께 암묵적으로 포함될 수 있다"고 되어 있지만, 암묵적으로 포함되는 것은 **`PRIMARY KEY`뿐**이다. `UNIQUE` 컬럼은 NULL을 허용한다(4절 참고). 대체 키를 NULL 없이 쓰려면 `UNIQUE`와 `NOT NULL`을 **함께** 걸어야 한다.

이 제약조건이 위반되면 데이터베이스 엔진은 INSERT 또는 UPDATE 명령을 거부하고 오류를 반환한다. 이를 통해 애플리케이션에서 필수 필드를 검증하기 전에, 데이터베이스 수준에서 일관된 데이터 품질을 보장할 수 있다.

```sql
-- NOT NULL 제약조건 위반 예제
INSERT INTO employees (emp_id, first_name, hire_date)
VALUES (1, NULL, SYSDATE);
-- 오류: NOT NULL 제약조건 위반
```

위와 같이 이름을 입력하지 않을 때 오류가 발생하도록 하려면, 테이블을 생성할 때 다음과 같은 구문으로 `NOT NULL` 제약조건을 설정한다.

**ANSI SQL 문법**

```sql
CREATE TABLE table_name (
    column_name data_type [CONSTRAINT constraint_name] [NOT NULL] [DEFAULT value]
);
```

위 구문 규칙에 따라 Oracle에서 `first_name` 컬럼에 NOT NULL 제약을 설정하려면 자료형 뒤에 `NOT NULL`을 붙이기만 하면 된다.

**예제: Oracle**

```sql
CREATE TABLE employees (
    emp_id NUMBER(6),
    first_name VARCHAR2(20) NOT NULL,
    hire_date DATE DEFAULT SYSDATE
);
```

- `emp_id`: 최대 6자리 정수만 허용.
- `first_name`: 최대 20자, NULL 불가.
- `hire_date`: 입력하지 않으면 현재 날짜가 기본값으로 설정됨. (Oracle의 `DATE`와 `SYSDATE`는 시·분·초까지 포함한다.)

PostgreSQL에서도 NOT NULL 제약을 설정하는 구문은 동일하다.

**예제: PostgreSQL**

```sql
CREATE TABLE employees (
    emp_id INT,
    first_name VARCHAR(20) NOT NULL,
    hire_date DATE DEFAULT CURRENT_DATE
);
```

- `emp_id`: 정수 타입.
- `first_name`: 최대 20자, NULL 불가.
- `hire_date`: 입력하지 않으면 현재 날짜가 기본값으로 설정됨.

테이블을 생성할 때 외에, **이미 생성된 테이블**에도 제약조건을 설정할 수 있다. 그 방법은 `ALTER TABLE` 명령을 사용하는 것이다.

**예제: Oracle**

```sql
-- 기존 테이블에 NOT NULL 제약조건 추가
ALTER TABLE employees MODIFY first_name NOT NULL;

-- 기존 테이블에 CHECK 제약조건 추가
ALTER TABLE employees ADD CONSTRAINT chk_salary CHECK (salary >= 0);
```

**예제: PostgreSQL**

```sql
-- 기존 테이블에 NOT NULL 제약조건 추가
ALTER TABLE employees ALTER COLUMN first_name SET NOT NULL;

-- 기존 테이블에 CHECK 제약조건 추가
ALTER TABLE employees ADD CONSTRAINT chk_salary CHECK (salary >= 0);
```

> 이미 데이터가 있는 테이블에 제약을 추가하면, **기존 데이터가 그 규칙을 어기는 경우 추가 자체가 실패**한다. `first_name`이 NULL인 행이 하나라도 있으면 `NOT NULL`을 걸 수 없다. 먼저 데이터를 정리한 뒤 추가한다.

**VS Code에서 도구로 설정하기**: VS Code에 Database Client나 SQLTools 같은 확장을 설치했다면, 화면에서 테이블의 제약조건을 간단히 설정할 수 있다.

1. **데이터베이스 연결**: 좌측 사이드바의 Database 아이콘을 클릭하여 데이터베이스 서버에 연결한다.
2. **테이블 선택**: 연결된 데이터베이스 안의 대상 테이블을 선택한다.
3. **속성 편집**: 테이블을 우클릭하거나 속성(Properties) 탭을 열어 컬럼 목록을 확인한다.
4. **제약조건 적용**:
   - 특정 컬럼을 선택한 후, 속성 패널에서 **Nullable** 체크박스를 해제하여 NOT NULL 제약조건을 설정한다.
   - **Default Value** 필드에 값을 입력하여 DEFAULT 제약조건을 설정한다.
   - 테이블 수준의 CHECK, UNIQUE, FOREIGN KEY 제약조건은 테이블 속성 패널 또는 SQL 에디터에서 DDL을 직접 작성하여 적용한다.
5. **적용 및 확인**: 변경 사항을 저장(Commit)하면 데이터베이스에 해당 제약조건이 반영된다.

> **NULL과 빈 문자열은 다르다**: `NOT NULL`은 `NULL`만 막는다. 빈 문자열(`''`)이나 공백(`'   '`)은 통과한다. 이름이 비어 있으면 안 된다면 `CHECK (char_length(trim(first_name)) > 0)`을 함께 걸거나, 애플리케이션에서 `@NotBlank`로 검증한다. (Oracle은 예외적으로 빈 문자열을 NULL로 취급하므로 `NOT NULL`만으로 빈 문자열도 막힌다.)

> **보충 — 자바와 비교**: 자바 `int` 같은 기본형은 `null`이 될 수 없으므로, JPA는 기본형 필드를 매핑할 때 DDL에 `not null`을 붙인다. 반면 `@NotNull`(Bean Validation)은 **DB 제약이 아니라 애플리케이션에서 저장 전에 검사**하는 것이다. 둘은 다른 층의 검증이다(7-1절 참고).

### 2-2. DEFAULT 제약조건

`DEFAULT` 제약조건은 기본값을 대입해 주는 제약조건으로, 필수 컬럼 중에 **사용자가 입력할 수 없거나 입력해서는 안 되는** 경우에 사용한다.

예를 들어 조회수, 입력 시간, 수정 시간은 사용자가 직접 입력하게 할 수 없는 컬럼들이다. 시간을 정확히 입력할 수 없을 뿐만 아니라, 위조가 가능하기 때문이다.

기본값으로 설정하는 값은 데이터 타입과 호환되어야 하며, 상수 값을 설정할 수도 있고 함수(예: 현재 날짜, 현재 사용자)를 사용하여 설정할 수도 있다.

`DEFAULT` 제약조건은 `NOT NULL` 제약조건과 함께 사용될 때 특히 효과적이며, 필수 필드에 합리적인 기본값을 제공하여 데이터 무결성을 강화한다.

**DEFAULT 제약조건의 역할**

- **입력 간소화**: 사용자가 모든 필드를 입력하지 않아도 기본값이 자동 설정되어 입력 과정이 단순해진다.
- **데이터 일관성**: 값을 생략한 모든 행에 동일한 기본값이 적용되어 데이터의 일관성을 보장한다.
- **NULL 방지**: `NOT NULL`과 결합하여, 값을 생략했을 때 NULL 대신 기본값이 들어가게 한다.

DEFAULT 제약조건을 설정하는 ANSI SQL 구문은 다음과 같다.

**ANSI SQL 문법**

```sql
CREATE TABLE table_name (
    column_name data_type [DEFAULT value]
);
```

Oracle에서는 다음처럼 설정한다.

**예제: Oracle**

```sql
CREATE TABLE employees (
    emp_id NUMBER(6),
    first_name VARCHAR2(20) NOT NULL,
    hire_date DATE DEFAULT SYSDATE,
    department_id NUMBER(4) DEFAULT 10
);
```

- `hire_date`: 날짜를 입력하지 않으면 현재 날짜(`SYSDATE`)가 기본값으로 설정된다.
- `department_id`: 부서 ID를 입력하지 않으면 기본 부서(10)가 할당된다.

PostgreSQL에서는 다음처럼 설정한다.

**예제: PostgreSQL**

```sql
CREATE TABLE employees (
    emp_id INT,
    first_name VARCHAR(20) NOT NULL,
    hire_date DATE DEFAULT CURRENT_DATE,
    department_id INT DEFAULT 10
);
```

- `hire_date`: 날짜를 입력하지 않으면 현재 날짜(`CURRENT_DATE`)가 기본값으로 설정된다.
- `department_id`: 부서 ID를 입력하지 않으면 기본 부서(10)가 할당된다.

DEFAULT 제약조건은 테이블 생성 시 정의할 수 있으며, 이미 생성된 테이블에는 `ALTER TABLE` 명령으로 추가하거나 수정할 수 있다.

```sql
-- Oracle
ALTER TABLE employees MODIFY department_id DEFAULT 10;

-- PostgreSQL
ALTER TABLE employees ALTER COLUMN department_id SET DEFAULT 10;
```

> **원본 자료 바로잡기 — DEFAULT 추가 구문**: 원본의 `ALTER TABLE employees ADD CONSTRAINT df_dept DEFAULT 10 FOR department_id;`는 **SQL Server 전용** 문법이다. SQL Server는 DEFAULT를 이름 있는 제약으로 관리하지만, Oracle과 PostgreSQL에서는 이 구문이 오류가 난다. 위처럼 컬럼 정의를 변경하는 방식으로 쓴다.

**기본값은 "생략"했을 때만 들어간다**: `NULL`을 명시적으로 넣으면 기본값이 아니라 NULL이 저장된다(NOT NULL이면 오류). 기본값은 INSERT 문에서 그 컬럼 자체를 **빼거나** `DEFAULT` 키워드를 쓸 때만 적용된다.

```sql
INSERT INTO employees (emp_id, first_name) VALUES (1, '홍길동');                    -- department_id = 10
INSERT INTO employees (emp_id, first_name, department_id) VALUES (2, '김철수', DEFAULT); -- department_id = 10
INSERT INTO employees (emp_id, first_name, department_id) VALUES (3, '이영희', NULL);    -- department_id = NULL
```

> **JPA에서 특히 주의**: JPA(Hibernate)는 INSERT할 때 엔티티의 **모든 컬럼을 SQL에 포함**한다. 자바 필드가 `null`이면 `department_id = NULL`을 명시적으로 넣는 셈이라, **DB의 DEFAULT가 적용되지 않는다.** 그래서 JPA에서는 기본값을 자바 쪽에서 채우는 것이 일반적이다.
>
> ```java
> private Integer departmentId = 10;      // 필드 초기값
>
> @CreationTimestamp                      // Hibernate가 저장 시각을 채움
> private LocalDateTime createdAt;
> ```

## 3. 체크 제약조건 (Check Constraints)

체크 제약조건은 **비교 연산(조건식)**으로 값의 유효성을 검사하는 제약조건이다. 이 제약조건이 필요한 이유는 자료형, 값의 길이, 도메인 제약만으로는 잡아낼 수 없는 결함이 있기 때문이다.

예를 들어 성적 컬럼의 값이 100을 넘거나, 나이 컬럼의 값이 음수가 되거나, 전화번호 컬럼에 `'hello'`가 들어가는 것은 기존 제약으로는 막을 수 없다. 타입(숫자, 문자열)과 길이는 모두 맞기 때문이다.

CHECK 제약조건은 말 그대로 **조건을 검사**하는 제약조건이다. ANSI SQL 구문상의 문법은 다음과 같다.

**ANSI SQL 문법**

```sql
CREATE TABLE table_name (
    column1 data_type,
    column2 data_type,
    CONSTRAINT chk_name CHECK (condition)
);
```

Oracle에서 급여와 상여금의 범위를 검사해 입력 값을 제약하는 방법은 다음과 같다.

**예제: Oracle**

```sql
CREATE TABLE employees (
    emp_id NUMBER(6),
    salary NUMBER(10, 2),
    bonus NUMBER(10, 2),
    CONSTRAINT chk_salary_bonus CHECK (salary >= 0 AND bonus <= salary)
);
```

- 급여(`salary`)는 0 이상이어야 한다.
- 상여금(`bonus`)은 급여(`salary`)를 초과할 수 없다.

PostgreSQL에서 체크 제약조건을 설정하는 방법은 다음과 같다.

**예제: PostgreSQL**

```sql
CREATE TABLE employees (
    emp_id INT,
    salary NUMERIC(10, 2),
    bonus NUMERIC(10, 2),
    CONSTRAINT chk_salary_bonus CHECK (salary >= 0 AND bonus <= salary)
);
```

- Oracle과 동일한 조건을 적용한다.

위 예제처럼 CHECK는 한 컬럼뿐 아니라 **여러 컬럼을 비교**하는 조건도 테이블 단위로 걸 수 있다. 값 목록 중 하나만 허용할 때는 `IN`을 쓴다.

```sql
gender VARCHAR(1) CHECK (gender IN ('M', 'F')),     -- M 또는 F만
score  INT        CHECK (score BETWEEN 0 AND 100)   -- 0~100
```

> **주의 — CHECK는 NULL을 통과시킨다**: CHECK는 조건식이 **거짓(FALSE)**인 데이터만 거부한다. `salary >= 0`에 `salary = NULL`을 넣으면 결과는 거짓이 아니라 **UNKNOWN(모름)**이므로 **통과**한다. 위 예제에서 `bonus`가 NULL이어도 마찬가지다. NULL도 막으려면 `NOT NULL`을 함께 걸어야 한다.

> **주의 — MySQL 버전**: MySQL은 **8.0.16 미만**에서 CHECK 구문을 오류 없이 받아들이지만 **실제로 검사하지 않았다.** 오래된 MySQL을 쓰는 프로젝트라면 CHECK가 동작하는지 꼭 확인한다. Oracle과 PostgreSQL은 정상 동작한다.

**정규식으로 더 정밀하게**: DBMS마다 문법은 다르지만, 일반적으로 정규식을 이용해 체크 제약을 좀 더 정밀하게 걸 수 있다. 앞의 전화번호에 `'hello'`가 들어가는 문제도 이렇게 막는다.

```sql
-- PostgreSQL: ~ 연산자 (대소문자 무시는 ~*)
CONSTRAINT chk_phone CHECK (phone ~ '^01[016789]-\d{3,4}-\d{4}$')

-- Oracle: REGEXP_LIKE 함수
CONSTRAINT chk_phone CHECK (REGEXP_LIKE(phone, '^01[016789]-[0-9]{3,4}-[0-9]{4}$'))
```

> **보충 — 값 목록이 자주 바뀌면 CHECK 대신 테이블로**: `status IN ('ACTIVE', 'WITHDRAWN')`처럼 값 목록이 자주 바뀐다면, 상태 목록을 별도 테이블로 두고 FK로 참조하는 방식도 있다. 값이 거의 바뀌지 않으면 CHECK가 간단하다.

지금까지 다룬 `NOT NULL`, `DEFAULT`, `CHECK` 제약조건과 함께 자료형, 값의 길이가 올바르게 설정되면 **컬럼에 올바른 값만** 입력되도록 할 수 있다.

하지만 모든 컬럼이 올바른 값을 갖는다고 해서 데이터베이스에 결함이 없다고 할 수는 없다. 모든 컬럼이 각각 올바른 값을 가져도 **동일한 레코드가 중복해서 입력**되면, 그것은 도메인 차원이 아닌 **엔티티 차원의 결함**이 된다.

## 4. 엔티티 제약조건 (Entity Constraints)

엔티티 제약조건은 테이블 안에서 **행(row)의 중복이 발생하지 않게** 하는 제약조건이다. 중복을 허용하지 않는 키를 설정해서 행이 중복되지 않도록 한다.

엔티티 제약조건으로 설정하는 키는 **기본 키(`PRIMARY KEY`)**와 **`UNIQUE`** 제약조건이다.

**기본 키**는 테이블 안의 각 행을 유일하게 식별하는 키로,

- NULL 값을 허용하지 않고
- 중복을 방지하며
- 행을 식별하는 역할을 한다.

이는 테이블의 주 식별자로서, 행을 삭제·수정할 때 행을 선택하는 기준이 된다. 한 테이블에는 **1개의 PK**만 지정할 수 있다. 단, 여러 컬럼을 묶어 하나의 **복합 기본키**로 만드는 것은 가능하다.

반면 **`UNIQUE`** 제약조건도 특정 컬럼 또는 컬럼 조합의 값이 중복되지 않도록 보장하지만,

- 기본 키와 달리 컬럼 단위의 중복을 방지할 뿐이고,
- 중복만 발생하지 않는다면 NULL 값을 허용한다(단, DBMS에 따라 NULL 처리 방식이 다르다).

따라서 `UNIQUE` 제약조건은 **대체 키(Alternate Key)**로 사용되기도 하며, 기본 키 외에 다른 기준으로 행의 고유성을 확보할 때 활용된다. 이메일, 아이디, 사업자번호처럼 PK는 아니지만 겹치면 안 되는 값에 건다.

| | PRIMARY KEY | UNIQUE |
|---|---|---|
| 테이블당 개수 | 1개 | 여러 개 가능 |
| NULL 허용 | ❌ | ⭕ (기본) |
| 용도 | 행의 식별자 | 업무상 겹치면 안 되는 값(대체 키) |
| 인덱스 | 자동 생성 | 자동 생성 |

다음은 `PRIMARY KEY`와 `UNIQUE`를 설정하는 ANSI SQL 구문이다.

**ANSI SQL 문법**

```sql
CREATE TABLE table_name (
    column1 data_type,
    column2 data_type,
    CONSTRAINT pk_name PRIMARY KEY (column1),
    CONSTRAINT uq_name UNIQUE (column2)
);
```

Oracle에서 설정하는 방법은 다음과 같다.

**예제: Oracle**

```sql
CREATE TABLE employees (
    emp_id NUMBER(6),
    email VARCHAR2(50),
    CONSTRAINT pk_emp PRIMARY KEY (emp_id),
    CONSTRAINT uq_email UNIQUE (email)
);
```

- `emp_id`: 기본 키로 설정되어, NULL 불가이고 중복 불가이다.
- `email`: 대체 키로 설정되어, 중복 불가이지만 NULL은 허용될 수 있다.

다음은 PostgreSQL에서 설정하는 방법이다.

**예제: PostgreSQL**

```sql
CREATE TABLE employees (
    emp_id INT,
    email VARCHAR(50),
    CONSTRAINT pk_emp PRIMARY KEY (emp_id),
    CONSTRAINT uq_email UNIQUE (email)
);
```

- Oracle과 동일한 구조를 가진다. PostgreSQL에서 `PRIMARY KEY`는 암묵적으로 `NOT NULL`과 `UNIQUE` 제약조건을 포함한다.

VS Code를 이용한다면, 2-1절에서 본 것처럼 Database Client 같은 확장의 테이블 속성 화면에서 PK와 UNIQUE도 설정할 수 있다.

**복합 키**: 여러 컬럼의 **조합**이 겹치면 안 될 때는 컬럼 여러 개를 묶어 PK나 UNIQUE를 건다.

```sql
-- 한 회원은 한 메뉴에 좋아요를 한 번만
CONSTRAINT pk_likes PRIMARY KEY (member_id, menu_id)

-- 한 카테고리 안에서만 메뉴 이름이 겹치지 않으면 된다
CONSTRAINT uq_menus_category_name UNIQUE (category_id, kor_name)
```

**UNIQUE와 NULL**: 표준 SQL은 "NULL은 값이 아니라 '모름'이므로 NULL끼리는 같다고 볼 수 없다"고 본다. 그래서 대부분의 DBMS에서 UNIQUE 컬럼에 **NULL은 여러 개** 들어갈 수 있다.

| DBMS | UNIQUE 컬럼에 NULL 여러 개 |
|---|---|
| PostgreSQL | 허용 (15 버전부터 `UNIQUE NULLS NOT DISTINCT`로 막을 수 있음) |
| MySQL | 허용 |
| Oracle | 허용 (단일 컬럼 기준) |
| SQL Server | **1개만** 허용 |

> **보충 — 자연키 vs 대리키**: 이메일, 주민번호처럼 업무에서 원래 쓰는 값을 PK로 쓰는 것을 **자연키**, `emp_id`처럼 의미 없는 일련번호를 PK로 두는 것을 **대리키(인조키)**라고 한다. 자연키는 바뀔 수 있고(이메일 변경), 바뀌면 그걸 참조하는 모든 FK까지 바꿔야 한다. 그래서 보통은 **대리키를 PK로** 두고, 자연키에는 `UNIQUE`(+ `NOT NULL`)를 건다.

> **보충 — PK 인덱스는 DBMS마다 다르다**: "PK에는 클러스터드 인덱스가 생긴다"는 설명을 자주 보는데, **MySQL(InnoDB)과 SQL Server**에 해당하는 이야기다. 클러스터드 인덱스는 테이블 데이터 자체가 PK 순서로 정렬되어 저장되는 방식이다. **PostgreSQL**과 Oracle(기본 설정)은 데이터를 순서 없이 쌓고(heap), PK용 **일반 B-tree 인덱스를 따로** 만든다. 어느 쪽이든 PK로 찾는 조회가 빠르다는 점은 같다.

> **보충 — 조건부 UNIQUE**: "탈퇴하지 않은 회원끼리만 이메일이 겹치면 안 된다"처럼 일부 행에만 유일성을 걸고 싶을 때, PostgreSQL은 **부분 인덱스**를 쓴다.
>
> ```sql
> CREATE UNIQUE INDEX uq_members_email_active ON members (email) WHERE status <> 'WITHDRAWN';
> ```

이제 도메인 제약조건으로 모든 컬럼이 올바른 값을 가지도록 했고, 엔티티 제약조건으로 모든 행에서 중복이 발생하지 않도록 했다. 그렇다면 이제 데이터베이스는 결함이 없는 데이터만 가지게 된 것일까?

이 제약조건만으로는 **자식 테이블이 존재하지도 않는 부모를 가리키는** 결함을 여전히 막을 수 없다.

## 5. 관계 제약조건 (Relationship Constraints)

관계 제약조건은 테이블 간의 **참조 무결성(Referential Integrity)**을 보장한다. 한 테이블의 열(외래 키)이 다른 테이블의 기본 키 또는 대체 키를 참조할 때, **참조된 값이 실제로 존재해야** 한다. 또한 참조된 행이 삭제되거나 수정될 때의 동작(`ON DELETE`, `ON UPDATE`)을 정의할 수 있다.

이 제약조건은 참조키를 가지고 있는 **자식 테이블에 설정**한다. 참조키가 입력될 때 그 키를 가진 행이 정말 부모 테이블에 있는지를 검사하게 한다.

- 부모에 없는 값을 자식에 넣으려고 하면 오류가 난다. (없는 직원 번호로 주문을 넣는 경우)
- FK 컬럼에 **NULL은 허용**된다(따로 `NOT NULL`을 걸지 않았다면). NULL은 "아직 참조 대상이 없음"을 뜻한다. 반드시 부모가 있어야 한다면 `NOT NULL`을 함께 건다.

이 제약조건의 구문은 `FOREIGN KEY (column2) REFERENCES other_table(other_column)`처럼, 외래 키 컬럼은 무엇이고 그 키가 참조하는 부모 테이블의 이름과 컬럼은 무엇인지를 설정한다.

실제 ANSI SQL의 전체 구문은 다음과 같다.

**ANSI SQL 문법**

```sql
CREATE TABLE table_name (
    column1 data_type,
    column2 data_type,
    CONSTRAINT fk_name FOREIGN KEY (column2) REFERENCES other_table(other_column)
        ON DELETE [CASCADE | SET NULL | SET DEFAULT | RESTRICT | NO ACTION]
        ON UPDATE [CASCADE | SET NULL | SET DEFAULT | RESTRICT | NO ACTION]
);
```

관계 제약조건에 포함된 `ON DELETE`와 `ON UPDATE` 절은 부모 테이블의 데이터가 삭제되거나 수정될 때, 이를 참조하는 자식 테이블의 데이터를 어떻게 처리할지 결정한다.

| 옵션 | 부모가 삭제(수정)되면 | 사용 예 |
|---|---|---|
| `NO ACTION` | 자식이 있으면 **거부** (생략 시 기본값) | 대부분의 관계 |
| `RESTRICT` | 자식이 있으면 **즉시 거부** | NO ACTION과 거의 같음 |
| `CASCADE` | 자식도 **함께 삭제(수정)** | 게시글 삭제 시 댓글도 삭제 |
| `SET NULL` | 자식의 FK를 **NULL로** 변경 | 직원이 삭제되면 주문은 남기고 담당자만 비움 |
| `SET DEFAULT` | 자식의 FK를 **기본값으로** 변경 | 기본 부서로 옮기기 |

예를 들어 `ON DELETE SET NULL`로 설정하면 부모 테이블의 행이 삭제될 때 자식 테이블의 해당 외래 키 값은 NULL로 변경된다(그러려면 FK 컬럼이 NULL을 허용해야 한다). `ON UPDATE CASCADE`로 설정하면 부모 테이블의 키 값이 변경될 때 자식 테이블의 외래 키 값도 자동으로 함께 변경된다.

그리고 `NO ACTION`은 부모 테이블의 행이 삭제되거나 수정될 때, 이를 참조하는 자식 테이블의 행이 존재하면 해당 작업을 **거부**하는 동작이다. 즉, 자식 테이블에 아직 연결된 데이터가 남아 있으면 부모 테이블의 변경을 허용하지 않아 데이터 무결성을 유지한다.

> **원본 자료 바로잡기 — NO ACTION은 "즉시"가 아니다**: 원본은 NO ACTION이 작업을 "즉시 거부"한다고 했지만, **즉시** 검사하는 것은 `RESTRICT`다. 표준 SQL과 PostgreSQL에서 `NO ACTION`은 검사를 **문장이 끝날 때**까지(제약을 `DEFERRABLE`로 만들면 **트랜잭션 커밋 때**까지) 미룬다. 그래서 같은 트랜잭션 안에서 부모를 지운 뒤 자식을 다른 부모로 옮기는 작업이 NO ACTION에서는 가능하고 RESTRICT에서는 불가능하다. 결과적으로 "자식이 남아 있으면 거부"라는 점은 같다. MySQL(InnoDB)에서는 둘이 완전히 같다.

**예제: Oracle**

```sql
CREATE TABLE orders (
    order_id NUMBER(6),
    emp_id NUMBER(6),
    CONSTRAINT fk_orders_emp FOREIGN KEY (emp_id) REFERENCES employees(emp_id)
);
```

- `orders` 테이블의 `emp_id`는 `employees` 테이블의 `emp_id`에 존재해야 한다.
- `employees`에서 해당 직원을 삭제할 때 `orders`에 그 직원의 주문이 남아 있으면 삭제 실패(기본 동작: NO ACTION).

> **원본 자료 바로잡기 — Oracle의 참조 동작 지원 범위**: 원본에는 "Oracle은 ON DELETE/ON UPDATE 절을 직접 지원하지 않는다"고 되어 있지만, Oracle은 **`ON DELETE CASCADE`와 `ON DELETE SET NULL`을 지원**한다. 지원하지 않는 것은 **`ON UPDATE` 절 전체**와 `SET DEFAULT`, 그리고 `NO ACTION`/`RESTRICT` 키워드를 명시하는 것이다(생략하면 NO ACTION처럼 동작한다). 부모 키 변경을 자식에 전파해야 한다면 트리거나 애플리케이션에서 처리한다.
>
> ```sql
> -- Oracle에서 가능한 형태
> CONSTRAINT fk_orders_emp FOREIGN KEY (emp_id) REFERENCES employees(emp_id)
>     ON DELETE SET NULL
> ```

**예제: PostgreSQL**

```sql
CREATE TABLE orders (
    order_id INT,
    emp_id INT,
    CONSTRAINT fk_orders_emp FOREIGN KEY (emp_id) REFERENCES employees(emp_id)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);
```

- `ON DELETE SET NULL`: `employees`에서 직원이 삭제되면, `orders`의 `emp_id`는 NULL로 설정된다.
- `ON UPDATE CASCADE`: `employees`의 `emp_id`가 변경되면, `orders`의 `emp_id`도 자동으로 변경된다.

**어떤 옵션을 고를까** — 부모가 사라졌을 때 자식 데이터가 업무적으로 어떻게 되어야 하는지로 정한다.

| 상황 | 선택 |
|---|---|
| 자식이 남아 있으면 부모를 지우면 안 된다 | `NO ACTION`(기본값) / `RESTRICT` |
| 부모 없이는 자식이 의미가 없다(게시글과 댓글) | `CASCADE` |
| 자식은 남기되 연결만 끊는다(직원 퇴사 후에도 주문 기록 유지) | `SET NULL` |

> **CASCADE는 신중하게**: 회원 삭제 → 주문 삭제 → 주문 항목 삭제 → 결제 내역 삭제처럼 연쇄적으로 지워질 수 있다. 주문·결제처럼 **기록으로 남아야 하는 데이터**에는 CASCADE를 걸지 않고, 회원은 실제로 지우지 않고 `status = 'WITHDRAWN'`처럼 상태만 바꾸는 **논리 삭제(soft delete)**를 쓰는 경우가 많다.

> **보충 — FK 컬럼에는 인덱스를 직접 만든다(PostgreSQL, Oracle)**: PK와 UNIQUE에는 인덱스가 자동으로 생기지만, **PostgreSQL과 Oracle은 FK 컬럼에 인덱스를 자동으로 만들지 않는다**(MySQL은 만든다). FK 컬럼은 조인 조건(`orders.emp_id = employees.emp_id`)과 부모 삭제 시 자식 검사에 자주 쓰이므로 인덱스를 따로 만드는 것이 좋다.
>
> ```sql
> CREATE INDEX idx_orders_emp_id ON orders (emp_id);
> ```

## 6. 제약조건 이름 붙이기와 관리

### 6-1. 컬럼 단위 vs 테이블 단위 선언

앞의 예제들에서 `NOT NULL`은 컬럼 옆에, PK·UNIQUE·CHECK·FK는 `CONSTRAINT 이름 ...` 형태로 테이블 끝에 썼다. 두 방식의 차이는 다음과 같다.

```sql
CREATE TABLE employees (
    emp_id NUMBER(6) PRIMARY KEY,                -- 컬럼 단위: 간단하지만 이름은 DB가 자동 생성
    email VARCHAR2(50) NOT NULL,
    CONSTRAINT uq_emp_email UNIQUE (email)       -- 테이블 단위: 이름 지정, 여러 컬럼 가능
);
```

| | 컬럼 단위 | 테이블 단위 (`CONSTRAINT 이름 ...`) |
|---|---|---|
| 여러 컬럼 묶기 | 불가 | 가능(복합 PK·UNIQUE·FK, 여러 컬럼 비교 CHECK) |
| 이름 지정 | 보통 자동 이름 | 직접 지정 |
| NOT NULL | 컬럼 단위만 가능 | — |

### 6-2. 이름을 직접 붙이는 이유

이름을 지정하지 않으면 Oracle은 `SYS_C0012345`, PostgreSQL은 `employees_email_key`, Hibernate는 `UK6dotkott2kjsp8vw4d0m25fb7` 같은 이름을 만든다. 제약을 위반하면 **에러 메시지에 이 이름이 찍힌다.**

```
ERROR: duplicate key value violates unique constraint "uq_emp_email"
```

이름만 보고 "직원 이메일 중복"임을 바로 알 수 있다. 나중에 제약을 지우거나 바꿀 때도 이름이 필요하다. 팀에서 접두사 규칙을 정해두면 좋다.

| 접두사 | 제약 | 예 |
|---|---|---|
| `pk_` | PRIMARY KEY | `pk_emp` |
| `fk_` | FOREIGN KEY | `fk_orders_emp` (자식_부모) |
| `uq_` / `uk_` | UNIQUE | `uq_email` |
| `chk_` / `ck_` | CHECK | `chk_salary_bonus` |

### 6-3. 제약 삭제와 확인

```sql
-- 삭제 (Oracle, PostgreSQL 공통)
ALTER TABLE employees DROP CONSTRAINT uq_emp_email;

-- NOT NULL 해제
ALTER TABLE employees MODIFY first_name NULL;                -- Oracle
ALTER TABLE employees ALTER COLUMN first_name DROP NOT NULL; -- PostgreSQL
```

```sql
-- 걸려 있는 제약 확인 (PostgreSQL)
SELECT conname, contype, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'employees'::regclass;
-- contype: p=PK, f=FK, u=UNIQUE, c=CHECK  (psql에서는 \d employees)

-- 걸려 있는 제약 확인 (Oracle)
SELECT constraint_name, constraint_type, search_condition
FROM user_constraints
WHERE table_name = 'EMPLOYEES';
-- constraint_type: P=PK, R=FK, U=UNIQUE, C=CHECK(NOT NULL 포함)
```

## 7. JPA(ORM) 관점에서의 제약조건 설정

스프링/JPA 환경에서는 엔티티 클래스에 어노테이션을 붙여, DDL 자동 생성(`spring.jpa.hibernate.ddl-auto`가 `create`, `update` 등) 시 제약조건을 반영할 수 있다.

```java
@Entity
@Table(name = "members", uniqueConstraints = {
    @UniqueConstraint(name = "uq_members_email", columnNames = "email")   // UNIQUE (이름 지정)
})
@Check(name = "chk_members_point", constraints = "point >= 0")           // CHECK (Hibernate 전용)
public class Member {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;                                     // PRIMARY KEY

    @Column(nullable = false, length = 50)
    private String name;                                 // NOT NULL, VARCHAR(50)

    @Column(nullable = false)
    private String email;                                // NOT NULL (+ 위의 uniqueConstraints)

    @Column(nullable = false)
    private Integer point = 0;                           // 기본값은 자바에서

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "team_id", nullable = false,
                foreignKey = @ForeignKey(name = "fk_members_team"))
    private Team team;                                   // FOREIGN KEY (NOT NULL)
}
```

| 범주 | DB 제약 | JPA 설정 |
|---|---|---|
| 도메인 | NOT NULL | `@Column(nullable = false)`, `@JoinColumn(nullable = false)` |
| 도메인 | DEFAULT | Hibernate의 `@ColumnDefault("'ACTIVE'")` — DDL에만 반영됨. 실제 값은 자바 필드 초기값으로 채우는 것이 안전 |
| 체크 | CHECK | Hibernate의 `@Check` (JPA 표준 어노테이션은 버전에 따라 다름) |
| 엔티티 | PRIMARY KEY | `@Id` (복합키는 `@EmbeddedId` / `@IdClass`) |
| 엔티티 | UNIQUE | `@Column(unique = true)` 또는 `@Table(uniqueConstraints = ...)` (이름 지정·복합 UNIQUE는 후자) |
| 관계 | FOREIGN KEY | `@ManyToOne` + `@JoinColumn(foreignKey = @ForeignKey(name = ...))` |

> **보충 — `@Column(unique = true)`보다 `uniqueConstraints`**: `@Column(unique = true)`는 간단하지만 제약 이름을 지정할 수 없어 `UK6dotk...` 같은 이름이 생긴다. 이름을 붙이거나 여러 컬럼을 묶으려면 `@Table(uniqueConstraints = ...)`를 쓴다.

> **보충 — 어노테이션은 DDL을 만들 때만 의미가 있다**: `nullable = false`, `unique = true` 같은 설정은 Hibernate가 **테이블을 생성할 때** 제약을 만드는 데 쓰인다. `ddl-auto: none`이나 `validate`로 운영하면서 테이블을 직접 SQL(또는 Flyway 같은 마이그레이션 도구)로 관리한다면, 어노테이션과 실제 DB 제약이 **따로 놀 수 있다.** 실무에서는 운영 DB의 스키마를 SQL로 관리하고, 어노테이션은 그 스키마를 문서화하는 용도로 맞춰두는 경우가 많다. 또 `ddl-auto: update`는 컬럼은 추가해도 **이미 있는 컬럼에 제약을 새로 추가하거나 바꾸지는 않는 경우가 많다.**

### 7-1. DB 제약과 Bean Validation은 다른 층이다

| | DB 제약 | Bean Validation (`@NotNull`, `@NotBlank`, `@Size`, `@Email`, `@Min`...) |
|---|---|---|
| 검사 위치 | DB 엔진 | 애플리케이션 (컨트롤러 `@Valid`, 엔티티 저장 직전 등) |
| 검사 시점 | SQL 실행 시 | 요청이 들어올 때 / 저장 전 |
| 실패 결과 | DB 에러 → 스프링 예외 | 검증 예외 → 보통 400 응답 |
| 사용자 메시지 | 만들기 어렵다 | 필드별로 친절한 메시지를 줄 수 있다 |
| 우회 가능성 | 없음 | 다른 경로로 들어온 데이터는 못 막는다 |

**둘 다 쓴다.** 사용자 입력은 Bean Validation으로 먼저 걸러 친절한 오류 메시지를 주고, DB 제약은 그걸 통과한 데이터와 다른 경로로 들어온 데이터까지 막는 **마지막 방어선**으로 둔다.

```java
public record SignupRequest(
    @NotBlank @Size(max = 50) String name,       // 화면에 "이름을 입력하세요"를 띄울 수 있다
    @NotBlank @Email String email
) {}
```

## 8. 제약 위반이 일어나면 — 에러 코드와 스프링 예외, 트랜잭션

제약을 어기면 DB는 SQL을 거부하고 에러를 돌려준다.

| 위반 | 범주 | PostgreSQL SQLSTATE | Oracle 에러 |
|---|---|---|---|
| NOT NULL 위반 | 도메인 | `23502` | `ORA-01400` |
| CHECK 위반 | 체크 | `23514` | `ORA-02290` |
| UNIQUE / PK 중복 | 엔티티 | `23505` | `ORA-00001` |
| FK 위반 (부모 없음) | 관계 | `23503` | `ORA-02291` |
| FK 위반 (자식 있는 부모 삭제) | 관계 | `23503` | `ORA-02292` |

PostgreSQL에서 `23`으로 시작하는 코드는 모두 **무결성 제약 위반**(integrity constraint violation) 분류다.

**스프링에서는**: 스프링은 DBMS마다 다른 에러를 공통 예외로 바꿔준다. 제약 위반은 대부분 **`DataIntegrityViolationException`**(중복 키는 그 하위 `DuplicateKeyException`)으로 올라온다. 이 예외는 **런타임 예외**라서, `@Transactional` 메서드 안에서 발생하면 **트랜잭션 전체가 롤백**된다.

```java
@Transactional
public void pay(Long memberId, int amount) {
    memberRepository.decreasePoint(memberId, amount);   // point가 마이너스가 되면 CHECK 위반 → 예외
    orderRepository.save(new Order(memberId));          // 실행되지 않음
}   // 예외 발생 → 앞서 실행한 작업까지 전부 롤백
```

**전역 예외 처리로 응답 바꾸기**: 이 예외를 그대로 두면 500 에러가 된다. `@RestControllerAdvice`에서 받아 사용자에게 맞는 응답으로 바꾼다.

```java
@ExceptionHandler(DataIntegrityViolationException.class)
public ResponseEntity<ErrorResponse> handleIntegrity(DataIntegrityViolationException e) {
    return ResponseEntity.status(HttpStatus.CONFLICT)                // 409
            .body(new ErrorResponse("DATA_CONFLICT", "이미 존재하거나 허용되지 않는 값입니다."));
}
```

> 어떤 제약이 깨졌는지 구분해서 메시지를 주고 싶다면, 예외 메시지에 포함된 **제약 이름**(`uq_members_email` 등)을 보고 분기할 수 있다. 제약 이름을 직접 지어두면 이럴 때 유용하다.

> **JPA에서 에러가 늦게 보이는 이유**: JPA는 `save()` 시점에 바로 SQL을 보내지 않고 **flush 시점**(보통 트랜잭션 커밋 직전)에 보낼 수 있다. 그래서 제약 위반 예외가 `save()` 줄이 아니라 메서드가 끝날 때 터지는 것처럼 보일 수 있다. (`IDENTITY` 전략의 INSERT는 `save()` 즉시 실행되므로 바로 보인다.)

## 9. 종합 예시 — 네 가지 범주를 한 스키마에

```sql
-- PostgreSQL
CREATE TABLE departments (
    dept_id   INT GENERATED BY DEFAULT AS IDENTITY,
    dept_name VARCHAR(50) NOT NULL,                                   -- 도메인
    CONSTRAINT pk_departments PRIMARY KEY (dept_id),                  -- 엔티티
    CONSTRAINT uq_departments_name UNIQUE (dept_name)                 -- 엔티티
);

CREATE TABLE employees (
    emp_id        INT GENERATED BY DEFAULT AS IDENTITY,
    first_name    VARCHAR(20)    NOT NULL,                            -- 도메인
    email         VARCHAR(50)    NOT NULL,                            -- 도메인
    phone         VARCHAR(13),
    salary        NUMERIC(10, 2) NOT NULL,                            -- 도메인
    bonus         NUMERIC(10, 2) NOT NULL DEFAULT 0,                  -- 도메인
    hire_date     DATE           NOT NULL DEFAULT CURRENT_DATE,       -- 도메인
    department_id INT,
    CONSTRAINT pk_emp PRIMARY KEY (emp_id),                           -- 엔티티
    CONSTRAINT uq_emp_email UNIQUE (email),                           -- 엔티티
    CONSTRAINT chk_salary_bonus CHECK (salary >= 0 AND bonus <= salary),       -- 체크
    CONSTRAINT chk_emp_phone CHECK (phone ~ '^01[016789]-\d{3,4}-\d{4}$'),     -- 체크
    CONSTRAINT fk_emp_dept FOREIGN KEY (department_id)
        REFERENCES departments(dept_id) ON DELETE SET NULL            -- 관계
);
CREATE INDEX idx_emp_department_id ON employees (department_id);

CREATE TABLE orders (
    order_id INT GENERATED BY DEFAULT AS IDENTITY,
    emp_id   INT NOT NULL,
    CONSTRAINT pk_orders PRIMARY KEY (order_id),                      -- 엔티티
    CONSTRAINT fk_orders_emp FOREIGN KEY (emp_id)
        REFERENCES employees(emp_id)                                  -- 관계 (NO ACTION)
);
CREATE INDEX idx_orders_emp_id ON orders (emp_id);
```

| 테이블 | 제약이 지키는 업무 규칙 |
|---|---|
| `departments` | 부서 이름은 필수이고 겹칠 수 없다 |
| `employees` | 이름·이메일·급여는 필수 / 이메일은 한 명만 쓸 수 있다 / 급여는 0 이상, 상여금은 급여 이하 / 전화번호는 휴대폰 형식만 / 입사일을 안 넣으면 오늘 / 부서가 없어지면 소속만 비워진다 |
| `orders` | 주문에는 반드시 실제 직원이 있어야 하고, 주문이 남은 직원은 삭제할 수 없다 |

## 10. 마무리

스키마 설계에서 네 가지 제약조건 범주는 상호보완적으로 작동한다.

- **도메인 제약조건**은 개별 데이터 값의 형식과 범위를 정의한다.
- **체크 제약조건**은 데이터 값 간의 복잡한 비즈니스 규칙을 강제한다.
- **엔티티 제약조건**은 테이블 내 행의 고유성과 식별성을 보장한다.
- **관계 제약조건**은 테이블 간의 참조 무결성을 유지하여 데이터의 일관성을 확보한다.

이 네 가지가 결합되어 데이터베이스의 무결성을 완성하며, 정규화된 구조 위에 의미 있는 데이터가 저장되도록 보장한다.

**한 줄 정리**

- 제약조건은 **잘못된 데이터를 DB가 직접 거부**하게 만드는 규칙이다. 누가 어떤 경로로 넣든 지켜진다.
- 도메인(**타입·길이·NOT NULL·DEFAULT**) → 체크(**CHECK**) → 엔티티(**PK·UNIQUE**) → 관계(**FK**) 순으로 "값 → 행 → 테이블 간" 결함을 막는다.
- NULL은 특별 취급된다: UNIQUE는 NULL 여러 개를 허용하고, CHECK는 NULL을 통과시키고, DEFAULT는 NULL을 명시하면 적용되지 않는다.
- 제약에는 **이름을 붙인다.** 에러 메시지와 유지보수가 쉬워진다.
- 애플리케이션 검증(Bean Validation)과 DB 제약은 **둘 다** 쓴다. DB 제약은 마지막 방어선이다.
- 제약 위반은 스프링에서 `DataIntegrityViolationException`(런타임 예외)이 되어 `@Transactional` 작업을 **롤백**시킨다.
