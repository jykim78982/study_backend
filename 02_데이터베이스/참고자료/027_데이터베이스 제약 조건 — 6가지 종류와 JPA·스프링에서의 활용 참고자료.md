# 데이터베이스 제약 조건 — 6가지 종류와 JPA·스프링에서의 활용

데이터베이스에서 **제약 조건(Constraint)**은 "데이터의 **무결성(Integrity)**과 정확성을 보장하기 위해 테이블의 컬럼이나 테이블 전체에 강제하는 규칙"이다. 잘못되거나 오염된 데이터(중복된 이메일, 존재하지 않는 회원의 주문, 비어 있으면 안 되는 값 등)가 DB에 들어오는 것을 **DB 엔진 차원에서 원천 차단**한다.

## 0. 왜 DB에 규칙을 거는가

애플리케이션 코드에서도 "이메일이 중복인지 확인", "가격이 0 이상인지 확인"을 할 수 있다. 그런데도 DB에 제약 조건을 거는 이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| **입구가 여러 개다** | 데이터는 우리 서버만 넣는 게 아니다. 관리자가 SQL 도구로 직접 넣기도 하고, 배치 프로그램이나 다른 서비스가 넣기도 한다. 코드 검증은 그 코드를 거친 데이터만 지킨다. DB 제약은 **누가 넣든** 지킨다. |
| **동시 요청을 막을 수 있다** | 회원가입에서 `existsByEmail()`로 확인 후 `save()`하는 사이에, 같은 이메일로 다른 요청이 끼어들면 둘 다 "중복 없음"으로 통과할 수 있다. `UNIQUE` 제약은 이런 경쟁 상황에서도 두 번째 INSERT를 DB가 거부한다. |
| **마지막 방어선이다** | 코드는 바뀌고 실수도 생긴다. 제약은 스키마에 남아 있는 한 항상 동작한다. |
| **데이터 자체가 문서가 된다** | `CHECK (price >= 0)`을 보면 "가격은 음수가 될 수 없다"는 업무 규칙을 테이블 정의만 보고 알 수 있다. |

> 트랜잭션의 ACID 중 **일관성(Consistency)**, 즉 "트랜잭션 전후 데이터가 업무 규칙에 맞는 유효한 상태"를 DB가 직접 지켜주는 장치가 바로 제약 조건이다.

**무결성의 종류**: 제약 조건이 지키는 무결성은 보통 세 가지로 나눈다.

| 무결성 | 뜻 | 지키는 제약 |
|---|---|---|
| 개체 무결성 | 모든 행은 식별 가능해야 한다(식별자가 비거나 중복되면 안 된다) | `PRIMARY KEY` |
| 참조 무결성 | 참조하는 값은 실제로 존재하는 대상을 가리켜야 한다 | `FOREIGN KEY` |
| 도메인 무결성 | 컬럼 값은 정해진 형식·범위 안에 있어야 한다 | 데이터 타입, `NOT NULL`, `CHECK`, `DEFAULT`, `UNIQUE` |

## 1. 주요 제약 조건 6가지 한눈에 보기

| 제약 조건 | 키워드 | 핵심 역할 및 특징 |
|---|---|---|
| `PRIMARY KEY` | 기본키 (PK) | 테이블의 각 행을 유일하게 식별하는 컬럼. **UNIQUE + NOT NULL** 성격을 가진다. 테이블당 1개만 지정 가능 |
| `FOREIGN KEY` | 외래키 (FK) | 다른 테이블의 PK(또는 UNIQUE 컬럼)를 참조해 테이블 간 관계를 형성하고 참조 무결성을 보장 |
| `NOT NULL` | 필수값 | 해당 컬럼에 NULL 입력을 허용하지 않음 |
| `UNIQUE` | 중복 불가 | 컬럼 내 모든 값이 서로 달라야 함. NULL은 여러 개 허용되는 것이 일반적(DBMS마다 차이) |
| `CHECK` | 값 범주 제한 | 조건식을 지정해 그 조건을 만족하는 값만 허용 |
| `DEFAULT` | 기본값 지정 | INSERT 시 컬럼을 **생략**하면 지정한 기본값을 자동 입력 |

> 엄밀히 말하면 `DEFAULT`는 잘못된 값을 **막는** 규칙이 아니라 값을 **채워주는** 설정이라, 표준 SQL에서는 제약 조건으로 분류하지 않는다. 다만 컬럼 정의에 함께 쓰이고 데이터 품질에 영향을 주므로 보통 같이 다룬다.

## 2. PRIMARY KEY (기본키, PK)

행(엔티티)을 식별하기 위한 가장 핵심적인 식별자 제약 조건이다.

**특징**:

- 테이블 안에서 데이터의 유일성을 보장한다.
- NULL 값을 가질 수 없고, 중복된 값도 허용하지 않는다.
- 한 테이블에는 오직 **1개의 PK**만 지정할 수 있다. 단, 여러 컬럼을 묶어 하나의 **복합 기본키**로 만드는 것은 가능하다.
- DBMS는 PK에 **인덱스를 자동으로 만들어** 식별자로 찾는 조회를 빠르게 한다.

```sql
-- 단일 PK (컬럼 옆에 쓰는 방식)
CREATE TABLE members (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(255)
);

-- 복합 PK (테이블 끝에 쓰는 방식 — 여러 컬럼은 이렇게만 가능)
CREATE TABLE likes (
    member_id BIGINT,
    menu_id   BIGINT,
    created_at TIMESTAMP,
    CONSTRAINT pk_likes PRIMARY KEY (member_id, menu_id)
);
```

> **보충 — PK 인덱스는 DBMS마다 다르다**: "PK에는 클러스터드 인덱스가 생긴다"는 설명을 자주 보는데, **MySQL(InnoDB)과 SQL Server**에 해당하는 이야기다. 클러스터드 인덱스는 테이블 데이터 자체가 PK 순서로 정렬되어 저장되는 방식이다. **PostgreSQL**과 Oracle(기본 설정)은 데이터를 순서 없이 쌓고(heap), PK용 **일반 B-tree 인덱스를 따로** 만든다. 어느 쪽이든 PK로 찾는 조회가 빠르다는 점은 같다.

> **보충 — 자연키 vs 대리키**: 이메일, 주민번호처럼 업무에서 원래 쓰는 값을 PK로 쓰는 것을 **자연키**, `id`처럼 의미 없는 일련번호를 PK로 두는 것을 **대리키(인조키)**라고 한다. 자연키는 바뀔 수 있고(이메일 변경), 바뀌면 그걸 참조하는 모든 FK까지 바꿔야 한다. 그래서 보통은 **대리키를 PK로** 두고, 자연키에는 `UNIQUE`를 건다.

## 3. FOREIGN KEY (외래키, FK)

두 테이블 사이의 **참조 무결성**(Referential Integrity)을 유지하기 위해 사용한다.

**특징**:

- 자식 테이블의 FK 컬럼 값은 반드시 **부모 테이블의 PK(또는 UNIQUE) 컬럼에 존재하는 값**이어야 한다.
- 부모에 없는 값을 자식에 넣으려고 하면 DB 오류가 난다. (주문에 없는 회원 번호를 넣는 경우)
- FK 컬럼에 **NULL은 허용**된다(따로 `NOT NULL`을 걸지 않았다면). NULL은 "아직 참조 대상이 없음"을 뜻한다. 반드시 부모가 있어야 한다면 `NOT NULL`을 함께 건다.
- 부모 데이터가 **삭제되거나 수정될 때** 자식 데이터를 어떻게 할지 옵션으로 정할 수 있다.

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    member_id BIGINT NOT NULL,
    -- member_id는 members 테이블의 id(PK)를 참조한다
    CONSTRAINT fk_orders_member FOREIGN KEY (member_id)
        REFERENCES members(id) ON DELETE CASCADE
);
```

**참조 동작 옵션** (`ON DELETE` / `ON UPDATE` 뒤에 쓴다)

| 옵션 | 부모가 삭제(수정)되면 | 사용 예 |
|---|---|---|
| `NO ACTION` | 자식이 있으면 **거부** (생략 시 기본값) | 대부분의 관계 |
| `RESTRICT` | 자식이 있으면 **즉시 거부** | NO ACTION과 거의 같음 |
| `CASCADE` | 자식도 **함께 삭제(수정)** | 게시글 삭제 시 댓글도 삭제 |
| `SET NULL` | 자식의 FK를 **NULL로** 변경 | 카테고리 삭제 시 메뉴는 남기고 "미분류"로 |
| `SET DEFAULT` | 자식의 FK를 **기본값으로** 변경 | 기본 카테고리로 옮기기 |

> **원본 자료 바로잡기 — 기본값은 NO ACTION**: 옵션을 생략했을 때의 기본값은 표준 SQL과 PostgreSQL, MySQL 모두 `NO ACTION`이다. `RESTRICT`와 결과는 거의 같지만, PostgreSQL에서 `NO ACTION`은 검사를 **문장 끝(또는 지연 설정 시 트랜잭션 끝)까지 미룰 수 있고** `RESTRICT`는 즉시 검사한다는 차이가 있다. MySQL(InnoDB)에서는 둘이 완전히 같다.

> **CASCADE는 신중하게**: 회원 삭제 → 주문 삭제 → 주문 항목 삭제 → 결제 내역 삭제처럼 연쇄적으로 지워질 수 있다. 주문·결제처럼 **기록으로 남아야 하는 데이터**에는 CASCADE를 걸지 않고, 회원은 실제로 지우지 않고 `status = 'WITHDRAWN'`처럼 상태만 바꾸는 **논리 삭제(soft delete)**를 쓰는 경우가 많다.

> **보충 — FK 컬럼에는 인덱스를 직접 만든다(PostgreSQL)**: PK와 UNIQUE에는 인덱스가 자동으로 생기지만, **PostgreSQL은 FK 컬럼에 인덱스를 자동으로 만들지 않는다**(MySQL은 만든다). FK 컬럼은 조인 조건(`orders.member_id = members.id`)과 부모 삭제 시 자식 검사에 자주 쓰이므로 인덱스를 따로 만드는 것이 좋다.
>
> ```sql
> CREATE INDEX idx_orders_member_id ON orders (member_id);
> ```

## 4. NOT NULL

컬럼에 값이 **반드시 있어야** 함을 강제하는 필수 항목 제약 조건이다.

**특징**:

- 값을 명시하지 않거나(그리고 DEFAULT도 없거나) `NULL`을 넣으려고 하면 작업이 거부된다.
- 다른 제약과 달리 **컬럼 단위로만** 쓴다(테이블 끝에 따로 쓰지 않는다).

```sql
CREATE TABLE members (
    id BIGINT PRIMARY KEY,
    name VARCHAR(50) NOT NULL   -- 이름은 빈 값 허용 불가
);
```

> **NULL과 빈 문자열은 다르다**: `NOT NULL`은 `NULL`만 막는다. 빈 문자열(`''`)이나 공백(`'   '`)은 통과한다. 이름이 비어 있으면 안 된다면 `CHECK (char_length(trim(name)) > 0)`을 함께 걸거나, 애플리케이션에서 `@NotBlank`로 검증한다. (Oracle은 예외적으로 빈 문자열을 NULL로 취급한다.)

> **보충 — 자바와 비교**: 원본 자료는 NOT NULL을 "자바의 기본형(Primitive type)이나 `@NotNull`"에 비유한다. 자바 `int`는 `null`이 될 수 없으므로, JPA는 기본형 필드를 매핑할 때 DDL에 `not null`을 붙인다. 반면 `@NotNull`(Bean Validation)은 **DB 제약이 아니라 애플리케이션에서 저장 전에 검사**하는 것이다. 둘은 다른 층의 검증이다(7절 참고).

## 5. UNIQUE (유일성 제약 조건)

중복된 데이터 입력을 막을 때 사용한다. 이메일, 아이디, 사업자번호처럼 PK는 아니지만 겹치면 안 되는 값에 건다.

**PK와의 차이점**:

| | PRIMARY KEY | UNIQUE |
|---|---|---|
| 테이블당 개수 | 1개 | 여러 개 가능 |
| NULL 허용 | ❌ | ⭕ (기본) |
| 용도 | 행의 식별자 | 업무상 겹치면 안 되는 값 |
| 인덱스 | 자동 생성 | 자동 생성 |

```sql
CREATE TABLE members (
    id BIGINT PRIMARY KEY,
    email VARCHAR(255) UNIQUE,                 -- 이메일 중복 가입 불가
    nickname VARCHAR(30),
    CONSTRAINT uk_members_nickname UNIQUE (nickname)
);

-- 복합 UNIQUE: 조합이 겹치면 안 된다
-- 한 카테고리 안에서만 메뉴 이름이 겹치지 않으면 된다
CREATE TABLE menus (
    id BIGINT PRIMARY KEY,
    category_id BIGINT,
    kor_name VARCHAR(100),
    CONSTRAINT uk_menus_category_name UNIQUE (category_id, kor_name)
);
```

**UNIQUE와 NULL**: 표준 SQL은 "NULL은 값이 아니라 '모름'이므로 NULL끼리는 같다고 볼 수 없다"고 본다. 그래서 대부분의 DBMS에서 UNIQUE 컬럼에 **NULL은 여러 개** 들어갈 수 있다.

| DBMS | UNIQUE 컬럼에 NULL 여러 개 |
|---|---|
| PostgreSQL | 허용 (15 버전부터 `UNIQUE NULLS NOT DISTINCT`로 막을 수 있음) |
| MySQL | 허용 |
| Oracle | 허용 (단일 컬럼 기준) |
| SQL Server | **1개만** 허용 |

> **보충 — 조건부 UNIQUE**: "탈퇴하지 않은 회원끼리만 이메일이 겹치면 안 된다"처럼 일부 행에만 유일성을 걸고 싶을 때, PostgreSQL은 **부분 인덱스**를 쓴다.
>
> ```sql
> CREATE UNIQUE INDEX uk_members_email_active ON members (email) WHERE status <> 'WITHDRAWN';
> ```

## 6. CHECK

컬럼에 들어올 값의 **범위나 논리적 조건식**을 지정한다.

**특징**:

- 조건식이 **거짓(FALSE)**이 되는 데이터만 거부한다.
- 도메인 유효성 검증(나이는 0 이상, 상태는 정해진 값 중 하나 등)에 유용하다.
- 한 컬럼뿐 아니라 **여러 컬럼을 비교**하는 조건도 테이블 단위로 걸 수 있다.

```sql
CREATE TABLE members (
    id BIGINT PRIMARY KEY,
    age INT CHECK (age >= 0),                          -- 나이는 0 이상
    gender VARCHAR(1) CHECK (gender IN ('M', 'F')),    -- M 또는 F만
    point INT NOT NULL DEFAULT 0,
    CONSTRAINT ck_members_point CHECK (point >= 0)     -- 포인트는 마이너스 불가
);

-- 여러 컬럼 비교: 할인가는 정가보다 클 수 없다
CREATE TABLE menus (
    id BIGINT PRIMARY KEY,
    price INT NOT NULL,
    sale_price INT,
    CONSTRAINT ck_menus_sale_price CHECK (sale_price IS NULL OR sale_price <= price)
);
```

> **주의 — CHECK는 NULL을 통과시킨다**: `age >= 0`에 `age = NULL`을 넣으면 결과는 거짓이 아니라 **UNKNOWN(모름)**이다. CHECK는 FALSE만 막으므로 **NULL은 통과**한다. NULL도 막으려면 `NOT NULL`을 함께 걸어야 한다.

> **주의 — MySQL 버전**: MySQL은 **8.0.16 미만**에서 CHECK 구문을 오류 없이 받아들이지만 **실제로 검사하지 않았다.** 오래된 MySQL을 쓰는 프로젝트라면 CHECK가 동작하는지 꼭 확인한다. PostgreSQL은 예전부터 정상 동작한다.

> **보충 — 상태값은 CHECK 대신 별도 테이블로 하기도 한다**: `status IN ('ACTIVE', 'WITHDRAWN')`처럼 값 목록이 자주 바뀐다면, 상태 목록을 별도 테이블로 두고 FK로 참조하는 방식도 있다. 값이 거의 바뀌지 않으면 CHECK가 간단하다.

## 7. DEFAULT (기본값)

INSERT할 때 특정 컬럼을 **생략**하면 자동으로 들어갈 기본값을 지정한다.

**특징**:

- 컬럼을 명시하지 않았을 때 NULL 대신 지정한 기본값이 들어간다.
- 등록일시, 상태값, 카운트 초기화 등에 주로 쓰인다.

```sql
CREATE TABLE members (
    id BIGINT PRIMARY KEY,
    status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',          -- 기본 상태값 ACTIVE
    point INT NOT NULL DEFAULT 0,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP -- 현재 시간 자동 입력
);

INSERT INTO members (id) VALUES (1);                  -- status='ACTIVE', point=0, created_at=지금
INSERT INTO members (id, status) VALUES (2, NULL);    -- ❌ NULL을 직접 넣었으므로 기본값이 아니라 NULL → NOT NULL 위반
```

> **원본 자료 바로잡기 — 기본값은 "생략"했을 때만 들어간다**: 원본에는 "값이 입력되지 않으면(NULL 또는 생략) 기본값을 입력한다"고 되어 있지만, **`NULL`을 명시적으로 넣으면 기본값이 아니라 NULL이 저장된다.** 기본값은 INSERT 문에서 그 컬럼 자체를 **빼거나** `DEFAULT` 키워드를 쓸 때만 적용된다.

> **JPA에서 특히 주의**: JPA(Hibernate)는 INSERT할 때 엔티티의 **모든 컬럼을 SQL에 포함**한다. 자바 필드가 `null`이면 `status = NULL`을 명시적으로 넣는 셈이라, **DB의 DEFAULT가 적용되지 않는다.** 그래서 JPA에서는 기본값을 자바 쪽에서 채우는 것이 일반적이다.
>
> ```java
> private String status = "ACTIVE";       // 필드 초기값
> private Integer point = 0;
>
> @CreationTimestamp                      // Hibernate가 저장 시각을 채움
> private LocalDateTime createdAt;
> ```

## 8. 제약 조건 이름 붙이기와 관리

### 8-1. 컬럼 단위 vs 테이블 단위 선언

```sql
CREATE TABLE members (
    id BIGINT PRIMARY KEY,                    -- 컬럼 단위: 간단하지만 이름은 DB가 자동 생성
    email VARCHAR(255) NOT NULL,
    CONSTRAINT uk_members_email UNIQUE (email) -- 테이블 단위: 이름 지정, 여러 컬럼 가능
);
```

| | 컬럼 단위 | 테이블 단위 (`CONSTRAINT 이름 ...`) |
|---|---|---|
| 여러 컬럼 묶기 | 불가 | 가능(복합 PK·UNIQUE·FK) |
| 이름 지정 | 보통 자동 이름 | 직접 지정 |
| NOT NULL | 컬럼 단위만 가능 | — |

### 8-2. 이름을 직접 붙이는 이유

이름을 지정하지 않으면 DBMS가 `members_email_key`, Hibernate가 `UK6dotkott2kjsp8vw4d0m25fb7` 같은 이름을 만든다. 제약을 위반하면 **에러 메시지에 이 이름이 찍힌다.**

```
ERROR: duplicate key value violates unique constraint "uk_members_email"
```

이름만 보고 "회원 이메일 중복"임을 바로 알 수 있다. 또 나중에 제약을 지우거나 바꿀 때도 이름이 필요하다. 팀에서 접두사 규칙을 정해두면 좋다.

| 접두사 | 제약 | 예 |
|---|---|---|
| `pk_` | PRIMARY KEY | `pk_likes` |
| `fk_` | FOREIGN KEY | `fk_orders_member` (자식_부모) |
| `uk_` | UNIQUE | `uk_members_email` |
| `ck_` | CHECK | `ck_members_point` |

### 8-3. 이미 만든 테이블에 추가·삭제하기

```sql
-- 추가
ALTER TABLE members ADD CONSTRAINT uk_members_email UNIQUE (email);
ALTER TABLE members ADD CONSTRAINT ck_members_point CHECK (point >= 0);
ALTER TABLE orders  ADD CONSTRAINT fk_orders_member FOREIGN KEY (member_id) REFERENCES members(id);
ALTER TABLE members ALTER COLUMN name SET NOT NULL;         -- NOT NULL은 컬럼 변경으로 (PostgreSQL)
ALTER TABLE members ALTER COLUMN status SET DEFAULT 'ACTIVE';

-- 삭제
ALTER TABLE members DROP CONSTRAINT uk_members_email;
ALTER TABLE members ALTER COLUMN name DROP NOT NULL;
```

> 이미 데이터가 있는 테이블에 제약을 추가하면, **기존 데이터가 그 규칙을 어기는 경우 추가 자체가 실패**한다(이미 중복 이메일이 있으면 UNIQUE를 걸 수 없다). 먼저 데이터를 정리한 뒤 추가한다.

### 8-4. 걸려 있는 제약 확인하기 (PostgreSQL)

```sql
-- psql에서 테이블 구조와 제약·인덱스 보기
\d members

-- SQL로 조회
SELECT conname, contype, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'members'::regclass;
-- contype: p=PK, f=FK, u=UNIQUE, c=CHECK
```

## 9. JPA(ORM) 관점에서의 제약 조건 설정

스프링/JPA 환경에서는 엔티티 클래스에 어노테이션을 붙여, DDL 자동 생성(`spring.jpa.hibernate.ddl-auto`가 `create`, `update` 등) 시 제약 조건을 반영할 수 있다.

```java
@Entity
@Table(name = "members", uniqueConstraints = {
    @UniqueConstraint(name = "uk_members_email", columnNames = "email")   // UNIQUE (이름 지정)
})
@Check(name = "ck_members_point", constraints = "point >= 0")             // CHECK (Hibernate 전용)
public class Member {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;                                     // PRIMARY KEY

    @Column(nullable = false, length = 50)
    private String name;                                 // NOT NULL, VARCHAR(50)

    @Column(nullable = false)
    private String email;                                // NOT NULL (+ 위의 uniqueConstraints)

    @Column(nullable = false)
    private Integer point = 0;                           // 기본값은 자바에서

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "team_id", nullable = false,
                foreignKey = @ForeignKey(name = "fk_members_team"))
    private Team team;                                   // FOREIGN KEY (NOT NULL)
}
```

| DB 제약 | JPA 설정 |
|---|---|
| PRIMARY KEY | `@Id` (복합키는 `@EmbeddedId` / `@IdClass`) |
| FOREIGN KEY | `@ManyToOne` + `@JoinColumn(foreignKey = @ForeignKey(name = ...))` |
| NOT NULL | `@Column(nullable = false)`, `@JoinColumn(nullable = false)` |
| UNIQUE | `@Column(unique = true)` 또는 `@Table(uniqueConstraints = ...)` (이름 지정·복합 UNIQUE는 후자) |
| CHECK | Hibernate의 `@Check` (JPA 표준 어노테이션은 버전에 따라 다름) |
| DEFAULT | Hibernate의 `@ColumnDefault("'ACTIVE'")` — DDL에만 반영됨. 실제 값은 자바 필드 초기값으로 채우는 것이 안전 |

> **보충 — `@Column(unique = true)`보다 `uniqueConstraints`**: `@Column(unique = true)`는 간단하지만 제약 이름을 지정할 수 없어 `UK6dotk...` 같은 이름이 생긴다. 이름을 붙이거나 여러 컬럼을 묶으려면 `@Table(uniqueConstraints = ...)`를 쓴다.

> **보충 — 어노테이션은 DDL을 만들 때만 의미가 있다**: `nullable = false`, `unique = true` 같은 설정은 Hibernate가 **테이블을 생성할 때** 제약을 만드는 데 쓰인다. `ddl-auto: none`이나 `validate`로 운영하면서 테이블을 직접 SQL(또는 Flyway 같은 마이그레이션 도구)로 관리한다면, 어노테이션과 실제 DB 제약이 **따로 놀 수 있다.** 실무에서는 운영 DB의 스키마를 SQL로 관리하고, 어노테이션은 그 스키마를 문서화하는 용도로 맞춰두는 경우가 많다. 또 `ddl-auto: update`는 컬럼은 추가해도 **이미 있는 컬럼에 제약을 새로 추가하거나 바꾸지는 않는 경우가 많다.**

### 9-1. DB 제약과 Bean Validation은 다른 층이다

| | DB 제약 | Bean Validation (`@NotNull`, `@NotBlank`, `@Size`, `@Email`, `@Min`...) |
|---|---|---|
| 검사 위치 | DB 엔진 | 애플리케이션 (컨트롤러 `@Valid`, 엔티티 저장 직전 등) |
| 검사 시점 | SQL 실행 시 | 요청이 들어올 때 / 저장 전 |
| 실패 결과 | DB 에러 → 스프링 예외 | 검증 예외 → 보통 400 응답 |
| 사용자 메시지 | 만들기 어렵다 | 필드별로 친절한 메시지를 줄 수 있다 |
| 우회 가능성 | 없음 | 다른 경로로 들어온 데이터는 못 막는다 |

**둘 다 쓴다.** 사용자 입력은 Bean Validation으로 먼저 걸러 친절한 오류 메시지를 주고, DB 제약은 그걸 통과한 데이터와 다른 경로로 들어온 데이터까지 막는 **마지막 방어선**으로 둔다.

```java
public record SignupRequest(
    @NotBlank @Size(max = 50) String name,       // 화면에 "이름을 입력하세요"를 띄울 수 있다
    @NotBlank @Email String email
) {}
```

## 10. 제약 위반이 일어나면 — 에러 코드와 스프링 예외, 트랜잭션

제약을 어기면 DB는 SQL을 거부하고 에러를 돌려준다. PostgreSQL은 에러 종류마다 **SQLSTATE 코드**를 붙인다.

| 위반 | SQLSTATE | PostgreSQL 메시지 예 |
|---|---|---|
| UNIQUE / PK 중복 | `23505` | duplicate key value violates unique constraint "uk_members_email" |
| FK 위반 | `23503` | insert or update on table "orders" violates foreign key constraint "fk_orders_member" |
| NOT NULL 위반 | `23502` | null value in column "name" of relation "members" violates not-null constraint |
| CHECK 위반 | `23514` | new row for relation "members" violates check constraint "ck_members_point" |

`23`으로 시작하는 코드는 모두 **무결성 제약 위반**(integrity constraint violation) 분류다.

**스프링에서는**: 스프링은 DBMS마다 다른 에러를 공통 예외로 바꿔준다. 제약 위반은 대부분 **`DataIntegrityViolationException`**(중복 키는 그 하위 `DuplicateKeyException`)으로 올라온다. 이 예외는 **런타임 예외**라서, `@Transactional` 메서드 안에서 발생하면 **트랜잭션 전체가 롤백**된다.

```java
@Transactional
public void pay(Long memberId, int amount) {
    memberRepository.decreasePoint(memberId, amount);   // point가 마이너스가 되면 CHECK 위반 → 예외
    orderRepository.save(new Order(memberId));          // 실행되지 않음
}   // 예외 발생 → 앞서 실행한 작업까지 전부 롤백
```

**전역 예외 처리로 응답 바꾸기**: 이 예외를 그대로 두면 500 에러가 된다. `@RestControllerAdvice`에서 받아 사용자에게 맞는 응답으로 바꾼다.

```java
@ExceptionHandler(DataIntegrityViolationException.class)
public ResponseEntity<ErrorResponse> handleIntegrity(DataIntegrityViolationException e) {
    return ResponseEntity.status(HttpStatus.CONFLICT)                // 409
            .body(new ErrorResponse("DATA_CONFLICT", "이미 존재하거나 허용되지 않는 값입니다."));
}
```

> 어떤 제약이 깨졌는지 구분해서 메시지를 주고 싶다면, 예외 메시지에 포함된 **제약 이름**(`uk_members_email` 등)을 보고 분기할 수 있다. 제약 이름을 직접 지어두면 이럴 때 유용하다.

> **JPA에서 에러가 늦게 보이는 이유**: JPA는 `save()` 시점에 바로 SQL을 보내지 않고 **flush 시점**(보통 트랜잭션 커밋 직전)에 보낼 수 있다. 그래서 제약 위반 예외가 `save()` 줄이 아니라 메서드가 끝날 때 터지는 것처럼 보일 수 있다. (`IDENTITY` 전략의 INSERT는 `save()` 즉시 실행되므로 바로 보인다.)

## 11. 종합 예시 — 카페 앱 스키마에 제약 걸기

```sql
CREATE TABLE members (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY,
    email      VARCHAR(255) NOT NULL,
    name       VARCHAR(50)  NOT NULL,
    point      INT          NOT NULL DEFAULT 0,
    status     VARCHAR(20)  NOT NULL DEFAULT 'ACTIVE',
    created_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_members PRIMARY KEY (id),
    CONSTRAINT uk_members_email UNIQUE (email),
    CONSTRAINT ck_members_point CHECK (point >= 0),
    CONSTRAINT ck_members_status CHECK (status IN ('ACTIVE', 'WITHDRAWN'))
);

CREATE TABLE categories (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY,
    name       VARCHAR(50) NOT NULL,
    sort_order INT         NOT NULL DEFAULT 0,
    CONSTRAINT pk_categories PRIMARY KEY (id),
    CONSTRAINT uk_categories_name UNIQUE (name)
);

CREATE TABLE menus (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY,
    category_id BIGINT,
    kor_name    VARCHAR(100) NOT NULL,
    eng_name    VARCHAR(100),
    price       INT          NOT NULL,
    CONSTRAINT pk_menus PRIMARY KEY (id),
    CONSTRAINT fk_menus_category FOREIGN KEY (category_id)
        REFERENCES categories(id) ON DELETE SET NULL,      -- 카테고리 삭제 시 메뉴는 미분류로
    CONSTRAINT uk_menus_category_name UNIQUE (category_id, kor_name),
    CONSTRAINT ck_menus_price CHECK (price >= 0)
);
CREATE INDEX idx_menus_category_id ON menus (category_id);

CREATE TABLE likes (
    member_id  BIGINT    NOT NULL,
    menu_id    BIGINT    NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_likes PRIMARY KEY (member_id, menu_id),  -- 한 회원은 한 메뉴에 한 번만
    CONSTRAINT fk_likes_member FOREIGN KEY (member_id) REFERENCES members(id) ON DELETE CASCADE,
    CONSTRAINT fk_likes_menu   FOREIGN KEY (menu_id)   REFERENCES menus(id)   ON DELETE CASCADE
);
CREATE INDEX idx_likes_menu_id ON likes (menu_id);
```

| 테이블 | 제약이 지키는 업무 규칙 |
|---|---|
| `members` | 이메일은 한 명만 쓸 수 있다 / 포인트는 마이너스가 될 수 없다 / 상태는 두 가지뿐이다 |
| `categories` | 같은 이름의 카테고리는 하나뿐이다 |
| `menus` | 가격은 0 이상 / 한 카테고리 안에서 메뉴 이름은 겹치지 않는다 / 카테고리가 지워지면 메뉴는 남고 미분류가 된다 |
| `likes` | 같은 회원이 같은 메뉴에 좋아요를 두 번 누를 수 없다 / 회원이나 메뉴가 지워지면 좋아요도 지워진다 |

> `likes`의 PK가 `(member_id, menu_id)`라서 `member_id`로 시작하는 조회는 PK 인덱스를 쓸 수 있다. 하지만 `menu_id`만으로 찾는 조회(메뉴별 좋아요 수)는 그 인덱스를 잘 못 쓰므로 `idx_likes_menu_id`를 따로 만들었다. 복합 인덱스는 **앞쪽 컬럼부터** 활용된다.

## 12. 한 줄 정리

- 제약 조건은 **잘못된 데이터를 DB가 직접 거부**하게 만드는 규칙이다. 누가 어떤 경로로 넣든 지켜진다.
- **PK**(식별), **FK**(참조), **NOT NULL**(필수), **UNIQUE**(중복 금지), **CHECK**(조건), **DEFAULT**(생략 시 기본값).
- NULL은 특별 취급된다: UNIQUE는 NULL 여러 개를 허용하고, CHECK는 NULL을 통과시키고, DEFAULT는 NULL을 명시하면 적용되지 않는다.
- 제약에는 **이름을 붙인다.** 에러 메시지와 유지보수가 쉬워진다.
- 애플리케이션 검증(Bean Validation)과 DB 제약은 **둘 다** 쓴다. DB 제약은 마지막 방어선이다.
- 제약 위반은 스프링에서 `DataIntegrityViolationException`(런타임 예외)이 되어 `@Transactional` 작업을 **롤백**시킨다.
