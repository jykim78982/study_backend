# SQL 필터링·집계·정렬·매핑과 GET 파라미터 처리

## 1. 필터링은 자바가 아니라 SQL이 해야 한다

`if`문으로 걸러내는 건 **데이터베이스가 가진 필터링 기능을 안 쓰고 내가 직접 필터링하겠다**는 것과 같다. 1억 명 회원 중 성이 "김"씨인 회원이 5명이라면, 그 5명을 뽑기 위해 **1억 번을 비교**해야 한다는 뜻이다.

- 데이터를 조작하고 집계하는 기능은 **SQL로** 처리한다. 데이터베이스를 쓰는 이상 자바로는 절대 하지 않는다.
- **자바는 사용자와의 관계(입출력)만 담당한다.** 데이터 관리에서 자바가 맡는 건 껍데기뿐이고, 업무 로직은 SQL이 담당한다.

## 2. SQL 처리 순서 — 필터링 → 집계 → 정렬 → 매핑

한 번에 여러 기능을 동시에 처리할 수는 없으므로, 연산하기 적합한 **순서**가 정해져 있다.

**필터링 → 집계 → 정렬 → 매핑**

- **필터링**: `WHERE` — 비교 연산으로 원하는 행만 골라낸다.
- **집계**: `GROUP BY` — 집계하고 싶은 컬럼을 지정해 그룹으로 묶는다.
- **정렬**: `ORDER BY` — 결과를 정렬한다. 넷 중 제일 쉽다.
- **매핑**: `SELECT` — 원하는 내용으로 변환하거나 원하는 속성만 추려내는 **마지막** 작업. SQL을 배운 사람일수록 `SELECT`가 제일 먼저 나온다고 착각하는 함정에 빠지기 쉽다.

`SELECT ... FROM menus`의 `FROM` 절은 **소스를 만드는 곳**이다(여기서 `JOIN`, `UNION` 등을 추가로 배우게 된다). 추가로 `LIMIT`, `OFFSET`으로 개수·시작 위치를 지정할 수 있다.

**문법상의 작성 순서와 실제 실행 순서는 다르다.**

```
작성 순서: SELECT FROM WHERE GROUP BY ORDER BY
실행 순서: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
```

이 "필터→집계→정렬→매핑" 흐름은 SQL만의 것이 아니라 자바를 포함해 여기저기서 반복되는 패턴이다.

## 3. HTTP GET 요청과 옵션(파라미터)

웹 클라이언트가 웹 서버에게 요청할 수 있는 기능을 **메서드**라고 한다. 순수 HTML만으로 요청할 수 있는 건 **GET과 POST**뿐이고, 나머지 메서드는 JS 등 별도 코드가 있어야 요청할 수 있다.

- URL 뒤에 `?`를 붙이고 보낼 값(param)을 전달할 수 있다. 예를 들어 "아메리카노 아이스로 주세요"라면, **아메리카노**는 GET 요청 대상이고 **아이스·얼음 많이·샷 추가**는 옵션이다.
- 옵션은 **제공자(개발자)가 구현해둬야 하고, 사용자는 그 옵션이 있다는 걸 알아야** 요청할 수 있다.
- 서버에서 입력값은 `req`(`resp`가 아니라)를 통해서만 받을 수 있다. `req.getParameter(...)`로 가져온다.

**주의할 점**: 사용자 입력이 겉으로 숫자처럼 보여도, `req.getParameter`가 돌려주는 값은 **항상 문자열**이다. 숫자로 쓰려면 직접 변환해야 한다.

## 4. 옵션값을 그냥 `int`로 변환하면 안 되는 이유

옵션은 사용자마다 다르게 전달될 수 있다 — 옵션 없이 주문할 수도, 옵션 하나만 넣을 수도, 여러 개를 넣을 수도 있다. 즉 **옵션이 아예 오지 않을 가능성을 항상 염두에 둬야 한다.**

값이 안 왔을 때를 대비해 흔히 쓰는 패턴은 이렇다.

1. 기본값을 먼저 설정해둔다.
2. 파라미터가 정상적으로 왔을 때만 그 값으로 변환한다.

이 패턴을 메뉴 목록의 `price` 옵션(예: "가격이 얼마짜리만 보여줘")에 적용하면, 실제로 `price` 파라미터에 담길 수 있는 값은 세 가지 중 하나다.

- 숫자로 된 문자열
- 빈 문자열
- `null`(파라미터 자체가 없음)

산술 연산을 하려면 결국 정수형으로 다뤄야 한다. 그런데 "전체 가격대"(=필터 없음)를 표현해야 하는 경우가 문제다.

- **기본 자료형(`int`)에는 `null`을 담을 수 없다.** 기본값이 `0`인데, `0`을 그대로 쓰면 "0원짜리만 보여줘"라는 뜻이 되어버려서 "없음"과 완전히 다른 의미가 된다.
- 그래서 **사용자 입력값처럼 "없을 수도 있는" 값을 다룰 때는 기본 자료형을 쓰면 안 된다.**
- `null`을 담을 수 있는 정수형은 **`Integer`(래퍼 클래스)**다. `Integer`로 받아야만 "값이 없다"는 상태를 그대로 표현할 수 있다.

```java
String priceParam = req.getParameter("price");
Integer price = null;
if (priceParam != null && !priceParam.equals("")) {
    price = Integer.parseInt(priceParam);
}
```

- 받은 값이 빈 문자열이 아닌 경우에만 파싱해서 담는다.
- **문자열을 비교할 때 `!=`를 쓰면 안 된다** — 이건 객체(주소)를 비교하는 연산자다. 값 비교는 반드시 `.equals(...)`로 한다.

이렇게 만든 `price` 값을 리포지토리에 전달하는 방법은 두 가지가 있을 수 있다.

1. 기존 `findAll()`에 인자를 추가한다.
2. `findAllByPrice(Integer price)`처럼 **별도 함수를 새로 만든다.**

## 5. `WHERE` 절 — 비교·논리·NULL 연산

`WHERE`는 자바의 `if`문과 같다고 생각하면 된다.

- **NULL 비교**: `=`로는 비교할 수 없다. `서술 = NULL`은 항상 참이 아닌 것으로 처리된다 — 반드시 `IS NULL` / `IS NOT NULL`을 써야 한다.
- **논리 연산**: `AND`, `OR`을 그대로 쓸 수 있다.
- **여러 값 중 하나(OR의 반복 대체)**: `price = 1500 OR price = 2500 OR price = 5000`처럼 `OR`을 여러 번 쓰는 대신 `IN`을 쓴다.
- **범위 비교**: 1500원부터 5000원까지처럼 순차적인 범위라면 `BETWEEN ... AND ...`를 쓴다.

```sql
SELECT * FROM menus
WHERE price = 1500 OR price = 2500 OR price = 5000;

SELECT * FROM menus
WHERE price BETWEEN 1500 AND 5000;

SELECT * FROM menus
WHERE price IN (1500, 2500, 5000);
```

- **배제(반대)할 때**는 `NOT`을 많이 쓴다 — `NOT IN`으로 반대 결과를 얻을 수 있다.
- **불리언 값 비교**: `IS NULL`처럼, 불리언 값은 `IS TRUE` / `IS FALSE`로 비교한다(다른 DBMS는 `=`로 비교하기도 하지만, PostgreSQL은 이 방식을 쓴다).

## 6. 패턴 연산 — `LIKE`

전체 이름을 다 입력하지 않고 "아메"처럼 **일부 키워드로 검색**하고 싶을 때 쓰는 게 패턴 연산자 `LIKE`다.

- 정확히 일치하는 값을 찾을 때는 `=`를 쓴다.
- **`%`는 "아무 문자나 몇 글자든 올 수 있다"**는 뜻이다. `LIKE`를 쓸 때만 `%`가 이런 의미로 해석된다.

```sql
SELECT * FROM menus
WHERE kor_name LIKE '%아%';
```

- `'%아%'`는 "아"가 앞이든 가운데든 뒤든 어디에 있어도 찾는다 — "마끼아또"처럼 "아"가 가운데 있는 것도 결과에 포함된다.
- **글자 수까지 제한하고 싶다면 `_`(언더바)**를 쓴다. `_`는 정확히 한 글자를 의미한다.

```sql
SELECT * FROM menus
WHERE kor_name LIKE '아__';
```

- `'아%'`는 "아"로 시작하기만 하면 길이 제한이 없어서 "아메리"도 "아메리카노"도 다 걸린다.
- `'아__'`는 "아"로 시작하는 정확히 세 글자만 찾는다.

기타 참고사항:

- **`ILIKE`**: `LIKE`의 대소문자 구분 안 하는 버전. 한글 비교에는 의미가 없다.
- **`~`(similar to)**: PostgreSQL 전용이라 특별히 쓸 일이 없다.
- **정규표현식**: SQL이 아니라 별도의 언어로, 이 자체만으로 책 한 권(1300페이지) 분량이다. 특정 플랫폼 전용이 아니라 여러 언어(JS 등)에서 공통으로 쓰이는 표현식이라, 나중에 JS를 다룰 때 함께 배우게 된다.

## 7. SARGable Query — 인덱스를 타는 쿼리 작성법

**SARGable**은 **S**earch **ARG**ument**able**의 줄임말로, "인덱스 검색 인자(조건)로 쓸 수 있는 쿼리"라는 뜻이다. 즉 인덱스를 제대로 타고 빠르게 검색할 수 있는 `WHERE` 조건의 형태를 말한다.

**비유 — 가나다순으로 정리된 도서관 색인**

- **SARGable(인덱스 잘 타는 쿼리)**: "성씨가 '김'으로 시작하는 작가의 책"을 찾는 경우. 색인에서 'ㄱ' 파트로 바로 이동해 '김' 부분만 찾으면 된다.
- **Non-SARGable(인덱스 못 타는 쿼리)**: "이름의 두 번째 글자가 '민'인 작가의 책"을 찾는 경우. 색인이 가나다순이어도 두 번째 글자는 정렬 기준이 아니므로, 책 1만 권을 처음부터 끝까지 다 들춰봐야 한다(전체 탐색/Full Scan).

인덱스를 만들어 둬도 **컬럼 자체를 가공하거나 함수로 감싸면** 그 인덱스를 전혀 못 쓴다. 대표적인 세 가지 실수와 개선법:

1. **컬럼에 연산을 적용한 경우**
   - 안 좋은 예: `WHERE salary * 12 = 36000000` — 모든 행의 `salary`에 12를 일일이 곱해봐야 비교할 수 있다.
   - 개선: `WHERE salary = 36000000 / 12` — 컬럼은 그대로 두고 조건값 쪽을 연산하면 인덱스를 탈 수 있다.
2. **컬럼을 함수로 감싼 경우**
   - 안 좋은 예: `WHERE SUBSTRING(name, 1, 1) = '김'` — 모든 이름에서 첫 글자를 잘라내는 함수를 매번 실행해야 한다.
   - 개선: `WHERE name LIKE '김%'` — 앞글자가 '김'으로 시작하는 위치로 색인이 바로 찾아간다.
3. **와일드카드(`%`)를 앞에 붙인 경우**
   - 안 좋은 예: `WHERE email LIKE '%gmail.com'` — 앞글자를 모르므로 색인 전체를 다 뒤져야 한다.
   - 개선: `WHERE email LIKE 'user%'` — 앞글자가 정해져 있으면 그 위치로 바로 이동한다.

이 원칙은 6절의 `LIKE`뿐 아니라 앞서 다룬 모든 `WHERE` 조건에 그대로 적용된다 — `%아%`처럼 와일드카드를 양쪽에 붙인 검색이나, 날짜 컬럼을 가공한 비교는 인덱스를 타지 못한다.

**한 줄 요약**: SARGable Query란 "DB가 만들어 둔 인덱스를 지름길 삼아 바로 찾아갈 수 있도록, `WHERE` 절의 컬럼을 원본 그대로 두고 조건문을 작성하는 것"이다.

## 8. 집계 — `COUNT`, `AVG`와 `GROUP BY`

**집계**는 데이터를 그룹으로 묶어서 단일 값 여러 개를 뽑아내는 것이다. 총합, 최솟값, 최댓값, 개수, 평균 등이 대표적인 집계 함수다. 이런 값을 뽑아내는 건 전부 **함수의 힘**을 빌린다 — DB에도 함수 개념이 있다.

- **`COUNT`**: 넘겨주는 대상이 뭐냐에 따라 결과가 달라진다. `COUNT(price)`는 `price`에 들어있는 값의 개수를 세는데, **`price`가 `NULL`인 행은 개수에서 빠진다.**
- 그래서 테이블의 전체 레코드 수를 알고 싶다면, `NULL`이 들어갈 수 있는 컬럼이 아니라 **식별자(주로 `id`)** 컬럼을 대상으로 세는 게 바람직하다.
- **`AVG`**: 원하는 컬럼으로 평균을 구한다. `COUNT(*)`처럼 `*`를 넘기면 연산량이 더 많아지므로, 가능하면 필요한 컬럼을 직접 지정하는 게 낫다.

전체를 대상으로 단일 값 하나만 뽑는 집계는 실무에서 잘 쓰지 않는다. **`GROUP BY`와 함께 그룹별로 집계하는 방식**을 훨씬 많이 쓴다 — 전국 단위 개표 방송에서 지역·성별·연령별로 집계된 득표수를 보여주는 것과 같은 원리다.

```sql
SELECT category_id, AVG(price) avg_price
FROM menus
GROUP BY category_id;
```

- 카테고리별 평균 가격처럼, **집계 결과가 "무엇에 대한" 값인지 기준을 함께 표시**해야 한다.
- `AVG(price)`라는 이름 그대로 두면 "평균"이라는 이름만으로는 무엇의 평균인지 알 수 없다 — 그래서 **별칭(alias)**으로 `avg_price`처럼 의미를 담아 결과 컬럼명을 바꾼다.
- `GROUP BY`를 쓰면, **`SELECT`에는 집계 대상이 아닌 다른 컬럼을 함께 쓸 수 없다** — `GROUP BY`에 지정한 컬럼과 집계 함수 결과만 쓸 수 있다.

## 9. `HAVING` — 집계 결과를 다시 필터링하기

집계해서 카테고리별 평균 가격을 구했다면, 이번엔 "평균이 3000원 이상인 카테고리만" 보고 싶을 수 있다. 이때 `WHERE avg_price >= 3000`을 쓰면 **구문 오류**가 난다 — `WHERE`는 `GROUP BY`보다 뒤에 올 수 없기 때문이다(6절의 실행 순서 참고).

그렇다고 `WHERE`를 앞으로 옮기면, 이번엔 "평균 가격이라는 값 자체가 아직 존재하지 않는다"는 오류가 난다 — 실제 실행 순서가 `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`이기 때문에, `WHERE`가 실행되는 시점에는 아직 집계도, 별칭도 만들어지지 않은 상태다.

- 별칭은 `SELECT` 단계에서 정의된다 — 그래서 `WHERE`에서는 그 별칭을 쓸 수 없다.
- 원래 이름(`AVG(price)`)으로도 안 된다 — `GROUP BY` 절이 처리된 **다음에야** `AVG(price)` 자체가 계산되기 때문이다.

그래서 **`GROUP BY`로 묶인 결과를 다시 필터링할 때 쓰는 전용 절이 `HAVING`**이다.

```sql
SELECT category_id, avg(price) avg_price FROM menus
GROUP BY category_id
HAVING avg(price) >= 3000;
```

이 구문은 ANSI SQL(표준) 그대로라서, 모든 DBMS에서 동일하게 통한다.
