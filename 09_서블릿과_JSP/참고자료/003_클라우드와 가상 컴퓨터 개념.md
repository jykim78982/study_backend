# 클라우드와 가상 컴퓨터 개념

## 1. 지금 쓰고 있는 터미널이 항상 "내 컴퓨터"는 아니다

터미널에 결과가 뜬다고 해서 그게 항상 로컬 컴퓨터에서 실행된 건 아니다. 예를 들어 `ssh`로 원격 서버에 접속해서 명령어를 입력하는 경우처럼, 지금 우리가 쓰는 방식 자체가 이미 클라우드 방식일 수 있다 — 겉보기엔 로컬 터미널 같아도, 실제로는 원격의 가상 컴퓨터에 접속해서 쓰고 있는 상황일 수 있다는 뜻이다.

## 2. 서버를 마련하는 방식의 변화 — 구매 → 코로케이션 → 임대 → 클라우드

배포를 하려면 **24시간 꺼지지 않는 안전한 컴퓨터(서버)**가 있어야 한다. 이 서버를 마련하는 방식은 시대에 따라 바뀌어왔다.

1. **직접 구매해서 직접 보관**: 서버를 사서 개인이나 회사가 직접 관리. 관리가 불편하다는 문제가 있다.
2. **코로케이션(Co-location)**: 서버는 직접 구매하되, 데이터센터에 가져다 맡기는 방식. "내가 사고 싶은 서버가 있는데, 데이터센터에 꽂아만 줄 수 없나?"라는 필요에서 나왔다. 가비아 등이 대표적인 데이터센터다.
3. **서버 임대(호스팅)**: 서버를 직접 사지 않고 데이터센터가 가진 서버 중에서 스펙을 골라 빌려 쓰는 방식. 서버를 직접 사는 것보다 훨씬 편하다.
4. **클라우드**: 물리적인 서버 한 대를 통째로 빌리는 게 아니라, 하나의 물리 컴퓨터를 논리적으로 잘게 쪼갠 자원을 구매하는 방식.

즉 "서버를 마련한다"는 목적은 같지만, **물리적으로 소유·보관하던 것에서 → 논리적으로 필요한 만큼만 구독하는 방식**으로 흘러온 것이 이 변화의 핵심이다.

## 3. 클라우드란 무엇인가

인터넷을 그림으로 표현할 때 구름(cloud) 모양이나 거미줄 모양을 즐겨 쓴 데서 이름이 유래했다. **클라우드는 내가 물리적으로 소유하는 게 아니라, 인터넷을 통해 원격으로 빌려 쓰는 논리적인 컴퓨팅 자원**이다.

온라인으로 구매할 수 있는 자원은 크게 세 층위로 나뉜다.

| 계층 | 의미 | 예시 |
|---|---|---|
| **인프라(Infra)** | 컴퓨터(연산·저장 자원) 자체 | CPU, 메모리, 디스크, 네트워크 |
| **플랫폼(Platform)** | 인프라 위에서 도는 실행 환경 | OS, DB, 데이터 분석 환경 등 |
| **소프트웨어(Software)** | 최종 사용자가 쓰는 서비스 | 완성된 애플리케이션 |

이 세 가지를 각각 **원격으로 구독해서 쓸 수 있게 만든 환경**이 클라우드다. 그래서 서비스 이름도 이 계층을 따라 **IaaS**(Infrastructure as a Service), **PaaS**(Platform as a Service)로 불린다.

## 4. 컴퓨터가 어떻게 "서비스"가 되는가 — 가상화와 하이퍼바이저

컴퓨터를 물리적으로 직접 만져서 쓰는 게 아니라, 원격 접속으로 쓴다고 해도 여전히 의문이 남는다 — 사용자가 원하는 크기(스펙)로 딱 맞춰 파는 게 쉬운 일이 아니기 때문이다. 이걸 가능하게 하는 기술이 **가상화(Virtualization)**다.

- 예: 윈도우 서버 계열(Azure가 이 방식을 씀)은 **Hyper-V**라는 가상화 기술을 쓴다.
- 사용자가 "메모리 900MB만 필요해요"처럼 시중에 없는 단위를 요구해도, Hyper-V로 그 스펙 그대로의 **가상 컴퓨터**를 실제로 만들어낼 수 있다.
- 가상 CD 이미지로 OS를 설치하고, 만들어진 가상 컴퓨터의 전원을 켜서 실제 컴퓨터처럼 쓸 수 있다.

**Q. 가상 컴퓨터가 내 컴퓨터 안에 있으니 마음대로 접근할 수 있는 것 아닌가?**
**A.** 물리적으로는 같은 컴퓨터 안에 있지만, 엄연히 별도의 가상 공간이므로 **네트워크를 통하거나 하이퍼바이저(Hyper-V) 창을 통해서만** 접근할 수 있다. 지금 서비스받고 있는 클라우드 자원 대부분이 이 구조로 동작한다.

인프라 자체를 이렇게 가상으로 만들어 서비스로 제공할 수 있게 되면서, **자원을 원하는 만큼 잘게 쪼개 살 수 있게** 됐고, 이것이 **월 단위 구독(클라우드 요금제)** 형태로 자리 잡았다.

## 5. AWS, Azure, GCP — 회사만 다를 뿐 개념은 같다

- **AWS(Amazon Web Services)**: 아마존이 제공하는 클라우드 서비스. 배포할 때 흔히 쓰는 **EC2**가 컴퓨터(가상 서버)를 렌탈하는 서비스다.
  - 가입 시 무료 사용량이 있지만, 가입 자체에 카드 등록이 필수이고 무료 기간을 넘기면 과금된다.
- **Azure**: 마이크로소프트가 제공하는 클라우드 서비스. AWS와 하는 일(컴퓨팅 자원 판매)은 같고 **회사만 다르다.**
- **GCP(Google Cloud Platform)**: 구글이 제공하는 클라우드 서비스. AWS의 EC2에 대응하는 가상 서버 렌탈 서비스로 **Compute Engine**을 제공한다.

즉 AWS·Azure·GCP·기타 클라우드 업체는 **"물리 컴퓨터를 가상화해서 원하는 만큼 나눠 파는" 같은 개념을, 서로 다른 회사가 각자의 브랜드로 제공**하고 있는 것이다.

## 6. 왜 로컬이 아니라 가상 컴퓨터(WSL)에 개발 환경을 만드는가

우리가 데이터베이스를 로컬 OS(윈도우)에 바로 설치하지 않고 **WSL**(가상 리눅스 환경)에 설치한 이유가 바로 이 흐름과 이어진다.

- 실제 배포는 **윈도우가 아니라 리눅스 서버**에서 이뤄질 것이기 때문에, 처음부터 **리눅스에 가까운 환경**에서 개발·테스트하는 것이 배포 환경과의 차이를 줄여준다.
- 여기서 중요한 질문이 하나 더 생긴다 — **로컬(WSL)에서 DB도 깔고 소프트웨어도 잘 돌아갔다면, 서버에도 정확히 같은 환경(같은 DB 버전, 같은 JDK 버전, 같은 디렉토리 구조)이 갖춰져 있어야 하지 않을까?**
- 만약 서버의 DB 버전이나 JDK 버전이 로컬과 다르면, 로컬에서는 되던 게 서버에서는 **안 돌아갈 수도 있다.**

## 7. 해결책 — 환경 자체를 통째로 배포하기

이 "환경 불일치" 문제를 해소하는 방법이 바로 **가상 컴퓨터 자체를 배포하는 것**이다.

- Hyper-V로 만든 가상 컴퓨터 위에 DB, JDK, 소프트웨어까지 전부 설치하고 테스트를 마쳤다면, 서버에서 다시 이것저것 세팅할 필요 없이 **이 가상 컴퓨터를 통째로 배포 서버로 옮기면** 된다.
- 가상 컴퓨터를 **내보내기(export)**하고 대상 서버에서 **불러오기(import)**만 하면, 추가 세팅 없이 로컬과 동일한 환경이 그대로 재현된다.

앞으로는 이런 방식의 "환경을 통째로 옮기는" 가상 컴퓨터를 **Docker**라는 도구를 통해 다루게 된다.
