# 서블릿 프로그램 만들기

Maven 같은 빌드 도구 없이, **jar 파일을 직접 받아서** 서블릿과 임베디드 톰캣을 동작시켜보는 실습.

1. VS Code + 수동으로 받은 jar(`lib` 폴더) + 임베디드 톰캣으로 직접 실행
2. 톰캣을 통째로 설치해서 정적 HTML 파일 서비스하기
3. 컴파일된 `.class` 파일과 톰캣 표준 폴더 구조(`WEB-INF/classes`)를 수동으로 배치해서 배포하기
5. 서블릿 생명주기(Lifecycle)를 직접 콘솔 로그로 확인하기

이전 노트에서는 Maven이 의존성과 디렉토리 구조를 자동으로 관리해주는 걸 다뤘다면, 이 실습은 그 반대로 **Maven 없이 톰캣과 서블릿이 실제로 어떻게 맞물려 돌아가는지**를 손으로 직접 만져보는 과정이다.

## [실습 1] VS Code + 임베디드 톰캣으로 서블릿 실행하기

### 1단계: 프로젝트 폴더와 lib 폴더 준비

VS Code에서 새 프로젝트를 만들고 이름을 `servlet_hello_project`로 한다. 프로젝트 루트에 `lib` 폴더가 있는지 확인한다.

VS Code 하단에 **제한 모드(Restricted Mode)** 표시가 뜨면 클릭해서 **신뢰(Trust)** 버튼을 눌러준다 — 제한 모드에서는 프로젝트 설정이 제대로 동작하지 않을 수 있다.

### 2단계: 필요한 jar 파일 다운로드

Maven 없이 라이브러리를 쓰려면, jar 파일을 직접 찾아서 받아야 한다. Maven 중앙 저장소 사이트에서 `servlet-api`를 검색하되, **버전은 빼고 이름만으로** 검색한다. 검색 결과의 버전 탭에서 원하는 버전을 고르고, 오른쪽의 "Browse" 링크를 클릭하면 실제 다운로드 가능한 파일 목록이 나온다.

다음 jar 파일들을 찾아 받아서 프로젝트의 `lib` 폴더에 넣는다.

- `jakarta.servlet-api-6.0.0.jar` — 서블릿 표준 API
- `tomcat-embed-core-10.1.19.jar` — 임베디드 톰캣 핵심 기능
- `tomcat-embed-el-10.1.19.jar` — 톰캣이 내부적으로 쓰는 표현언어(EL) 처리기
- `jakarta.annotation-api-2.1.1.jar` — `@WebServlet` 같은 애노테이션 지원

```
servlet_hello_project/
└── lib/
    ├── jakarta.annotation-api-2.1.1.jar
    ├── jakarta.servlet-api-6.0.0.jar
    ├── tomcat-embed-core-10.1.19.jar
    └── tomcat-embed-el-10.1.19.jar
```

이전 노트 7장에서 다룬 것처럼, jar 하나만 받으면 안 되고 서로 관련된 여러 jar가 함께 필요하다 — 다만 Maven이 없으니 그 전이 의존성을 **직접 하나하나 찾아서** 받아야 하는 것이 이 방식의 번거로움이다.

### 3단계: 클래스패스(Referenced Libraries) 등록 — 자동으로 안 될 때만

VS Code가 `lib` 폴더의 jar를 자동으로 인식하지 못하면, 이전에 다룬 것과 같은 방식으로 수동 등록한다.

1. VS Code 좌측 하단 **JAVA PROJECTS** 패널에서 `...`(More Actions) 아이콘을 클릭하고 **Configure Classpath**를 선택한다
2. **Referenced Libraries** 항목으로 이동한다
3. **Add Libraries...**(`+` 버튼)를 눌러 `lib` 폴더 안의 jar 파일 3개를 모두 선택해서 추가한다

### 4단계: `HelloServlet.java` 작성

```java
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

import java.io.IOException;
import java.io.PrintWriter;

public class HelloServlet extends HttpServlet {

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        // 응답 데이터의 타입과 인코딩 설정
        resp.setContentType("text/html; charset=UTF-8");

        // 브라우저로 출력할 스트림 가져오기
        PrintWriter out = resp.getWriter();
        out.println("<html>");
        out.println("<body>");
        out.println("<h1>Hello, Servlet!</h1>");
        out.println("<p>VSCode 환경에서 서블릿 실행 성공!</p>");
        out.println("</body>");
        out.println("</html>");
    }
}
```

이전에 다룬 `doGet`이 바로 이 자리다 — `service`가 GET 요청을 받으면 이 메소드로 분기해준다.

### 5단계: 임베디드 톰캣 실행 클래스 `ServerApp.java` 작성

```java
import org.apache.catalina.startup.Tomcat;

import java.io.File;

public class ServerApp {

    public static void main(String[] args) throws Exception {
        // 1. 가져온 라이브러리(Jar)로 임베디드 톰캣 객체 생성
        Tomcat tomcat = new Tomcat();

        // 2. 서버 포트 설정 (8080)
        tomcat.setPort(8080);
        tomcat.getConnector();

        // 3. 웹 애플리케이션 루트(Context) 설정
        String docBase = new File(".").getAbsolutePath();
        var context = tomcat.addContext("", docBase);

        // 4. 서블릿 등록 및 URL 매핑 (/hello 주소 연결)
        String servletName = "HelloServlet";
        tomcat.addServlet("", servletName, new HelloServlet());
        context.addServletMappingDecoded("/hello", servletName);

        // 5. 톰캣 서버 시작 및 브라우저 요청 대기
        tomcat.start();
        System.out.println("Server started on http://localhost:8080/hello");
        tomcat.getServer().await();
    }
}
```

`tomcat.addServlet(...)`으로 `HelloServlet` 객체를 등록하고, `addServletMappingDecoded("/hello", ...)`로 `/hello` 주소와 그 객체를 연결한다. 이전 노트 10장에서 다룬 흐름 그대로, `/hello` 요청이 오면 톰캣이 이 매핑을 보고 `HelloServlet`의 서비스 함수를 호출한다.

### 6단계: 실행 및 확인

1. `ServerApp.java`를 열고 `main` 메소드 위의 Run 버튼(또는 `F5`/`Ctrl+F5`)을 누른다
2. 터미널에 `Server started on http://localhost:8080/hello`가 출력되는지 확인한다
3. 브라우저에서 `http://localhost:8080/hello`로 접속해서 결과를 확인한다

## [실습 2] 톰캣 서버를 직접 설치해 HTML 파일 서비스하기

이번엔 서블릿 코드 없이, **톰캣 자체를 설치**해서 정적 HTML 파일을 서비스하는 가장 기본적인 형태를 확인한다.

### 1단계: 톰캣 다운로드 및 압축 해제

Apache Tomcat 공식 사이트(`https://tomcat.apache.org/`)에서 왼쪽 메뉴의 **Tomcat 10**을 클릭하고, 자신의 환경에 맞는 파일(Windows는 `.zip`, macOS는 `.tar.gz`)을 받는다. 원하는 경로(예: `C:\tomcat` 또는 `~/tomcat`)에 압축을 푼다.

### 2단계: HTML 파일 작성

톰캣의 `webapps/ROOT` 폴더에 `index.html` 파일을 만들고 원하는 내용을 작성한다.

### 3단계: 톰캣 실행 및 접속

`tomcat설치디렉토리/bin` 폴더로 이동해서 서버를 실행한다.

- Windows: `startup.bat`
- macOS/Linux: `./startup.sh`

검은 콘솔 창이 뜨면 그대로 둔 채(닫으면 서버가 종료된다), 브라우저에서 `http://localhost:8080/index.html`에 접속해 HTML 화면을 확인한다.

이 실습에는 서블릿도 자바 코드도 없다 — 톰캣이 정적 파일을 그대로 서비스하는 가장 단순한 웹 서버 동작만 확인하는 단계다. [실습 1]의 임베디드 톰캣이 사실은 이 "톰캣 본체"를 자바 코드 안에서 직접 띄운 것과 같다는 걸 비교해서 이해하면 좋다.

## [실습 3] `.class` 파일과 표준 폴더 구조를 수동 배치해 서블릿 실행하기

컴파일된 `.class` 파일과 `WEB-INF` 폴더 구조를 톰캣의 `webapps`에 직접 만들어 넣어, **IDE도 빌드 도구도 없이** 서블릿이 배포되는 원리를 확인하는 실습이다.

### 사전 작업

[실습 1]의 서블릿 프로젝트를 열어서 `HelloServlet` 클래스에 `@WebServlet("/hello")` 애노테이션을 붙이고 저장한다(필요한 import는 quick fix로 추가한다). 그리고 프로젝트를 다시 실행해서 `.class` 파일이 새로 생성된 걸 확인한다.

### 1단계: 톰캣 표준 웹 애플리케이션 폴더 구조 만들기

톰캣은 웹앱을 배포할 때 `webapps` 아래에 정해진 폴더 구조를 요구한다. 톰캣 설치 경로의 `webapps` 폴더로 이동해서, `ROOT` 안에 `WEB-INF` 폴더가 있는지 확인하고 그 안에 `classes` 폴더를 만든다.

```
tomcat/
└── webapps/
    └── ROOT/
        └── WEB-INF/
            └── classes/   ← 이 위치에 .class 파일이 들어가야 함
```

Maven이 관례로 강제하는 `src/main/java` 구조(이전 노트 8장)와 마찬가지로, 톰캣도 배포용 표준 구조가 정해져 있다 — 다만 이번엔 그걸 우리가 손으로 직접 맞춰줘야 한다는 점이 다르다.

### 2단계: `.class` 파일을 `WEB-INF/classes`로 복사

`servlet_hello_project`에서 컴파일된 `HelloServlet.class` 파일을 찾아, 톰캣의 `webapps/myweb/WEB-INF/classes/` 폴더 안에 그대로 붙여넣는다.

**옵션 — 터미널에서 직접 컴파일하고 싶다면**: IDE의 자동 빌드 없이 `javac`로 직접 컴파일할 수도 있다. 이때는 톰캣이 제공하는 `servlet-api.jar` 경로를 `javac`에 알려줘야 한다.

```bash
# 1. HelloServlet.java 파일이 있는 위치로 이동
cd 프로젝트폴더

# 2. javac 명령어로 컴파일 (톰캣 lib 폴더의 servlet-api.jar를 참조)
# Windows CMD
javac -cp "C:\tomcat\lib\servlet-api.jar" -d . HelloServlet.java

# macOS / Linux
javac -cp "~/tomcat/lib/servlet-api.jar" -d . HelloServlet.java
```

컴파일이 끝나면 `HelloServlet.class` 파일이 만들어진다.

### 3단계: 톰캣 실행 및 결과 확인

톰캣의 `bin` 폴더로 이동해서 서버를 실행한다.

- Windows: `startup.bat`
- macOS/Linux: `./startup.sh`

브라우저에서 `http://localhost:8080/hello`로 접속한다(톰캣 10+ 버전 기준, 애노테이션 `@WebServlet("/hello")`으로 매핑이 자동 적용된다는 전제).

### 4단계: 404 에러가 날 때 — `web.xml`로 수동 매핑하기

`@WebServlet` 애노테이션 스캔이 적용되지 않아 404가 뜨는 경우, 톰캣의 `WEB-INF/web.xml` 파일에 서블릿 등록과 URL 매핑을 **직접** 추가해준다.

```xml
<servlet>
    <servlet-name>helloServlet</servlet-name>
    <servlet-class>HelloServlet</servlet-class>
</servlet>

<servlet-mapping>
    <servlet-name>helloServlet</servlet-name>
    <url-pattern>/hello</url-pattern>
</servlet-mapping>
```

이건 [실습 1]에서 자바 코드로 했던 다음 두 줄과 **완전히 같은 역할**을 XML로 표현한 것이다.

```java
tomcat.addServlet("", servletName, new HelloServlet());
context.addServletMappingDecoded("/hello", servletName);
```

전체 `web.xml`은 다음과 같은 형태다(위 `<servlet>`/`<servlet-mapping>` 블록을 기존 내용 중간에 끼워 넣는다).

```xml
<?xml version="1.0" encoding="UTF-8"?>
<web-app xmlns="https://jakarta.ee/xml/ns/jakartaee"
  xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee
                      https://jakarta.ee/xml/ns/jakartaee/web-app_6_0.xsd"
  version="6.0"
  metadata-complete="true">

  <display-name>Welcome to Tomcat</display-name>
  <description>
     Welcome to Tomcat
  </description>

  <servlet>
        <servlet-name>helloServlet</servlet-name>
        <servlet-class>HelloServlet</servlet-class>
    </servlet>

    <servlet-mapping>
        <servlet-name>helloServlet</servlet-name>
        <url-pattern>/hello</url-pattern>
    </servlet-mapping>

</web-app>
```

## [실습 5] 서블릿 생명주기(Lifecycle)

톰캣이 실행하는 서블릿 코드는 그 흐름 중간중간에 **사용자가 오버라이드할 수 있는 메소드들**을 미리 준비해 놓고 있다. 어떤 메소드를 오버라이드하면 그 안에서 무엇을 할 수 있고, 그 메소드가 정확히 **언제** 실행되는지를 이해하는 것이 이 실습의 목표다. 이전 노트 2장에서 다룬 생명주기를, 이번엔 콘솔 로그로 직접 눈으로 확인해본다.

### 1. 서블릿 핵심 오버라이드 메소드 목록

전체 흐름은 이렇다. `service`가 요청마다 실행되면서 HTTP 메소드에 따라 `doGet`/`doPost`/그 외 `doXxx`로 갈라진다.

```
init → service → doGet  → destroy
             ├─→ doPost
             └─→ do…
```

| 메소드 | 호출 시점 | 주요 용도 |
|---|---|---|
| `init(ServletConfig config)` | 서블릿 객체 생성 직후 (최초 1회) | 리소스 초기화 (DB 연결, 설정 로드 등) |
| `service(HttpServletRequest, HttpServletResponse)` | 클라이언트 요청 시마다 | HTTP 메소드(GET, POST 등)에 따라 알맞은 `doXxx()`로 분기 |
| `doGet(HttpServletRequest, HttpServletResponse)` | GET 요청 수신 시 | 데이터 조회 및 화면 전달 처리 |
| `doPost(HttpServletRequest, HttpServletResponse)` | POST 요청 수신 시 | 데이터 생성/수정/삭제 등 폼 데이터 처리 |
| `destroy()` | 서블릿 객체 소멸 전 (서버 종료/재배포 시) | 리소스 해제 (DB 연결 종료, 파일 닫기 등) |

`init`과 `destroy`는 **딱 한 번**만 실행되고, `service`부터 `doGet`/`doPost`까지는 **요청이 올 때마다** 실행된다는 게 핵심 차이다.

### 2. 실습 예제 — `LifecycleServlet.java`

이전에 만든 `servlet_hello_project`([실습 1] 참고)에 파일을 하나 더 추가한다.

```java
import jakarta.servlet.ServletConfig;
import jakarta.servlet.ServletException;
import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

import java.io.IOException;
import java.io.PrintWriter;

@WebServlet("/test")
public class LifecycleServlet extends HttpServlet {

    private int requestCount;

    // 1. 초기화 메서드 (서블릿 생성 시 1회 실행)
    @Override
    public void init(ServletConfig config) throws ServletException {
        super.init(config);
        this.requestCount = 0;
        System.out.println("[init] 서블릿이 생성 및 초기화되었습니다.");
    }

    // 2. 요청 분기 메서드 (모든 요청 시마다 doGet/doPost 전에 실행)
    @Override
    protected void service(HttpServletRequest req, HttpServletResponse resp) 
            throws ServletException, IOException {

        requestCount++;
        System.out.println("[service] 요청 수신 (누적 요청 수: " + requestCount + ")");

        // super.service()를 호출해야 HTTP 메서드에 맞춰 doGet/doPost로 전달됨
        super.service(req, resp);
    }

    // 3. GET 요청 처리 메서드
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) 
            throws ServletException, IOException {

        System.out.println("[doGet] GET 방식 요청 처리 중");

        resp.setContentType("text/html; charset=UTF-8");
        PrintWriter out = resp.getWriter();

        out.println("<html><body>");
        out.println("<h2>Servlet Lifecycle & Override Test</h2>");
        out.println("<p>총 방문 횟수: " + requestCount + "</p>");
        out.println("<form action='test' method='POST'>");
        out.println("  <input type='submit' value='POST 요청 보낼 버튼'>");
        out.println("</form>");
        out.println("</body></html>");
    }

    // 4. POST 요청 처리 메서드
    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) 
            throws ServletException, IOException {

        System.out.println("[doPost] POST 방식 요청 처리 중");

        resp.setContentType("text/html; charset=UTF-8");
        PrintWriter out = resp.getWriter();

        out.println("<html><body>");
        out.println("<h2>POST 요청 수신 성공</h2>");
        out.println("<a href='test'>GET 요청으로 돌아가기</a>");
        out.println("</body></html>");
    }

    // 5. 소멸 메서드 (서버 종료/재배포 시 1회 실행)
    @Override
    public void destroy() {
        System.out.println("[destroy] 서블릿이 소멸합니다. 리소스를 정리합니다.");
    }
}
```

`@WebServlet("/test")` 애노테이션으로 URL 매핑까지 클래스 안에서 끝내버릴 수도 있지만, 아래 3단계처럼 `ServerApp.java`에서 코드로도 등록해서 이중으로 확실하게 맞춰둔다. `service`가 `super.service(req, resp)`를 호출해야 실제로 `doGet`/`doPost`로 흐름이 이어진다는 점은 이전에 다룬 "오버라이드 안에서 `super`로 원래 흐름을 이어가는" 패턴 그대로다.

### 3. URL 매핑하기

`ServerApp.java`에 `LifecycleServlet`을 등록하고 `/test`로 매핑하는 두 줄을 추가한다.

```java
tomcat.addServlet("", "test", new LifecycleServlet());
context.addServletMappingDecoded("/test", "test");
```

전체 `ServerApp.java`는 다음과 같다 — [실습 1]에서 만든 `HelloServlet` 등록 코드 아래에 이어 붙인다.

```java
import org.apache.catalina.startup.Tomcat;
import org.apache.tomcat.util.scan.StandardJarScanner;

import java.io.File;

public class ServerApp {

    public static void main(String[] args) throws Exception {
        // 1. 가져온 라이브러리(Jar)로 임베디드 톰캣 객체 생성
        Tomcat tomcat = new Tomcat();

        // 2. 서버 포트 설정 (8080)
        tomcat.setPort(8080);
        tomcat.getConnector();

        // 3. 웹 애플리케이션 루트(Context) 설정
        String docBase = new File(".").getAbsolutePath();
        var context = tomcat.addContext("", docBase);

        // 4. 서블릿 등록 및 URL 매핑 (/hello 주소 연결)
        String servletName = "HelloServlet";
        tomcat.addServlet("", servletName, new HelloServlet());
        context.addServletMappingDecoded("/hello", servletName);

        tomcat.addServlet("", "test", new LifecycleServlet());
        context.addServletMappingDecoded("/test", "test");

        // 5. 톰캣 서버 시작 및 브라우저 요청 대기
        tomcat.start();
        System.out.println("Server started on http://localhost:8080/hello");
        tomcat.getServer().await();
    }
}
```

한 임베디드 톰캣 안에 `/hello`와 `/test` 두 개의 URL이 각각 다른 서블릿 객체로 매핑되어 있다 — 톰캣이 요청받은 경로를 보고 어느 서블릿의 `service`를 호출할지 골라내는 구조다.

### 4. 동작 확인 순서

1. 애플리케이션 실행 후 브라우저에서 `http://localhost:8080/test` 접속 (GET 요청)
2. 브라우저 화면의 "POST 요청 보낼 버튼" 클릭 (POST 요청)
3. 브라우저 새로고침 실행 (GET 요청 추가)
4. 서버(Tomcat) 종료

콘솔 출력 결과 예시:

```
[init] 서블릿이 생성 및 초기화되었습니다.
[service] 요청 수신 (누적 요청 수: 1)
[doGet] GET 방식 요청 처리 중
[service] 요청 수신 (누적 요청 수: 2)
[doPost] POST 방식 요청 처리 중
[service] 요청 수신 (누적 요청 수: 3)
[doGet] GET 방식 요청 처리 중
...
[destroy] 서블릿이 소멸합니다. 리소스를 정리합니다.
```

이 로그가 정확히 앞서 1장의 표를 눈으로 증명해준다.

- `[init]`은 **딱 한 번**, 브라우저가 처음 `/test`에 접속할 때(서블릿 객체가 최초로 만들어질 때) 찍힌다
- 이후 요청마다 `[service]`가 먼저 찍히고, 그 안에서 요청 방식에 따라 `[doGet]` 또는 `[doPost]`가 이어서 찍힌다 — `requestCount`가 요청마다 누적되는 것도 `service`가 매번 실행된다는 증거다
- `[destroy]`는 서버를 종료하는 순간, **딱 한 번**만 찍힌다

## 네 실습을 정리하면

| 실습 | 빌드/의존성 관리 | 서블릿 배포 방식 | 확인 초점 |
|---|---|---|---|
| 1. VS Code + 임베디드 톰캣 | jar를 수동으로 받아 `lib`에 배치 | 자바 코드(`tomcat.addServlet`)로 직접 등록 | 최소 구성으로 서블릿 띄우기 |
| 2. 톰캣 직접 설치 | 필요 없음(정적 파일만) | `webapps/ROOT`에 HTML 파일만 배치 | 톰캣 본체의 정적 서비스 동작 |
| 3. `.class` + 표준 폴더 구조 | 컴파일만 수동으로(`javac -cp`) | `WEB-INF/classes` + `web.xml`(또는 애노테이션)로 배포 | 배포 원리를 손으로 직접 구성 |
| 5. 생명주기 확인 | [실습 1] 프로젝트 재사용 | `@WebServlet` + 코드 등록 병행 | `init`/`service`/`doGet`/`doPost`/`destroy` 호출 시점 |

네 실습 모두 결국 톰캣이 **"이 URL로 요청이 오면 이 서블릿 객체의 서비스 함수를 호출한다"**는 매핑을 어떤 방식으로 등록받는지, 그리고 그 서블릿 객체 안에서 **어떤 메소드가 언제 실행되는지**가 핵심이다 — 자바 코드로 직접 등록하느냐(실습 1), 애노테이션으로 하느냐, `web.xml`로 명시하느냐(실습 3)의 차이일 뿐이다. Maven이 없다 보니 실습 1·3에서는 Maven 기반 프로젝트가 자동으로 해주던 의존성 다운로드와 표준 폴더 구성을 전부 손으로 해야 했다는 점이, 왜 빌드 도구가 필요한지를 거꾸로 체감하게 해주는 부분이다.
