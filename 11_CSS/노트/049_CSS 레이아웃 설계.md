# CSS 레이아웃 설계

## 1. CSS 파일을 어디에 둘 것인가 — 코로케이션

스타일 적용 방법은 인라인 · 인터널 · external 세 가지가 있는데, 기본은 **external**이다. 인라인은 외부에서 덮어쓰기가 불가능해 CSS 본연의 역할(캐스케이딩)을 할 수 없으므로 예외적인 경우가 아니면 쓰지 않는다. 같은 대상에 같은 우선순위의 스타일을 인라인·인터널·external로 각각 준다면, 소스 순서와 무관하게 **인라인이 항상 이긴다**.

여러 페이지가 만들어질 때 모든 페이지가 제각각 다른 스타일을 갖지 않는다 — 이 공통된 스타일 묶음을 **테마**라고 한다. 그래서 CSS 파일을 관리할 때는 두 층으로 나눠 생각해야 한다.

- **공통분모(테마)**: 모든 페이지가 함께 쓰는 스타일 → 별도의 공통 위치에 둔다.
- **페이지별 특화 스타일**: 그 페이지에서만 쓰는 스타일 → 파일 수가 많아지므로 찾기 쉬운 곳에 둬야 한다.

이때 "찾기 쉬운 곳"은 CSS만 모아두는 전용 폴더가 아니라, **그 CSS를 쓰는 HTML 근처**다. 완전히 분리된 CSS 폴더에 두면 디렉터리를 뒤져가며 찾아야 해서 생산성이 떨어진다. 이렇게 관련 파일(HTML·CSS·JS)을 근처에 모아두는 방식을 **코로케이션(co-location)**이라고 부른다. 실제로 이 프로젝트도 `admin/menus/list.html`과 `admin/menus/list.css`, `admin/menus/layout.html`과 `admin/menus/layout.css`가 같은 폴더에 코로케이션되어 있다.

## 2. 공통 스타일을 포함하는 방법 — link vs @import

코로케이션된 개별 CSS가 공통분모(`/css/style.css`)를 가져다 쓰는 방법은 두 가지다.

- **HTML에서 `<link>`로 공통 CSS까지 별도로 추가**하는 방법
- **CSS 파일 안에서 `@import`로 다른 CSS를 포함**하는 방법

```html
<!-- layout.html -->
<link rel="StyleSheet" href="layout.css">
```

```css
/* layout.css */
@import url(/css/style.css);

.root {
    height: 100%;
}
```

이 프로젝트는 후자를 택했다 — `layout.css`와 `list.css` 모두 첫 줄에서 `@import url(/css/style.css);`로 공통 스타일을 끌어오고, HTML에는 `layout.css`(또는 `list.css`) 하나만 `link`로 연결한다. 이렇게 하면 HTML에서 여러 개의 `<link>`를 나열하지 않아도, 페이지 전용 CSS 파일 하나만 열어도 그 CSS가 어떤 공통 스타일 위에서 동작하는지 한눈에 알 수 있다.

두 방법은 편의성뿐 아니라 **로드 순서**에서도 차이가 있다.

- HTML에서 `<link>`로 개별 CSS와 공용 CSS를 나란히 추가하면, 브라우저는 두 `<link>`를 만나는 즉시 **개별 CSS와 공용 CSS를 동시에(병렬로) 요청·로드**한다.
- 반면 개별 CSS 파일 안에 `@import`로 공용 CSS를 포함시키면, 브라우저는 먼저 **개별 CSS 파일을 로드한 뒤** 그 안에 적힌 `@import` 구문을 읽고 나서야 **공용 CSS를 순차적으로 로드**한다.

즉 `@import`는 로드 자체가 한 단계 늦게, 순서대로 일어난다는 차이가 있다. 이 프로젝트처럼 파일 수가 적은 학습 환경에서는 체감되지 않지만, 규모가 커지면 `@import` 쪽이 초기 렌더링을 늦추는 요인이 될 수 있다는 점을 알아두면 좋다.

## 3. DOM과 CSSOM — 화면이 만들어지는 과정

HTML은 로드되자마자 그대로 화면에 그려지는 것이 아니다. 구문이 올바른지 확인하고 파싱한 뒤, 각 태그·텍스트·속성이 메모리 위에 객체로 올라간다 — 이 문서 객체를 **DOM(Document Object Model)**이라고 한다.

CSS도 마찬가지로 별도로 파싱되어 메모리에 올라가는데, 이때 만들어지는 스타일 객체 트리를 **CSSOM(CSS Object Model)**이라고 한다. CSSOM이 DOM 위에 얹혀서 결합된 결과가 실제로 화면에 그려지는 내용이다. HTML이 로드된 이후부터는 화면과 DOM이 서로 동기화된다 — DOM을 바꾸면 화면이 바뀌고, 사용자의 입력(예: `input` 값 변경)은 DOM에 반영된다. 자바스크립트가 다루는 대상도 결국 이 DOM·CSSOM 객체들이다.

## 4. 레이아웃(방) 먼저, 콘텐츠는 나중에

레이아웃을 짤 때는 크게 두 방향이 있다.

- **탑다운**: 큰 영역(방)부터 만들고 안쪽 자잘한 요소를 채워나간다.
- **버텀업**: 작은 것부터 만들어서 나중에 구조를 짠다.

실무에서는 탑다운이 일반적이다 — 사이트를 방(레이아웃) 단위로 먼저 나누고, 그 방 안에 가구(섹션)를 배치하고, 가구 안에 콘텐츠를 채우는 순서다. `layout.html`이 바로 콘텐츠를 다 걷어내고 방의 뼈대만 남긴 형태다.

```html
<!-- layout.html -->
<div class="root">
  <header class="header">
  </header>
  <div class="content">
    <aside></aside>
    <main></main>
  </div>
  <footer class="footer"></footer>
</div>
```

이렇게 방만 남겨두고 헤더 · 콘텐츠 영역 · 푸터의 크기 관계부터 잡은 다음, 실제 콘텐츠(`list.html`의 메뉴 목록 같은 내용)를 그 안에 채워 넣는 순서로 작업한다.

## 5. 시맨틱 태그가 아닌 곳에는 이름을 명시하라

`header`·`footer`·`aside`·`main` 같은 시맨틱 태그를 태그 선택자로 직접 잡아 스타일링하면, 문서 안에 같은 태그가 여러 번 중첩되어 있을 때(예: `list.html`은 최상위 `header`와 `main` 안의 `section > header`가 따로 있다) 원치 않는 곳까지 같이 스타일이 걸릴 위험이 있다. 그래서 레이아웃 단계에서는 태그 자체를 선택자로 쓰지 않고, **클래스(또는 섹션이라면 아이디)로 명시적으로 이름을 부여**해서 쓴다. 4절의 `layout.html`에서 `<header class="header">`, `<footer class="footer">`처럼 방을 만들자마자 클래스를 붙여둔 것이 바로 이 때문이다.

```css
.header { ... }
.content { ... }
.footer { ... }
```

`header` 태그 대신 `.header` 클래스를, `footer` 태그 대신 `.footer` 클래스를 쓰는 이유가 이것이다. 특정 페이지·특정 영역에만 적용하고 싶은 스타일은 이렇게 이름을 정해서 범위를 한정해야, 다른 페이지나 다른 위치의 같은 태그까지 스타일이 새는 것을 막을 수 있다.

## 6. 박스 모델 — 요소의 크기는 콘텐츠만이 아니다

이렇게 이름을 붙인 박스에 크기를 줄 때, 그 크기가 정확히 무엇을 가리키는지부터 알아야 한다. 모든 요소는 안쪽부터 바깥쪽으로 4겹으로 이루어진 **박스 모델(Box Model)** 구조를 가진다.

| 겹 | 이름 | 의미 |
|---|---|---|
| 1(가장 안쪽) | 콘텐츠(Content) | 실제 텍스트·이미지 등 내용이 차지하는 영역 |
| 2 | 패딩(Padding) | 콘텐츠와 경계선 사이의 안쪽 여백 |
| 3 | 경계선(Border) | 패딩을 감싸는 테두리 |
| 4(가장 바깥쪽) | 마진(Margin) | 경계선 바깥, 다른 요소와의 바깥쪽 여백 |

요소의 `width`/`height`를 지정해도 그 값은 기본적으로 **콘텐츠 영역만**의 크기다. 즉 실제로 그 요소가 화면에서 차지하는 전체 너비·높이는 `콘텐츠 + 패딩 + 경계선(+ 마진)`을 모두 합한 값이 된다. 원했던 크기(예: 순수하게 지정한 `width`)와 실제로 차지하는 크기가 달라 보이는 "박스 바깥의 이상한 여백" 문제는 대부분 이 4겹 구조 중 패딩·경계선·마진이 지정한 크기 위에 추가로 더해지고 있다는 사실을 놓쳐서 생긴다. 다음 절에서 다루는 `margin: 0` 리셋도 결국 이 박스 모델의 마진 겹을 초기화하는 작업이다 — 원인을 진단할 때는 "콘텐츠 크기는 맞는데 마진·패딩·경계선 중 뭐가 더해지고 있는가"를 겹 단위로 하나씩 확인하는 것이 기본 디버깅 순서다.

## 7. 높이 100%의 함정과 margin 초기화

`html`·`body`에 `height: 100%`를 준다고 해서 자식들이 자동으로 딱 맞게 정리되는 것은 아니다. `style.css`는 이 기본 리셋을 담당한다.

```css
/* style.css */
html {
    height: 100%;
}
body {
    height: 100%;
    margin: 0;
}
```

- `body`는 브라우저 기본값으로 `margin`을 갖고 있다(대체로 8px). 이걸 초기화하지 않으면 콘텐츠가 뷰포트 가장자리에 딱 붙지 않고 여백이 남는다. 값이 없다는 의미로 줄 때는 `margin: 0;`처럼 단위 없이 `0`만 쓴다 — 0은 픽셀이든 퍼센트든 어차피 0이므로 단위가 의미가 없다.
- `body`의 `margin`을 없애는 것은 **모든 페이지에 공통으로 필요한 리셋**이라서, 개별 페이지 CSS가 아니라 공통 CSS(`style.css`)에 둔다. 반대로 특정 페이지에서만 필요한 조정은 그 페이지 전용 CSS에 둬야 한다 — 이게 곧 1절에서 말한 "공통분모 vs 페이지별 스타일"의 실제 적용 사례다.
- 여백이라는 개념은 절대적인 것이 아니라 **상대적**이다. 자식이 가질 수 있는 공간은 어디까지나 부모가 가진 영역 안으로 한정된다. 부모의 영역을 자식들이 이미 다 나눠 가졌다면, 남는 여백은 0이다 — "여백이 있다"는 건 부모가 가진 공간 중에서 자식들이 아직 차지하지 않은 부분이 있다는 뜻일 뿐이다.
- 문제는 어떤 자식에게 `height: 100%`를 주는 순간, 그 자식은 "내 형제들이 얼마를 가졌는지와 무관하게 부모가 가진 만큼 나도 다 가지겠다"고 선언하는 셈이 된다는 점이다. `html`도 `100%`, `body`도 `100%`인 것까지는 문제가 없다 — 뷰포트 자체를 넘어설 수는 없기 때문이다. 하지만 그 `body` 안에 `height: 64px`짜리 헤더와 `height: 100px`짜리 푸터처럼 **고정 높이를 가진 자식**이 있는 상태에서, 다른 자식(예: 콘텐츠 영역)에게까지 `height: 100%`를 그대로 준다면 어떻게 될까?
  - `body`(100%, 뷰포트 전체 높이) 안에 헤더(64px) + 푸터(100px) + 콘텐츠(`body` 기준 100%)가 나란히 있다고 하면, 콘텐츠는 `100%`를 그대로 요구하므로 `뷰포트 높이 + 164px`만큼의 공간을 셋이 합쳐서 요구하는 셈이 된다.
  - `body`는 뷰포트를 벗어날 수 없지만, 그 안의 자식들이 합쳐서 요구하는 높이는 뷰포트를 넘어설 수 있다 — 이 초과분만큼 스크롤바가 생긴다.
  - `height: 100%` 자체가 문제가 아니라, **이미 고정 크기를 가진 형제가 있는데도 나머지 자식에게 똑같이 100%를 주는 것**이 스크롤바의 원인이다. 이걸 해결하려면 콘텐츠에게 "전체(100%)"가 아니라 "형제들이 이미 가져간 만큼을 뺀 나머지"를 줘야 한다.

## 8. calc()로 나머지 영역 채우기

`layout.css`는 헤더·푸터는 고정 높이를 주고, 그 사이 콘텐츠 영역은 "나머지 전부"를 차지하도록 만든다.

```css
.root {
    height: 100%;
}

.header {
    height: 64px;
    background-color: aqua;
}

.content {
    height: calc(100% - 164px);
    background-color: beige;
}

.footer {
    height: 100px;
    background-color: bisque;
}
```

`.root`가 부모(`body`)로부터 물려받은 `100%` 안에서, 헤더(64px) + 푸터(100px) = 164px를 뺀 나머지를 `.content`가 차지하도록 `calc(100% - 164px)`로 계산한다. `calc()`는 이렇게 퍼센트와 픽셀처럼 단위가 다른 값끼리도 섞어서 연산할 수 있게 해주는 함수다. 콘텐츠 내용의 많고 적음과 상관없이 `.content`가 항상 헤더·푸터 사이 남는 공간을 정확히 채우게 되므로, 푸터가 화면 중간에 붕 떠버리는 문제 없이 항상 화면 맨 아래에 자연스럽게 붙는다.

다만 이 방식은 **과거에 쓰던 계산 방법**이다. 심지어 `calc()`조차 없던 더 옛날에는 고정 높이 요소들의 값을 일일이 손으로 더하고 빼서 나머지 영역의 크기를 구해야 했다. `calc()`가 생기면서 그 계산을 CSS 안에서 직접 할 수 있게 됐지만, 그래도 여전히 "형제들의 고정 크기를 다 알고 있어야 나머지를 구할 수 있다"는 한계는 남는다 — 헤더나 푸터의 높이가 바뀌면 `calc()` 식도 같이 고쳐야 한다. 뒤에서 다룰 플렉스박스는 이런 수동 계산 없이도 "나머지 공간을 알아서 채우는" 방식을 제공하는, 더 나은 대안이다.

## 9. 플렉스박스(Flexbox) 기초

과거에는 CSS만으로 레이아웃(방)을 짤 표준 도구가 없어서, 원래 표만 감싸는 용도인 `table` 태그를 중첩해서 방처럼 억지로 써야 했다. 이런 편법(핵, hack)을 해결하기 위해 CSS3에서 등장한 것이 **플렉스박스**다.

```css
.header {
    height: 64px;
    background-color: aqua;

    display: flex;
    flex-direction: column-reverse;
}

.header > span {
    background-color: red;
}
```

- `display: flex`를 주는 순간 그 요소는 **플렉스 컨테이너**가 되고, 자식들은 **플렉스 아이템**이 된다. 겉보기에는 원래 `div`와 다르지 않아 보이지만, 이제 정렬·여백 관련 속성을 추가로 쓸 수 있게 된다.
- `flex-direction`은 아이템이 배치되는 방향을 결정한다. 기본값(`row`)은 가로로 나란히 배치하지만, `column`을 주면 세로로 쌓이고, `row-reverse`/`column-reverse`를 주면 순서가 거꾸로 뒤집힌다. `layout.css`의 `.header`는 `column-reverse`를 줬으므로, `span 1 → 2 → 3` 순서로 작성된 마크업이 화면에서는 `3 → 2 → 1` 순서로 세로로 쌓여 보인다.
- 플렉스박스는 레이아웃(방)뿐 아니라 가구(섹션) 내부 배치나 텍스트 정렬에도 똑같은 방식으로 쓸 수 있다. 사용법이 일관되기 때문에 "정렬하고 싶은 대상이 있으면 컨테이너에 `display: flex`부터 준다"는 접근이 CSS 레이아웃의 기본 전략이 된다.

### 9-1. 플렉스박스 속성 체계

플렉스 관련 속성은 역할별로 다음과 같이 묶어서 이해하면 외우기 쉽다.

| 분류 | 속성 | 역할 |
|---|---|---|
| 용어 | `flex container` / `flex item` | 컨테이너(부모)와 아이템(자식) 구분 |
| 신축성 | `flex`, `flex-grow`, `flex-shrink`, `flex-basis` | 아이템이 남는 공간을 나눠 갖거나 줄어드는 비율 |
| 줄 배치 | `flex-direction`, `flex-wrap`, `flex-flow` | 방향과 줄바꿈 여부(`flex-flow`는 direction+wrap 축약형) |
| 순서 | `order` | 마크업 순서와 무관하게 화면상 표시 순서를 재배치 |
| 정렬 | `justify-content`, `align-items`, `align-self` | 주축(main axis)/교차축(cross axis) 정렬, 개별 아이템만 다르게 정렬 |

- `flex-grow`는 컨테이너에 남는 여유 공간을 아이템들이 어떤 비율로 나눠 가질지, `flex-shrink`는 공간이 모자랄 때 어떤 비율로 줄어들지를 정한다. `flex-basis`는 신축 계산의 기준이 되는 기본 크기다. `flex`는 이 세 값을 한 번에 지정하는 축약 속성이다.
- `order`는 HTML 마크업의 순서를 바꾸지 않고도 화면에 보이는 순서만 바꿀 수 있다 — `layout.css`에서 `flex-direction: column-reverse`로 전체를 뒤집는 것과 달리, `order`는 특정 아이템 하나만 순서를 옮기고 싶을 때 쓴다.

### 9-2. display: flex vs inline-flex — 컨테이너 자체의 배치

`display` 값에 따라 플렉스 컨테이너 자신이 문서 흐름에서 어떻게 배치되는지도 달라진다.

- **`display: flex`**: 컨테이너 자신은 **블록 레벨**로 배치된다. 다른 요소와 같은 줄에 나란히 놓이지 않고, 위아래로 한 줄씩 차지한다. `.header`, `.content`, `.footer`처럼 "방"을 만들 때 쓰는 값이 이것이다.
- **`display: inline-flex`**: 컨테이너 자신은 **인라인 레벨**로 배치되어 다른 텍스트·인라인 요소와 한 줄에 나란히 놓일 수 있다. 그 내부의 아이템 정렬 방식(주축·교차축 정렬 등)은 `flex`와 동일하게 작동한다 — 예를 들어 `<a>제목</a>`, `<span>[39]</span>`, `<a>좋아요</a>`를 감싼 컨테이너에 `inline-flex`를 주면, 그 컨테이너 자체는 인라인처럼 흘러가면서 내부 세 아이템은 플렉스 정렬 규칙대로 나란히 정돈된다.

즉 "컨테이너 바깥에서 어떻게 흐르는가"는 `flex`/`inline-flex`가 결정하고, "컨테이너 안에서 아이템들이 어떻게 배치되는가"는 9-1의 속성들이 결정한다 — 두 층위를 분리해서 생각하면 헷갈리지 않는다.
