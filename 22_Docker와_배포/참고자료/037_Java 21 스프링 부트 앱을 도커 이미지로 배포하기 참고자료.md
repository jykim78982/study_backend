# Java 21 스프링 부트 앱을 도커 이미지로 배포하기

## 1. 백엔드 앱을 왜 도커 이미지로 만들어야 할까?

열심히 만든 백엔드 프로그램을 내 컴퓨터에서 실행했을 때는 아무 문제가 없었는데, 서버나 다른 팀원의 컴퓨터로 옮기면 갑자기 동작하지 않는 경우가 자주 발생한다. 자바 버전이 다르거나 필요로 하는 프로그램 설정이 조금만 틀어져도 오류가 나기 때문이다.

```
[개발자 PC]                              [서버 / 팀원 PC]
✓ Java 21                                ✗ Java 17 (버전 불일치)
✓ 환경 변수 설정 완료        파일만 복사  ✗ 환경 변수 누락
✓ 백엔드 앱 정상 작동      ───────────▶  ✗ 백엔드 앱 실행 오류
```

이 문제를 해결하기 위해 백엔드 앱과 앱을 실행하는 데 필요한 환경을 하나의 상자에 통째로 넣어서 포장한다. 이 상자를 **도커 이미지**라고 부른다. 그리고 이 상자를 만드는 레시피가 바로 **Dockerfile**(도커파일)이다. 레시피를 적어두면 언제 어디서든 버튼 하나로 완전히 똑같은 실행 상자를 만들어낼 수 있다.

**도커 파일과 도커 이미지의 차이는?** 도커 파일도 이미지도 모두 파일로 이루어져 있다. 그러면 그냥 도커 이미지만 있으면 될 것 같은데, 도커 파일을 만들고 도커 이미지가 따로 있는 이유가 뭘까?

Dockerfile은 "베이스 리눅스 OS 위에 특정 애플리케이션을 설치하고 어떤 명령어를 실행한다"라는 내용이 담긴 **텍스트 형태의 레시피** 파일이다. 반면 도커 이미지는 그 레시피대로 리눅스 운영체제와 애플리케이션, 실행 환경이 모두 포함되어 실제 생성된 **용량이 큰 결과물** 파일이다. 소스 코드 관리의 용이성과 배포 효율성을 위해 텍스트 명령어 집합(Dockerfile)과 실제 실행 환경 바이너리(도커 이미지)를 분리하여 관리한다.

| 구분 | Dockerfile (텍스트 레시피) | Docker Image (실제 실행 환경) |
|---|---|---|
| 내용 | 설치·실행 과정을 적은 명령어 | 베이스 리눅스 OS + 런타임·라이브러리 + 내 앱이 패키징된 완성본 |
| 크기 | 수 KB | 수백 MB ~ 수 GB |
| 관리 | Git으로 버전 관리·공유. 몇 줄만 고쳐 바로 다시 빌드 | 레지스트리(Docker Hub 등)에 올려 배포 |

```
Dockerfile ──(docker build)──▶ Docker Image ──(docker run)──▶ 컨테이너
```

> **추가 설명 — 이미지는 레이어를 쌓은 것이다**: 이미지는 하나의 덩어리가 아니라 Dockerfile의 명령 하나하나가 만든 **레이어**를 차곡차곡 쌓은 것이다. 맨 아래 베이스 OS(예: Ubuntu) 레이어, 그 위에 런타임(JRE) 레이어, 맨 위에 내 앱 레이어가 올라간다. 레이어는 읽기 전용이라 여러 이미지가 같은 베이스 레이어를 함께 쓸 수 있고, 다시 빌드할 때 바뀌지 않은 레이어는 **캐시**로 재사용해 빠르게 빌드된다.

## 2. 스프링 부트를 하나로 묶은 JAR 파일 만들기

도커 이미지라는 상자에 백엔드 프로그램을 넣기 전에, 먼저 작성한 자바 코드를 하나의 실행 파일로 뭉쳐야 한다. 스프링 부트에서는 이를 **JAR 파일**이라고 부른다.

터미널을 열고 프로젝트 폴더로 이동한 뒤, Gradle 명령어 하나로 JAR 파일을 쉽게 만들어낼 수 있다.

```bash
./gradlew bootJar
```

이 명령어를 입력하면 빌드가 진행되고, 프로젝트 폴더 안의 `build/libs` 경로에 끝자리가 `.jar`로 끝나는 하나의 커다란 실행 파일이 만들어진다. 이 파일 안에는 우리가 작성한 코드와 스프링 부트를 실행하는 데 필요한 모든 재료가 들어 있다.

> **추가 설명 — `bootJar`와 `build`의 차이**:
>
> | 명령 | 하는 일 | `build/libs`에 생기는 파일 |
> |---|---|---|
> | `./gradlew bootJar` | 실행용 JAR만 만든다. 테스트는 돌지 않는다 | `security-0.0.1-SNAPSHOT.jar` 하나 |
> | `./gradlew build` | 컴파일 + **테스트** + 모든 JAR 생성 | 실행용 JAR + `security-0.0.1-SNAPSHOT-plain.jar` 두 개 |
>
> 실행용 JAR는 의존 라이브러리까지 모두 품은 "뚱뚱한 JAR(fat jar)"라서 `java -jar`만으로 실행된다. plain JAR는 내 코드만 담긴 일반 JAR라 혼자서는 실행되지 않는다. 이 차이가 뒤의 Dockerfile에서 중요해진다.

## 3. JAR 파일을 실행할 운영체제 고르기

JAR 파일을 만들었다면 이제 이를 실행할 기반 운영체제 이미지(**베이스 이미지**)를 선택해야 한다. 도커 허브(Docker Hub)와 같은 도커 이미지 저장소에는 수많은 베이스 이미지가 등록되어 있으므로, 프로젝트 환경에 맞는 최적의 이미지를 검색하고 선택하는 과정이 필요하다.

### 전체 이미지 목록 검색하기

터미널에서 `docker search` 명령어를 사용하면 도커 허브에 등록된 베이스 이미지를 검색할 수 있다. 예를 들어 자바 환경을 찾기 위해 다음과 같이 검색한다.

```bash
docker search java
```

이 명령어를 실행하면 이름, 설명, 별점(STARS), 공식 인증 여부(OFFICIAL) 등이 포함된 전체 검색 결과 목록이 출력된다.

### JDK가 설치된 공식 이미지로 한정하기

단순히 전체 목록을 검색하면 자바와 관련된 온갖 개인 이미지나 오래된 리포지토리가 섞여 나와 원하는 이미지를 찾기 어렵다. 따라서 신뢰할 수 있고 최신 JDK가 미리 설치되어 있는 공식 베이스 이미지로 범위를 좁혀야 한다.

#### 공식(Official) 이미지 조건 추가하기

검색 명령어에 `--filter is-official=true` 옵션을 붙이면 도커에서 공식적으로 검증하고 관리하는 안전한 이미지 목록만 선별할 수 있다.

```bash
docker search --filter is-official=true openjdk
```

#### JDK 배포판 검색 및 선정하기

최근에는 `openjdk` 공식 이미지 대신 OpenJDK 기반의 안정적인 배포판인 **Eclipse Temurin** 이미지를 자주 사용한다. 도커 허브 웹사이트나 검색을 통해 JDK가 포함된 공식 이미지를 찾는다.

```bash
docker search --filter is-official=true eclipse-temurin
```

> **추가 설명 — `openjdk` 이미지는 더 이상 쓰지 않는다**: Docker Hub의 공식 `openjdk` 이미지는 2022년에 **지원 중단(deprecated)** 되어 새 버전이 올라오지 않는다. 설명란에도 그렇게 적혀 있다. 그 대안으로 안내되는 것이 `eclipse-temurin`(Eclipse 재단 Adoptium), `amazoncorretto`(아마존) 같은 배포판 이미지다. 예전 자료에서 `FROM openjdk:17`을 보더라도 새로 작성할 때는 배포판 이미지를 쓴다.

#### 태그(Tag)를 통한 버전 명시

이미지 이름 뒤에 콜론(`:`)과 **태그**를 붙여 필요한 자바 버전과 환경을 지정한다. 단순히 운영체제만 있는 이미지를 골라 자바를 직접 설치할 수도 있지만, 개발 생산성을 위해 이미 Java Development Kit이 준비된 `eclipse-temurin:21-jdk`와 같은 태그 형태의 베이스 이미지를 고르는 것이 일반적이다.

### 태그(Tag) 목록 확인 및 버전이 존재하는지 확인하는 방법

원하는 이미지에 정확히 어떤 버전의 태그가 존재하는지 미리 알기는 어렵다. 기본 `docker search` 명령어로는 이미지의 태그 목록까지 바로 조회할 수 없기 때문에, 사용 가능한 태그를 파악하려면 다음과 같은 방법을 활용한다.

- **도커 허브 웹사이트 검색**: Docker Hub 공식 홈페이지에서 `eclipse-temurin`을 검색한 뒤 **Tags** 탭에 진입하면 최신 지원 버전과 태그 목록을 명확히 확인할 수 있다.
- **도커 허브 API(cURL/jq) 활용**: 터미널에서 아래와 같이 도커 허브 API를 호출하여 태그 목록을 CLI상에서 직접 조회할 수 있다.

```bash
curl -s https://registry.hub.docker.com/v2/repositories/library/eclipse-temurin/tags/ | jq -r '.results[].name'
```

> **추가 설명 — API 결과는 나눠서 온다**: 위 API는 한 번에 **10개씩만** 돌려준다(페이지 단위). 더 보려면 주소 뒤에 `?page_size=100`을 붙이고, 원하는 버전만 보려면 `?name=21-jre`처럼 이름으로 거른다. `jq`는 JSON을 다루는 도구라 Ubuntu에 기본으로 없을 수 있다(`sudo apt install jq`).
>
> ```bash
> curl -s "https://registry.hub.docker.com/v2/repositories/library/eclipse-temurin/tags/?page_size=100&name=21-jre" | jq -r '.results[].name'
> ```

확인한 태그 정보를 기반으로 이미지 이름 뒤에 콜론(`:`)과 태그를 붙여 필요한 자바 버전과 환경을 지정한다.

> **추가 설명 — eclipse-temurin 태그 읽는 법**:
>
> | 태그 | 뜻 |
> |---|---|
> | `21-jdk` | Java 21, JDK(컴파일러 포함). 빌드 단계용 |
> | `21-jre` | Java 21, JRE(실행만). 실행 단계용으로 더 가볍다 |
> | `21-jre-alpine` | 알파인 리눅스 기반이라 가장 가볍다. musl을 쓰고 `bash`가 없어 일부 라이브러리·스크립트가 안 될 수 있다 |
> | `21-jre-jammy`, `21-jre-noble` | 베이스 OS를 Ubuntu 22.04(jammy)·24.04(noble)로 명시한 것 |
> | `21` | `21-jdk`와 같다 |
> | `latest` | 태그를 생략하면 붙는 값. 최신 버전으로 계속 바뀌므로 배포용으로는 쓰지 않는다 |

## 4. Java 21 기준 Dockerfile 작성하기

이제 방금 만든 JAR 파일을 가지고 도커 상자를 만드는 레시피인 Dockerfile을 작성한다. 프로젝트의 가장 최상위 폴더 위치에 **확장자 없이** `Dockerfile`이라는 이름으로 파일을 만든다.

**도커 파일과 도커 이미지를 분리해 사용하는 이유**

Dockerfile은 몇 줄의 텍스트로만 이루어져 있어서 파일 크기가 매우 작다. 그래서 Git에 올려서 쉽게 저장하고 내용도 마음대로 고칠 수 있다. 하지만 도커 이미지는 자바 프로그램, 각종 실행 라이브러리, 필요한 파일들이 전부 들어간 완제품 형태라 용량이 몇백 메가바이트(MB) 이상으로 매우 커진다. 따라서 용량이 작은 레시피(Dockerfile)만 공유하고, 완성본(이미지)은 필요할 때마다 만들어서 쓰도록 분리하여 관리한다.

Java 21 버전을 기반으로 작동하는 스프링 부트 앱의 기본 작성 형태는 다음과 같다.

```dockerfile
# 1. Java 21 실행 환경이 갖춰진 기본 상자를 가져온다.
FROM eclipse-temurin:21-jdk

# 2. 작업할 폴더 위치를 지정한다.
WORKDIR /app

# 3. 내 컴퓨터에서 만든 JAR 파일을 도커 상자 안으로 복사한다.
COPY build/libs/*.jar app.jar

# 4. 상자가 열릴 때 백엔드 프로그램을 자동으로 실행한다.
ENTRYPOINT ["java", "-jar", "app.jar"]
```

이 레시피는 먼저 Java 21이 설치된 기본 환경을 빌려온다. 그 뒤 도커 상자 안의 `/app` 폴더로 우리가 만들어둔 JAR 파일을 `app.jar`라는 깔끔한 이름으로 복사해 가져온다. 마지막으로 도커가 작동을 시작할 때 `java -jar app.jar` 명령어를 실행하여 백엔드 서버를 띄우게 된다.

> **추가 설명 — `*.jar`가 두 개를 집으면 실패한다**: `bootJar`로 만들었다면 `build/libs`에 JAR가 하나뿐이라 괜찮다. 하지만 `./gradlew build`로 만들었다면 plain JAR까지 두 개가 걸려 `COPY`가 "여러 파일을 복사하려면 목적지가 디렉터리여야 한다"는 오류를 낸다. 해결 방법은 셋 중 하나다.
> - 파일 이름을 정확히 쓴다: `COPY build/libs/security-0.0.1-SNAPSHOT.jar app.jar`
> - `build.gradle`에서 plain JAR를 끈다: `jar { enabled = false }`
> - 빌드할 때 `bootJar`만 쓴다.

### ENTRYPOINT 대신 CMD를 사용한 이유

이 예시에서 ENTRYPOINT 대신 CMD를 사용한 이유는 실행 명령어 덮어쓰기(Override)의 유연성을 확보하기 위해서이다.

> 원문 바로잡기 — 바로 위 Dockerfile은 `ENTRYPOINT`로 작성되어 있고, `CMD`를 쓴 것은 7절의 멀티 스테이지 예시다. 이 소절은 **7절 예시가 CMD를 고른 이유**로 읽으면 된다.

- **ENTRYPOINT**: 컨테이너를 특정 executable(실행 파일)로 고정할 때 사용한다. `docker run` 실행 시 명령어 뒤에 전달하는 추가 인자가 ENTRYPOINT에 지정된 명령어의 매개변수(argument)로 뒤에 덧붙여져 실행된다. 명령 자체를 바꾸기 위해서는 `--entrypoint` 플래그를 별도로 지정해야 하므로 컨테이너의 핵심 역할을 고정하고 안전하게 유지하는 데 유리하다.
- **CMD**: 컨테이너가 실행될 때 기본적으로 수행할 명령어나 ENTRYPOINT에 전달할 기본 인자를 정의한다. 하지만 `docker run` 실행 시 뒤에 다른 명령어를 입력하면, 기존에 설정된 CMD 내용 전체가 사용자가 전달한 명령어와 인자로 완전히 대체된다.

두 명령어의 주요 차이점과 동작 방식을 비교하면 다음과 같다.

| 구분 | ENTRYPOINT | CMD |
|---|---|---|
| 주요 목적 | 컨테이너를 실행 파일처럼 고정하여 구동 | 컨테이너의 기본 실행 명령 및 인자 설정 |
| `docker run <cmd>` 실행 시 | 전달된 `<cmd>`가 매개변수로 뒤에 덧붙음 | 전달된 `<cmd>`가 기존 CMD를 완전히 대체함 |
| 명령 덮어쓰기 방법 | `docker run --entrypoint <new_cmd>` 사용 | `docker run <image> <new_cmd>` 형태 사용 |

스프링 부트 애플리케이션을 운용할 때 단순히 애플리케이션을 띄우는 목적 외에도, 다양한 환경 변수나 JVM 옵션을 임시로 변경하여 테스트해야 하는 상황이 자주 발생한다.

예를 들어 디버깅이나 내부 문제 해결을 위해 애플리케이션 대신 컨테이너 내부 쉘로 진입해야 할 때, CMD를 사용하면 다음과 같이 단일 명령으로 쉽게 전환할 수 있다.

```bash
# 기본 CMD를 무시하고 컨테이너 내부의 bash 쉘로 즉시 접속
docker run -it my-backend bash
```

또한, 힙 메모리 크기 변경이나 특정 덤프 추출 옵션 등을 임시로 적용하고자 할 때도 간편하게 인자를 교체하여 실행할 수 있다.

```bash
# 기본 CMD 대신 JVM 메모리 옵션을 추가하여 실행
docker run my-backend java -Xmx512m -jar app.jar
```

이처럼 디버깅, 성능 테스트, 운영 중 긴급 점검 등 컨테이너 내부 실행 명령을 즉각적으로 변경해야 하는 상황에서 CMD를 사용하는 것이 훨씬 더 높은 유연성을 제공한다.

> **추가 설명 — ENTRYPOINT를 써도 할 수 있는 것들**: CMD의 유연성이 꼭 필요한 것은 아니다. ENTRYPOINT로 고정해 두어도 아래처럼 같은 일을 할 수 있다.
>
> ```bash
> # 실행 중인 컨테이너에 쉘로 들어가기 (가장 많이 쓰는 방법)
> docker exec -it <컨테이너 이름> bash
>
> # ENTRYPOINT를 잠깐 바꿔서 쉘로 시작하기
> docker run -it --entrypoint bash my-backend
>
> # JVM 옵션은 환경 변수로 넘기기 — 명령을 통째로 다시 쓸 필요가 없다
> docker run -e JAVA_TOOL_OPTIONS="-Xmx512m" my-backend
>
> # 스프링 설정은 ENTRYPOINT 뒤에 인자로 덧붙이기
> docker run my-backend --spring.profiles.active=prod
> ```
>
> 그래서 실무에서는 **실행 명령은 ENTRYPOINT로 고정하고, 바꿀 만한 기본 인자만 CMD로** 두는 조합이 많다. 어느 쪽이든 **배열 형식**(`["java", "-jar", "app.jar"]`)으로 써야 `java`가 컨테이너의 1번 프로세스가 되어 `docker stop`의 종료 신호를 바로 받고 스프링이 정상 종료된다. 문자열 형식(`CMD java -jar app.jar`)은 `sh -c`로 감싸져 실행되어 신호가 앱까지 전달되지 않을 수 있다.
>
> 또 `eclipse-temurin` 이미지는 Ubuntu 기반이라 `bash`가 있지만, **알파인 이미지에는 `bash`가 없으므로** `sh`로 들어간다.

## 5. 도커 이미지 빌드하고 컨테이너 실행해보기

레시피를 완성했으니 실제로 도커 이미지를 구워내고 컨테이너로 띄워서 제대로 작동하는지 시험한다.

### 5-1. 이미지 만들기 (빌드)

터미널에서 아래 명령어를 입력하여 `my-backend`라는 이름의 도커 이미지를 만든다. 맨 뒤의 점(`.`)은 현재 폴더에 있는 Dockerfile을 사용하겠다는 뜻이다.

```bash
docker build -t my-backend .
```

> **추가 설명 — 마지막 `.`의 정확한 뜻**: `.`은 **빌드 컨텍스트**, 즉 "빌드에 쓸 파일들이 있는 폴더"다. 도커는 이 폴더 전체를 도커 엔진으로 보내고, Dockerfile의 `COPY`는 이 폴더를 기준으로 파일을 찾는다. Dockerfile도 기본으로 이 폴더에서 찾기 때문에 "현재 폴더의 Dockerfile"처럼 보이는 것이다. 그래서 `COPY ../other.jar`처럼 컨텍스트 밖의 파일은 복사할 수 없다. 컨텍스트에 `build/`, `.git/`, `node_modules/` 같은 큰 폴더가 있으면 빌드가 느려지므로 `.dockerignore`로 뺀다.
>
> ```
> # .dockerignore
> .git
> .gradle
> build
> .idea
> ```

`docker build` 명령에서 자주 사용하는 주요 옵션은 다음과 같다.

- `-t, --tag`: 빌드할 이미지의 이름과 태그(예: `my-backend:v1.0`)를 지정한다.
- `-f, --file`: 기본 파일명인 Dockerfile 대신 다른 위치나 이름의 도커파일 경로를 직접 지정한다. (예: `-f ./docker/Dockerfile.dev`)
- `--build-arg`: Dockerfile 내부의 ARG 변수에 전달할 빌드 시점의 환경 변수 값을 설정한다. (예: `--build-arg VERSION=1.0`)
- `--no-cache`: 이전에 빌드할 때 생성된 캐시를 사용하지 않고 모든 단계를 처음부터 다시 빌드한다.
- `--platform`: 다중 아키텍처 환경에서 빌드할 대상 플랫폼을 지정한다. (예: `--platform linux/amd64`)

> **추가 설명 — `--platform`이 필요한 경우**: 애플 실리콘 맥(M1~M4)에서 빌드하면 기본으로 **ARM용(`linux/arm64`) 이미지**가 만들어진다. 대부분의 클라우드 서버는 인텔·AMD(`linux/amd64`)라서 그대로 올리면 `exec format error`로 실행되지 않는다. 맥에서 서버용 이미지를 만들 때 `--platform linux/amd64`를 붙인다. 윈도우·WSL은 보통 amd64라 신경 쓸 일이 적다.
>
> 태그를 생략하면 `my-backend:latest`가 된다. 같은 이름으로 다시 빌드하면 이름이 새 이미지로 옮겨 가고, 예전 이미지는 이름이 없는 `<none>` 이미지로 남는다(6절의 dangling 이미지).

### 5-2. 생성된 도커 이미지 확인하기

빌드가 완료된 도커 이미지는 일반적인 파일처럼 특정 폴더에 독립된 단일 파일 형태로 노출되지 않고, **도커 데몬(Docker Daemon)이 관리하는 내부 저장소 영역**에 저장된다.

생성된 이미지 목록과 용량, 이미지 ID 등의 정보는 터미널에서 다음 명령어로 확인할 수 있다.

```bash
docker images
```

특정 이미지(`my-backend`)만 조회하려면 다음과 같이 검색한다.

```bash
docker images my-backend
```

운영체제별 실제 이미지가 저장되는 도커 내부 물리 경로 예시는 다음과 같다. (직접 해당 경로의 파일을 수정하거나 접근하는 것은 권장되지 않으며, docker CLI 명령어를 통해 조회하고 관리해야 한다.)

- Linux: `/var/lib/docker/`
- macOS: `~/Library/Containers/com.docker.docker/Data/vms/0/data/Docker.raw` (가상 머신 디스크 이미지 내부)
- Windows (WSL2): `\\wsl$\docker-desktop-data\version-pack-data\community\docker\`

> **추가 설명 — 우리 환경의 저장 위치**: 위 Windows 경로는 **Docker Desktop**을 쓸 때의 경로다(버전에 따라 위치가 바뀌기도 한다). 수업처럼 Docker Desktop 없이 **WSL의 Ubuntu 안에 도커 엔진을 직접 설치**했다면, 도커는 그냥 리눅스에서 도는 것이므로 Ubuntu 안의 `/var/lib/docker/`에 저장된다. 이미지들이 차지하는 용량은 경로를 뒤지기보다 `docker system df`로 확인한다.
>
> ```bash
> docker system df       # 이미지·컨테이너·볼륨·빌드 캐시가 쓰는 디스크 용량
> docker history my-backend   # 이미지의 레이어별 크기 (어느 단계가 무거운지)
> ```

### 5-3. 컨테이너 실행하기

이미지가 다 만들어졌으면, 이를 실제 실행 상태인 **컨테이너**로 구동시킨다.

```bash
docker run -p 8080:8080 my-backend
```

여기서 `-p 8080:8080` 옵션은 **내 컴퓨터의 8080번 포트로 들어오는 통신 요청을 도커 상자 안의 8080번 포트로 전달**해 주겠다는 문지기 역할을 설정하는 것이다.

```
[내 컴퓨터(호스트 PC)]                               [도커 상자(컨테이너)]
  8080번 포트(외부)  ──── 문지기(-p 8080:8080) ────▶  8080번 포트(내부)  ──▶ 웹 애플리케이션
                      "이 요청은 상자 안의 8080으로!"
```

`-p 호스트포트:컨테이너포트` 순서다. 앞 숫자가 **내가 브라우저로 접속할 포트**, 뒤 숫자가 **앱이 컨테이너 안에서 실제로 열고 있는 포트**다. `-p 3000:8080`이라면 앱은 안에서 8080으로 떠 있고, 밖에서는 `localhost:3000`으로 들어간다. `-p`가 없으면 앱이 정상적으로 떠도 컨테이너 밖에서는 접속할 수 없다.

실행 후 웹 브라우저를 열고 `http://localhost:8080`으로 접속했을 때 앱의 응답이나 API 결과가 잘 돌아온다면 백엔드 도커화에 성공한 것이다.

**docker run과 docker start의 차이점**

- **docker run**: 이미지를 바탕으로 새로운 컨테이너를 생성(create)하고 동시에 실행(start)하는 명령어이다. 즉, 상자를 처음 만들어서 개봉하는 과정이다.
- **docker start**: 이미 만들어졌다가 중지된 기존 컨테이너를 다시 재실행하는 명령어이다. 이미 존재하는 상자의 스위치를 다시 켜는 것과 같다.

> **추가 설명 — 실행할 때 자주 쓰는 옵션과 명령**:
>
> ```bash
> docker run -d -p 8080:8080 --name backend my-backend   # -d: 백그라운드, --name: 컨테이너 이름
> docker ps          # 실행 중인 컨테이너 (-a: 멈춘 것까지)
> docker logs -f backend
> docker stop backend
> docker start backend
> docker rm backend  # 컨테이너 삭제 (실행 중이면 -f)
> ```
>
> `docker run`은 실행할 때마다 **새 컨테이너를 만든다.** 이름 없이 여러 번 실행하면 멈춘 컨테이너가 계속 쌓이니, 한 번 만든 컨테이너는 `stop`/`start`로 다시 쓰거나 `--rm` 옵션(멈추면 자동 삭제)을 붙인다.

## 6. 도커 이미지 삭제 및 정리하기

더 이상 사용하지 않는 이미지를 삭제하거나 디스크 공간을 확보하려면 다음 명령어들을 활용한다.

### 특정 이미지 삭제하기 (`docker rmi`)

이미지 이름(태그)이나 이미지 ID를 지정하여 불필요한 이미지를 삭제한다.

```bash
docker rmi my-backend
```

해당 이미지를 기반으로 생성된 컨테이너가 존재할 경우 삭제가 거부될 수 있다. 이 경우 컨테이너를 먼저 삭제하거나 `-f` 옵션을 주어 강제로 삭제해야 한다.

```bash
docker rmi -f my-backend
```

> **추가 설명 — 강제 삭제보다 컨테이너부터 정리하기**: `-f`로 지우면 이미지의 이름만 떼어지고, 그 이미지를 쓰는 컨테이너가 남아 있는 한 실제 데이터는 디스크에 그대로 남는다(이름 없는 이미지가 된다). 깔끔하게 지우려면 순서대로 정리한다.
>
> ```bash
> docker ps -a --filter ancestor=my-backend   # 이 이미지로 만든 컨테이너 찾기
> docker rm <컨테이너 ID>                      # 컨테이너 먼저 삭제
> docker rmi my-backend                       # 그 다음 이미지 삭제
> ```

### 사용하지 않는 쓰레기 이미지 일괄 정리하기 (`docker image prune`)

빌드 과정에서 실패하거나 다른 빌드로 인해 이름이 사라져 태그가 `<none>`으로 표시되는 일명 **'dangling 이미지'**만 골라 한번에 삭제한다.

```bash
docker image prune
```

컨테이너에서 현재 사용하지 않는 모든 이미지를 한꺼번에 정리하려면 `-a` 옵션을 추가한다.

```bash
docker image prune -a
```

> **추가 설명 — 정리 범위별 명령**:
>
> | 명령 | 지우는 것 |
> |---|---|
> | `docker container prune` | 멈춘 컨테이너 전부 |
> | `docker image prune` | 이름 없는(dangling) 이미지 |
> | `docker image prune -a` | 컨테이너가 쓰지 않는 이미지 전부(다시 받아야 하는 베이스 이미지 포함) |
> | `docker builder prune` | 빌드 캐시 |
> | `docker system prune` | 위의 멈춘 컨테이너·dangling 이미지·네트워크·빌드 캐시를 한 번에 |
>
> `docker volume prune`·`docker system prune --volumes`는 **볼륨까지** 지운다. DB 데이터가 볼륨에 있다면 함께 날아가므로 조심한다.

## 7. 빌드 테스트도 포함된 도커 파일

앞서 살펴본 방식은 내 컴퓨터(호스트)에서 먼저 `./gradlew bootJar`를 실행해 JAR 파일을 만든 뒤 이를 이미지에 복사하는 형태였다. 이 방식은 호스트의 자바 환경에 영향을 받거나 빌드 과정이 개발자의 환경에 의존하게 된다는 단점이 있다.

그 외에도 현재 로컬 환경에서 빌드한 결과물이 서버 환경에서 실행되지 않을 가능성도 있다. 왜냐하면 빌드 환경(내 컴퓨터)과 실행 환경(도커 컨테이너)이 완전히 동일하지는 않기 때문이다. 이런 문제를 해결하려면 **멀티 스테이지 빌드(Multi-stage build)** 방식을 사용할 수 있다.

**멀티 스테이지 빌드(Multi-stage build) 방식이란?**

하나의 Dockerfile 안에서 여러 개의 `FROM` 절을 사용하여 빌드 단계를 나눌 수 있는 기능이다. 소스 코드 컴파일, 라이브러리 다운로드, 실행 파일 생성 등의 작업을 수행하는 **'빌드 단계(Build Stage)'**와, 이렇게 만들어진 최종 결과물(JAR 파일 등)만 가져와 구동하는 **'실행 단계(Runtime Stage)'**를 명확히 분리하여 구성하는 방식을 말한다.

멀티 스테이지 빌드 방식을 사용하면 개발자의 컴퓨터에 자바나 Gradle이 설치되어 있지 않아도 도커 안에서 빌드부터 실행 파일 생성까지 모든 과정을 완결할 수 있다. 빌드 환경(JDK)과 실행 환경(JRE)을 분리함으로써 소스 코드나 빌드 도구가 최종 이미지에 남지 않아 보안성이 높아지고 이미지 용량이 크게 줄어든다는 강력한 장점이 있다.

Java 21 버전을 기반으로 멀티 스테이지 빌드 방식을 적용한 Dockerfile 작성 형태는 다음과 같다.

```dockerfile
# 1단계: Gradle로 프로젝트 빌드
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
COPY . .
RUN ./gradlew build -x test --no-daemon

# 2단계: 실행 환경 (JRE만 포함해 이미지를 가볍게)
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /app/build/libs/*.jar app.jar

EXPOSE 8080
CMD ["java", "-jar", "app.jar"]
```

이 레시피의 각 설정 항목을 상세히 살펴보면 다음과 같다.

**1단계: 빌드 환경 구성 및 JAR 파일 생성 (`AS build`)**

- `FROM eclipse-temurin:21-jdk AS build`: Java 21 JDK가 설치된 베이스 이미지를 불러오고, 이 빌드 단계를 `build`라는 이름의 별칭으로 지정한다.
- `WORKDIR /app`: 이후 명령어들이 실행될 컨테이너 내부의 작업 디렉토리를 `/app`으로 설정한다.
- `COPY . .`: 현재 프로젝트의 모든 소스 코드와 설정 파일을 컨테이너 내부의 `/app` 경로로 복사한다.
- `RUN ./gradlew build -x test --no-daemon`: 테스트 실행을 제외(`-x test`)하고 데몬 프로세스 없이(`--no-daemon`) Gradle 빌드를 수행하여 실행 가능한 JAR 파일을 생성한다.

**2단계: 최적화된 실행 환경 구성**

- `FROM eclipse-temurin:21-jre`: 컴파일 도구(JDK)가 제외되고 자바 실행 환경만 포함된 가벼운 JRE 이미지를 새 베이스 이미지로 지정한다. 이 시점에서 1단계의 빌드 전용 용량은 최종 이미지에서 모두 떨어져 나간다.
- `WORKDIR /app`: 실행 단계에서 사용할 컨테이너 내 작업 디렉토리를 `/app`으로 재설정한다.
- `COPY --from=build /app/build/libs/*.jar app.jar`: 1단계(`build`)에서 생성된 `build/libs/*.jar` 파일을 가져와 현재 스테이지의 `/app/app.jar`라는 단일 파일로 복사한다.

**컨테이너 실행 설정**

- `EXPOSE 8080`: 해당 컨테이너가 외부와 통신할 때 8080 포트를 사용한다는 점을 명시한다.
- `CMD ["java", "-jar", "app.jar"]`: 컨테이너가 시작될 때 `app.jar`를 실행하여 백엔드 애플리케이션을 구동한다.

> 원문 바로잡기 — 1단계에서 `./gradlew build`를 쓰면 스프링 부트 3는 `build/libs`에 **실행용 JAR와 `-plain.jar` 두 개**를 만든다. 그러면 2단계의 `COPY --from=build /app/build/libs/*.jar app.jar`가 두 파일을 집어 빌드가 실패한다. 1단계를 `RUN ./gradlew bootJar --no-daemon`으로 바꾸거나(테스트도 돌지 않으므로 `-x test`도 필요 없다), `build.gradle`에 `jar { enabled = false }`를 넣는다.

> **추가 설명 — 이 Dockerfile을 실제로 돌릴 때 막히는 곳**:
> - **`./gradlew: Permission denied`**: 윈도우에서 만들었거나 Git이 실행 권한을 잃으면 `gradlew`를 실행할 수 없다. `RUN chmod +x gradlew && ./gradlew bootJar --no-daemon`으로 쓴다.
> - **`/bin/sh^M: bad interpreter`**: `gradlew`의 줄바꿈이 윈도우식(CRLF)이면 리눅스에서 실행되지 않는다. 파일을 LF로 저장하거나 `.gitattributes`에 `gradlew text eol=lf`를 둔다.
> - **매번 의존성을 처음부터 받는다**: `COPY . .`로 소스를 통째로 먼저 넣으면, 코드 한 줄만 바꿔도 그 뒤 레이어 캐시가 깨져 Gradle이 라이브러리를 매번 다시 받는다. 잘 바뀌지 않는 **빌드 설정 파일을 먼저 복사해 의존성만 받아 두고**, 그 다음 소스를 복사하면 빌드가 훨씬 빨라진다.
>
> ```dockerfile
> FROM eclipse-temurin:21-jdk AS build
> WORKDIR /app
> COPY gradlew settings.gradle build.gradle ./
> COPY gradle gradle
> RUN chmod +x gradlew && ./gradlew dependencies --no-daemon   # 이 레이어는 build.gradle이 바뀔 때만 다시 실행
> COPY src src
> RUN ./gradlew bootJar --no-daemon
>
> FROM eclipse-temurin:21-jre
> WORKDIR /app
> COPY --from=build /app/build/libs/*.jar app.jar
> EXPOSE 8080
> ENTRYPOINT ["java", "-jar", "app.jar"]
> ```
>
> - **테스트를 빼는 이유**: 빌드 단계에는 DB 컨테이너가 없어서, DB에 연결하는 테스트가 있으면 빌드가 실패한다. 그래서 `-x test`나 `bootJar`로 테스트를 빼고, 테스트는 CI 같은 별도 단계에서 돌린다. 제목의 "빌드 테스트도 포함된"은 **빌드까지 도커 안에서 한다**는 뜻으로 보면 된다.

## 8. 도커 파일에 사용할 수 있는 명령어들

Dockerfile을 작성할 때 자주 사용하는 주요 지시어와 역할은 다음과 같다.

**FROM**: 생성할 이미지의 기반이 되는 베이스 이미지를 지정한다. Dockerfile은 반드시 `FROM` 명령어(또는 `ARG`)로 시작해야 한다.

```dockerfile
FROM eclipse-temurin:21-jdk
```

**WORKDIR**: 이후 실행될 명령어들이 수행될 컨테이너 내부의 작업 디렉토리를 설정한다. 해당 경로가 없으면 자동으로 생성한다.

```dockerfile
WORKDIR /app
```

**COPY**: 호스트 컴퓨터의 파일이나 디렉토리를 컨테이너 내부의 지정한 경로로 복사한다.

```dockerfile
COPY build/libs/*.jar app.jar
```

**ADD**: COPY와 유사하게 파일의 복사를 수행하지만, URL을 통한 원격 파일 다운로드 및 `.tar` 형태의 압축 파일 자동 해제 기능을 추가로 제공한다. 단순 파일 복사 시에는 COPY 사용이 권장된다.

```dockerfile
ADD sample.tar.gz /app/
```

**RUN**: 이미지를 빌드하는 동안 컨테이너 내부에서 쉘 명령어를 실행하여 새로운 레이어를 생성한다. 주로 필요한 패키지를 설치하거나 소스 코드를 빌드할 때 사용한다.

```dockerfile
RUN ./gradlew build -x test
```

**ENV**: 컨테이너 내부에서 사용할 환경 변수를 설정한다. 설정된 환경 변수는 빌드 단계뿐만 아니라 컨테이너 실행 시에도 유효하다.

```dockerfile
ENV APP_ENV=production
```

**ARG**: 이미지 빌드 시점에만 사용되는 변수를 정의한다. `docker build` 실행 시 `--build-arg` 옵션을 통해 값을 전달할 수 있다.

```dockerfile
ARG VERSION=1.0.0
```

**EXPOSE**: 컨테이너가 런타임에 수신할 포트를 지정하여 문서화한다. 실제 호스트의 포트와 매핑하려면 `docker run -p` 옵션을 별도로 사용해야 한다.

```dockerfile
EXPOSE 8080
```

**VOLUME**: 컨테이너 내부 데이터를 호스트의 디렉토리나 도커 볼륨에 지속적으로 저장할 수 있도록 볼륨 마운트 포인트를 생성한다.

```dockerfile
VOLUME /tmp
```

**ENTRYPOINT**: 컨테이너가 시작될 때 반드시 실행할 기본 명령어를 설정한다. 컨테이너를 실행 파일 형태로 고정하여 구동할 때 사용한다.

```dockerfile
ENTRYPOINT ["java", "-jar", "app.jar"]
```

**CMD**: 컨테이너가 실행될 때 수행할 기본 명령어나 ENTRYPOINT에 전달할 인자를 정의한다. `docker run` 실행 시 전달되는 명령어 인자에 의해 쉽게 덮어씌워질 수 있다.

```dockerfile
CMD ["java", "-jar", "app.jar"]
```

> **추가 설명 — 한눈에 보는 실행 시점**:
>
> | 명령 | 언제 동작하나 | 이미지에 레이어를 만드나 |
> |---|---|---|
> | `FROM`, `WORKDIR`, `COPY`, `ADD`, `RUN` | **빌드할 때**(`docker build`) | `COPY`·`ADD`·`RUN`은 레이어를 만든다 |
> | `ARG` | 빌드할 때만. 컨테이너 안에는 남지 않는다 | 아니오 |
> | `ENV` | 빌드할 때와 **실행할 때 모두** | 아니오(설정 정보로 저장) |
> | `EXPOSE`, `VOLUME` | 실행할 때 참고하는 표시 | 아니오 |
> | `ENTRYPOINT`, `CMD` | **실행할 때**(`docker run`). 여러 번 쓰면 마지막 것만 유효 | 아니오 |
>
> `RUN`과 `CMD`를 헷갈리기 쉽다. `RUN`은 이미지를 **만드는 동안** 한 번 실행되고 결과가 이미지에 저장된다. `CMD`는 이미지를 만들 때는 아무것도 하지 않고, 컨테이너가 **켜질 때마다** 실행된다.
>
> `ARG`에는 비밀번호를 넣지 않는다. 빌드 기록(`docker history`)에 값이 남는다. DB 비밀번호 같은 값은 이미지에 굽지 않고, 실행할 때 `docker run -e`나 Compose의 `environment`로 넘긴다.

## 9. 주의할 점과 다음 단계 준비하기

### 자바 버전 일치시키기

내 컴퓨터에서 프로젝트를 만들 때 사용한 자바 버전과 Dockerfile에 적은 자바 버전이 다르면 실행 시 오류가 발생한다. 이번 설정처럼 Java 21 환경에서 빌드했다면 Dockerfile의 베이스 이미지도 똑같이 Java 21(`eclipse-temurin:21-jdk` 등)을 사용해야 한다.

> **추가 설명 — 어느 쪽이 다르면 오류인가**: 자바는 **아래 버전과 호환**된다. Java 17로 빌드한 JAR는 Java 21에서도 대부분 잘 돌지만, Java 21로 빌드한 JAR를 Java 17에서 실행하면 `UnsupportedClassVersionError`(class file version 65.0 / 61.0)로 바로 실패한다. 1절 그림의 "Java 17(버전 불일치)"가 바로 이 경우다. 불필요한 위험을 줄이려면 `build.gradle`의 `java { toolchain { languageVersion = JavaLanguageVersion.of(21) } }`와 베이스 이미지 태그를 **같은 버전으로 맞춰 두는 것**이 가장 안전하다.

### 내장 DB 사용 시 데이터 손실 주의

스프링 부트 내부의 H2 같은 내장 데이터베이스를 사용하고 있는 경우, 도커 컨테이너를 종료하면 저장이 안 되고 데이터가 통째로 사라질 수 있다. 중요한 데이터는 별도의 외부 데이터베이스 컨테이너를 연결해서 관리하는 것이 안전하다.

> **추가 설명 — 언제 사라지나**:
>
> | 경우 | 앱(컨테이너) 재시작 | 컨테이너 삭제(`docker rm`) |
> |---|---|---|
> | H2 메모리 모드(`jdbc:h2:mem:`) | **사라진다**(도커와 상관없이 앱이 내려가면 사라짐) | 사라진다 |
> | H2 파일 모드, 컨테이너 안 경로 | 남는다(컨테이너 쓰기 레이어에 있음) | **사라진다** |
> | 파일·DB 데이터를 **볼륨**에 저장 | 남는다 | **남는다** |
>
> 핵심은 "컨테이너 안에 쓴 것은 컨테이너와 운명을 같이한다"는 것이다. 새 버전을 배포할 때는 보통 컨테이너를 지우고 새로 만들기 때문에, 지켜야 하는 데이터는 반드시 볼륨이나 별도의 DB 컨테이너(그 DB도 볼륨 사용)에 둔다.

### 다음 단계: 도커 컴포즈(Docker Compose)

백엔드 앱 하나만 띄우는 것은 성공했다. 하지만 실제 서비스를 만들 때는 백엔드 외에도 프론트엔드 웹 페이지와 데이터베이스(MySQL, PostgreSQL 등)를 함께 구동해야 한다. 다음 과정에서는 여러 개의 도커 상자를 명령어 한 줄로 한꺼번에 묶어서 띄우고 서로 통신하게 만드는 도커 컴포즈 환경을 구축한다.

> **추가 설명 — 컨테이너끼리 연결할 때 `localhost`를 쓰지 않는다**: 백엔드 컨테이너 안에서 `localhost`는 **백엔드 컨테이너 자신**이다. 그래서 `spring.datasource.url=jdbc:postgresql://localhost:5432/...`로 두면 DB 컨테이너를 찾지 못한다. Compose로 묶으면 같은 네트워크 안에서 **서비스 이름**(예: `db`)이 주소가 되므로 `jdbc:postgresql://db:5432/...`처럼 쓴다. 이 값은 이미지에 굽지 말고 `SPRING_DATASOURCE_URL` 같은 환경 변수로 넘기면, 같은 이미지를 로컬·서버에서 그대로 쓸 수 있다.
