# AOP와 프록시 — 곁다리 코드를 호출 흐름 밖으로 빼는 방법

AOP가 무엇을 해결하려는 방법론인지, 그리고 그 방법을 **프록시**로 어떻게 구현하는지 정리한다. 계산기 예제로 곁다리 코드를 직접 박아 넣는 방식의 불편함을 확인하고, 프록시를 쓰기 위한 준비(인터페이스)까지 해본다.

## 1. AOP는 도구를 만드는 사람의 방법론이다

### 두 종류의 개발자

개발자는 크게 두 종류로 볼 수 있다.

| 구분 | 예 | 주로 쓰는 기술 |
|---|---|---|
| **플랫폼을 만드는 개발자** | 스프링, JPA(Hibernate), 테스트 도구를 만드는 사람 | 리플렉션 API, AOP, 프록시 |
| **플랫폼 위에서 응용 프로그램을 만드는 개발자** | 스프링으로 쇼핑몰, 카페 주문 앱, 사내 업무 시스템 같은 서비스를 만드는 사람 | 플랫폼이 제공하는 기능(`@Transactional` 등) |

**리플렉션 API**는 클래스 정보(필드, 메서드, 어노테이션)를 실행 중에 들여다보는 기능이다. 이 정보를 꺼내 **자동화 도구**를 만든다. 클래스 정보로 SQL을 만들어 주거나(JPA), 객체를 만들어 조립해 주거나(스프링 IoC), `@Transactional`을 읽고 트랜잭션을 걸어 주는 것들이 그 예다.

그래서 응용 프로그램만 만드는 개발자는 리플렉션 API를 쓸 일이 거의 없다. "리플렉션이 뭐냐"고 묻는 개발자도 있는데, 그것 없이도 잘 개발해 왔고 몰라도 문제가 없었기 때문이다.

> 강의 중 리플렉션으로 만든 도구의 예로 "컴파일러"가 나왔는데, 자바 컴파일러(javac)는 리플렉션 API가 아니라 소스 코드를 직접 분석해 동작한다. 리플렉션은 **이미 컴파일되어 실행 중인** 클래스를 들여다보는 기능이므로, 스프링·JPA·JUnit처럼 **실행 시점에** 동작하는 도구들이 주로 쓴다.

### 필요가 먼저, 기술은 나중

AOP도 마찬가지다. 응용 프로그램을 만들면서 AOP를 직접 쓸 일은 많지 않다. 도구를 만드는 사람이 쓰는 방법론이다.

- 처음에는 응용 프로그램을 만드는 도구를 가져다 쓴다.
- 경력이 쌓이다 보면 "이 도구는 왜 이렇게 만들었지? 버전이 올라갈수록 내가 원하는 것과 멀어지네. **이건 내가 만들어야겠다**"는 판단이 서는 때가 온다.
- 그때 리플렉션 API와 AOP를 다시 깊게 공부해서 "이 클래스는 이렇게 변환할까? 이건 프록시로 만들까?"를 고민하게 된다.

반대로, 만들 것에 대한 비전 없이 "리플렉션을 알면 고급 개발자래", "AOP가 중요하대"라는 이유로 파고드는 것은 공허하다. "그걸로 뭘 만들 건데?"에 답할 수 없기 때문이다. 지금은 **AOP가 무엇인지, `@Transactional`이 AOP로 어떻게 한 줄이 되었는지**까지만 이해하고 간다.

## 2. Aspect — 사용자가 아닌 역할자의 관점

- **주 업무 로직**은 **사용자(고객)**가 원하는 업무를 구현하는 코드다.
- 그 주 업무를 만들다 보면 **개발자, 운영자** 같은 다른 역할자들이 필요로 하는 코드가 주 업무를 둘러싸며 붙는다. 사용자는 그런 코드가 있는지도 모른다. 사용자는 "덧셈·뺄셈을 해 달라"고 했을 뿐이다.

이렇게 **다른 관점을 가진 역할자에 의해 만들어지는 코드**를 **Aspect(관점)**라고 한다. 엄밀히 보면 주 업무도 사용자의 관점이지만, 그것은 관점이라 부르지 않고 주 업무 바깥의 관점만 Aspect라고 한다.

> **Aspect-Oriented를 "관점 지향"이라고 번역하면** "관점을 지향해서 만들어야 한다"는 느낌이 들어 의미가 잘 맞지 않는다. AOP는 "**이 별도의 관점 코드를 어떻게 관리하는 게 바람직한가**"에 대한 방법론이라고 이해하면 된다.

## 3. Core Concern과 Cross-cutting Concern

| 용어 | 뜻 | 예 |
|---|---|---|
| **Core Concern** (주 관심사, Primary Concern) | 사용자가 요구한 관심사 | 덧셈, 주문하기, 메뉴 등록 |
| **Cross-cutting Concern** (횡단 관심사) | 주 관심사가 아닌, 다른 역할자의 관심사 | 로그 처리, 실행 시간 측정, 보안 처리, 트랜잭션 처리 |

> 같은 개념을 자료마다 다르게 부른다. Core Concern은 **핵심 관심사·핵심 기능·주 업무**, Cross-cutting Concern은 **횡단 관심사·부가 기능·공통 기능·곁다리 업무**라고도 한다. 스프링 관련 책과 문서에서는 "핵심 기능 / 부가 기능"이라는 표현을 많이 쓴다.

클래스 안의 메서드 세 개가 각각 얼마나 걸리는지 재거나, 호출 순서를 확인하려고 로그를 찍으려면 **모든 메서드의 앞뒤에** 같은 코드를 꽂아야 한다.

과거에는 실제로 이렇게 했다. 팀장이 "로그 한번 출력해 보자"고 한마디 하면, 말단 직원은 코드를 다 열어서 붙여야 했다. 창의적이지도 즐겁지도 않은 단순 노가다다. 그리고 테스트가 끝나면 다시 다 떼어내야 한다.

## 4. AOP의 아이디어 — 호출 흐름을 바꾼다

"그걸 꼭 그 메서드 코드 **안에** 넣어야만 로그를 출력할 수 있는 거야? 아니잖아."

곁다리 코드가 물리적으로 메서드 안에 있어야 하는 것이 아니다. **실행 순서**만 같으면 된다.

1. 메서드들의 앞뒤에 붙어 있던 곁다리 코드를 **잘라내서 밖으로** 뺀다.
2. 그 곁다리 코드를 **한 곳**(Proxy)에 둔다.
3. 사용자가 핵심 객체를 **직접 호출하지 않고**, 곁다리 객체를 **거쳐서** 호출하게 한다.

```
[이전]  클라이언트 → 핵심 메서드( 곁다리 + 주 업무 + 곁다리 )

[AOP]   클라이언트 → Proxy( 곁다리 앞 → 핵심 메서드 호출 → 곁다리 뒤 ) → 클라이언트
                              │
                              └→ 핵심 메서드( 주 업무만 )
```

호출되는 순서는 이전과 **똑같다.** 곁다리 앞 → 주 업무 → 곁다리 뒤. 그런데 곁다리 코드는 **한 곳에만** 있고, 어떤 메서드를 호출하든 이 곳을 거치므로 모두 로그가 찍힌다.

**왜 "Cross-cutting"인가**: 프로그램의 흐름은 위에서 아래로(수직) 흘러가는데, 곁다리 코드는 그 흐름을 **가로질러(cross) 잘라낸(cutting)** 관심사이기 때문이다. Core Concern이 아닌, 개발자·운영자의 관심사를 잘라낸 것이다.

### 두 가지 방법 비교

| | 방법 1: 코드에 직접 박기 | 방법 2: AOP (밖으로 빼기) |
|---|---|---|
| 곁다리 코드 위치 | 모든 메서드 안에 복사 | 한 곳(Proxy)에만 |
| 넣을 때 | 복사·붙여넣기 수십 번 | 한 번 작성 |
| 뺄 때 | 하나라도 빠뜨리면 안 되니 전부 찾아서 삭제 | 거쳐 가지 않게만 하면 끝 |
| 소스 코드 | 반드시 있어야 함 | **없어도 됨** — 이미 운영 중인 코드를 열지 않고 붙일 수 있다 |

## 5. 걸림돌 — 호출하는 쪽 코드를 바꿔야 하지 않나?

아이디어는 좋은데 걸림돌이 하나 있다. 컨트롤러가 서비스를 직접 호출하다가 이제 Proxy를 거쳐 호출해야 한다면, **컨트롤러 코드를 고쳐야** 하는 것 아닌가? 로그 하나 찍자고 코드를 수정해서 다시 배포해야 하나?

### 스프링 DI가 해결한다

스프링 DI에서 객체를 사용하는 쪽은 IoC 컨테이너에서 꺼내 쓸 뿐, 꺼낸 것이 **어떤 구현체인지 모른다.** 대부분 **인터페이스**로 참조하기 때문이다.

예를 들어 JPA 리포지토리를 생각해 보자. 우리는 `MenuRepository` **인터페이스만** 정의했고, 그것을 구현한 클래스를 만든 적이 없다. 누가 구현했고 클래스 이름이 뭔지도 모르지만, 인터페이스만 맞으면 잘 갖다 썼다.

> 강의 중에는 "Hibernate의 EntityManager가 리포지토리 구현 클래스를 만든다"는 답이 나왔는데, 정확히는 **Spring Data JPA**가 만든다. Spring Data JPA는 애플리케이션이 시작될 때 리포지토리 인터페이스를 찾아, 실제 일을 하는 `SimpleJpaRepository` 객체를 감싼 **프록시 객체**를 자바의 동적 프록시 기능으로 만들어 컨테이너에 넣는다. 클래스 이름은 `jdk.proxy2.$Proxy123`처럼 실행 중에 자동으로 붙는다. Hibernate의 `EntityManager`는 `SimpleJpaRepository`가 **안에서** 실제 DB 작업을 할 때 쓰는 도구다. 즉 우리는 매일 프록시를 쓰고 있었다.

같은 원리로, 원래 서비스 대신 **같은 인터페이스를 흉내 낸 객체**를 컨테이너에 슬쩍 넣으면, 사용하는 쪽은 차이를 모른 채 그 객체를 호출하게 된다.

> **Proxy(프록시)**: 누군가의 인터페이스를 그대로 흉내 내서 "내가 걔야, 걔가 할 수 있는 거 나도 다 할 수 있어"라고 하면서 앞에 서는 대리 객체. 호출을 받으면 곁다리 코드를 실행하고 진짜 객체에게 일을 넘긴다.

AOP를 이야기할 때 떠올려야 할 두 용어는 이것이다.

- **Cross-cutting Concern**: 곁다리로 꽂아 넣어야 할 로직이 무엇인가
- **Proxy**: 그 로직을 어디에 두는가 → 프록시에 둔다

스프링 같은 DI 도구를 쓰지 않는다면, 사용하는 쪽 코드에서 **프록시를 직접 지목해서** 쓰도록 고쳐야 한다. 그래도 곁다리 코드를 한 곳에 모으는 가치는 충분하다. 스프링을 쓰면 그 수정조차 필요 없다.

## 6. 예제 — 계산기에 시간 측정 곁다리 붙이기

`src` 아래에 `aop` 폴더를 따로 만들어(기존 프로젝트와 섞이지 않게) `App.java`와 `Calculator.java`를 둔다.

### 6-1. 곁다리 코드를 직접 박은 계산기

덧셈·뺄셈만 하는 계산기가 너무 느리다는 불만이 들어왔다. 어느 메서드가 오래 걸리는지 알아보려고 **시간 측정 코드**를 넣는다. 느린 상황을 흉내 내려고 0~1초를 랜덤하게 쉬게 했다.

```java
public class Calculator {

    public static int add(int x, int y) {
        long start = System.currentTimeMillis();            // ┐ 곁다리 (Cross-cutting)

        // ===== 주 업무 (Core) =====
        try {
            Thread.sleep((long) (Math.random() * 1000));    // 느린 상황 시뮬레이션 (0~1초)
        } catch (InterruptedException e) {}
        int result = x + y;
        // ==========================

        long end = System.currentTimeMillis();              // ┐ 곁다리
        System.out.printf("소요시간: %dms%n", end - start); // ┘
        return result;
    }

    public static int sub(int x, int y) { /* 같은 구조로 x - y */ }
}
```

```java
public class App {
    public static void main(String[] args) {
        int addResult = Calculator.add(10, 8);
        int subResult = Calculator.sub(10, 8);
        System.out.printf("add result: %d%n", addResult);
        System.out.printf("sub result: %d%n", subResult);
    }
}
```

```
소요시간: 260ms
소요시간: 956ms
add result: 18
sub result: 2
```

`Math.random()`은 0 이상 1 미만의 값을 주므로, 1000을 곱하면 0~999ms가 된다. 0.5가 나오면 500ms(0.5초)를 쉰다. 실행할 때마다 덧셈이 느릴 때도, 뺄셈이 느릴 때도 있다.

이 코드에서 `start`와 `end`/출력 부분이 **곁다리(Cross-cutting Concern)**이고 그 사이가 **주 업무(Core Concern)**이다. `Thread.sleep`은 느린 주 업무를 흉내 낸 것이라 주 업무 쪽에 포함된다.

이제 테스트가 끝났으니 측정 코드를 빼라고 한다. 혹시 또 붙이라고 할까 봐 주석으로 막는다. 한 시간 뒤 "다시 붙여 봐"라고 한다. 다시 주석을 푼다. 메서드가 두 개면 참을 만하지만, 수십 개라면 "이게 인간이 할 짓인가" 싶어진다. 곁다리 업무는 주 업무와 달리 **소모적이고 생산적이지 않은데, 반복까지** 된다. 이것을 해결하려는 것이 AOP다.

> **추가 설명 — currentTimeMillis가 돌려주는 값**: `System.currentTimeMillis()`는 `1781234567890` 같은 큰 숫자를 돌려준다. 이것은 **1970년 1월 1일 0시 0분 0초(UTC)**를 0으로 놓고 지금까지 흐른 **밀리초**다. 이 기준 시각을 **유닉스 에포크(Unix Epoch)**라고 한다. 스톱워치를 1970년에 켜 두고 지금까지 계속 올라간 값이라고 보면 된다. 1000이 1초이므로, 1000으로 나누면 초, 다시 60으로 나누면 분이 된다. 이 숫자를 직접 나눗셈해서 연·월·일을 계산할 수도 있지만, 자바는 `LocalDateTime` 같은 날짜 클래스로 변환·포맷을 제공한다.
>
> 강의에서는 이 기준점을 "서기"(서기 1년)라고 설명했지만, 서기는 연도를 세는 기준일 뿐이고 `currentTimeMillis`의 기준은 1970년이다.

> **추가 설명 — 경과 시간은 nanoTime으로**: `currentTimeMillis()`는 "지금 몇 시인지"를 위한 값이라, 컴퓨터 시계가 동기화되며 조정되면 값이 튈 수 있다. **걸린 시간**을 잴 때는 시계 조정의 영향을 받지 않는 `System.nanoTime()`을 쓰는 것이 정확하다.

### 6-2. 프록시를 쓰려면 — static 함수 묶음에서 객체로

자바의 기본 프록시 기능을 쓰려면 조건이 있다. 프록시는 원본(계산기)과 **똑같이 행동하는 것처럼** 쓰여야 하고, 사용하는 쪽은 그 행동을 약속한 **인터페이스**로 원본을 사용해야 한다.

그런데 지금 계산기는 인터페이스라는 개념과 거리가 멀다.

- `static` 메서드만 있는 `Calculator`는 **캡슐(객체)이 아니다.** 함수를 묶어 놓기만 한 **그루핑 도구**일 뿐이다. 코드 어디에도 객체를 만들거나 다룬 적이 없다. 객체 지향이 아니라 **함수 중심(절차적) 프로그래밍**이다.
- 매개변수 `x`, `y`는 상태라기보다 호출자와 함수 사이에 값을 주고받는 **통신용 값**이다.

**객체가 되려면 상태가 있어야 한다.** `x`, `y`를 멤버 변수로 옮기면, 객체가 살아 있는 동안 메서드들이 **상태를 공유**하며 일하게 된다.

```java
public class CalculatorImpl implements Calculator {   // 구현체
    private int x;
    private int y;

    public CalculatorImpl() {}                          // 기본 생성자
    public CalculatorImpl(int x, int y) {               // 상태를 받는 생성자
        this.x = x;
        this.y = y;
    }

    @Override
    public int add() {
        long start = System.currentTimeMillis();
        // ... 시뮬레이션 sleep ...
        int result = this.x + this.y;                   // 매개변수 대신 객체의 상태 사용
        long end = System.currentTimeMillis();
        System.out.printf("소요시간: %dms%n", end - start);
        return result;
    }

    @Override
    public int sub() { /* this.x - this.y */ }
}
```

> **생성자 주의**: 생성자를 하나라도 직접 만들면 자바는 기본 생성자를 **자동으로 만들어 주지 않는다.** 매개변수 있는 생성자만 만들면 `new CalculatorImpl()`은 쓸 수 없다. 이것을 이용해 "반드시 x, y를 주고 시작해라"를 **강제**할 수도 있다. 기본 생성자도 필요하면 직접 만든다.

사용하는 쪽이 구현체 클래스(`CalculatorImpl`)로 참조하면 결합도가 높다. 구현체에는 관심이 없어야 한다. 그래서 약속을 **인터페이스**로 뽑는다.

```java
public interface Calculator {   // 약속
    int add();
    int sub();
}
```

```java
public class App {
    public static void main(String[] args) {
        Calculator calc = new CalculatorImpl(10, 8);   // 인터페이스로 참조
        System.out.printf("add result: %d%n", calc.add());
        System.out.printf("sub result: %d%n", calc.sub());
    }
}
```

실행 결과는 이전과 똑같아야 한다. 구현 클래스에 `implements Calculator`를 빠뜨리지 않도록 주의한다. 이것이 객체를 사용하는 가장 보편적인 방법이며, 이제 **같은 인터페이스를 흉내 내는 프록시**를 끼워 넣을 준비가 되었다.

### 6-3. 다음 단계 — 자바 동적 프록시로 곁다리 빼기

> 강의는 6-2까지 진행했다. 아래는 슬라이드에 나온 다음 단계(프록시 클래스에 Cross-cutting Concern 구현)를 계산기 예제에 맞춰 미리 정리한 것이다.

자바 기본 라이브러리의 `java.lang.reflect.Proxy`는 **인터페이스만 주면** 그 인터페이스를 구현한 프록시 객체를 실행 중에 만들어 준다. 프록시의 어떤 메서드가 호출되든 `InvocationHandler`의 `invoke()` 하나로 모인다.

```java
Calculator target = new CalculatorImpl(10, 8);   // 시간 측정 코드를 뺀, 주 업무만 있는 원본

Calculator proxy = (Calculator) Proxy.newProxyInstance(
    CalculatorImpl.class.getClassLoader(),
    new Class[] { Calculator.class },             // 이 인터페이스를 흉내 낸다
    new InvocationHandler() {
        @Override
        public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
            long start = System.currentTimeMillis();              // 곁다리 (앞)

            Object result = method.invoke(target, args);          // 진짜 객체의 메서드 호출

            long end = System.currentTimeMillis();                // 곁다리 (뒤)
            System.out.printf("%s 소요시간: %dms%n", method.getName(), end - start);
            return result;
        }
    });

int total = proxy.add();   // 프록시를 거쳐 호출 → 시간이 찍힌다
int diff  = proxy.sub();   // 같은 곁다리 코드 하나로 모든 메서드에 적용된다
```

- `CalculatorImpl`의 `add()`, `sub()`에는 이제 **주 업무만** 남는다.
- 시간 측정을 빼고 싶으면 `proxy` 대신 `target`을 쓰면 끝이다. 원본 코드는 한 줄도 손대지 않는다.
- 스프링에서는 이 "프록시를 쓸지 원본을 쓸지"를 DI 컨테이너가 결정하므로, 사용하는 쪽 코드조차 바꿀 필요가 없다.

`invoke()` 안에서 진짜 메서드를 호출하는 줄을 기준으로, 곁다리 코드를 **어느 시점에** 실행할지에 따라 이름이 붙는다.

| 시점 | 실행 위치 |
|---|---|
| **Before** | 진짜 메서드 호출 **전** |
| **After returning** | 진짜 메서드가 **정상 반환한 뒤** |
| **After throwing** | 진짜 메서드가 **예외를 던졌을 때** |
| **Around** | 호출 **전후를 모두** 감싼다 (위 예제가 Around) |

`@Transactional`의 곁다리도 Around다. 앞에서 트랜잭션을 시작하고, 정상 반환이면 커밋, 예외면 롤백한다.

> **추가 설명 — 인터페이스가 없으면?**: `java.lang.reflect.Proxy`는 **인터페이스가 있어야만** 프록시를 만들 수 있다. 그래서 6-2에서 인터페이스부터 만든 것이다. 스프링은 인터페이스가 없는 클래스도 프록시로 만들 수 있도록 **CGLIB**(클래스를 상속해서 프록시를 만드는 라이브러리)를 함께 쓰며, 스프링 부트는 기본적으로 CGLIB 방식을 사용한다.

## 7. 웹을 위한 스프링 모듈 — 개념과 구현

Java SE 위에 Java EE와 Spring이 있고, 스프링은 웹을 위해 **MVC, 트랜잭션, 인증과 권한** 같은 기능을 제공한다. 이 기능들은 각각 바탕이 되는 개념 위에 만들어졌다.

| 기능 (구현) | 바탕 개념 |
|---|---|
| DI (객체 조립, 3계층 아키텍처) | IoC |
| 트랜잭션 (`@Transactional`) | AOP |
| 인증과 권한 (시큐리티) | 필터 |

## 8. 한 줄 정리

- AOP는 주로 **도구를 만드는 사람**이 쓰는 방법론이다. 필요가 생겼을 때 깊게 공부하고, 지금은 개념과 `@Transactional`의 원리까지 이해한다.
- **Aspect**는 사용자가 아닌 개발자·운영자 같은 역할자의 관점 코드다. **Core Concern**은 사용자가 요구한 것, **Cross-cutting Concern**은 흐름을 가로질러 잘라낸 곁다리(로그, 보안, 트랜잭션)다.
- AOP의 아이디어: 곁다리 코드를 메서드 밖 **한 곳(Proxy)**으로 빼고, **호출 흐름**만 그곳을 거치게 한다. 실행 순서는 같고, 붙였다 떼기가 쉬우며, 소스 코드가 없어도 된다.
- 사용하는 쪽이 **인터페이스**로 참조하고 **DI**로 객체를 받으면, 원본 대신 프록시를 넣어도 아무것도 고칠 필요가 없다.
- 자바 동적 프록시는 인터페이스가 필요하다. 그래서 static 함수 묶음을 **상태를 가진 객체 + 인터페이스**로 바꿨다.
