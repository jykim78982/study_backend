# JPA 트랜잭션 실습 — 커밋과 롤백을 테스트로 확인하기

**대상**: PostgreSQL 제약조건 실습을 끝내고 categories / menus 테이블 구조를 아는 사람. JPA 엔티티·리포지토리 기본 사용법을 알고 있다. JUnit은 잘 모른다.

**목표**: 트랜잭션 노트 두 편에서 배운 커밋·롤백 동작을 테스트 코드로 직접 실행해 확인한다.

**완성물**: Spring Boot 4.1.x + JDK 21 + PostgreSQL 환경에서 Category / Menu 엔티티로 6개 시나리오 테스트를 모두 실행하고, 콘솔 출력을 통해 커밋/롤백 결과를 확인한 상태.

**준비물**

- JDK 21 설치
- PostgreSQL 서버 실행 중
- VSCode 설치
- Spring Boot 4.1.x (Initializr 생성 시 최신 버전 선택)

> 원문의 단계별 테스트는 다섯 개(정상 커밋, NOT NULL, UNIQUE, FK, 체크드 예외 커밋)뿐이라 "6개 시나리오"와 맞지 않는다. 원문 서비스에 이미 있는 `saveMenuWithCheckedException`(rollbackFor로 롤백)을 실행하는 테스트를 10-3에 추가해 6개를 채웠다.

> 원문을 그대로 실행하면 **9단계(FK)와 10단계(체크드 예외)가 의도대로 동작하지 않는다.** 9단계는 FK 위반이 아니라 "트랜잭션 없음" 예외가 나고, 10단계는 아직 없는 메서드를 호출해 컴파일되지 않는다. 각 단계에 바로잡은 코드를 적어두었다.

## 1. 프로젝트 생성과 DB 준비

Spring Boot 프로젝트를 생성하고, `application.yml`에 PostgreSQL 연결 정보를 설정하며, 데이터베이스를 만든다.

**1-1. VSCode Initializr로 프로젝트 생성**

1. `File > New > File...` 또는 `Ctrl+N` / `Cmd+N`
2. **Spring Initializr** 선택
3. Project Metadata: Group `com.example`, Artifact `demo`
4. Project: Gradle project
5. Language: Java
6. Spring Boot: 4.1.x (최신 버전)
7. Dependencies: **Spring Data JPA, PostgreSQL Driver, Spring Web**
8. Generate Project
9. 프로젝트 폴더 열기

**1-2. application.yml 설정**

`src/main/resources/application.properties`를 삭제하고, `application.yml`을 만든다.

파일: `src/main/resources/application.yml`

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/계정_db
    username: ncafe
    password: your_password
  jpa:
    hibernate:
      ddl-auto: create-drop
    show-sql: true
    properties:
      hibernate:
        format_sql: true
```

PostgreSQL 비밀번호는 자신의 비밀번호로 바꾼다.

> 원문은 `username: postgres`로 되어 있지만, 1-3에서 `public` 스키마 권한을 `ncafe`에게 주므로 `ncafe`로 접속하는 것이 흐름에 맞다. 관리자 계정(`postgres`)으로 접속하면 GRANT 없이도 동작하지만, 앱이 관리자 권한으로 DB를 쓰게 되므로 실무에서는 피한다. 원격 서버의 DB를 쓴다면 `localhost:5432` 대신 그 서버 주소와 포트를 넣는다.

> **추가 설명 — 커밋·롤백 로그 보기**: `show-sql`은 Hibernate가 만든 **SQL만** 출력한다. 트랜잭션이 언제 시작되고 커밋·롤백되었는지는 출력하지 않는다. 이것까지 보고 싶다면 트랜잭션 매니저의 로그 레벨을 올린다.
>
> ```yaml
> logging:
>   level:
>     org.springframework.orm.jpa.JpaTransactionManager: DEBUG
> ```
>
> 그러면 `Creating new transaction ...`, `Committing JPA transaction ...`, `Rolling back JPA transaction ...` 같은 로그가 나와서 커밋과 롤백을 직접 볼 수 있다.

**1-3. 데이터베이스 생성**

PostgreSQL 서버에 접속해서 다음 명령어를 입력한다. `계정_db`는 자기 계정 이름으로 바꾼다.

```bash
newlec@newlecture:~$ sudo -u postgres psql -c 'CREATE DATABASE "계정_db";'
[sudo: authenticate] Password:
CREATE DATABASE
newlec@newlecture:~$ sudo -u postgres psql -d "계정_db" -c 'GRANT ALL ON SCHEMA public TO ncafe;'
GRANT
```

> **추가 설명 — PostgreSQL을 Docker로 띄운 경우**: 서버가 컨테이너 안에 있으므로 `sudo -u postgres psql`이 아니라 `docker exec`로 컨테이너 안에서 실행한다. 컨테이너 이름은 `docker ps`로 확인하고, 관리자 계정은 컨테이너를 만들 때 지정한 `POSTGRES_USER`(기본값 `postgres`)를 쓴다.
>
> ```bash
> docker exec -it 컨테이너이름 psql -U postgres -c 'CREATE DATABASE "계정_db";'
> docker exec -it 컨테이너이름 psql -U postgres -d "계정_db" -c 'GRANT ALL ON SCHEMA public TO ncafe;'
> ```

**✅ 확인**

- `src/main/resources/application.yml` 파일이 존재한다.
- `src/main/resources/application.properties` 파일은 삭제되었다.
- PostgreSQL에서 `계정_db` 데이터베이스가 생성되었다.

> 원문의 확인 항목과 자주 하는 실수 표에는 `transaction_db`라는 이름이 나오지만, 위 명령과 설정에서는 `계정_db`를 쓴다. 이름을 하나로 통일했다.

**🎓 코멘트**: `ddl-auto: create-drop`은 애플리케이션 시작 시 테이블을 만들고, 종료 시 삭제한다. 테스트 환경에서는 이 설정이 유용하다. `show-sql: true`는 실행되는 SQL을 콘솔에 출력하고, `format_sql: true`는 SQL을 가독성 있게 포맷한다.

> `create-drop`이므로 **테스트가 끝나면 테이블이 사라진다.** 테스트 후 DB 클라이언트에서 데이터를 직접 보고 싶다면 `create`나 `update`로 바꾼다. 이 실습은 콘솔 출력으로 확인하므로 `create-drop`으로 충분하다.

**❌ 자주 하는 실수**

| 증상 | 원인 | 해결 |
|---|---|---|
| `Connection refused` | PostgreSQL 서버가 실행되지 않음 | PostgreSQL 서버를 시작한다. |
| `FATAL: database "계정_db" does not exist` | 데이터베이스 미생성 | 1-3의 `CREATE DATABASE`를 실행한다. |
| `password authentication failed` | 비밀번호 오류 | `application.yml`의 password 값을 확인한다. |
| `permission denied for schema public` | 접속 계정에 스키마 권한이 없음 | 1-3의 `GRANT`를 실행한다. |

**📝 핵심**: `application.yml`은 Spring Boot의 기본 설정 파일이다. `ddl-auto: create-drop`은 테스트 환경에서 테이블을 자동으로 관리한다.

## 2. Category 엔티티

Category 엔티티를 정의한다. NOT NULL과 UNIQUE 제약조건을 반영한다.

**2-1. Category.java 만들기**

파일: `src/main/java/com/example/demo/Category.java`

```java
package com.example.demo;

import jakarta.persistence.*;

@Entity
@Table(name = "categories")
public class Category {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String name;

    public Category() {}

    public Category(String name) {
        this.name = name;
    }

    public Long getId() { return id; }
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
}
```

**✅ 확인**

- `Category.java` 파일이 `src/main/java/com/example/demo/`에 존재한다.
- `@Column(nullable = false, unique = true)`가 `name` 필드에 적용되어 있다.

**🎓 코멘트**: `nullable = false`는 NOT NULL 제약조건을, `unique = true`는 UNIQUE 제약조건을 나타낸다. `ddl-auto`로 테이블을 만들 때 이 설정이 DDL에 반영되어 데이터베이스 레벨에서 강제된다. `GenerationType.IDENTITY`는 PostgreSQL의 IDENTITY 컬럼(`generated by default as identity`)을 사용한다.

> 원문은 "JPA 레벨에서도 검증된다"고 했는데, **NOT NULL만 해당**한다. Hibernate는 Bean Validation 라이브러리가 없으면 저장 직전에 `nullable = false` 필드가 null인지 스스로 검사하고, null이면 SQL을 보내지도 않고 예외를 던진다(7단계에서 확인). **UNIQUE는 JPA가 미리 검사하지 않는다.** 중복인지 알려면 DB에 물어봐야 하므로, INSERT를 보낸 뒤 DB가 거부해야 알 수 있다(8단계).

**❌ 자주 하는 실수**

| 증상 | 원인 | 해결 |
|---|---|---|
| `No default constructor for entity` | 매개변수 없는 생성자가 없음 | JPA는 엔티티를 만들 때 기본 생성자를 쓴다. `public Category() {}`를 둔다. |
| 테이블 이름이 `categories`가 아니라 `category`로 만들어짐 | `@Table` 누락 | `@Table(name = "categories")`를 추가한다. 없으면 클래스 이름 기준으로 `category` 테이블이 생긴다. 9단계의 네이티브 쿼리처럼 테이블 이름을 직접 쓰는 곳에서 `relation "categories" does not exist` 오류가 난다. |

> 원문 표의 `Could not find setter for property — @Column 누락`은 실제로는 일어나지 않는다. `@Column`이 없어도 필드는 기본 설정으로 컬럼에 매핑된다. 위 표로 바꿨다.

**📝 핵심**: `@Column(nullable = false)`는 NOT NULL 제약조건을, `@Column(unique = true)`는 UNIQUE 제약조건을 나타낸다.

## 3. Menu 엔티티

Menu 엔티티를 정의한다. NOT NULL과 FK 제약조건을 반영한다.

**3-1. Menu.java 만들기**

파일: `src/main/java/com/example/demo/Menu.java`

```java
package com.example.demo;

import jakarta.persistence.*;

@Entity
@Table(name = "menus")
public class Menu {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @ManyToOne
    @JoinColumn(name = "category_id", nullable = false)
    private Category category;

    public Menu() {}

    public Menu(String name, Category category) {
        this.name = name;
        this.category = category;
    }

    public Long getId() { return id; }
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public Category getCategory() { return category; }
    public void setCategory(Category category) { this.category = category; }
}
```

**✅ 확인**

- `Menu.java` 파일이 `src/main/java/com/example/demo/`에 존재한다.
- `@ManyToOne`과 `@JoinColumn(name = "category_id", nullable = false)`가 `category` 필드에 적용되어 있다.

**🎓 코멘트**: `@ManyToOne`은 다대일 관계를 나타낸다. `@JoinColumn(name = "category_id")`는 외래키 컬럼 이름을 지정한다. `nullable = false`는 `category_id` 컬럼이 NOT NULL이라는 것을 나타낸다. 이 제약조건은 데이터베이스 레벨에서 강제되며, `category_id`에 NULL을 넣을 수 없다.

> **추가 설명 — 만들어지는 DDL**: 이 엔티티로 Hibernate가 만드는 `menus` 테이블에는 `category_id bigint not null`과 함께 `foreign key (category_id) references categories` 제약이 붙는다. 9단계의 FK 위반 테스트는 이 제약을 이용한다.

**❌ 자주 하는 실수**

| 증상 | 원인 | 해결 |
|---|---|---|
| 시작 시 `Could not determine recommended JdbcType for 'com.example.demo.Category'` | `@ManyToOne` 누락 | Hibernate가 `Category`를 일반 값으로 저장하려다 실패한 것이다. `@ManyToOne`을 추가한다. |
| 테이블 이름이 `menu`로 만들어짐 | `@Table` 누락 | `@Table(name = "menus")`를 추가한다. |

**📝 핵심**: `@ManyToOne`은 다대일 관계를 나타낸다. `@JoinColumn(name = "category_id")`는 외래키 컬럼 이름을 지정한다.

## 4. 리포지토리

리포지토리 인터페이스를 정의한다.

**4-1. CategoryRepository.java 만들기**

파일: `src/main/java/com/example/demo/CategoryRepository.java`

```java
package com.example.demo;

import org.springframework.data.jpa.repository.JpaRepository;

public interface CategoryRepository extends JpaRepository<Category, Long> {
}
```

**4-2. MenuRepository.java 만들기**

파일: `src/main/java/com/example/demo/MenuRepository.java`

```java
package com.example.demo;

import org.springframework.data.jpa.repository.JpaRepository;

public interface MenuRepository extends JpaRepository<Menu, Long> {
}
```

**✅ 확인**

- `CategoryRepository.java`와 `MenuRepository.java` 파일이 `src/main/java/com/example/demo/`에 존재한다.
- 두 인터페이스 모두 `JpaRepository`를 상속한다.

**🎓 코멘트**: `JpaRepository`는 Spring Data JPA의 기본 인터페이스로, `save`, `findById`, `delete` 등 기본적인 CRUD 메서드를 제공한다. 커스텀 쿼리가 필요할 때는 `@Query` 어노테이션을 사용한다.

**❌ 자주 하는 실수**

| 증상 | 원인 | 해결 |
|---|---|---|
| `No qualifying bean of type 'CategoryRepository'` | 리포지토리가 `@SpringBootApplication` 클래스(`DemoApplication`)의 패키지 **밖**에 있어 스캔되지 않음 | `com.example.demo` 또는 그 하위 패키지에 둔다. `@Repository`는 붙이지 않아도 된다. Spring Data가 `JpaRepository`를 상속한 인터페이스를 찾아 구현체를 자동으로 만든다. |
| `Not a managed type: class ...` | 리포지토리의 제네릭에 엔티티가 아닌 클래스를 넣었거나 `@Entity` 누락 | `JpaRepository<Category, Long>`처럼 엔티티 타입을 넣고, 엔티티에 `@Entity`를 붙인다. |

> 원문 표는 "`@Repository` 누락"을 원인으로 적고 해결란에 "필요 없다"고 적어 앞뒤가 맞지 않는다. 실제로 리포지토리 빈을 찾지 못하는 흔한 원인은 패키지 위치다.

**📝 핵심**: `JpaRepository`는 Spring Data JPA의 기본 인터페이스다. 리포지토리 인터페이스는 `JpaRepository`를 상속한다.

## 5. MenuService

`MenuService`를 만들고, `@Transactional`이 붙은 메서드를 정의한다.

**5-1. MenuService.java 만들기**

파일: `src/main/java/com/example/demo/MenuService.java`

```java
package com.example.demo;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import jakarta.persistence.EntityManager;
import jakarta.persistence.PersistenceContext;

@Service
public class MenuService {

    @PersistenceContext
    private EntityManager em;

    private final CategoryRepository categoryRepository;
    private final MenuRepository menuRepository;

    public MenuService(CategoryRepository categoryRepository, MenuRepository menuRepository) {
        this.categoryRepository = categoryRepository;
        this.menuRepository = menuRepository;
    }

    // 1. 정상 커밋: Category 와 Menu 를 함께 저장
    @Transactional
    public void saveCategoryAndMenu(String categoryName, String menuName) {
        Category category = new Category(categoryName);
        categoryRepository.save(category);

        Menu menu = new Menu(menuName, category);
        menuRepository.save(menu);
    }

    // 2. NOT NULL 위반 → 롤백
    @Transactional
    public void saveMenuWithNullName(Category category) {
        Menu menu = new Menu(null, category);
        menuRepository.save(menu);
    }

    // 3. UNIQUE 위반 → 롤백
    @Transactional
    public void saveDuplicateCategory(String categoryName) {
        Category category = new Category(categoryName);
        categoryRepository.save(category);
    }

    // 4. FK 위반 → 롤백 (9단계에서 사용, 원문에 없어 추가)
    @Transactional
    public void saveMenuWithInvalidCategory() {
        em.createNativeQuery(
            "INSERT INTO menus (name, category_id) VALUES ('FK Test Menu', 99999)"
        ).executeUpdate();
    }

    // 5. 체크드 예외 + rollbackFor → 롤백 (10-3에서 사용)
    @Transactional(rollbackFor = Exception.class)
    public void saveMenuWithCheckedException(Category category) throws Exception {
        Menu menu = new Menu("Test Menu", category);
        menuRepository.save(menu);

        throw new Exception("Checked exception for rollback test");
    }
}
```

> 원문은 `EntityManager em`을 주입받기만 하고 쓰지 않는다. 그리고 9단계에서는 테스트 클래스가 `em`으로 네이티브 쿼리를 직접 실행하는데, 그 테스트 메서드에는 트랜잭션이 없어서 FK 위반까지 가지 못한다(9단계 참고). 그래서 네이티브 INSERT를 **트랜잭션이 있는 서비스 메서드**(`saveMenuWithInvalidCategory`)로 옮겼다. 서비스에 `em`이 있는 이유가 이것이다.

**✅ 확인**

- `MenuService.java` 파일이 `src/main/java/com/example/demo/`에 존재한다.
- 모든 메서드에 `@Transactional` 어노테이션이 적용되어 있다.
- `saveMenuWithCheckedException` 메서드는 `@Transactional(rollbackFor = Exception.class)`를 사용한다.

**🎓 코멘트**: `@Transactional`은 메서드 실행을 트랜잭션으로 감싼다. 기본적으로 `RuntimeException`과 `Error`가 발생하면 롤백하고, 체크드 예외(Checked Exception)는 커밋한다. `rollbackFor = Exception.class`는 체크드 예외도 롤백하도록 지정한다. `EntityManager`는 JPA의 핵심 인터페이스로, 엔티티를 데이터베이스와 연결한다. `@PersistenceContext`는 `EntityManager`를 주입받는다.

> **추가 설명 — 리포지토리를 직접 부를 때와 서비스로 부를 때**: `SimpleJpaRepository`의 `save()` 같은 메서드에는 이미 `@Transactional`이 붙어 있다. 그래서 테스트에서 `categoryRepository.save()`를 직접 부르면 **그 한 줄이 하나의 트랜잭션으로 바로 커밋**된다. 반면 `@Transactional` 서비스 메서드 안에서 부르면 리포지토리는 서비스의 트랜잭션에 **참여**하고, 커밋·롤백은 서비스 메서드가 끝날 때 한 번에 결정된다. 7~10단계는 이 차이를 이용한다.

**❌ 자주 하는 실수**

| 증상 | 원인 | 해결 |
|---|---|---|
| `TransactionRequiredException: Executing an update/delete query` | `em.createNativeQuery(...).executeUpdate()` 같은 변경 쿼리를 트랜잭션 없이 실행 | 변경 쿼리를 실행하는 메서드에 `@Transactional`을 붙인다. (리포지토리의 `save()`는 자체 트랜잭션이 있어 이 예외가 나지 않는다.) |
| `No qualifying bean of type 'MenuService'` | `@Service` 누락 | `@Service`를 클래스에 추가한다. |

**📝 핵심**: `@Transactional`은 메서드 실행을 트랜잭션으로 감싼다. `rollbackFor`는 특정 예외 발생 시 롤백하도록 지정한다.

## 6. 정상 커밋 테스트

정상적인 커밋 시나리오를 테스트한다.

**6-1. 테스트 클래스 만들기**

VSCode에서 테스트 클래스를 만든다. 두 방법 중 하나를 쓴다.

- **직접 만들기**: `src/test/java/com/example/demo/` 폴더에서 우클릭 → **New File** → `TransactionTest.java` 입력
- **도구로 만들기**: `MenuService.java`에서 우클릭 → **Source Action** → **Generate Tests…** → 클래스 이름을 `TransactionTest`로 입력

> 원문 순서(New File로 파일을 만든 뒤 Generate Tests 선택)는 두 방법이 섞여 있다. Generate Tests는 **테스트할 클래스(MenuService)**에서 실행하는 메뉴다. 이 실습은 클래스 이름을 `TransactionTest`로 쓰므로 직접 만드는 쪽이 간단하다.

**6-2. TransactionTest.java 작성**

파일: `src/test/java/com/example/demo/TransactionTest.java`

```java
package com.example.demo;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;

@SpringBootTest
public class TransactionTest {

    @Autowired
    private MenuService menuService;

    @Autowired
    private CategoryRepository categoryRepository;

    @Autowired
    private MenuRepository menuRepository;

    @Test
    public void testNormalCommit() {
        try {
            menuService.saveCategoryAndMenu("Normal Category", "Normal Menu");
            System.out.println("✅ 정상 커밋: Category 와 Menu 가 저장되었다.");

            // 검증
            Category category = categoryRepository.findAll().stream()
                .filter(c -> c.getName().equals("Normal Category"))
                .findFirst()
                .orElse(null);

            if (category != null) {
                System.out.println("✅ 검증: Category 'Normal Category' 가 데이터베이스에 존재한다.");
            } else {
                System.out.println("❌ 검증 실패: Category 'Normal Category' 가 데이터베이스에 없다.");
            }

        } catch (Exception e) {
            System.out.println("❌ 예외 발생: " + e.getMessage());
            e.printStackTrace();
        }
    }
}
```

**✅ 확인**

- `TransactionTest.java` 파일이 `src/test/java/com/example/demo/`에 존재한다.
- `testNormalCommit` 메서드가 정의되어 있다.
- `@SpringBootTest` 어노테이션이 클래스에 적용되어 있다.
- 실행하면 디버그 콘솔에 `insert into categories`, `insert into menus` SQL과 ✅ 메시지 두 줄이 출력된다.

**🎓 코멘트**: `@SpringBootTest`는 Spring 컨텍스트를 로드하여 통합 테스트를 실행한다. `@Autowired`는 Spring 컨테이너에서 빈을 주입받는다. `try-catch` 블록은 예외를 잡고, `System.out.println`으로 결과를 콘솔에 출력한다. JUnit 어설션 없이 콘솔 출력을 통해 결과를 확인한다.

> **추가 설명 — 이 방식은 테스트가 항상 "성공"으로 표시된다**: 예외를 모두 `catch`로 잡고 출력만 하므로, 검증이 실패해도 JUnit은 초록색(성공)을 표시한다. 결과는 반드시 **콘솔 메시지**로 판단해야 한다. 실무에서는 출력 대신 **어설션**으로 검증해서, 기대와 다르면 테스트가 빨간색(실패)이 되게 한다.
>
> ```java
> import static org.junit.jupiter.api.Assertions.*;
>
> @Test
> void testNormalCommitWithAssert() {
>     menuService.saveCategoryAndMenu("Assert Category", "Assert Menu");
>     assertTrue(categoryRepository.findAll().stream()
>         .anyMatch(c -> c.getName().equals("Assert Category")));
> }
>
> @Test
> void testUniqueViolationWithAssert() {
>     categoryRepository.save(new Category("Dup"));
>     assertThrows(DataIntegrityViolationException.class,
>         () -> menuService.saveDuplicateCategory("Dup"));   // 예외가 나야 성공
> }
> ```

> **추가 설명 — 테스트끼리 데이터를 공유한다**: 같은 테스트 클래스의 메서드들은 **스프링 컨텍스트를 하나 공유**한다. 테이블은 컨텍스트가 시작될 때 한 번 만들어지고 모든 테스트가 끝난 뒤 삭제되므로, 앞 테스트에서 넣은 데이터가 뒤 테스트에 남아 있다. 그래서 각 테스트는 서로 **다른 이름**(`"Normal Category"`, `"NotNull Test Category"` 등)을 쓴다. `menuRepository.count()` 결과도 실행 순서에 따라 달라지므로, 메뉴 검증은 개수보다 **이름으로** 하는 것이 정확하다(10단계).

**❌ 자주 하는 실수**

| 증상 | 원인 | 해결 |
|---|---|---|
| `@Autowired` 필드가 `null` → `NullPointerException` | `@SpringBootTest` 누락. 스프링 컨텍스트가 없어서 아무것도 주입되지 않음 | `@SpringBootTest`를 클래스에 추가한다. |
| 테스트 실행 버튼이 안 보임 / 테스트가 실행되지 않음 | `@Test` 누락 또는 `org.junit.Test`(JUnit 4)를 import | `org.junit.jupiter.api.Test`를 import 한다. |
| `Unable to find a @SpringBootConfiguration` | 테스트 클래스가 `DemoApplication`과 다른 패키지에 있음 | 테스트도 `com.example.demo` 패키지(또는 하위)에 둔다. |

> 원문 표의 "`@SpringBootTest` 누락 → No qualifying bean"과 "`@Autowired` 누락 → Could not autowire"는 실제 증상과 다르다. `@SpringBootTest`가 없으면 빈을 찾는 과정 자체가 없어서 필드가 `null`로 남고, `@Autowired`가 없어도 마찬가지로 `null`이 되어 실행 중에 `NullPointerException`이 난다.

**📝 핵심**: `@SpringBootTest`는 Spring 컨텍스트를 로드하여 통합 테스트를 실행한다. `try-catch` + `System.out.println`으로 결과를 콘솔에 출력한다.

## 7. NOT NULL 위반 → 롤백

NOT NULL 제약조건 위반 시 롤백되는 것을 테스트한다.

**7-1. testNotNullViolation 메서드 추가**

파일: `src/test/java/com/example/demo/TransactionTest.java`

```java
    @Test
    public void testNotNullViolation() {
        try {
            // Category 를 먼저 저장
            Category category = new Category("NotNull Test Category");
            categoryRepository.save(category);

            // NOT NULL 위반: Menu 의 name 이 null
            menuService.saveMenuWithNullName(category);
            System.out.println("❌ 예기치 않은 결과: NOT NULL 위반이 롤백되지 않았다.");

        } catch (Exception e) {
            System.out.println("✅ NOT NULL 위반: 예외 발생 → 롤백");
            System.out.println("   예외 메시지: " + e.getMessage());

            // 검증: Category 는 커밋되었지만, Menu 는 롤백되었는지 확인
            Category savedCategory = categoryRepository.findAll().stream()
                .filter(c -> c.getName().equals("NotNull Test Category"))
                .findFirst()
                .orElse(null);

            if (savedCategory != null) {
                System.out.println("✅ 검증: Category 'NotNull Test Category' 는 커밋되었다.");
            } else {
                System.out.println("❌ 검증 실패: Category 'NotNull Test Category' 가 롤백되었다.");
            }

            // Menu 가 롤백되었는지 확인
            long menuCount = menuRepository.count();
            System.out.println("✅ 검증: 현재 Menu 개수: " + menuCount);
        }
    }
```

**✅ 확인**

- `testNotNullViolation` 메서드가 `TransactionTest.java`에 추가되었다.
- NOT NULL 위반 시 예외가 발생하고, 롤백이 수행된다.
- 예외 메시지에 `not-null property references a null or transient value : com.example.demo.Menu.name`이 보인다.
- 콘솔에 `insert into menus` SQL이 **출력되지 않는다.**

**🎓 코멘트**: NOT NULL 위반은 `DataIntegrityViolationException`으로 올라온다. 이 예외는 `RuntimeException`이므로, `@Transactional`의 기본 동작에 의해 롤백된다. Category는 서비스 호출 **전에** 리포지토리로 따로 저장해 그 자리에서 커밋되었으므로, Menu 롤백 후에도 데이터베이스에 존재한다.

> **추가 설명 — 이 예외는 DB가 아니라 Hibernate가 냈다**: 2단계에서 본 것처럼 Hibernate는 `nullable = false` 필드가 null이면 **SQL을 보내기 전에** `PropertyValueException`을 던진다. 그래서 콘솔에 `insert into menus`가 찍히지 않는다. 스프링이 이것을 `DataIntegrityViolationException`으로 바꿔서 올려준다. 프로젝트에 Bean Validation(`spring-boot-starter-validation`)을 추가하면 Hibernate는 이 자체 검사를 끄고, INSERT가 DB까지 가서 DB의 NOT NULL 제약이 거부한다. 어느 쪽이든 런타임 예외라 롤백된다.

> **추가 설명 — 이 시나리오에서 롤백되는 것**: 서비스 트랜잭션 안에서 한 일은 실패한 Menu 저장 하나뿐이라, 롤백으로 되돌려지는 데이터가 사실상 없다. "앞의 작업까지 함께 되돌려지는" 진짜 롤백을 보려면 Category 저장도 같은 서비스 메서드 안으로 넣으면 된다. 그러면 Menu가 실패할 때 **Category까지 함께 사라진다.**
>
> ```java
> @Transactional
> public void saveCategoryAndNullMenu(String categoryName) {
>     Category category = categoryRepository.save(new Category(categoryName));  // 같은 트랜잭션
>     menuRepository.save(new Menu(null, category));                            // 실패 → Category도 롤백
> }
> ```

**❌ 자주 하는 실수**

| 증상 | 원인 | 해결 |
|---|---|---|
| Category 검증이 "롤백되었다"로 나옴 | Category 저장을 서비스 메서드 안으로 옮김 | 이 테스트는 Category를 **테스트에서** 리포지토리로 먼저 저장해야 "Category는 커밋, Menu는 롤백"을 확인할 수 있다. |
| 다른 테스트를 고쳤더니 Menu 개수가 달라짐 | 테스트끼리 데이터를 공유함 | 개수는 참고용으로 보고, 확실한 검증은 이름으로 한다. |

> 원문 표의 `ConstraintViolationException` / `DataIntegrityViolationException` 행은 이 테스트에서 **의도적으로 일으키는** 예외라 "자주 하는 실수"가 아니다. 위 표로 바꿨다.

**📝 핵심**: NOT NULL 위반은 런타임 예외이므로, `@Transactional`의 기본 동작에 의해 롤백된다. Category는 Menu 저장 전에 커밋되었으므로, Menu 롤백 후에도 데이터베이스에 존재한다.

## 8. UNIQUE 위반 → 롤백

UNIQUE 제약조건 위반 시 롤백되는 것을 테스트한다.

- 이번에는 콘솔에 두 번째 `insert into categories` SQL이 **출력된 뒤** 예외가 난다. 예외 메시지에 `duplicate key value violates unique constraint`가 포함된다.

**🎓 코멘트**: UNIQUE 제약조건 위반은 `DataIntegrityViolationException`(또는 그 하위 예외)을 발생시킨다. 이 예외는 `RuntimeException`이므로, `@Transactional`의 기본 동작에 의해 롤백된다. 첫 번째 Category는 두 번째 Category 저장 전에 커밋되었으므로, 두 번째 Category 롤백 후에도 데이터베이스에 존재한다.

**📝 핵심**: UNIQUE 위반은 런타임 예외이므로, `@Transactional`의 기본 동작에 의해 롤백된다. 첫 번째 Category는 두 번째 Category 저장 전에 커밋되었으므로, 두 번째 Category 롤백 후에도 데이터베이스에 존재한다.

## 9. FK 위반 → 롤백

외래키(FK) 제약조건 위반 시 롤백되는 것을 테스트한다. `EntityManager`의 네이티브 쿼리로 존재하지 않는 `category_id`를 삽입한다.

> **원문 바로잡기 — 테스트에서 직접 executeUpdate를 하면 FK 위반까지 가지 않는다**: 원문은 테스트 클래스에 `EntityManager`를 주입하고 테스트 메서드에서 바로 `em.createNativeQuery(...).executeUpdate()`를 실행한다. 그런데 이 테스트 메서드에는 `@Transactional`이 없다. JPA는 INSERT·UPDATE·DELETE 쿼리를 트랜잭션 없이 실행하지 못하게 막으므로, FK 검사 전에 `TransactionRequiredException: Executing an update/delete query`가 난다. 원문 코드는 이 예외도 `catch`로 잡아 "✅ FK 위반"이라고 출력하기 때문에, **성공한 것처럼 보이지만 실제로는 FK를 시험하지 못한 것**이다.
>
> 그래서 네이티브 INSERT를 트랜잭션이 있는 서비스 메서드 `saveMenuWithInvalidCategory()`(5단계)로 옮기고, 테스트는 그 메서드를 호출한다. 예외 메시지에 `foreign key`가 포함되는지 꼭 확인한다.

**9-1. testForeignKeyViolation 메서드 추가**

파일: `src/test/java/com/example/demo/TransactionTest.java`

```java
    @Test
    public void testForeignKeyViolation() {
        try {
            // 존재하지 않는 category_id(99999)로 메뉴 INSERT (서비스의 트랜잭션 안에서 실행)
            menuService.saveMenuWithInvalidCategory();

            System.out.println("❌ 예기치 않은 결과: FK 위반이 롤백되지 않았다.");

        } catch (Exception e) {
            System.out.println("✅ FK 위반: 예외 발생 → 롤백");
            System.out.println("   예외 종류: " + e.getClass().getName());
            System.out.println("   예외 메시지: " + e.getMessage());

            // 검증: 'FK Test Menu' 가 없는지 확인
            boolean exists = menuRepository.findAll().stream()
                .anyMatch(m -> m.getName().equals("FK Test Menu"));
            System.out.println(exists
                ? "❌ 검증 실패: 'FK Test Menu' 가 저장되었다."
                : "✅ 검증: 'FK Test Menu' 는 롤백되어 없다.");
        }
    }
```

**✅ 확인**

- `testForeignKeyViolation` 메서드가 `TransactionTest.java`에 추가되었다.
- 예외 메시지에 `violates foreign key constraint`가 포함된다. (`TransactionRequiredException`이 보이면 원문 방식으로 실행한 것이다.)
- `'FK Test Menu'`는 저장되지 않았다.

**🎓 코멘트**: `EntityManager.createNativeQuery`는 네이티브 SQL 쿼리를 실행한다. `executeUpdate`는 INSERT, UPDATE, DELETE 쿼리를 실행하며, **트랜잭션 안에서만** 실행할 수 있다. FK 제약조건 위반은 런타임 예외이므로, `@Transactional`의 기본 동작에 의해 롤백된다.

> **추가 설명 — 왜 네이티브 쿼리를 쓰나**: JPA로 `new Menu("...", category)`를 저장하면 `category`는 실제 존재하는 엔티티여야 해서, 없는 `category_id`를 넣기가 오히려 어렵다. SQL을 직접 쓰면 `99999`처럼 없는 값을 바로 넣을 수 있다. 네이티브 쿼리에는 엔티티 이름이 아니라 **실제 테이블·컬럼 이름**(`menus`, `category_id`)을 쓴다.

> **추가 설명 — 예외 종류가 다를 수 있다**: 리포지토리(`save()`)에서 난 예외는 스프링이 `DataIntegrityViolationException`으로 바꿔주지만, 서비스에서 `EntityManager`를 **직접** 쓰면 이 변환을 거치지 않아 Hibernate의 `ConstraintViolationException`(또는 JPA의 `PersistenceException`)이 그대로 올라올 수 있다. 어느 쪽이든 런타임 예외라 롤백 동작은 같다. 예외 종류 출력 줄로 확인해 본다.

**❌ 자주 하는 실수**

| 증상 | 원인 | 해결 |
|---|---|---|
| `TransactionRequiredException: Executing an update/delete query` | 트랜잭션 없이 `executeUpdate()` 실행 | 서비스 메서드에 `@Transactional`을 붙이고 거기서 실행한다. |
| `relation "menu" does not exist` 또는 `column "categoryId" does not exist` | 네이티브 쿼리에 엔티티·필드 이름을 씀 | 실제 테이블·컬럼 이름(`menus`, `category_id`)을 쓴다. |
| `syntax error at or near ...` | SQL 문법 오류 | 따옴표, 괄호, 쉼표를 확인한다. |

**📝 핵심**: `EntityManager.createNativeQuery`는 네이티브 SQL 쿼리를 실행하며, 변경 쿼리는 트랜잭션 안에서만 실행된다. FK 위반은 런타임 예외이므로, `@Transactional`의 기본 동작에 의해 롤백된다.

## 10. 체크드 예외 → 커밋되는 함정과 rollbackFor

체크드 예외가 발생하면 기본적으로 커밋되는 함정을 확인하고, `rollbackFor`로 롤백하도록 수정한다.

> 원문은 10-1에서 테스트를 먼저 쓰고 10-2에서 서비스 메서드를 추가하는데, 그 순서로는 테스트가 **아직 없는 메서드를 호출**해서 컴파일 오류가 난다. 서비스 메서드를 먼저 추가하도록 순서를 바꿨다. 원문 테스트 코드 안의 긴 안내 주석도 이 순서 때문에 들어간 것이라 정리했다.

**10-1. MenuService.java에 saveMenuWithCheckedExceptionNoRollback 메서드 추가**

파일: `src/main/java/com/example/demo/MenuService.java`

```java
    // 체크드 예외 → 커밋되는 함정 확인
    @Transactional
    public void saveMenuWithCheckedExceptionNoRollback(Category category) throws Exception {
        Menu menu = new Menu("Test Menu No Rollback", category);
        menuRepository.save(menu);

        throw new Exception("Checked exception for commit test");
    }
```

**10-2. testCheckedExceptionCommit 메서드 추가**

파일: `src/test/java/com/example/demo/TransactionTest.java`

```java
    @Test
    public void testCheckedExceptionCommit() {
        // Category 를 먼저 저장
        Category category = new Category("Checked Exception Category");
        categoryRepository.save(category);

        try {
            // rollbackFor 없이 체크드 예외를 던지는 메서드
            menuService.saveMenuWithCheckedExceptionNoRollback(category);
            System.out.println("❌ 예기치 않은 결과: 예외가 발생하지 않았다.");

        } catch (Exception e) {
            System.out.println("✅ 체크드 예외: 예외 발생");
            System.out.println("   예외 메시지: " + e.getMessage());

            // 검증: 예외가 났는데도 Menu 가 저장(커밋)되었는지 확인
            boolean exists = menuRepository.findAll().stream()
                .anyMatch(m -> m.getName().equals("Test Menu No Rollback"));
            System.out.println(exists
                ? "✅ 검증: 'Test Menu No Rollback' 이 커밋되었다. (체크드 예외는 기본적으로 커밋된다)"
                : "❌ 검증 실패: 'Test Menu No Rollback' 이 롤백되었다.");
        }
    }
```

**10-3. rollbackFor로 롤백 확인 (6번째 시나리오)**

5단계의 `saveMenuWithCheckedException`은 같은 상황에서 `rollbackFor = Exception.class`를 지정한 메서드다. 이번에는 Menu가 **남지 않아야** 한다.

파일: `src/test/java/com/example/demo/TransactionTest.java`

```java
    @Test
    public void testCheckedExceptionRollbackFor() {
        Category category = new Category("RollbackFor Category");
        categoryRepository.save(category);

        try {
            menuService.saveMenuWithCheckedException(category);
            System.out.println("❌ 예기치 않은 결과: 예외가 발생하지 않았다.");

        } catch (Exception e) {
            System.out.println("✅ 체크드 예외 + rollbackFor: 예외 발생");
            System.out.println("   예외 메시지: " + e.getMessage());

            boolean exists = menuRepository.findAll().stream()
                .anyMatch(m -> m.getName().equals("Test Menu"));
            System.out.println(exists
                ? "❌ 검증 실패: 'Test Menu' 가 커밋되었다."
                : "✅ 검증: 'Test Menu' 는 롤백되어 없다. (rollbackFor 로 체크드 예외도 롤백)");
        }
    }
```

**✅ 확인**

- `MenuService.java`에 `saveMenuWithCheckedExceptionNoRollback` 메서드가 추가되었다.
- `testCheckedExceptionCommit`, `testCheckedExceptionRollbackFor` 메서드가 `TransactionTest.java`에 추가되었다.
- 체크드 예외가 발생해도 기본 설정에서는 Menu가 **커밋**되고, `rollbackFor = Exception.class`를 지정하면 **롤백**된다.

**🎓 코멘트**: `@Transactional`의 기본 동작은 `RuntimeException`과 `Error`만 롤백하고, 체크드 예외는 커밋한다. 체크드 예외가 발생해도 트랜잭션은 커밋되므로, 작업이 실패했는데 일부 데이터가 남아 데이터 무결성이 깨질 수 있다. `rollbackFor = Exception.class`는 체크드 예외도 롤백하도록 지정한다.

> **추가 설명 — 왜 체크드 예외는 커밋할까**: 스프링은 EJB의 관례를 따른다. 체크드 예외는 "잔액 부족"처럼 **호출한 쪽이 처리하도록 예상된 업무상 결과**로, 런타임 예외는 "프로그램 오류"로 본다. 그래서 체크드 예외는 작업 결과를 버리지 않는다. 하지만 이 기본값을 모르면 오류가 났는데 데이터가 저장되는 사고가 난다. 실무에서는 업무 예외를 **`RuntimeException`을 상속**해서 만들거나, 필요한 곳에 `rollbackFor`를 명시한다.

**❌ 자주 하는 실수**

| 증상 | 원인 | 해결 |
|---|---|---|
| 체크드 예외가 났는데 데이터가 커밋됨 | `rollbackFor` 미지정 | `@Transactional(rollbackFor = Exception.class)`를 사용한다. |
| 테스트에서 `cannot find symbol: method saveMenuWithCheckedExceptionNoRollback` | 서비스 메서드를 아직 추가하지 않음 | 10-1을 먼저 한다. |
| `unreported exception java.lang.Exception; must be caught or declared to be thrown` | 체크드 예외를 던지는 메서드를 `try-catch` 없이 호출 | 호출부를 `try-catch`로 감싸거나 테스트 메서드에 `throws Exception`을 붙인다. |

**📝 핵심**: `@Transactional`의 기본 동작은 `RuntimeException`과 `Error`만 롤백하고, 체크드 예외는 커밋한다. `rollbackFor = Exception.class`는 체크드 예외도 롤백하도록 지정한다.

| 8 | UNIQUE 제약조건 위반 시 롤백되는 것을 테스트한다. |

| 시나리오 | 예외 | 누가 막았나 | 결과 |
|---|---|---|---|
| 정상 저장 | 없음 | — | 커밋 |
