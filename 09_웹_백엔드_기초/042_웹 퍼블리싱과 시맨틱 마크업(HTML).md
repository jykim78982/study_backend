# 웹 퍼블리싱과 시맨틱 마크업(HTML)

## 1. 웹 퍼블리싱이란 — 생각보다 난도가 높은 포지션

**웹 퍼블리싱**은 디자이너가 만들어준 시안(이미지)을 그대로 화면에 구현하는 작업이다. 만들어지는 결과물은 두 종류의 문서로 나뉜다.

- **컨텐츠를 담은 문서** — HTML
- **스타일을 담은 문서** — CSS

과거에는 이런 흐름으로 일이 진행됐다.

1. **기획자**가 와이어프레임·스토리보드처럼 선으로 간단히 스케치한 초안을 만든다(디자인은 아니다).
2. 그 초안을 **디자이너**가 다듬는다.
   - 맥락 없이 맡기는 경우: "멋지고 트렌디하면서도 단정하게 만들어주세요." — 이렇게 맡기면 디자이너가 방향을 확신할 수 없어서, 시안을 만들 때마다 "이런 느낌이 맞나요?"처럼 하나하나 다시 확인을 받아야 한다.
   - 맥락을 주고 맡기는 경우: "교육센터라는 느낌이 들게, 배경에 패턴을 담고, 초록색 메인 컬러에 노란색 포인트를 주세요."
3. 디자이너가 준 이미지를 보고 **퍼블리셔**가 실제 문서(HTML+CSS)로 구현한다.

CSS를 제대로 다룰 수 있는 사람이 생각보다 적고, CSS 자체의 난도가 높고 손이 많이 가서 외주를 주는 경우가 많다. CSS를 조금만 고쳐도 연관된 값들을 많이 알아야 하고, 잘 모르고 건드리면 박스가 겹치거나 레이아웃이 통째로 무너진다.

- **AI로 퍼블리싱을 만들 수는 있지만**, AI가 뽑아내는 결과물은 어디까지나 템플릿이다. 그걸 수정하려면 생각보다 많은 걸 알아야 한다.
- 큰 그림만 물어보는 건 아마추어도 할 수 있다. **디테일하게 물어보고 판단할 수 있어야 전문가** 소리를 들을 수 있다.
- 웹 퍼블리싱은 결국 "웹 문서 만들기"이므로, 웹 자체에 대한 이해도가 충분해야 한다.

## 2. 웹의 탄생 — 하이퍼텍스트와 CERN

원래는 전자문서만 있었는데, 여기에 **하이퍼텍스트**(문서 안에서 다른 문서로 바로 이동하는 바로가기 텍스트)를 넣자는 아이디어가 나왔다.

- 장소는 **CERN**(입자 가속기가 묻혀있는 곳)이었고, 이 물리학 연구소에 문서 관리를 위해 파견된 컴퓨터공학도 **팀 버너스리**가 주인공이다.
- 문서가 너무 많아서 찾기 어려웠고, 그래서 문서 안에 하이퍼텍스트를 심자고 제안한 것이 **웹**의 시작이다.
- 의도는 좋았지만, 처음엔 일반 사람들에게 큰 의미가 없었다.

## 3. 마크업과 태그 — 컨텐츠를 구분하는 방법

문서 안의 내용을 그냥 텍스트 덩어리로 두면 문맥 파악이 안 되고, 소프트웨어(브라우저·검색엔진)도 이걸 어떻게 처리해야 할지 알 수 없다. 그래서 **구분자**가 필요하다.

- 웹 문서에서는 이 구분자를 **태그**로 표현한다(`h1`은 제목, `p`는 문장, `ul`은 순서 없는 목록 등).
- 태그로 컨텐츠를 감싸는 과정을 **마크업**이라 하고, 태그의 집합을 **마크업 언어**라고 부른다. 웹에서 쓰는 마크업 언어가 **HTML**이다.
- 이 태그들은 팀 버너스리가 정의했고, 이걸 읽어서 화면에 그려주는 도구가 브라우저다. 미리 약속된 태그가 브라우저에 심어져 있어서, 브라우저는 태그만 보고도 그게 어떤 컨텐츠인지 알 수 있다.

**HTML 문서의 기본 구조**:

```html
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <title>페이지 제목</title>
</head>
<body>
    <!-- 사용자에게 보여줄 내용 -->
</body>
</html>
```

- `html` 태그가 하이퍼텍스트를 포함한 문서 전체를 감싼다.
- `head`는 사용자에게 직접 보이진 않지만 문서에 영향을 주는 메타 정보 영역이다(`meta`, `title`은 필수).
- `body`는 실제 사용자에게 보여주는 컨텐츠 영역이다.
- 워드프로세서 같은 다른 문서 도구들도 사실 태그(내부적으로는 이름이 다를 뿐) 개념을 쓰고 있다 — HTML만의 독특한 개념이 아니다.

## 4. 컨텐츠의 4가지 종류와 태그

웹 문서의 컨텐츠는 크게 네 가지로 나뉜다: **목록, 문장, 표, 입력폼**.

### 제목

컨텐츠 위에 붙는 라벨. 큰 제목과 작은 제목이 있고, 이 제목들이 모여 문서의 **구조(아웃라인)**를 만든다 — 제목 모음이 곧 목차가 되고, 제목을 보고 원하는 컨텐츠를 찾을 수 있다.

- `h1`~`h6` 6단계로 나뉘고, 각 단계마다 기본 스타일이 있다(이 기본 스타일을 그대로 쓸지, 덧붙일지, 리셋할지는 선택의 문제다).

### 목록

```html
<ul>
    <li>항목 1</li>
    <li>항목 2</li>
</ul>
```

- `ul`(unordered list): 순서가 존재하지 않는 목록.
- `ol`(ordered list): 순서(넘버링)가 존재하는 목록.
- 둘 다 항목은 `li`(list item)로 표현한다.
- `dl`은 "정의"를 표현할 때 쓴다(`dt`=정의할 용어, `dd`=정의 내용).
- 특화된 메뉴/메뉴아이템 태그도 있지만 실무에서 잘 쓰지는 않는다.

**`ol`이냐 `ul`이냐는 자의적 판단의 여지가 있다** — 순서가 지켜져야 하는 내용(요리 절차)이라면 `ol`, 그냥 종류를 나열하는 것(학습할 주제 목록)이라면 `ul`이 맞다. 예를 들어 학습 순서를 반드시 지켜야 한다면 `ol`, 그냥 학습할 종류를 나열하는 거라면 `ul`을 쓰면 된다.

### 문장

`p` 태그로 표현한다.

### 표

두 개 이상의 컬럼으로 이루어진 목록이라면 표로 볼 수 있다.

```html
<table border="1">
    <tr>
        <td>제목</td>
        <td>h1,h2,h3,h4,h5,h6</td>
    </tr>
    <tr>
        <td>목록</td>
        <td>ul,ol,li,dl,dt,dd</td>
    </tr>
</table>
```

- `table`로 전체를 감싸고, 행은 `tr`, 행 안의 칸은 `td`로 표현한다.
- `border` 속성으로 테두리를 지정할 수 있다(위 표는 실습 문서의 실제 코드에서 가져온 예다).

### 입력폼

**입력폼**은 사용자에게 값을 입력받을 때 쓴다. 입력이 필요하면 무조건 `form` 태그를 써야 한다.

`form` 안에서 쓰는 태그들:

- `fieldset`: 관련된 입력들을 하나의 박스로 묶어주는 기본 스타일을 만든다.
- `legend`: `fieldset` 내부에서만 쓰는, 그 박스의 제목을 나타내는 태그.
- `label`: 각 입력 항목의 이름표.

form 예시:

```html
<form>
    <fieldset>
        <legend>개인정보</legend>
        <div>
            <label>이름</label>
            <input />
        </div>
        <div>
            <label>연락처</label>
            <input />
        </div>
    </fieldset>
    <fieldset>
        <legend>과거병력</legend>
        <div>
            <label>병명</label>
            <input />
        </div>
        <div>
            <label>발생년도</label>
            <input />
        </div>
    </fieldset>
</form>
```

**사용자 입력을 받는 방식은 크게 세 가지**로 나뉜다.

1. **쿼리스트링을 통한 요청** — 페이지를 요청하면서 값을 같이 보낸다(주소창의 `?cnt=1`처럼). 이 값은 사용자가 직접 타이핑하는 게 아니라, **미리 만들어둔 링크를 클릭**하는 방식으로 객관화되어 전달된다.

    ```html
    <nav>
        <h2>다음 중 당신이 원하는 반복 횟수는?</h2>
        <ul>
            <li><a href="?cnt=1">1회</a></li>
            <li><a href="?cnt=2">2회</a></li>
            <li><a href="?cnt=3">3회</a></li>
            <li><a href="?cnt=4">4회</a></li>
        </ul>
    </nav>
    ```

2. **객관식으로 주기 애매해서 직접 물어봐야 할 때** — 이럴 땐 `form`을 써서 사용자가 값을 직접 입력하게 한다.

    ```html
    <form action="list" method="get">
        <div>
            <label>횟수</label>
            <input name="cnt">
        </div>
        <div>
            <button>입력</button>
        </div>
    </form>
    ```

    `input`에 `name` 속성을 심어줘야, 그 값이 `cnt`라는 key로 서버에 전달된다. **사용자가 쿼리스트링을 직접 타이핑하는 일은 없다** — 링크를 클릭하거나 폼을 제출하는 방식으로만 전달된다.

3. 그 외 회원가입 폼처럼 여러 항목을 한 번에 입력받는 경우도 같은 `form` 구조를 쓴다.

    ```html
    <form>
        <div>
            <label>아이디</label>
            <input name="username">
        </div>
        <div>
            <label>비밀번호</label>
            <input name="password">
        </div>
        <div>
            <button>확인</button>
        </div>
    </form>
    ```

정리하면: 객관식으로 고를 수 있으면 **링크(쿼리스트링)**, 주관식으로 직접 입력받아야 하면 **`form`**을 쓰는 것이 기본 원칙이다.

## 5. `div` — 범용 구분 태그와 그 한계

`div`(디비전)는 목록·문장처럼 의미가 정해진 태그가 아니라, **컨텐츠를 구분해야 할 때 쓰는 범용 태그**다.

- 모든 걸 `div`로 나눠도 데이터 구분 자체는 된다. 그런데 이렇게 하면 "어떤 내용을 구분하고 있는지"가 뭉개진다 — 초기 AI가 만드는 결과물이 대개 이런 식이다. 구현은 편하지만 내용의 의미가 사라진다.
- **의미론적으로 문서를 만드는 것을 "시맨틱하게 만든다"고 한다.**
- 그렇다고 `div`를 아예 안 쓰는 건 아니다 — 특별한 의미는 없지만 여러 요소를 하나로 묶어야 할 때는 `div`가 딱 맞다. 마치 코드에서 중괄호로 블록을 묶듯, 두 개의 문장(`p`)을 하나의 그룹으로 묶고 싶을 때 `div`로 감싼다(제목이 이끄는 범위가 `p` 하나인지 그다음 `p`까지인지 헷갈릴 수 있기 때문).

## 6. 시맨틱 태그와 SEO(Search Engine Optimization) — 왜 의미를 담아야 하나

사이트 방문 로그를 보면 **구글 봇**이 자주 다녀간다. 구글 봇이 페이지를 긁어가서 검색 결과에 띄워주는 것이다.

- 페이지 안에 뭐가 담겨있는지 모르면, 검색엔진은 "퍼갈 게 없다"고 판단한다 — 뭘 가져가야 하는지 모르기 때문이다.
- **시맨틱하게 마크업하면**, 기계(크롤러)가 내용을 가져가서 나름대로 정리하고, 검색했을 때 정리된 모양으로 보여줄 수 있다.
- 이게 바로 **SEO**(검색엔진 최적화)와 직결된다. 홍보 예산이 무제한이면 신경 안 써도 되지만, 보편적인 회사는 구글 검색을 통한 유입에 크게 의존하므로 문서를 잘 구조화하는 게 중요하다.

**HTML5의 시맨틱 태그 등장**: HTML5 이전에는 `div`만으로 문서를 구성해서, "이 전체에서 뭐가 메인인지", "이 내용이 꼭 필요한 건지 곁다리인지"를 구분할 방법이 없었다. `div`는 무색무취라 표현 방법이 막연했다. HTML5는 여기에 의미를 가진 태그를 추가했다.

- **`section`**: 제목을 가지고 있는 블럭을 감싸는 기본 시맨틱 태그.
- **`article`**: 저작자 정보가 붙을 만한, 독립적인 컨텐츠 단위(글쓴이가 있는 게시물 같은 느낌).
- **`nav`**: 주된 내용이 링크(네비게이션)로 이루어진 블록.
- **`aside`**: 본문에 곁다리로 붙는 부가 정보.
- 어떤 특화 태그를 써야 할지 애매하면, **일단 "제목+내용"은 다 `section`으로** 감싸고, 더 특화된 성격이 뚜렷하면 그때 `article`/`nav`/`aside`로 바꾸면 된다.

## 7. 실전 코드로 판단해보기 — 실습 문서(`index.html`)

실습으로 만든 `index.html`에서 실제로 시맨틱 태그를 골라 쓴 부분들:

```html
<nav>
    <h2>학습 내용</h2>
    <ul>
        <li><a href="">퍼블리싱 이란?</a></li>
        <li><a href="">태그란?</a></li>
        <li><a href="">태그의 종류</a></li>
    </ul>
</nav>

<article>
    <h2>웹 퍼블리싱에 대한 이해</h2>
    <div>
        <p>웹 퍼블리싱은 웹문서를 만드는 작업 또는 과정을 말한다. ...</p>
        <p>설명 추가</p>
    </div>
</article>

<section>
    <h2>태그의 종류</h2>
    <table border="1"> <!-- 3장의 표 --> </table>
</section>
```

- "학습 내용" 목차는 링크 목록이 주된 내용이므로 `nav`로 감쌌다.
- "웹 퍼블리싱에 대한 이해" 부분은 `article`로 감쌌다. 이 내용은 특정 저작자가 작성한 설명 글(칼럼이나 블로그 포스트 같은)이라, 글쓴이 정보가 붙을 만한 독립적인 컨텐츠이므로 `article`로 보는 게 타당하다.
- "태그의 종류" 표는 제목+내용 구조라서 기본값인 `section`으로 감쌌다.

**판단 기준을 정리하면**:

1. 주된 내용이 링크 모음이면 → `nav`
2. 저작자 정보가 붙을 만한 독립된 컨텐츠면 → `article`
3. 본문에 곁다리로 붙는 부가 정보면 → `aside`
4. 위 셋에 해당하지 않고 제목+내용 구조면 → 일단 `section`
5. 특별한 의미 없이 여러 요소를 그냥 묶어야 하면 → `div`

이렇게 직접 구조를 짜본 뒤, AI에게 문서를 만들어달라고 하고 그 결과를 두고 "이 태그는 왜 여기 썼는지, 다른 태그가 더 맞지 않는지" 서로 논쟁해보는 연습이 실력을 키우는 데 도움이 된다.
