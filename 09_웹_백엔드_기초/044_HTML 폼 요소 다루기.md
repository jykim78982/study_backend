# HTML 폼 요소 다루기

## 1. `placeholder` — 입력 전에만 보이는 안내 문구

사용자가 값을 입력하기 전에 "무엇을 입력해야 하는지"를 보여주다가, 사용자가 값을 입력하는 순간 사라지는 문자다. 잠깐 자리만 맡고 있는 문자라서 **placeholder(플레이스홀더)**라고 부른다.

```html
<label>이미지</label>
<input type="file" accept="image/jpg, image/png">

<label>한국명</label>
<input placeholder="예) 카페라떼, 차">
```

`placeholder`는 값이 아니다 — 사용자가 실제로 입력한 값이 서버로 전달되는 것이지, placeholder 문구 자체는 전송되지 않는다.

## 2. `autofocus` — 페이지가 열리자마자 포커스를 주는 속성

페이지를 새로고침해도 특정 입력창이 자동으로 선택되지 않는 게 기본 동작이다. 이때 `autofocus`를 넣으면 페이지가 열리자마자 그 입력창에 포커스가 가 있어서, 사용자가 별도로 클릭하지 않고 바로 키보드 입력을 시작할 수 있다.

```html
<input name="kor-name" autofocus>
```

- **한 문서 안에서 `autofocus`는 실질적으로 한 곳에만 의미가 있다.** 여러 입력창에 동시에 넣어도 페이지가 열릴 때 포커스를 받을 수 있는 요소는 하나뿐이라, 두 개 이상 넣는 건 의미가 없다.

## 3. 왜 속성 표기 방식이 두 가지로 갈렸는가 — SGML → XHTML → HTML5

같은 속성인데도 사람마다 표기법이 다른 걸 본 적이 있을 것이다.

```html
<!-- 이렇게 쓰는 사람도 있고 -->
<input autofocus>

<!-- 이렇게 쓰는 사람도 있다 -->
<input autofocus="autofocus" />
```

이건 취향 차이가 아니라 **HTML 표준이 겪은 역사** 때문에 생긴 차이다.

- 초기 HTML(4.0 무렵)은 SGML 문법을 따랐다. SGML 기반 문법은 상당히 느슨해서, 여는 태그에 대응하는 닫는 태그를 안 써도 되고, 속성에 키만 있고 값이 없어도 됐다. 문제는 이 느슨함 때문에 사용자가 임의로 새 태그(커스텀 태그)를 끼워 넣기가 어려웠다는 점이다.
- 그래서 팀 버너스리는 "웹 문서가 앞으로 더 다양한 컨텐츠·자원을 공유하는 장소가 될 텐데, 그러려면 문서 안에 커스텀 태그를 자유롭게 포함할 수 있어야 한다"고 보고, HTML을 SGML이 아니라 **XML** 기반으로 새로 짜자고 제안했다. 이렇게 나온 것이 **XHTML**이다.
- XML 기반이 되면서 문법이 훨씬 엄격해졌다 — **여는 태그가 있으면 반드시 닫는 태그가 있어야 하고**, `input`처럼 원래 닫는 태그가 없는 단일 태그도 끝에 **`/`를 붙여서 스스로 닫아야 하고**, **속성은 키가 있으면 반드시 값도 있어야 한다**(`autofocus`만 쓸 수 없고 `autofocus="autofocus"`로 써야 함).
- 이후 XHTML 2.0이 기존과 완전히 다른 구조로 나오면서 혼란이 커졌고, 스마트폰(아이폰) 시대가 열리면서 웹이 "문서"보다 "애플리케이션 플랫폼"으로 요구받는 방향이 강해졌다. 이 흐름에서 애플·모질라 등 브라우저 업체들이 W3C와는 별도로 **WHATWG**라는 단체를 꾸려 그래픽·멀티미디어·네트워크·로컬 저장소·3D 가속 같은, 그동안 플래시(Flash)·실버라이트(Silverlight/WPF) 같은 플러그인이 채워주던 기능들을 브라우저 표준 API로 직접 흡수하는 방향으로 **HTML5**를 만들기 시작했다.
- 결과적으로 XHTML은 표준 규격으로서는 사실상 정체됐고, HTML5가 정식 표준으로 자리잡기까지 상당한 공백기가 있었다.
- **지금 우리가 보는 두 가지 표기법(`autofocus` vs `autofocus="autofocus"`, `<input>` vs `<input />`)은 이 역사의 흔적이다.** XHTML 시절 문법(엄격한 키=값, self-closing 슬래시)과 HTML5의 느슨한 문법이 섞여서 관습으로 남아있는 것이다. 중요한 건 **한 문서 안에서는 한 가지 방식으로 일관되게 쓰는 것**이다 — 이 문서가 순수 HTML인지 XHTML인지에 따라 정해지는 문제이지, 아무렇게나 섞어 써도 되는 게 아니다.

## 4. `autocomplete` — 브라우저가 과거 입력값을 제안해주는 기능

같은 `name` 값을 가진 입력창에 예전에 입력했던 값이 있으면, 브라우저가 그 값을 자동완성 후보로 보여준다(기본값은 `on`). 이 동작을 원하지 않으면 꺼야 한다.

```html
<input name="username" autocomplete="off">
```

과거에 입력했던 값(예: 다른 사이트에서 `username`이라는 이름으로 입력했던 값)이 그대로 노출되는 걸 원하지 않을 때 `off`로 끈다.

## 5. `datalist` — 입력 후보 목록 제공하기

사용자가 입력할 내용을 아예 자유 입력으로 두지 않고, 몇 가지를 미리 제안하고 싶을 때 쓴다.

```html
<input list="menu-suggestions">
<datalist id="menu-suggestions">
  <option value="아메리카노">
  <option value="카페라떼">
</datalist>
```

- `datalist`에 `option`들을 넣고 고유한 `id`를 부여한 뒤, `input`에 `list` 속성으로 그 `id`를 연결하면 된다.
- 사용자가 입력창에 타이핑하면 이 목록에서 필터링된 후보가 자동완성처럼 나타나고, 클릭하면 그대로 입력된다. 자유 입력을 막지는 않으면서 후보를 제안하는 용도다.

## 6. 버튼 두 가지 표기 — `<button>` vs `<input type="submit">`

전송 버튼을 만드는 방법은 두 가지다.

```html
<input type="submit" value="전송">
<button type="submit">전송</button>
```

- 기능과 모양이 동일하다 — 둘 다 폼을 전송한다.
- 원래는 `<input type="submit">`만 있었다. 이후 `<button>`이 추가된 이유는, 버튼 안에 텍스트뿐 아니라 **이미지 같은 다양한 컨텐츠를 넣고 싶다는 요구** 때문이다. `<input>`은 `value` 속성 하나로만 라벨을 표현할 수 있지만, `<button>`은 태그이기 때문에 그 안에 무엇이든(이미지, 아이콘 등) 감쌀 수 있고 그 내용이 그대로 버튼의 라벨이 된다.
- 지금은 `<button>`을 기본으로 쓰는 것이 일반적이다.

## 7. 콘텐츠인가, 데코레이션인가 — 판단 기준

폼을 만들다 보면 "이걸 실제 의미가 있는 컨텐츠로 넣어야 하나, 그냥 눈에 예쁘게 꾸미기만 하면 되나"를 판단해야 하는 순간이 자주 온다.

- **취소 버튼처럼 실제로 폼을 전송하지 않는 버튼**은 `<button type="button">`으로 만든다(또는 애초에 버튼이 아니라 목록의 링크로 표현). `<button>`은 모양은 버튼이어도, `type="button"`이면 눌러도 전송 기능을 하지 않는다 — 즉 겉모양이 버튼이라고 해서 항상 "전송"의 의미를 갖는 건 아니다.
- **"필수 입력"이라는 표시(예: `*`)** 같은 것도 판단 기준은 같다 — 사용자에게 반드시 전달해야 하는 정보라면 콘텐츠로 취급하고, 단순히 화면을 꾸미기 위한 것이라면 스타일(CSS)로 처리한다. "이 정보를 사용자에게 말해줘야 하는가"가 콘텐츠와 데코레이션을 가르는 기준이다.

## 8. `required` — 빈 값 전송을 브라우저 단에서 막기

사용자가 아무것도 입력하지 않은 채로 폼을 전송하면, 서버는 그 빈 값을 받아서 처리해야 한다. 유효하지 않은 값을 계속 받아 처리하는 과정에서 서버 자원(메모리·프로세스)이 낭비되고, 이런 허점이 과거에는 서비스 거부(DoS) 공격에 악용되기도 했다. 자바스크립트가 초기에 각광받은 이유 중 하나도, 서버로 보내기 전에 클라이언트 쪽에서 값을 검증할 수 있게 해준다는 데 있었다.

HTML은 이제 자바스크립트 없이도 이 검증의 일부를 자체적으로 처리할 수 있다.

```html
<input name="kor-name" required>
```

- `required`가 붙은 입력창이 비어 있으면, 브라우저가 아예 폼 전송을 막고 사용자에게 입력을 요구한다. 서버까지 빈 값이 전달되는 것을 원천적으로 줄여준다.
- 세밀한 형식 검증(길이 제한, 정규식 패턴 등)은 별도의 속성이나 자바스크립트로 보완해야 한다 — `required`는 "값이 아예 비어 있는 경우"만 막아준다.

## 9. `name` 속성 — 서버와 클라이언트가 공유하는 키

`input`의 값이 서버로 전달될 때, 그 값을 식별하는 이름표가 `name` 속성이다.

```html
<input name="kor-name">
<input name="eng-name">
<input name="price">
<input name="description">
```

- **이 이름은 클라이언트가 마음대로 정하는 게 아니라, 서버가 받기로 정해둔 이름과 반드시 일치해야 한다.** 서버가 어떤 키로 값을 받을지 미리 정해두고 공개하면, 클라이언트는 그 규약을 그대로 따라야 값이 제대로 전달된다.
- `name`이 없는 입력창은 값을 입력해도 **아예 전송되지 않는다** — 폼 전송 시 `name=값` 쌍으로 데이터가 구성되기 때문에, 이름이 없으면 서버 입장에서는 그 값이 애초에 존재하지 않는 것과 같다.

## 10. `select` — 화면에 보이는 텍스트가 아니라 `option`의 값이 전송된다

카테고리 선택처럼 정해진 목록 중 하나를 고르게 할 때는 `select`(콤보박스)를 쓴다.

```html
<select name="category-id">
  <option value="1">커피</option>
  <option value="2">차</option>
</select>
```

- 사용자 눈에는 "커피", "차" 같은 텍스트가 보이지만, 실제로 서버에 전달되는 값은 각 `option`의 **`value`**(위 예시에서는 카테고리를 식별하는 `id`)다. 화면에 보이는 텍스트와 실제로 전달되는 값이 다를 수 있다는 점을 항상 염두에 둬야 한다.
- 목록이 길어서 좁아 보인다면 `size` 속성으로 한 번에 보이는 줄 수를 지정할 수 있다(예: `size="10"`).

## 11. GET과 URL 길이 제한 — "등록해줘" 같은 요청은 POST로

메뉴를 새로 등록하는 것처럼 서버에 무언가를 **만들어 달라고 요청**하는 것은 "조회"가 아니다. GET은 리소스를 조회할 때 쓰는 메서드이고, 조회하려는 값은 URL의 쿼리스트링에 실려 전달된다.

- 문제는 **URL 자체에 길이 제한이 있다**는 점이다. 브라우저 개발자도구의 네트워크 탭을 열어보면, 요청 URL이 요청 헤더의 일부로 들어간다는 걸 확인할 수 있다. 이 요청 라인·헤더 전체가 감당할 수 있는 길이에는 한계가 있어서, 폼에 입력하는 여러 필드값을 전부 쿼리스트링으로 밀어 넣는 방식은 애초에 적합하지 않다.
- 게다가 "메뉴를 등록해달라"는 요청은 의미상으로도 조회(GET)가 아니라 **생성 요청**이다. 그래서 이런 폼은 GET이 아니라 **POST**로 전송해야 한다 — POST는 값을 URL이 아니라 요청 바디(body)에 담아 보내므로 길이 제한 문제에서도 자유롭다.
