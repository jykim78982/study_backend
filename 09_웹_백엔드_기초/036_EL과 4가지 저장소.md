# EL과 4가지 저장소

## 1. 서블릿 → JSP → EL/JSTL — View에서 코드 블록을 줄여가는 과정

서블릿만으로 화면을 만들면 HTML 문서를 한 줄 한 줄 `out.write(...)`로 찍어내야 해서 불편하다. 이 불편을 해결하려고 등장한 게 **JSP** — HTML 문서 안에 필요한 부분만 자바 코드를 끼워 넣을 수 있는, **템플릿 기반** 개발 방식이다. 반드시 JSP·서블릿이 아니어도, "문서(템플릿)와 로직이 분리되어 있고 템플릿 기반으로 개발한다"는 발상 자체가 핵심이다.

JSP를 쓰면 `out.write()` 코드를 우리가 직접 만들 필요가 없다 — 이걸 대신 처리해주는 도우미 역할을 하는 게 **제스퍼(Jasper)**, JSP를 서블릿으로 변환·컴파일해주는 엔진이다. 우리는 계속 "JSP를 부탁"하는 입장이고, 실제 변환은 제스퍼가 한다.

### 스파게티 코드 → MVC

JSP 파일 하나에 출력부(HTML)와 제어부(자바 로직)가 뒤섞이면 **스파게티 코드**가 된다. 이 문제를 풀기 위해 등장한 방법론이 **MVC**다.

**화면(View)과 로직(Controller)을 갈라놓는 핵심 도구 : 모델**

### Model 1 vs Model 2

Model1과 Model2의 차이는 **컨트롤러와 뷰를 물리적으로(파일 단위로) 나누느냐 아니냐**다. 파일이 물리적으로 나뉘면 협업이 가능해지고, 초기 로딩 속도나 사용성도 달라진다.

그런데 Model2로도 아직 남은 문제가 있다 — **뷰(JSP)의 껍데기 안에 여전히 자바 코드 블록이 남아있다.** 이걸 없애기 위해 등장한 게 **EL (Expression Language)**과 **JSTL**이다.

## 2. 작업 결과를 전달하는 저장소 — 4가지 스코프

Controller가 만든 결과(Model)를 View에 전달하려면 **저장소** 개념이 필요하다. JSP에는 생존 범위가 다른 저장소 4개가 있다.

| 저장소 | 생존 범위 |
|---|---|
| `page` | 현재 페이지(JSP) 하나 안에서만 |
| `request` | 포워드(forward) 관계가 이어지는 동안 |
| `session` | 한 사용자가 처음 요청한 순간부터 세션이 끝날 때까지 |
| `application` | 서버가 떠 있는 내내 |

**포워드 관계에서는 `request` 저장소를 쓴다** — Controller가 `request.setAttribute(...)`로 담아두면, 포워딩된 View에서 같은 요청 안이므로 그대로 꺼내 쓸 수 있다.

## 3. View에서 값을 꺼낼 때 코드 블록이 남는 문제

View는 Controller가 전달한 결과(모델)를 써야 하는데, 이걸 자바 코드 블록으로 직접 꺼내 화면 사이에 꽂아 넣는 방식은 여전히 코드 블록을 남긴다.

```jsp
<%= menu.getKorName() %>
```

저장소 4개 어디서 값을 꺼내든 매번 `getAttribute(...)` 같은 코드 블록을 써야 한다는 게 문제 — "자바 코드를 없애자"는 목표로 등장한 게 **EL**이다.

## 4. EL(Expression Language) — 저장소 값을 꺼내는 표현식

EL은 표현식을 다르게 쓰게 해줄 뿐, **코드 자체를 없앤 게 아니다.** 제스퍼가 지원하는 표현식으로 바뀌었을 뿐, 실제로는 여전히 `getKorName()` 같은 getter가 호출된다 — 다만 그게 자바 코드 블록이 아니라 제스퍼가 지원하는 별도 양식이 된 것.

```jsp
<%= menu.getId() %>       →  ${menu.id}
<%= menu.getKorName() %>  →  ${menu.korName}
<%= menu.getEngName() %>  →  ${menu.engName}
```

**변환 규칙:** `get`을 지우고 앞글자를 소문자로 바꾼다. `korName`으로 쓰면 내부적으로 `getKorName()`이 호출된다.

### Controller → View 전달도 EL로 받는다

```java
// Controller
request.setAttribute("cnt", 30);
```

```jsp
<!-- View -->
${cnt}
```

### 배열이든 컬렉션이든 똑같이 쓸 수 있다

`ArrayList`를 보내도 EL에서는 배열처럼 그대로 갖다 쓸 수 있다. 속성값을 꺼낼 때는 **점(`.`) 표기**와 **대괄호(`[]`) 표기** 둘 다 가능하다.

```
${n.title}   또는   ${n["title"]}
```

점 표기가 더 일반적이다. **중첩**된 객체도 점을 계속 이어서 접근할 수 있다 (`get()` 두 번 중첩되는 상황도 `.`으로 해결된다).

## 5. 저장소 우선순위 — 이름이 같으면 어디서 꺼내오나

세션과 리퀘스트 양쪽에 같은 이름(`menu`)으로 값을 담았다면, EL로 `${menu}`를 썼을 때 어디서 꺼내올까? **오류가 나지 않고**, 저장소를 정해진 순서대로 뒤진다.

```
page → request → session → application → (없으면 notfound)
```

그래서 리퀘스트와 세션에 동시에 `menu`가 있으면, **우선순위가 앞선 `request`의 값만 가져온다.** 세션 쪽 값을 꺼내고 싶다면 저장소를 직접 지정하면 된다.

```jsp
${sessionScope.menu}
```

`sessionScope`처럼 스코프 이름을 붙여 원하는 저장소를 명시적으로 지정할 수 있다.

> 참고: 국가 프로젝트에서는 기술 기반에 따라 SI(신규 프로젝트, 프론트엔드+백엔드 분리)와 SM(기존 프로젝트 운영, JSP 유지) 방식이 나뉘는 경우가 있다 — JSP는 지금도 SM 성격의 운영 프로젝트에서 여전히 쓰인다.

## 6. 파라미터(param) — 사용자가 전달한 값

URL 끝의 `?p=2` 같은 **쿼리 스트링**이나, 사용자가 form을 통해 입력한 값도 JSP 입장에서는 모두 **param**으로 받는다.

- **변수명 주의:** `page`라는 이름은 내장 객체와 겹쳐서 변수명으로 쓸 수 없다. 서블릿에서는 `req`로 받아왔더라도, JSP 안에서는 `request`라는 내장 객체 이름으로 접근해야 한다.
- 사용자가 전달한 값은 **전부 문자열(String)**이다. 숫자로 쓰려면 직접 파싱(`Integer.parseInt(...)` 등)해야 하는데, 이걸 매번 코드로 꺼내는 건 번거롭다.

```jsp
${param.p}
```

**사용자가 전달한 파라미터도 EL로 바로 꺼낼 수 있다** — 코드 블록 없이 `param.이름`으로 접근한다.

## 7. 요청 헤더(header) — 브라우저가 전달하는 정보

**헤더**는 브라우저가 서버로 전달하는 부가 정보다. 브라우저 개발자 도구의 네트워크 탭에서 요청 헤더를 직접 확인할 수 있다.

- `user-agent`: 접속한 사용자(브라우저/기기) 정보
- 접속 IP: 브라우저가 서버에 알아서 보내주기 때문에 서버가 알 수 있다 (예: 어떤 사이트에서 "내 아이피"를 검색하면 그 사이트가 요청 헤더로 전달받은 IP를 그대로 보여주는 원리)

사용자 파라미터와 마찬가지로, 요청 헤더도 EL로 코드 블록 없이 꺼낼 수 있다.

```jsp
${header["user-agent"]}
```

**주의:** `user-agent`처럼 이름에 **대시(`-`)**가 들어간 헤더는 점 표기(`header.user-agent`)로 쓸 수 없다 — EL이 `-`를 연산자로 해석해 버리기 때문에, 이럴 때는 반드시 **대괄호 표기**를 써야 한다. 헤더 이름의 대소문자는 상관없지만 스펠링에는 유의해야 한다.

## 8. IP는 어느 저장소·파라미터도 아니다 — `pageContext`

IP는 헤더에도, 4가지 저장소에도, 사용자 param에도 딱 들어맞지 않는다. 이럴 때 쓰는 게 **`pageContext`**다.

`pageContext`는 "페이지에서 쓸 수 있는 도구를 모아둔 것"이다. 저장소(`page` 스코프)로도 쓸 수 있지만, 그 안에는 페이지를 만들 때 필요한 여러 도구가 함께 들어있다. 예를 들어 `pageContext`에는 `request`를 가져오는 `getRequest`가 있고, 여기서 다시 원격 주소를 꺼낼 수 있다.

```jsp
${pageContext.request.remoteAddr}
```

## 9. EL은 지역변수를 쓸 수 없다

EL에서 자바 코드의 **지역변수**는 절대 접근할 수 없다 (`${ip}`처럼 자바 코드에서 만든 지역변수를 EL이 그냥 알아서 읽어오는 건 불가능). 그런 값을 EL에서 쓰고 싶다면, **`pageContext`에 담아서** 페이지 스코프 값으로 만들어야 한다 — 그래야 EL이 저장소 값으로 인식해서 꺼내올 수 있다.

## 10. EL의 연산자 — `empty`, 비교, 산술

- **`empty` 연산자:** 값이 있는지/없는지 확인할 때 쓴다 (예: 파라미터 값이 비어있는지 검사).
- **비교 연산자:** 값끼리 비교하는 연산도 EL 안에서 바로 쓸 수 있다.
- **산술 연산:** 덧셈/뺄셈 같은 계산도 EL 표현식 안에서 가능하다.

즉 EL은 단순히 값을 꺼내는 것뿐 아니라, 꺼낸 값을 바로 검사·비교·연산하는 것까지 코드 블록 없이 처리할 수 있게 해준다.
