# 웹 애플리케이션과 JSP

서블릿을 다루기 전에, **서블릿이 왜 존재하는지**를 이해하는 배경지식이 필요하다. 서블릿을 떠올리면 "웹 서버 프로그래밍" 용어가 많이 등장하는데, 지금은 프론트엔드/백엔드로 역할이 나뉘어 있지만 예전에는 그냥 **서버 프로그래밍**이라고 불렀다(사실 지금도 그렇게 부르는 경우가 많다). 그리고 웹이라는 기술 자체가 생각보다 최근에 나온 게 아니다.

## 1. 분산형(엔터프라이즈) 애플리케이션의 등장

지점과 본사가 서로 관련 내용을 조회하고 전달할 수 있어야 하는 상황을 생각해보자. 각 지점이 자기 컴퓨터에서만 돌아가는 **standalone(독립형)** 프로그램을 쓰고 있다면, 지점끼리 같은 데이터를 볼 방법이 없다.

그래서 **여러 곳에서 같이 조회할 수 있는 분산형 애플리케이션**이 필요해졌다 — 이런 걸 **엔터프라이즈(기업형) 애플리케이션**이라고 부른다.

- 각자 떨어져 있는 상황에서도 조회하는 내용이 **같아야** 한다
- 그래서 데이터를 공유하기 위한 **서버**가 등장한다
- 클라이언트는 서버에게 요청하고, 서버로부터 데이터를 공유받는 **서버-클라이언트 방식**으로 동작한다

**업데이트가 까다로웠다.** 지금은 자동 업데이트가 당연하지만, 예전에는 개발팀이 버전을 올리면 사용자가 기존 프로그램을 **직접 삭제하고 새 버전을 재설치**해야 했다. 30년 전에는 "삭제하러 가는 것"조차 쉽지 않았다. 게다가 당시 윈도우는 DLL을 공유하는 방식이었기 때문에, 애플리케이션 하나를 업데이트했더니 그 DLL이 바뀌면서 **엉뚱하게 다른 프로그램(예: 아래한글)이 갑자기 안 되는** 부작용까지 생기곤 했다.

## 2. 엔터프라이즈 웹 애플리케이션 — 설치 부담을 없애다

분산 애플리케이션의 "설치·재설치 부담"을 줄이기 위해 등장한 게 **웹**을 얹는 방식이다.

- 모든 사용자는 이미 **브라우저**를 갖고 있다
- 그러면 서버가 데이터만 주지 말고, **아예 문서(화면)를 만들어서 줘버리자**는 발상이 나온다
- 이렇게 하면 클라이언트는 **아무것도 설치할 필요가 없다** — 브라우저 하나면 충분하다

다만 이번엔 새로운 불편함이 생긴다. 데이터만 주는 게 아니라, **문서(HTML/CSS가 입혀진 결과물)로 만들어서 줘야** 한다. 요청이 올 때마다 그 문서를 만들어내는 **서버 쪽 기술, 실행 환경**이 필요해졌고, 자바에서 이 역할을 대표하는 게 바로 **서블릿**이다.

문서를 매번 새로 만드는 것 자체는 데이터만 주는 것과 비교해 큰 차이가 나지 않고, 인터넷 속도도 충분히 발달해서 문제가 되지 않았다. 그 결과:

- 클라이언트용 윈도우 프로그램을 따로 만들던 개발자들이 대부분 사라졌다
- UI와 데이터를 함께 다루는 **웹 서버 개발자**만 있으면 되는 구조가 됐다
- 웹 서버와 개발 환경만 구축해두면, 클라이언트는 브라우저로 요청만 하면 된다
- 서버는 요청을 받아 애플리케이션을 **실행**해서 결과를 돌려준다 — 이 실행 환경을 **WAS**(Web Application Server)라고 부른다

## 3. 우리가 만드는 것 — 서버 앱, 그리고 톰캣의 두 얼굴

우리가 만드는 건 결국 **서버 애플리케이션**이다. 톰캣은 예전엔 우리 애플리케이션을 얹어 돌리는 "실행 환경"이었지만, 최근 흐름은 **애플리케이션을 만드는 쪽에서 톰캣 자체를 도구로 갖다 쓰는** 방향으로 가고 있다.

톰캣을 쓰는 방식은 크게 두 가지다.

1. **독립적인 서버 형태의 고전적인 톰캣** — 톰캣을 서버로 미리 띄워두고, 그 위에 내가 만든 클래스를 배포하는 방식
2. **임베디드 톰캣** — 내가 코드로 톰캣을 직접 띄우고, 그 안에서 서블릿까지 함께 관리하는 방식

최근에는 **2번 방향**으로 많이 가고 있다.

## 4. 아파치 재단

톰캣은 **아파치(Apache)**에서 제공한다. 아파치 재단은 1999년부터 활동해왔고, 우리가 지금 쓰고 있는 수많은 오픈소스 기술들이 이 재단 아래에서 관리되고 있다. 그만큼 비중이 큰 재단이니 어느 정도의 배경 지식은 갖고 있는 게 좋다.

## 5. 톰캣의 디렉토리와 서블릿이라는 단위

톰캣을 직접 만들었든, 임베디드로 쓰든, 서버 형식으로 실행하든 상관없이, 톰캣은 기본적으로 **ROOT 디렉토리**를 갖고 있고, 원하면 홈 디렉토리를 별도로 지정할 수도 있다.

서버 프로그램은 사용자가 원하는 기능들을 **하나씩, 기능별로** 만들어나간다. 이 서버 애플리케이션에서 **하나의 기능을 담당하는 조각 하나하나**를 **서블릿**이라고 부른다 — 즉 "서블릿을 만든다"는 건 "서버 애플리케이션의 기능 조각 하나를 만든다"는 뜻이다.

내가 만든 클래스, 내가 만든 함수를 아무 약속 없이 만들면 톰캣이 그걸 실행할 수 없다. 톰캣이 내가 만든 클래스를 알아보고 실행할 수 있게 하려면 **약속(규약)을 지켜야** 한다.

- `HttpServlet`을 상속받는다
- 정해진 함수(`doGet`, `doPost` 등)를 오버라이드하는 방식으로 구현한다
- 번역(컴파일)된 결과물(`.class` 파일)을 정해진 경로에 넣는 것이 곧 **배포**하는 방법이다

파일 하나하나가 다 서블릿이다. `App.java`는 그 서블릿들을 실행하기 위해 톰캣을 직접 띄우는 코드다. 만약 임베디드 톰캣을 쓰지 않는다면 `App.java` 자체가 필요 없다 — 그냥 톰캣 서버에 컴파일된 클래스 파일(Maven 프로젝트 기준 `target` 폴더 안의 `.class` 파일)을 배포하면 된다.

## 6. 매핑 정보가 없으면 무슨 일이 생기는가 — 직접 지워보고 확인

```java
Tomcat tomcat = new Tomcat();
tomcat.setPort(8080);
tomcat.getConnector();
```

이건 "톰캣아, 8080번에서 기다리고 있어라"는 설정이다. 하지만 톰캣이 **WAS 역할**을 하려면 여기에 더해서 "어떤 URL이 오면 어떤 서블릿을 실행해줘야 하는지"를 알려주는 **매핑 정보**가 필요하다.

원래는 `App.java`에서 서블릿마다 하나하나 매핑을 코드로 등록했지만, 지금은 이렇게 지시할 수 있다.

```java
WebResourceRoot resources = new StandardRoot(context);
resources.addPreResources(new DirResourceSet(resources, "/WEB-INF/classes",
        new File("target/classes").getAbsolutePath(), "/"));
context.setResources(resources);
```

"이 경로에 있는 클래스들을 네가 훑어서, 애노테이션이 있으면 그 정보를 읽어서 미리 로드해놔라"는 뜻이다. `main()` 함수가 실행되자마자 이 경로를 뒤져서 `@WebServlet`이 붙은 클래스들을 찾아 매핑 정보를 메모리에 올려두고, 그다음 톰캣이 시작된다. 이후 매핑된 경로로 요청이 오면, 톰캣이 `newInstance`로 서블릿 객체를 만들어 서비스를 호출하는 역할을 하게 된다.

**질문: 만약 이 코드 블록을 통째로 지워버리면, 톰캣은 실행이 될까?**

**답: 실행은 된다.** 톰캣 자체는 8080 포트에서 정상적으로 대기한다. 하지만 애노테이션을 읽어서 매핑 정보를 만드는 코드가 없으니, **어떤 URL로 요청이 와도 그에 맞는 서블릿을 찾을 방법이 없다** — 그 결과 모든 서블릿 요청이 계속 **404 에러**로 끝난다. 톰캣이 살아있는 것과, 서블릿이 실제로 실행되는 것은 별개의 문제라는 걸 보여주는 실험이다.

## 7. 서블릿으로 화면을 만들어보면 — 왜 이렇게까지 고통스러운가

기본적인 서블릿 구조를 봤으니, 이제 실제로 서블릿을 "이용"하는 쪽으로 넘어가보자. 예전에 만들었던 cafe 프로젝트의 **메뉴 목록 페이지**(`admin/menus`)를 서블릿으로 서비스해야 하는 상황을 생각해보자.

**"그냥 `webapp/admin/menus`에 있는 HTML 파일을 그대로 서비스하면 안 되나요? 굳이 서블릿으로 만들어야 할 이유가 있나요?"**

이전에 만든 `HelloServlet`을 떠올려보면, 그 안엔 이런 코드가 있었다.

```java
out.println("<html>");
out.println("<body>");
out.println("<h1>Hello, Servlet!</h1>");
out.println("<p>VSCode 환경에서 서블릿 실행 성공!</p>");
out.println("</body>");
out.println("</html>");
```

서블릿으로 화면을 만들려면, HTML 문서를 **한 줄 한 줄 `out.println()`으로 힘겹게 찍어내야** 한다. 이미 완성된 HTML 파일이 있는데, 굳이 이걸 저렇게 자바 코드로 바꿔서 옮겨야 할 이유가 뭘까?

**답: 정적 HTML 문서는 "그 순간의 데이터"를 담을 수 없기 때문이다.** 메뉴 목록은 DB나 데이터 파일에 들어 있다. 중요한 건 **문서가 만들어지는 시점**에 해당하는 데이터를 그 문서에 실을 수 있어야 한다는 것인데, HTML 파일 그 자체는 이런 능력이 없다.

## 8. 정적 문서와 동적 문서

- **정적(static) 문서**: 한 번 만들어놓으면 고정된다. 사용자가 요청할 때마다 그 미리 만들어둔 파일을 그대로 돌려준다
- **동적(dynamic) 문서**: 미리 만들어놓지 않는다. **요청이 오는 그 순간**에, 그 시점에 해당하는 데이터를 실어서 문서를 새로 만들어낸다

현실에서는 동적 문서가 압도적으로 많이 쓰인다.

- 일기예보를 보고 싶은데, 어제 만들어둔 문서를 그대로 보여준다면 쓸모가 있을까?
- 농구 경기를 실시간으로 보고 싶은데, 어제 만든 문서로 커버가 될까?

생각보다 정적 문서만으로 충분한 경우는 많지 않다. 필요에 따라 조건 처리를 하거나, 반복문을 돌리거나, 값을 채워 넣어서 그때그때 문서를 만들어내는 과정을 서블릿이 담당해야 한다.

## 9. 그래도 `out.println`은 끔찍하다 — JSP(Jasper)라는 도구

정리하면 이런 딜레마에 빠진다.

- HTML로 서비스하자니 → **정적 파일**이라 데이터를 실을 수 없다
- 서블릿으로 만들자니 → 한 줄 한 줄 `out.println`을 반복하는 게 **끔찍하다**

여기서 등장하는 게 도구다. **서블릿 코드를 직접 다 짜지 않고, HTML을 그대로 작성하면서 필요한 부분에만 자바 코드를 끼워 넣는 방식**이 있다 — 이 방식을 실제로 처리해주는 도구의 이름이 **Jasper(재스퍼)**다.

두 가지 방법을 놓고 비교해보면:

1. 우리가 HTML을 서블릿 코드로 일일이 옮겨 붙인다
2. **재스퍼에게 그 변환 작업을 맡긴다**

서버 프로그래머는 결국 사용자에게 **문서화된 결과물**을 만들어서 줘야 하는 입장이다. 데이터만 던져주면 안 되고, 문서로 포장해서 줘야 한다 — 이 포장 작업을 재스퍼가 대신 해준다.

### 재스퍼가 일하는 순서

`.jsp` 확장자로 요청이 들어오면:

1. 톰캣이 재스퍼를 깨운다
2. 재스퍼가 그 `.jsp` 파일을 **서블릿 코드로 변환하고, 컴파일까지** 해준다
3. 톰캣이 그렇게 만들어진 서블릿을 실행(`run`)한다

실제로 `maven_servlet_project`의 `admin/menus/list.jsp`가 이 변환을 거친다. `list.jsp`는 `list.html`과 내용이 거의 같지만, 첫 줄에 지시 블록(`<%@ page ... %>`)이 붙어 있다.

```jsp
<%@ page language="java" contentType="text/html; charset=UTF-8" pageEncoding="UTF-8"%>
<!DOCTYPE html>
<html lang="ko">
<head>
<meta charset="UTF-8">
...
```

이 `.jsp` 파일을 톰캣이 실행하면, 실제로 `list_jsp.java`라는 서블릿 소스가 자동으로 생성된다. 그 안을 들여다보면 다음처럼, 우리가 손으로 짰다면 지긋지긋했을 `out.write(...)` 호출이 HTML 한 줄마다 하나씩 자동으로 채워져 있다.

```java
out.write("\r\n");
out.write("<!DOCTYPE html>\r\n");
out.write("<html lang=\"ko\">\r\n");
out.write("<head>\r\n");
out.write("<meta charset=\"UTF-8\">\r\n");
```

**이 생성된 결과물(`list_jsp.java`)은 우리가 절대 직접 손댈 필요도, 눈여겨볼 필요도 없다** — 재스퍼가 우리 대신 이 지루한 변환 작업을 전부 해주기 때문이다.

## 10. 그런데 재스퍼가 한글을 깨먹는다면?

관리자 메뉴 목록 화면을 재스퍼에게 맡겼는데, 한글이 깨져서 나오는 상황을 가정해보자. [[008_인코딩과 Content-Type, 데이터 출력 방식]]에서 다룬 인코딩 문제와 원리는 같다 — 캐릭터셋(문자 인코딩)을 지정해주지 않으면 어긋난다.

파일 자체가 UTF-8로 저장되어 있어도, **응답으로 나갈 때 캐릭터셋을 지정하지 않으면** 브라우저가 엉뚱하게 해석해서 깨질 수 있다. 그래서 재스퍼에게도 최소한의 지시를 내려야 한다 — 그게 바로 `.jsp` 파일 맨 위에 붙는 **지시 블록(directive)**이다.

```jsp
<%@ page language="java" contentType="text/html; charset=UTF-8" pageEncoding="UTF-8"%>
```

이 한 줄이 재스퍼에게 알려주는 내용은 이렇다.

- `language="java"` — 이 페이지 안에 자바 언어가 포함될 수 있다
- `contentType="text/html; charset=UTF-8"` — 이 페이지가 만들어내는 콘텐츠의 타입은 HTML이고, 인코딩은 UTF-8이다
- `pageEncoding="UTF-8"` — 이 `.jsp` 파일 소스 자체를 읽어들일 때도 UTF-8로 읽어라

`%@` 형태의 지시 블록으로 재스퍼에게 이런 정보를 전달할 수 있고, 이 설정이 빠지면 한글이 깨진다.
