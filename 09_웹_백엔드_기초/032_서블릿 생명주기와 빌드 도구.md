# 서블릿 생명주기와 빌드 도구

## 1. 스프링은 서블릿 위에 있다

앞으로 백엔드를 스프링으로 만들어갈 것이지만, **스프링은 서블릿을 기저에 두고, 서블릿을 가려서 그 위에서 대신 해주는 프레임워크**다. 서블릿을 아예 모른 채로 스프링만 다루는 건 좋은 방법이 아니다.

기반 기술을 전혀 모르는 것과, 기반 기술을 알고 그 위에 있는 도구를 쓰는 것은 **이해력의 차이가 크다.** 겉핥기로 스프링만 배우기보다, 서블릿이 어떤 메소드들을 갖고 있고 어떤 흐름으로 동작하는지 먼저 봐야 한다.

## 2. 서블릿의 생명주기

```
init → service → doGet/doPost → destroy
```

- **`init`**: 서블릿 객체가 생성될 때 **딱 한 번** 실행되는 초기화 메소드
- **`service`**: 요청이 들어올 때마다 실행되며, HTTP 메소드(GET/POST 등)에 따라 `doGet`/`doPost`로 분기해주는 역할
- **`doGet`/`doPost`**: 실제 요청 처리 로직이 들어가는 자리
- **`destroy`**: 서버 종료나 재배포 시 **딱 한 번** 실행되는 소멸 메소드

실제 코드로 보면 이렇다.

```java
public class LifecycleServlet extends HttpServlet {

    private int requestCount;

    // 1. 초기화 메서드 (서블릿 생성 시 1회 실행)
    @Override
    public void init(ServletConfig config) throws ServletException {
        super.init(config);
        this.requestCount = 0;
        System.out.println("[init] 서블릿이 생성 및 초기화되었습니다.");
    }

    // 2. 요청 분기 메서드 (모든 요청 시마다 doGet/doPost 전에 실행)
    @Override
    protected void service(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {

        requestCount++;
        System.out.println("[service] 요청 수신 (누적 요청 수: " + requestCount + ")");

        // super.service()를 호출해야 HTTP 메서드에 맞춰 doGet/doPost로 전달됨
        super.service(req, resp);
    }

    // 3. GET 요청 처리 메서드
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        System.out.println("[doGet] GET 방식 요청 처리 중");
        // ... 응답 작성
    }

    // 4. POST 요청 처리 메서드
    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        System.out.println("[doPost] POST 방식 요청 처리 중");
        // ... 응답 작성
    }

    // 5. 소멸 메서드 (서버 종료/재배포 시 1회 실행)
    @Override
    public void destroy() {
        System.out.println("[destroy] 서블릿이 소멸합니다. 리소스를 정리합니다.");
    }
}
```

`service`가 `super.service(req, resp)`를 호출해야 실제로 요청의 HTTP 메소드에 맞춰 `doGet`/`doPost`로 흐름이 이어진다. 이건 [[029_오버라이드와 super, 생성자 체이닝]]에서 다룬 것처럼, 오버라이드한 메소드 안에서 `super`를 호출해 원래 흐름을 이어가는 것과 같은 패턴이다.

## 3. 프로젝트 파일은 "도구가 요구하는 것"

지금까지 VS Code로 `Create Java Project`를 하고, `Ctrl+S`로 컴파일하고, `Ctrl+F5`로 실행해왔다. 이때 만들어지는 프로젝트 파일들(`.vscode/settings.json` 등)은 **도구의 힘을 빌리기 위해 도구가 우리에게 요구하는 준비물**이다.

- 도구의 힘을 빌릴 필요가 없다면 메모장으로도 개발할 수 있다
- 하지만 도구(IDE, 빌드 도구 등)의 힘을 빌리려면, 그 도구가 요구하는 설정을 준비해줘야 한다
- 문제는 **이 설정이 도구마다 서로 다르다**는 것

예를 들어 IDE 중 **VS Code**와 **IntelliJ**, **Eclipse**는 성격이 다르다.

- IntelliJ와 Eclipse는 자바 개발자들 사이에서 오랜 역사를 가진 도구다
- VS Code는 최근 AI와 맞물리면서 사용량이 급격히 늘었고, 공교롭게도 그만큼 IntelliJ와 Eclipse의 사용 비중은 줄어드는 추세다

**VS Code에서 만든 프로젝트를 IntelliJ가 그대로 로드해서 컴파일·실행할 수 있을까?** → **아니다.** VS Code의 설정과 IntelliJ의 설정은 호환되지 않는다.

예를 들어 VS Code로 만든 프로젝트를 GitHub에 올렸을 때, 협업 상대방이 IntelliJ를 쓰는 사람이라면 그 프로젝트 파일을 그대로 열어 작업할 수 없다 — 프로젝트 설정 파일 자체가 IDE마다 다르기 때문이다.

## 4. 빌드 도구는 왜 IDE와 분리되어야 하는가

프로젝트를 만드는 과정은 보통 다음 흐름을 따른다.

```
프로젝트 생성 → 라이브러리 설정 → 코드 작업 → 컴파일 → 테스트 → 패키지 만들기 → 배포
```

Eclipse든 VS Code든, IDE는 이 과정을 전부 해낼 수 있다. **하지만 IDE가 이 일을 할 수 있다고 해서 IDE 자체를 빌드 도구로 쓰지는 말자.**

- **IDE**(Integrated Development Environment, 통합 개발 환경)는 수많은 도구를 한데 합쳐놓은 큰 틀이다
- **빌드**는 그 IDE가 가진 여러 기능 중 **하나일 뿐**이다
- 그 빌드 기능만 IDE에서 따로 떼어내 독립적인 도구로 만든 것이 바로 **Maven**, 그리고 나중에 나온 **Gradle**이다

빌드 기능을 IDE로부터 분리해서 독립된 도구로 쓰면, 어떤 IDE를 쓰든 그 IDE가 "이 독립된 빌드 도구를 가져와서 결합"하는 식으로 사용할 수 있다. 그러면 프로젝트가 특정 IDE 전용이 아니게 되어, 앞서 3장에서 본 IDE 간 비호환 문제가 사라진다.

**Maven과 Gradle, 뭘 배워야 하나?**

- 빌드 도구의 **개념**을 배울 때는 오래되고 안정적인 **Maven**을 기준으로 하고, 최종 프로젝트에서는 **Gradle**을 쓰는 방향이 좋다
- 처음부터 Gradle을 안 쓰는 이유: **VS Code에서 Gradle을 다루는 성숙도가 아직 떨어진다**
- Maven은 오래되고 팬층이 두텁고 안정적이며, Gradle은 더 최신이고 유연하지만 그만큼 모험이 필요하다

## 5. 형상관리 도구 — CVS와 Git의 차이

빌드 도구 자체에도 형상관리(버전관리) 기능이 딸려 있는 경우가 있지만, 지금은 별도로 **Git**을 형상관리로 쓰고, 유닛테스트는 **JUnit**을 가져와 쓴다.

과거의 대표적 형상관리 도구인 **CVS**는 Git과 근본적으로 방식이 다르다.

- **CVS**: 파일이 한 곳(서버)에 모여 있고, 누군가 파일을 수정하려고 열면 **서버에서 lock**이 걸려 다른 사람이 동시에 건드릴 수 없다. **동기화 방식** — 애초에 충돌이 나지 않도록 접근 자체를 막는다
- **Git**: **머지(merge) 방식** — 각자 따로 작업한 뒤, 나중에 합치다가 충돌이 나면 개발자가 직접 해결해서 올린다. **충돌이 나는 걸 전제로** 하는 도구다

빌드 도구에도 Maven과 Gradle이 있듯, 형상관리에도 여러 도구가 있고 규모와 상황(안정성이 중요한 큰 환경 vs 유연성이 필요한 환경)에 따라 다르게 선택하게 된다.

## 6. Maven 로컬 저장소와 `pom.xml`

사용자 계정 아래에 **`.m2`** 폴더가 있는데, 이게 **Maven의 로컬 저장소**다. `사용자계정/.m2/repository`에 가보면 그동안 받아진 jar 파일 목록을 볼 수 있다.

빌드 도구를 쓰지 않던 시절에는 필요한 jar 파일을 사이트에서 직접 검색해서 받아야 했다. 지금은 **`pom.xml`의 `dependency`에 필요한 라이브러리를 적어두기만 하면**, 프로젝트를 열 때 도구가 활성화되면서 지정한 의존성을 자동으로 받아온다.

```xml
<dependencies>
  <dependency>
    <groupId>jakarta.servlet</groupId>
    <artifactId>jakarta.servlet-api</artifactId>
    <version>6.0.0</version>
    <scope>provided</scope>
  </dependency>

  <dependency>
    <groupId>org.apache.tomcat.embed</groupId>
    <artifactId>tomcat-embed-core</artifactId>
    <version>10.1.19</version>
  </dependency>
</dependencies>
```

VS Code에서는 `Ctrl+Shift+P` → `Add Dependency`로도 필요한 의존성을 검색해서 `pom.xml`에 바로 추가할 수 있다.

- Maven 프로젝트라면 `pom.xml`에 좌표(groupId/artifactId/version)만 적어주면 되고
- 그렇지 않다면 jar 파일을 직접 다운로드해야 한다

## 7. 라이브러리 하나가 아니라 "의존성 트리"가 딸려온다

라이브러리를 하나 사용한다고 해서, 그 라이브러리의 jar 파일 하나만 받으면 끝일까? **아니다.** 직접 하나만 가져오면 십중팔구 `ClassNotFoundException`이 난다.

라이브러리도 내부적으로 다른 라이브러리를 사용해서 만들어지기 때문이다. `.m2`에서 jar 파일이 받아진 걸 보면, 내가 지정한 것 외에도 훨씬 많은 파일이 함께 들어와 있는 걸 볼 수 있다.

- 이렇게 **종속 라이브러리까지 체계적으로 함께 받아오는 구조**를 전이 의존성(transitive dependency)이라고 한다
- Maven은 이 종속 관계를 버전별로 알맞게 계산해서 한 번에 받아준다

`pom.xml`의 핵심은 이 파일이 프로젝트의 구조와 의존성을 정의하는 **설계도** 역할을 한다는 것이다. Maven은 이 설정을 읽어서 실제 프로젝트 구조를 만들어낸다.

## 8. 표준 디렉토리 구조 — 정해져 있지만 안 보인다

`pom.xml`에 "자바 소스 코드는 여기에 있다"는 경로 설정이 보이는가? **보이지 않는다.** 설정할 수는 있지만, 보통은 하지 않는다.

경로를 명시하지 않으면 Maven은 **묵시적으로**(관례로) 다음 구조를 따른다.

```
src/main/java/도메인_기반_패키지/...   ← 실제 소스 코드
src/test/java/...                    ← 테스트 코드 (별도 폴더)
```

이 구조를 보면 "이건 Maven 프로젝트구나"라고 바로 알아볼 수 있다. 디렉토리 구조를 바꿀 수는 있지만, 굳이 바꾸지 않고 관례를 따르는 게 일반적이다 — 다르게 바꾸면 오래된 문서나 다른 사람이 만든 코드와 엉키는 문제가 생기기 쉽다.

## 9. IDE 실행 방식과 Maven 명령을 함께 쓸 수 있다

Maven 명령어(`compile`, `test` 등)를 직접 실행할 수도 있지만, 이런 명령을 매번 치지 않고 지금까지 써온 **IDE의 실행 방법을 그대로 써도** 정상적으로 동작한다.

- 실행 방법은 IDE에 통합되어 있고, 그 위에 Maven의 기능(의존성 관리, 표준화된 구조)까지 더해지므로 **둘의 장점을 동시에 가져갈 수 있다**
- 이 프로젝트는 Maven으로 만들어졌기 때문에, VS Code가 아닌 다른 IDE(Eclipse 등)에서 열어도 그대로 이어서 작업할 수 있다 — 4장에서 다룬 "IDE 간 프로젝트 비호환" 문제가 Maven 기반이라면 해결된다

앞으로는 Maven을 기반으로 서블릿 프로젝트를 만들게 되고, 이 방식으로 진행하다가 마주치는 문제들을 해결하기 위한 다음 단계로 **스프링**을 배우게 된다. 스프링이 무엇이고 왜 필요한지는 그 문제들을 실제로 마주친 뒤에 설명한다.

## 10. `HelloServlet`이 실제로 요청에 응답하는 과정

사용자가 브라우저에서 `/hello`로 요청을 보내는 상황을 순서대로 보면 이렇다.

1. Tomcat에게 "8080번 포트에서 대기하다가, 요청이 오면 나에게 알려달라"고 설정한다
2. 현재 디렉토리 경로를 홈 디렉토리(Context의 docBase)로 지정한다
3. `/hello` 요청이 오면 `HelloServlet` 객체를 갖고 있다가, 그 객체의 서비스 함수(`service` → `doGet`/`doPost` 흐름)를 호출하도록 미리 매핑해둔다
4. `tomcat.start()`로 서버를 실제로 띄운다

```java
public class App {
    public static void main(String[] args) throws Exception {
        // 1. 임베디드 톰캣 객체 생성
        Tomcat tomcat = new Tomcat();
        tomcat.setPort(8080);
        tomcat.getConnector();

        // 2. Context 설정 (현재 디렉토리를 홈 디렉토리로)
        String docBase = new File(".").getAbsolutePath();
        Context context = tomcat.addContext("", docBase);

        // 3. 순수 자바 코드로 서블릿 등록 및 URL 매핑
        String servletName = "helloServlet";
        Tomcat.addServlet(context, servletName, new HelloServlet());
        context.addServletMappingDecoded("/hello", servletName);

        // 4. 서버 시작 및 대기
        tomcat.start();
        System.out.println("Server started on http://localhost:8080/hello");
        tomcat.getServer().await();
    }
}
```

```java
public class HelloServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        resp.setContentType("text/html; charset=UTF-8");
        PrintWriter out = resp.getWriter();
        out.println("<html><body>");
        out.println("<h1>Hello, Maven & Servlet!</h1>");
        out.println("<p>메이븐(Maven)을 통한 서블릿 실행 성공!</p>");
        out.println("</body></html>");
    }
}
```

사용자가 매핑된 URL(`/hello`)로 요청을 보내면, Tomcat이 그 요청을 `HelloServlet`으로 넘기고, `HelloServlet`의 서비스 흐름(`service` → `doGet`)이 실행되어 요청에 대한 응답이 만들어진다. **요청과 서블릿의 서비스 메소드가 URL 매핑을 통해 연결되어 있다**는 것이 이 전체 구조의 핵심이다.
