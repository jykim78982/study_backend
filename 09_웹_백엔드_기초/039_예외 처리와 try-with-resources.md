# 예외 처리와 try-with-resources

## 1. 오류의 세 종류 — 구문오류, 논리오류, 예외

코드에 문제가 생기는 경우는 크게 세 가지로 나뉜다.

| 종류 | 원인 | 특징 |
|---|---|---|
| **구문오류** | 문법 자체가 틀림 | 컴파일이 안 되므로 배포 자체가 불가능 — 치명적일 게 없다(애초에 실행이 안 됨) |
| **논리오류** | 구문은 완벽한데 개념이 틀림 | 예: 4명 평균을 구해야 하는데 3으로 나눔. 어디가 문제인지 한 땀 한 땀 찾아야 한다 |
| **예외** | 코드에는 문제가 없는데, 사용하는 사용자·장치·환경에 문제가 있음 | 유효하지 않은 값 입력, 인터넷 끊김, 파일 손상 등 |

**예외를 한마디로 정의하면 "입력(과 출력)에 대한 오류"다.** 코드 자체는 정상인데, 코드 바깥에서 예상하지 못한 상황이 들어오는 경우다.

- 파일을 읽으려는데 권한이 없다 / 파일이 없다 / 내용이 없다 / 포맷이 다르다
- 출력하려는데 디스크가 꽉 찼다 / 권한이 없다
- 인터넷이 갑자기 끊긴다, CD가 오염되어 안 읽힌다

이런 입력값 하나하나를 전부 `if`로 조건 처리하기는 현실적으로 어렵다 — 그래서 **try-catch**라는 별도의 처리 방식이 쓰인다.

## 2. 예외 검사는 누가 해야 하는가 — 애플리케이션이 아니라 API

파일을 읽거나 쓸 때 "권한이 있는지, 용량이 충분한지, 파일이 있는지"를 **애플리케이션마다 일일이 검사**하는 게 맞을까, 아니면 **API(라이브러리)가 그 역할을 맡는 게** 맞을까?

- 애플리케이션 단에서 검사하면, 그 코드를 쓰는 **모든 애플리케이션이 똑같은 검사 로직을 반복**해야 한다.
- 그래서 이런 검사는 **API가 하는 것이 맞다.** 대신 API가 문제를 발견했을 때, 이걸 호출한 프로그램에게 **어떻게 알려줄지**가 새로운 문제가 된다.

## 3. return으로는 예외를 알릴 수 없다

"함수가 `return`으로 알려주면 되지 않나?"라고 생각하기 쉽지만, `return`은 **원래 기능의 결과값을 돌려주기 위한 것**이지, 예외 상황을 전달하기 위한 통로가 아니다.

- 게다가 API 호출 중간에 **다른 라이브러리를 한 번 더 거치는 경우**가 많다. 이럴 때 `return` 값으로 문제를 표시하면, 그 값을 최종적으로 받는 게 **응용 프로그램이 아니라 중간 라이브러리**가 될 수 있다.
- **예외가 발생했을 때 어떻게 대응할지는 응용 프로그램이 결정해야 할 일**이다. 중간 라이브러리가 자기 마음대로 판단해서 조치해버리면 안 된다.

그래서 자바는 **"응용 프로그램에게까지 확실히 전달되는 보고 체계"**, 즉 예외(Exception) 메커니즘을 별도로 둔다.

## 4. 자바의 방식 — 숫자 코드가 아니라 객체를 던진다

예전 방식은 "1번 오류", "517번 오류"처럼 **숫자 식별자**를 전달하는 방식이었다 — 오류가 나면 "예외 코드표"를 뒤져서 무슨 뜻인지 찾아야 했다.

자바는 예외를 **숫자가 아니라 객체**로 표현한다.

```java
throw new 음수를_만드는_오류입니다();
```

- 숫자 대신 **클래스 이름 자체가 무슨 문제인지 말해준다** — 오류 메시지에 클래스 이름이 그대로 드러나기 때문에 직관적이다.
- 코드를 작성하는(써먹는) 입장에서도, 라이브러리가 어떤 예외를 던질 수 있는지 **빨간 줄(컴파일 경고)**로 미리 알려준다 — 라이브러리 자체가 "나는 이런 예외를 던질 수 있어"라고 구문적으로 표시해두기 때문이다.

## 5. 커스텀 예외 만들기 — 실습 코드

실습으로 만든 `except` 패키지에 실제로 이 개념을 그대로 구현한 예제가 있다.

```java
package except;

// RuntimeException - 강요하지 않음
// Exception - 코드 작성할 때 부터 강요함
public class 음수를_만드는_오류입니다 extends Exception {

}
```

```java
package except;

public class 영을_만드는_오류입니다 extends Exception {

}
```

- **예외를 위한 객체는 식별자를 만든 것**이지, 속성이나 메서드를 담기 위한 것이 목적이 아니다 — 그래서 클래스 몸통이 비어 있어도 충분하다.
- **`Exception`을 상속받아야만** `throw`로 던질 수 있는 자격이 생긴다. IDE에서 quick-fix로 그냥 평범한 클래스를 만들면 `throw` 자체가 안 된다.

이 예외를 실제로 던지는 쪽:

```java
public static int subtract(int a, int b) throws 음수를_만드는_오류입니다, 영을_만드는_오류입니다 {

    if (a < b)
        throw new 음수를_만드는_오류입니다();

    if (a == b)
        throw new 영을_만드는_오류입니다();

    return a - b;
}
```

- 메서드 시그니처의 `throws 음수를_만드는_오류입니다, 영을_만드는_오류입니다`는 "이 메서드는 이런 예외들을 던질 수 있다"고 **미리 알려주는 선언**이다. 이 메서드를 쓰는 쪽은 이 선언을 보고 처리 여부를 결정할 수 있다.

## 6. 던진 예외를 받는 쪽 — 다시 던지거나, 내가 처리하거나

예외를 던지는 메서드를 호출하는 쪽에게는 선택지가 두 가지다.

1. **다시 던지기**: 호출하는 함수 머리에도 `throws`를 붙여서, "나도 이 오류가 나면 그냥 위로 던질래"라고 미룬다.
2. **내가 처리하기**: `try-catch`로 감싸서 직접 대응한다.

**기준은 "내가 선택할 수 있는가"가 아니라 "내가 처리할 내용인가 아닌가"다.** 내가 책임질 수 있는 지점이면 그 자리에서 잡고, 아니면 위로 던진다.

```java
int result2 = 0;
try {
    result2 = Clac.subtract(10, 20);
} catch (음수를_만드는_오류입니다 e) {
    System.out.println("연산 오류 발생");
} catch (영을_만드는_오류입니다 e) {
    System.out.println("결과가 0이 나오는 오류 발샐");
} catch (Exception e) {

}
```

(마지막 출력 문구의 오타 `발샐`은 실습 코드 원문 그대로다.) 예외는 대부분 그 자리에서 완전히 해결할 수 없는 경우가 많아서, "잠시 후 다시 시도해주세요"처럼 **안내만 하고 끝나는 경우가 흔하다.**

**책임지지 않고 계속 위로 던지면 어떻게 될까?** 아무도 `catch`하지 않은 채 `main`까지 올라가면, 결국 **자바 실행 환경(JVM)이 받는다** — 그리고 처리하지 않은 예외를 발생시킨 애플리케이션을 그대로 종료시켜버린다. 이때는 이미 출력된 결과조차 하나도 안 보일 수 있다(예외가 발생한 지점 이후 코드는 실행되지 않으므로).

## 7. `Exception` vs `RuntimeException`

- **`Exception`(체크 예외)**: 코드를 작성하는 시점부터 컴파일러가 처리를 **강제**한다 — `try-catch`로 잡거나 `throws`로 던지거나, 둘 중 하나를 반드시 정해야 한다.
- **`RuntimeException`(언체크 예외)**: 컴파일 시점에는 아무것도 강요하지 않는다. 실제로 실행되다가 문제가 생기면 그때 예외로 나타난다.

라이브러리를 만드는 입장에서는, 사용하는 쪽이 이 예외의 존재를 **반드시 알았으면** 하는 경우 `Exception`을, 사용하는 쪽에 처리를 강요하고 싶지 않을 때는 `RuntimeException`을 선택하는 식으로 판단한다. 다만 체크 예외로 강제하면, 중간에 끼는 라이브러리들까지 전부 `throws`를 붙여야 해서 **강요가 과할 경우 오히려 쓰기 불편해질 수 있다**는 트레이드오프도 있다.

## 8. 예외를 여러 개 처리하는 방법들

하나의 서비스에서 여러 예외가 발생할 수 있을 때 선택지가 늘어난다.

1. **책임지지 않기** — 계속 위로 던진다.
2. **기존 `catch` 절에 조건 추가하기** — "이것 또는 이것이 발생하면 이렇게 처리" 식으로 묶는다.
3. **`catch`를 추가하기** — 다른 예외마다 다른 처리를 하고 싶을 때, `catch` 블록을 늘린다.
4. **묶어서 처리하기** — 세세하게 구분할 필요가 없다면, `catch (Exception e)`처럼 상위 타입 하나로 퉁칠 수 있다. `switch`문의 `default`처럼, 앞에서 세세하게 잡고 마지막에 남은 걸 이걸로 받는 식이다.

(중첩 `try-catch`도 문법적으로는 가능하지만, 코드가 복잡해져서 실무에서는 잘 쓰지 않는다.)

**`e.printStackTrace()`는 개발 중 디버깅용으로만 쓰는 게 좋다.** 호출 관계를 그대로 보여줘서 개발자가 원인을 추적하기엔 좋지만, 사용자나 외부인에게 이 내용이 그대로 노출되면 내부 구조가 드러나는 문제가 생긴다.

## 9. 예외를 다른 타입으로 바꿔서 던지기 — 계층 사이의 조율

리포지토리처럼 **최종 사용자가 아닌 중간 계층**은 예외를 놓고 고민이 생긴다 — 지금은 컨트롤러가 리포지토리를 직접 쓰지만, 나중에 그 사이에 계층이 더 늘어나면 예외를 계속 그대로 던지는 것도, 여기서 다 처리해버리는 것도 애매해진다.

`JdbcMenuRepository`의 이전 버전(현재는 주석 처리되어 실제로 실행되지는 않는 코드)은 이런 접근을 보여준다.

```java
// try {
//     Connection conn = DriverManager.getConnection(URL, UID, PWD);
//     Statement st = conn.createStatement();
//     ResultSet rs = st.executeQuery(sql);
//
//     // 닫아줘서 깔끔하게 정리하는 것이 좋다.
//     rs.close();
//     conn.close();
// } catch (SQLException e) {
//     throw new RuntimeException(e);
// }
```

- `SQLException`(체크 예외)을 잡아서, `RuntimeException`(언체크 예외)으로 **감싸 다시 던진다.**
- 이렇게 하면 상위(컨트롤러 등)에서 이 예외를 **반드시 처리해야 하는 의무가 사라진다** — 처리는 여전히 선택지로 남고, 결국 안 잡으면 예외는 그대로 위로 계속 전파된다.
- SQL 관련 예외는 세분화하면 타임아웃 예외 등 여러 하위 타입이 있는데, 결국 전부 `SQLException`의 자식이므로 `catch (SQLException e)` 하나로 부모 타입까지 통틀어 받을 수 있다.

## 10. try-with-resources — 자원을 자동으로 반납하기

`Connection`, `Statement`, `ResultSet` 같은 자원은 다 쓰고 나면 **빨리 반납해야 한다.** DB가 허용하는 연결 개수는 한정되어 있어서, 반납이 늦어지면 언젠가 자원이 바닥난다(누수).

- `Connection`은 연결 자체를 위한 버퍼를 정리하고, `ResultSet`은 fetch해온 데이터를 정리한다 — 그래서 둘 다 각각 `close()`가 필요하다.
- 문제는 매번 `close()`를 손으로 챙기는 게 번거롭고, 빼먹기도 쉽다는 것이다.

이걸 해결하는 문법이 **try-with-resources**다. `maven_servlet_project`의 `JdbcMenuRepository.findAll()`이 실제로 이 방식으로 정리되어 있다.

```java
try (Connection conn = DriverManager.getConnection(URL, UID, PWD);
        Statement st = conn.createStatement();
        ResultSet rs = st.executeQuery(sql)) {

    while (rs.next()) {
        menus.add(mapRow(rs));
    }
} catch (SQLException e) {
    e.printStackTrace();
}
```

- **소괄호 `( )` 안에서 선언한 자원들은, 뒤이어 나오는 중괄호 `{ }` 블록 안에서 그대로 쓸 수 있다.**
- 이 블록을 벗어나는 순간(정상 종료든 예외 발생이든), 소괄호 안에서 선언한 자원들이 **선언의 역순으로 자동 `close()`된다** — `rs` → `st` → `conn` 순서로 정리된다.
- 그래서 `close()` 호출 코드를 따로 작성할 필요가 없다. 이전 버전(9절)에서 `rs.close(); conn.close();`를 손으로 적어야 했던 것과 비교하면, 코드 영역이 훨씬 깔끔해진다.
- `findById(int id)`에서는 이 문법이 **중첩**으로도 쓰인다 — 바깥 `try (Connection conn; PreparedStatement pst)`, 안쪽 `try (ResultSet rs = pst.executeQuery())`처럼, 리소스를 얻는 시점이 다르면 try-with-resources도 단계별로 나눠 쓸 수 있다.

**주의할 점**: `catch` 블록에서 그냥 `e.printStackTrace()`로 조치를 끝내고 예외를 밖으로 전달하지 않으면, 상위(컨트롤러 등)는 오류가 났다는 사실 자체를 알 방법이 없다 — 오류가 났어도 빈 리스트가 정상 결과처럼 반환된다. 컨트롤러 단에서 오류를 감지해 사용자에게 안내하고 싶다면, 9절처럼 예외를 다시 던지는 방식과 함께 고려해야 한다.
